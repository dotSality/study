## 1. Цель и место в экосистеме репозитория

Создать самоучитель по ассемблеру x86-64, который:

1. Ведёт человека без формального бэкграунда от нуля до умения писать, собирать, запускать и отлаживать небольшие программы на ассемблере.
2. **Заканчивается плавным переходом к языку C**: последние главы показывают, что каждая конструкция C — это знакомая читателю ассемблерная схема, и передают эстафету самоучителю «C, затем Rust» (`books/c-and-rust-book/`).

Позиция в репозитории — третий самоучитель по общему Плану, наравне с `linear-algebra` (завершён) и `c-and-rust-book` (26 глав написаны, решения закрыты по гл. 18).

## 2. Функциональные требования

### FR-1. Структура — по Плану, без отклонений

Глава → части → параграфы + практика. Каждый параграф содержит все 6 элементов Плана §2.3 (определения; интуиция; 2–3 разобранных примера; связь с практикой; типичные ошибки; ссылки на источники). В каждой части 6–15 заданий с ID `Г{глава}.Ч{часть}.З{номер}` в **собственном пространстве имён** книги (коллизий с `c-and-rust-book` нет — разные файлы). Решения — только в `solutions/`, зеркально главам, с вариативностью подходов по Плану §6 п. 5.

Специфика дисциплины для рубрики «интуиция»: ASCII-схемы регистров, кадра стека и раскладки байтов в памяти — норма, как схемы памяти в C-книге.

### FR-2. Самодостаточность (следствие Р3)

Книга не предполагает у читателя знания C, двоичной системы, устройства памяти или установленного компилятора. Всё это вводится в первой главе своими словами. Пересечение с главой 1 C-книги допустимо и ожидаемо; дословного копирования быть не должно (Правило Плана §4.3).

### FR-3. Мост в C

Финальный блок книги обязан:

- показать `gcc -S` / `clang -S` на программах, которые читатель уже понимает на уровне инструкций;
- сопоставить конструкции C с уже пройденными ассемблерными схемами (переменная ↔ ячейка/регистр, функция ↔ `call` + кадр стека, массив ↔ базовый адрес + индексная адресация, указатель ↔ адрес, `struct` ↔ смещения полей, стек ↔ куча через `malloc`);
- объяснить формулу «C — переносимый ассемблер» уже как вывод, а не как лозунг;
- явно передать читателя в `books/c-and-rust-book/` с указанием, что в его главе 1 можно пролистать.

Сквозной пример главы-моста — **змейка из главы 8, переписанная на C**: читатель видит собственную программу, которую он собрал из инструкций вручную, в виде полутора экранов кода на C, и понимает, во что именно компилятор её развернёт. Это самая наглядная стыковка двух книг, какая здесь возможна.

### FR-4. Прикладная линия и финальная работа

Книга учит писать **программы**, а не фрагменты. Три уровня практики:

1. **Задания в каждой части** — 6–15 штук по Плану §2.2, распределение сложности 30/40/30. Верхние ~30% каждой части — не «допишите строку», а законченная работающая программа с заданными входом, выходом и ограничениями.
2. **Промежуточные мини-проекты** — задания, собирающие материал нескольких предыдущих глав в одну программу (по образцу проектных чекпоинтов части 12.Ч2 C-книги). Где именно их разместить — решается на этапе 2.
3. **Финальная глава — два проекта** (решение Р6), по одному в каждой части: виртуальная машина байт-кода (§4.1) и змейка в терминале (§4.2). Прямая аналогия с главой 25 C-книги, где итоговая глава тоже состоит из двух управляемых проектов.

Требования к каждому из проектов (сформулированы владельцем 2026-07-30):

- **не типовой и не базовый**: не «калькулятор», не «отсортируйте массив», не набор упражнений под общим заголовком;
- **составной**: обязан задействовать одновременно арифметику и флаги, ветвления и таблицы переходов, стек и соглашение о вызове, работу с памятью (массивы/строки/структуры/куча) и вызовы libc — то есть провалить его, зная только часть книги, невозможно;
- **доведённый до работающей программы**, а не до эскиза; собирается и запускается на обоих контурах (FR-5);
- построен как **управляемый проект с чекпоинтами**: проектные решения и их разбор вместо классических параграфов (допущение Плана §3 для проектных глав, уже применённое в главах 25–26 C-книги);
- задания части — ступени этого проекта плюс вариации/расширения.

**Почему проектов два, а не один.** Они закрывают разные половины материала и почти не пересекаются:

| | VM (Ч1) | Змейка (Ч2) |
|---|---|---|
| Побитовые операции, декодирование | сильно | слабо |
| Таблица переходов | диспетчер опкодов | диспетчер клавиш |
| Собственные кадры вызовов, рекурсия | сильно | нет |
| Индексная адресация `disp(base,index,scale)` | средне | сильно — двумерное поле |
| Структуры, куча, кольцевой буфер | сильно | сильно — тело змейки |
| Реальное время, взаимодействие с терминалом | нет | сильно |

Порядок частей: **сначала VM, потом змейка**. VM — прямое продолжение главы 7 (как на самом деле исполняются инструкции), а змейка даёт видимый играбельный финал и служит сквозным примером для главы-моста: «а теперь та же змейка на C».

Место в порядке глав: итоговая глава идёт **перед** главой-мостом в C. Так книга сначала закрывает ассемблер как самостоятельный навык, а мост остаётся последним и действительно «перетекает» в C.

### FR-5. Двухконтурная верификация кода

Правило Плана §4.4 и §2.3 операционного документа C-книги («некомпилирующийся фрагмент в текст не попадает») действуют без послаблений. Каждая программа прогоняется **на обоих доступных контурах**:

| Контур | Машина | Тулчейн | Формат объектника |
|---|---|---|---|
| **L** (Linux) | винда, WSL1 Ubuntu 24.04 | gcc 13.3 / clang 18.1.3, `as`, `objdump`, valgrind 3.22 | ELF |
| **M** (macOS) | Mac M3 | Apple clang 17 (`-arch x86_64` + Rosetta 2), `as`, `objdump`, `lldb` | Mach-O |

Оба контура используют одну и ту же System V AMD64 ABI: те же регистры, то же соглашение о вызове, то же выравнивание стека. Расхождения — только в оформлении, и они выносятся во врезки (см. NFR-2).

Проверено 2026-07-30 прямым прогоном на маке: `clang -arch x86_64` собирает и `-S`, и исполняемый файл, программа отрабатывает (Rosetta 2 установлена).

### FR-6. Инструменты как часть предмета

Ассемблер без инструментов не изучается. Книга обязана научить:

- собирать: `as`/`clang`/`gcc` из `.s`, раздельное ассемблирование + компоновка;
- дизассемблировать: `objdump -d` (на маке это LLVM-версия, на WSL — binutils);
- отлаживать пошагово с просмотром регистров и памяти — **основной отладчик `lldb`** (есть на маке из коробки; на WSL ставится `apt`). `gdb` на маке отсутствует и требует подписи сертификатом — в основной путь не берётся, упоминается как альтернатива для контура L;
- пользоваться Compiler Explorer как справочным стендом (после проверки его пригодности на этапе 1).

### FR-7. Операционный документ и трекер

По образцу `c-and-rust-book/C-and-Rust-learning.md` создаётся `books/asm-book/Asm-learning.md`: жёсткие правила захода, шаблон главы, шаблон решений, таблица-трекер по главам (Глава / Ревизия / Решения / Сверка), журнал окружения и договорённостей, шаблон промпта для запуска захода.

## 3. Нефункциональные требования и технические ограничения

### NFR-1. Никаких сырых системных вызовов

Номера и соглашения системных вызовов Linux и macOS различаются — программа с `syscall`-номерами не переносится между контурами. Поэтому весь ввод-вывод и работа с кучей идут **через libc** (`puts`, `printf`, `malloc`, `free`), а программа линкуется компилятором (`clang prog.s -o prog`), а не голым `ld`. Побочная выгода: читатель с первой главы вызывает те самые функции, которые потом увидит в C, — мост начинает строиться сразу.

### NFR-2. Каталог различий контуров — ведётся с первой главы

Известные расхождения L/M, которые придётся оформить как сквозную врезку (перечень уточняется на этапе 1):

- **имена символов**: Mach-O добавляет ведущее подчёркивание (`_main`), ELF — нет;
- **директивы секций**: `.text` / `.data` против `.section __TEXT,__text,...`;
- **адресация глобальных данных**: macOS требует позиционно-независимого кода, поэтому RIP-относительная адресация (`lea sym(%rip), %rax`) вводится **сразу как единственно правильная**, а не как продвинутая тема;
- **выравнивание стека**: SysV требует 16-байтового выравнивания `%rsp` в точке вызова; нарушение на маке валит libc-функции. Тема обязана появиться в главе про функции, а не в примечании.

Каждый пункт подтверждается прогоном на обоих контурах и попадает в текст только после этого.

### NFR-3. Синтаксис — AT&T (GAS) как основной (решение Р5)

Обоснование: `-S` у gcc и clang по умолчанию выдаёт именно его, а вся книга построена на чтении вывода компилятора; каноническая академическая литература по x86-64 (CS:APP / CMU 15-213) написана в нём же. Intel-синтаксис вводится отдельным параграфом как «второй диалект» — потому что справочники Intel/AMD и большинство дизассемблеров используют его, и читатель обязан уметь переключаться. Параграф про Intel-синтаксис нужен ещё и потому, что часть источников реестра (руководства Intel/AMD) написана в нём: без явного «переводчика» ссылки на них читатель применить не сможет.

### NFR-4. Язык и терминология

Русский; устоявшийся английский термин в скобках при первом употреблении (План §7). Арбитр терминологии для этой дисциплины определяется на этапе 1 — предположительно спецификация psABI и руководства Intel/AMD, по аналогии с ролью стандарта C5 в томе I C-книги.

### NFR-5. Объём и ритм работ

Ориентир по существующим книгам репозитория: глава ≈ 800–1500 строк, файл решений ≈ 1.3–2× главы. Один заход = одна глава или один файл решений, с коммитом и обновлением трекера (План §5). При 9 главах (§4) это ≈ 20–24 захода плюс 2 подготовительных (этапы 1–2) и 2 ревизионных. Глава 8 несёт два полноценных проекта — её текст и решения пишутся по одной части за заход (Плана §5 это прямо допускает для крупных глав), то есть 4 захода вместо двух.

Формат коммита — по образцу C-книги: `book(asm): ch NN <slug> — <chapter|revision|solutions|check>`, тело в 1–3 строки.

### 4.1. Итоговый проект Ч1: виртуальная машина байт-кода

Программа на ассемблере, которая читает файл байт-кода и исполняет его. Тематически замыкает книгу: читатель, разобравшийся, как процессор исполняет инструкции, пишет собственный процессор.

Предварительные чекпоинты проекта (уточняются на этапе 2):

1. формат байт-кода и чтение файла в память (`fopen`/`fread`/`malloc`);
2. стек операндов в куче — рост, границы, диагностика переполнения;
3. цикл выборки-декодирования-исполнения;
4. диспетчер по опкоду — таблица переходов;
5. арифметика, сравнения и условные переходы виртуальной машины;
6. `CALL`/`RET` внутри виртуальной машины — собственные кадры вызовов (двойная рекурсия: кадры VM живут в куче, кадры самого ассемблерного кода — на настоящем стеке);
7. ввод-вывод виртуальной машины через libc;
8. диагностика: режим трассировки исполнения, понятные сообщения об ошибках байт-кода.

Демонстрационная программа для VM — факториал или числа Фибоначчи через рекурсию: она проверяет чекпоинты 5–7 разом.

Покрытие материала книги (проверка требования «составная» из FR-4): гл. 2 — декодирование операндов и адресация, гл. 3 — арифметика и флаги, гл. 4 — таблица переходов, гл. 5 — соглашение о вызове и кадры, гл. 6 — куча, структуры и раскладка данных, гл. 7 — отладка собственной VM в отладчике. Ни одна глава не остаётся незадействованной.

#### Что VM требует от предыдущих глав

Единственное требование VM сверх уже запланированного материала — **загрузка байт-кода**: чтение файла в буфер. Куча, структуры, таблицы переходов, ABI и адресация в программе и так есть по существу дисциплины, а не ради проекта.

Причём в ассемблере чтение файла — не отдельная тема, а применение уже известного: это вызов библиотечных функций `fopen`/`fread`/`fclose` с указателями в аргументах. Как передавать указатель в функцию, читатель узнаёт в главе 5 (соглашение о вызове), как выделить буфер под данные — в главе 6 (куча). Дальше остаётся один параграф «вызов библиотечных функций, заполняющих буфер» в главе 6. Ни порядок глав, ни нарастание сложности это не нарушает (требование Плана §3 о монотонности выполняется).

Три способа закрыть вопрос, если и одного параграфа окажется много:

- **А (по умолчанию).** Параграф про `fopen`/`fread` в главе 6, рядом с кучей. Буфер в куче + функция, которая его наполняет, — естественная пара.
- **Б (без файлов вообще).** Байт-код кладётся в секцию статических данных или передаётся через аргументы командной строки. Тогда VM не нуждается в файловом вводе-выводе ни в каком виде, а загрузка из файла становится заданием-расширением в конце главы 8.
- **В.** Загрузка файла делается первым чекпоинтом самой главы 8 — как проектное решение с разбором, а не как теория предыдущей главы. Допустимо: главы-проекты по Плану §3 могут вводить прикладные детали по месту (так устроены главы 12 и 25 C-книги).

Требование порождено словом «составное», а не выбором VM: любое составное приложение откуда-то берёт вход.

### 4.2. Итоговый проект Ч2: змейка в терминале

Классическая змейка в текстовом терминале: поле, растущее тело, еда, столкновения, счёт, нарастающий темп.

Предварительные чекпоинты (уточняются на этапе 2):

1. поле как двумерный массив, отрисовка кадра ANSI-последовательностями через `printf`;
2. тело змейки как кольцевой буфер координат в куче — голова растёт, хвост отпускается;
3. ввод с клавиатуры без Enter, диспетчер клавиш таблицей переходов;
4. движение, столкновения со стеной и с собой, поедание и рост;
5. тайминг кадра и нарастание скорости; генерация еды через `rand`/`srand`;
6. таблица рекордов в файле, корректное восстановление терминала при выходе.

#### Ввод с клавиатуры: проверенное решение

Главный технический риск проекта — сырой (raw) ввод: чтение клавиши без Enter и без блокировки игрового цикла.

«Правильный» путь через `termios` для этой книги **непригоден**: структура `struct termios` и значения констант `ICANON`/`ECHO` различаются между Linux и macOS, а в ассемблере смещения полей и константы зашиваются числами — получилось бы два разных модуля ввода под два контура (нарушение духа FR-5).

Рабочая альтернатива, **проверена прогоном на контуре M 2026-07-30** (x86-64 через Rosetta, в настоящем псевдотерминале):

```
system("stty raw -echo min 0 time 1");   // сырой режим + чтение с таймаутом
int c = getchar();                        // 'w' -> 119; клавиши нет -> -1, без блокировки
system("stty sane");                      // восстановление терминала
```

Результат прогона: нажатие `w` пришло как `c=119` без Enter и без эха; на итерациях без нажатия `getchar` возвращал `-1`, не блокируя цикл. Это обычные вызовы libc, одинаковые на обеих системах, — развилки по контурам нет.

Два уточнения к тексту книги:

- тайминг кадра задавать **явно** (`nanosleep`/`usleep`), а не полагаться на таймаут `time 1`: так частота кадров управляется программой, а не настройками терминала;
- восстановление терминала (`stty sane`) обязано выполняться на всех путях выхода, включая аварийный, — это отдельный чекпоинт и хороший повод поговорить о дисциплине освобождения ресурсов (та же тема, что «кто выделил — тот освобождает» для кучи).

**Требует подтверждения на контуре L**: `stty` с параметрами `min`/`time` — POSIX, но по правилу Плана §4.4 в текст это войдёт только после реального прогона в WSL.

#### Как верифицируется интерактивная программа

Правило §2.3 «весь код прогоняется» для игры выполнимо: партия проигрывается скриптом, который подаёт нажатия в псевдотерминал и читает кадры вывода. Приём **проверен 2026-07-30** на контуре M (управляющий скрипт на `pty` подал нажатие и получил ожидаемый код клавиши). Это прямой аналог того, чем в C-книге проверяли Win32-главу (автоматизация через P/Invoke).

### 4.3. Открытый вопрос охвата

### 7.1. Действия, привязанные к конкретной машине

Часть проверок нельзя выполнить с мака. Они выписаны отдельно, чтобы не потерялись между сессиями; при создании `Asm-learning.md` (FR-7) этот список переносится в его журнал окружения.

**В первой же сессии на виндовой машине — запустить фоновой задачей (распоряжение владельца 2026-07-30):**

1. **Прогон сырого ввода в WSL** (закрывает В9). Проверить, что на контуре L ведёт себя так же, как подтверждено на маке:
   - `system("stty raw -echo min 0 time 1")` включает сырой режим без эха;
   - `getchar()` возвращает код клавиши без Enter, а при отсутствии нажатия — `-1`, не блокируя цикл;
   - `system("stty sane")` восстанавливает терминал.

   Прогонять в настоящем псевдотерминале (управляющий скрипт подаёт нажатия и читает вывод) — в обычном пайпе `stty` работать не будет: терминала нет. Результат — в журнал `Asm-learning.md` с датой и версиями.

   Проверочная программа (та же, что отработала на маке; на C, потому что проверяется механизм, а не ассемблерная его запись):

   ```c
   #include <stdio.h>
   #include <stdlib.h>
   int main(void) {
       system("stty raw -echo min 0 time 1");
       for (int i = 0; i < 10; i++) {
           int c = getchar();
           printf("tick %d c=%d\r\n", i, c);
           fflush(stdout);
       }
       system("stty sane");
       return 0;
   }
   ```

   Управляющий скрипт: открыть псевдотерминал (`pty.openpty()` в Python), запустить программу с этим pty на stdin/stdout, через ~0.3 с записать в мастер один байт `w`, дочитать вывод. Ожидаемый результат — строка с `c=119` (клавиша дошла без Enter и без эха) и строки с `c=-1` на итерациях без нажатия (чтение не заблокировалось). Вывод контура M для сверки: `tick 0 c=119`, далее `tick 1..9 c=-1`.

   *Если поведение разойдётся* — запасной путь — `termios` с двумя платформенными модулями ввода; это дороже и требует сверки раскладки `struct termios` и значений `ICANON`/`ECHO` по источникам отдельно для каждой системы. Решение принимает владелец.

2. Заодно зафиксировать в журнале актуальный состав тулчейна WSL (версии gcc/clang/binutils, наличие `lldb`) — записи в журнале C-книги датированы 2026-07-05 и могли устареть.

**Ограничение:** глава 8 (часть про змейку) не пишется, пока пункт 1 не закрыт.
