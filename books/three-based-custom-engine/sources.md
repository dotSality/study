## 1. Методическое решение: как подтверждаются утверждения об API three.js

Правило 5.2 книги требует зафиксировать это решение **в момент создания реестра**, иначе на ревизии получится системное нарушение п. 4.3 Плана («минимум два независимых источника на часть»).

**Проблема.** У API three.js независимого второго источника не существует физически: библиотека одна, и любое утверждение вида «`WebGLRenderer` делает X» восходит к одному и тому же проекту. Формальное требование «два независимых источника» здесь невыполнимо буквально.

**Решение — тройная связка, где источники подтверждают разные слои утверждения:**

| Слой утверждения | Чем подтверждается | Источники |
|---|---|---|
| **Почему так устроено**, какие есть альтернативы, чем платим | Теория рендеринга и архитектуры движков — независима от three.js | разделы 2 и 3 (T…, E…) |
| **Как это называется и что обещано** в зафиксированной версии | Первоисточник проекта: документация, руководство, исходный код | раздел 4 (J1–J5) |
| **Что фактически происходит** | Прогон по трёхслойной схеме верификации (раздел 4 книги) | стенд `harness/`, снимки `engine/` |

Утверждение считается подтверждённым, когда согласуются все три слоя. Теоретический слой обязателен: часть, опирающаяся только на документацию three.js и прогон, требования п. 4.3 Плана **не** закрывает.

**Границы независимости (проверено 2026-07-28, соблюдать буквально):**

1. **Документация (J1), руководство (J2), примеры (J4) и исходный код (J3) — это один источник**, а не четыре: все они принадлежат проекту three.js. Двумя источниками части они не являются ни в какой комбинации.
2. **J2 (three.js manual) и W7 (WebGL2 Fundamentals) не независимы друг от друга**: руководство three.js выросло из threejsfundamentals того же автора (Gregg Tavares, GitHub `greggman`), что и webgl2fundamentals. Вдвоём они требование «два источника» не закрывают.
3. При расхождении документации и фактического поведения **арбитр — исходный код (J3) плюс прогон**. Расхождение не замалчивается: оно попадает в текст главы как факт с указанием версии и даты проверки.
4. Каждое утверждение об API записывается вместе с версией, на которой оно проверено (**three 0.185.1**, зафиксирована решением этапа 0). Формулировки без версии запрещены.

## 9. Правила использования реестра (из Плана, разделы 4.3–4.4, и правил книги, раздел 5)

1. **Каждая часть каждой главы сверяется минимум с двумя независимыми источниками**; идентификаторы (T…, E…, J…, W…, G…, I…) проставляются в конце каждой части в блоке «Источники».
2. Для утверждений об API three.js действует тройная связка раздела 1 и её границы независимости. Комбинации, **не** закрывающие требование двух источников: любые два из J1–J5; пара J2 + W7.
3. Ресурсы с пометкой 🔶 не могут быть единственной опорой части — только вместе с академическим или официальным источником.
4. **Арбитры при расхождениях:** по графическому контуру — W1 (при необходимости W2/W3); по формату ассетов — G1; по фактическому поведению библиотеки — J3 плюс прогон.
5. Источник с пометкой 📗 сверяется по локальной копии из раздела 8. Источник с пометкой 📕 применить нельзя: часть закрывается открытыми источниками, а невозможность сверки фиксируется как открытый вопрос в `outline.md` — **но не заменяется знаниями агента по памяти** (п. 4.4 Плана).
6. **Ссылка на раздел книги проставляется по тому изданию, которое реально на руках** (раздел 8), а не по последнему вышедшему. Сейчас это касается T3 (сверка по 4-му изд., не по 5-му) и E5 (по 1-му изд., не по 2-му). Разделы между изданиями смещаются, и ссылка «по последнему» — та же догадка, что и утверждение по памяти.
7. Каждое утверждение об API записывается вместе с версией проверки (three 0.185.1). Утверждение без версии считается непроверенным.
8. Прямое копирование текста источников запрещено — только пересказ/синтез со ссылкой.
9. Найденный по ходу работы новый источник добавляется в реестр **до** использования, с проверкой по критериям п. 4.2 Плана и датой проверки.
