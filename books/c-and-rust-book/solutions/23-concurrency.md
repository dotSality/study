## Часть 23.1. Потоки и каналы

### Г23.Ч1.З1

**Условие.** Напишите программу: три потока, каждый печатает пять строк вида `поток N: строка K` с паузой `Duration::from_millis(5)` между строками; `main` дожидается всех через `join` и печатает `все закончили`. Приведите вывод одного прогона. Затем уберите все три `join` и объясните, почему вывод стал короче и почему у вас (или у соседа) он может оказаться и полным.

**Решение.** Три потока порождаются циклом, ручки складываются в вектор — так их не потерять (правило гигиены §23.1.1: «каждый `spawn` должен иметь план по своему `join`»). Файл `p1/t1_join.rs`:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let mut handles = Vec::new();

    for n in 1..=3 {
        handles.push(thread::spawn(move || {
            for k in 1..=5 {
                println!("поток {n}: строка {k}");
                thread::sleep(Duration::from_millis(5));
            }
        }));
    }

    for h in handles {
        h.join().unwrap(); // ждём каждого по очереди
    }
    println!("все закончили");
}
```

Две детали кода. Во-первых, `move` обязателен: замыкание захватывает `n`, а поток может пережить итерацию цикла (§23.1.2); `n` — Copy-тип, так что каждый поток получает свою копию номера — здесь это ровно то, что нужно (а в §23.2.2 та же копия окажется ловушкой). Во-вторых, ручки нельзя джойнить прямо в цикле порождения: `h.join()` внутри первого цикла означал бы «запустить поток и тут же дождаться его» — потоки выстроились бы в очередь, и никакого чередования мы бы не увидели. Поэтому два цикла: сначала все три `spawn`, потом все три `join`.

```
$ rustc --edition 2024 t1_join.rs
$ ./t1_join.exe
поток 1: строка 1
поток 2: строка 1
поток 3: строка 1
поток 2: строка 2
поток 1: строка 2
поток 3: строка 2
поток 3: строка 3
поток 1: строка 3
поток 2: строка 3
поток 1: строка 4
поток 2: строка 4
поток 3: строка 4
поток 2: строка 5
поток 1: строка 5
поток 3: строка 5

```

Это вывод **одного конкретного прогона**. Устойчивы в нём две вещи: строк ровно шестнадцать (3 × 5 + итог) и `все закончили` — последняя. Всё остальное — расписание ОС: у каждого потока строки идут по возрастанию `K` (это его собственный последовательный код), но чередование между потоками свободное. Чтобы не гадать, мы прогнали программу 60 раз и посмотрели на первые три строки:

```
     52 поток 1: строка 1|поток 2: строка 1|поток 3: строка 1|
      8 поток 1: строка 1|поток 3: строка 1|поток 2: строка 1|
```

*(Схема распределения, не вывод программы: строки прогона склеены через `|`, слева — сколько прогонов из 60 дали такой порядок.)* Даже на старте, где потоки создаются подряд, порядок первых строк не гарантирован — в восьми прогонах из шестидесяти третий поток обогнал второго.

**Теперь уберём `join`.** Файл `p1/t1_nojoin.rs` — та же программа без второго цикла:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    for n in 1..=3 {
        thread::spawn(move || {
            for k in 1..=5 {
                println!("поток {n}: строка {k}");
                thread::sleep(Duration::from_millis(5));
            }
        });
    }

    // join нет: main никого не ждёт
    println!("все закончили");
}
```

Три прогона подряд:

```
$ ./t1_nojoin.exe
все закончили
поток 3: строка 1
$ ./t1_nojoin.exe
все закончили
поток 1: строка 1
```

Из шестнадцати строк выживают одна-две. Распределение по 60 прогонам (сколько строк успело напечататься):

```
     24 1
     20 2
     16 3
```

*(Схема распределения, не вывод программы.)* Ни разу не больше трёх — и ни разу не полный вывод.

**Почему так.** `main` не выполняет никакой работы, кроме трёх `spawn` и одного `println!`, — на это уходят микросекунды, а каждый рабочий поток после первой же строки уходит спать на 5 мс. Когда `main` возвращается, **процесс завершается целиком, вместе со всеми недоработавшими потоками** (§23.1.1, R9): их не «убивают» персонально — просто исчезает процесс, в котором они жили. Отсюда и порядок: `все закончили` печатается **первой** строкой, хотя в тексте программы стоит последней.

Насколько «первой» — видно по третьему прогону: там вывод оборвался посреди строки, `поток ` без номера и без перевода строки. Процесс погас между двумя записями в буфер вывода — нагляднее доказательства «поток не дописывает начатое» не придумаешь.

**Почему у соседа вывод может оказаться полным?** Потому что никакой гарантии в обратную сторону тоже нет. Между `spawn` и завершением `main` планировщик волен отдать процессор рабочим потокам и не возвращать его главному сколь угодно долго: на загруженной машине, на одном ядре, при другом размере пауз — все пятнадцать строк успеют напечататься, и программа будет выглядеть «правильной». Это ровно та же ловушка, что «у меня UB не стреляет» (§13.1.3): отсутствие `join` — не ошибка, которая проявляется всегда, а ставка на расписание. Отсюда правило §23.1.1: пауза (`sleep`) — не синхронизация; единственный честный способ дождаться потока — `join`.

**Ответ.** С `join` печатается шестнадцать строк: пятнадцать рабочих в свободном чередовании (у каждого потока свои пять — по возрастанию) и `все закончили` последней; конкретный прогон приведён выше. Без `join` вывод сокращается до одной-трёх строк, а `все закончили` становится **первой**: `main` не ждёт никого, и завершение `main` завершает процесс со всеми потоками — они гибнут даже посреди недописанной строки. Полный вывод без `join` не запрещён: он получится, если планировщик отдаст потокам процессор раньше, чем `main` доберётся до своей последней строки, — но рассчитывать на это нельзя.

**Вариант 2 (область потоков вместо ручек).** `thread::scope` (§23.1.2) даёт тот же результат без единого `join`: область не выпускает выполнение за свою закрывающую скобку, пока живы её потоки. Файл `p1/t1_scope.rs`:

```rust
use std::thread;
use std::time::Duration;

fn main() {
    thread::scope(|s| {
        for n in 1..=3 {
            s.spawn(move || {
                for k in 1..=5 {
                    println!("поток {n}: строка {k}");
                    thread::sleep(Duration::from_millis(5));
                }
            });
        }
    }); // выход из области = все потоки завершены, ручки не нужны

    println!("все закончили");
}
```

```
$ ./t1_scope.exe

поток 2: строка 1
поток 3: строка 1
поток 2: строка 2
поток 3: строка 2
поток 1: строка 2
поток 1: строка 3
поток 3: строка 3
поток 2: строка 3
поток 1: строка 4
поток 3: строка 4
поток 2: строка 4
поток 2: строка 5
поток 1: строка 5
поток 3: строка 5

```

*Сравнение.* Вывод неотличим от основного решения (с точностью до расписания), но забыть дождаться потоков здесь **невозможно**: ожидание встроено в выход из области, а не в отдельный цикл, который можно случайно не написать. Плата — потоки не могут пережить область: вариант годится для «временной бригады внутри функции» и не годится для фоновых задач, живущих дольше вызвавшего кода (там нужны `spawn` + `move` + ручка). Второе отличие пригодится в задании З4: scoped-потоки умеют *заимствовать* окружение, обычные — нет.

### Г23.Ч1.З2

**Условие.** Напишите функцию `spawn_worker(n: u64) -> std::thread::JoinHandle<u64>`, запускающую поток, который возвращает сумму чисел от 1 до `n`. В `main` запустите двух рабочих (`n = 100` и `n = 1000`), получите оба результата через `join` и напечатайте их сумму (ожидается 505 550). Объясните: откуда `JoinHandle` знает тип `u64` и что вернёт `join`, если рабочий запаникует.

**Решение.** Функция запускает поток и **возвращает ручку, не дожидаясь его**, — в этом весь смысл: два рабочих должны считать одновременно, а не по очереди. Файл `p1/t2_worker.rs`:

```rust
use std::thread;

fn spawn_worker(n: u64) -> std::thread::JoinHandle<u64> {
    thread::spawn(move || {
        let mut sum: u64 = 0;
        for i in 1..=n {
            sum += i;
        }
        sum // тип этого выражения и задаёт JoinHandle<u64>
    })
}

fn main() {
    let w1 = spawn_worker(100);
    let w2 = spawn_worker(1000);

    let a = w1.join().unwrap();
    let b = w2.join().unwrap();

    println!("worker(100) = {a}");
    println!("worker(1000) = {b}");
    println!("total = {}", a + b);
}
```

`move` здесь обязателен по той же причине, что и в задании З1: замыкание захватывает параметр `n`, а поток переживёт вызов `spawn_worker` — `n` живёт в кадре этой функции, и заимствовать его нельзя (E0373, задание З4). Поскольку `u64` — Copy, «уносить» нечего: замыкание получает копию.

```
$ rustc --edition 2024 t2_worker.rs
$ ./t2_worker.exe
worker(100) = 5050
worker(1000) = 500500
total = 505550
```

Вывод **устойчив**: рабочие считают независимо, каждый — свою частную сумму, разделяемого состояния нет вовсе. Проверка арифметики: 100 · 101 / 2 = 5050, 1000 · 1001 / 2 = 500 500, сумма — 505 550, как и обещано условием.

**Откуда `JoinHandle` знает тип `u64`.** `thread::spawn` обобщён по типу возвращаемого значения замыкания (R9): его сигнатура — `fn spawn<F, T>(f: F) -> JoinHandle<T> where F: FnOnce() -> T + Send + 'static, T: Send + 'static`. Тело нашего замыкания заканчивается выражением `sum` типа `u64` — значит, `T = u64` выводится так же, как выводится тип любой обобщённой функции по её аргументу (§19.1.1), и `spawn` возвращает `JoinHandle<u64>`. Никаких `void *` и приведений, как в `pthread_create` (§13.1.4): тип результата приезжает вместе с ручкой и проверяется компилятором. `join()` возвращает не сам `u64`, а `Result<u64, Box<dyn Any + Send>>` — «значение или авария».

**Что вернёт `join`, если рабочий запаникует.** `Err`. Паника разматывает *свой* поток, а не программу (§23.1.1): `main` получает `Err` и решает, что делать. Файл `p1/t2_panic.rs` — рабочий, который паникует на `n = 0`:

```rust
use std::thread;

fn spawn_worker(n: u64) -> std::thread::JoinHandle<u64> {
    thread::spawn(move || {
        if n == 0 {
            panic!("worker got n = 0");
        }
        (1..=n).sum()
    })
}

fn main() {
    let good = spawn_worker(100);
    let bad = spawn_worker(0);

    match good.join() {
        Ok(v) => println!("good: Ok({v})"),
        Err(_) => println!("good: Err"),
    }
    match bad.join() {
        Ok(v) => println!("bad: Ok({v})"),
        Err(_) => println!("bad: Err (worker panicked, main is alive)"),
    }
}
```

```
$ ./t2_panic.exe

thread '<unnamed>' (28072) panicked at t2_panic.rs:6:13:
worker got n = 0
good: Ok(5050)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
bad: Err (worker panicked, main is alive)
```

Обратите внимание на порядок строк: сообщение паники ушло в **stderr**, а `good: Ok(5050)` — в **stdout**, и консоль смешала два потока вывода как получилось (в нашем прогоне `good:` оказалась посреди сообщения паники). Это не ошибка программы и не признак того, что паника случилась «позже», — просто два независимых канала вывода. Код завершения процесса — 0: для программы это штатный сценарий, авария рабочего доехала до `main` значением.

Полезная деталь: `Err` несёт полезный груз — `Box<dyn Any + Send>` с аргументом `panic!`. Разбирать его умеет `downcast_ref` (тема `Any` в курсе не вводилась), поэтому мы ограничиваемся `Err(_)`. Практический вывод из §23.1.1: молча игнорировать `Err` от `join` — значит терять аварии; минимальная дисциплина — `.unwrap()` на `join`, чтобы падение рабочего стало заметным и в главном потоке.

**Ответ.** Программа печатает `worker(100) = 5050`, `worker(1000) = 500500`, `total = 505550` — устойчиво, без разделяемого состояния. Тип `u64` в `JoinHandle<u64>` компилятор выводит из типа последнего выражения замыкания: `spawn` обобщён по нему (`F: FnOnce() -> T`, `T: Send + 'static`). Если рабочий паникует, `join()` возвращает `Err` с грузом-паникой; программа не падает (код завершения 0), сообщение паники печатается в stderr, а решение о судьбе аварии принимает `main`.

### Г23.Ч1.З3

**Условие.** Соберите конвейер «числа → канал → сумма»: поток шлёт в канал числа от 1 до 10, `main` суммирует их циклом `for` по получателю (ожидается 55). Затем добавьте второго отправителя (`tx.clone()`) с теми же числами — сумма должна стать 110, а программа не должна зависнуть. Покажите, где умирает каждый отправитель.

**Решение.** Начнём с одного отправителя. Файл `p1/t3_one.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        for i in 1..=10 {
            tx.send(i).unwrap();
        }
    }); // tx уехал в поток по move и умирает вместе с ним

    let mut total = 0;
    for n in rx {
        total += n;
    }
    println!("total = {total}");
}
```

```
$ rustc --edition 2024 t3_one.rs
$ ./t3_one.exe
total = 55
```

Цикл `for n in rx` крутится, пока канал открыт (§23.1.3). Закрывается канал, когда умирает **последний** отправитель; здесь отправитель один, он уехал в поток по `move` и уничтожается на закрывающей скобке замыкания — вместе с потоком. Поэтому цикл завершается сам, без счётчика полученных сообщений.

**Второй отправитель.** Клон `tx.clone()` — это «mp» в mpsc: второй конец той же трубы. Ключевой вопрос — где умирает каждый из них. Файл `p1/t3_two.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    let tx2 = tx.clone();
    thread::spawn(move || {
        for i in 1..=10 {
            tx.send(i).unwrap();
        }
    }); // отправитель 1 умирает здесь
    thread::spawn(move || {
        for i in 1..=10 {
            tx2.send(i).unwrap();
        }
    }); // отправитель 2 умирает здесь

    let mut total = 0;
    for n in rx {
        total += n;
    }
    println!("total = {total}");
}
```

Оригинал `tx` уезжает `move`-замыканием в первый поток, клон `tx2` — во второй. **В `main` не остаётся ни одного живого отправителя** — поэтому `drop(tx)` не нужен и программа не зависает. Три прогона подряд:

```
$ ./t3_two.exe
total = 110
$ ./t3_two.exe
total = 110
$ ./t3_two.exe
total = 110
```

Сумма **устойчива**: 55 + 55 = 110. Недетерминирован только *порядок* прихода сообщений (гарантирован лишь порядок сообщений одного отправителя, §23.1.3), а сложение от порядка не зависит.

**Где умирает каждый отправитель — по шагам.**

1. `mpsc::channel()` создаёт один `Sender` (`tx`) и один `Receiver` (`rx`).
2. `tx.clone()` создаёт второй `Sender` (`tx2`); теперь у канала два живых конца-отправителя.
3. Первый `thread::spawn(move || …)` забирает `tx` в замыкание; замыкание уничтожается вместе с потоком — отправитель № 1 мёртв.
4. Второй `spawn` так же забирает `tx2` — после завершения второго потока мёртв отправитель № 2.
5. Как только умер **последний** из двух, канал закрывается: очередной оборот `for n in rx` не находит ни сообщений, ни надежды на них — и цикл завершается.
6. `rx` умирает в конце `main`.

Типичная ошибка здесь — написать `let tx2 = tx.clone();` и *оставить оригинал в `main`*: два клона уедут в потоки и умрут, а оригинал доживёт до конца `main`, который в это время стоит в цикле `for n in rx`. Тогда программа напечатает все двадцать сообщений и повиснет навсегда — механизм разобран в задании З7.

**Ответ.** С одним отправителем `total = 55`, с двумя — `total = 110`; обе величины устойчивы, недетерминирован лишь порядок доставки. Программа не зависает, потому что оба отправителя (оригинал `tx` и клон `tx2`) уехали в потоки по `move` и умерли вместе с ними — в `main` не осталось ни одного живого конца-отправителя, канал закрылся, и цикл `for n in rx` завершился сам.

**Вариант 2 (клоны в цикле + `drop` оригинала + `sum`).** Если отправителей не два, а произвольное число, их удобнее раздавать в цикле — но тогда оригинал `tx` остаётся в `main` и его нужно хоронить руками. Сумму при этом можно не копить циклом: получатель — итератор (§21.2.3). Файл `p1/t3_iter.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for _ in 0..2 {
        let tx = tx.clone();
        thread::spawn(move || {
            for i in 1..=10 {
                tx.send(i).unwrap();
            }
        });
    }
    drop(tx); // оригинал в main тоже обязан умереть

    let total: i32 = rx.iter().sum(); // §21.2.3
    println!("total = {total}");
}
```

```
$ ./t3_iter.exe
total = 110
$ ./t3_iter.exe
total = 110
```

*Сравнение.* Тот же результат, но масштабируется: чтобы получить четырёх отправителей, достаточно поменять `0..2` на `0..4`, тогда как в основном решении пришлось бы дописывать переменные `tx3`, `tx4` и по блоку `spawn` на каждую. Плата — обязательный `drop(tx)`: в цикле клонируется оригинал, и он переживает цикл (в основном решении хоронить было нечего). Именно эта строка чаще всего и забывается — см. З7. Вторая разница косметическая: `rx.iter().sum()` короче цикла с аккумулятором, но требует явного типа (`let total: i32`), потому что выводить его `sum` больше неоткуда.

### Г23.Ч1.З4

**Условие.** «Спросите компилятор»: соберите пример 1 из §23.1.2 (поток печатает заимствованный вектор) без `move`. Почините двумя способами — `move` и `thread::scope` — и сформулируйте, чем решения отличаются по владению вектором после запуска потоков.

**(а) Что такое `'static` в note и почему `spawn` его требует.** `'static` — время жизни «до конца программы»: тип с ограничением `T: 'static` не содержит заимствований, которые могли бы кончиться раньше (§15.3 — времена жизни ссылок; арбитр — R7). Важно не спутать два разных `'static`: у *ссылки* `&'static str` это «указывает на данные, живущие вечно», у *типа* `T: 'static` — «внутри нет ссылок с более коротким временем жизни»; `Vec<i32>`, `String`, `i32` этому ограничению удовлетворяют, а `&'a Vec<i32>` — нет.

Сигнатура `spawn` (R9) требует `F: FnOnce() -> T + Send + 'static`. Причина прямая: `thread::spawn` не даёт **никаких** обещаний о том, когда поток завершится. Ручку `JoinHandle` можно выбросить, и поток продолжит работать «отвязанным»; он может пережить функцию, в которой родился, вместе со всеми её локальными переменными. Если бы замыкание держало ссылку на `v` — локальную переменную `main`, — оно бы указывало на освобождённый кадр стека. Это ровно то самое «висячее» заимствование, которое система времён жизни ловит с главы 15; здесь оно закрыто одним ограничением в сигнатуре.

**(б) Почему компилятор отказывает, хотя `join` стоит сразу за `spawn`.** Потому что он проверяет **типы, а не траектории выполнения**. Проверка ограничения `'static` происходит в точке вызова `spawn`, по типу аргумента: замыкание, захватившее `&Vec<i32>` с временем жизни кадра `main`, не удовлетворяет `'static` — и разговор окончен. Что там дальше по тексту программы (`join` на следующей строке, ранний `return`, паника) — анализа не касается: сигнатура одна для всех вызовов, и она обязана быть верной для худшего случая, а худший случай — «ручку выбросили, поток живёт своей жизнью». Та же логика уже встречалась дважды: E0382 в §15.1.2 («перемещение видно в типе, даже если ветка не выполнится») и E0499 в scoped-примере 3 §23.1.2.

Обратите внимание, где именно указан виновник: первая половина отчёта говорит про заимствование `v` в замыкании (`may outlive borrowed value 'v'`), а `note` называет требование — `function requires argument type to outlive 'static`. Это две половины одной претензии: замыкание заимствует, а `spawn` заимствований не принимает.

**Починка 1 — `move`.** Файл `p1/t4_move.rs`:

```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("вектор: {v:?}");
    });

    handle.join().unwrap();
    // здесь v уже недоступен: он уехал в замыкание
}
```

**Починка 2 — `thread::scope`.** Файл `p1/t4_scope.rs`:

```rust
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    thread::scope(|s| {
        s.spawn(|| {

        });
    });

    println!("v в main цел: {v:?} (длина {})", v.len());
}
```

Здесь `move` не нужен: `s.spawn` требует от замыкания не `'static`, а «жить не дольше области» — и область на выходе гарантированно дожидается всех своих потоков, так что заём не переживёт владельца.

**Чем починки отличаются по владению.** Проверим это отказом, а не рассуждением. Файл `p1/t4_after_move.rs` — версия с `move`, где `v` используется в `main` после запуска потока:

```rust
}
```

(б) Отказ выдаётся по типу аргумента в точке вызова, а не по фактической траектории: близость `join` компилятор не анализирует, ограничение обязано выполняться для худшего случая — «ручку выбросили, поток живёт дальше». Обе починки работают: `move` передаёт вектор в собственность потоку (после запуска `v` в `main` мёртв — E0382), `thread::scope` оставляет владение в `main` и лишь одалживает вектор на время области (после области `v` цел и доступен).

### Г23.Ч1.З5

**Условие.** Дана программа: `main` печатает `старт`, запускает поток A (печатает `A1`, `A2`), затем поток B (печатает `B1`), затем делает `a.join()`, печатает `середина`, делает `b.join()`, печатает `финиш`. Перечислите все строгие гарантии порядка строк в выводе (что *обязано* быть раньше чего) и приведите два разных легальных полных вывода. Проверьте прогонами.

**Решение.** Файл `p1/t5_order.rs` — программа из условия:

```rust
use std::thread;

fn main() {
    println!("старт");

    let a = thread::spawn(|| {
        println!("A1");
        println!("A2");
    });
    let b = thread::spawn(|| {
        println!("B1");
    });

    a.join().unwrap();
    println!("середина");
    b.join().unwrap();
    println!("финиш");
}
```

**Гарантии порядка.** Каждый поток исполняет свой код последовательно, а `join` — единственная точка, где один поток обязан дождаться другого. Отсюда полный список того, что *обязано* быть раньше чего:

1. `старт` — раньше всех остальных строк. Она печатается до обоих `spawn`, а до `spawn` потоков не существует.
2. `A1` раньше `A2` — это две строки подряд в одном потоке.
3. `A1` и `A2` раньше `середина`. Строка `середина` печатается после `a.join()`, а `join` возвращается только когда поток A завершился — то есть после обеих его строк.
4. `B1` раньше `финиш` — по той же причине через `b.join()`.
5. `середина` раньше `финиш` — обе печатает `main`, подряд.

И всё. Транзитивные следствия (например, `A1` раньше `финиш`) — не новые гарантии, а сумма перечисленных. Строка `B1` в этом списке почти свободна: она обязана быть только после `старт` и до `финиш` — про её отношение к `A1`, `A2` и `середина` не гарантировано **ничего**.

**Легальные полные выводы.** Из списка получается ровно четыре допустимых расстановки — они различаются местом `B1` среди прочих строк:

```
старт          старт          старт          старт
A1             A1             B1             A1
A2             B1             A1             A2
B1             A2             A2             середина
середина       середина       середина       B1
финиш          финиш          финиш          финиш
```

*(Схема, не вывод программы: четыре легальных исхода в столбик.)*

**Проверка прогонами.** Три прогона подряд дали один и тот же вывод — первый столбец:

```
$ rustc --edition 2024 t5_order.rs
$ ./t5_order.exe
старт
A1
A2
B1
середина
финиш
```

Это ожидаемо: поток A стартует первым и печатает две короткие строки быстрее, чем ОС успевает переключиться. Но «почти всегда» — не «всегда». Прогнали программу 300 раз и посчитали исходы:

```
    289 старт|A1|A2|B1|середина|финиш|
     10 старт|A1|B1|A2|середина|финиш|
      1 старт|A1|A2|середина|B1|финиш|
```

*(Схема распределения, не вывод программы: строки прогона склеены через `|`.)*

Три из четырёх предсказанных исходов встретились на живой машине, включая самый поучительный — последний. В нём `B1` напечаталась **после** `середина`: `main` успел дождаться потока A, напечатать `середина` — и только потом поток B добрался до своей единственной строки. Именно этот случай ломает интуицию «раз `spawn` для B стоит раньше `a.join()`, значит, B напечатается раньше `середина`»: `spawn` лишь *создаёт* поток, а когда тот получит процессор — решает ОС.

Четвёртый исход (`B1` первой, до `A1`) за 300 прогонов не выпал, но он законен: поток B может получить процессор раньше потока A. Отсутствие исхода в выборке — не доказательство его невозможности; ровно так же в §13.1.3 «у меня UB не стреляет» не означало отсутствия UB.

**Ответ.** Строгих гарантий пять: `старт` — первая; `A1` раньше `A2`; `A1` и `A2` раньше `середина` (через `a.join()`); `B1` раньше `финиш` (через `b.join()`); `середина` раньше `финиш`. Про положение `B1` относительно `A1`, `A2` и `середина` не гарантировано ничего. Два разных легальных полных вывода — `старт, A1, A2, B1, середина, финиш` (289 прогонов из 300) и `старт, A1, A2, середина, B1, финиш` (1 прогон из 300); встретился и третий — `старт, A1, B1, A2, середина, финиш` (10 из 300).

### Г23.Ч1.З6

**Условие.** Объясните ошибку примера 2 из §23.1.3 (печать `message` после `send`): почему `send` забирает владение и от какой многопоточной беды это спасает (свяжите с тремя условиями гонки данных из §13.1.4). Почините двумя способами: (а) клон перед отправкой; (б) перестановка печати до `send` — и объясните, почему в (б) снимок значения честнее, чем в (а).

**Решение.** Файл `p1/t6_bad.rs` — пример 2 §23.1.3 дословно:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let message = String::from("данные");
        tx.send(message).unwrap();
        println!("отправлено: {message}"); // ⛔ значение уже уехало
    });

    println!("получено: {}", rx.recv().unwrap());
}
```

```
$ rustc --edition 2024 t6_bad.rs
error[E0382]: borrow of moved value: `message`
  --> t6_bad.rs:10:32
   |
 8 |         let message = String::from("данные");
   |             ------- move occurs because `message` has type `String`, which does not implement the `Copy` trait
 9 |         tx.send(message).unwrap();
   |                 ------- value moved here
10 |         println!("отправлено: {message}"); // ⛔ значение уже уехало
   |                                ^^^^^^^ value borrowed here after move
```

**Почему `send` забирает владение.** Никакой многопоточной магии: `send` — обычная функция, принимающая параметр **по значению** (`fn send(&self, t: T) -> Result<(), SendError<T>>`, R9). Передача не-Copy-значения по значению — это перемещение (§15.1.2): владение `message` переехало в аргумент, а оттуда — в очередь канала. Дальше строка `println!` пытается *заимствовать* переменную, у которой больше нет содержимого, — E0382, та же ошибка, что при передаче `String` в обычную функцию в главе 15. Компилятору неважно, что на другом конце трубы поток: правило одно на все перемещения.

**От какой беды это спасает.** Представим, что заём после `send` разрешён. Тогда `message` одновременно доступна двум потокам: отправителю (через переменную) и получателю (через очередь) — а получатель волен не только читать её, но и изменять, ведь он теперь хозяин. Складываются все три условия гонки данных из §13.1.4:

| Условие гонки (§13.1.4) | Как складывалось бы после «разрешённого» заимствования |
|---|---|
| два потока обращаются к одной памяти | буфер строки в куче виден и отправителю (заём), и получателю (владение) |
| хотя бы один доступ — запись | получатель может дописать строку, отсортировать вектор, освободить буфер |
| нет синхронизации между доступами | канал синхронизирует *передачу сообщения*, а не последующее чтение через старую переменную |

В C аналогичный код (`queue_push(q, ptr); printf("%s", ptr);`) собирается молча, и дисциплина «после передачи в очередь указателем не пользоваться» держится на комментариях — как владение в §7.1.2. Здесь она держится на системе типов: **пока сообщение едет и после доставки у него ровно один хозяин** — читать и писать его одновременно попросту некому. Это и есть «передача вместо разделения»: гонка невозможна не потому, что доступ синхронизирован, а потому, что второго участника не существует.

**Починка (а) — клон перед отправкой.** Файл `p1/t6_clone.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let message = String::from("данные");
        let copy = message.clone(); // своя копия остаётся в потоке
        tx.send(message).unwrap();
        println!("отправлено: {copy}");
    });

    println!("получено: {}", rx.recv().unwrap());
}
```

```
$ ./t6_clone.exe
получено: данные
отправлено: данные
```

(Порядок этих двух строк недетерминирован: их печатают разные потоки. В нашем прогоне `main` успел напечатать `получено:` первым.)

**Починка (б) — печать до отправки.** Файл `p1/t6_before.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let message = String::from("данные");
        println!("отправляю: {message}"); // печать до send — заём, не вынос
        tx.send(message).unwrap();
    });

    println!("получено: {}", rx.recv().unwrap());
}
```

```
$ ./t6_before.exe
отправляю: данные
получено: данные
```

Здесь порядок строк, наоборот, гарантирован: `отправляю:` печатается до `send`, а `получено:` — после `recv`, который ждёт сообщения.

**Почему в (б) снимок значения честнее.** В варианте (а) поток печатает **копию, сделанную до отправки**, — и утверждает этим, что «отправлено вот это». Пока строка неизменяема, копия и оригинал совпадают, но стоит вставить между `clone` и `send` хоть одну строчку правки (`message.push_str("!")`) — и печать станет ложью, причём молчаливой: компилятор не связывает копию с оригиналом никакими обязательствами. Вариант (а) вдобавок платит настоящей аллокацией и копированием буфера — ради строки диагностики.

Вариант (б) печатает **ту самую переменную, которая через строку уедет в канал**: между печатью и отправкой ничего не происходит, и снимок гарантированно соответствует отправленному. Заимствование для `println!` тут законно — владение ещё не тронуто, вынос случится позже. Общее правило: **всё, что нужно знать о значении, узнавайте до передачи владения**; клон — инструмент на случай, когда данные нужны обеим сторонам *для работы*, а не для отчёта.

**Ответ.** `send` принимает аргумент по значению, поэтому владение `message` переезжает в канал (§15.1.2), а последующий `println!` — заимствование мёртвой переменной: E0382. Спасает это от гонки данных: если бы отправитель сохранял доступ к отправленному, у одного буфера оказалось бы два потока-пользователя, из которых как минимум один (получатель-владелец) может писать, без всякой синхронизации, — все три условия §13.1.4 налицо. Обе починки работают, но (б) честнее: печатается сам объект непосредственно перед отправкой, тогда как (а) печатает копию, которая может разойтись с оригиналом при любой правке между `clone` и `send`, да ещё и оплачивает лишнюю аллокацию.

### Г23.Ч1.З7

**Условие.** Программа из примера 3 §23.1.3 без строки `drop(tx)` печатает все шесть сообщений и зависает. Объясните механизм: кто кого ждёт и почему это не deadlock двух замков, а взаимное ожидание «цикл ждёт закрытия канала — канал ждёт смерти оригинала `tx` — оригинал умрёт после цикла». Предложите две починки, не считая `drop`: перенос создания `tx` внутрь области видимости и приём «получить ровно N сообщений» (`rx.iter().take(6)` — §21.2.2).

**Решение.** Файл `p1/t7_hang.rs` — пример 3 §23.1.3 без строки `drop(tx)`:

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    for worker in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            for step in 1..=2 {
                tx.send(format!("рабочий {worker}: шаг {step}")).unwrap();
                thread::sleep(Duration::from_millis(10));
            }
        });
    }
    // drop(tx) забыт: оригинал жив до конца main

    for received in rx {
        println!("{received}");
    }
    println!("этой строки вы не увидите");
}
```

```
$ rustc --edition 2024 t7_hang.rs
$ timeout 5 ./t7_hang.exe
рабочий 0: шаг 1
рабочий 1: шаг 1
рабочий 2: шаг 1
рабочий 2: шаг 2
рабочий 1: шаг 2
рабочий 0: шаг 2
--- run exit=124 ---
```

Все шесть сообщений получены (порядок между рабочими недетерминирован), последняя строка не напечатана, процесс снят по таймауту — код 124 от `timeout`.

**Механизм — кто кого ждёт.** Разберём состав жильцов канала. `mpsc::channel()` создал одного `Sender` (`tx` в `main`) и одного `Receiver`. Цикл создал три клона, каждый уехал в свой поток и умер вместе с ним. Итого через ~20 мс живых отправителей остаётся ровно один — **оригинал `tx` в `main`**. А цикл `for received in rx` завершается только при закрытии канала, то есть при смерти **последнего** отправителя (§23.1.3). Дальше замыкается круг:

```
цикл `for … in rx`  ждёт  закрытия канала
        канал       ждёт  смерти последнего Sender — оригинала tx
      оригинал tx   ждёт  конца main (это его область видимости)
         main       ждёт  завершения цикла `for … in rx`
```

*(Схема ожидания, не вывод программы.)*

**Почему это не deadlock двух замков.** Классический deadlock (пример 1 §23.2.4) — это два *потока*, каждый держит ресурс и ждёт чужой; там участвуют минимум две нити исполнения и минимум два замка. Здесь же поток **один** — главный, и он ждёт события, наступление которого зависит от его же собственного продвижения по коду: `tx` умрёт на закрывающей скобке `main`, до которой выполнение не дойдёт, пока не закончится цикл. Ресурс никем не удерживается «назло»: программа стоит, потому что условие выхода из цикла может наступить только *после* цикла. Ближайший родственник этой ошибки — не deadlock, а самоблокировка из примера 3 §23.2.1, где поток ждёт замок, ключ от которого лежит у него в кармане.

Полезно заметить и то, чего в этой ситуации **нет**: рабочие потоки давно мертвы, никто ничего не держит, гонки данных не было ни секунды — программа корректна с точки зрения типов и просто никогда не закончится. Компилятор такое не ловит (§23.2.4: «компилируется — значит, нет гонок данных», не более).

**Починка 1 — оригинал в своей области видимости.** Если `tx` живёт в блоке, он умирает на закрывающей скобке блока, задолго до цикла. Файл `p1/t7_scoped_tx.rs`:

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    {
        let tx = tx; // оригинал переехал в блок и умрёт на его закрывающей скобке
        for worker in 0..3 {
            let tx = tx.clone();
            thread::spawn(move || {
                for step in 1..=2 {
                    tx.send(format!("рабочий {worker}: шаг {step}")).unwrap();
                    thread::sleep(Duration::from_millis(10));
                }
            });
        }
    } // здесь оригинал tx мёртв

    for received in rx {
        println!("{received}");
    }
    println!("канал закрыт");
}
```

```
$ ./t7_scoped_tx.exe
рабочий 0: шаг 1
рабочий 1: шаг 1
рабочий 2: шаг 1
рабочий 1: шаг 2
рабочий 2: шаг 2
рабочий 0: шаг 2
канал закрыт
```

Строка `let tx = tx;` — не тавтология: она перемещает оригинал в переменную с областью видимости блока (§15.1.2), и уничтожение происходит по правилу конца области, а не по явному вызову. Приём удобен тем, что защищает от повторения ошибки при правках: чтобы «забыть» похоронить отправителя, нужно теперь сломать структуру блока.

**Починка 2 — получить ровно N сообщений.** Если число сообщений известно заранее, закрытие канала вообще не нужно как условие выхода: берём столько, сколько ждём (`iter().take(6)`, §21.2.2). Файл `p1/t7_take.rs`:

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    for worker in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            for step in 1..=2 {
                tx.send(format!("рабочий {worker}: шаг {step}")).unwrap();
                thread::sleep(Duration::from_millis(10));
            }
        });
    }
    // drop(tx) не нужен: берём ровно 6 сообщений и не ждём закрытия канала

    for received in rx.iter().take(6) {
        println!("{received}");
    }
    println!("шесть сообщений получены");
}
```

```
$ ./t7_take.exe
рабочий 0: шаг 1
рабочий 1: шаг 1
рабочий 2: шаг 1
рабочий 2: шаг 2
рабочий 1: шаг 2
рабочий 0: шаг 2
шесть сообщений получены
```

Оригинал `tx` здесь по-прежнему жив до конца `main` — и это больше не мешает: `take(6)` завершает итерацию по счётчику, не спрашивая канал, будут ли ещё сообщения. Цена — жёсткая зависимость от числа: пошлют пять — программа зависнет на шестом `recv`; пошлют семь — седьмое молча пропадёт вместе с получателем. Поэтому приём хорош там, где количество сообщений — часть протокола (ровно один итог от каждого из N рабочих), и плох там, где рабочие шлют «сколько получится».

**Ответ.** Программа печатает все шесть сообщений и зависает: цикл `for received in rx` ждёт закрытия канала, канал ждёт смерти последнего отправителя, а последний живой отправитель — это оригинал `tx`, который умрёт только в конце `main`, куда выполнение не попадёт, пока не завершится цикл. Это не deadlock двух замков (там два потока и два удерживаемых ресурса), а самоблокировка одного потока на условии, которое зависит от его же продвижения. Починки без `drop`: (1) поместить оригинал `tx` в блок — он умрёт на закрывающей скобке блока (`p1/t7_scoped_tx.rs`); (2) читать фиксированное число сообщений — `rx.iter().take(6)` (`p1/t7_take.rs`), тогда закрытие канала перестаёт быть условием выхода.

### Г23.Ч1.З8

**Условие.** Параллельная сумма. В cargo-пакете напишите `sequential_sum(data: &[i64]) -> i64` и `parallel_sum(data: &[i64]) -> i64`: вторая делит срез `split_at` пополам, каждый из двух scoped-потоков суммирует свою половину и шлёт итог в канал, результат — сумма двух сообщений. Тесты: совпадение с последовательной суммой на `1..=10_000` (и равенство 50 005 000), пустой срез, один элемент, отрицательные числа. Все зелёные; приведите строку `test result`.

**Решение.** Пакет создан командой `cargo new --lib psum` (§20.2.1). Здесь просится именно `thread::scope`: половины среза — заимствования чужого вектора, и «унести» их потоку нельзя, а область гарантированно дождётся обоих потоков (§23.1.2). Файл `p1/psum/src/lib.rs`:

```rust
use std::sync::mpsc;
use std::thread;

/// Последовательная сумма: эталон для сравнения.
pub fn sequential_sum(data: &[i64]) -> i64 {
    let mut total = 0;
    for x in data {
        total += x;
    }
    total
}

/// Параллельная сумма: две половины, два scoped-потока, итоги — через канал.
pub fn parallel_sum(data: &[i64]) -> i64 {
    let (left, right) = data.split_at(data.len() / 2);

    thread::scope(|s| {
        let (tx, rx) = mpsc::channel();
        let tx2 = tx.clone();

        s.spawn(move || {
            let part: i64 = left.iter().sum();
            tx.send(part).unwrap();
        });
        s.spawn(move || {
            let part: i64 = right.iter().sum();
            tx2.send(part).unwrap();
        });

        // оба сообщения обязательно придут: область дождётся обоих потоков
        rx.recv().unwrap() + rx.recv().unwrap()
    })
}
```

Разбор устройства.

- **`split_at(mid)`** (R9) отдаёт две половины среза без копирования данных; при нечётной длине левая короче правой на элемент — на сумму это не влияет.
- **`move` у scoped-замыканий** относится только к `tx`/`tx2`: отправителей нужно унести (иначе они останутся жить в кадре `parallel_sum` и канал не закроется), а срезы `left`/`right` захватываются по ссылке — это и есть то, ради чего взят `scope`.
- **`rx.recv().unwrap() + rx.recv().unwrap()`** — два блокирующих приёма. Зависнуть они не могут: область не выпустит выполнение наружу, пока оба потока не завершатся, а каждый из них перед завершением обязательно шлёт ровно одно сообщение. Порядок слагаемых при этом произволен — от него сумма не зависит.
- **Пустой срез** тоже отрабатывает: `split_at(0)` даёт две пустые половины, каждый поток шлёт `0`.

Тесты (тот же файл, ниже):

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn matches_sequential_on_10_000() {
        let data: Vec<i64> = (1..=10_000).collect();
        assert_eq!(parallel_sum(&data), sequential_sum(&data));
        assert_eq!(parallel_sum(&data), 50_005_000);
    }

    #[test]
    fn empty_slice() {
        assert_eq!(parallel_sum(&[]), 0);
    }

    #[test]
    fn single_element() {
        assert_eq!(parallel_sum(&[42]), 42);
    }

    #[test]
    fn negative_numbers() {
        let data = [-5, 3, -10, 7, -1];
        assert_eq!(parallel_sum(&data), sequential_sum(&data));
        assert_eq!(parallel_sum(&data), -6);
    }
}
```

Контрольное число 50 005 000 — это 10 000 · 10 001 / 2; тест на отрицательных числах проверяет заодно, что мы не перепутали половины местами (сумма −6 у обеих версий).

```

test tests::empty_slice ... ok
test tests::single_element ... ok
test tests::negative_numbers ... ok
test tests::matches_sequential_on_10_000 ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Порядок строк `test … ok` меняется от прогона к прогону: прогонщик исполняет тесты в отдельных потоках (§20.2.2) — теперь это не магия, а ровно то, чем мы занимаемся всю главу. Устойчива строка `test result: ok. 4 passed; 0 failed`.

**Ответ.** `sequential_sum` складывает срез циклом; `parallel_sum` делит его `split_at(len/2)`, запускает два scoped-потока (каждый суммирует свою половину и шлёт итог в канал `mpsc`) и возвращает сумму двух принятых сообщений. Все четыре теста зелёные: `test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out`. Зависание невозможно, потому что область дожидается обоих потоков, а каждый из них шлёт ровно одно сообщение перед смертью.

**Вариант 2 (итоги через `join`, без канала).** Scoped-поток умеет возвращать значение — ручка `s.spawn(...)` даёт `join()` с типизированным результатом, как обычный `spawn` (§23.1.1). Тогда канал не нужен вовсе. Файл `p1/psum_join/src/lib.rs`:

```rust
/// Тот же расчёт, но итоги возвращаются значением из join — без канала.
pub fn parallel_sum(data: &[i64]) -> i64 {
    let (left, right) = data.split_at(data.len() / 2);

    thread::scope(|s| {
        let h1 = s.spawn(|| left.iter().sum::<i64>());
        let h2 = s.spawn(|| right.iter().sum::<i64>());
        h1.join().unwrap() + h2.join().unwrap()
    })
}
```

Тесты — те же четыре, дословно; результат тот же:

```
$ cargo test
running 4 tests
test tests::empty_slice ... ok
test tests::single_element ... ok
test tests::negative_numbers ... ok
test tests::matches_sequential_on_10_000 ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

*Сравнение.* Версия с `join` короче на семь строк, не требует `move` (захватывать нечего — только срезы) и не создаёт очередь; ошибиться в ней негде: сколько потоков — столько и результатов, компилятор следит за типами. Версия с каналом выигрывает, когда сообщений **не по одному на поток** или когда их число заранее неизвестно: канал позволяет обрабатывать итоги по мере поступления, а `join` — только в том порядке, в каком написаны ручки (`h1.join()` ждёт первый поток, даже если второй давно закончил). Для задачи «две половины, два числа» канал — избыточная механика, зато он честно показывает приём, который в §23.1.3 назван починкой `race.c`: частные итоги плюс труба.

### Г23.Ч1.З9

**Условие.** Конвейер из двух каналов: `main` шлёт задания-числа `[3, 5, 7, 11]` в канал заданий; поток-обработчик берёт их циклом `for`, возводит в квадрат и шлёт строки вида `3^2 = 9` в канал результатов; `main` печатает результаты и завершает конвейер. Программа должна завершаться сама: продумайте, где умирает каждый из четырёх концов двух каналов (напишите это комментариями в коде).

**Решение.** Два канала — две трубы навстречу друг другу: `main` → обработчик (задания) и обработчик → `main` (результаты). У каждой трубы два конца, всего четыре; программа завершается сама тогда и только тогда, когда каждый из четырёх умирает в известном месте. Файл `p1/t9_pipe.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (task_tx, task_rx) = mpsc::channel::<u64>();
    let (res_tx, res_rx) = mpsc::channel::<String>();

    thread::spawn(move || {
        for n in task_rx {
            res_tx.send(format!("{n}^2 = {}", n * n)).unwrap();
        }
        // конец 3: res_tx умирает здесь, вместе с замыканием потока,
        // и закрывает канал результатов
    }); // конец 2: task_rx уехал в поток и умирает вместе с ним

    for n in [3, 5, 7, 11] {
        task_tx.send(n).unwrap();
    }
    drop(task_tx); // конец 1: канал заданий закрыт — цикл в потоке завершится

    for line in res_rx {
        println!("{line}");
    }
    // конец 4: res_rx умирает в конце main
    println!("конвейер завершён");
}
```

```
$ rustc --edition 2024 t9_pipe.rs
$ ./t9_pipe.exe
3^2 = 9
5^2 = 25
7^2 = 49
11^2 = 121
конвейер завершён
```

Вывод **полностью детерминирован**, и это не случайность: отправитель заданий один (`main`), обработчик один, значит, порядок сообщений в каждой трубе — порядок отправки (§23.1.3). Недетерминизм появился бы, добавь мы второй обработчик.

**Домино завершения — по шагам.**

1. `main` отправляет четыре задания и выполняет `drop(task_tx)`. Это **конец 1**: единственный отправитель заданий мёртв, канал заданий закрыт.
2. Обработчик дочитывает очередь (сообщения, отправленные до закрытия, никуда не пропадают — они уже в буфере), после чего цикл `for n in task_rx` завершается: канал закрыт и пуст.
3. Замыкание потока заканчивается — уничтожаются его захваты: `task_rx` (**конец 2**) и `res_tx` (**конец 3**). Смерть `res_tx` закрывает канал результатов: других отправителей у него нет.
4. Цикл `for line in res_rx` в `main` дочитывает четыре результата и завершается — канал закрыт.
5. `res_rx` уничтожается в конце `main` (**конец 4**).

Ключевая асимметрия, которую стоит удержать в голове: `drop(task_tx)` пишется руками, потому что оригинал отправителя остаётся в `main`; остальные три конца хоронятся сами — они уехали в поток или дожили до конца своей области. Забыть `drop(task_tx)` — получить в точности зависание из задания З7, только этажом ниже: цикл обработчика никогда не кончится, `res_tx` никогда не умрёт, и `main` навсегда останется в цикле по `res_rx`.

**Проверка на типах.** Обратите внимание на явные параметры `mpsc::channel::<u64>()` и `mpsc::channel::<String>()`. Без них компилятор тоже справится (типы выводятся из первого `send`), но с ними ошибка «перепутал трубы» — `res_tx.send(n)` вместо `task_tx.send(n)` — становится ошибкой компиляции с внятным сообщением о несовпадении типов, а не логической путаницей.

**Ответ.** Программа печатает `3^2 = 9`, `5^2 = 25`, `7^2 = 49`, `11^2 = 121`, `конвейер завершён` — детерминированно, поскольку в каждой трубе ровно один отправитель. Четыре конца умирают так: `task_tx` — явным `drop` в `main` после отправки заданий; `task_rx` и `res_tx` — вместе с замыканием потока-обработчика (первый закрывает цикл обработчика, смерть второго закрывает канал результатов); `res_rx` — в конце `main`. Смерть каждого конца запускает следующее звено: закрытый канал заданий завершает цикл обработчика, конец обработчика закрывает канал результатов, закрытый канал результатов завершает цикл в `main`.

### Г23.Ч1.З10

**Условие.** «Кто первый». Три потока-«бегуна» с паузами 300, 50 и 150 мс шлют своё имя в общий канал; `main` берёт **одно** первое сообщение (`recv`), объявляет победителя и уничтожает получателя (`drop(rx)`). Опоздавшие «бегуны» получат `Err` от `send` — обработайте его тихим выходом (без паники) и докажите прогоном, что программа доживает до финальной печати без аварий (в конце `main` подождите 500 мс, чтобы опоздавшие успели «добежать»).

**Решение.** Здесь `Err` от `send` — не авария, а штатный сценарий: «победитель определён, остальных не слушают» (§23.1.3, о рефлекторном `unwrap`). Файл `p1/t10_race.rs`:

```rust
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    for (name, delay) in [("runner A", 300u64), ("runner B", 50), ("runner C", 150)] {
        let tx = tx.clone();
        thread::spawn(move || {
            thread::sleep(Duration::from_millis(delay));
            if tx.send(name).is_err() {
                // получателя больше нет: тихий выход вместо паники
                println!("{name}: too late, nobody listens");
                return;
            }
            println!("{name}: finished, message sent");
        });
    }
    drop(tx);

    let winner = rx.recv().unwrap(); // одно первое сообщение
    println!("winner: {winner}");
    drop(rx); // получатель уничтожен — опоздавшие получат Err

    thread::sleep(Duration::from_millis(500)); // дать опоздавшим добежать
    println!("main finished without panics");
}
```

Разбор решений в коде.

- **Цикл по массиву пар** `[(имя, задержка), …]` избавляет от трёх почти одинаковых блоков; `&'static str` и `u64` — Copy-типы, так что `move`-замыкание получает копии имени и задержки, а клон отправителя — своим `let tx = tx.clone();`.
- **`drop(tx)` после цикла** нужен по правилу З7: оригинал остался в `main`. Здесь он не спасает от зависания (мы читаем ровно одно сообщение через `recv`, а не крутим цикл), но оставлять живой отправитель без нужды — плохая привычка: стоит потом заменить `recv` на цикл, и программа повиснет.
- **`rx.recv().unwrap()`** — единственное место, где `unwrap` уместен: `Err` тут означал бы «все три отправителя умерли, не отправив ничего», то есть сломанную программу, а не штатный ход событий.
- **`drop(rx)`** — момент, ради которого написано задание: получатель уничтожается, и все последующие `send` возвращают `Err`.
- **`if tx.send(name).is_err() { … return; }`** — тихий выход. Никакого `unwrap`: опоздавший рапортует в свой `println!` и завершает работу. Тот же смысл имел бы `let _ = tx.send(name);`, но тогда мы бы не увидели, что `Err` действительно случился.
- **Пауза 500 мс в конце `main`** — не синхронизация (§23.1.1: слипами не лечат), а способ *не завершить процесс* раньше, чем опоздавшие добегут: их не `join`-ят, ручки не сохранялись. Самому позднему бегуну нужно 300 мс — запас двукратный.

Три прогона подряд:

```
$ rustc --edition 2024 t10_race.rs
$ ./t10_race.exe
runner B: finished, message sent
winner: runner B
runner C: too late, nobody listens
runner A: too late, nobody listens
main finished without panics
$ ./t10_race.exe
winner: runner B
runner B: finished, message sent
runner C: too late, nobody listens
runner A: too late, nobody listens
main finished without panics
```

**Что здесь устойчиво, а что нет.** Победитель устойчив: 50 мс против 150 и 300 — разрыв в сотню миллисекунд планировщик не отыграет, так что `winner: runner B` печатается в каждом прогоне. Устойчив и состав вывода: два опоздавших получают `Err` и рапортуют об этом, последняя строка — `main finished without panics`. А вот порядок первых двух строк недетерминирован — их печатают разные потоки: в первом прогоне поток B успел напечатать свою строку до того, как `main` проснулся на `recv`, в третьем — наоборот. Порядок строк `runner C` и `runner A` между собой определён их задержками (150 мс раньше 300 мс).

**Чем доказано отсутствие аварий.** Тремя фактами сразу: (1) строка `main finished without panics` напечатана — значит, `main` дошёл до конца; (2) код завершения процесса — 0 (`--- run exit=0 ---` в протоколе прогона); (3) в выводе нет ни одной строки `thread '<unnamed>' … panicked at` — а она появилась бы даже при панике в потоке, не роняющей программу (сравните с заданием З2). Если заменить `if … is_err()` на `tx.send(name).unwrap()`, два опоздавших потока запаникуют, и в stderr появятся две таких строки — программа при этом всё равно завершится кодом 0, потому что паника рабочего потока `main` не роняет. Это и есть причина, по которой `Err` от `send` нужно обрабатывать осознанно: «авария» останется незамеченной в коде завершения, но зашумит вывод и потеряет данные, которые поток не успел обработать.

**Ответ.** Победитель — `runner B` (50 мс), это устойчиво во всех прогонах. Опоздавшие `runner C` и `runner A` получают от `send` значение `Err`, потому что `main` уничтожил получателя (`drop(rx)`); обработка — печать `too late, nobody listens` и `return`, без паники. Программа доживает до финальной строки `main finished without panics` и завершается кодом 0; в выводе нет ни одного сообщения о панике. Недетерминирован только относительный порядок строк `winner:` и `runner B: finished, message sent` — их печатают разные потоки.

## Часть 23.2. Разделяемое состояние: Mutex, Arc и маркерные трейты

### Г23.Ч2.З1

**Условие.** Создайте `Mutex<String>` со строкой `"старт"`, напечатайте его `{:?}`-форматом, затем в блоке возьмите пропуск и дважды допишите текст (`"; запись 1"`, `"; запись 2"`), напечатайте `{:?}` ещё раз. Приведите оба вывода и объясните каждую часть Debug-представления (`data`, `poisoned`) и почему второй `println!` не завис, хотя пропуск брался выше.

**Решение.** Файл `p2/m1_mutex.rs`:

```rust
use std::sync::Mutex;

fn main() {
    let text = Mutex::new(String::from("старт"));
    println!("{text:?}");

    {
        let mut guard = text.lock().unwrap();
        guard.push_str("; запись 1");
        guard.push_str("; запись 2");
    } // пропуск умер — замок отпёрт

    println!("{text:?}");
}
```

```
$ rustc --edition 2024 m1_mutex.rs
$ ./m1_mutex.exe
Mutex { data: "старт", poisoned: false, .. }
Mutex { data: "старт; запись 1; запись 2", poisoned: false, .. }
```

**Разбор Debug-представления.**

- **`data: "старт"`** — само запертое значение. Печатается оно потому, что `Mutex<T>` реализует `Debug` при `T: Debug`, и печать *заглядывает внутрь* замка. Заметьте: другого пути к данным нет — `T` живёт внутри `Mutex<T>` (§23.2.1), и в этом отличие от C, где мьютекс лежал бы *рядом* с данными.
- **`poisoned: false`** — флаг отравления: держатель пропуска ни разу не паниковал, замок «чист». Если бы поток упал, не отпустив пропуск, здесь стояло бы `true`, а `lock()` возвращал бы `Err(PoisonError)` — разбор в задании З7.
- **`..`** — многоточие в Debug-выводе структуры: у `Mutex` есть и другие поля (внутренние данные примитива синхронизации ОС), но печатать их незачем — это `finish_non_exhaustive()` в реализации `Debug`, «здесь есть ещё поля, они вас не касаются».
- **Две записи** — обычные вызовы `String::push_str` через пропуск: `MutexGuard` реализует `DerefMut`, поэтому точка достаёт до методов `String`, как через `&mut String` (§22.1.2 про Deref-коэрцию, §23.2.1 про пропуск).

**Почему второй `println!` не завис.** Пропуск `guard` — обычное значение, и уничтожается он по правилу конца области видимости (§15.1.1): фигурные скобки вокруг записей — не украшение, а именно то, что убивает `guard` и отпирает замок в его `Drop` (§22.1.2: «замки многопоточности будут отпираться в `drop`»). К моменту второго `println!` замок свободен, и печать берёт его без очереди.

Но это не полный ответ: интересно, что было бы, **не** отпусти мы пропуск. Проверим — файл `p2/m1_locked.rs`:

```rust
use std::sync::Mutex;

fn main() {
    let text = Mutex::new(String::from("старт"));

    let mut guard = text.lock().unwrap();
    guard.push_str("; запись 1");
    println!("{text:?}"); // печатаем, НЕ отпустив пропуск
    drop(guard);

    println!("{text:?}"); // а теперь замок свободен
}
```

```
$ ./m1_locked.exe
Mutex { data: "<locked>", poisoned: false, .. }
Mutex { data: "старт; запись 1", poisoned: false, .. }
```

Программа **не зависла**: вместо данных Debug напечатал `<locked>`. Значит, печать не встаёт в очередь за ключом — она пробует взять замок неблокирующим способом и, если он занят, честно сообщает, что заглянуть не удалось. Это важное практическое наблюдение: `{:?}` от `Mutex` безопасен для диагностики в любом месте программы, включая место, где вы уже держите пропуск, — самоблокировки (пример 3 §23.2.1) он не устраивает. Не путайте с `lock()`: **вот он** в такой ситуации повис бы навсегда.

Заодно виден и порядок событий: первая печать `m1_locked` показывает `<locked>` ещё до `drop(guard)`, вторая — уже готовую строку.

**Ответ.** Программа печатает `Mutex { data: "старт", poisoned: false, .. }` и `Mutex { data: "старт; запись 1; запись 2", poisoned: false, .. }`. В Debug-представлении `data` — запертое значение (доступное только через замок), `poisoned` — флаг отравления (паниковал ли держатель пропуска), `..` — «есть и другие поля, не показанные намеренно». Второй `println!` не завис, потому что пропуск умер на закрывающей скобке блока и его `Drop` отпер замок; вдобавок Debug-печать `Mutex` вообще не блокирует — при занятом замке она печатает `data: "<locked>"`, что мы проверили отдельной программой.

### Г23.Ч2.З2

**Условие.** Четыре потока кладут каждый своё число (1..=4) в общий `Arc<Mutex<Vec<i32>>>`. После `join` всех потоков отсортируйте вектор и напечатайте. Предскажите и проверьте значения `Arc::strong_count` в двух точках: до запуска потоков (после создания четырёх клонов) и после всех `join`. Объясните, почему без сортировки тест «вектор равен `[1, 2, 3, 4]`» был бы нестабилен.

**Решение.** Условие требует посмотреть на счётчик владельцев *до запуска потоков*, поэтому клоны делаются отдельным шагом, а не внутри цикла `spawn`. Файл `p2/m2_vec.rs`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(Vec::new()));

    let clones: Vec<Arc<Mutex<Vec<i32>>>> = (0..4).map(|_| Arc::clone(&data)).collect();
    println!("owners before spawn: {}", Arc::strong_count(&data));

    let mut handles = Vec::new();
    for (i, own) in clones.into_iter().enumerate() {
        handles.push(thread::spawn(move || {
            own.lock().unwrap().push(i as i32 + 1);
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("owners after join: {}", Arc::strong_count(&data));

    let mut result = data.lock().unwrap().clone();
    result.sort();
    println!("sorted: {result:?}");
}
```

**Предсказание счётчиков.** До запуска потоков живых ручек пять: оригинал `data` в `main` плюс четыре клона в векторе `clones` — `Arc::strong_count` должен показать **5** (правила те же, что у `Rc` в §22.1.4, только счётчик атомарный). После `join` всех потоков каждый клон уже уничтожен вместе со своим замыканием, а `clones` опустошён `into_iter()` — остаётся один оригинал, то есть **1**.

Три прогона подряд:

```
$ rustc --edition 2024 m2_vec.rs
$ ./m2_vec.exe
owners before spawn: 5
owners after join: 1
sorted: [1, 2, 3, 4]
$ ./m2_vec.exe
owners before spawn: 5
owners after join: 1
sorted: [1, 2, 3, 4]
```

Предсказание подтвердилось; обе величины **устойчивы**. Важно, что смотреть на счётчик имеет смысл именно в этих двух точках: в промежутке, пока потоки живут, значение недетерминировано — оно зависит от того, сколько потоков уже умерло к моменту чтения (та же оговорка сделана в §23.2.2).

**Строка `let mut result = data.lock().unwrap().clone();`.** Клон вектора нужен, чтобы не сортировать данные *под замком* и не держать пропуск до конца `main`: взяли, скопировали, отпустили (правило короткого пропуска, §23.2.1). Пропуск здесь умирает в конце того же выражения — временное значение `MutexGuard` живёт до точки с запятой.

**Почему без сортировки тест был бы нестабилен.** Порядок элементов в векторе — это порядок, в котором потоки добрались до замка, а его задаёт планировщик ОС. Каждый из четырёх потоков делает ровно один `push`, но кто окажется первым — вопрос расписания: легальны все 4! = 24 перестановки. Тест `assert_eq!(v, vec![1, 2, 3, 4])` проверял бы не логику программы, а везение: он зеленел бы почти всегда (на нашей машине потоки обычно успевают по порядку) и краснел бы раз в сотню прогонов — худший вид теста, «мигающий». Сортировка (или сравнение множествами) убирает из проверки то, что программа и не обещала: обещано, что **все четыре числа попадут в вектор**, а не что они лягут по возрастанию. Это правило 6 из свода §23.2.4: любой легальный порядок событий должен давать верный ответ — в том числе и в тестах.

**Ответ.** `Arc::strong_count` показывает **5** до запуска потоков (оригинал плюс четыре клона) и **1** после всех `join` (клоны умерли вместе с замыканиями); отсортированный вектор — `[1, 2, 3, 4]`. Без сортировки тест на точное равенство был бы нестабилен: порядок `push`-ей задаёт планировщик, легальны все 24 перестановки, и проверка ловила бы расписание, а не корректность.

**Вариант 2 (канал вместо разделяемого состояния).** Здесь потоки ничего не читают из общего вектора — каждый лишь кладёт своё число. А раз данные не нужно *разделять*, их можно *передать*: сборка списка делается каналом, без `Arc`, без `Mutex` и без единого замка (правило 1 §23.2.4). Файл `p2/m2_chan.rs`:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for i in 1..=4 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(i).unwrap(); // ничего общего, кроме трубы
        });
    }
    drop(tx);

    let mut result: Vec<i32> = rx.iter().collect();
    result.sort();
    println!("sorted: {result:?}");
}
```

```
$ ./m2_chan.exe
sorted: [1, 2, 3, 4]
$ ./m2_chan.exe
sorted: [1, 2, 3, 4]
```

*Сравнение.* Вариант короче и проще: нет замка (значит, нечего забыть отпустить и негде устроить самоблокировку), нет счётчика владельцев, нет `join` — цикл `rx.iter()` сам заканчивается, когда умирает последний отправитель. Взамен пропадает и то, ради чего задание написано: наблюдать за `Arc::strong_count` больше не за чем, а порядок элементов остаётся ровно таким же недетерминированным (сортировка нужна и здесь). Разделяемое состояние выигрывает, когда потокам нужно **читать** общий результат по ходу работы или когда сообщений слишком много, чтобы гонять их по трубе; для схемы «каждый поток отдаёт свой итог один раз» канал — прямое попадание, и именно так §23.1.3 чинил `race.c`.

### Г23.Ч2.З3

**Условие.** Воспроизведите счётчик из §23.2.2 (10 потоков по `+= 1`, `Result: 10`). Затем измените: 100 потоков, каждый прибавляет 10 в цикле из 10 итераций (итого ожидается 10 000). Прогоните пять раз и убедитесь в устойчивости результата. Объясните, почему здесь невозможна потеря инкрементов из §13.1.4.

**Решение.** Счётчик из §23.2.2 — файл `p2/m3_ten.rs`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}
```

```
$ rustc --edition 2024 m3_ten.rs
$ ./m3_ten.exe
Result: 10
```

**Сто потоков по сто.** Каждый поток делает десять оборотов, прибавляя по 10, — итого 100 · 10 · 10 = 10 000. Пропуск берётся *внутри* цикла и живёт одно выражение: так замок занят ровно на время `+= 10`, а не на все десять оборотов (правило короткого пропуска, §23.2.1). Файл `p2/m3_hundred.rs`:

```rust
use std::sync::{Arc, Mutex};

    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..100 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..10 {
                *counter.lock().unwrap() += 10; // пропуск живёт одно выражение
            }
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}
```

Пять прогонов подряд:

```
$ ./m3_hundred.exe
Result: 10000
$ ./m3_hundred.exe
Result: 10000
$ ./m3_hundred.exe
Result: 10000
$ ./m3_hundred.exe
Result: 10000
$ ./m3_hundred.exe
Result: 10000
```

Пять из пяти. Сравните с табло `race.c` из §13.1.4, где та же по смыслу программа на C давала `1165767`, `1050465`, `991268` — каждый прогон свой. Устойчивость здесь не везение: недетерминирован лишь **порядок**, в котором тысяча обращений к замку выстроится в очередь, а сумма от порядка слагаемых не зависит.

**Почему невозможна потеря инкрементов из §13.1.4.** В C потеря происходила так: `counter++` — это три машинных шага (прочитать в регистр, прибавить, записать обратно), и два потока успевали прочитать одно и то же значение, каждый прибавлял к своей копии и записывал — второй результат затирал первый, один инкремент испарялся. Три условия гонки данных выполнялись полностью: два потока, конфликтующий доступ (есть запись), нет синхронизации.

Здесь третье условие выполнить нельзя — по построению:

- **К данным нет пути мимо замка.** Число живёт *внутри* `Mutex<i32>`, а единственный способ добраться до него — `lock()`, который возвращает пропуск. Это не соглашение и не комментарий, как в C, где `pthread_mutex_t` лежал рядом с данными и его разрешалось «случайно» не взять, — это тип.
- **Пропуск в каждый момент один.** `lock()` блокирует, пока замок занят: второй поток встаёт в очередь. Значит, все три шага «прочитал — прибавил — записал» происходят под одним пропуском, и перемешивать их не с чем.
- **Пропуск возвращается сам.** Замок отпирается в `Drop` пропуска (§22.1.2, §23.2.1) — забыть `unlock`, как в C, физически не выйдет; даже паника под замком не «заклинит» его, а отравит (задание З7).

Формально: чтобы два потока конфликтующе обратились к числу, оно должно быть доступно двум потокам одновременно — а `Mutex` выдаёт доступ по одному. Гонка данных здесь не «маловероятна» и не «поймана бы санитайзером» — она **невыразима**, и именно это отличает проверку в компиляции от проверки на прогоне (таблица §23.2.3: TSan видит гонки одного прогона, система типов — всех).

Стоит держать в голове границу утверждения (§23.2.4): устранена **гонка данных**, а не всякая многопоточная ошибка. Тот же счётчик легко испортить логически — например, прочитать значение, отпустить замок, что-то посчитать и записать обратно результат, вычисленный по устаревшему числу. Такой код тоже компилируется; ловится он не типами, а дисциплиной «инвариант — под одним пропуском» (задание З8).

**Ответ.** Обе версии дают устойчивый результат: `Result: 10` и `Result: 10000` — последний повторён в пяти прогонах подряд. Потеря инкрементов из §13.1.4 здесь невозможна, потому что число заперто в `Mutex`: доступ к нему существует только через пропуск, пропуск в каждый момент выдан ровно одному потоку, а вся тройка «прочитал — прибавил — записал» происходит под этим пропуском. Третье условие гонки данных (конфликтующий доступ без синхронизации) не выполнимо по построению, а не по счастливому расписанию.

### Г23.Ч2.З4

**Условие.** Пройдите цепочку отказов §23.2.2 руками, собирая каждый вариант: (а) `Mutex` без `Arc` в цикле потоков — объясните E0382 и слова «in previous iteration of loop»; (б) `Rc<Mutex<...>>` — объясните E0277: что именно небезопасно в счётчике `Rc` (какие три условия гонки §13.1.4 сложились бы на нём); (в) почему `Arc` чинит: что в нём атомарно и чем это отличается от «завернуть счётчик в Mutex».

**Решение.** Собираем каждый шаг цепочки отдельной программой — «спросите компилятор» в чистом виде.

**(а) `Mutex` без `Arc`.** Файл `p2/m4_no_arc.rs`:

Читаем по частям. `Mutex<i32>` **не `Copy`** — это первая хорошая новость: тихо размножиться по потокам, как счётчик из задания З5, он не может. Значит, `move`-замыкание его **уносит**. Первая же итерация цикла увозит единственный экземпляр в первый поток — и всё, `counter` в `main` мёртв. Отсюда фраза «value moved into closure here, **in previous iteration of loop**»: компилятор сообщает, что виновата не текущая итерация, а предыдущая — цикл требует, чтобы значение было доступно на каждом обороте, а его вынесли на первом. Формулировка знакома по §15.1.2, где в цикле раздавали `String`.

Указано место *использования* (`println!` на строке 20) — это первое место после цикла, где мёртвая переменная понадобилась. Если бы печати не было, ошибка всё равно осталась бы: замыкания второй-десятой итераций тоже требуют `counter`.

Вывод: замку нужны **совладельцы** — по одному на поток, с общим содержимым.

**Что именно небезопасно в счётчике `Rc`.** Счётчик сильных ссылок внутри `Rc` изменяется обычными операциями «прочитать — прибавить — записать», ровно как `counter++` в `race.c`. Если бы два потока клонировали и роняли один `Rc` одновременно, сложились бы все три условия гонки данных из §13.1.4:

| Условие гонки (§13.1.4) | На счётчике `Rc` |
|---|---|
| два потока обращаются к одной памяти | оба клонируют/уничтожают ручки, ведущие к одному блоку со счётчиком |
| хотя бы один доступ — запись | и `Rc::clone` (+1), и уничтожение ручки (−1) пишут в счётчик |
| нет синхронизации | `Rc` не синхронизирует ничего: его инкремент — обычный неатомарный `+= 1` |

Последствия хуже потерянного инкремента: заниженный счётчик означает освобождение данных при живых ручках (use-after-free и двойное освобождение — беды из каталога §7.2.1), завышенный — утечку. Причём **испорчен был бы не наш `i32`** (он-то под замком), а служебный счётчик самого умного указателя. Именно поэтому запрет стоит на типе целиком, а не на «записи в данные».

**(в) Почему `Arc` чинит.** `Arc` (atomically reference counted, R9) — тот же счётчик владельцев с тем же интерфейсом (`Arc::new`, `Arc::clone`, `Arc::strong_count`), но **изменение счётчика атомарно**: аппаратная операция «прибавь и запиши» неделима, её нельзя перемешать с чужой такой же. Третье условие гонки на счётчике перестаёт выполняться, тип получает `Send`/`Sync` — и досмотр на `spawn` пройден. Рабочая версия — задание З3 (`p2/m3_ten.rs`), печатает `Result: 10`.

Ключевое различие, которое стоит проговорить: **`Arc` — это не «`Rc`, завёрнутый в `Mutex`»**. Замок вокруг счётчика означал бы отдельный объект синхронизации ОС, вызов `lock`/`unlock` на каждый клон и очередь потоков там, где нужно всего лишь прибавить единицу; кроме того, кто-то должен был бы защищать замком *сам* доступ к счётчику, а это уже курица и яйцо. Атомарная операция дешевле замка на порядок и не требует ни очереди, ни пропуска. И обратите внимание на разделение труда в паре `Arc<Mutex<T>>`: `Arc` защищает **служебный счётчик владельцев** (атомарно), `Mutex` — **пользовательские данные** (очередью). Каждый охраняет своё; заменить один другим нельзя.

Цена атомарности — она не бесплатна (R9): в однопоточном коде остаётся `Rc`, потому что незачем платить за синхронизацию, которая никому не нужна. Это ровно тот выбор, который курс сделал в §22.1.4, обещав многопоточного собрата.

**Ответ.** (а) `Mutex<i32>` не `Copy`, поэтому `move`-замыкание уносит единственный экземпляр на первой же итерации цикла — E0382 с уликой «value moved into closure here, in previous iteration of loop»: на втором обороте увозить уже нечего. (б) `Rc<Mutex<i32>>` не реализует `Send`, а `spawn` требует `Send` от каждого захвата замыкания — E0277; небезопасен именно счётчик ссылок `Rc`: он меняется неатомарно, и два потока, клонирующие ручку, устроили бы гонку данных на нём (два потока, запись, нет синхронизации), с двойным освобождением или утечкой в качестве последствия. (в) `Arc` меняет счётчик атомарными операциями, поэтому получает `Send`/`Sync` и проходит досмотр; это дешевле, чем «завернуть счётчик в `Mutex`» (нет объекта синхронизации, нет очереди, нет пропуска на каждый клон), и распределение ролей в `Arc<Mutex<T>>` остаётся честным: `Arc` охраняет счётчик владельцев, `Mutex` — сами данные.

### Г23.Ч2.З5

**Условие.** Ловушка Copy (§23.2.2, пример 1): объясните, почему программа компилируется без предупреждений и печатает `counter в main = 0`; какую роль играют `Copy`-семантика `u64` (§15.1.3) и правило захвата `move`-замыканий (§21.1.2). Проверьте своё объяснение: замените тип счётчика на не-Copy (например, `Vec<u64>` с `push`) и покажите, что теперь программа честно не компилируется (какой код ошибки?).

**Решение.** Файл `p2/m5_copy.rs` — пример 1 §23.2.2:

```rust
use std::thread;

fn main() {
    let mut counter: u64 = 0;
    let mut handles = vec![];

    for _ in 0..2 {
        handles.push(thread::spawn(move || {
            for _ in 0..1_000_000 {
                counter += 1; // инкрементируем... а что именно?
            }
            println!("в потоке насчиталось: {counter}");
        }));
    }
    for h in handles {
        h.join().unwrap();
    }

    println!("counter в main = {counter}");
}
```

```
$ rustc --edition 2024 m5_copy.rs
$ ./m5_copy.exe
в потоке насчиталось: 1000000
в потоке насчиталось: 1000000
counter в main = 0
```

**Почему компилируется без предупреждений.** Сложим два правила, каждое из которых мы уже знаем.

1. **`u64` — `Copy`** (§15.1.3): у типов с этим маркером «перемещение» — это побитовое копирование, и оригинал остаётся полноценно живым. Ровно поэтому цикл не спотыкается на второй итерации: в задании З4 непереносимый `Mutex` дал E0382 «value moved into closure here, in previous iteration of loop», а здесь уносить нечего — каждому замыканию достаётся собственная копия нуля.
2. **`move`-замыкание захватывает по значению** (§21.1.2): ключевое слово `move` заставляет замыкание взять переменную «в собственность» — но для Copy-типа собственность означает копию. Компилятору не в чем упрекнуть программу: ни одного нарушения владения, ни одного заимствования, ни одной гонки. Предупреждать не о чем — с точки зрения типов всё безупречно.

**Почему печатается `counter в main = 0`.** Потому что переменных-счётчиков в программе **три**: одна в `main` и по одной внутри каждого замыкания. Потоки честно досчитали свои копии до миллиона и напечатали их (`в потоке насчиталось: 1000000` — дважды), а тот `counter`, что живёт в `main`, никто ни разу не трогал: он как был нулём, так и остался. Общего счётчика в программе просто нет.

Обратите внимание, чем эта ошибка **не** является. Это не гонка данных: не то что «инкременты потерялись» — они попали не туда. Гонку Rust бы не собрал (§23.2.2), а вот логическую ошибку «общий объект оказался тремя разными» — собирает молча. Коварство в том, что симптом выглядит как гонка: потоки рапортуют о работе, итог в `main` пуст. Отсюда правило: увидев `move` рядом с Copy-типом, спросите себя, нужна ли потоку копия или ему нужен доступ к общему; во втором случае — `Arc<Mutex<T>>` (задание З3).

**Проверка объяснения: не-Copy-счётчик.** Если диагноз верен («молчит, потому что `Copy`»), то счётчик не-Copy-типа обязан вызвать ту же ошибку, что и `Mutex` в задании З4. Файл `p2/m5_vec.rs` — то же самое, но счётчик — вектор, а прибавление — `push`:

```rust
use std::thread;

fn main() {
    let mut counter: Vec<u64> = Vec::new(); // тот же счётчик, но не Copy
    let mut handles = vec![];

    for _ in 0..2 {
        handles.push(thread::spawn(move || {
            for _ in 0..1_000_000 {
                counter.push(1);
            }
            println!("в потоке насчиталось: {}", counter.len());
        }));
    }
    for h in handles {
        h.join().unwrap();
    }

    println!("counter в main = {}", counter.len());
}
```

### Г23.Ч2.З6

**Условие.** Заполните таблицу «Send? Sync? почему» для типов: `i64`, `String`, `Rc<String>`, `RefCell<i32>`, `Mutex<Vec<i32>>`, `Arc<Mutex<i32>>`, `mpsc::Sender<i32>`, `MutexGuard<'static, i32>`. Каждый минус докажите минимальной ⛔-программой на основе `is_send::<T>()` / `is_sync::<T>()` (§23.2.3, пример 1) с текстом полученной E0277. Для `Arc<RefCell<i32>>` объясните по note компилятора, почему матрёшка не Send, хотя Arc «хороший».

**Решение.** Сначала — положительная часть каталога: всё, что в таблице отмечено плюсом, доказывается одной компилирующейся программой (приём §23.2.3). Файл `p2/m6_catalog.rs`:

```rust

use std::rc::Rc;
use std::sync::mpsc::Sender;
use std::sync::{Arc, Mutex, MutexGuard};

fn is_send<T: Send>() {}
fn is_sync<T: Sync>() {}

fn main() {
    // Обычные данные: и Send, и Sync.
    is_send::<i64>();
    is_sync::<i64>();
    is_send::<String>();
    is_sync::<String>();

    // Однопоточная ячейка: переехать может, разделяться — нет.
    is_send::<RefCell<i32>>();

    // Синхронизированные контейнеры: и Send, и Sync.
    is_send::<Mutex<Vec<i32>>>();
    is_sync::<Mutex<Vec<i32>>>();
    is_send::<Arc<Mutex<i32>>>();
    is_sync::<Arc<Mutex<i32>>>();

    // Конец канала: создан, чтобы уезжать в поток.
    is_send::<Sender<i32>>();

    // Пропуск замка: показывать другим потокам можно, переезжать — нет.
    is_sync::<MutexGuard<'static, i32>>();

    let _ = Rc::new(String::new()); // Rc в каталоге только со знаком минус

    println!("all positive checks passed at compile time");
}
```

Отдельно проверены концы канала: `mpsc::Sender<i32>` — `Sync` (проверено компиляцией на 1.97), а `Receiver<i32>` не `Sync`, что соответствует «single consumer» в названии mpsc, — так они и разведены в таблице §23.2.3. Матрёшка `Arc<RefCell<i32>>` не `Send`, потому что `Arc<T>: Send` требует `T: Send + Sync`, а `RefCell` не `Sync`, — компилятор говорит это строкой `required for 'Arc<RefCell<i32>>' to implement 'Send'`.

### Г23.Ч2.З7

**Условие.** Отравление: предскажите вывод примера 2 из §23.2.1 (поток паникует под замком, `main` разбирает `Err`), затем сломайте программу — замените разбор `match` на `data.lock().unwrap()` — и объясните полученную каскадную панику (текст ошибки, код завершения 101). Сформулируйте, когда каскад — правильная политика, а когда нужен `into_inner`; приведите по одному примеру сценария на каждую.

**Решение.** Файл `p2/m7_poison.rs` — пример 2 §23.2.1 дословно:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(vec![1, 2, 3]));

    let d = Arc::clone(&data);
    let handle = thread::spawn(move || {
        let _guard = d.lock().unwrap();
        panic!("поток упал, держа замок");
    });
    let _ = handle.join(); // Err — поток запаниковал

    match data.lock() {
        Ok(guard) => println!("данные: {guard:?}"),
        Err(poisoned) => {
            println!("замок отравлен!");
            let guard = poisoned.into_inner(); // забрать пропуск вопреки яду
            println!("данные на месте: {guard:?}");
        }
    }
}
```

**Предсказание.** Поток берёт пропуск и паникует, не отпустив его, — значит, замок помечается отравленным. Паника рабочего потока программу не роняет (§23.1.1), `join` вернёт `Err`, который здесь намеренно игнорируется (`let _ =`). Дальше `data.lock()` вернёт **`Err(PoisonError)`** — сработает вторая ветка `match`: `замок отравлен!`, затем `into_inner` выдаст пропуск вопреки яду, и данные окажутся целыми, `[1, 2, 3]`: поток не успел ничего изменить. В stderr при этом появится сообщение о панике потока. Код завершения — 0.

```

$ ./m7_poison.exe

thread '<unnamed>' (28896) panicked at m7_poison.rs:10:9:
поток упал, держа замок
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
замок отравлен!
данные на месте: [1, 2, 3]
```

Предсказание сбылось полностью. (Строки `замок отравлен!` и `данные на месте:` идут в stdout, сообщение паники — в stderr; их взаимное расположение в консоли от прогона к прогону может меняться, номер потока в скобках — тоже.)

**Ломаем: `unwrap` вместо разбора.** Файл `p2/m7_unwrap.rs` — то же самое, но `match` заменён на `data.lock().unwrap()`:

```rust
    let _ = handle.join();

    let guard = data.lock().unwrap(); // ⚠️ каскад: unwrap вместо разбора Err
    println!("данные: {guard:?}");
}
```

```
$ ./m7_unwrap.exe

thread '<unnamed>' (28884) panicked at m7_unwrap.rs:10:9:
поток упал, держа замок
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

thread 'main' (7912) panicked at m7_unwrap.rs:14:29:
called `Result::unwrap()` on an `Err` value: PoisonError { .. }
--- run exit=101 ---
```

**Разбор каскада.** Паник теперь две, и это две разные аварии в двух разных потоках:

1. `thread '<unnamed>' … panicked at m7_unwrap.rs:10:9: поток упал, держа замок` — исходная авария рабочего потока. Она никого не роняет: `main` продолжает работу.
2. `thread 'main' … panicked at m7_unwrap.rs:14:29: called 'Result::unwrap()' on an 'Err' value: PoisonError { .. }` — паника **главного** потока: `unwrap` на `Err` (§18.1.2). Отравление приехало значением, `unwrap` превратил его в аварию.

Разница в последствиях принципиальна: паника главного потока — это конец программы, и код завершения меняется с 0 на **101** (стандартный код паники, §18.1.2). Строка `PoisonError { .. }` — Debug-представление ошибки; полезного текста в ней нет, зато сам факт назван точно.

**Когда каскад — правильная политика.** Когда авария одного участника означает, что состояние всей подсистемы под сомнением, а продолжать работу с сомнительным состоянием опаснее, чем упасть. Пример: сервис ведёт под замком структуру индекса — «дерево + счётчик узлов»; поток упал посередине перестройки дерева, и счётчик уже не соответствует дереву. Прочитать такой индекс — значит вернуть пользователю неверные ответы и разнести порчу дальше по системе. Здесь каскад (`unwrap`) — честное «останавливаем стройку»: процесс падает, супервизор перезапускает его с чистого листа.

**Когда нужен `into_inner`.** Когда инвариант данных прост, заведомо цел (или его можно проверить и починить), а падение всей программы обошлось бы дороже потери одного рабочего. Пример: общий журнал `Vec<String>`, куда потоки дописывают строки. Поток упал, не дописав — максимум, что могло случиться, это отсутствие последней строки; вектор как коллекция консистентен всегда. Ронять из-за этого сервис — расточительство: `into_inner` забирает пропуск, программа продолжает писать журнал. То же и в нашем опыте: данные `[1, 2, 3]` заведомо целы, поток паникует до единственной возможной правки.

Правило 5 из свода §23.2.4 добавляет к этому важное: политика должна быть **одинаковой по всей программе**. Смесь «здесь `unwrap`, там `into_inner`» означает, что поведение при аварии зависит от того, какой поток первым добрался до замка, — сюрприз в самый неподходящий момент.

**Ответ.** Программа с `match` печатает `замок отравлен!` и `данные на месте: [1, 2, 3]`, в stderr — сообщение о панике рабочего потока; код завершения 0. После замены на `data.lock().unwrap()` возникает каскад: рабочий поток паникует под замком, отравляет его, а `unwrap` в `main` превращает `Err(PoisonError)` в панику главного потока — `called 'Result::unwrap()' on an 'Err' value: PoisonError { .. }`, процесс завершается кодом **101**. Каскад уместен, когда данные под замком могли остаться в противоречивом состоянии (пример: индекс «дерево + счётчик» посреди перестройки) — падение лучше неверных ответов. `into_inner` уместен, когда инвариант прост и заведомо цел (пример: общий журнал `Vec<String>`, где худшее последствие — недописанная строка), и ронять из-за этого всю программу дороже, чем продолжить.

**Условие.** Банковский счёт. Тесты: пополнение и снятие в один поток; отказ при недостатке средств (баланс не меняется); 8 потоков × 1000 пополнений по 1 → ровно 8000; 10 потоков одновременно снимают по 1 со счёта в 5 — ровно 5 успехов и баланс 0. Дополнительно: напишите (не запуская или в тесте с `#[ignore]`) «гоночную» версию `withdraw_racy` из §23.2.4 и объясните сценарий, в котором она уводит баланс в минус.

**Решение.** Пакет `cargo new --lib bank`. Главное проектное решение — в `try_withdraw`: пропуск берётся **один раз на всю транзакцию**, проверка и списание происходят под ним. Файл `p2/bank/src/lib.rs`:

```rust
use std::sync::Mutex;

/// Счёт: баланс живёт внутри замка — мимо него пути нет.
pub struct Account {
    balance: Mutex<i64>,
}

impl Account {
    pub fn new(initial: i64) -> Self {
        Account {
            balance: Mutex::new(initial),
        }
    }

    pub fn deposit(&self, amount: i64) {
        *self.balance.lock().unwrap() += amount;
    }

    /// Проверка и списание — под ОДНИМ пропуском: транзакция цельная.
    pub fn try_withdraw(&self, amount: i64) -> bool {
        let mut balance = self.balance.lock().unwrap();
        if *balance >= amount {
            *balance -= amount;
            true
        } else {
            false
        }
    }

    pub fn balance(&self) -> i64 {
        *self.balance.lock().unwrap()
    }
}
```

Обратите внимание на сигнатуры: все методы берут **`&self`**, а не `&mut self`, — и при этом меняют баланс. Это внутренняя изменяемость (§22.2.1) в её многопоточном изводе: право на запись выдаёт не компилятор через `&mut`, а замок в рантайме. Именно поэтому счёт можно положить в `Arc` и раздать потокам: изменяющие ссылки `Arc` не выдаёт (§22.1.4), а `&self` — сколько угодно.

Гоночная версия из §23.2.4 живёт в том же файле — как экспонат:

```rust
/// ⚠️ Гоночная версия из §23.2.4: проверка и списание — под РАЗНЫМИ пропусками.
/// Гонки данных нет, есть логическая гонка: баланс уходит в минус.
pub fn withdraw_racy(balance: &Mutex<i64>, amount: i64) -> bool {
    let enough = *balance.lock().unwrap() >= amount; // замок взят и отпущен
    if enough {
        *balance.lock().unwrap() -= amount; // замок взят заново
        true
    } else {
        false
    }
}

/// пауза не создаёт ошибку, а лишь делает её воспроизводимой на любой машине.
pub fn withdraw_racy_slow(balance: &Mutex<i64>, amount: i64, window_ms: u64) -> bool {
    let enough = *balance.lock().unwrap() >= amount;
    std::thread::sleep(std::time::Duration::from_millis(window_ms));
    if enough {
        *balance.lock().unwrap() -= amount;
        true
    } else {
        false
    }
}
```

### Г23.Ч2.З9

**Условие.** Параллельный частотный словарь. В cargo-пакете: `word_freq(text: &str) -> HashMap<String, u32>` (однопоточная идиома `entry`/`or_insert` из §17.2.1) и `word_freq_parallel(chunks: Vec<String>) -> HashMap<String, u32>`: каждый кусок — своему потоку; поток строит **частный** словарь без замка и один раз вливает его в общий `Arc<Mutex<HashMap<...>>>`. Тесты: совпадение с однопоточной версией; суммирование слова, встречающегося в разных кусках; пустой вход. Все зелёные; приведите строку `test result` и объясните, чем схема «частный словарь + один влив» лучше схемы «замок на каждое слово» (правило 4 из §23.2.4).

**Решение.** Пакет `cargo new --lib wordfreq`. Однопоточная версия — идиома `entry`/`or_insert` из §17.2.1 без изменений; параллельная строится на правиле 4 §23.2.4: «вычисления — до замка, под замком — только запись общего». Файл `p2/wordfreq/src/lib.rs`:

```rust
use std::collections::HashMap;
use std::sync::{Arc, Mutex};
use std::thread;

/// Однопоточная идиома entry/or_insert из §17.2.1.
pub fn word_freq(text: &str) -> HashMap<String, u32> {
    let mut freq = HashMap::new();
    for word in text.split_whitespace() {
        *freq.entry(word.to_string()).or_insert(0) += 1;
    }
    freq
}

/// Каждый кусок считается в своём потоке БЕЗ замка; общий словарь берётся
/// под пропуск ровно один раз — на влив готового частного результата.
pub fn word_freq_parallel(chunks: Vec<String>) -> HashMap<String, u32> {
    let shared = Arc::new(Mutex::new(HashMap::new()));
    let mut handles = Vec::new();

    for chunk in chunks {
        let shared = Arc::clone(&shared);
        handles.push(thread::spawn(move || {
            let private = word_freq(&chunk); // считаем вне замка

            let mut common = shared.lock().unwrap(); // один влив под пропуском
            for (word, count) in private {
                *common.entry(word).or_insert(0) += count;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }

    let result = shared.lock().unwrap().clone();
    result
}
```

Три детали, каждая — прямое следствие правил главы.

- **`for chunk in chunks`** отдаёт куски по значению: каждый `String` уезжает в свой поток по `move`, и заимствований, требующих `'static`, не возникает (§23.1.2).
- **Частный словарь** строится обычной однопоточной функцией — тем же `word_freq`, что и в тестах. Пока он строится, замок свободен: другие потоки не ждут.
- **Влив** — единственное место, где берётся пропуск, и он живёт ровно до конца цикла слияния. Ключи разных кусков могут совпадать, поэтому вливаем через `entry`/`or_insert` с прибавлением, а не `insert` (иначе счётчики затирались бы).

Первый тест сравнивает словари целиком — и это законно: `HashMap` сравнивается по содержимому, а не по порядку (§17.2.1), так что недетерминизм порядка вливов на результат не влияет. Третий — вырожденные входы: пустой список кусков (потоков не будет вовсе) и пустая строка (`split_whitespace` не даст ни одного слова).

**Чем «частный словарь + один влив» лучше «замка на каждое слово».** Альтернатива выглядела бы так: `*shared.lock().unwrap().entry(word).or_insert(0) += 1;` внутри цикла по словам. Она тоже корректна — и почти бесполезна:

| | частный словарь + один влив | замок на каждое слово |
|---|---|---|
| Взятий замка на кусок из N слов | 1 | N |
| Что происходит под замком | слияние готового словаря | разбор строки, хеширование, вставка |
| Что делают остальные потоки | считают свои куски параллельно | стоят в очереди почти всё время |
| Масштабируемость по ядрам | близка к линейной | никакая: работа сериализуется замком |
| Накладные расходы | одна аллокация словаря на поток | одно взятие/отпускание замка на слово |

Суть в том, что **замок сериализует всё, что происходит под ним**. Если под пропуском выполняется вся полезная работа, потоки выстраиваются в очередь и программа исполняется последовательно — только с добавленной ценой синхронизации; многопоточная версия окажется медленнее однопоточной. Правило 4 §23.2.4 («пропуск короткий, транзакция цельная») требует держать под замком лишь то, что действительно общее: здесь это одна операция слияния, а разбор текста и построение частного словаря к общему состоянию отношения не имеют.

Заметьте, что правило не противоречит уроку задания З8: там мы, наоборот, **удлиняли** удержание замка, чтобы проверка и списание попали под один пропуск. Противоречия нет — критерий один: под замком должно быть ровно то, что образует неделимую операцию над общими данными, не больше и не меньше.

**Ответ.** `word_freq` — однопоточная идиома `entry`/`or_insert`; `word_freq_parallel` отдаёт каждый кусок своему потоку, тот строит **частный** словарь без замка и один раз вливает его в общий `Arc<Mutex<HashMap<…>>>` через `entry`/`or_insert` с прибавлением. Тесты зелёные: `test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out`. Схема лучше «замка на каждое слово» потому, что замок сериализует всё, что происходит под ним: при захвате на каждое слово потоки почти всё время стоят в очереди и параллелизм исчезает (остаётся только цена синхронизации), тогда как здесь на кусок из N слов приходится одно взятие замка, а разбор текста идёт параллельно.

**Вариант 2 (область потоков, без замка вообще).** Раз каждый поток отдаёт свой результат ровно один раз, разделяемое состояние не нужно: пусть частные словари возвращаются значением из `join`, а сливает их главный поток. Файл `p2/wordfreq_scope/src/lib.rs`:

```rust
/// Тот же расчёт без единого замка: частные словари возвращаются значением
/// из join, слияние делает главный поток — разделять нечего.
pub fn word_freq_parallel(chunks: Vec<String>) -> HashMap<String, u32> {
    thread::scope(|s| {
        let handles: Vec<_> = chunks
            .iter()
            .map(|chunk| s.spawn(move || word_freq(chunk)))
            .collect();

        let mut total: HashMap<String, u32> = HashMap::new();
        for h in handles {
            for (word, count) in h.join().unwrap() {
                *total.entry(word).or_insert(0) += count;
            }
        }
        total
    })
}
```

Тесты — те же три, дословно:

```
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

*Сравнение.* Здесь нет ни `Arc`, ни `Mutex`, ни клонирования итогового словаря — а значит, нет и целого класса ошибок: нечего забыть отпустить, негде устроить самоблокировку, неоткуда взяться отравлению. Вдобавок куски не приходится отдавать потокам по значению: `chunks.iter()` одалживает их, потому что область дождётся всех (`s.spawn` требует не `'static`, а «не дольше области», §23.1.2). Плата — слияние строго последовательно и **в порядке ручек**: `h.join()` для первого потока ждёт именно его, даже если второй давно закончил; в версии с замком поток, закончивший раньше, вливает свой результат сразу. На практике это заметно, только если куски сильно разного размера. Второе ограничение то же, что в задании З8: scoped-потоки не переживут функцию — для фонового пересчёта, продолжающегося после возврата, вариант не годится.

### Г23.Ч2.З10

**Условие.** Миграция из главы 22. Возьмите журнал датчиков из §22.2.2 (`Sensor` с общим `SharedLog = Rc<RefCell<Vec<String>>>`) и переведите его в многопоточность: `SharedLog = Arc<Mutex<Vec<String>>>`, каждый датчик пишет из своего потока, `main` после `join` печатает журнал. Составьте таблицу замен (тип, создание, клон, взятие доступа — что было / что стало) и убедитесь, что метод `measure` изменился в одной строке. Объясните: почему порядок записей в журнале недетерминирован, и почему печать после сортировки (или сравнение множествами) делает программу проверяемой тестом.

**Решение.** Обещание §22.2.2 — «переучиваться не придётся» — проверяется буквально: берём журнал датчиков из главы 22 и меняем в нём только имена типов. Пакет `cargo new --lib sensors`; библиотека — файл `p2/sensors/src/lib.rs`:

```rust
use std::sync::{Arc, Mutex};

/// Было (§22.2.2): type SharedLog = Rc<RefCell<Vec<String>>>;
pub type SharedLog = Arc<Mutex<Vec<String>>>;

pub struct Sensor {
    pub name: &'static str,
    pub log: SharedLog,
}

impl Sensor {
    pub fn measure(&self, value: i32) {
        // единственная изменившаяся строка метода: borrow_mut() -> lock().unwrap()
        self.log.lock().unwrap().push(format!("{}: {}", self.name, value));
    }
}
```

**Таблица замен.**

| Что | Было (§22.2.2, один поток) | Стало (эта глава, много потоков) |
|---|---|---|
| Псевдоним типа | `Rc<RefCell<Vec<String>>>` | `Arc<Mutex<Vec<String>>>` |
| Импорты | `use std::cell::RefCell; use std::rc::Rc;` | `use std::sync::{Arc, Mutex};` |
| Создание | `Rc::new(RefCell::new(Vec::new()))` | `Arc::new(Mutex::new(Vec::new()))` |
| Клон ручки | `Rc::clone(&log)` | `Arc::clone(&log)` |
| Доступ на запись | `self.log.borrow_mut()` | `self.log.lock().unwrap()` |
| Доступ на чтение | `log.borrow().iter()` | `log.lock().unwrap().iter()` |
| Счётчик владельцев | `Rc::strong_count(&log)` | `Arc::strong_count(&log)` |
| Что делает второй писатель | паникует: `RefCell already borrowed` | **ждёт** в очереди за пропуском |
| Цена | неатомарный счётчик, флаг заимствования | атомарный счётчик, примитив синхронизации ОС |
| Структура `Sensor` | два поля: `name`, `log` | **не изменилась** (изменился только тип псевдонима) |

Метод `measure` действительно изменился в одной строке — `borrow_mut()` превратился в `lock().unwrap()`. Разница в семантике при этом существенная: `borrow_mut` при конфликте **паникует**, `lock` — **встаёт в очередь** (§23.2.1). Для журнала это ровно то, что нужно: два датчика, пишущие одновременно, не должны ронять программу, они должны писать по очереди. Появившийся `unwrap` — разбор `LockResult`: `Err` означал бы отравление замка (задание З7).

**Программа.** Файл `p2/sensors/src/main.rs` — каждый датчик пишет из своего потока:

```rust
use sensors::{Sensor, SharedLog};
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let log: SharedLog = Arc::new(Mutex::new(Vec::new()));

    let thermo = Sensor {
        name: "температура",
        log: Arc::clone(&log),
    };
    let baro = Sensor {
        name: "давление",
        log: Arc::clone(&log),
    };

    let h1 = thread::spawn(move || {
        thermo.measure(21);
        thermo.measure(22);
    });
    let h2 = thread::spawn(move || {
        baro.measure(748);
    });

    h1.join().unwrap();
    h2.join().unwrap();

    println!("владельцев журнала: {}", Arc::strong_count(&log));
    for line in log.lock().unwrap().iter() {
        println!("{line}");
    }
}
```

```
$ cargo run --quiet
владельцев журнала: 1
температура: 21
температура: 22
давление: 748
```

**Две вещи в этом выводе стоит прокомментировать.**

Первая: **владельцев `1`, а не `3`**, как было в главе 22. Ручек по-прежнему создавалось три (оригинал плюс два клона), но клоны уехали в потоки внутри датчиков и умерли вместе с ними — а `strong_count` мы печатаем *после* `join`, когда оба потока уже мертвы. В однопоточной версии §22.2.2 датчики жили до конца `main` и держали свои ручки. Это не разница между `Rc` и `Arc`, а разница между «объект живёт до конца функции» и «объект уехал в поток и умер вместе с ним».

Вторая: **порядок строк журнала недетерминирован**. В нашем прогоне оба измерения термометра попали раньше барометра, но легален и вывод, где `давление: 748` стоит первым или между двумя строками термометра. Гарантировано только то, что записи *одного* датчика идут в порядке вызовов `measure`: их делает один поток последовательно. Между датчиками порядок задаёт планировщик — кто первым дошёл до `lock`, тот первым и записал.

**Отсюда — проверяемость тестом.** Тест `assert_eq!(lines, vec!["температура: 21", "температура: 22", "давление: 748"])` был бы «мигающим»: он проверял бы расписание, а не программу. Программа обещает другое: **все записи попадут в журнал и записи каждого датчика не перемешаются между собой**. Проверять надо ровно это — и здесь помогает сортировка (или сравнение множествами): она убирает из проверки то, чего программа не гарантирует. Файл `p2/sensors/src/lib.rs`, продолжение:

```rust
/// Каждый датчик пишет из своего потока; журнал возвращается отсортированным.
pub fn collect_sorted(measurements: Vec<(&'static str, Vec<i32>)>) -> Vec<String> {
    let log: SharedLog = Arc::new(Mutex::new(Vec::new()));
    let mut handles = Vec::new();

    for (name, values) in measurements {
        let sensor = Sensor {
            name,
            log: Arc::clone(&log),
        };
        handles.push(std::thread::spawn(move || {
            for v in values {
                sensor.measure(v);
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }

    let mut lines = log.lock().unwrap().clone();
    lines.sort(); // порядок записей недетерминирован — сортируем для проверяемости
    lines
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn sorted_log_is_stable() {
        let lines = collect_sorted(vec![
            ("температура", vec![21, 22]),
            ("давление", vec![748]),
        ]);
        assert_eq!(
            lines,
            vec![
                String::from("давление: 748"),
                String::from("температура: 21"),
                String::from("температура: 22"),
            ]
        );
    }

    #[test]
    fn all_measurements_survive() {
        let lines = collect_sorted(vec![("a", (1..=50).collect()), ("b", (1..=50).collect())]);
        assert_eq!(lines.len(), 100);
    }
}
```

```
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Второй тест — «стресс на сто записей»: два датчика по 50 измерений каждый. Он ловит потерю записей, если бы её удалось устроить (при `Mutex` — не удастся: каждая запись под пропуском), и подтверждает, что сортировка ничего не съедает.

**Ответ.** Миграция сводится к таблице замен выше: `Rc` → `Arc`, `RefCell` → `Mutex`, `borrow_mut()` → `lock().unwrap()`, `borrow()` → `lock().unwrap()`; структура `Sensor` не меняется вовсе, а метод `measure` — в одной строке. Порядок записей в журнале недетерминирован, потому что датчики пишут из разных потоков и очередь за пропуском выстраивает планировщик ОС; гарантирован лишь порядок записей *внутри* одного датчика. Печать после сортировки (или сравнение множествами) убирает из проверки то, чего программа не обещает, и оставляет то, что обещает: все записи на месте — поэтому тест перестаёт быть «мигающим». Дополнительное наблюдение: `Arc::strong_count` после `join` равен 1, а не 3, как в §22.2.2, — клоны умерли вместе с потоками.

**Вариант 2 (журнал через канал, без замка).** Если журнал только пополняется, а читается один раз в конце, разделяемое состояние можно убрать совсем: пусть датчик держит не сам журнал, а конец трубы, а собирает журнал один поток-владелец. Файл `p2/sensors_chan/src/lib.rs`:

```rust
use std::sync::mpsc::Sender;

/// Вариант без разделяемого состояния: журнал собирает один поток-владелец,
/// датчики держат не сам журнал, а конец трубы.
pub type LogSender = Sender<String>;

pub struct Sensor {
    pub name: &'static str,
    pub log: LogSender,
}

impl Sensor {
    pub fn measure(&self, value: i32) {
        self.log.send(format!("{}: {}", self.name, value)).unwrap();
    }
}

pub fn collect_sorted(measurements: Vec<(&'static str, Vec<i32>)>) -> Vec<String> {
    let (tx, rx) = std::sync::mpsc::channel();
    let mut handles = Vec::new();

    for (name, values) in measurements {
        let sensor = Sensor {
            name,
            log: tx.clone(),
        };
        handles.push(std::thread::spawn(move || {
            for v in values {
                sensor.measure(v);
            }
        })); // конец трубы умирает вместе с датчиком и потоком
    }
    drop(tx); // оригинал тоже обязан умереть, иначе цикл не завершится

    let mut lines: Vec<String> = rx.iter().collect();
    for h in handles {
        h.join().unwrap();
    }

    lines.sort();
    lines
}
```

Тесты — те же два, дословно:

```
$ cargo test
running 2 tests
test tests::sorted_log_is_stable ... ok
test tests::all_measurements_survive ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

*Сравнение.* Структура `Sensor` осталась той же формы — изменился лишь тип поля `log`, и `measure` снова переписан в одну строку. Но модель другая: вместо «все владеют журналом по очереди» — «журнал принадлежит одному, остальные шлют ему записи». Плюсы: нет замка (нечего забыть, нечем заблокироваться, нечего отравить), писатели никогда не ждут друг друга — `send` не блокирует, и медленный датчик не тормозит быстрый. Минусы: журнал недоступен для чтения, пока идёт сбор (в версии с `Mutex` любой владелец может в любой момент взять пропуск и прочитать накопленное), и появляется обязанность хоронить отправителей — забытый `drop(tx)` подвесит `rx.iter()`, как в задании З7. Заметьте порядок в коде: сначала `rx.iter().collect()`, потом `join`. Обратный порядок тоже работал бы — буфер канала концептуально не ограничен, `send` не блокирует (§23.1.3), — но так виднее логика: `collect` дожидается смерти всех отправителей, то есть завершения всех потоков-датчиков, а `join` после него нужен уже только для того, чтобы поймать панику датчика, если она случится.

## Уточнения к тексту главы

Одно наблюдение с прогонов стоит держать под рукой — оно объясняет, почему в таблице §23.2.3 концы канала разведены по разным строкам.

**Таблица `Send`/`Sync` в §23.2.3: `Sender<T>` против `Receiver<T>`.** Свойства у концов канала разные, и каждое подтверждается отдельной программой (rustc 1.97):

- `Sender<i32>` — **`Sync` есть**: программа `is_sync::<Sender<i32>>();` компилируется (`p2/m6_sync_sender.rs`). Практическое следствие: отправителя можно раздавать потокам по ссылке, не клонируя.
- `Receiver<i32>` — **`Sync` нет**: E0277 «cannot be shared between threads safely» (`p2/m6_probe_recv_sync.rs`). Это согласуется с «single consumer» в расшифровке mpsc.
- `Send` есть у обоих (`p2/m6_probe_recv.rs`), причём наследуется от груза: `Sender<Rc<i32>>` уже не `Send` (`p2/m6_probe_sender_rc.rs`, note `required for 'Sender<Rc<i32>>' to implement 'Send'`).

Отсюда и вид таблицы главы: у `Sender<T>` в столбце `Sync` — плюс, у `Receiver<T>` — прочерк. Разбор — в решении Г23.Ч2.З6.
