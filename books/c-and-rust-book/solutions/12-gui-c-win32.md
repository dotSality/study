# Решения. Глава 12. GUI на C: событийная модель и Win32

> Сборник решений самоучителя «C, затем Rust». Условия заданий продублированы из `chapters/12-gui-c-win32.md`. Весь код собран и запущен на эталоне тома I — **GCC 15.2.0 (MinGW-w64), `gcc -std=c17 -Wall -Wextra`**; 37 сборок стенда прошли **без единого предупреждения**. Приведённые выводы программ, сообщения компилятора и компоновщика — дословные результаты реального прогона.
>
> Глава оконная, и «вывод программы» здесь чаще всего не текст в консоли, а **поведение окна**. Чтобы такие результаты были воспроизводимы и проверяемы, каждая оконная программа стенда прогонялась под управлением служебной программы-водителя. Водитель не «кликает мышью по экрану»: он посылает окнам ровно те сообщения, которые в этих случаях порождает сама система, и читает обратно тексты окон и контролов — `BM_CLICK` кнопке (кнопка после него шлёт родителю `WM_COMMAND`/`BN_CLICKED` — §12.2.1), `WM_LBUTTONDOWN`/`WM_LBUTTONUP` в клиентскую область, `WM_CHAR` в поле ввода (набор с клавиатуры), `WM_SYSCOMMAND` с `SC_CLOSE` вместо щелчка по «крестику», `WM_GETTEXT`/`GetWindowText` для чтения. Поэтому все описанные ниже наблюдения — измеренные, а не пересказанные. Единственная разница с живой мышью: в логе §12.1.3 перед `WM_CLOSE` не видно нескольких сообщений мыши в неклиентской области — их порождает само движение курсора; на состав и порядок остальных сообщений это не влияет.
>
> **Ручная приёмка интерфейса** — удобство прокрутки, ввод с клавиатуры вживую, поведение на очень больших файлах — остаётся за читателем и владельцем книги, как и сказано в §12.2.4: это неотменяемая часть приёмки любого GUI.
>
> Санитайзеры под MinGW не линкуются (журнал окружения), поэтому там, где задание требует отчёта инструмента о нарушении памяти (Г12.Ч2.З6), тот же дефект воспроизведён консольной моделью на Linux-контуре — **WSL Ubuntu 24.04, gcc 13.3.0, AddressSanitizer и Valgrind 3.22.0**; отчёты приведены дословно.
>
> Часть чисел зависит от машины и версии Windows: номера и общее число сообщений в логе, точные размеры клиентской области, адреса дескрипторов. Такие места помечены оговоркой «на эталонной машине». Ошибочные сборки и намеренно неверные программы помечены ⛔ — их предъявление входит в условие соответствующих заданий.

## Часть 12.1. Событийная модель и минимальное окно

### Г12.Ч1.З1

**Условие.** Соберите и запустите программу с `MessageBox` из примера 1 §12.1.1. Затем замените флаги на `MB_YESNOCANCEL | MB_ICONWARNING` и текст на осмысленный вопрос. Перечислите все значения, которые теперь может вернуть вызов (по таблице возвратов §12.1.1 и справочнику C11), и продемонстрируйте каждое запуском с печатью результата. Что возвращает закрытие диалога «крестиком» и почему оно здесь вообще работает (сравните с `MB_YESNO`)?

**Решение.** Разберём по шагам, что именно меняется при замене флагов.

1. **Флаги `MB_`* берутся по одному из группы.** `MB_YESNOCANCEL` — из группы «набор кнопок», `MB_ICONWARNING` — из группы «значок»; они не конфликтуют и склеиваются побитовым ИЛИ (§12.1.1). Набор кнопок определяет и множество возможных возвратов: три кнопки — три исхода.
2. **Какие именно значения.** По таблице §12.1.1 и справочнику C11: `IDYES` == 6, `IDNO` == 7, `IDCANCEL` == 2. Значения `IDOK` == 1 здесь не будет: кнопки OK в наборе нет.
3. **Возврат нужно разбирать.** Диалог с вопросом, ответ которого никто не читает, — декорация (§12.1.1, «типичные ошибки»). Поэтому программа печатает и число, и имя константы.

```c
#include <windows.h>
#include <stdio.h>

int main(void)
{
    int answer = MessageBox(NULL,
                            "Save changes before exit?",
                            "Mini notepad",
                            MB_YESNOCANCEL | MB_ICONWARNING);

    printf("MessageBox returned %d", answer);
    switch (answer) {          /* три возможных исхода этого набора кнопок */
    case IDYES:    printf(" (IDYES)\n");    break;
    case IDNO:     printf(" (IDNO)\n");     break;
    case IDCANCEL: printf(" (IDCANCEL)\n"); break;
    default:       printf(" (unexpected)\n"); break;
    }
    return 0;
}
```

Программа консольная (нужен `printf`), поэтому собирается без `-mwindows`:

```
gcc -std=c17 -Wall -Wextra ask3.c -o ask3.exe -luser32
```

Четыре запуска — три кнопки и «крестик»:

```
./ask3.exe        # нажата Yes
MessageBox returned 6 (IDYES)

./ask3.exe        # нажата No
MessageBox returned 7 (IDNO)

./ask3.exe        # нажата Cancel
MessageBox returned 2 (IDCANCEL)

./ask3.exe        # диалог закрыт «крестиком»
MessageBox returned 2 (IDCANCEL)
```

**Почему «крестик» здесь работает.** Правило из справочника C11 (MessageBox): если в диалоге **есть кнопка Cancel**, то закрытие «крестиком» и клавиша Esc возвращают `IDCANCEL`; если кнопки Cancel нет, Esc и «крестик» не действуют вовсе (исключение — набор с единственной кнопкой OK: там закрытие возвращает `IDOK`, это мы видели в примере 1 §12.1.1). Логика тут простая: система должна вернуть **какой-то** ответ, и она возвращает тот, который по смыслу означает «пользователь отказался». Если такого ответа в наборе нет — отказывать нечем, и окно просто не закрывается.

Контрольный опыт с тем же вопросом, но набором `MB_YESNO`:

```c
    int answer = MessageBox(NULL,
                            "Save changes before exit?",
                            "Mini notepad",
                            MB_YESNO | MB_ICONWARNING);
```

Прогон: попытка закрыть диалог «крестиком» не даёт ничего — диалог остаётся на экране (проверено: после команды закрытия окно диалога живо, процесс продолжает ждать). Отвечает он только на нажатие Yes или No:

```
./ask_yesno.exe   # «крестик» не сработал; затем нажата No
MessageBox returned 7
```

**Ответ:** с флагами `MB_YESNOCANCEL | MB_ICONWARNING` вызов может вернуть ровно три значения — `IDYES` (6), `IDNO` (7) и `IDCANCEL` (2); все три предъявлены запусками. Закрытие «крестиком» возвращает `IDCANCEL` (2) — то же, что нажатие Cancel; работает оно потому, что в наборе есть кнопка Cancel, и система отображает на неё все способы отказаться (крестик, Esc). У `MB_YESNO` такой кнопки нет — «крестик» у него не работает совсем, и это подтверждено контрольным прогоном: диалог не закрывается, пока не нажата Yes или No. Практический вывод: если диалог обязан быть отменяемым, выбирайте набор с Cancel — `MB_OKCANCEL` или `MB_YESNOCANCEL`.

### Г12.Ч1.З3

**Условие.** Соберите логирующее окно (пример 1 §12.1.3; функцию `msg_name` напишите сами для кодов WM_NCCREATE, WM_CREATE, WM_SIZE, WM_PAINT, WM_CLOSE, WM_DESTROY — значения кодов есть в `<windows.h>` и справочнике C11). Запустите, ничего не трогая, закройте крестиком, приложите лог. Отметьте в нём: какие сообщения пришли до возврата `CreateWindowEx`; где граница «показа» окна; сколько всего сообщений пришло без единого действия пользователя, кроме закрытия. Объясните, почему лог не пуст, хотя вы «ничего не делали».

**Решение.** Программа консольная (нужен `printf`), поэтому собирается без `-mwindows`, а дескриптор модуля берётся не из `WinMain`, а функцией `GetModuleHandle(NULL)` (§12.1.2, ⛔-пример 3).

```c
/* Логирующее окно: программа консольная (нужен printf), поэтому без -mwindows */
#include <windows.h>
#include <stdio.h>

static int n = 0; /* сквозной номер сообщения */

/* Имена интересующих нас сообщений; для остальных — пустая строка */
static const char *msg_name(UINT m)
{
    switch (m) {
    case WM_NCCREATE: return " (WM_NCCREATE)";
    case WM_CREATE:   return " (WM_CREATE)";
    case WM_SIZE:     return " (WM_SIZE)";
    case WM_PAINT:    return " (WM_PAINT)";
    case WM_CLOSE:    return " (WM_CLOSE)";
    case WM_DESTROY:  return " (WM_DESTROY)";
    default:          return "";
    }
}

LRESULT CALLBACK LogProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    n++;
    printf("%3d: 0x%04X%s\n", n, uMsg, msg_name(uMsg));
    fflush(stdout);          /* лог виден сразу, а не после выхода */

    switch (uMsg) {
    case WM_DESTROY:
        PostQuitMessage(0);
        return 0;
    }
    return DefWindowProc(hwnd, uMsg, wParam, lParam);
}
```

Каркас `main` — как в §12.1.2, плюс два маркера: печать после возврата `CreateWindowEx` и печать итога после цикла.

```c
    HWND hwnd = CreateWindowEx(0, CLASS_NAME, "Message log",
                               WS_OVERLAPPEDWINDOW,
                               CW_USEDEFAULT, CW_USEDEFAULT, 480, 320,
                               NULL, NULL, hInstance, NULL);
    printf("-- CreateWindowEx has returned; showing the window --\n");
    fflush(stdout);
    if (hwnd == NULL)
        return 1;

    ShowWindow(hwnd, SW_SHOWNORMAL);

    MSG msg = {0};
    while (GetMessage(&msg, NULL, 0, 0) > 0) {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }
    printf("-- message loop is over: %d messages total --\n", n);
```

О `fflush`: вывод в файл или в конвейер буферизуется, и без сброса лог появился бы одним куском в конце — а нам важен порядок относительно маркеров.

```
gcc -std=c17 -Wall -Wextra logwin.c -o logwin.exe -luser32
./logwin.exe
```

**Что отмечено в логе.**

- **До возврата `CreateWindowEx`** пришли сообщения №1–4: маркер `-- CreateWindowEx has returned --` печатается сразу после вызова, а он стоит пятым по счёту. Среди них — `WM_NCCREATE` (№2) и `WM_CREATE` (№4) в документированном порядке, а перед ними ещё одно (№1, `0x0024` — системный запрос о допустимых размерах окна). Значит, оконная процедура начинает работать **внутри** `CreateWindowEx`, когда переменная `hwnd` ещё не присвоена. Это в точности механизм ⛔-примера 3 §12.1.2: «вежливый ноль» на `WM_NCCREATE` отменяет создание.
- **Граница показа** — маркер после №4. Всё, что ниже, — следствие `ShowWindow`: серия установочных сообщений, `WM_SIZE` (№20 — окну сообщили размер клиентской области) и `WM_PAINT` (№28 — «пора рисовать»). Первый `WM_PAINT` приходит всегда: при первом показе вся клиентская область считается «грязной» (§12.2.3).
- **Сколько всего.** До нашего единственного действия — закрытия — окно получило 28 сообщений. Всего за жизнь программы — 41. Закрытие занимает хвост: №29 (`0x0112` — `WM_SYSCOMMAND`, «выполнить команду системного меню»; именно его порождает щелчок по «крестику»), №30 — `WM_CLOSE`, который мы не обрабатываем, поэтому `DefWindowProc` вызывает `DestroyWindow`, дальше служебные, №40 — `WM_DESTROY` с нашим `PostQuitMessage`, №41 — последнее сообщение уничтожаемого окна.
- **`WM_QUIT` в логе нет.** Кода `0x0012` в 41 строке не встречается ни разу, хотя цикл завершился именно им: `PostQuitMessage` кладёт `WM_QUIT` в очередь, `GetMessage` возвращает на нём 0 и до `DispatchMessage` дело не доходит. Это же — ответ на пункт (г) задания Г12.Ч1.З5.

**Почему лог не пуст.** Потому что «ничего не делать» в событийной модели невозможно: окно — это объект системы, и система обязана согласовать с ним каждый шаг своей работы. Она спрашивает допустимые размеры, сообщает о создании неклиентской и клиентской части, об изменении размера и позиции, о получении и потере фокуса и активности, о необходимости перерисоваться. Наша процедура на 35 из 41 сообщения не отвечает ничего — их обрабатывает `DefWindowProc`, и именно поэтому «пустое» окно примера 1 §12.1.2 ведёт себя как полноценное: перетаскивается, меняет размер, закрывается. Пустой лог означал бы, что окна нет.

**Ответ:** лог содержит 41 сообщение (на эталонной машине); до возврата `CreateWindowEx` приходят четыре из них — `0x0024`, `WM_NCCREATE` (0x0081), `0x0083` и `WM_CREATE` (0x0001), то есть оконная процедура работает ещё внутри вызова, создающего окно. Граница показа — маркер после четвёртого сообщения; всё, что ниже, вызвано `ShowWindow`, включая `WM_SIZE` (№20) и первый `WM_PAINT` (№28). Без единого действия пользователя окно получило 28 сообщений, оставшиеся 13 — следствие закрытия (`WM_SYSCOMMAND` → `WM_CLOSE` → … → `WM_DESTROY` → `WM_NCDESTROY`). Лог не пуст потому, что события порождает не пользователь, а система: создание, показ, размер, активация, фокус и перерисовка — всё это сообщения, и 35 из 41 обработал за нас `DefWindowProc`.

**Вариант 2 (таблица вместо `switch`).** Имена сообщений — это данные, а не логика, и их удобно держать таблицей: добавить строку дешевле, чем добавить `case`, а саму таблицу можно потом переиспользовать (например, отсортировать или напечатать целиком).

```c
typedef struct {
    UINT        code;
    const char *name;
} MsgName;

/* Дописать строку в таблицу дешевле, чем добавить case: данные, а не код */
static const MsgName MSG_NAMES[] = {
    { WM_NCCREATE, "WM_NCCREATE" },
    { WM_CREATE,   "WM_CREATE"   },
    { WM_SIZE,     "WM_SIZE"     },
    { WM_PAINT,    "WM_PAINT"    },
    { WM_CLOSE,    "WM_CLOSE"    },
    { WM_DESTROY,  "WM_DESTROY"  },
};

static const char *msg_name(UINT m)
{
    for (size_t i = 0; i < sizeof MSG_NAMES / sizeof MSG_NAMES[0]; i++)
        if (MSG_NAMES[i].code == m)
            return MSG_NAMES[i].name;
    return NULL;             /* неизвестное сообщение — печатаем только код */
}
```

Форматирование при этом переезжает в вызывающий код — зато из таблицы уходят служебные пробелы и скобки:

```c
    const char *name = msg_name(uMsg);

    n++;
    if (name != NULL)
        printf("%3d: 0x%04X (%s)\n", n, uMsg, name);
    else
        printf("%3d: 0x%04X\n", n, uMsg);
```

Прогон даёт лог, совпадающий с первым вариантом строка в строку (те же 41 сообщение, те же номера у именованных):

```
  2: 0x0081 (WM_NCCREATE)
  4: 0x0001 (WM_CREATE)
 20: 0x0005 (WM_SIZE)
 28: 0x000F (WM_PAINT)
 30: 0x0010 (WM_CLOSE)
 40: 0x0002 (WM_DESTROY)
-- message loop is over: 41 messages total --
```

*Сравнение.* `switch` короче и не требует ни структуры, ни цикла — для шести кодов это честный выбор, и компилятор превратит его в таблицу переходов сам. Таблица выигрывает, когда имён становится много (в `<windows.h>` их сотни) или когда они нужны не только для печати: по массиву можно пройти циклом, отфильтровать, отсортировать, сосчитать статистику по кодам — со `switch` ничего этого не сделать, потому что там имена существуют только внутри кода функции. Плата — линейный поиск (для шести элементов незаметный) и разделение форматирования между таблицей и вызывающим кодом. Правило выбора то же, что и в главе 9 при выборе структуры данных: если перечень фиксирован и мал — `switch`; если перечень растёт и над ним нужны операции — данные.

### Г12.Ч1.З4

**Условие.** *(понимание)* Оконная процедура — указатель на функцию. Ответьте развёрнуто: кто и в какой момент вызывает `WindowProc` (проследите путь от события до вызова через очередь, `GetMessage` и `DispatchMessage`); где система взяла адрес нашей функции; чем эта схема совпадает со схемой `qsort` + компаратор из §6.3.3 и чем отличается (кто владеет циклом, как долго он живёт). Термин «обратный вызов» (callback) — дайте определение своими словами.

**Решение.** Разберём по пунктам условия.

**1. Кто и когда вызывает `WindowProc`.** Полный путь одного события — щелчка мышью по клиентской области:

```
пользователь щёлкает мышью
   │
   ▼
драйвер -> система: «в точке (x, y) нажата левая кнопка»
   │
   ▼
система определяет, какому ОКНУ принадлежит точка (x, y)   ← это её работа, не наша
   │
   ▼
в очередь потока, создавшего это окно, встаёт сообщение:
   MSG { hwnd = окно-адресат, message = WM_LBUTTONDOWN, wParam, lParam, ... }
   │
   ▼
наш цикл: GetMessage(&msg, ...)  — достаёт сообщение из головы очереди
   │                               (очередь пуста -> блокируется и ждёт)
   ▼
наш цикл: DispatchMessage(&msg)  — просит систему доставить сообщение адресату
   │
   ▼
СИСТЕМА: по msg.hwnd находит класс окна, в классе — поле lpfnWndProc,
         и ВЫЗЫВАЕТ по этому адресу нашу функцию:
                WindowProc(msg.hwnd, msg.message, msg.wParam, msg.lParam)
   │
   ▼
наш код внутри case WM_LBUTTONDOWN
```

Ключевой момент — предпоследняя стрелка: вызов делает **система**, изнутри `DispatchMessage`. Наш цикл сообщений её об этом просит, но кто именно и с какими аргументами дёрнет `WindowProc`, решает не он. Есть и второй путь, минующий очередь: часть сообщений система вручает оконной процедуре напрямую (§12.1.3, «отправленные и положенные»); так пришли `WM_NCCREATE` и `WM_CREATE` — внутри `CreateWindowEx`, когда цикла ещё не существовало (лог Г12.Ч1.З3, сообщения №1–4).

**2. Где система взяла адрес.** Мы отдали его сами — одной строкой при заполнении `WNDCLASS`:

```c
    wc.lpfnWndProc   = WindowProc;                  /* указатель на функцию! */
```

`RegisterClass(&wc)` скопировал структуру в системную таблицу классов процесса. С этого момента адрес нашей функции живёт в данных системы, и она вправе вызывать его когда угодно — в том числе изнутри наших же вызовов `CreateWindowEx` и `DestroyWindow`. Имя функции без скобок — это указатель на функцию (§6.3.3): преобразование неявное, никакого `&` не требуется. Обратите внимание, что связь идёт **через класс, а не через окно**: все окна одного класса делят одну процедуру — отсюда и вся тема §12.2.2 про «состояние в кармане окна».

**3. Совпадение со схемой `qsort`.** Одно и то же в обоих случаях:

| | `qsort` (§6.3.3) | оконная процедура |
|---|---|---|
| что отдаём | адрес функции-компаратора | адрес `WindowProc` в поле `lpfnWndProc` |
| кому | библиотечной функции `qsort` | системе, через `RegisterClass` |
| кто вызывает наш код | `qsort` изнутри своего цикла | система изнутри `DispatchMessage` |
| сигнатура | задана чужим кодом (`int (*)(const void *, const void *)`) | задана системой (`LRESULT CALLBACK (HWND, UINT, WPARAM, LPARAM)`) |
| наш код знает, когда его позовут | нет | нет |

Общий смысл одинаков: **инверсия управления**. Обычно наш код вызывает чужой; здесь наоборот — мы отдаём кусочек себя чужому коду, и он решает, когда его выполнить. Сигнатуру в обоих случаях диктует принимающая сторона, и отступить от неё нельзя: и `qsort`, и система вызывают по адресу, ничего не зная о нашей функции, кроме её типа.

**4. Отличия.** Их три, и все — про масштаб.

- **Кто владеет циклом.** У `qsort` цикл (сортировки) целиком внутри одного вызова: `qsort` начал, покрутил, закончил, вернул управление. У оконной процедуры цикл наш — `while (GetMessage(...) > 0)`, — но это цикл-«насос», который сам ничего не делает, кроме передачи сообщений системе. То есть у `qsort` чужой цикл вызывает наш код, а здесь наш цикл просит систему вызвать наш же код.
- **Как долго живёт.** Цикл `qsort` живёт микросекунды и умирает вместе с вызовом. Цикл сообщений живёт **всю программу**: от `ShowWindow` до `WM_QUIT`. Всё содержательное поведение программы — внутри обратных вызовов, а `WinMain` после запуска цикла не делает ничего.
- **Сколько разных событий.** Компаратор отвечает на один вопрос («кто из двух больше»), оконная процедура — на сотни разных (лог Г12.Ч1.З3: 41 сообщение за пару секунд, из них шесть кодов нам знакомы). Отсюда обязательный `default`-выход `DefWindowProc`: отвечать на все вопросы системы мы не в состоянии, и не должны.

**5. Определение своими словами.** **Обратный вызов** — это функция, которую мы пишем, но не вызываем: её адрес передаётся чужому коду, и тот вызывает её сам, когда наступит нужный ему момент. Мы задаём **что** делать, чужой код — **когда**.

**Ответ:** `WindowProc` вызывает система — изнутри `DispatchMessage` (а часть сообщений доставляет процедуре напрямую, минуя очередь: так приходят `WM_NCCREATE` и `WM_CREATE` внутри `CreateWindowEx`). Путь события: устройство → система определяет окно-адресат → сообщение встаёт в очередь потока → `GetMessage` достаёт его (на пустой очереди блокируясь) → `DispatchMessage` просит систему доставить → система по `msg.hwnd` находит класс окна, берёт из него `lpfnWndProc` и вызывает нашу функцию. Адрес система получила от нас: строка `wc.lpfnWndProc = WindowProc;` перед `RegisterClass`, где имя функции без скобок — указатель на неё (§6.3.3). Схема совпадает с `qsort` + компаратор: инверсия управления, сигнатура диктуется принимающей стороной, момент вызова нам неизвестен. Отличия: цикл `qsort` чужой, короткий и скрыт внутри одного вызова, а здесь цикл наш, но лишь качает очередь, живёт всю программу и обслуживает сотни разных кодов событий — потому и нужен `DefWindowProc` для всего необработанного. Обратный вызов — функция, которую пишем мы, а вызывает чужой код: мы задаём «что», он — «когда».

### Г12.Ч1.З5

**Условие.** *(понимание)* Составьте таблицу штатного завершения программы: четыре звена (WM_CLOSE → DestroyWindow → WM_DESTROY → PostQuitMessage → WM_QUIT → выход из цикла), и для каждого звена — что сломается, если его убрать: (а) не обрабатывать WM_CLOSE вовсе; (б) обработать WM_CLOSE, но забыть DestroyWindow; (в) не обрабатывать WM_DESTROY (проверьте запуском — ⛔ пример 3 §12.1.3); (г) почему case WM_QUIT в оконной процедуре бесполезен.

**Решение.** Сначала таблица цепочки — кто кому что посылает и кто обязан ответить.

| № | Звено | Кто это делает | Что происходит | Если звена нет |
|---|---|---|---|---|
| 1 | `WM_CLOSE` | система (по щелчку в «крестик», Alt+F4, команде системного меню) | окну **предлагают** закрыться | — (сообщение шлём не мы) |
| 2 | `DestroyWindow(hwnd)` | наш обработчик `WM_CLOSE` **или** `DefWindowProc` | окно уничтожается | окно не закрывается никогда (случай «б») |
| 3 | `WM_DESTROY` | система, при уничтожении окна | окну сообщают: «тебя сносят» | — (сообщение шлём не мы) |
| 4 | `PostQuitMessage(0)` | только наш обработчик `WM_DESTROY` | в очередь кладётся `WM_QUIT` | процесс-зомби (случай «в») |
| 5 | `WM_QUIT` → `GetMessage` вернул 0 | система + наш цикл | цикл завершается, `WinMain` доходит до `return` | — |

Видно, что из пяти строк наши в ней только две: вызвать `DestroyWindow` (или отдать `WM_CLOSE` в `DefWindowProc`) и вызвать `PostQuitMessage`. Остальное делает система.

**(а) Не обрабатывать `WM_CLOSE` вовсе.** Не ломается ничего: сообщение уходит в `DefWindowProc`, а он документированно вызывает `DestroyWindow` сам. Именно так устроен пример 1 §12.1.2, и его прогон это подтверждает: окно закрывается «крестиком», процесс завершается с кодом 0. Обрабатывать `WM_CLOSE` нужно только тогда, когда закрытие требуется **оспорить** — спросить подтверждение (пример 2 §12.1.3, задания Г12.Ч1.З8 и Г12.Ч2.З10).

**(б) Обработать `WM_CLOSE`, но забыть `DestroyWindow`.** Это самая коварная из трёх поломок: программа выглядит живой, но перестаёт закрываться.

```c
    case WM_CLOSE:
        printf("WM_CLOSE received -- and swallowed (no DestroyWindow)\n");
        fflush(stdout);
        return 0;              /* окно остаётся жить */
```

Прогон (программа консольная, чтобы видеть происходящее; закрытие пробовали дважды):

```
./close_b.exe
WM_CLOSE received -- and swallowed (no DestroyWindow)
WM_CLOSE received -- and swallowed (no DestroyWindow)
```

Проверка состояния: окно живо после обеих попыток, процесс работает. Программа честно получила просьбу закрыться, честно её рассмотрела — и ответила «нет», ничего об этом не сообщив пользователю. Снять её можно только диспетчером задач. Логика ошибки ровно та же, что в ⛔-примере §12.1.2: `return 0` означает «сообщение обработано», а обработка оказалась пустой.

**(в) Не обрабатывать `WM_DESTROY`.** Убираем `case WM_DESTROY` целиком — всё уходит в `DefWindowProc`:

```c
LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    /* никаких case: всё, включая WM_DESTROY, уходит в DefWindowProc */
    return DefWindowProc(hwnd, uMsg, wParam, lParam);
}
```

Прогон:

```
окно закрыто -> дескриптор окна больше не действителен: да
процесс завершился: нет
через 5 секунд процесс всё ещё жив: да
список процессов:  Id 22680  close_c  MainWindowTitle: (пусто)
```

Окно исчезло, процесс остался — тот самый «процесс-зомби» из ⛔-примера 3 §12.1.3, и в списке процессов он виден как программа **без единого окна**. Причина: `DefWindowProc` не зовёт `PostQuitMessage` за нас, `WM_QUIT` в очередь никто не положил, а `GetMessage` продолжает честно ждать сообщений — которых больше не будет, потому что окон нет. Отсюда дисциплина: **у главного окна `WM_DESTROY` → `PostQuitMessage` — всегда**.

**(г) Почему `case WM_QUIT` бесполезен.** Потому что `WM_QUIT` не адресован окну: у него нет `hwnd`. `PostQuitMessage` кладёт его в очередь **потока**, а `GetMessage`, встретив его, не передаёт дальше, а возвращает 0 — и цикл `while (GetMessage(...) > 0)` заканчивается прямо там. До `DispatchMessage`, а значит и до оконной процедуры, `WM_QUIT` не доходит никогда.

Это подтверждается логом из Г12.Ч1.З3 напрямую: в 41 записи кода `0x0012` (`WM_QUIT`) нет ни одной, хотя цикл завершился именно им — последнее, что увидела процедура, это `0x0082` (`WM_NCDESTROY`), а следующей строкой идёт итог после цикла. Код в `case WM_QUIT:` был бы мёртвым.

**Ответ:** цепочка завершения — `WM_CLOSE` (система предлагает закрыться) → `DestroyWindow` (наш код или `DefWindowProc`) → `WM_DESTROY` (система сообщает об уничтожении) → `PostQuitMessage` (только наш код) → `WM_QUIT` в очереди → `GetMessage` возвращает 0 → цикл завершается. Наших звеньев в ней два — `DestroyWindow` и `PostQuitMessage`. (а) Не обрабатывать `WM_CLOSE` безопасно: `DefWindowProc` вызывает `DestroyWindow` сам, окно закрывается штатно; обработчик нужен только чтобы оспорить закрытие. (б) Обработать `WM_CLOSE` и забыть `DestroyWindow` — окно перестаёт закрываться совсем (проверено: две попытки закрытия, оба раза окно живо); снять программу можно только диспетчером задач. (в) Не обрабатывать `WM_DESTROY` — окно закрывается, а процесс остаётся жить без окон (проверено: процесс `close_c` жив и через пять секунд после исчезновения окна): `WM_QUIT` некому положить в очередь, `GetMessage` ждёт вечно. (г) `case WM_QUIT` бесполезен, потому что `WM_QUIT` адресован потоку, а не окну, и гасит цикл ещё в `GetMessage`; в логе Г12.Ч1.З3 кода `0x0012` нет ни разу.

### Г12.Ч1.З6

**Условие.** *(понимание)* В ⛔-примере 3 §12.1.2 окно не создалось. Объясните механизм: какое сообщение пришло изнутри `CreateWindowEx`, какого ответа ждала система и как «вежливый ноль» заглушки превратился в отказ от создания. Почему правило «всё необработанное — в `DefWindowProc`» страхует и от этой ошибки, и от десятков подобных? Почините программу одной строкой и подтвердите запуском.

**Решение.** Воспроизведём отказ, затем разберём его и починим.

```c
/* ⛔ Оконная процедура-«заглушка»: молча съедает все сообщения */
LRESULT CALLBACK BadProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    (void)hwnd; (void)uMsg; (void)wParam; (void)lParam;
    return 0; /* НЕТ вызова DefWindowProc — и это ошибка */
}
```

```
gcc -std=c17 -Wall -Wextra create_fail.c -o create_fail.exe -luser32
./create_fail.exe
```

```
CreateWindowEx failed: the window was never created
```

```
echo $?
1
```

**Механизм.** Из лога Г12.Ч1.З3 мы знаем факт: сообщения приходят окну **до** возврата `CreateWindowEx` — там их было четыре, и вторым шёл `WM_NCCREATE` (0x0081). Это и есть ключевое сообщение: система посылает его при создании неклиентской области окна и, по справочнику C11 (WM_NCCREATE), **ждёт от обработчика TRUE**, то есть ненулевое значение, — как разрешения продолжать. Ответ 0 означает «отменить», и тогда «`CreateWindow` or `CreateWindowEx` function will return a `NULL` handle».

Наша заглушка отвечает `0` на **всё**, и на `WM_NCCREATE` тоже. Программист писал «ничего не делаю, возвращаю ноль» — а система прочла «создание запрещаю». Отсюда общее правило: у сообщений бывают **контракты на возвращаемое значение**, и `0` — не нейтральное «ок», а конкретный ответ, смысл которого у каждого сообщения свой. Проверка `hwnd == NULL` в этой программе — единственное, что превратило молчаливую катастрофу в внятную диагностику: без неё программа пошла бы вызывать `ShowWindow(NULL, ...)` и «зависла» бы в цикле сообщений для несуществующего окна.

**Почему `DefWindowProc` страхует.** Потому что он знает правильные ответы за нас — на `WM_NCCREATE` он возвращает TRUE, на `WM_CLOSE` вызывает `DestroyWindow`, на `WM_NCHITTEST` сообщает, в какую часть окна попал курсор, и так далее для сотен кодов. Мы физически не можем знать контракты всех сообщений (в логе Г12.Ч1.З3 их 41 за две секунды, и это ещё пустое окно); отдавая необработанное `DefWindowProc`, мы соглашаемся на поведение по умолчанию — то самое, которое делает «пустое» окно полноценным. Ошибка «вернуть 0 на всякий случай» ломает не одно сообщение, а любое из тех, где 0 что-то значит.

**Починка одной строкой.** Меняем `return 0;` на возврат обработчика по умолчанию:

```c
LRESULT CALLBACK GoodProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    return DefWindowProc(hwnd, uMsg, wParam, lParam); /* <-- одна изменённая строка */
}
```

```
gcc -std=c17 -Wall -Wextra create_ok.c -o create_ok.exe -luser32
./create_ok.exe
window created: ok
```

Проверка у живого окна: окно найдено, заголовок `Born at last`, видимо, закрывается «крестиком». Одна строка вернула программе всё поведение окна разом.

**Есть и другая «починка одной строкой» — и она поучительна.** Можно ответить TRUE точечно, только на `WM_NCCREATE`:

```c
    if (uMsg == WM_NCCREATE) return TRUE;  /* <-- одна добавленная строка */
    return 0;
```

Прогон показывает, что окно **создаётся** — и что этого мало:

```
./create_true.exe
window created: ok
```

```
окно найдено: да, видимо: да, заголовок: ''      <-- заголовка нет!
после команды закрытия -- окно живо: да, процесс жив: да
```

Заголовок пуст, потому что текст окна устанавливает `DefWindowProc`, обрабатывая `WM_SETTEXT`, — а мы съели и его; закрыть окно нельзя по той же причине. То есть точечный ответ чинит ровно одно сообщение из сотен, а `DefWindowProc` — все сразу. Правильная починка — первая.

**Ответ:** изнутри `CreateWindowEx` окну приходит `WM_NCCREATE`; система ждёт от обработчика ненулевого значения (TRUE) как разрешения продолжать создание, а заглушка возвращает 0 — документированный ответ «отменить», после которого `CreateWindowEx` возвращает `NULL` (прогон: `CreateWindowEx failed: the window was never created`, код возврата 1). «Вежливый ноль» превратился в отказ потому, что 0 — не нейтральное «обработано», а конкретный ответ с конкретным смыслом; у разных сообщений смысл разный. Правило «всё необработанное — в `DefWindowProc`» страхует от этой и подобных ошибок, потому что `DefWindowProc` знает контракты всех сообщений, а мы — нескольких. Починка: заменить `return 0;` на `return DefWindowProc(hwnd, uMsg, wParam, lParam);` — окно создаётся (`window created: ok`), имеет заголовок и закрывается. Альтернативная однострочная починка `if (uMsg == WM_NCCREATE) return TRUE;` создаёт окно, но оставляет его без заголовка и без реакции на закрытие — она лечит один симптом, а не причину.

### Г12.Ч1.З7

**Условие.** *(прикладное)* Напишите оконную программу-«кликер»: по каждому нажатию левой кнопки мыши в клиентской области (сообщение `WM_LBUTTONDOWN`) заголовок окна меняется на `Clicks: N`, где N — счётчик нажатий. Понадобятся: `static`-счётчик (§4.2.2), `snprintf` для сборки строки (см. введение функции в §12.2.1 — или соберите строку вручную средствами гл. 5) и `SetWindowText(hwnd, строка)`. Штатное завершение — обязательно (проверка диспетчером задач).

**Решение.** Три требования условия отображаются на три строки кода внутри одного `case`.

1. **Счётчик обязан пережить выход из функции.** Оконная процедура вызывается заново на каждое сообщение и между вызовами ничего не помнит, поэтому счётчик — `static` (§4.2.2): он размещается не в кадре стека, а рядом с глобальными данными, и инициализируется нулём один раз.
2. **Строку собираем `snprintf`-ом в буфер известного размера.** Ограничение `sizeof buf` — не формальность: длина числа не наша константа (§5.2.3).
3. **`SetWindowText(hwnd, ...)`** — у окна верхнего уровня «текст окна» и есть заголовок (§12.2.1).

```c
LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    static int clicks = 0;   /* переживает выходы из функции (§4.2.2) */

    switch (uMsg) {
    case WM_LBUTTONDOWN: {
        char title[32];
        clicks++;
        snprintf(title, sizeof title, "Clicks: %d", clicks);
        SetWindowText(hwnd, title);   /* «текст окна» верхнего уровня — заголовок */
        return 0;
    }

    case WM_DESTROY:
        PostQuitMessage(0);           /* штатное завершение — обязательно */
        return 0;
    }
    return DefWindowProc(hwnd, uMsg, wParam, lParam);
}
```

Каркас `WinMain` — из §12.1.2; начальный заголовок задан сразу правильным (`"Clicks: 0"`), чтобы окно не показывало «Hello» до первого щелчка.

```
gcc -std=c17 -Wall -Wextra clicker.c -o clicker.exe -luser32 -mwindows
./clicker.exe
```

Прогон (заголовок читается у живого окна после каждого щелчка):

```
старт      -> 'Clicks: 0'
щелчок 1   -> 'Clicks: 1'
щелчок 2   -> 'Clicks: 2'
щелчок 3   -> 'Clicks: 3'
закрытие   -> процесс завершился
```

Последняя строка — и есть «проверка диспетчером задач»: после закрытия окна процесса в списке нет. Если бы мы забыли `PostQuitMessage`, он остался бы висеть, как в Г12.Ч1.З5 (в).

Обратите внимание, чего в программе **нет**: мы не рисуем заголовок, не перерисовываем окно, не следим за тем, попал ли щелчок в кнопку. Сообщение `WM_LBUTTONDOWN` приходит только на клиентскую область (щелчок по рамке или заголовку — это другие, неклиентские сообщения), а перерисовку заголовка делает система. Наш вклад — три строки.

**⛔ Типичная неверная попытка: счётчик без `static`.** Ошибка настолько частая, что стоит увидеть её вживую:

```c
    int clicks = 0;          /* забыт static -- переменная рождается заново */
```

Программа собирается без единого предупреждения (переменная используется, инициализирована — придраться не к чему) и даже «работает»:

```
старт      -> 'Clicks: 0'
щелчок 1   -> 'Clicks: 1'
щелчок 2   -> 'Clicks: 1'
щелчок 3   -> 'Clicks: 1'
```

Первый щелчок выглядит правильным — и это худшее, что могло случиться: беглая проверка ошибку не заметит. Причина в §4.2.2: обычная локальная переменная живёт от входа в функцию до выхода, а оконная процедура входит и выходит на **каждое** сообщение; `clicks` рождается нулём, увеличивается до единицы и умирает. В событийной модели «локальное состояние обработчика» — почти всегда ошибка: состояние либо `static` (как здесь), либо, что правильнее для настоящих программ, в структуре, привязанной к окну (§12.2.2).

**Ответ:** программа-кликер состоит из обработчика `WM_LBUTTONDOWN` (`static`-счётчик, `snprintf` в буфер `char title[32]`, `SetWindowText(hwnd, title)`) и обработчика `WM_DESTROY` с `PostQuitMessage(0)`; собирается командой `gcc -std=c17 -Wall -Wextra clicker.c -o clicker.exe -luser32 -mwindows`. Прогон: заголовок последовательно принимает значения `Clicks: 1`, `Clicks: 2`, `Clicks: 3`, после закрытия окна процесс исчезает из списка процессов. Если убрать `static`, программа компилируется без предупреждений, но заголовок навсегда застревает на `Clicks: 1`: переменная создаётся заново при каждом вызове процедуры.

**Вариант 2 (строка собирается вручную, без `snprintf`).** Условие разрешает обойтись средствами главы 5 — посмотрим, из чего на самом деле состоит `%d`. Задача сводится к переводу числа в десятичные цифры: получаются они делением с остатком, то есть в обратном порядке, и их надо перевернуть.

```c
/* Записывает неотрицательное v в out как десятичные цифры и ставит '\0'.
   Буфер out обязан вмещать не меньше 11 байт (10 цифр int и терминатор). */
static void uint_to_str(unsigned v, char *out)
{
    char digits[11];
    int  n = 0;

    do {                       /* цифры получаются в обратном порядке */
        digits[n++] = (char)('0' + v % 10);
        v /= 10;
    } while (v != 0);

    for (int i = 0; i < n; i++)
        out[i] = digits[n - 1 - i];   /* переписываем задом наперёд */
    out[n] = '\0';
}
```

Цикл `do…while`, а не `while`: для нуля тело обязано выполниться хотя бы раз, иначе строка получится пустой. Символ цифры — это `'0' + значение` (§2.1.3: символы кодируются числами, и десять цифр идут подряд).

Обработчик тогда собирает заголовок из готового префикса и числа:

```c
    case WM_LBUTTONDOWN: {
        char title[32] = "Clicks: ";     /* 8 значащих символов */
        clicks++;
        uint_to_str((unsigned)clicks, title + strlen(title));
        SetWindowText(hwnd, title);
        return 0;
    }
```

`title + strlen(title)` — адрес байта-терминатора, то есть места, куда дописывать (§6.2.1: имя массива в выражении распадается в указатель на первый элемент, §6.2.2: прибавление сдвигает). Инициализация `char title[32] = "Clicks: "` заполняет нулями весь остаток массива, так что `strlen` работает по-честному.

Прогон совпадает с основным вариантом:

```
старт      -> 'Clicks: 0'
щелчок 1   -> 'Clicks: 1'
щелчок 2   -> 'Clicks: 2'
щелчок 3   -> 'Clicks: 3'
```

*Сравнение.* Основной вариант в одну строку делает то, на что второму нужны функция, два цикла и рассуждение о размере буфера, — и делает безопаснее: `snprintf` физически не выйдет за `sizeof buf`, тогда как `uint_to_str` полагается на обещание вызывающего («не меньше 11 байт»), которое компилятор не проверяет. Ручная сборка выигрывает в двух ситуациях: когда `snprintf` недоступен (микроконтроллер без полноценной стандартной библиотеки — там `printf`-семейство тянет за собой килобайты кода) и когда важно понимать, что именно происходит внутри форматирования, — а понимать полезно, потому что то же преобразование «число → цифры» лежит в основе любой печати. Для прикладного кода на настольной системе выбор однозначен: `snprintf` с `sizeof buf`.

### Г12.Ч1.З8

**Условие.** *(прикладное)* Реализуйте «вежливое закрытие» (пример 2 §12.1.3), но с `MB_YESNO` вместо `MB_OKCANCEL`: Yes — закрыться, No — остаться. Проверьте оба пути. Затем объясните обнаруженный побочный эффект: почему у диалога подтверждения перестал работать «крестик» (§12.1.1, пример 2 — свойство наборов кнопок без Cancel) и какой набор кнопок вернул бы ему смысл.

**Решение.** Обработчик `WM_CLOSE` — это то самое место, где программа получает право оспорить закрытие (§12.1.3, звено 1 цепочки завершения).

```c
    case WM_CLOSE: /* пользователь нажал «крестик» — спрашиваем подтверждение */
        if (MessageBox(hwnd, "Really quit?", "Confirm", MB_YESNO) == IDYES)
            DestroyWindow(hwnd);
        return 0;  /* No: ничего не делаем — окно живёт дальше */

    case WM_DESTROY:
        PostQuitMessage(0);
        return 0;
```

Три детали. Первым аргументом `MessageBox` идёт `hwnd` — у диалога появляется окно-владелец, и он ведёт себя как вопрос именно этого окна. Сравнение с `IDYES`, а не с `IDOK`: набор сменился, сменились и коды (Г12.Ч1.З1). И `return 0` в обеих ветках: сообщение обработано нами, `DefWindowProc` звать нельзя — иначе он закроет окно вопреки ответу «No».

```
gcc -std=c17 -Wall -Wextra polite.c -o polite.exe -luser32 -mwindows
./polite.exe
```

Прогон обоих путей:

```
окно 'Polite window' открыто
команда закрытия -> появился диалог 'Confirm'; кнопки: Yes(6), No(7)
нажата No        -> главное окно живо, процесс работает
команда закрытия -> диалог 'Confirm' снова
нажата Yes       -> окно уничтожено, процесс завершился с кодом 0
```

**Побочный эффект.** У диалога подтверждения перестал работать «крестик»: команда закрытия, посланная самому диалогу, не даёт ничего — он остаётся на экране (проверено в том же прогоне: после попытки закрыть диалог он жив, и программа продолжает ждать ответа). Причина — та же, что разобрана в Г12.Ч1.З1: закрытие «крестиком» система отображает на кнопку **Cancel**, а в наборе `MB_YESNO` её нет; отказаться нечем, поэтому запрос на закрытие игнорируется. С `MB_OKCANCEL` из примера 2 §12.1.3 такой проблемы не было — там Cancel есть, и «крестик» возвращал `IDCANCEL`, что программа читала как «остаться».

Заметим, что для пользователя это не косметика, а тупик: диалог модальный, окно-владелец на вопрос не отвечает, и единственный выход — нажать одну из двух кнопок. Вопрос «Really quit?» в наборе Yes/No безвыходен по построению — у него нет ответа «я передумал спрашивать».

**Какой набор вернул бы смысл.** Любой, содержащий Cancel: `MB_OKCANCEL` (как в примере главы) или `MB_YESNOCANCEL`, если нужны именно три исхода. Для вопроса о закрытии с несохранёнными изменениями естественен как раз третий вариант — Yes (сохранить и выйти), No (выйти без сохранения), Cancel (остаться); именно он используется в Г12.Ч2.З10.

**Ответ:** обработчик — `case WM_CLOSE: if (MessageBox(hwnd, "Really quit?", "Confirm", MB_YESNO) == IDYES) DestroyWindow(hwnd); return 0;` плюс обязательный `WM_DESTROY` → `PostQuitMessage(0)`. Прогон подтверждает оба пути: No — окно остаётся жить и работает дальше; Yes — окно уничтожается, процесс завершается с кодом 0. «Крестик» у диалога подтверждения перестал работать потому, что система отображает закрытие диалога на кнопку Cancel, а набор `MB_YESNO` её не содержит: отказаться нечем, и запрос игнорируется — диалог остаётся на экране до нажатия Yes или No. Смысл «крестику» вернул бы любой набор с Cancel: `MB_OKCANCEL` (как в примере 2 §12.1.3) или `MB_YESNOCANCEL`, если нужны три исхода.

## Часть 12.2. Виджеты, состояние и контрольный проект

### Г12.Ч2.З1

**Условие.** Соберите счётчик `counter1.c` (§12.2.1) и убедитесь в работе кнопок. Добавьте кнопку `-1` (ID 4) слева от Reset: счётчик должен уходить и в отрицательные значения. Перечислите все места программы, которые пришлось тронуть, и объясните, почему оконная процедура — ровно одно из них.

**Решение.** Сначала контрольный прогон исходного счётчика:

```
gcc -std=c17 -Wall -Wextra counter1.c -o counter1.exe -luser32 -mwindows
./counter1.exe
```

```

+1       -> '1'
+1       -> '2'
+1       -> '3'
Reset    -> '0'
```

Теперь добавляем кнопку. Правки — пять, и все механические.

**(1) Новый идентификатор.** ID — «произвольное целое, уникальное среди детей одного родителя» (§12.2.1); 1, 2, 3 заняты, берём 4:

```c
#define ID_BTN_PLUS  1
#define ID_BTN_MINUS 4 /* (1) новый идентификатор — уникальный среди детей */
#define ID_BTN_RESET 2
#define ID_LABEL     3
```

**(2) Создание виджета** в `WM_CREATE` — там же, где остальные:

```c
        /* (2) новая кнопка -- слева от Reset, то есть Reset уезжает вправо */
        CreateWindowEx(0, "BUTTON", "-1",
                       WS_CHILD | WS_VISIBLE,
                       120, 20, 80, 30,
                       hwnd, (HMENU)(INT_PTR)ID_BTN_MINUS, cs->hInstance, NULL);
```

**(3) Сдвиг Reset.** «Слева от Reset» означает, что место в точке x = 120 теперь занято, и Reset переезжает на 220 — координаты у нас жёсткие (в блокноте §12.2.4 этим займётся `WM_SIZE`).

**(4) Ветка диспетчеризации** в `WM_COMMAND`:

```c
            case ID_BTN_MINUS:   /* (4) новая ветка диспетчеризации */
                g_count--;
                show_count();
                break;
```

**(5) Ширина окна** в `WinMain`: 320 → 340, иначе третья кнопка не поместится (три кнопки по 80 плюс поля — 300 пикселей клиентской области).

```

```

Счётчик уходит в минус, как и требовалось: `g_count` — обычный `int`, ничто не мешало ему быть отрицательным и раньше, просто уменьшать его было нечем. `snprintf("%d")` печатает знак сам.

**Почему оконная процедура — ровно одно место.** Из пяти правок содержательных всего две, и обе внутри `WindowProc`: создать виджет и обработать его уведомление. Причина — в схеме §12.2.1: кнопка не обрабатывает себя сама «где-то ещё». Всё, что связано с её внешним видом и механикой нажатия (подсветка при наведении, «вдавливание», реакция на пробел и Enter, перерисовка), делает системный класс `"BUTTON"`, реализованный в `user32`, — этого кода в нашей программе нет вовсе. Наружу кнопка выдаёт ровно одно событие — `WM_COMMAND` родителю. А у родителя обработчик один: оконная процедура. Поэтому **вся логика приложения стекается в одну функцию**, и добавление кнопки — это добавление `case`, а не нового модуля, не нового цикла и не нового обработчика где-то ещё. Ровно эта централизация делает Win32-программу читаемой: чтобы понять, что делает приложение, достаточно прочитать один `switch`.

**Ответ:** после добавления кнопки `-1` (ID 4) счётчик работает в обе стороны: три `+1` дают `3`, пять `-1` доводят до `-2`, `Reset` возвращает `0`. Тронуть пришлось пять мест: новый `#define ID_BTN_MINUS 4`; вызов `CreateWindowEx` для кнопки в `WM_CREATE`; координата Reset (120 → 220, потому что новая кнопка встала слева от него); новая ветка `case ID_BTN_MINUS` в `WM_COMMAND`; ширина окна в `WinMain` (320 → 340). Содержательных из них две, и обе — в оконной процедуре: она единственное место, куда стекаются события от всех виджетов, потому что рисование и механику нажатия ведёт системный класс `"BUTTON"`, а наружу кнопка выдаёт единственное уведомление `WM_COMMAND`, адресованное родителю.

**⛔ Типичная неверная попытка: занятый идентификатор.** Выдадим новой кнопке номер 2 — тот же, что у Reset (легко получается, если ID разбросаны по файлу или пришли из разных заголовков):

```c
#define ID_BTN_MINUS 2 /* тот же номер, что у Reset! */
#define ID_BTN_RESET 2
```

Программа собирается без единого предупреждения — при условии, что в `switch` осталась одна ветка из двух. Дети созданы, у обоих `GetDlgCtrlID` возвращает 2:

```
дети (класс/ID/текст): Button:1:'+1'  Button:2:'-1'  Button:2:'Reset'  Static:3:'0'
```

Прогон:

```
старт -> '0'
+1    -> '1'
+1    -> '2'
-1    -> '1'
Reset -> '0'     <-- выглядит правильно!
Reset -> '-1'    <-- а вот и правда
```

Первое нажатие Reset при значении 1 дало 0 — и это то самое случайное совпадение, из-за которого ошибку не находят при беглой проверке. На самом деле Reset выполняет `g_count--`: `WM_COMMAND` от обеих кнопок приходит с `LOWORD(wParam) == 2`, и `switch` не может их различить — различать нечем.

Нюанс, который стоит знать: если оставить в `switch` **обе** ветки, компилятор всё-таки поймает дубликат — но не как ошибку идентификаторов, а как ошибку `switch`:

```
counter_dupid2.c: In function 'WindowProc':
counter_dupid2.c:34:13: error: duplicate case value
   34 |             case ID_BTN_RESET:
      |             ^~~~
counter_dupid2.c:30:13: note: previously used here
   30 |             case ID_BTN_MINUS:
      |             ^~~~
```

То есть страховка есть, но узкая и случайная: она срабатывает, только если оба идентификатора попали в один `switch` в виде `case`. Сами вызовы `CreateWindowEx` никто не проверяет — уникальность ID остаётся на совести программиста, как и сказано в ⛔-примере §12.2.1.

**Вариант 2 (кнопки описаны таблицей).** Каждая новая кнопка в основном решении требует правок в трёх разных местах файла — а это ровно тот случай, когда данные просятся из кода в таблицу (гл. 8 и 9). Опишем кнопку структурой: идентификатор, надпись и то, что она делает со счётчиком.

```c
typedef struct {
    int         id;       /* идентификатор дочернего окна */
    const char *caption;  /* надпись на кнопке */
    int         value;    /* дельта или новое значение */
    int         absolute; /* 1 — присвоить value, 0 — прибавить value */
} Button;

/* Добавить кнопку — значит дописать строку в эту таблицу */
static const Button BUTTONS[] = {
    { ID_BTN_PLUS,  "+1",    +1, 0 },
    { ID_BTN_MINUS, "-1",    -1, 0 },
    { ID_BTN_RESET, "Reset",  0, 1 },
};
#define BUTTON_COUNT (sizeof BUTTONS / sizeof BUTTONS[0])
```

Поле `absolute` нужно потому, что Reset выпадает из «прибавить дельту»: он присваивает. Два вида операции — два поля, и обе кнопки описываются одинаково.

Создание превращается в цикл, а координата вычисляется из номера:

```c
    case WM_CREATE: {
        CREATESTRUCT *cs = (CREATESTRUCT *)lParam;
        for (size_t i = 0; i < BUTTON_COUNT; i++)
            CreateWindowEx(0, "BUTTON", BUTTONS[i].caption,
                           WS_CHILD | WS_VISIBLE,
                           20 + (int)i * 100, 20, 80, 30,
                           hwnd, (HMENU)(INT_PTR)BUTTONS[i].id,
                           cs->hInstance, NULL);
```

Диспетчеризация — поиск по таблице вместо `switch`:

```c
/* Поиск описания кнопки по идентификатору; NULL — «не наша кнопка» */
static const Button *find_button(int id)
{
    for (size_t i = 0; i < BUTTON_COUNT; i++)
        if (BUTTONS[i].id == id)
            return &BUTTONS[i];
    return NULL;
}
...
    case WM_COMMAND:
        if (HIWORD(wParam) == BN_CLICKED) {
            const Button *b = find_button(LOWORD(wParam));
            if (b != NULL) {
                g_count = b->absolute ? b->value : g_count + b->value;
                show_count();
            }
        }
        return 0;
```

Проверка `b != NULL` обязательна: `WM_COMMAND` приходит не только от наших трёх кнопок.

Прогон совпадает с основным решением:

```
gcc -std=c17 -Wall -Wextra counter_table.c -o counter_table.exe -luser32 -mwindows
старт -> '0' | +1 -> '1' | +1 -> '2' | -1 -> '1' | Reset -> '0'
```

*Сравнение.* Основной вариант прямолинеен: три вызова `CreateWindowEx` и три `case` читаются подряд и не требуют ни структуры, ни поиска. Табличный вариант меняет три правки в разных местах файла на одну строку в таблице — и вместе с этим уносит из кода координаты: они вычисляются из номера, так что кнопки не могут «наехать» друг на друга, и переставить их местами — значит переставить строки таблицы. Плата: появилось поле `absolute`, которое существует только ради Reset (одна кнопка из трёх — «не такая»), и вместо мгновенного `switch` теперь линейный поиск. Правило выбора: пока кнопок три и все они делают разное — `switch` честнее; как только кнопок десяток и они однотипны (панель инструментов, цифровая клавиатура, палитра) — таблица, потому что новая кнопка перестаёт быть правкой кода и становится правкой данных. Ту же дилемму «код или данные» мы уже решали в Г12.Ч1.З3 с именами сообщений.

### Г12.Ч2.З2

**Условие.** Соберите проект блокнота (§12.2.4) командой `make`. Приведите протокол: полная сборка → повторный `make` (`up to date`) → `touch storage.c` + `make` → `touch storage.h` + `make` — и объясните каждый шаг через пререквизиты Makefile (§11.2.3). Почему правка `storage.h` пересобирает оба объектных файла, а правка `storage.c` — один?

**Решение.** В каталоге проекта четыре файла: `notepad.c`, `storage.c`, `storage.h`, `Makefile`. Makefile — из §12.2.4; напомним его пререквизиты, они и есть ответ на все вопросы задания:

```make
notepad.exe: notepad.o storage.o
	$(CC) notepad.o storage.o -o notepad.exe -luser32 -mwindows

notepad.o: notepad.c storage.h
	$(CC) $(CFLAGS) -c notepad.c

storage.o: storage.c storage.h
	$(CC) $(CFLAGS) -c storage.c
```

Граф зависимостей читается так:

```
notepad.exe
   ├── notepad.o ── notepad.c
   │              └─ storage.h
   └── storage.o ── storage.c
                  └─ storage.h
```

Протокол (GNU Make 4.4.1, Git Bash):

```
$ make
gcc -std=c17 -Wall -Wextra -c notepad.c
gcc -std=c17 -Wall -Wextra -c storage.c
gcc notepad.o storage.o -o notepad.exe -luser32 -mwindows
$ make
make: 'notepad.exe' is up to date.
$ touch storage.c && make
gcc -std=c17 -Wall -Wextra -c storage.c
gcc notepad.o storage.o -o notepad.exe -luser32 -mwindows
$ touch storage.h && make
gcc -std=c17 -Wall -Wextra -c notepad.c
gcc -std=c17 -Wall -Wextra -c storage.c
gcc notepad.o storage.o -o notepad.exe -luser32 -mwindows
```

**Шаг за шагом.**

1. **Полная сборка.** Цели `notepad.exe` не существует — правило выполняется; но сначала make должен получить его пререквизиты, а их тоже нет. Рекурсивно: `notepad.o` (нет) → компилируем, `storage.o` (нет) → компилируем, затем компоновка. Порядок команд — снизу вверх по графу.
2. **Повторный `make`.** Все файлы на месте, и `notepad.exe` новее обоих объектных, а те новее своих исходников. Ни одно правило не выполняется, make сообщает `'notepad.exe' is up to date.` Именно за это make и держат: он не пересобирает то, что не изменилось.
3. **`touch storage.c`.** `touch` обновляет время изменения файла, не трогая содержимое, — этого достаточно: make сравнивает **времена**, а не содержимое. Теперь `storage.c` новее `storage.o` → правило `storage.o` выполняется. Дальше `storage.o` новее `notepad.exe` → выполняется правило компоновки. А `notepad.o` не тронут: его пререквизиты (`notepad.c`, `storage.h`) не менялись. Две команды вместо трёх.
4. **`touch storage.h`.** Заголовок указан в пререквизитах **обоих** объектных файлов, поэтому устаревают оба, и пересобирается всё — три команды, как при полной сборке.

**Почему заголовок пересобирает оба, а реализация — один.** Потому что это два разных вида зависимости, и различие здесь не техническое, а смысловое.

`storage.c` — это **реализация**: её текст превращается в машинный код только внутри `storage.o`. Никто, кроме компилятора, обрабатывающего `storage.c`, её не видит; `notepad.c` про неё не знает ничего и знать не должен (§11.2.2). Изменилась реализация — устарел ровно один объектный файл. Компоновщик потом соберёт новый `storage.o` со старым `notepad.o`, и это корректно: вызовы по имени `storage_load` разрешаются на этапе компоновки (§11.2.1).

`storage.h` — это **интерфейс**, и он физически вклеивается директивой `#include` в оба `.c`-файла (§11.1.1: `#include` — буквальная подстановка текста). После препроцессора объявления из заголовка становятся частью текста и `notepad.c`, и `storage.c`. Изменение заголовка меняет **вход обоих компиляций**: у `notepad.c` — объявления функций, которые он вызывает; у `storage.c` — те же объявления, по которым он сверяет свои определения. Пересобрать нужно оба, иначе получится ровно тот «make-детектив» из Г11.Ч2.З7: половина программы собрана по старому заголовку, половина по новому, компоновщик молчит, а программа врёт.

Отсюда правило Makefile: **в пререквизитах объектного файла перечисляются все заголовки, которые он включает**. Забыть заголовок — значит получить необновлённый `.o` и молчаливо неверную программу; лишний заголовок в списке — всего лишь несколько лишних секунд компиляции.

Оговорка по платформе: на Windows GNU Make 4.4.1 сравнивает отметки времени **с точностью до секунды**, поэтому `touch` и `make`, выполненные подряд в пределах одной секунды, могут не заметить изменения — в протоколе выше между шагами выдержана пауза. На Linux (make 4.3) разрешение наносекундное, и пауза не нужна.

**Ответ:** протокол — четыре запуска: полная сборка (три команды: две компиляции и компоновка), повторный `make` (`make: 'notepad.exe' is up to date.` — ни одной команды), `touch storage.c && make` (две команды: пересборка `storage.o` и компоновка), `touch storage.h && make` (снова три команды). Объяснение через пререквизиты: make сравнивает времена изменения цели и её пререквизитов; `storage.c` — пререквизит только `storage.o`, поэтому устаревает один объектный файл, а `notepad.o` остаётся годным (вызовы разрешаются компоновщиком по именам). `storage.h` перечислен в пререквизитах **обоих** объектных файлов, потому что директивой `#include` он буквально вклеивается в оба `.c`: изменение заголовка меняет вход обеих компиляций, и пересобирать нужно оба — иначе части программы окажутся собраны по разным версиям интерфейса, компоновщик этого не заметит, а программа станет молчаливо неверной.

### Г12.Ч2.З3

**Условие.** Соберите `clicks_paint.c` (§12.2.3). Затем пересоберите без `-lgdi32` и без `-mwindows`, приведите точный текст ошибки и разберите её по методике §11.2.1: кто её выдал (компилятор или компоновщик), почему `#include <windows.h>` не лечит, что означает префикс `__imp_` и суффикс `A` в имени `__imp_TextOutA`, чем чинится. Почему вариант с `-mwindows`, но без `-lgdi32` всё-таки собирается (§12.1.2, платформенное примечание)?

**Решение.** Три сборки одного и того же исходника.

**Сборка 1 — как в главе:**

```
gcc -std=c17 -Wall -Wextra clicks_paint.c -o clicks_paint.exe -luser32 -lgdi32 -mwindows
```

Проходит молча. Прогон: в окне текст `Clicks: 0`, каждый щелчок увеличивает число. Проверено измерением ширины нарисованного текста: до щелчков правый край текста приходится на x = 73, после двенадцати щелчков (`Clicks: 12` — цифрой больше) — на x = 81. То есть цикл «клик → `InvalidateRect` → `WM_PAINT` → `TextOut`» отработал и данные дошли до пикселей.

**Сборка 2 — без `-lgdi32` и без `-mwindows`:**

```
gcc -std=c17 -Wall -Wextra clicks_paint.c -o cp_bad.exe -luser32
```

```
ld.exe: C:\Users\Max\AppData\Local\Temp\ccEvNdkN.o:clicks_paint.c:(.text+0x143): undefined reference to `__imp_TextOutA'
collect2.exe: error: ld returned 1 exit status
```

Разбор по методике §11.2.1 — по «почерку» сообщения:

- **Кто выдал.** `ld.exe` — это **компоновщик**; `collect2.exe` — обёртка, через которую его зовёт gcc. Компилятор своё дело сделал: он произвёл объектный файл (`ccEvNdkN.o` — временное имя), и в сообщении указано место в нём, `(.text+0x143)`. Значит, стадия компиляции пройдена, упало на стадии компоновки.
- **Слово `reference`.** «Ссылка без определения»: в объектном файле есть **обращение** к функции, но нигде в собираемой программе нет её **тела**. Ровно та же диагностика, что у `-lvec` в §11.2.3, только библиотека теперь системная.
- **Почему `#include <windows.h>` не лечит.** Потому что заголовок даёт **объявление**, а не определение (§11.2.1). Объявление нужно компилятору — чтобы знать типы аргументов и возврата; именно поэтому компиляция и прошла. Определение (машинный код функции) живёт в библиотеке, и его ищет компоновщик, для которого заголовков не существует вовсе. Симптом «компилируется, но не компонуется» всегда читается так: объявление есть, определения нет.
- **Префикс `__imp_`.** Функция берётся не из статической библиотеки, а из **DLL**: `gdi32.dll` — часть Windows. Обращение к такой функции идёт не напрямую, а через таблицу импорта, и символ этой таблицы компоновщик называет `__imp_` + имя функции. Тем самым в имени зашифрован и диагноз: не хватает **библиотеки импорта** (`libgdi32.a`), которая эту таблицу описывает.
- **Суффикс `A`.** Это A/W-механика из §12.1.1: `TextOut` — макрос, разворачивающийся в `TextOutA` (ANSI-вариант, `char`-строки) или `TextOutW` (UTF-16). Мы собираем в режиме по умолчанию MinGW, то есть без `UNICODE`, — препроцессор подставил `TextOutA`, и компоновщик ищет именно его. Полезное следствие: по суффиксу в сообщении сразу видно, в каком режиме собрана программа.
- **Чем чинится.** Добавить библиотеку-поставщика: `-lgdi32`. Имя функции в сообщении прямо указывает, где искать: `TextOut` — функция GDI, GDI живёт в `gdi32`.

**Сборка 3 — с `-mwindows`, но без `-lgdi32`:**

```
gcc -std=c17 -Wall -Wextra clicks_paint.c -o cp_mw.exe -luser32 -mwindows
```

Проходит молча — и это не случайность и не «магия компилятора». Ключ `-mwindows` в MinGW делает две вещи сразу, и обе видны в спецификациях драйвера (`gcc -dumpspecs`):

```
%{!m32:-m i386pep} %{m32:-m i386pe} %{mwindows:--subsystem windows} ...
%{pg:-lgmon} ... %{mwindows:-lgdi32 -lcomdlg32} ... -ladvapi32 -lshell32 -luser32 -lkernel32
```

Первая строка — про подсистему (то, что мы наблюдали в Г12.Ч1.З2): `-mwindows` добавляет компоновщику `--subsystem windows`. Вторая — библиотеки: конструкция `%{mwindows:-lgdi32 -lcomdlg32}` читается как «если задан `-mwindows`, подставить `-lgdi32 -lcomdlg32`». Вот почему `gdi32` подключается сама. Заодно в конце той же строки виден список библиотек по умолчанию — `-ladvapi32 -lshell32 -luser32 -lkernel32`: `user32` в нём есть, и потому программы главы собрались бы и без явного `-luser32`.

Оба факта — свойства **конкретного тулчейна**, а не языка и не Windows. Поэтому в главе принято правило «библиотеки пишем явно» (§12.1.2): команда сборки должна читаться как список зависимостей, а не полагаться на невидимые умолчания, которые в другом окружении окажутся другими.

**Ответ:** ошибку `undefined reference to \`__imp_TextOutA'` выдал **компоновщик** (`ld.exe`, через обёртку `collect2.exe`) — компиляция прошла, объектный файл был создан, и место обращения указано в нём (`.text+0x143`). `#include <windows.h>` не лечит, потому что заголовок даёт объявление (нужное компилятору), а недостаёт определения — машинного кода функции, который ищет компоновщик и который лежит в системной библиотеке. Префикс `__imp_` означает, что функция импортируется из DLL через таблицу импорта, то есть не хватает библиотеки импорта `libgdi32.a`; суффикс `A` — ANSI-вариант из пары A/W (§12.1.1), выбранный потому, что сборка идёт без `UNICODE`. Чинится добавлением `-lgdi32`. Вариант с `-mwindows`, но без `-lgdi32`, собирается потому, что в спецификациях MinGW прописано `%{mwindows:-lgdi32 -lcomdlg32}` — ключ подставляет обе библиотеки сам (там же видно, что `-luser32` входит в список по умолчанию); это свойство тулчейна, а не гарантия, поэтому библиотеки в командах сборки указываются явно.

### Г12.Ч2.З4

**Условие.** *(понимание)* По таблице упаковки WM_COMMAND (§12.2.1): щёлкнули кнопку Save блокнота. Выпишите, что лежит в `HIWORD(wParam)`, `LOWORD(wParam)` и `lParam` этого сообщения. Зачем нужны обе проверки — и кода уведомления, и ID? Придумайте сценарий, где проверка только ID сработает на событии, на которое реагировать не следовало (подсказка: у EDIT тоже есть уведомления, см. З8).

**Решение.** По таблице §12.2.1 для уведомления от виджета: старшее слово `wParam` — код уведомления, младшее — идентификатор виджета, `lParam` — дескриптор окна виджета. Для щелчка по Save блокнота (`#define ID_BTN_SAVE 3`):

| Поле | Значение | Смысл |
|---|---|---|
| `HIWORD(wParam)` | `BN_CLICKED` == 0 | что случилось: кнопка нажата |
| `LOWORD(wParam)` | 3 | у кого: `ID_BTN_SAVE` |
| `lParam` | `HWND` кнопки Save | чей именно дескриптор |

Проверим это не рассуждением, а измерением. В копию блокнота добавлен журнал: обработчик `WM_COMMAND` дописывает в файл разобранное сообщение и сверяет `lParam` с дескрипторами своих детей.

```c
static void log_command(const AppState *st, WPARAM wParam, LPARAM lParam)
{
    FILE *f = fopen(LOG_NAME, "a");
    if (f == NULL)
        return;
    const char *who = "?";
    if ((HWND)lParam == st->edit)          who = "EDIT";
    else if ((HWND)lParam == st->btn_load) who = "BUTTON Load";
    else if ((HWND)lParam == st->btn_save) who = "BUTTON Save";
    else if (lParam == 0)                  who = "menu or accelerator";
    fprintf(f, "WM_COMMAND: HIWORD=0x%04X LOWORD=%u lParam=%p -> %s\n",
            (unsigned)HIWORD(wParam), (unsigned)LOWORD(wParam),
            (void *)lParam, who);
    fclose(f);
}
```

Журнал прогона: щёлкнули Save, щёлкнули Load, установили текст программно, передали фокус в поле ввода.

```
WM_COMMAND: HIWORD=0x0000 LOWORD=3 lParam=00000000008a0fb0 -> BUTTON Save
WM_COMMAND: HIWORD=0x0000 LOWORD=2 lParam=000000000019114e -> BUTTON Load
WM_COMMAND: HIWORD=0x0100 LOWORD=1 lParam=00000000002e0f88 -> EDIT
```

Первая строка — ровно предсказанная таблица: `0x0000` (`BN_CLICKED`), `3`, дескриптор кнопки Save. (Адреса дескрипторов у каждого запуска свои — сверять их с числами бессмысленно, сверять с `st->btn_save` осмысленно, что журнал и делает.)

**Зачем обе проверки.** Потому что пара «ID + код уведомления» отвечает на два независимых вопроса: **кто** и **что именно** сделал. Идентификатор один на всю жизнь виджета, а событий у виджета много. Кнопка — виджет бедный на события, но и она умеет сообщать не только о нажатии; поле ввода `EDIT` присылает целый набор: `EN_SETFOCUS` (0x0100), `EN_KILLFOCUS` (0x0200), `EN_CHANGE` (0x0300), `EN_UPDATE` (0x0400), `EN_ERRSPACE` (0x0500), `EN_MAXTEXT` (0x0501), `EN_HSCROLL` (0x0601), `EN_VSCROLL` (0x0602) — все с одним и тем же `LOWORD(wParam) == ID_EDIT`. Проверка только по ID означает «реагировать на всё, что этот виджет вообще может сказать».

Есть и третий источник сообщений с той же упаковкой — меню: по таблице §12.2.1 у него `lParam == 0`, а старшее слово `wParam` нулевое, то есть неотличимое от `BN_CLICKED`. Значит, одного поля не хватает в обе стороны: по коду уведомления нельзя понять, кто отправитель, а по идентификатору — что произошло.

**Сценарий, где проверка только ID сработает не вовремя** (он же реализован в Г12.Ч2.З8). Пусть блокнот показывает в строке состояния число символов и обновляет её так:

```c
        if (LOWORD(wParam) == ID_EDIT) {   /* ⛔ код уведомления не проверен */
            show_chars(st);
            return 0;
        }
```

Пользователь нажимает Save — в строке состояния появляется `saved to notes.txt`. Затем он просто щёлкает в поле ввода, чтобы продолжить работу: поле получает фокус, шлёт родителю `WM_COMMAND` с `EN_SETFOCUS`, наш обработчик не глядя вызывает `show_chars` — и сообщение об успешном сохранении подменяется числом. Пользователь не узнал, сохранилось ли что-нибудь, хотя не сделал ничего. Прогон двух версий блокнота подряд подтверждает разницу дословно:

```
правильная версия (проверяются код и ID):
  Save          status='saved to notes.txt'
  фокус в поле  status='saved to notes.txt'

⛔ версия (проверяется только ID):
  Save          status='saved to notes.txt'
  фокус в поле  status='22 chars'
```

Ни ошибки, ни предупреждения — только испорченное поведение: типичная GUI-ошибка, которую компилятор не видит (⛔-пример 3 §12.2.1).

**Ответ:** при щелчке по Save в сообщении `WM_COMMAND` лежит: `HIWORD(wParam)` == `BN_CLICKED` (0), `LOWORD(wParam)` == 3 (`ID_BTN_SAVE`), `lParam` == дескриптор окна кнопки Save; измерение журналом даёт `HIWORD=0x0000 LOWORD=3 lParam=<HWND кнопки Save>`. Обе проверки нужны потому, что ID отвечает на вопрос «кто», а код уведомления — «что именно случилось», и у одного виджета событий много: `EDIT` шлёт `EN_SETFOCUS` (0x0100), `EN_KILLFOCUS` (0x0200), `EN_CHANGE` (0x0300), `EN_UPDATE` (0x0400) и другие — все с одинаковым `LOWORD(wParam) == ID_EDIT`; кроме того, с той же упаковкой приходят сообщения от меню (`lParam == 0`). Сценарий сбоя: счётчик символов, реагирующий только на ID, обновит строку состояния и по `EN_SETFOCUS` — то есть простое переключение фокуса в поле сотрёт сообщение `saved to notes.txt`; прогон ⛔-версии показывает `22 chars` там, где правильная версия сохраняет `saved to notes.txt`.

### Г12.Ч2.З5

**Условие.** *(понимание)* Создайте в `WinMain` программы counter1 **два** окна класса CounterClass (два вызова CreateWindowEx + ShowWindow; цикл сообщений один). Опишите наблюдаемое поведение кликов в разных окнах и объясните его через глобальные переменные. Повторите опыт с counter2 (каждому окну — своя структура AppState) и объясните разницу через «карман» GWLP_USERDATA. Какое из поведений имеет в виду документация, говоря «Each window has its own instance data»?

**Решение.** Правка одна и та же в обеих программах: вместо одного `CreateWindowEx` — два, с разными заголовками и позициями; цикл сообщений остаётся единственным, он качает очередь **потока**, а не окна.

```c
    /* Два окна одного класса — одна оконная процедура на двоих */
    HWND w1 = CreateWindowEx(0, CLASS_NAME, "Counter A", WS_OVERLAPPEDWINDOW,
                             100, 100, 320, 200, NULL, NULL, hInstance, NULL);
    HWND w2 = CreateWindowEx(0, CLASS_NAME, "Counter B", WS_OVERLAPPEDWINDOW,
                             460, 100, 320, 200, NULL, NULL, hInstance, NULL);
    if (w1 == NULL || w2 == NULL)
        return 1;
    ShowWindow(w1, nCmdShow);
    ShowWindow(w2, nCmdShow);
```

**Опыт 1: counter1 (состояние в глобалях).** Прогон, метки читаются у обоих окон после каждого щелчка:

```
старт:        A='0'  B='0'
2 клика в A:  A='0'  B='2'
1 клик  в B:  A='0'  B='3'
Reset  в A:   A='0'  B='0'
```

Наблюдаемое поведение выглядит абсурдно, но объясняется двумя строками программы:

```c
static int  g_count = 0;
static HWND g_label;     /* одна метка на всю программу — вот где беда */
```

- **Счётчик общий.** `g_count` в программе один, а окон два: щелчок в любом окне двигает одно и то же число. Два клика в A и один в B дали 3 — сумму, а не два независимых счётчика.
- **Метка одна, и это последняя созданная.** Обработчик `WM_CREATE` выполняется для каждого окна и каждый раз **перезаписывает** `g_label`. Окно B создавалось вторым, поэтому в `g_label` остался дескриптор его метки. Отсюда самое странное: щёлкаешь в окне A, а меняется цифра в окне B. Метка окна A не обновляется никогда — она так и показывает `0`, оставшийся от начального текста при создании.
- **Побочное наблюдение.** Закрытие любого из двух окон завершает всю программу: обработчик `WM_DESTROY` один на класс, и `PostQuitMessage` кладёт `WM_QUIT` в очередь потока — цикл заканчивается, второе окно исчезает вместе с процессом. Для реального многооконного приложения это отдельная задача (считать живые окна и звать `PostQuitMessage`, когда закрылось последнее), но к состоянию отношения не имеет.

Корень всех трёх эффектов один: у глобальной переменной ровно один экземпляр на программу, а у окна класса — сколько угодно экземпляров. Пока окно одно, разница незаметна; со второго окна «works well enough for small programs» заканчивается (§12.2.2).

**Опыт 2: counter2 (структура на окно).** Правка в `WinMain` — каждому окну свой адрес состояния:

```c
    /* Два состояния — по одному на окно; оба живут до конца WinMain */
    AppState state_a = {0};
    AppState state_b = {0};

    HWND w1 = CreateWindowEx(0, CLASS_NAME, "Counter A", WS_OVERLAPPEDWINDOW,
                             100, 100, 320, 200, NULL, NULL, hInstance, &state_a);
    HWND w2 = CreateWindowEx(0, CLASS_NAME, "Counter B", WS_OVERLAPPEDWINDOW,
                             460, 100, 320, 200, NULL, NULL, hInstance, &state_b);
```

Прогон:

```
старт:        A='0'  B='0'
2 клика в A:  A='2'  B='0'
1 клик  в B:  A='2'  B='1'
Reset  в A:   A='0'  B='1'
```

Теперь окна независимы полностью: свой счётчик, своя метка, `Reset` в одном не трогает другое. При этом оконная процедура **та же самая** — ни одной строки в ней не изменилось между опытами; изменилось только то, откуда она берёт данные.

Механика — из §12.2.2, по шагам для окна A:

1. `CreateWindowEx(..., &state_a)` кладёт адрес `state_a` в последний параметр.
2. Изнутри вызова окну приходит `WM_NCCREATE`; в `lParam` — указатель на `CREATESTRUCT`, а в его поле `lpCreateParams` — наш `&state_a`.
3. Обработчик прячет указатель в «карман» окна: `SetWindowLongPtr(hwnd, GWLP_USERDATA, (LONG_PTR)cs->lpCreateParams)` — и обязательно зовёт `DefWindowProc`, потому что у `WM_NCCREATE` контракт на возвращаемое значение (Г12.Ч1.З6).
4. Любой другой обработчик достаёт указатель обратно: `get_state(hwnd)` → `GetWindowLongPtr(hwnd, GWLP_USERDATA)`.

Ключевое: **карман принадлежит окну, а не классу**. Одна процедура, два окна — два кармана, два разных указателя, два разных состояния. Аргумент `hwnd`, который система передаёт первым параметром, и есть тот ключ, по которому процедура понимает, чью бухгалтерию доставать.

**Что имеет в виду документация.** Фраза «Each window has its own instance data» описывает **второе** поведение — counter2. Она о том, что данные экземпляра принадлежат окну (лежат в его кармане `GWLP_USERDATA`), а не классу и не программе. Первое поведение — прямое нарушение этого принципа: данные, которые по смыслу принадлежат экземпляру, вынесены в глобали, то есть сделаны общими на весь процесс; отсюда и общий счётчик, и чужая метка. Именно поэтому §12.2.2 называет схему «состояние в структуре, указатель — в кармане окна» правильной схемой Win32, а глобали — приёмом, работающим, пока окно одно.

**Ответ:** в counter1 два окна ведут себя так: щелчки в любом окне двигают общий `g_count`, а показывается результат только в метке **последнего созданного** окна (B), потому что `WM_CREATE` каждого окна перезаписывает единственную переменную `g_label`; метка окна A навсегда остаётся с `0`, а `Reset` в A обнуляет цифру в B — измерено: 2 клика в A дают B='2' при A='0'. Причина в том, что у глобальной переменной один экземпляр на программу, а окон у класса сколько угодно. В counter2 те же два окна независимы (A='2', B='0'; затем A='2', B='1'; `Reset` в A не трогает B) при неизменной оконной процедуре: каждому `CreateWindowEx` передан свой `&state`, указатель приезжает в `WM_NCCREATE` через `CREATESTRUCT.lpCreateParams` и прячется в карман **этого** окна `SetWindowLongPtr(GWLP_USERDATA)`, а обработчики достают его по `hwnd` — карман принадлежит окну, а не классу. Документация фразой «Each window has its own instance data» имеет в виду именно второе поведение; первое — нарушение этого принципа, незаметное ровно до появления второго окна.

### Г12.Ч2.З6

**Условие.** *(понимание)* В `do_save` (§12.2.4) разберите арифметику буфера: что именно возвращает `GetWindowTextLength`, зачем `malloc` получает `len + 1` и что передаётся вторым аргументом `GetWindowText`. Предскажите точное последствие замены на `malloc(len)` (какой байт куда не поместится) и класс ошибки по каталогу §7.2.1. Каким инструментом её поймать и как выглядел бы отчёт (по образцам §7.2.2)?

**Решение.** Три строки, три разных числа — разберём каждое.

```c
    int len = GetWindowTextLength(st->edit); /* длина без терминатора */
    char *buf = malloc((size_t)len + 1);
    ...
    GetWindowText(st->edit, buf, len + 1); /* копирует текст и ставит '\0' */
```

- **`GetWindowTextLength`** возвращает длину текста **в символах, без завершающего нуля** (C11, справочник). Для содержимого поля `line one\r\nline two` это 18: восемь букв, пробел, `\r`, `\n`, ещё восемь — терминатор не считается. Проверено на живом блокноте: файл из 33 байт после загрузки даёт `GetWindowTextLength` == 33.
- **`malloc(len + 1)`** — плюс один байт под терминатор. C-строка это не «len символов», а «len символов **и** `'\0'`» (§5.2.1); всё, что дальше передаётся в `storage_save` и `strlen`, работает только при наличии нуля.
- **Второй аргумент `GetWindowText` — это `len + 1`, размер буфера целиком, включая место под терминатор.** Функция копирует не более `n - 1` символов и **всегда** ставит `'\0'` (C11, справочник GetWindowText); при нехватке места текст усекается. Именно поэтому передаём `len + 1`, а не `len`: иначе последний символ текста был бы отброшен ради нуля.

Итого арифметика согласована: буфер `len + 1`, размер сообщён как `len + 1`, записано `len` символов плюс терминатор — ровно `len + 1` байт.

**Что будет при `malloc(len)`.** Буфер станет на байт короче, а вот размер, сообщённый функции, останется прежним — `len + 1`. `GetWindowText` честно скопирует `len` символов (индексы `0 … len-1`, они помещаются) и поставит `'\0'` в позицию `buf[len]` — **на один байт за границей блока**. Один байт записи за пределы выделенной памяти. По каталогу §7.2.1 это **переполнение буфера кучи** (heap buffer overflow, CERT C MEM35-C — «выделяй достаточно»), причём в самой коварной форме: перезаписывается всего один байт, чаще всего служебный байт кучи или соседний блок, и программа продолжает работать как ни в чём не бывало — до момента, когда куча споткнётся о собственные испорченные данные, возможно, в совсем другом месте.

**Каким инструментом ловить.** AddressSanitizer или Valgrind (§7.2.2). Под MinGW ни того, ни другого нет — санитайзеры не линкуются (журнал окружения), — поэтому дефект воспроизведён консольной моделью на Linux-контуре. Модель повторяет контракт обеих функций Win32: одна возвращает длину без терминатора, вторая копирует не больше `n - 1` символов и всегда ставит `'\0'`.

```c
/* Аналог GetWindowTextLength: длина текста БЕЗ терминатора */
static int control_text_length(void)
{
    return (int)strlen(CONTROL_TEXT);
}

/* Аналог GetWindowText: копирует не больше n-1 символов и ставит '\0' */
static int control_text(char *buf, int n)
{
    int i = 0;
    while (i < n - 1 && CONTROL_TEXT[i] != '\0') {
        buf[i] = CONTROL_TEXT[i];
        i++;
    }
    buf[i] = '\0';   /* терминатор -- всегда */
    return i;
}

int main(void)
{
    int len = control_text_length();
    printf("text length without terminator: %d\n", len);

#ifdef BUG
    char *buf = malloc((size_t)len);       /* ⛔ забыли +1 под терминатор */
#else
    char *buf = malloc((size_t)len + 1);   /* правильно */
#endif
    if (buf == NULL)
        return 1;

    control_text(buf, len + 1);            /* n -- размер буфера С терминатором */
    printf("got: [%s]\n", buf);

    free(buf);
    return 0;
}
```

Правильная версия под ASan проходит чисто:

```
gcc -std=c17 -Wall -Wextra -g -fsanitize=address model.c -o model_ok
./model_ok
text length without terminator: 18
got: [line one
line two]

```

### Г12.Ч2.З7

**Условие.** *(понимание)* Объясните выбор `"rb"`/`"wb"` в storage.c: что за байты `\r\n` приходят из EDIT; что сделал бы с ними текстовый режим `"w"` при записи на Windows (§10.2.1, C15) и что показал бы hex-дамп файла после первого же Save→Load→Save; почему в бинарном режиме цикл Save→Load возвращает в контрол в точности исходный текст.

**Решение.** Начнём с факта: что именно отдаёт многострочное поле ввода. Замер на живом блокноте — набрали две строки, нажали Save, посмотрели файл:

```
bytes: 6c 69 6e 65 20 6f 6e 65 0d 0a 6c 69 6e 65 20 74 77 6f   (18 байт)
text : line one\r\nline two
```

Между строками — **два** байта, `0d 0a`, то есть `\r\n` (CR LF). Так устроен контрол `EDIT`: перевод строки в его содержимом — это пара «возврат каретки + перевод строки», исторический формат Windows. Именно эти байты попадают в `GetWindowText`, а оттуда в `storage_save`.

**Что сделал бы текстовый режим.** Текстовый режим (`"w"`) на Windows выполняет преобразование конца строки: каждый `\n`, отданный программой, записывается на диск как пара `\r\n` (§10.2.1, C15). Но у нас `\n` уже идёт **после** своего `\r` — и режим об этом не знает, он смотрит на одиночные символы. Результат: `\r` пишется как есть, `\n` превращается в `\r\n`, вместе получается `\r\r\n`. Демонстрация — одна и та же строка, записанная двумя режимами:

```
text from EDIT: 6c 69 6e 65 20 6f 6e 65 0d 0a 6c 69 6e 65 20 74 77 6f   (18 bytes)

bin.txt      6c 69 6e 65 20 6f 6e 65 0d 0a 6c 69 6e 65 20 74 77 6f      (18 bytes)
txt.txt      6c 69 6e 65 20 6f 6e 65 0d 0d 0a 6c 69 6e 65 20 74 77 6f   (19 bytes)
```

Файл, записанный в текстовом режиме, на байт длиннее, и на месте одного `0d` теперь два.

**Что показал бы дамп после цикла Save→Load→Save.** Хуже всего то, что дефект **накапливается**: загруженный обратно текст содержит уже `\r\r\n`, и следующая запись в текстовом режиме снова удваивает единственный `\n`. Три круга подряд:

```
round 1: 6c 69 6e 65 20 6f 6e 65 0d 0d 0d 0a 6c 69 6e 65 20 74 77 6f            (20 bytes)
round 2: 6c 69 6e 65 20 6f 6e 65 0d 0d 0d 0d 0a 6c 69 6e 65 20 74 77 6f         (21 bytes)
round 3: 6c 69 6e 65 20 6f 6e 65 0d 0d 0d 0d 0d 0a 6c 69 6e 65 20 74 77 6f      (22 bytes)
```

Каждое сохранение добавляет по одному `0d` на каждый перевод строки. Через сотню сохранений файл на сотню строк распухнет на десять тысяч лишних байт, а текст в поле обрастёт мусорными символами. Заметить это на первом Save невозможно — один лишний байт в дампе; заметно становится, когда файл уже испорчен.

**Почему бинарный режим возвращает текст в точности.** Потому что бинарный режим не преобразует ничего: `fwrite` пишет байты как есть, `fread` читает байты как есть (§10.2.1). Цепочка `EDIT → GetWindowText → fwrite → файл → fread → SetWindowText → EDIT` оказывается тождественной: сколько байт вышло, столько и вернулось, в том же порядке. Замер на живом блокноте подтверждает это дважды: файл из 33 байт после Load даёт в поле ровно 33 символа (`GetWindowTextLength` == 33) и тот же текст; текст `line one\r\nline two` после Save лежит в файле как 18 байт с единственной парой `0d 0a`.

**Ещё одна причина читать в бинарном режиме — арифметика размера.** `storage_load` берёт размер файла через `fseek`/`ftell` (§10.2.2), а буфер заполняет через `fread`. В текстовом режиме эти два числа расходятся: `ftell` даёт размер файла на диске, а `fread` возвращает меньше — пары `\r\n` схлопнулись в один `\n`:

```
reading bin.txt in text mode: ftell says 18, fread returned 17
```

Вот почему в `storage_load` терминатор ставится по фактически прочитанному (`buf[got] = '\0'`), а не по размеру файла (`buf[size]`): при чтении в текстовом режиме между `got` и `size` образовался бы хвост неинициализированных байтов. В бинарном режиме `got == size`, и обе записи совпали бы — но привычка ставить терминатор по факту чтения защищает и от короткого чтения при ошибке.

**Ответ:** из EDIT приходят байты `0d 0a` (CR LF) на каждый перевод строки — так контрол хранит многострочный текст; замер на живом блокноте: `line one\r\nline two` = 18 байт с одной парой `0d 0a`. Текстовый режим `"w"` на Windows превращает каждый записываемый `\n` в пару `\r\n`, а стоящий перед ним `\r` пишет как есть — получается `\r\r\n`: тот же текст даёт 19 байт вместо 18. После каждого цикла Save→Load→Save добавляется ещё один `0d` (20, 21, 22 байта в трёх последовательных прогонах), то есть дефект накапливается и файл распухает. Бинарный режим `"rb"`/`"wb"` не преобразует ничего, поэтому цикл Save→Load возвращает в контрол ровно исходную последовательность байт (проверено: 33-байтовый файл даёт в поле 33 символа того же текста). Дополнительная причина бинарного чтения: в текстовом режиме `ftell` и `fread` расходятся (18 против 17 на том же файле), и размер буфера, вычисленный по `ftell`, перестаёт соответствовать реально прочитанному — отсюда `buf[got] = '\0'` в `storage_load`.

### Г12.Ч2.З8

**Условие.** *(прикладное)* Живой счётчик символов: строка состояния блокнота должна показывать `N chars` при каждом изменении текста. Поле EDIT шлёт родителю уведомление `EN_CHANGE` через WM_COMMAND (проверка `HIWORD(wParam) == EN_CHANGE && LOWORD(wParam) == ID_EDIT`); в обработчике возьмите `GetWindowTextLength` и обновите статус через snprintf. Учтите документированный нюанс (C11, справочник EN_CHANGE): при `ES_MULTILINE` программная установка текста через SetWindowText уведомления НЕ порождает — поэтому после do_load обновите счётчик явно. Продемонстрируйте: набор текста меняет счётчик, Load — тоже (благодаря явному вызову).

**Решение.** Изменения — три, все в `notepad.c`.

**(1) Функция показа счётчика.** Длину даёт `GetWindowTextLength` (та же, что в `do_save`, — без терминатора), строку собирает `snprintf` в буфер известного размера:

```c
/* Новое: длина текста в поле -> строка состояния */
static void show_chars(const AppState *st)
{
    char buf[32];
    int  len = GetWindowTextLength(st->edit); /* длина без терминатора */
    snprintf(buf, sizeof buf, "%d chars", len);
    SetWindowText(st->status, buf);
}
```

**(2) Обработка уведомления** — с обеими проверками, кода и идентификатора (почему обеими — разобрано в Г12.Ч2.З4):

```c
    case WM_COMMAND: {
        AppState *st = get_state(hwnd);
        /* Новое: уведомление поля ввода — проверяем И код, И идентификатор */
        if (HIWORD(wParam) == EN_CHANGE && LOWORD(wParam) == ID_EDIT) {
            show_chars(st);
            return 0;
        }
        if (HIWORD(wParam) == BN_CLICKED) {
            switch (LOWORD(wParam)) {
            case ID_BTN_LOAD: do_load(st); break;
            case ID_BTN_SAVE: do_save(st); break;
            }
        }
        return 0;
    }
```

**(3) Явный вызов после загрузки.** Документированный нюанс: при `ES_MULTILINE` установка текста через `SetWindowText` уведомления `EN_CHANGE` не порождает (C11, справочник EN_CHANGE). Значит, после загрузки счётчик остался бы от прошлого текста — обновляем сами:

```c
static void do_load(const AppState *st)
{
    char *text = storage_load(FILE_NAME);
    if (text == NULL) {
        set_status(st, "load failed: no " FILE_NAME);
        return;
    }
    SetWindowText(st->edit, text);
    free(text);
    /* SetWindowText при ES_MULTILINE уведомления EN_CHANGE не порождает,
       поэтому счётчик обновляем сами */
    show_chars(st);
}
```

Что нюанс действительно существует, видно из журнала Г12.Ч2.З4: там программная установка текста в поле не породила ни одной записи `WM_COMMAND` — а набор с клавиатуры порождает их на каждый символ.

Прогон (`make`, затем набор текста, Load, Save и переключение фокуса):

```
старт            status='ready'
набрано 'abcde'  status='5 chars'   (поле: 'abcde')
Load             status='22 chars'  (в файле 22 байта)
Save             status='saved to notes.txt'
фокус в поле     status='saved to notes.txt'
```

Обе части задания выполнены: набор текста меняет счётчик посимвольно (`EN_CHANGE` приходит на каждое нажатие), загрузка тоже обновляет его — благодаря явному вызову, а не уведомлению.

Побочный эффект, который стоит назвать честно: строка состояния теперь совмещает две роли — счётчик и сообщения об операциях, и счётчик их вытесняет. После `do_load` сообщение `loaded from notes.txt` перезаписывается счётчиком в той же функции, так что пользователь его не увидит; сообщение после Save, наоборот, живёт (сохранение текст не меняет, `EN_CHANGE` не приходит) — до первой же правки. Если бы обе роли были важны, строк состояния делают две или совмещают текст в одной (`saved to notes.txt, 22 chars`); в рамках задания достаточно понимать, что общий ресурс интерфейса теперь делят два источника.

**⛔ Типичная неверная попытка: проверять только идентификатор.** Уберём проверку кода уведомления — программа собирается без предупреждений и на первый взгляд работает:

```c
        if (LOWORD(wParam) == ID_EDIT) {   /* ⛔ код уведомления не проверен */
            show_chars(st);
            return 0;
        }
```

Тот же прогон, что и выше:

```
старт            status='ready'
набрано 'abcde'  status='5 chars'
Load             status='22 chars'
Save             status='saved to notes.txt'
фокус в поле     status='22 chars'      <-- сообщение о сохранении стёрто
```

Разница в последней строке: щелчок в поле ввода (или переход туда табуляцией) порождает `EN_SETFOCUS` — уведомление с тем же `LOWORD(wParam) == ID_EDIT`, — и обработчик, не глядя на код, обновляет счётчик, затирая сообщение о сохранении. Пользователь потерял информацию, ничего не сделав. Это тот самый сценарий, который требовалось придумать в Г12.Ч2.З4.

**Ответ:** добавлены функция `show_chars` (`GetWindowTextLength` → `snprintf(buf, sizeof buf, "%d chars", len)` → `SetWindowText(st->status, buf)`), ветка `if (HIWORD(wParam) == EN_CHANGE && LOWORD(wParam) == ID_EDIT) { show_chars(st); return 0; }` в `WM_COMMAND` и явный вызов `show_chars(st)` в конце `do_load`. Прогон: набор `abcde` даёт `5 chars` (уведомление приходит на каждый символ), Load 22-байтового файла — `22 chars` (через явный вызов, так как `SetWindowText` при `ES_MULTILINE` уведомления не порождает), Save — `saved to notes.txt`. Если убрать проверку `HIWORD`, счётчик срабатывает и на `EN_SETFOCUS`: простой щелчок в поле стирает сообщение `saved to notes.txt` и заменяет его на `22 chars`.

### Г12.Ч2.З9

**Условие.** *(прикладное)* Кнопка Clear (ID 5): очищает поле (`SetWindowText(st->edit, "")`), но сначала спрашивает подтверждение `MessageBox` с `MB_OKCANCEL | MB_ICONWARNING` (владелец — hwnd, §12.1.3 пример 2). Cancel — ничего не происходит. Обновите WM_SIZE, чтобы кнопка встала в ряд с Load/Save, и статус — `cleared` после очистки.

**Решение.** Кнопка добавляется по той же схеме, что и в Г12.Ч2.З1, но проект блокнота требует ещё двух правок: поле в структуре состояния и строка в раскладке.

**(1) Идентификатор и поле состояния.** ID 5 — первый свободный (1–4 заняты):

```c
#define ID_BTN_CLEAR 5   /* новый идентификатор — свободный среди детей */
```

Дескриптор кнопки хранится в состоянии не ради `WM_COMMAND` (там хватает ID), а ради `WM_SIZE`: раскладке нужен `HWND`, чтобы двигать окно.

**(2) Создание** — в `WM_CREATE`, нулевого размера, как и остальные (размеры выставит первый `WM_SIZE`):

```c
        st->btn_clear = CreateWindowEx(0, "BUTTON", "Clear", WS_CHILD | WS_VISIBLE,
                                       0, 0, 0, 0, hwnd, (HMENU)(INT_PTR)ID_BTN_CLEAR,
                                       cs->hInstance, NULL);
```

```c
        MoveWindow(st->btn_clear, 210, h - 80, 90,     28,      TRUE); /* третья в ряду */
```

**(4) Действие с подтверждением.** Владелец диалога — `hwnd` главного окна, набор кнопок с Cancel (в отличие от Г12.Ч1.З8, здесь «крестик» у диалога работает — есть на что его отобразить):

```c
/* Очистка с подтверждением: владелец диалога — наше окно */
static void do_clear(HWND hwnd, const AppState *st)

                   MB_OKCANCEL | MB_ICONWARNING) != IDOK)
```

Обратите внимание на порядок двух последних строк и на комментарий: очистка — это тоже программная установка текста, и `EN_CHANGE` она не порождает (нюанс из Г12.Ч2.З8). Поэтому статус `cleared` не будет тут же затёрт счётчиком `0 chars` — что для этого задания удобно, а в Г12.Ч2.З10 обернётся необходимостью взводить флаг вручную.

**(5) Диспетчеризация** — новая ветка рядом с двумя прежними; функции нужен ещё и `hwnd` (владелец диалога):

```c
            case ID_BTN_CLEAR: do_clear(hwnd, st); break;
```


Раскладка подтверждает, что кнопка встала третьей в ряд: координаты x у трёх кнопок 18, 118, 218 при одинаковых y и размерах.

**Ответ:** добавлены `#define ID_BTN_CLEAR 5`, поле `HWND btn_clear` в `AppState`, создание кнопки в `WM_CREATE`, строка `MoveWindow(st->btn_clear, 210, h - 80, 90, 28, TRUE)` в `WM_SIZE` и функция `do_clear(hwnd, st)`, которая при ответе, отличном от `IDOK`, не делает ничего, а при `IDOK` очищает поле `SetWindowText(st->edit, "")` и ставит статус `cleared`; в `WM_COMMAND` — ветка `case ID_BTN_CLEAR`. Прогон: кнопка встала третьей в ряду (x = 18, 118, 218), Cancel оставляет текст `hello world` и статус `11 chars` нетронутыми, OK очищает поле и даёт статус `cleared`. Статус после очистки не затирается счётчиком, потому что `SetWindowText` при `ES_MULTILINE` не порождает `EN_CHANGE`.

### Г12.Ч2.З10

**Условие.** *(прикладное)* Финальная ступень: защита от потери несохранённых изменений. Добавьте в AppState флаг `dirty`: ставится в обработчике EN_CHANGE (З8), снимается после успешного Save и после Load. Обработайте WM_CLOSE: если dirty — `MessageBox` c `MB_YESNOCANCEL`: Yes — сохранить и закрыться, No — закрыться без сохранения, Cancel — остаться (вернитесь к цепочке З5 части 12.1: где в ней ваш код). Проверьте все три пути и случай «закрытие с чистым флагом» (диалога быть не должно). Не забудьте: сам Load ставит текст программно — флаг не должен взводиться (нюанс З8).

**Решение.** Собираем последнюю ступень поверх Г12.Ч2.З9.

**(1) Флаг в состоянии.**

```c
typedef struct {
    HWND edit;
    HWND btn_load;
    HWND btn_save;
    HWND btn_clear;
    HWND status;
    int  dirty;   /* 1 — в тексте есть несохранённые изменения */
} AppState;
```

**(2) Где флаг взводится.** Ровно в одном месте — там, где текст правит человек:

```c
        if (HIWORD(wParam) == EN_CHANGE && LOWORD(wParam) == ID_EDIT) {
            st->dirty = 1;         /* текст правил человек */
            show_chars(st);
            return 0;
        }
```

**(3) Где снимается.** После загрузки и после **успешного** сохранения — в обоих случаях содержимое поля совпало с файлом:

```c
    SetWindowText(st->edit, text); /* программно: EN_CHANGE не придёт */
    free(text);
    st->dirty = 0;                 /* в поле ровно то, что в файле */
    show_chars(st);
```

```c
    if (rc == 0) {
        st->dirty = 0;             /* сохранили — расхождения больше нет */
        set_status(st, "saved to " FILE_NAME);
    } else {
        set_status(st, "save failed");
    }
    return rc;
```

Здесь пригодился нюанс из Г12.Ч2.З8: `SetWindowText` в `do_load` уведомления не порождает, поэтому `st->dirty = 0` не будет тут же перебит обработчиком `EN_CHANGE`. Если бы порождал, порядок «установить текст → сбросить флаг» пришлось бы защищать отдельно, а так он работает сам.

Тот же нюанс требует одной строки, которой в условии нет, но без которой защита дырява: **`do_clear` тоже меняет текст программно** — а очистка поля это самая настоящая потеря данных. Уведомления не будет, значит флаг взводим вручную:

```c
    SetWindowText(st->edit, "");
    st->dirty = 1;                 /* текст изменён программно — EN_CHANGE не будет */
```

Функции `do_load`, `do_save` и `do_clear` при этом теряют `const` у параметра: они больше не только читают состояние, но и пишут в него.

**(4) Обработчик `WM_CLOSE`.** Возвращаемся к цепочке Г12.Ч1.З5: наш код — это звено 2 (вызвать или не вызвать `DestroyWindow`); звено 4 (`PostQuitMessage` в `WM_DESTROY`) уже на месте, остальные звенья — работа системы.

```c
    case WM_CLOSE: { /* наше звено цепочки завершения: спросить и решить */
        AppState *st = get_state(hwnd);
        if (st->dirty) {
            int answer = MessageBox(hwnd, "Save changes before closing?",
                                    "Mini notepad", MB_YESNOCANCEL | MB_ICONWARNING);
            if (answer == IDCANCEL)
                return 0;                 /* остаёмся: DestroyWindow не зовём */
            if (answer == IDYES && do_save(st) != 0)
                return 0;                 /* сохранить не вышло — не теряем текст */
        }
        DestroyWindow(hwnd);              /* дальше по цепочке: WM_DESTROY */
        return 0;
    }
```

Три ветки — три исхода диалога, и все три сводятся к одному вопросу: звать `DestroyWindow` или нет. Плюс четвёртый путь: если флаг чист, диалога нет вовсе — сразу `DestroyWindow`.

Одна деталь сверх условия: при ответе Yes проверяется результат `do_save`. Если сохранение не удалось (диск заполнен, файл занят другим процессом), закрываться нельзя — иначе программа потеряет текст ровно в том сценарии, ради которого весь этот диалог и написан. Ради этой проверки `do_save` изменена так, чтобы возвращать `int` (0 — успех), как `storage_save`.

Прогон всех четырёх путей плюс контрольный опыт с Load:

```
(1) грязный + Cancel
    набрано 'draft one' -> команда закрытия -> диалог 'Mini notepad', кнопки Yes/No/Cancel
    нажата Cancel -> окно живо, текст цел ('draft one'), файла notes.txt нет

(2) грязный + No
    команда закрытия -> диалог -> нажата No
    процесс завершён; файл notes.txt так и не создан        <-- закрылись без сохранения

(3) грязный + Yes
    набрано 'saved by Yes' -> команда закрытия -> диалог -> нажата Yes
    процесс завершён; в файле: 'saved by Yes'               <-- сохранил и вышел

(4) чистый флаг
    набрано 'then saved' -> Save (status='saved to notes.txt') -> команда закрытия
    диалог не появился; процесс завершён

(5) Load снимает флаг
    Load (status='10 chars', поле='then saved') -> команда закрытия
    диалог не появился; процесс завершён
```

Пункт (5) — проверка последнего требования условия: загрузка не считается изменением, потому что `SetWindowText` не порождает `EN_CHANGE`, а `do_load` явно сбрасывает флаг.

**Ответ:** в `AppState` добавлено поле `int dirty`; оно взводится в ветке `EN_CHANGE` обработчика `WM_COMMAND` (единственное место, где текст правит человек), сбрасывается в `do_load` после установки текста и в `do_save` при `rc == 0`, и взводится вручную в `do_clear` — потому что программная установка текста уведомления не порождает. Обработчик `WM_CLOSE`: при чистом флаге сразу `DestroyWindow`; при грязном — `MessageBox(..., MB_YESNOCANCEL | MB_ICONWARNING)`, где `IDCANCEL` → `return 0` (окно живёт), `IDYES` → `do_save` и, если сохранение удалось, `DestroyWindow`, `IDNO` → `DestroyWindow` без сохранения. В цепочке завершения Г12.Ч1.З5 наш код — звено 2 (вызвать `DestroyWindow` или отказаться); звено 4, `PostQuitMessage` в `WM_DESTROY`, остаётся на месте. Прогон подтверждает все четыре пути: Cancel — окно и текст целы, файл не создан; No — процесс завершён, файл не создан; Yes — процесс завершён, в файле сохранённый текст; чистый флаг — закрытие без диалога. Load флаг не взводит (проверено отдельно: после Load закрытие проходит без вопроса).

**Вариант 2 (вместо флага — копия последнего сохранённого текста).** «Грязноту» можно не запоминать, а **вычислять**: хранить копию текста на момент последнего Save или Load и при закрытии сравнить её с текущим содержимым поля.

```c
typedef struct {
    ...
    char *saved;   /* копия текста на момент последнего Save/Load; владелец — мы */
} AppState;

/* Копия содержимого поля в куче; NULL — не хватило памяти */
static char *edit_text(HWND edit)
{
    int len = GetWindowTextLength(edit);
    char *buf = malloc((size_t)len + 1);
    if (buf == NULL)
        return NULL;
    GetWindowText(edit, buf, len + 1);
    return buf;
}

/* Запомнить текущий текст как «сохранённый» */
static void remember(AppState *st)
{
    char *copy = edit_text(st->edit);
    if (copy == NULL)
        return;               /* не смогли — старая копия остаётся, хуже не будет */
    free(st->saved);          /* free(NULL) допустим (§7.1.2) */
    st->saved = copy;
}

/* Отличается ли текст в поле от запомненного */
static int is_dirty(const AppState *st)
{
    char *cur = edit_text(st->edit);
    if (cur == NULL)
        return 1;             /* не смогли сравнить — считаем, что есть изменения */
    int dirty = (st->saved == NULL) ? (cur[0] != '\0')
                                    : (strcmp(cur, st->saved) != 0);
    free(cur);
    return dirty;
}
```

Функция `edit_text` — это выделенная из `do_save` арифметика буфера (Г12.Ч2.З6), теперь используемая трижды: при сохранении, при запоминании и при сравнении. `remember` вызывается в `WM_CREATE` (точка отсчёта — пустой текст), в конце `do_load` и при успешном `do_save`; `is_dirty` — только в `WM_CLOSE`:

```c
    case WM_CLOSE: {
        AppState *st = get_state(hwnd);
        if (is_dirty(st)) {
            ...  /* тот же диалог MB_YESNOCANCEL */
```

Владение памятью — по правилам главы 7: копию выделяем мы, освобождаем тоже мы, и последний `free` делается при сносе окна:

```c
    case WM_DESTROY: {
        AppState *st = get_state(hwnd);
        free(st->saved);      /* владелец копии — мы: освобождаем при сносе окна */
        st->saved = NULL;
        PostQuitMessage(0);
        return 0;
    }
```

Ветка `EN_CHANGE` при этом упрощается — взводить нечего:

```c
        if (HIWORD(wParam) == EN_CHANGE && LOWORD(wParam) == ID_EDIT) {
            show_chars(st);   /* флаг ставить не нужно: он не существует */
            return 0;
        }
```

`do_clear` тоже не требует особой строки: очистка изменит текст, а сравнение это заметит само.

Прогон:

```
(1) набрано 'draft' -> закрытие -> диалог есть -> Cancel -> окно живо
(2) те же пять символов стёрты (текст снова пуст) -> закрытие
    диалог НЕ появился; процесс завершён
(3) набрано 'hello copy' -> Save -> закрытие
    диалог не появился; процесс завершён; в файле 'hello copy'
```

Пункт (2) — главное отличие от основного решения. Тот же опыт на версии с флагом:

```
набрано 'draft', затем стёрто (поле пусто) -> закрытие
диалог появился                              <-- флаг взведён и не опускается
```

*Сравнение.* Флаг — одно поле `int`, две присваивающие строки и мгновенная проверка; он не требует памяти и не зависит от размера текста. Его слабость в том, что он запоминает **факт правки**, а не результат: пользователь, набравший символ и тут же его стёрший, при закрытии получит вопрос о сохранении несуществующих изменений. Хуже другое — флаг надо не забыть выставить в **каждом** месте, которое меняет текст: `do_clear` пришлось дописывать вручную именно поэтому, и любая будущая кнопка («Вставить дату», «Привести к верхнему регистру») потребует того же; забытая строка — тихая дыра в защите. Копия, наоборот, самодостаточна: изменение текста откуда угодно будет замечено, потому что вычисляется сравнением, а не запоминается, — и ложных вопросов она не задаёт. Плата: память под второй экземпляр текста (для мегабайтного файла — второй мегабайт), сравнение линейно от длины (в момент закрытия это незаметно), и появляется владение динамическим ресурсом со всеми обязанностями главы 7 — `free` при замене копии и `free` при сносе окна. Правило выбора: для небольших документов и там, где важна безошибочность защиты, лучше копия; для больших данных или когда «пользователь трогал текст» само по себе значимо (журнал правок, индикатор «изменено» в заголовке) — флаг. Настоящие редакторы обычно берут третий путь — стек операций отмены: он даёт и точное сравнение с сохранённым состоянием, и историю, но это уже структура данных из главы 9, а не поле в структуре состояния.
