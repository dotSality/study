## Часть 19.1. Обобщённые типы

### Г19.Ч1.З1

**Условие.** Напишите обобщённую функцию `smallest<T: PartialOrd>(list: &[T]) -> &T` — зеркало `largest` из §19.1.1 — и прогоните её на тех же трёх векторах (`numbers`, `letters`, `words`). До запуска предскажите все три строки вывода. Убедитесь, что тело отличается от `largest` одним символом.

**Решение.** *Предсказание.* Векторы те же, что в §19.1.1: `[34, 50, 25, 100, 65]`, `['y', 'm', 'a', 'q']`, `["pear", "apple", "watermelon"]`. Минимумы: **25**; **a** (у `char` порядок — по скалярным значениям Unicode, §17.1.4, а `a` — самая ранняя из четырёх букв); **apple** (у `&str` порядок лексикографический, и `a` < `p` < `w`).

Файл `g1.rs`:

```rust
fn smallest<T: PartialOrd>(list: &[T]) -> &T {
    let mut smallest = &list[0];
    for item in list {
        if item < smallest {
            smallest = item;
        }
    }
    smallest
}
```

```
наименьшее число: 25
наименьшая буква: a
наименьшая строка: apple
```

Предсказание совпало по всем трём строкам.

*Один символ.* Сличим тела:

```
largest:   if item > largest  { largest  = item; }
smallest:  if item < smallest { smallest = item; }
```

Различие по существу ровно одно — оператор `>` заменён на `<`; остальное (имена переменной и функции) — косметика, на которую компилятору всё равно. Это и есть подтверждение тезиса §19.1.1 «обобщение вынесло всё, кроме сути»: суть здесь — направление сравнения, и она занимает один символ.

Обратите внимание, что ограничение осталось прежним — `T: PartialOrd`. Трейт `PartialOrd` даёт типу **все четыре** оператора порядка сразу (`<`, `<=`, `>`, `>=` — R9), поэтому под `<` отдельного разрешения просить не нужно: контракт один на всё семейство.

**Ответ:** функция — листинг `g1.rs`; вывод — `наименьшее число: 25` / `наименьшая буква: a` / `наименьшая строка: apple`, предсказание совпало полностью. От `largest` тело отличается единственным значащим символом: оператором сравнения `>` → `<`; ограничение `T: PartialOrd` менять не нужно, потому что этот трейт вводит все четыре оператора порядка разом.

### Г19.Ч1.З2

**Условие.** Уберите из своей `smallest` ограничение (`<T>` вместо `<T: PartialOrd>`) и соберите. Выпишите из ошибки: код, операцию, которую не разрешил компилятор, и полный текст `help`. Затем удалите из `main` все вызовы `smallest` и соберите снова — изменилось ли что-нибудь? Объясните, почему (в чём отличие от макросов §11.1.3).

**Решение.** ⛔ Файл `g2_bad.rs` — та же функция без ограничения, `main` зовёт её на векторе чисел:

```rust
fn smallest<T>(list: &[T]) -> &T {
    let mut smallest = &list[0];
    for item in list {
        if item < smallest {
            smallest = item;
        }
    }
    smallest
}
```

```
 --> g2_bad.rs:4:17
  |
4 |         if item < smallest {
  |            ---- ^ -------- &T
  |            |
  |            &T
  |
help: consider restricting type parameter `T` with trait `PartialOrd`
  |
1 | fn smallest<T: std::cmp::PartialOrd>(list: &[T]) -> &T {
  |              ++++++++++++++++++++++
```

Выписываем требуемое:

- **код ошибки** — `E0369`;
- **операция** — бинарный оператор `<`, применённый к `&T` (компилятор дважды подписывает оба операнда: и `item`, и `smallest` имеют тип `&T`);
- **полный текст `help`** — `consider restricting type parameter `T` with trait `PartialOrd``, и следом готовая правка: сигнатура с `T: std::cmp::PartialOrd` и подчёркивание `++++++++++++++++++++++` ровно под вставленным текстом.

Заметьте деталь: компилятор предлагает **полный путь** `std::cmp::PartialOrd`, хотя короткое `PartialOrd` тоже легально — имя есть в прелюдии (§19.1.1). Полный путь — форма, которая сработает в любом окружении, в том числе если имя `PartialOrd` в вашем модуле чем-то перекрыто; правка «вслепую» обязана быть безопасной.

*Вторая половина опыта.* ⛔ Файл `g2_nocall_bad.rs` — та же функция, но `main` про неё не знает:

```rust
fn main() {
    println!("ни одного вызова smallest в этой программе нет");
}
```

```
error[E0369]: binary operation `<` cannot be applied to type `&T`
 --> g2_nocall_bad.rs:4:17
  |
4 |         if item < smallest {
  |            ---- ^ -------- &T
  |            |
  |            &T
  |
help: consider restricting type parameter `T` with trait `PartialOrd`
  |
1 | fn smallest<T: std::cmp::PartialOrd>(list: &[T]) -> &T {
  |              ++++++++++++++++++++++
```

**Ничего не изменилось** — та же ошибка, тот же код, та же строка, тот же `help`. Отличается только имя файла в шапке.

*Почему.* Тело обобщённой функции проверяется **в точке определения** (§19.1.1). Компилятор рассуждает не «какие типы сюда придут», а «что разрешено *любому* `T`»: перемещать, брать ссылку, вернуть — всё; сравнивать — нет, пока не сказано иное. Вызовы к этому рассуждению не имеют отношения: их может быть три, один или ноль. Отсюда практический вывод: **обобщённый код в Rust нельзя «спрятать» от проверки, не используя его.**

*Отличие от макросов (§11.1.3).* Макрос препроцессора — это текст, который до подстановки не существует как код. `#define` с ошибкой лежит в заголовке молча: препроцессор его не разбирает, компилятор его не видит, пока кто-нибудь не напишет вызов. Ошибка появляется **в точке использования** — и в чужих координатах: она указывает на строку вызова, а текст, который её вызвал, пришёл из другого файла. Отсюда знаменитая «лавина в чужих строках» из таблицы §19.1.3. У обобщённой функции ровно наоборот: ошибка приходит **один раз, в координатах определения**, и приходит до того, как появился хоть один пользователь.

Разница видна и по последствиям для библиотек: сломанный макрос в вашем заголовке взорвётся у того, кто его позовёт (и чинить будет он, в своём коде); сломанная обобщённая функция не даст собрать саму библиотеку — до пользователя она не доедет.

**Ответ:** код `E0369`; неразрешённая операция — бинарный `<` над `&T`; `help` — `consider restricting type parameter `T` with trait `PartialOrd`` с готовой правкой `fn smallest<T: std::cmp::PartialOrd>(list: &[T]) -> &T`. После удаления всех вызовов **не изменилось ничего**: ошибка та же. Причина — тело обобщённой функции проверяется в точке определения, «а любой ли `T` это умеет?», и число вызовов на проверку не влияет. Отличие от макросов §11.1.3: макрос — нераспознанный текст до подстановки, его ошибка возникает в точке использования и в чужих координатах; ограничение же проверяется один раз, в координатах определения, ещё до появления первого пользователя.

### Г19.Ч1.З3

**Условие.** Обобщённая структура: `struct Pair<T> { first: T, second: T }` и метод `fn swapped(self) -> Pair<T>` (в `impl<T>`), возвращающий пару с переставленными полями. Создайте `Pair` из чисел и `Pair` из `String`, переставьте обе, напечатайте поля. Объясните: почему `swapped` берёт `self` по значению и что случится с исходной парой после вызова (§16.1.3)?

**Решение.** Файл `g3.rs`:

```rust
struct Pair<T> {
    first: T,
    second: T,
}

impl<T> Pair<T> {
    fn swapped(self) -> Pair<T> {
        Pair {
            first: self.second,
            second: self.first,
        }
    }
}

fn main() {
    let nums = Pair { first: 1, second: 2 };
    let nums = nums.swapped();
    println!("числа после обмена: {} {}", nums.first, nums.second);

    let words = Pair {
        first: String::from("первый"),
        second: String::from("второй"),
    };
    let words = words.swapped();
    println!("строки после обмена: {} {}", words.first, words.second);
}
```

```
числа после обмена: 2 1
строки после обмена: второй первый
```

*Почему `self` по значению.* Потому что тело **перекладывает поля в новую пару**: `first: self.second` — это перемещение значения из старой структуры в новую. Перемещать содержимое можно только из того, чем владеешь: будь приёмник `&self`, компилятор отверг бы `self.second` с E0507 «cannot move out of … which is behind a shared reference» — мы увидим этот запрет в лицо в варианте 2. Сигнатура `fn swapped(self) -> Pair<T>` честно объявляет контракт: «отдай мне пару целиком, получи новую». Это ровно тот выбор приёмника, который §16.1.2 предписывает для методов-преобразований: `&self` — посмотреть, `&mut self` — изменить на месте, `self` — потребить и вернуть что-то новое.

Отдельно отметим, чего в сигнатуре **нет**: никакого `T: Clone` или `T: Copy`. Перекладывание владения не требует от типа ничего — это то самое «разрешено любому `T`» из §19.1.1. Поэтому один и тот же метод работает и для `Pair<i32>`, и для `Pair<String>`.

*Что случится с исходной парой.* Она **исчезнет как переменная**: значение перемещено в метод, и обращаться к старому имени больше нельзя. В листинге это скрыто затенением (`let nums = nums.swapped();` — приём §14.2.1), поэтому предъявим запрет отдельно. ⛔ Файл `g3_bad.rs` — `main` пробует читать исходную пару после вызова:

```rust
fn main() {
    let nums = Pair { first: 1, second: 2 };
    let swapped = nums.swapped();
    println!("после обмена: {} {}", swapped.first, swapped.second);
    println!("а исходная пара: {} {}", nums.first, nums.second);
}
```

```
error[E0382]: borrow of moved value: `nums`
  --> g3_bad.rs:19:52
   |
16 |     let nums = Pair { first: 1, second: 2 };
   |         ---- move occurs because `nums` has type `Pair<i32>`, which does not implement the `Copy` trait
17 |     let swapped = nums.swapped();
   |                        --------- `nums` moved due to this method call
18 |     println!("после обмена: {} {}", swapped.first, swapped.second);
19 |     println!("а исходная пара: {} {}", nums.first, nums.second);
   |                                                    ^^^^^^^^^^^ value borrowed here after move
```

Важная тонкость, ради которой опыт и поставлен на **числовой** паре: `Pair<i32>` не спасает `Copy` у поля. Пометка `Copy` — свойство *типа целиком* (§15.1.3), а `Pair` мы объявили без `derive(Copy)` — и компилятор пишет это прямым текстом: «`Pair<i32>`, which does not implement the `Copy` trait». Интуиция «внутри же числа, они копируются» здесь не работает: копируемость не наследуется от полей автоматически, её просят.

**Ответ:** код — листинг `g3.rs`, вывод `числа после обмена: 2 1` и `строки после обмена: второй первый`. `swapped` берёт `self` по значению, потому что тело **перемещает** поля в новую пару, а перемещать можно только из своего (через `&self` было бы E0507); это канонический приёмник метода-преобразования по §16.1.2, и он не требует от `T` ни `Copy`, ни `Clone`. Исходная пара после вызова **перемещена**: обращение к ней даёт `E0382: borrow of moved value` — причём и для `Pair<String>`, и для `Pair<i32>`, поскольку `Copy` не выводится из полей, а объявляется у типа.

**Вариант 2 (обмен на месте через `&mut self`).** Ту же задачу можно решить, не потребляя пару: не «сделай новую», а «переставь поля в этой». Приёмник тогда `&mut self`, а сам обмен делает знакомая по решению Г15.Ч2.З9 функция `std::mem::swap`. Файл `g3v2.rs`:

```rust
impl<T> Pair<T> {
    fn swap_in_place(&mut self) {
        std::mem::swap(&mut self.first, &mut self.second);
    }
}

fn main() {
    let mut nums = Pair { first: 1, second: 2 };
    nums.swap_in_place();
    println!("числа после обмена: {} {}", nums.first, nums.second);

    let mut words = Pair {
        first: String::from("первый"),
        second: String::from("второй"),
    };
    words.swap_in_place();
    println!("строки после обмена: {} {}", words.first, words.second);

    words.swap_in_place();
    println!("и обратно: {} {}", words.first, words.second);
}
```

```

строки после обмена: второй первый
и обратно: первый второй
```

Почему именно `mem::swap`, а не «через временную переменную», как в C? ⛔ Наивная запись не собирается — файл `g3v2_naive_bad.rs`:

```rust

        let t = self.first;
        self.first = self.second;
        self.second = t;
    }
```

```
  |                 ^^^^^^^^^^ move occurs because `self.first` has type `T`, which does not implement the `Copy` trait
  |
```

Вот и ответ на «почему `self` по значению» с другой стороны: через ссылку **вынуть** поле нельзя — структура на мгновение осталась бы с дыркой, а этого borrow checker не допускает (E0507; вторая ошибка того же прогона — на строке `self.first = self.second`). `mem::swap` существует ровно потому, что обмен — единственная перестановка, которая дырки не создаёт: два значения меняются местами одновременно.

*Сравнение.* Оба метода дают один результат, но продают его за разную цену. `swapped(self)` **потребляет** пару и возвращает новую: старое имя после вызова недоступно (E0382 выше), зато метод годится в цепочку выражений и не требует, чтобы переменная была `mut`. `swap_in_place(&mut self)` пару **сохраняет**: та же переменная живёт дальше под тем же именем, обмен можно повторить (третья строка вывода — возврат в исходное состояние), и никаких перемещений полей не происходит вовсе. Плата — требование `mut` у переменной и невозможность применить метод к временному значению или к паре за разделяемой ссылкой. Когда что предпочесть: `swapped` — когда пара логически «однократная» (построили, преобразовали, отдали дальше) и когда хочется читаемой цепочки; `swap_in_place` — когда пара живёт долго и переставляется многократно, например внутри цикла сортировки, где создавать новую структуру на каждом шаге было бы расточительно. Общее правило §16.1.2 не меняется: приёмник выбирается по судьбе значения, а не по вкусу.

### Г19.Ч1.З4

**Условие.** Три способа получить пустой `Vec<u8>`: аннотация, turbofish и `Vec::new()` с последующим `push(7u8)`. Проверьте, что все три собираются. Затем оставьте `let v = Vec::new();` без аннотации и без `push` — получите E0282. Объясните по тексту ошибки, что означает `Vec<_>` и почему `push` «чинил» программу.

**Решение.** Файл `g4.rs` — все три способа в одной программе:

```rust
fn main() {
    let a: Vec<u8> = Vec::new();
    let b = Vec::<u8>::new();
    let mut c = Vec::new();
    c.push(7u8);
    println!("a: {a:?}, b: {b:?}, c: {c:?}");
}
```

```
a: [], b: [], c: [7]
```

Собрались все три, без единого предупреждения. Способы различаются только тем, **откуда компилятор берёт `T`**:

- `let a: Vec<u8> = Vec::new();` — из аннотации слева: тип переменной известен, `Vec::new()` обязан ему соответствовать;
- `let b = Vec::<u8>::new();` — из turbofish справа: тип-аргумент передан прямо вызову, как значение в круглых скобках (§19.1.2);
- `let mut c = Vec::new(); c.push(7u8);` — из **последующего использования**: вывод типов смотрит вперёд по телу функции и видит `push` с аргументом `u8`.

Третий способ, строго говоря, даёт пустой вектор лишь на одну строку — но именно он показывает, как работает вывод типов: решение о `T` принимается не в точке `Vec::new()`, а по совокупности всего, что с переменной происходит в её области видимости.

⛔ Файл `g4_bad.rs` — ни аннотации, ни turbofish, ни `push`, и вообще ни одного использования:

```rust
fn main() {
    let v = Vec::new();
}
```

```
2 |     let v: Vec<T> = Vec::new();
  |          ++++++++
```

Отдельно стоит отметить: ошибка приходит, **даже если переменная больше нигде не встречается**. Мы проверили и вариант с использованием — файл `g4_len_bad.rs` (`let v = Vec::new();` плюс `println!("{}", v.len());`, как в §19.1.2): сообщение совпадает дословно, вплоть до координат `2:9`. Причина одна и та же: `len()` ничего не сообщает о типе элемента, а неиспользуемая переменная всё равно обязана иметь тип — «вектор неизвестно чего» не существует ни на секунду.

*Что означает `Vec<_>`.* Прочерк `_` в тексте ошибки — это **дырка, которую вывод типов не смог заполнить**: та самая «дырка под тип» из §19.1.2, показанная буквально. Компилятор дошёл до конца области видимости, собрал все известные ему факты о `v` и обнаружил, что про `T` не сказано ничего. Заметьте формулировку заголовка: не «нужна аннотация для `v`», а «type annotations needed **for `Vec<_>`**» — компилятор знает *конструктор* типа (это точно `Vec`), не знает *аргумент*. И подпись под вызовом — `type must be known at this point` — указывает не на ошибку в `Vec::new()`, а на момент, когда тип обязан определиться.

*Почему `push` «чинил» программу.* Потому что `push` — первое место, где `T` попадает в сигнатуру со **значением**: `fn push(&mut self, value: T)`. Передав `7u8`, мы сообщили `T = u8` — и дырка закрылась. Механизм тот же, что у обычного вывода типов из §14.2.1: компилятор решает уравнения по всей области видимости сразу, а не построчно сверху вниз. Отсюда и практическое правило: `Vec::new()` без пояснений законен ровно тогда, когда где-то ниже есть хоть одно использование, называющее тип элемента; если такого нет — сообщите тип сами, любым из двух явных способов.

**Ответ:** все три способа собираются, вывод `a: [], b: [], c: [7]`. Без аннотации, turbofish и `push` — `E0282: type annotations needed for `Vec<_>`` (та же ошибка и при наличии `v.len()`, дословно). `Vec<_>` означает: конструктор типа известен (`Vec`), а аргумент `T` вывод типов заполнить не смог — прочерк и есть незакрытая «дырка под тип». `push(7u8)` чинил программу потому, что `T` стоит в его сигнатуре (`fn push(&mut self, value: T)`): аргумент `7u8` даёт вывод типов уравнение `T = u8`, а решает он их по всей области видимости сразу, а не по порядку строк.

### Г19.Ч1.З5

**Условие.** *(понимание)* Даны `struct Point<T> { x: T, y: T }` и `struct Point2<T, U> { x: T, y: U }`. ### Г19.Ч1.З6

**Условие.** *(понимание)* Воспроизведите E0599 из §19.1.2 (`distance_from_origin` на `Point<i32>`). Объясните каждую часть сообщения: что значит `Point<{integer}>`, о чём говорит `note: the method was found for Point<f64>`. Ответьте: можно ли сделать такой метод доступным всем `Point<T>`, если `powi`/`sqrt` есть только у плавающих типов, — и как эту ситуацию соотнести с `impl Point<f64>` как честным компромиссом.

**Решение.** ⛔ Файл `g6_bad.rs` — структура и оба вида `impl` из §19.1.2, а в `main` добавлен вызов метода на целочисленной точке:

```rust
impl<T> Point<T> {
    fn x(&self) -> &T {
        &self.x
    }
}

impl Point<f64> {
    fn distance_from_origin(&self) -> f64 {
        (self.x.powi(2) + self.y.powi(2)).sqrt()
    }
}

fn main() {
    let integer = Point { x: 5, y: 10 };
    let float = Point { x: 1.5, y: 2.0 };
    println!("integer.x = {}", integer.x());
    println!("float: {}", float.distance_from_origin());
    println!("{}", integer.distance_from_origin());
}
```

```
error[E0599]: no method named `distance_from_origin` found for struct `Point<{integer}>` in the current scope
  --> g6_bad.rs:23:28
   |
 1 | struct Point<T> {
   | --------------- method `distance_from_origin` not found for this struct
...
23 |     println!("{}", integer.distance_from_origin());
   |                            ^^^^^^^^^^^^^^^^^^^^ method not found in `Point<{integer}>`
   |
   = note: the method was found for `Point<f64>`
```

Разбор по частям:

- **`no method named … found for struct `Point<{integer}>``** — заголовок называет приёмник вызова. `{integer}` мы разобрали в Г19.Ч1.З5: тип литералов `5` и `10` ещё не зафиксирован, и это здесь важно по существу. Компилятор не говорит «у `Point<i32>` нет метода» — он говорит «у точки *с каким-то целым* нет метода». Разница в том, что поиск метода произошёл **до** применения умолчаний: никакое целое не подошло бы, поэтому доводить вывод до `i32` незачем.
- **`struct Point<T> { … method `distance_from_origin` not found for this struct`** — вторая координата: компилятор показывает объявление типа, чтобы вы искали причину там, а не в строке вызова.
- **`^^^^ method not found in `Point<{integer}>``** — точка отказа: подчёркнуто имя метода, не приёмник. Метод как имя существует в программе; отсутствует он у *этого* инстанцирования.
- **`note: the method was found for `Point<f64>``** — самая содержательная строка. Компилятор сообщает: «метод такой есть, но он живёт у другого конкретного типа». Это прямое следствие того, что `Point<i32>` и `Point<f64>` — **два разных типа** (§19.1.2), а не «один тип с разной начинкой». Нота избавляет от получаса поисков опечатки: искать нужно не имя метода, а несовпадение инстанцирования.

*Можно ли сделать метод доступным всем `Point<T>`?* В том виде, в каком он написан, — **нет, и это не ограничение компилятора, а свойство задачи**. Тело зовёт `powi` и `sqrt`, которых у произвольного `T` нет: для `Point<String>` или `Point<bool>` «расстояние до начала координат» не определено ни математически, ни технически. Попытка объявить метод в `impl<T> Point<T>` провалилась бы прямо в определении — тем самым E0369/E0599 «у `T` нет такого метода», по правилу §19.1.1 «в теле доступно только то, что разрешено любому `T`».

Что *можно* сделать — три честных ответа, по возрастанию цены:

1. **Оставить `impl Point<f64>`** — метод существует ровно для того типа, для которого имеет смысл. Никаких требований к остальным `Point<T>`, никакого лишнего текста в сигнатурах.
2. **Расширить круг ограничением, а не типом** — `impl<T: Умеет + Умеет> Point<T>`, где перечислены нужные операции. Это условная реализация из §19.2.2 (в главе — `impl<T: Display + PartialOrd> Pair<T>`), и для арифметики она потребовала бы трейтов, которые курс не проходит. Механизм тот же: метод получают не все, а те, кто дотягивает.
3. **Продублировать реализацию** для каждого подходящего типа (`impl Point<f64>`, `impl Point<f32>`) — то есть вернуться к копипасте, от которой глава и уводит.

*Почему `impl Point<f64>` — честный компромисс.* Потому что он **не врёт в сигнатуре**. Альтернатива «сделать метод у всех и падать в рантайме на неподходящих типах» — это ровно поведение `void *` из §6.3.2: компилятор пропускает, программа взрывается у пользователя. Здесь же граница применимости зафиксирована в типе: `Point<i32>` не «сломается при вызове» — у него вызова просто нет, и узнаётся это до запуска. Тип платит только за те умения, которыми пользуется (§19.2.2), и получает ровно те методы, которые для него осмысленны.

**Ответ:** ошибка воспроизведена (`g6_bad.rs`), текст совпадает с §19.1.2 дословно. `Point<{integer}>` — приёмник вызова с ещё не зафиксированным типом целого литерала: поиск метода произошёл до применения умолчаний, потому что *никакое* целое не подошло бы. `note: the method was found for `Point<f64>`` сообщает, что метод в программе есть, но принадлежит **другому** конкретному инстанцированию — а `Point<i32>` и `Point<f64>` суть разные типы. Сделать метод доступным всем `Point<T>` нельзя: тело требует `powi`/`sqrt`, которых у произвольного `T` нет, и попытка объявить его в `impl<T>` не собралась бы в самом определении. Расширять круг следует ограничениями (условная реализация §19.2.2), а не отменой проверок. `impl Point<f64>` честен тем, что граница применимости записана в типе и проверяется до запуска, — в отличие от `void *`-подхода §6.3.2, где такой же вызов компилировался и падал в рантайме.

### Г19.Ч1.З7

*Сторона C.* Чтобы сравнение было не по памяти, а по факту, оба приёма тома I собраны и запущены — файл `g7c.c`, компилятор MinGW GCC 15.2, `-std=c17 -Wall -Wextra`:

```c
#define LARGEST(a, b) ((a) > (b) ? (a) : (b))

static int calls = 0;

static int next_reading(void) {
    calls += 1;
    printf("  next_reading вызвана, всего вызовов: %d\n", calls);
    return calls * 10;
}
```

```
1) макрос на числах: 7
2) макрос с побочным эффектом, порог 15 (побеждает порог):
  next_reading вызвана, всего вызовов: 1
  результат 15
3) тот же макрос, порог 5 (побеждает вызов):
  next_reading вызвана, всего вызовов: 1
  next_reading вызвана, всего вызовов: 2
  результат 20, хотя первый вызов вернул 10
4) макрос на разных типах: 97
5) void*: наибольшее число 100
6) void* с чужим компаратором: 19.5 (ожидали 24.25)
```

Сборка прошла **без единого предупреждения**. Читаем протокол:

- **строки 2–3** — двойное вычисление аргумента, о котором предупреждал §11.1.3, во всей красе. При пороге 15 побеждает порог, и `next_reading()` вызывается один раз; при пороге 5 побеждает вызов — и макрос вычисляет его **второй раз**, уже с другим результатом. Итог `20`, хотя сравнение выиграло значение `10`: функция вернула не то, что сравнивалось. Никакой диагностики;
- **строка 4** — `LARGEST('a', 3)` даёт `97`: типы молча приведены к общему, `char` превратился в его код. Проверки типов нет, есть арифметика препроцессора и обычных промоушенов;
- **строка 6** — `largest_void` на массиве `double` с компаратором для `int`: компилятор пропустил (казты в `void *` глушат всё), и функция уверенно вернула первый элемент `19.5` вместо максимума `24.25`. Ровно тот сценарий, который §6.3.2 называет «ошибка типа = UB».

*Итоговая таблица по трём осям* (образец — §19.1.3):

| | Макрос `LARGEST` (§11.1.3) | `void *` + компаратор (§6.3.2) | Параметр типа `largest<T>` |
|---|---|---|---|
| **когда проверяются типы** | никогда: подстановка текста, дальше — обычные промоушены (`LARGEST('a', 3)` → `97`, молча) | никогда: `void *` и казты выключают проверку (чужой компаратор пропущен) | при компиляции: тело — в определении (E0369 даже без вызовов, Г19.Ч1.З2), требования — в вызове (E0277, Г19.Ч1.З8) |
| **что происходит в рантайме** | ничего лишнего… кроме повторного вычисления аргументов: `next_reading()` позвана дважды, результат `20` вместо `10` | косвенный вызов компаратора **на каждое сравнение** плюс потеря оптимизаций; при несовпадении типов — молчаливый мусор (`19.5`) | прямой вызов конкретного экземпляра; накладных расходов ноль (R1: «вы не платите ничем во время выполнения») |
| **что лежит в бинарнике** | копия текста в каждой точке использования — как исходник, так и код | **один** экземпляр `largest_void` на все типы | **три** экземпляра `largest` (по числу использованных типов), проверено `--emit=llvm-ir` |

Строка «что лежит в бинарнике» — единственная, где Rust платит: экземпляров по числу типов. Это и есть честная цена мономорфизации, и она измеряется размером и временем сборки, а не скоростью работы.

**Ответ:** мономорфизация изготовит **три** экземпляра `largest` — по одному на `i32`, `char` и `&str`; четвёртый вызов повторяет тип третьего и нового экземпляра не создаёт. Подтверждено подсчётом определений в LLVM-IR (`--emit=llvm-ir`): три определения на четыре вызова, а контрольная программа с тремя вызовами одного типа даёт одно определение. Сравнение по трём осям — в таблице выше; ключевые факты, подтверждённые прогоном `g7c.c`: макрос вычислил аргумент дважды и вернул `20` вместо `10`, `LARGEST('a', 3)` молча выдал `97`, а `void *` с чужим компаратором вернул `19.5` вместо `24.25` — и всё это собралось без единого предупреждения.

*Почему первая ошибка указывает на вызов, а вторая — на derive.* Потому что это ошибки о разных вещах, хотя код у них один.

Первая — **несоблюдённое ограничение в точке применения**. Определение `largest` безупречно: оно требует `T: PartialOrd`, и это требование законно. Виноват не автор функции и не её текст, а *конкретная попытка* подставить в `T` тип, который требованию не отвечает. Компилятор и указывает на место попытки — на аргумент вызова, — а нотой `required by a bound in `largest`` объясняет, откуда взялось требование. Отсюда практическое правило §19.1.3: E0277 у вызова чинится **у типа**, а не ослаблением ограничений.

Вторая — отказ **внутри генерации кода**. Никакого вызова тут уже нет: `#[derive(PartialOrd)]` разворачивается в `impl PartialOrd for Reading`, а сама сигнатура трейта `PartialOrd` требует, чтобы у типа уже был `PartialEq`. Требование нарушено прямо в объявлении реализации — раньше и независимо от любых пользователей. Поэтому стрелка стоит на имени структуры, а строка `in this derive macro expansion` подписывает виновника: ошибка пришла из раскрытия derive-макроса. Нота ведёт не в ваш файл, а в `cmp.rs` стандартной библиотеки — туда, где это требование записано.

Полезно заметить и то, как меняется формулировка: `no implementation for `Reading < Reading` and `Reading > Reading`` на первой ступени (не хватает операторов **порядка**) → `no implementation for `Reading == Reading`` на второй (не хватает оператора **равенства**). Ошибка ползёт вниз по слоям: сначала нет крыши, потом выясняется, что нет фундамента.

*Что такое супертрейт.* **Супертрейт** (supertrait) — трейт, который обязан быть реализован у типа, чтобы тот мог реализовать другой трейт: «`PartialOrd` строится поверх `PartialEq`» (R9). Технически это ограничение на `Self` в объявлении трейта, синтаксически похожее на наследование (`trait PartialOrd: PartialEq`), а по смыслу — на «требуется предварительно». Логика здесь содержательная, а не бюрократическая: упорядочивание обязано согласовываться с равенством — если `a < b` ложно и `a > b` ложно, значит `a == b` должно быть истинно, иначе порядок бессмыслен. Компилятор не может проверить *согласованность* ваших реализаций, но может проверить, что базовая часть контракта вообще есть.

Мы уже видели супертрейт в деле, не зная имени: `Eq` устроен так же поверх `PartialEq` (§19.2.3), и в Г19.Ч2.З11 эта же цепочка сработает при попытке сделать свой тип ключом `HashMap`. Отсюда правило из «подводных камней» §19.1.3: не дерайвьте только вершину — читайте ноту про супертрейт и добавляйте базу.

**Ответ:** цепочка воспроизведена полностью (`g8a_bad.rs` → `g8b_bad.rs` → `g8c.rs`, итоговый вывод `Reading { celsius: 24 }`). Ступень 1 — `help: the trait `PartialOrd` is not implemented for `Reading``, `note: required by a bound in `largest``, `help: consider annotating `Reading` with `#[derive(PartialOrd)]``. Ступень 2 — `help: the trait `PartialEq` is not implemented for `Reading``, `note: required by a bound in `PartialOrd`` со ссылкой в `library\core\src\cmp.rs:1366`, `help: consider annotating `Reading` with `#[derive(PartialEq)]``. Первая ошибка указывает на вызов, потому что это несоблюдённое ограничение **в точке применения**: определение `largest` корректно, не дотягивает подставленный тип. Вторая указывает на derive, потому что отказ произошёл **внутри генерации реализации** (`in this derive macro expansion`), без всякого вызова: `impl PartialOrd for Reading` невозможен, пока нет `PartialEq`. Супертрейт — трейт, обязательный для реализации другого трейта (`PartialOrd` поверх `PartialEq`, `Eq` поверх `PartialEq`); смысл — порядок обязан согласовываться с равенством, а компилятор гарантирует хотя бы наличие базы.

### Г19.Ч1.З9

**Условие.** *(прикладное)* Напишите `fn count_above<T: PartialOrd>(items: &[T], limit: &T) -> usize` — сколько элементов строго больше порога. Прогоните на `[19, 24, 21, 30]` с порогом `21` (ответ 2) и на `["apple", "pear", "fig"]` с порогом `"banana"` (предскажите ответ до запуска). Объясните, почему порог передаётся ссылкой `&T`, а не значением `T` — проследите за владением при вызове со `String`-элементами.

**Решение.** *Предсказание для строк.* Порядок у `&str` лексикографический (§19.1.1): `"apple"` < `"banana"` (первая буква `a` < `b`); `"pear"` > `"banana"` (`p` > `b`); `"fig"` > `"banana"` (`f` > `b`). Строго больше порога — **два** элемента.

Файл `g9.rs`:

```rust
fn count_above<T: PartialOrd>(items: &[T], limit: &T) -> usize {
    let mut count = 0;
    for item in items {
        if item > limit {
            count += 1;
        }
    }
    count
}
```

```
выше 21: 2
после banana: 2
после Bob: 1
порог цел: Bob, список цел: ["Alice", "Bob", "Carol"]
```

Оба контроля сошлись: `24` и `30` больше `21`; `"pear"` и `"fig"` больше `"banana"`. Третий прогон — со `String`-элементами (`Alice`, `Bob`, `Carol`) и порогом `Bob`: строго больше только `Carol`, отсюда `1`.

Механика тела — прямая копия `largest` из §19.1.1: `for item in items` выдаёт **ссылки** на элементы (обход среза, §17.1.2), поэтому `item` имеет тип `&T`, и сравнение `item > limit` — это сравнение двух `&T`. Никакого разыменования не нужно: сравнение ссылок в Rust сравнивает то, на что они указывают, а не адреса (§19.1.1). Возвращаем `usize` — тип счётчиков и длин (§14.2.2).

*Почему порог — `&T`, а не `T`.* Короткий ответ: **чтобы вызов не съедал порог**. Развёрнутый — четвёртая строка вывода: после вызова и порог `Bob`, и весь список остались живы и распечатались. Если бы порог принимался по значению, вызывающий отдал бы его насовсем.

⛔ Проверим ровно это. Файл `g9_byvalue_bad.rs` — единственное отличие в сигнатуре (`limit: T`) и, соответственно, `*item > limit` в теле:

```rust
fn count_above<T: PartialOrd>(items: &[T], limit: T) -> usize {
    let mut count = 0;
    for item in items {
        if *item > limit {
            count += 1;
        }
    }
    count
}
```

Проследим владение по шагам (глава 15): `String` — тип с буфером в куче, `Copy` у него нет; передача по значению — перемещение; после перемещения имя `limit` в вызывающем коде недействительно; строка 19 пытается его прочитать — E0382. Функция при этом порог не хранит и не возвращает — она только сравнивает; отбирать владение ей незачем.

Заметьте, чего у сигнатуры со ссылкой **нет**: требования `T: Copy` или `T: Clone`. Приняв `limit: T`, мы бы либо навязали пользователю клонирование на каждом вызове (второй `help` компилятора — именно про это), либо сузили круг типов до копируемых, и `String` в него бы не вошёл. Ссылка снимает вопрос: сравнивать можно, не владея, — и это ровно та мысль, ради которой глава 15 вводила заимствование.

Мелкая, но показательная деталь: на числах разницы не видно. `count_above(&temps, &21)` и гипотетический `count_above(&temps, 21)` одинаково законны, потому что `i32` — `Copy`, и перемещения не происходит. Сигнатуру же выбирают по худшему случаю, а не по удобному: одна и та же обобщённая функция обязана работать и для `i32`, и для `String`.

**Ответ:** функция — листинг `g9.rs`; `[19, 24, 21, 30]` с порогом `21` → **2** (`24` и `30`); `["apple", "pear", "fig"]` с порогом `"banana"` → **2** (`"pear"` и `"fig"`; предсказание совпало), контрольный прогон со `String` даёт `1`. Порог передаётся `&T`, потому что функция порог только читает: по значению вызов **перемещал** бы его, и после вызова переменная стала бы недоступна — `E0382: borrow of moved value` с нотой компилятора `this parameter takes ownership of the value`. Ссылка вдобавок избавляет от требования `T: Copy`/`T: Clone`: обобщённая функция обязана обслуживать и `i32`, и `String`, а на `i32` разница незаметна только потому, что он копируется.

**Вариант 2 (индексный обход, C-школа).** Тот же счёт можно вести не обходом по ссылкам, а по индексам — так, как писался бы цикл в томе I. Файл `g9v2.rs`:

```rust
fn count_above<T: PartialOrd>(items: &[T], limit: &T) -> usize {
    let mut count = 0;
    let mut i = 0;
    while i < items.len() {
        if items[i] > *limit {
            count += 1;
        }
        i += 1;
    }
    count
}
```

```
выше 21: 2
после banana: 2
```

Результаты те же. Изменились две детали, и обе поучительны: `items[i]` — это уже **значение** типа `T` (индексация среза даёт элемент, а не ссылку на него), поэтому справа приходится писать `*limit`, разыменовывая порог; и появился ручной счётчик `i` с обязанностью не забыть `i += 1`.

*Сравнение.* Обход по ссылкам (`for item in items`) короче и безопаснее: индекса нет — значит, нет и класса ошибок «вышел за границу», «забыл увеличить», «увеличил дважды»; сравнение идёт между двумя `&T`, звёздочки не нужны вовсе. Индексный вариант длиннее на две строки и требует внимания к разыменованию, зато даёт то, чего у обхода по ссылкам нет: **позицию**. Пока задача — «посчитать», это никому не нужно; как только понадобится «сказать, где именно» (или пройти список задом наперёд, или сравнивать соседей `items[i]` и `items[i - 1]`), индексная форма становится единственной доступной на материале главы — так и сделано в варианте 2 к Г19.Ч1.З10. Практическое правило: по умолчанию — обход по ссылкам, индексы — когда индекс действительно участвует в задаче. Обе формы, к слову, в рантайме проверяют границы: `items[i]` при выходе за длину даст панику (§18.1.1), а не мусор, как в C.

Реализуйте (в `impl<T>`) метод `fn describe(&self) -> String`, использующий `format!` и поле `label`, и обобщённую функцию `fn max_sample<T: PartialOrd>(items: &[Sample<T>]) -> &Sample<T>`, сравнивающую по `value`. Прогоните на замерах температуры (`i32`) и напряжения (`f64`). До запуска предскажите, метод `describe` каких инстанцирований попадёт в бинарник — и объясните ответ мономорфизацией.

**Решение.** *Предсказание.* В бинарник попадут **два** экземпляра `describe`: для `Sample<i32>` и для `Sample<f64>`. Метод объявлен в `impl<T> Sample<T>`, то есть существует для всех `Sample<T>`, но мономорфизация штампует код не для «всех», а для **фактически использованных** типов (§19.1.3). Программа создаёт замеры двух видов — значит, экземпляров два. Тонкость, которую стоит проговорить заранее: тело `describe` не трогает `value` вовсе — оно работает только с `label: String`, одинаковым у всех инстанцирований. Логика подсказывает «хватило бы одной копии», но мономорфизация рассуждает по сигнатуре, а не по телу: `&self` — это `&Sample<i32>` или `&Sample<f64>`, разные типы с разной раскладкой памяти, и код обращения к полю у них разный.

Файл `g10.rs`:

```rust
struct Sample<T> {
    label: String,
    value: T,
}

impl<T> Sample<T> {
    fn describe(&self) -> String {
        format!("замер «{}»", self.label)
    }
}

fn max_sample<T: PartialOrd>(items: &[Sample<T>]) -> &Sample<T> {
    let mut best = &items[0];
    for item in items {
        if item.value > best.value {
            best = item;
        }
    }
    best
}
```

```
замер «день»: 24 °C
замер «холостой ход»: 4.98 В
```

Проверяем предсказание тем же приёмом, что в Г19.Ч1.З7, — `rustc --edition 2024 --emit=llvm-ir g10.rs -o g10.ll`:

```

@_RINvCsiLPkis0b4k_3g1010max_samplelEB2_
@_RNvMCsiLPkis0b4k_3g10INtB2_6SampledE8describeB2_
@_RNvMCsiLPkis0b4k_3g10INtB2_6SamplelE8describeB2_
```

Два экземпляра `describe` и два `max_sample` — предсказание подтверждено. Здесь искажённые имена читаются почти по-человечески: `Sampled` и `Samplel` — это `Sample<f64>` и `Sample<i32>` (буквы `d` и `l` кодируют типы, те же, что мы видели в Г19.Ч1.З7), а `8describe` — имя метода с длиной. Видно и то, что метод принадлежит **типу**: в имени сначала инстанцированный `Sample`, потом метод.

*Разбор устройства.* Три вещи в этой задаче стоит заметить.

**Первое: `impl<T>` без ограничений.** `describe` не требует от `T` ничего — и правильно, потому что тела `format!("замер «{}»", self.label)` касается только поле `label`. Правило минимальности §19.1.3 в действии: не просите умений, которыми не пользуетесь. Если бы мы написали `impl<T: Display> Sample<T>`, метод `describe` пропал бы у всех замеров с непечатаемым значением — без всякой причины.

**Второе: ограничение — у функции, а не у структуры.** `max_sample` требует `T: PartialOrd`, потому что сравнивает `item.value > best.value`. Структура же объявлена без ограничений: `Sample<T>` можно построить для любого типа значения, а сравнивать — только для сравнимого. Это тот же «этажный» приём, что у `Pair::new` и `show_larger` в §19.2.2: базовая возможность — всем, дополнительная — тем, кто дотягивает.

**Третье: почему `&Sample<T>`, а не `Sample<T>`.** Вернуть замер по значению функция не может: она получила срез по ссылке и не владеет элементами, а вынуть один наружу — значит либо забрать владение (нельзя, срез чужой), либо клонировать (потребовало бы `T: Clone` и ещё `String: Clone` для метки). Ссылка на найденный элемент — единственный честный ответ, и он же самый дешёвый. Ровно так устроен `largest` из §19.1.1, и по той же причине.

**Ответ:** код — листинг `g10.rs`, вывод `замер «день»: 24 °C` и `замер «холостой ход»: 4.98 В`. В бинарник попадут **два** экземпляра `describe` — для `Sample<i32>` и `Sample<f64>`; подтверждено подсчётом определений в LLVM-IR (`Sampled`/`Samplel` — `Sample<f64>` и `Sample<i32>`), рядом столько же экземпляров `max_sample`. Объяснение мономорфизацией: компилятор штампует по экземпляру на каждый **использованный** набор типов, а не на каждое объявление; и делает это по сигнатуре, а не по телу — хотя `describe` читает только `label`, приёмник `&self` у двух инстанцирований имеет разные типы, поэтому копии всё равно две.

**Вариант 2 (поиск позиции вместо ссылки).** Вместо ссылки на лучший элемент функция может вернуть его **индекс**. Файл `g10v2.rs`:

```rust
fn max_sample_index<T: PartialOrd>(items: &[Sample<T>]) -> usize {
    let mut best = 0;
    let mut i = 1;
    while i < items.len() {
        if items[i].value > items[best].value {
            best = i;
        }
        i += 1;
    }
    best
}
```

```
замер «день»: 24 °C (позиция 1)
сосед слева: замер «утро»
```

*Сравнение.* Результат тот же элемент, но добытый иначе — и с другими последствиями. Возврат `&Sample<T>` отдаёт **сам предмет**: с ним сразу можно работать (`hottest.describe()`), но он остаётся заимствованием у среза, то есть, пока ссылка жива, вектор нельзя изменять (правило «читатели XOR писатель», §15.2) — а связь «результат живёт не дольше входа» скоро придётся выписывать явно, лайфтаймами (часть 19.3; в `max_sample` её вывели правила умолчаний, §19.3.2). Возврат `usize` отдаёт **координату**: заимствования не остаётся вовсе, поэтому индекс можно сохранить, передать, положить в структуру — и уже потом обратиться к элементу; открывается и то, чего у ссылки нет, — соседи (`items[i - 1]` в последней строке вывода) и позиция в отчёте. Цена — две: индекс осмыслен только вместе с тем самым срезом (передали не тот — получите не тот элемент или панику по границе), и обращение `items[i]` стоит проверки границ на каждом доступе. Когда что: ссылка — когда результат нужен «здесь и сейчас» как значение; индекс — когда нужна позиция, соседи или долгая жизнь результата без удержания заимствования. И обратите внимание на пустой срез: обе версии на нём падают (`items[0]` и `items[best]` — паника индексации); честная промышленная сигнатура вернула бы `Option`, как это делает стандартный `first()` — приём главы 16, вполне доступный обеим формам.

## Часть 19.2. Трейты

### Г19.Ч2.З1

**Условие.** Объявите трейт `Describe` с методом `fn describe(&self) -> String` и реализуйте его для двух своих типов — например, `Book { title: String, pages: u32 }` и `Movie { title: String, minutes: u32 }`. В `main` напечатайте описания обоих. До запуска предскажите вывод.

**Решение.** *Предсказание.* Две строки, по одной на тип, каждая — результат своей реализации `describe`: описание книги с числом страниц и описание фильма с длительностью. Порядок — порядок вызовов в `main`, никакой «диспетчеризации» тут нет: компилятор знает конкретные типы обоих значений и подставляет конкретные тела.

Файл `t1.rs`:

```rust
trait Describe {
    fn describe(&self) -> String;
}

struct Book {
    title: String,
    pages: u32,
}

struct Movie {
    title: String,
    minutes: u32,
}

impl Describe for Book {
    fn describe(&self) -> String {
        format!("книга «{}», {} с.", self.title, self.pages)
    }
}

impl Describe for Movie {
    fn describe(&self) -> String {
        format!("фильм «{}», {} мин.", self.title, self.minutes)
    }
}
```

```
книга «Программирование на C», 272 с.
фильм «Гравитация», 91 мин.
```

Предсказание совпало. Разберём, что здесь чему соответствует.

**Объявление трейта — это список требований, а не код.** В `trait Describe` стоит сигнатура с точкой с запятой: `fn describe(&self) -> String;`. Тела нет — есть обязательство. Никакой памяти, никакого исполняемого кода за самим трейтом не стоит: это контракт, который компилятор будет сверять (§19.2.1).

**`impl Трейт for Тип` — выполнение контракта.** Два блока, по одному на тип, и в каждом — своё тело. Заголовок читается «выполняю контракт `Describe` для типа `Book`»: с этой конструкцией вы уже работали в §18.2.2, когда писали `impl From<io::Error> for AppError` «по рецепту», — теперь рецепт разобран.

**`&self` и `Self`.** Приёмник `&self` — тот же сокращённый приёмник, что в обычных `impl` (§16.1.2): метод читает поля и ничего не потребляет. Внутри объявления трейта конкретный тип неизвестен, его заменяет неявный `Self` — «тот тип, который меня реализует» (§19.2.1); в наших сигнатурах он спрятан внутри `&self`.

Стоит заметить, чего у трейта **нет**: он ничего не знает о полях. `Describe` не требует ни `title`, ни `pages` — реализация вольна собирать описание из чего угодно (или ни из чего, как `Divider` в §19.2.1). Контракт — про поведение, а не про устройство: в этом вся разница между трейтом и «базовой структурой с общими полями».

**Ответ:** код — листинг `t1.rs`; вывод — `книга «Программирование на C», 272 с.` и `фильм «Гравитация», 91 мин.`, предсказание совпало. Трейт объявляет сигнатуру без тела (обязательство), два блока `impl Describe for …` его выполняют; приёмник `&self` соответствует методу-читателю по §16.1.2, а сам контракт говорит только о поведении и ничего не требует от полей.

### Г19.Ч2.З2

**Условие.** Добавьте в `Describe` метод `fn label(&self) -> String` с телом по умолчанию, вызывающим `describe()` (например, `format!("[{}]", self.describe())`). Не меняя реализаций, вызовите `label()` у обоих типов; затем переопределите `label` у одного из них. Объясните: почему умолчание могло звать `describe`, которого в самом трейте нет «в готовом виде»?

**Решение.** Файл `t2.rs` — трейт с двумя методами, из которых второй имеет тело:

```rust
trait Describe {
    fn describe(&self) -> String;

    fn label(&self) -> String {
        format!("[{}]", self.describe())
    }
}
```

`Book` реализацию не менял вовсе (в его `impl` по-прежнему только `describe`), `Movie` переопределил `label`:

```rust
impl Describe for Movie {
    fn describe(&self) -> String {
        format!("фильм «{}», {} мин.", self.title, self.minutes)
    }

    fn label(&self) -> String {
        format!("<<{}>>", self.title)
    }
}
```

```
[книга «Программирование на C», 272 с.]
<<Гравитация>>
```

Первая строка — умолчание, доставшееся `Book` **бесплатно**: в его `impl` слова `label` нет, а метод у типа есть. Вторая — переопределение: `Movie` предъявил своё тело, и умолчание к нему не применялось (иначе мы увидели бы квадратные скобки).

*Почему умолчание может звать `describe`.* Потому что в момент **вызова** какая-то реализация `describe` гарантированно существует — и гарантирует это сам компилятор.

Разложим по шагам. Тело `label` живёт в объявлении трейта, где конкретный тип неизвестен; известно только, что это некоторый `Self`, реализующий `Describe`. Написать `self.describe()` законно ровно потому, что `describe` **входит в тот же контракт**: любой тип, добравшийся до реализации `Describe`, обязан был предоставить тело `describe` — иначе его `impl` не собрался бы (E0046, «контракт весь или никакого», §19.2.1). Иными словами, умолчание опирается не на «уже написанный код», а на **обещание, которое компилятор не даст нарушить**.

Проверить это можно от противного — ⛔ файл `t3a_bad.rs` из следующего задания: там `impl Describe for Book {}` пуст, и компилятор немедленно отказывает: `not all trait items implemented, missing: `describe``. То есть состояния «тип реализует `Describe`, но `describe` у него нет» не бывает — а значит, вызов внутри умолчания не может остаться без адресата.

Полезно понять и то, **когда** выбирается тело. Никакого поиска в рантайме не происходит: для `Book` компилятор при мономорфизации подставляет в `label` тело `Book::describe`, для `Movie` — вовсе не использует умолчание, потому что нашёл собственное. Всё решается при компиляции, вызов — прямой (§19.1.3).

Практическая ценность приёма — совместимость: добавив в трейт новый метод **с телом**, вы не ломаете ни одной существующей реализации (все они автоматически получают умолчание). Добавив метод без тела — ломаете все сразу: каждой придётся дописывать. Это ровно тот довод, по которому стандартная библиотека раздаёт умолчания щедро.

**Ответ:** код — листинг `t2.rs`; вывод `[книга «Программирование на C», 272 с.]` (умолчание, реализация `Book` не менялась) и `<<Гравитация>>` (переопределение у `Movie`). Умолчание может звать `describe`, потому что `describe` входит в тот же контракт: тип, реализовавший `Describe`, **обязан** был дать телу `describe` — пустой `impl` отвергается с E0046. Умолчание опирается не на существующий код, а на обещание, соблюдение которого проверяет компилятор; конкретное тело подставляется при мономорфизации, вызов остаётся прямым. Отсюда практическое следствие: новый метод с телом по умолчанию не ломает существующие реализации, а без тела — ломает все.

*Почему обе ловятся до запуска.* Потому что обе — вопросы **о типах**, а типы известны при компиляции целиком.

Общий знаменатель: и «контракт выполнен наполовину», и «операция применена к типу, который её не умеет» — это несоответствия, полностью описываемые типами. Всё, что описывается типами, Rust проверяет до запуска.

*Какой ценой аналогичные ошибки обходились в C.* Цены две, и они разные.

**Сравнение структур (§8.1.1).** Здесь C ведёт себя похоже — и тоже отказывается компилировать. Файл `t3c_eq.c`:

```c
struct Genre {
    int code;
};

int main(void) {
    struct Genre a = { 1 };
    struct Genre b = { 2 };
    printf("равны? %d\n", a == b);
    return 0;
}
```

```
t3c_eq.c: In function 'main':
t3c_eq.c:10:29: error: invalid operands to binary == (have 'struct Genre' and 'struct Genre')
   10 |     printf("равны? %d\n", a == b);
      |                             ^~
```

Ошибка есть, но сравните формулировки. C сообщает «недопустимые операнды» — и всё: ни имени недостающего умения, ни подсказки, ни готовой правки, потому что в языке нет понятия «тип может научиться сравниваться». Выход из положения один — писать `genres_equal(a, b)` руками для каждого типа, следя, чтобы функция не отстала от структуры при добавлении поля. Rust называет недостающий трейт и предлагает строку, после которой оператор появится, — и появится согласованно со всеми полями сразу.

**Неполный контракт (§6.3.2).** А вот здесь аналога проверке E0046 нет вовсе. Ближайший родственник трейта в C — структура с указателями на функции; «реализовать контракт» значит заполнить её поля, и никто не следит за тем, все ли заполнены. Файл `t3c_vtbl.c`:

```c
/* "контракт" на C: таблица указателей на функции */
struct Describe {
    const char *(*describe)(void);
    const char *(*label)(void);
};

static const char *book_describe(void) {
    return "книга «Программирование на C», 272 с.";
}

/* реализацию label забыли написать — поле останется NULL */
static struct Describe book = { book_describe, NULL };

int main(void) {
    printf("%s\n", book.describe());
    printf("%s\n", book.label());
    return 0;
}
```

Сборка эталонным компилятором тома I с `-Wall -Wextra` проходит **без единого предупреждения**, код возврата 0. Запуск:

```
Segmentation fault (код возврата 139)
```

Программа не напечатала **ничего** — даже первую строку, которая успела выполниться. Причина знакома по главе 10: `stdout` буферизован, а аварийное завершение уносит буфер с собой. Контрольный опыт `t3c_vtbl_flush.c` — та же программа с `fflush(stdout)` после первой печати:

```
книга «Программирование на C», 272 с.
```

и следом тот же Segmentation fault. То есть половина контракта работала прекрасно; вторая половина обнаружилась вызовом по нулевому указателю — в рантайме, у пользователя, без всякой диагностики на этапе сборки.

Вот и цена, которую спрашивает задание: в C «забыл реализовать» стоит **падения (или, что хуже, тихого мусора) во время работы**, причём отладка начинается с потери уже напечатанного вывода; «не умеет сравниваться» стоит **ручных функций сравнения** для каждого типа, которые надо помнить и обновлять. В Rust обе ситуации стоят одного: прочитать сообщение и дописать строку — до запуска.

**Ответ:** (а) `E0046: not all trait items implemented, missing: `describe`` — недостающее названо поимённо, координаты ведут в объявление трейта (`` `describe` from trait ``) и на заголовок реализации (`missing `describe` in implementation`). (б) `E0369: binary operation `==` cannot be applied to type `Genre`` — `note: an implementation of `PartialEq` might be missing for `Genre`` / `must implement `PartialEq``, `help: consider annotating `Genre` with `#[derive(PartialEq)]``. Обе ловятся до запуска, потому что обе — несоответствия, полностью описываемые типами: E0046 сравнивает два конечных списка методов, E0369 ищет реализацию трейта у известного типа. Цена в C: сравнение структур тоже не компилируется, но диагностика сводится к `invalid operands to binary ==` без имени недостающего умения и без правки — приходится писать функции сравнения руками для каждого типа (§8.1.1); а проверки полноты контракта нет вообще — таблица указателей на функции с незаполненным полем собирается без предупреждений и падает в рантайме (`t3c_vtbl.c`: Segmentation fault, код 139, причём буферизованный вывод теряется вместе с процессом), §6.3.2.

### Г19.Ч2.З4

**Условие.** *(понимание)* Перепишите `fn notify(item: &impl Summary)` в полную форму с `<T: Summary>` и убедитесь прогоном, что поведение не изменилось. Затем объявите `fn pick<T: Summary>(a: &T, b: &T) -> ...` — и попробуйте передать ей статью и комментарий одновременно. Объясните ошибку и сформулируйте, когда формы `&impl` и `<T:>` перестают быть взаимозаменяемыми.

**Решение.** Файл `t4.rs` — обе формы рядом:

```rust
fn notify(item: &impl Summary) {
    println!("новое в ленте: {}", item.summarize());
}

fn notify_generic<T: Summary>(item: &T) {
    println!("новое в ленте: {}", item.summarize());
}

fn pick<T: Summary>(a: &T, b: &T) -> String {
    if a.summarize().len() >= b.summarize().len() {
        a.summarize()
    } else {
        b.summarize()
    }
}
```

```
новое в ленте: комментарий @max
новое в ленте: статья «Rust 1.97 вышел»
```

Первые две строки — `notify`, вторые две — `notify_generic`: **вывод посимвольно одинаков**. Иначе и быть не могло: `&impl Трейт` — сахар, разворачивающийся в анонимный параметр типа с тем же ограничением (§19.2.2).

Одно пояснение к сигнатуре `pick`. В условии результат оставлен многоточием, и выбор здесь не произволен: вернуть `&T` (ссылку на «победителя») на материале части 19.2 **нельзя**. ⛔ Файл `t4_ref_bad.rs` показывает, почему:

*Объяснение ошибки.* `T` — **одна** переменная типа, и в одном вызове она получает **одно** значение. Компилятор идёт по аргументам слева направо: первый (`&article`) фиксирует `T = Article`; после этого второй параметр имеет уже вполне конкретный тип `&Article`, и `&comment` в него не годится — E0308, «ожидал `&Article`, получил `&Comment`». Подчёркивание стоит на втором аргументе не потому, что он «неправильный», а потому, что он пришёл вторым: поменяйте аргументы местами — виноватой окажется статья.

Существенно, что ограничение `T: Summary` при этом **соблюдено обоими** типами: и `Article`, и `Comment` реализуют `Summary`. Отказ не в умениях, а в тождестве: сигнатура требует, чтобы это был один и тот же тип. Ровно поэтому ошибка — E0308 («несовпадение типов»), а не E0277 («не выполнено ограничение»).

*Когда формы перестают быть взаимозаменяемыми.* Пока параметр **один**, формы эквивалентны — что и показали первые четыре строки вывода. Разница появляется, как только имя типа встречается в сигнатуре **больше одного раза**:

- `fn f(a: &impl Trait, b: &impl Trait)` — два **независимых** анонимных параметра типа: каждому `impl Trait` соответствует своя дырка, и типы могут быть разными;
- `fn f<T: Trait>(a: &T, b: &T)` — **один** параметр, использованный дважды: типы обязаны совпасть.

Подтверждение — файл `t4_two.rs`, где та же пара аргументов проходит без единой жалобы:

```rust
// два НЕЗАВИСИМЫХ типа: каждый &impl — своя дырка
fn compare_two(a: &impl Summary, b: &impl Summary) {
    println!("первый:  {}", a.summarize());
    println!("второй:  {}", b.summarize());
}
```

```
первый:  статья «Rust 1.97 вышел»
второй:  комментарий @max
первый:  статья «Rust 1.97 вышел»
второй:  статья «Rust 1.97 вышел»
```

Первый вызов — статья и комментарий (то самое, что отвергла `pick`), второй — две статьи: форма `&impl` допускает и разные типы, и одинаковые.

Отсюда формулировка, которую и просит задание: **формы взаимозаменяемы ровно до тех пор, пока параметр типа употребляется в сигнатуре один раз.** Как только он встречается дважды — в двух параметрах, в параметре и результате, во вложенном типе вроде `Vec<T>`, — выбор перестаёт быть косметическим: `<T: …>` связывает употребления в одно, `impl Трейт` оставляет их независимыми. И связывать это ограничение можно только полной формой: у `&impl Trait` попросту нет имени, которое можно было бы повторить.

Практический вывод (§19.2.2): один простой параметр — пишите `&impl Трейт`, короче и читается лучше; связанные параметры, повторное использование типа, длинные списки требований — полная форма и `where`.

**Ответ:** обе формы дают посимвольно одинаковый вывод (`t4.rs`, четыре первые строки) — `&impl Трейт` есть сахар над анонимным параметром типа. Передача статьи и комментария в `pick<T: Summary>(a: &T, b: &T)` даёт **E0308** `expected &Article, found &Comment`: `T` — одна переменная типа, первый аргумент фиксирует `T = Article`, и второй обязан совпасть; ограничение при этом соблюдено обоими типами — отказ в тождестве, а не в умениях (потому E0308, а не E0277). Формы перестают быть взаимозаменяемыми, как только параметр типа употребляется в сигнатуре более одного раза: `<T: Trait>` связывает употребления в один тип, два `&impl Trait` остаются независимыми — что подтверждает `t4_two.rs`, принимающий и разные типы, и одинаковые. Побочный результат: вариант `pick` с возвратом `&T` не собирается вовсе (E0106) — для него нужны времена жизни части 19.3.

### Г19.Ч2.З5

**Условие.** *(понимание)* Воспроизведите E0117 из §19.2.1 (свой `impl Display for Vec<i32>`). Разберите все три `note`: что такое «uncovered type parameters», куда ведёт ссылка, что предлагает компилятор. Выполните его совет: заведите newtype `struct Ints(Vec<i32>);` (приём §16.1.1), реализуйте `Display` для него (например, элементы через пробел — цикл по `&self.0`) и напечатайте `Ints(vec![1, 2, 3])` через `{}`.

**Решение.** ⛔ Файл `t5_bad.rs`:

```rust
use std::fmt;

impl fmt::Display for Vec<i32> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "вектор из {} элементов", self.len())
    }
}
```

```
error[E0117]: only traits defined in the current crate can be implemented for types defined outside of the crate
 --> t5_bad.rs:3:1
  |
3 | impl fmt::Display for Vec<i32> {
  | ^^^^^^^^^^^^^^^^^^^^^^--------
  |                       |
  |                       `Vec` is not defined in the current crate
  |
  = note: impl doesn't have any local type before any uncovered type parameters
  = note: for more information see https://doc.rust-lang.org/reference/items/implementations.html#orphan-rules
  = note: define and implement a trait or new type instead
```

*Разбор трёх нот.*

**`impl doesn't have any local type before any uncovered type parameters`.** Это формальная причина отказа. Правило сироты требует, чтобы в реализации участвовал хоть один «местный» (объявленный в вашем crate) тип, причём стоящий в записи **раньше** всех непокрытых параметров типа. **Непокрытый параметр типа** (uncovered type parameter) — параметр обобщённого трейта или типа, который не завёрнут в местный тип: он остаётся «открытым» для чужих crate, и именно через него две библиотеки могли бы дать одному типу две разные реализации. В нашей строке местных типов нет вовсе: `Display` — из `std::fmt`, `Vec` — из `std::vec`, `i32` — встроенный. Отсюда и формулировка: перед непокрытыми параметрами не нашлось ни одного своего типа. Практический перевод: **реализация без «местного родителя» отклоняется**.

**`for more information see https://doc.rust-lang.org/reference/items/implementations.html#orphan-rules`.** Ссылка ведёт в Rust Reference (R7 нашего реестра), в раздел `items/implementations`, якорь `#orphan-rules` — то есть в нормативную формулировку правила сироты. Именно этот документ курс назначил арбитром по вопросам реализации трейтов (§19.2.1), и компилятор отправляет ровно туда же, а не в учебник: правило сироты — часть спецификации языка, а не совет по стилю.

**`define and implement a trait or new type instead`.** Это выход, и в нём два равноправных пути. Первый — **свой трейт** для чужого типа: `impl МойТрейт for Vec<i32>` законен, потому что трейт местный. Второй — **свой тип** для чужого трейта: завернуть `Vec<i32>` в newtype и реализовать `Display` для обёртки. Правило соблюдено в обоих случаях, потому что в реализации участвует что-то ваше — и, значит, никакой другой crate такую же реализацию написать не сможет.

*Выполняем совет.* Файл `t5.rs`:

```rust
use std::fmt;

struct Ints(Vec<i32>);

impl fmt::Display for Ints {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let mut first = true;
        for n in &self.0 {
            if first {
                write!(f, "{n}")?;
                first = false;
            } else {
                write!(f, " {n}")?;
            }
        }
        Ok(())
    }
}

fn main() {
    let ints = Ints(vec![1, 2, 3]);
    println!("[{ints}]");
    println!("пустой: [{}]", Ints(vec![]));
    println!("to_string даёт: {:?}", ints.to_string());
}
```

```
[1 2 3]
пустой: []
to_string даёт: "1 2 3"
```

Разбор реализации — четыре детали, каждая из которых уже встречалась порознь:

- **`&self.0`** — обращение к единственному полю кортежной структуры по номеру (§16.1.1), а `&` перед ним даёт обход по ссылкам (§17.1.2): элементы вектора мы не забираем, обёртку не разрушаем.
- **флаг `first`** — разделитель ставится **перед** элементом, кроме первого. Так пробел не повисает в конце строки; на пустом векторе цикл не делает ни одного шага, и вывод честно пуст (вторая строка прогона).
- **`write!(f, …)?`** — пишем в переданный приёмник, а не на экран, и **пробрасываем** `Result` вопросительным знаком (§18.1.3). Оба правила из «подводных камней» §19.2.3 соблюдены: `println!` внутри `fmt` был бы багом (вывод ушёл бы мимо `format!`/`to_string`), а проглоченный `Result` скрыл бы ошибку записи.
- **`Ok(())`** в конце — успешное завершение: возвращаемый тип `fmt::Result` есть `Result<(), fmt::Error>` (R9), и после серии `write!` нам остаётся сообщить «всё записалось».

Третья строка прогона — бесплатный бонус: `.to_string()` появился у `Ints` сам собой. Это общая (blanket) реализация `impl<T: Display> ToString for T` из §19.2.2: реализовав `Display`, тип автоматически получает `ToString`. Печать через `{:?}` показывает результат в кавычках — перед нами именно `String`, а не что-то, «похожее на строку».

**Ответ:** ошибка воспроизведена (`t5_bad.rs`), текст совпадает с §19.2.1 дословно. Ноты: (1) «непокрытые параметры типа» — параметры, не завёрнутые в местный тип; правило требует местного типа перед ними, а в `impl Display for Vec<i32>` местного нет ни одного, поэтому реализация — «сирота»; (2) ссылка ведёт в Rust Reference (R7), раздел `items/implementations`, якорь `#orphan-rules` — нормативную формулировку правила; (3) предложены два выхода — свой трейт для чужого типа либо свой тип (newtype) для чужого трейта. Совет выполнен: `struct Ints(Vec<i32>)` с ручным `Display` печатает `[1 2 3]`, на пустом векторе — `[]`, и вместе с `Display` получает `.to_string()` по blanket-реализации `ToString`.

**Вариант 2 (собрать строку, записать одним `write!`).** Вместо серии записей в форматтер можно собрать текст в `String`, а в приёмник отдать его целиком. Файл `t5v2.rs`:

```rust
impl fmt::Display for Ints {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let mut out = String::new();
        let mut i = 0;
        while i < self.0.len() {
            if i > 0 {
                out.push(' ');
            }
            out.push_str(&self.0[i].to_string());
            i += 1;
        }
        write!(f, "{out}")
    }
}
```

```
[1 2 3]
пустой: []
to_string даёт: "1 2 3"
```

Вывод совпадает с основным решением по всем трём строкам.

*Сравнение.* Устройство разное в двух отношениях. Во-первых, **число обращений к форматтеру**: основное решение делает по одной записи на элемент (и каждая может вернуть ошибку, отсюда `?` в цикле), вариант 2 — ровно одну в самом конце, поэтому `?` не нужен вовсе и `Ok(())` не пишется: результат последнего `write!` и есть результат метода. Во-вторых, **память**: основное решение не выделяет ничего сверх того, что делает сам приёмник; вариант 2 строит промежуточную `String` (и внутри — ещё по одной на каждый `to_string()` элемента), то есть платит выделениями за читаемость. Есть и разница в «сборке разделителя»: во втором варианте роль флага `first` играет условие `i > 0`, что чуть короче, но требует индексного обхода со всеми его обязанностями (Г19.Ч1.З9, вариант 2). Когда что предпочесть: по умолчанию — писать прямо в `f` (так устроены все реализации `Display` в стандартной библиотеке: форматтер сам решает, куда складывать байты, и лишний буфер ему только мешает); собирать строку заранее имеет смысл, когда текст нужно **посчитать или поправить целиком** перед выдачей — например, выровнять по ширине или обрезать по длине, — то есть когда без готовой строки не обойтись.

### Г19.Ч2.З6

*Почему «один конкретный тип» — следствие мономорфизации.* Потому что `impl Summary` в позиции результата — это не «какой-нибудь Summary», а **имя, которое компилятор обязан разрешить в один конкретный тип при компиляции**. Цепочка рассуждений короткая:

1. Мономорфизация штампует машинный код под конкретные типы (§19.1.3) — в рантайме обобщённости не остаётся.

Свести пункты 2 и 3 нельзя: решение о типе требуется раньше, чем становится известен ответ. Поэтому `impl Trait` в результате — это маска для **одного** типа: вызывающий его не видит (в этом смысл записи), но компилятор — видит, и он один.

Отсюда же понятно, почему подсказанный `Box<dyn Summary>` эту задачу решает: он переносит выбор в рантайм ценой другого механизма — значение уезжает в кучу, а вызов метода идёт через таблицу, то есть косвенно (тот самый компромисс, что у `qsort` в §6.3.2). Это уже не мономорфизация, и цена другая; механизм ждёт главы 22, как и `Box<dyn Error>` из §18.1.3.

*Решение средствами главы 16.* Если «или-или» нужно выразить **типом**, для этого есть перечисление: enum — это и есть «одно из нескольких» с известными компилятору размером и раскладкой. Файл `t6.rs`:

```rust
enum FeedItem {
    Article(Article),
    Comment(Comment),
}

impl Summary for FeedItem {
    fn summarize(&self) -> String {
        match self {
            FeedItem::Article(a) => a.summarize(),
            FeedItem::Comment(c) => c.summarize(),
        }
    }
}

fn sample_item(use_article: bool) -> FeedItem {
    if use_article {
        FeedItem::Article(Article {
            headline: String::from("Rust 1.97 вышел"),
        })
    } else {
        FeedItem::Comment(Comment {
            username: String::from("max"),
        })
    }
}
```

```
лента: комментарий @max

```

Обе ветки теперь возвращают **один** тип — `FeedItem`, — а различие уехало внутрь него, в варианты. Реализация `Summary for FeedItem` — `match` с делегированием: каждая ветка зовёт `summarize` у своей начинки (образцы `FeedItem::Article(a)` связывают поле по ссылке, потому что `self` — ссылка; §16.2.2). Размер `FeedItem` известен: он равен размеру наибольшего варианта плюс тег (§16.2.3), и этого компилятору достаточно.

Последние три строки прогона показывают то, ради чего всё и затевалось: `Vec<FeedItem>` — **однородный** вектор из разнородных по смыслу элементов. С `impl Summary` такой вектор не собрать (у элементов должен быть один тип), а с enum — обычная коллекция главы 17.

Заметьте побочный выигрыш: `match` в реализации проверяется на полноту. Добавите завтра вариант `FeedItem::Poll` — компилятор потребует дописать ветку (§16.2.2). У решения через `Box<dyn Summary>` такой проверки нет: список возможных типов открыт.

Требование «один конкретный тип» следует из мономорфизации: чтобы сгенерировать код, компилятор обязан знать размер, раскладку и методы результата **при компиляции**, а выбор между ветками `if` делается в рантайме — совместить нельзя, поэтому `impl Trait` есть маска ровно одного типа, известного компилятору. Решение главы 16 — `enum FeedItem` с реализацией `Summary` через `match` с делегированием и возвратом `FeedItem` из функции с веткой (`t6.rs`): обе ветки дают один тип, различие уходит внутрь вариантов, размер известен как «наибольший вариант + тег», а бонусом появляется однородный `Vec<FeedItem>` и проверка полноты `match` при добавлении вариантов.

### Г19.Ч2.З7

**Условие.** *(понимание)* Почему у `Debug` есть derive, а у `Display` нет (R9)? Приведите два типа из курса, где представления `{:?}` и `{}` обязаны различаться, и покажите на `io::Error` из §18.1.2, что теряет пользователь, если показать ему Debug-форму. Когда `{:?}` в выводе программы честен?

**Решение.** *Почему у `Debug` есть derive, а у `Display` нет.* Потому что у этих двух трейтов **разные аудитории**, и только для одной из них существует правильный ответ по умолчанию.

`Debug` отвечает на вопрос «что лежит в этом значении?» — и ответ выводится из устройства типа механически: имя типа, имена полей, их Debug-представления. Аудитория — программист, знающий исходный код; ему нужна полнота и однозначность, а не красота. Раз ответ выводится из структуры, его может сгенерировать компилятор — отсюда `#[derive(Debug)]`.

`Display` отвечает на вопрос «как показать это значение **человеку**?» — и вот на него из устройства типа ничего не следует. Как печатать `Minutes(5)` — «5», «5 мин.», «00:05:00»? Как печатать `WithdrawError::Insufficient { balance: 70, need: 200 }` — так, как это сделает Г19.Ч2.З8, или совсем иначе? Ответ зависит от того, кому и зачем показывают, а этого в объявлении типа нет. R9 фиксирует прямо: `Display` «cannot be derived» — не потому, что трудно, а потому, что решение принадлежит автору типа. Компилятор, попытавшись угадать, дал бы неверный ответ молча — худший вид ошибки.

Практическое подтверждение — ⛔ файл `t7_bad.rs`, попытка напечатать через `{}` тип с одним лишь `derive(Debug)`:

```

  --> t7_bad.rs:10:30
   |
10 |     println!("Display точки: {p}");
   |                              ^^^ `Point` cannot be formatted with the default formatter
   |
help: the trait `std::fmt::Display` is not implemented for `Point`
  --> t7_bad.rs:2:1
   |
 2 | struct Point {
   | ^^^^^^^^^^^^
   = note: in format strings you may be able to use `{:?}` (or {:#?} for pretty-print) instead
```

Компилятор не предлагает «добавьте derive» — такого выхода нет; он предлагает либо написать реализацию, либо честно признать, что аудитория здесь программистская, и печатать `{:?}`.

*Два типа, где представления обязаны различаться.* Оба — из пройденного, и оба проверены прогоном (файл `t7.rs`):

```
Display строки: строка с "кавычками"
и переводом строки
Debug строки:   "строка с \"кавычками\"\nи переводом строки"
Display символа: п
Debug символа:   'п'
```

- **`String` / `&str`** (главы 15, 17). `{}` печатает **содержимое**: текст ровно такой, каким его увидит пользователь, — с настоящим переводом строки, без обрамления. `{:?}` печатает **литерал**: в кавычках, с экранированными спецсимволами (`\"`, `\n`). Различие здесь не косметическое, а необходимое: отладчику важно видеть границы строки и невидимые символы (иначе не отличишь `"abc "` от `"abc"`), а пользователю кавычки и `\n` вместо перевода строки — мусор. Совпасть эти формы не могут в принципе.
- **`char`** (§17.1.4). `{}` — сам символ (`п`), `{:?}` — символ в одинарных кавычках (`'п'`). Та же логика: в отладочной печати важно видеть, что это именно `char`, а не строка из одной буквы.

(Третий пример, уже из этой главы: `ParseError` в §19.2.3 — `Display: недопустимый символ 'x'` против `Debug: BadChar('x')`. Первое — фраза для человека, второе — имя варианта и его нагрузка.)

*Что теряет пользователь на `io::Error`.* Тот же прогон, третья пара строк:

```
Display ошибки: The system cannot find the file specified. (os error 2)
Debug ошибки:   Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
```

Debug-форма показывает **внутреннее устройство** значения: имя варианта `Os`, поле `code` с номером ошибки операционной системы, поле `kind` с категорией на языке стандартной библиотеки, поле `message` — в кавычках, как строковый литерал.

Что здесь теряет (точнее, приобретает не то) пользователь:

- **шум вместо сообщения.** Из шести элементов печати ему адресован ровно один — текст сообщения; остальное — служебные имена (`Os`, `code`, `kind`, `NotFound`), которые значат что-то лишь для того, кто читал документацию `std::io`;
- **кавычки и синтаксис Rust** в тексте, который он собирается прочесть как фразу;
- **иллюзию отладочной информации.** Формы вроде `Os { code: 2, … }` выглядят как «внутренняя ошибка программы»; пользователь, увидевший такое, скорее решит, что сломалась программа, чем что он ошибся в имени файла. Ровно об этом «подводный камень» §18.2.3 «Debug наружу».

Чего Debug-форма при этом **не** теряет: сам текст сообщения в ней есть. Проблема не в потере данных, а в адресации: человеку показали служебную запись вместо фразы. И заметьте, что ни одна из форм не называет имя файла — этот факт мы установили в решениях главы 18 (`Г18.Ч2.З…`, опыт с двумя разными несуществующими путями): путь в `io::Error` не хранится, и добавить его — обязанность вашего кода, а не выбор формата печати.

*Когда `{:?}` в выводе программы честен.* Когда **читатель вывода — программист**. Три законных случая, все встречались в курсе:

1. **Отладочная печать и диагностика для себя** — «посмотреть, что в структуре»: `println!("{p:?}")` в процессе работы над кодом, вывод в лог, дамп состояния.
2. **Тесты и утверждения** — упавший `assert_eq!` печатает ожидаемое и полученное именно через `Debug` (глава 20), и правильно: сообщение читает тот, кто чинит тест.
3. **Внутри Display-реализации, осознанно** — когда «программистская» форма и есть то, что нужно показать: в §19.2.3 `ParseError::BadChar(c)` печатает `{c:?}`, чтобы символ был виден в кавычках и невидимые символы не потерялись; в Г19.Ч2.З10 то же сделано с текстом непонятой команды.

И один пограничный случай: `{:?}` честен как **временная мера** в прототипе — с тем же статусом, что `unwrap` (§18.2.3): работает, пишется в одну строку, но остаётся меткой «здесь ещё не сделан интерфейс для человека». Нечестен же он ровно там, где вывод адресован пользователю: сообщение об ошибке, отчёт, интерфейс. Правило-лакмус то же, что для паники и `Result`: **спросите, кто прочитает эту строку.**

**Ответ:** derive у `Debug` есть, потому что «показать устройство значения» выводится из объявления типа механически; у `Display` derive нет (R9: «cannot be derived»), потому что «как показать значение человеку» из устройства типа не следует — это решение автора, и угаданный ответ был бы молча неверным; попытка `{}` без реализации даёт E0277 с советом использовать `{:?}`, а не «добавить derive». Типы, где формы обязаны различаться: `String`/`&str` (`{}` — содержимое с настоящим переводом строки, `{:?}` — литерал в кавычках с экранированием) и `char` (`п` против `'п'`). На `io::Error` пользователь вместо фразы `The system cannot find the file specified. (os error 2)` получает `Os { code: 2, kind: NotFound, message: "…" }` — служебные имена и кавычки, из которых ему адресован лишь фрагмент, плюс ложное впечатление «сломалась программа». `{:?}` честен тогда, когда вывод читает программист: отладка и логи, тесты (`assert_eq!` печатает через `Debug`), осознанная вставка внутрь `Display` (как `{c:?}` у `BadChar`), и — с оговоркой — прототип, где Debug-печать носит тот же статус временной меры, что `unwrap`.

### Г19.Ч2.З8

**Условие.** *(прикладное)* Верните банкомат из Г18.Ч2.З10: реализуйте `fmt::Display` для `WithdrawError` (`Zero` → «снятие нуля не имеет смысла», `Insufficient { balance, need }` → «нужно N, а на счёте M»). Замените в репортёре печать `{:?}` на `{}` и прогоните все четыре сценария. Бонусом покажите, что у ошибки появился `.to_string()`, — и объясните, откуда (blanket-реализация §19.2.2).

**Решение.** Файл `t8.rs` — банкомат из главы 18 без единой правки в логике, плюс реализация `Display`:

```rust
use std::fmt;

#[derive(Debug)]
enum WithdrawError {
    Zero,
    Insufficient { balance: u32, need: u32 },
}

impl fmt::Display for WithdrawError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            WithdrawError::Zero => write!(f, "снятие нуля не имеет смысла"),
            WithdrawError::Insufficient { balance, need } => {
                write!(f, "нужно {need}, а на счёте {balance}")
            }
        }
    }
}
```

Репортёр после правки — два рукава вместо трёх:

```rust
fn report(acc: &mut Account, amount: u32) {
    match acc.withdraw(amount) {
        Ok(rest) => println!("снято {amount}, остаток {rest}"),
        Err(e) => println!("отказ: {e}"),
    }
}
```

```
снято 30, остаток 70
отказ: снятие нуля не имеет смысла
отказ: нужно 200, а на счёте 70
снято 70, остаток 0
```

Все четыре сценария контроля Г18.Ч2.З10 сошлись по существу: 30 снимается, ноль отвергается, 200 не хватает (и в отказе названы обе величины — запрошенная и наличная), 70 снимается и обнуляет счёт. Слово «отказ» переехало из текста ошибки в репортёр и теперь применяется единообразно к обоим отказам — в главе 18 оно было частью одной конкретной фразы.

*Что изменилось по существу.* Репортёр перестал знать устройство ошибки. В главе 18 он разбирал варианты `match`-ем и **сам** сочинял фразы, а значит, обязан был знать и имена вариантов, и имена их полей. Теперь у него один рукав `Err(e)`, и добавление третьего вида отказа (скажем, «карта заблокирована») не потребует в нём ни строчки правок — формулировку принесёт с собой сам вариант. Это и есть смысл `Display` как контракта: **текст для человека принадлежит типу ошибки, а не месту, где её поймали.**

Тело `fmt` — обычный `match` по вариантам (§16.2.2). Обратите внимание на образец `WithdrawError::Insufficient { balance, need }`: имена полей связываются автоматически (§16.2.1), и в `write!` они подставляются встроенно — `{need}`, `{balance}`. И на приёмник: пишем в `f`, а результат `write!` возвращаем как результат метода — `?` здесь не нужен, потому что `write!` в каждом рукаве последний и единственный.

*Бонус: откуда `.to_string()`.* Последние строки `main` и прогона:

```rust
    let e = WithdrawError::Insufficient { balance: 0, need: 5 };
    let text: String = e.to_string();
    println!("to_string дал String длиной {}: {text}", text.len());
    println!("Debug той же ошибки: {e:?}");
```

```
to_string дал String длиной 34: нужно 5, а на счёте 0
Debug той же ошибки: Insufficient { balance: 0, need: 5 }
```

Метод `to_string` мы не писали и трейт `ToString` не реализовывали — он появился **вместе с** `Display`. Механизм — **общая реализация** (blanket implementation) из §19.2.2: в стандартной библиотеке записано `impl<T: Display> ToString for T` (R9), то есть «каждый тип, умеющий `Display`, автоматически умеет `ToString`». Это обычная условная реализация, только условие в ней — не «`T` равен такому-то типу», а «`T` реализует такой-то трейт», и покрывает она сразу все типы мира, включая те, которых ещё не существует. Ровно отсюда `.to_string()` у чисел в §19.2.3 (`255.to_string()`), хотя `impl ToString for i32` никто не писал.

Аннотация `let text: String` в листинге стоит не для компилятора (он выведет сам), а для читателя: `to_string` возвращает именно `String` — владеющую строку, которую можно хранить, передавать и накапливать, в отличие от `{}` в `println!`, где текст сразу уходит в вывод.

Две детали прогона стоит прокомментировать. Первая: длина **34** при 20 печатных знаках — это байты, а не символы (§17.1.4): кириллица в UTF-8 занимает по два байта. Вторая: Debug-форма той же ошибки (`Insufficient { balance: 0, need: 5 }`) никуда не делась — `derive(Debug)` и ручной `Display` живут рядом и отвечают разным аудиториям, как разбирала Г19.Ч2.З7.

**Ответ:** код — листинг `t8.rs`; четыре сценария дают `снято 30, остаток 70` / `отказ: снятие нуля не имеет смысла` / `отказ: нужно 200, а на счёте 70` / `снято 70, остаток 0`. Репортёр сократился до двух рукавов (`Ok` и `Err(e)`) и перестал зависеть от устройства ошибки: формулировку теперь несёт сам тип, а добавление нового варианта не потребует правок на границе. `.to_string()` появился у `WithdrawError` вместе с `Display` — по общей (blanket) реализации `impl<T: Display> ToString for T` из стандартной библиотеки (§19.2.2, R9); возвращает он `String` (длина 34 байта при 20 знаках — кириллица в UTF-8 по два байта), а Debug-форма остаётся доступной параллельно.

**Вариант 2 (текст формулирует граница).** Тот же вывод можно получить и без `Display` — оставив разбор вариантов в репортёре, как было в главе 18. Файл `t8v2.rs`:

```rust

    match acc.withdraw(amount) {
        Ok(rest) => println!("снято {amount}, остаток {rest}"),
        Err(WithdrawError::Zero) => println!("отказ: снятие нуля не имеет смысла"),
        Err(WithdrawError::Insufficient { balance, need }) => {
```

*Сравнение.* Разница не в результате, а в том, **где живёт текст**. У варианта 2 формулировки принадлежат границе: одно и то же значение ошибки в разных местах программы может быть показано по-разному (в консоли — фразой, в логе — короче, в веб-ответе — иначе), и для этого не нужно ничего менять в типе. Плата — связанность: репортёр обязан знать все варианты и все их поля, а появление нового варианта немедленно превращается в ошибку неполноты `match` в **каждом** таком месте. У основного решения ровно наоборот: текст принадлежит типу, границы его не касаются, новый вариант чинится в одном месте — зато и показать ошибку двумя разными способами уже нельзя без второго форматирующего метода. Есть и третье отличие, не сводящееся к вкусу: `Display` — это **контракт**, поэтому ошибка с ним становится пригодна к тому, чего вариант 2 не даёт вовсе, — печататься через `{e}` в чужом коде, отдавать `.to_string()`, укладываться в общий обработчик, ничего не знающий о вашем перечислении. Когда что: `Display` — для ошибок, которые пересекают границу модуля или библиотеки (канон §19.2.3: `enum` + `Debug` + `Display` + `From`); разбор на границе — когда сообщение сильно зависит от контекста вызова или когда одному и тому же отказу в разных местах положены разные слова.

### Г19.Ч2.З10

**Условие.** *(прикладное)* Реализуйте `FromStr` для `enum Command { Deposit(u32), Withdraw(u32), Balance }` — строки вида `"deposit 100"`, `"withdraw 50"`, `"balance"` (первое слово — команда, остаток — сумма через `parse::<u32>()`; разделитель ищите приёмом `first_word` из §15.3.2). Свой тип ошибки с `Display` обязателен. Прогоните `"deposit 100".parse::<Command>()`, `"balance".parse()`, `"fly 1".parse::<Command>()` и `"deposit x".parse::<Command>()`. Объясните роль `type Err` в сигнатуре `parse`.

**Решение.** Файл `t10.rs`. Тип ошибки — перечисление с двумя видами отказа и ручным `Display`:

```rust
#[derive(Debug)]
enum BadCommand {
    Unknown(String),
    BadAmount(String),
}

impl fmt::Display for BadCommand {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            BadCommand::Unknown(word) => write!(f, "неизвестная команда {word:?}"),
            BadCommand::BadAmount(rest) => write!(f, "не сумма: {rest:?}"),
        }
    }
}
```

Разбор строки — `first_word` дословно из §15.3.2 плюс вычисление остатка:

```rust
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();
    for i in 0..bytes.len() {
        if bytes[i] == b' ' {
            return &s[..i];
        }
    }
    &s[..]
}

impl FromStr for Command {
    type Err = BadCommand;

    fn from_str(s: &str) -> Result<Command, BadCommand> {
        let word = first_word(s);
        let rest = if word.len() < s.len() {
            &s[word.len() + 1..]
        } else {
            ""
        };

        if word == "balance" {
            Ok(Command::Balance)
        } else if word == "deposit" || word == "withdraw" {
            match rest.parse::<u32>() {
                Ok(amount) => {
                    if word == "deposit" {
                        Ok(Command::Deposit(amount))
                    } else {
                        Ok(Command::Withdraw(amount))
                    }
                }
                Err(_) => Err(BadCommand::BadAmount(String::from(rest))),
            }
        } else {
            Err(BadCommand::Unknown(String::from(word)))
        }
    }
}
```

```
Ok(Deposit(100))
Ok(Balance)
Err(Unknown("fly"))
Err(BadAmount("x"))
ошибка: неизвестная команда "fly"
ошибка: не сумма: "x"
deposit 100: пополнить на 100
withdraw 50: снять 50
balance: показать остаток
```

Первые четыре строки — четыре требуемых прогона в Debug-печати; следующие две — те же отказы, показанные через `Display` (`{e}`); последние три — разбор с чтением полезной нагрузки, чтобы видеть, что суммы действительно доехали до `Deposit`/`Withdraw`.

*Три детали устройства.*

**Вычисление остатка.** `first_word` режет по первому пробелу, поэтому если слово короче всей строки, то байт под индексом `word.len()` — это и есть тот самый пробел, и остаток начинается на единицу дальше: `&s[word.len() + 1..]`. Условие `word.len() < s.len()` отделяет случай «пробела не было вовсе» (тогда остаток пуст). Срез по байтам здесь безопасен: пробел — однобайтовый символ ASCII, значит, граница `word.len() + 1` заведомо попадает на начало символа, и паники «not a char boundary» (§18.1.1) не будет даже на кириллическом вводе.

**Проверка команды через `if`/`else if`.** Это форма из `fromstr_light.rs` (§19.2.3), где `Light` разбирался цепочкой `if s == "red" … else if …`. Она же и уместнее: у нас после проверки слова нужно ещё разобрать сумму, и ветка `deposit`/`withdraw` общая для двух команд.

**`Err(_)` при разборе суммы.** Ошибку `ParseIntError` мы намеренно **не пробрасываем**, а заменяем своей: `BadAmount` с текстом того, что не удалось прочесть. Причина — та же, что разобрала Г19.Ч2.З9: `ParseIntError` не знает ни строки, ни контекста. Наш тип ошибки контекст сохраняет, и пользователь видит `не сумма: "x"`, а не безадресное `invalid digit found in string`.

*Роль `type Err` в сигнатуре `parse`.* Строка `type Err = BadCommand;` заполняет **ассоциированный тип** (associated type) — «слот под тип» в объявлении трейта (§19.2.3, R7). Объявление `FromStr` выглядит так:

```
pub trait FromStr: Sized {
    type Err;
    fn from_str(s: &str) -> Result<Self, Self::Err>;
}
```

Трейт требует от реализации не только функцию, но и **ответ на вопрос «каким типом вы сообщаете об ошибке разбора?»**. Пока слот не заполнен, сигнатура `from_str` неполна: в ней стоит `Self::Err` — «тот тип, который назовёт реализация».

Отсюда и роль в `parse`. Метод строк объявлен (R9) примерно как

```
fn parse<F: FromStr>(&self) -> Result<F, F::Err>
```

то есть: «дайте мне тип `F`, умеющий `FromStr`, и я верну `Result` с успехом `F` и ошибкой **того типа, который назвал сам `F`**». Благодаря этому одна-единственная обобщённая функция обслуживает и `u32` (её ошибка — `ParseIntError`), и наш `Command` (ошибка — `BadCommand`), не зная о них заранее: тип ошибки приезжает вместе с типом результата.

Практических следствий два. Первое: `"deposit 100".parse::<Command>()` возвращает `Result<Command, BadCommand>` — компилятор знает конкретный тип ошибки, поэтому `match` по её вариантам полон и проверяем, а не «какая-то ошибка». Второе видно в листинге: `"balance".parse()` **без turbofish** требует аннотации слева — `let balance: Result<Command, BadCommand> = "balance".parse();`. Вывод типов должен откуда-то узнать `F`; из самой строки это не следует, и без подсказки была бы E0282 «type annotations needed», знакомая по Г19.Ч1.З4. Turbofish и аннотация здесь взаимозаменяемы — ровно как у `Vec::new()` в §19.1.2.

И отметим, чем ассоциированный тип отличается от обычного параметра: у типа может быть **только одна** реализация `FromStr`, а значит, и ровно один `Err`. Будь `Err` параметром (`FromStr<E>`), один тип мог бы разбираться десятью способами с десятью ошибками, и `parse` не знал бы, какой выбрать. Слот вместо параметра — это решение «у вопроса один ответ».

**Ответ:** реализация — листинг `t10.rs`; прогоны дают `Ok(Deposit(100))`, `Ok(Balance)`, `Err(Unknown("fly"))`, `Err(BadAmount("x"))`, а через `Display` — `неизвестная команда "fly"` и `не сумма: "x"`. `type Err` заполняет **ассоциированный тип** трейта `FromStr` — слот, отвечающий на вопрос «каким типом сообщаются ошибки разбора»; без него сигнатура `from_str(s: &str) -> Result<Self, Self::Err>` неполна. В `parse::<F>()` этот слот и делает функцию универсальной: она возвращает `Result<F, F::Err>`, то есть тип ошибки приезжает вместе с типом результата, и одна обобщённая функция обслуживает и `u32` (`ParseIntError`), и `Command` (`BadCommand`). Практические следствия: тип ошибки известен точно (полный `match` по вариантам) и `"balance".parse()` без turbofish требует аннотации слева, иначе E0282. Ассоциированный тип, а не параметр, — потому что у типа ровно одна реализация `FromStr` и, стало быть, ровно один вид ошибки разбора.

**Вариант 2 (один вид ошибки — newtype над строкой).** Тип ошибки можно сделать проще: не перечисление из двух видов отказа, а обёртку над текстом, как `BadLight` в §19.2.3. Файл `t10v2.rs`:

```rust
#[derive(Debug)]
struct BadCommand(String);

impl fmt::Display for BadCommand {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "не команда: {}", self.0)
    }
}
```

Обе неудачные ветки возвращают `Err(BadCommand(String::from(s)))` — целиком непонятую строку:

```
"deposit 100": пополнить на 100
"balance": показать остаток
"fly 1": ошибка — не команда: fly 1
"deposit x": ошибка — не команда: deposit x
```

*Сравнение.* Разница — в том, что вызывающий может **сделать** с ошибкой, а не в том, что он увидит. У варианта 2 ошибка — один непрозрачный тип: показать её человеку можно (Display на месте), а вот отреагировать по-разному нельзя. Программа не отличит «команда не та» от «сумма не та», и всё, что ей доступно, — напечатать текст. У основного решения отказ разложен на варианты, и это открывает `match`: на `Unknown` уместно напомнить список команд, на `BadAmount` — попросить повторить ввод суммы, и компилятор проследит, чтобы при добавлении третьего вида отказа ни одна такая развилка не осталась без ветки. Плата за это — больше кода (перечисление, по рукаву на вариант в `Display`) и необходимость решать заранее, какие категории отказов существуют. Есть и разница в том, что сохраняется: вариант 2 кладёт в ошибку **всю входную строку**, основное решение — только виноватый фрагмент (`"fly"`, `"x"`), что точнее для сообщения, но теряет контекст, если строка длинная и хочется показать её целиком. Когда что: обёртка над строкой хороша для разбора, ошибки которого только показывают (и для быстрого прототипа — это ровно уровень `BadLight` из главы); перечисление — когда на разные отказы полагаются разные действия, то есть по канону §19.2.3 для ошибок, пересекающих границу модуля.

*Минимальный набор — и доказательство минимальности.* Требуемый минимум — **`PartialEq`, `Eq`, `Hash`** (`Debug` в него не входит: он добавлен только ради печати ключа в отчёте). Проверим, что убрать нельзя ни одного:

- **без `Hash`** — ступень 2 выше: E0277 `the trait bound `PartId: Hash` is not satisfied`;
- **без `Eq`** — ⛔ файл `t11_noeq_bad.rs` с `#[derive(Debug, PartialEq, Hash)]`: `error[E0277]: the trait bound `PartId: Eq` is not satisfied` плюс тот же E0599 у `get` (уже с одной строкой в списке несоблюдённого);
- **без `PartialEq`** — ступень 2: `Eq` без него не дерайвится (супертрейт).

Почему требования именно такие, объясняет устройство хеш-таблицы (§9.3.1 в C, §17.2.1 в Rust): `Hash` нужен, чтобы вычислить корзину; `Eq` — чтобы внутри корзины отличить нужный ключ от чужого с тем же хешем. И **полное** равенство (`Eq`), а не частичное: таблица обязана считать, что ключ равен сам себе, иначе вставленное значение невозможно найти.

*Замена `shelf: u32` на `f64`.* ⛔ Файл `t11_f64_bad.rs` — тот же полный набор derive, но поле стало дробным. Ошибок **две**:

```
error[E0277]: the trait bound `f64: Eq` is not satisfied
 --> t11_f64_bad.rs:6:5
  |
3 | #[derive(Debug, PartialEq, Eq, Hash)]
  |                            -- in this derive macro expansion
...
6 |     shelf: f64,
  |     ^^^^^^^^^^ the trait `Eq` is not implemented for `f64`
  |
  = help: the following other types implement trait `Eq`:
            i128
            i16
            i32
            i64
            i8
            isize
            u128
            u16
          and 4 others
note: required by a bound in `std::cmp::AssertParamIsEq`
```

и вторая — `the trait bound `f64: Hash` is not satisfied`.

*Объяснение.* Derive устроен «поле за полем»: сгенерированная реализация `Eq` для структуры требует `Eq` от **каждого** поля (это видно по имени в ноте — `AssertParamIsEq`, служебная проверка, которую derive расставляет по полям). У `f64` его нет. Причина — `NaN` (R9): «не число» **не равно самому себе**, `NaN == NaN` даёт `false`. Значит, у плавающих типов равенство неполно: свойство «каждое значение равно себе» (рефлексивность) нарушено. `PartialEq` это допускает — на то он и «частичный»; `Eq` — пометка «исключений нет» — для `f64` была бы ложью, и стандартная библиотека её не даёт. Стрелка указывает на **поле**, а не на структуру: виновато не ваше объявление, а тип начинки.

Вторая ошибка — сверх того, о чём спрашивало задание, и она усиливает вывод: у `f64` нет и `Hash`. Причина того же корня: закон хеша гласит «равные ключи дают равные хеши», а с `NaN` (и с двумя нулями `0.0` и `-0.0`, которые равны, но различаются битами) согласовать хеш с равенством нельзя. Так что дробное поле закрывает дорогу в ключи `HashMap` дважды.

Практический вывод (§19.2.3): **дробные величины не годятся в ключи**. Если ключ логически содержит число с плавающей точкой, его переводят в целое (номер полки, миллиметры, копейки — то есть выбирают единицу, в которой величина целочисленна) или в строку с фиксированным форматом. Это не придирка компилятора, а честность о плавающей точке: «равенство» дробных величин почти всегда не то, что имеет в виду автор.

**Ответ:** минимальный набор — **`#[derive(PartialEq, Eq, Hash)]`** (`Debug` — сверх минимума, для печати). Путь по подсказкам: без derive — три ошибки сразу (E0277 про `Eq`, E0277 про `Hash` на `insert` и E0599 у `get` с полным списком в `help`); буквальное `#[derive(Eq)]` даёт E0277 про `PartialEq` — та же цепочка супертрейта, что в Г19.Ч1.З8, только `Eq` поверх `PartialEq`; полный набор работает (`Some(40)` по совпадающему ключу, `None` по отсутствующему). Минимальность доказана удалением: без `Hash`, без `Eq` и без `PartialEq` программа не собирается (три отдельных прогона). При `shelf: f64` derive отказывает **дважды**: `f64: Eq` не выполнено, потому что `NaN != NaN` ломает рефлексивность равенства и `Eq` как пометка «равенство полное» была бы ложью (стрелка указывает на поле — виноват тип начинки, а не структура); и `f64: Hash` не выполнено, потому что согласовать хеш с таким равенством нельзя. Вывод: дробные поля в ключи не годятся — величину переводят в целую единицу или в строку фиксированного формата.

**Типичный неверный подход: реализовать `PartialEq` руками, а `Hash` оставить derive.** Соблазн понятен: «на складе деталь определяется рядом, полка — справочная информация», — и равенство пишется по одному полю. Компилятор такое **пропускает**: `Eq` — пометка без методов, `Hash` дерайвится по всем полям, конфликта на уровне типов нет. Файл `t11_inconsistent.rs`:

```rust
// ⚠ намеренно рассогласованная пара: равенство смотрит только на ряд,
// а хеш (derive) считается по обоим полям
#[derive(Debug, Hash)]
struct PartId {
    row: char,
    shelf: u32,
}

impl PartialEq for PartId {
    fn eq(&self, other: &PartId) -> bool {
        self.row == other.row
    }
}

impl Eq for PartId {}
```

```
a == b? true
позиций в таблице: 2
get(A,1) = Some(40)
get(A,2) = Some(7)
get(A,3) = None
```

Программа собралась без единого предупреждения — и врёт. Первая строка: `PartId { row: 'A', shelf: 1 }` и `PartId { row: 'A', shelf: 2 }` **равны**. Вторая: в таблице их **два**, хотя равные ключи обязаны были схлопнуться в один. Последняя добивает: третий ключ, равный обоим (`row: 'A'`), не находит **ничего** — потому что его хеш посчитан по полю `shelf: 3`, и поиск ушёл в корзину, где никого нет.

Это и есть нарушение закона «равные ключи → равные хеши» (R9) в чистом виде: равенство склеило значения, хеш их развёл, и таблица потеряла способность отвечать на вопросы. Ошибок нет, паники нет, утечек нет — есть тихо неверные ответы, класс багов, за который том I ругал C. Правило §19.2.3 поэтому категорично: **для ключей — только полный derive-набор**; если равенство обязано быть нестандартным, `Hash` пишут руками по тем же полям, и оба места комментируют друг другом.

### Г19.Ч3.З1

**Условие.** Воспроизведите E0106 на своей функции `shortest(x: &str, y: &str) -> &str` (зеркало `longest`). Выпишите `help` и объясните формулировку «does not say whether it is borrowed from `x` or `y`» — почему компилятор проверяет вызовы по сигнатуре, а не по телу. Примените подсказку и добейтесь сборки.

**Решение.** ⛔ Файл `l1_bad.rs`:

```rust
fn shortest(x: &str, y: &str) -> &str {
    if x.len() < y.len() {
        x
    } else {
        y
    }
}
```

```
error[E0106]: missing lifetime specifier
 --> l1_bad.rs:1:34
  |
1 | fn shortest(x: &str, y: &str) -> &str {
  |                ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`
help: consider introducing a named lifetime parameter
  |
1 | fn shortest<'a>(x: &'a str, y: &'a str) -> &'a str {
  |            ++++     ++          ++          ++
```

Выписываем `help` целиком: `this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`` — «возвращаемый тип содержит одолженное значение, но сигнатура не говорит, у `x` оно одолжено или у `y`». И второй, деятельный: `consider introducing a named lifetime parameter` с готовой правкой и подчёркиванием `++` под каждой из четырёх вставок (объявление `<'a>` и три `'a` при ссылках).

*Почему компилятор проверяет вызовы по сигнатуре, а не по телу.* Формулировка сообщения — не жалоба на непонятливость, а описание отсутствующего **контракта**. Разложим на три довода, от практического к принципиальному.

**Довод первый: тело даёт ответ, которого нет при компиляции.** Какую ветку выберет `if x.len() < y.len()`, зависит от длин конкретных строк, а они известны только в рантайме. Даже прочитав тело целиком, компилятор не сможет сказать, чья память вернётся при данном вызове, — он может лишь заключить «либо `x`, либо `y`». А проверка обязана дать ответ до запуска. Отсюда и позиция Rust: страховать **худший случай** — результат считается связанным с обоими входами сразу, и жить ему не дольше того, который умрёт первым.

**Довод второй: тело — не место для проверки вызовов.** Функция вызывается из многих мест; если бы каждый вызов сверялся с телом, компилятору пришлось бы всякий раз заново прослеживать все пути внутри — и делать это заново после любой правки тела. Сигнатура же — краткое резюме, которого достаточно: проверил вызов против неё, и с телом дела нет. Это ровно та экономия, что позволяет проверять модули по отдельности.

**Довод третий, главный: сигнатура — граница ответственности.** Если проверка зависит от тела, то любое изменение тела способно молча сломать код вызывающих: сегодня функция возвращала кусок `x`, завтра — `y`, и чей-то давно работавший вызов перестал быть корректным, хотя его никто не трогал. Когда контракт записан в сигнатуре, автор функции волен переписывать тело как угодно, пока держит обещание; а нарушив обещание, он получит ошибку **у себя**, а не у пользователя. Тот же принцип, что у типов: `fn f(x: i32) -> String` не начинает вдруг возвращать `u8` оттого, что автор поменял внутренности.

Отсюда становится понятной и формулировка «does not say» — *не говорит*. Компилятор не заявляет «я не смог вывести»; он констатирует, что сигнатура не содержит нужного утверждения. Ответ должен дать автор — он один знает замысел.

*Применяем подсказку.* Файл `l1.rs`:

```rust
fn shortest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() < y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let a = String::from("длинная строка");
    let b = String::from("короче");
    println!("короче: {}", shortest(&a, &b));
}
```

```
короче: короче
```

Собралось. Читаем сигнатуру: «существует время жизни `'a`; оба входа живут как минимум `'a`; результат действителен как минимум `'a`» — то есть результат годен, пока живы **оба** аргумента (§19.3.1). Заметьте, что тело не изменилось ни на символ: аннотация ничего не делает, она сообщает.

Мелочь для проверки понимания: короче здесь оказалась строка `"короче"` — 6 символов против 14, но сравниваются **байты** (`len()` — длина в байтах, §17.1.4), и на кириллице обе величины вдвое больше; на порядок это не влияет, а вот на «длиннее ли `"abc"` строки `"аб"`» — повлияло бы.

**Ответ:** ошибка воспроизведена (`l1_bad.rs`): `E0106: missing lifetime specifier`, `help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y``, плюс `help: consider introducing a named lifetime parameter` с готовой сигнатурой `fn shortest<'a>(x: &'a str, y: &'a str) -> &'a str`. Формулировка означает: в сигнатуре нет утверждения о том, с каким из входов связан результат. Компилятор проверяет вызовы по сигнатуре, потому что (1) ответ «какая ветка» принадлежит рантайму, и страховать приходится худший случай; (2) сверка каждого вызова с телом заставляла бы перепроверять все пути функции при каждом обращении и после каждой правки; (3) главное — сигнатура есть граница ответственности: пока контракт держится, автор волен менять тело, не ломая чужие вызовы. Подсказка применена, `l1.rs` собирается и печатает `короче: короче`; тело при этом не изменилось — аннотация описывает, а не управляет.

**Условие.** Прогоните `shortest` в двух сценариях §19.3.1: результат используется внутри блока (обе строки живы) и результат вынесен за блок (E0597). Для каждой строки ошибки второго сценария скажите, на что она указывает (`binding declared here` / `dropped here while still borrowed` / `borrow later used here`) — сравните с рисунком областей.

**Решение.** *Сценарий 1 — результат используется внутри блока.* Файл `l2.rs`:

```rust
fn main() {
    let outer = String::from("снаружи");
    {
        let inner = String::from("внутри блока");
        let result = shortest(&outer, &inner);
        println!("внутри блока короче: {result}");
    }
    println!("outer всё ещё жива: {outer}");
}
```

```
внутри блока короче: снаружи
outer всё ещё жива: снаружи
```

Собралось и отработало. Контракт соблюдён: `result` используется там, где живы **обе** строки. Времена жизни `outer` и `inner` при этом разные — и это законно: `'a` не требует равенства, он берётся как общий минимум (§19.3.1). А первая строка вывода — маленький сюрприз для тех, кто читал глазами: короче оказалась `"снаружи"` (14 байт) против `"внутри блока"` (23 байта), хотя по числу символов разрыв меньше, — снова напоминание, что `len()` считает байты.

*Сценарий 2 — результат вынесен за блок.* ⛔ Файл `l2_bad.rs`:

```rust
}
```

```
14 |         result = shortest(&outer, &inner);

15 |     }

16 |     println!("короче: {result}");
   |                        ------ borrow later used here
```

*Построчный разбор — и соответствие рисунку областей.* Сообщение читается как протокол из четырёх пунктов, и каждый — точка на рисунке §19.3.1.

```
   fn main() {
       let outer = ...;                       ──┐ время жизни outer
       let result;                              │
       {                                        │
           let inner = ...;              ──┐    │  ← (1) binding declared here
           result = shortest(&outer, &inner);   │  ← (2) взято заимствование
       }                                 ──┘    │  ← (3) dropped here while still borrowed
       println!("{result}");                    │  ← (4) borrow later used here
   }                                          ──┘
```

1. **`binding `inner` declared here`** (строка 13) — указывает на **рождение владельца**. Это левая граница внутренней скобки: с этого места и до конца блока `inner` владеет своим буфером. Компилятор показывает её, чтобы вы видели, откуда отсчитывать: виновата не сама строка, но всё дальнейшее меряется от неё.
2. **`^^^^^^ borrowed value does not live long enough`** (строка 14, под `&inner`) — **точка взятия заимствования** и формальное место ошибки. Именно здесь из `inner` извлекается ссылка, которая по контракту `shortest<'a>` попадает в результат. Стрелка стоит под аргументом, а не под вызовом: проблема в конкретном заимствовании.
3. **`- `inner` dropped here while still borrowed`** (строка 15, закрывающая скобка) — **момент смерти владельца**. Правая граница внутренней скобки: здесь `inner` уничтожается (`drop`, §15.1.1), а заимствование, как сообщает компилятор, всё ещё живо. Это и есть нарушение: скобка заимствования не вложилась в скобку владельца.
4. **`------ borrow later used here`** (строка 16, под `result`) — **последнее использование заимствования**. Именно оно делает нарушение фактом: не будь этой строки, заимствование закончилось бы раньше смерти `inner`, и всё было бы законно (borrow checker считает заимствование живым до последнего использования, а не до конца области видимости).

Четыре пункта складываются в законченное доказательство: *взяли здесь* (2) *у того, кто родился здесь* (1), *владелец умер здесь* (3), *а ссылка понадобилась после — здесь* (4). Читать сообщения E0597 удобнее всего именно в этом порядке — 1, 2, 3, 4, — и сразу видно, какую из четырёх точек проще подвинуть: обычно чинится либо (1) — объявить владельца выше, во внешней области, либо (4) — использовать результат раньше, как в сценарии 1.

Отдельно стоит заметить, чего в сообщении **нет**: ни слова о том, какую ветку вернула бы `shortest`. А ведь в этом запуске она вернула бы `&outer` — `"снаружи"` короче! Компилятор запрещает **оба** исхода, потому что сигнатура обещала «не дольше меньшего из входов», и точка (§19.3.1). Проверка статическая: гарантии даются сразу на все исходы, а не на удачный.

**Ответ:** сценарий 1 (`l2.rs`) собирается и печатает `внутри блока короче: снаружи` / `outer всё ещё жива: снаружи` — результат использован там, где живы обе строки, и разные времена жизни входов законны. Сценарий 2 (`l2_bad.rs`) даёт E0597; строки сообщения: `binding `inner` declared here` — рождение владельца, левая граница внутренней области; `^^^^ borrowed value does not live long enough` под `&inner` — точка взятия заимствования и формальное место ошибки; `` `inner` dropped here while still borrowed`` на закрывающей скобке — смерть владельца, правая граница; `borrow later used here` под `result` — последнее использование заимствования, которое и делает нарушение фактом. Вместе они образуют доказательство «взяли — у этого — он умер — а ссылка понадобилась позже», то есть внутренняя скобка владельца не вместила скобку заимствования. Запрещены оба исхода `if`, включая тот, который в этом запуске сработал бы: проверка статическая.

### Г19.Ч3.З3

**Условие.** Верните Г16.Ч1.З5: структура `Label { text: &str }` теперь чинится **вторым** способом — аннотацией. Запишите `Label<'a>`, создайте экземпляр от строки-литерала и от `String`, напечатайте оба. Ответьте: почему вариант с литералом работал бы даже при `text: &'static str`, а вариант со `String` — нет?

**Решение.** Файл `l3.rs`:

```rust
struct Label<'a> {
    text: &'a str,
}

fn main() {
    let from_literal = Label { text: "литерал" };

    let owned = String::from("строка в куче");
    let from_string = Label { text: &owned };

    println!("из литерала: {}", from_literal.text);
    println!("из String:   {}", from_string.text);
}
```

```
из литерала: литерал
из String:   строка в куче
```

Долг Г16.Ч1.З5 закрыт: `&str`-поле стало законным, как только у структуры появился контракт с чужой памятью. Читается объявление так: «`Label<'a>` — структура, которая **не может пережить** ссылку, лежащую в её поле» (§19.3.2). Аннотация в угловых скобках — объявление параметра, `'a` при `&` — его использование; ровно та же пара ролей, что у `<T>` в `impl<T> Point<T>` (§19.1.2), потому что времена жизни — разновидность обобщённых параметров.

Обратите внимание, что оба экземпляра строятся **одинаково** и живут в одной программе. `Label<'a>` не спрашивает, откуда пришла ссылка: `'a` выводится из аргумента отдельно для каждого случая — для первого он окажется `'static`, для второго ограничен областью жизни `owned`. Один тип, два разных инстанцирования по времени жизни.

*Почему литерал прошёл бы и при `&'static str`, а `String` — нет.* Потому что у этих двух ссылок **разные владельцы, и один из них — сама программа**.

Строковый литерал `"литерал"` — не значение, которое кто-то создаёт и уничтожает: его байты лежат в исполняемом файле и доступны всё время работы процесса (§19.3.2; в C то же самое — статическая длительность хранения строковых литералов, C5 §6.4.5, курс §5.2.1). Ссылка на него имеет тип `&'static str` и удовлетворяет любому требованию: обещание «живу всю программу» сильнее всякого «живу как минимум столько-то».

`String` же — значение с буфером в куче, которым владеет переменная `owned`. Буфер освобождается, когда владелец выходит из области видимости (§15.1.1). Ссылка `&owned` действительна ровно до этого момента — то есть заведомо **не** всю программу. Требование `&'static str` она удовлетворить не может: обещать вечность за чужой счёт нельзя.

⛔ Проверим это, а не поверим на слово. Файл `l3_static_bad.rs` — то же самое, но поле объявлено `&'static str`:

Ошибка ровно там, где предсказано: на строке с `&owned`, и с исчерпывающей формулировкой — **`this usage requires that `owned` is borrowed for `'static``**. Первая же строка (`from_literal`) при этом прошла молча: литералу `'static` не в тягость.

Заметьте деталь, полезную для интуиции: `owned` умирает в самом конце `main`, то есть живёт почти всю программу. «Почти» здесь не считается — `'static` означает «до конца процесса», а не «долго». Никакое удлинение области видимости не спасёт: пока у значения есть владелец с областью, оно не `'static`.

*Мораль.* `'static` в объявлении поля — не «более безопасный» и не «более сильный» вариант `'a`, а **более узкий**: он превращает структуру из «вида на чью угодно строку» в «вид только на вечные строки». Именно поэтому `Label<'a>` — правильный ответ задания, а `'static` — тот самый «чит-код», о котором предупреждает §19.3.2: он не решает проблему висячих ссылок, он лишь отсекает всех, кроме литералов. Совет компилятора «consider using the `'static` lifetime» полезно читать с этой поправкой.

**Ответ:** код — листинг `l3.rs`; вывод `из литерала: литерал` / `из String: строка в куче`. `Label<'a>` означает «экземпляр не может пережить ссылку в своём поле»; `'a` выводится для каждого экземпляра свой. Вариант с литералом прошёл бы и при `text: &'static str`, потому что байты литерала лежат в исполняемом файле и доступны всё время работы процесса (§19.3.2; в C — статическая длительность хранения, C5 §6.4.5), а `'static` удовлетворяет любому требованию. Вариант со `String` — нет: буфер принадлежит переменной и освобождается на выходе из области видимости, поэтому ссылка заведомо не вечна. Проверено (`l3_static_bad.rs`): `E0597: `owned` does not live long enough` с прямой формулировкой `this usage requires that `owned` is borrowed for `'static``, причём строка с литералом в той же программе собирается без нареканий. `'static` в поле — не «более надёжный» `'a`, а более узкий: он сужает структуру до вида на вечные строки.

**Вариант 2 (владеющее поле — первый способ из Г16.Ч1.З5).** Ту же задачу можно решить и без единой аннотации, если поле будет владеть текстом. Файл `l3v2.rs`:

```rust
    text: String,

    let from_literal = Label {

    let owned = String::from("строка в куче");
    let from_string = Label {
        text: owned.clone(),
    };

    println!("из литерала: {}", from_literal.text);
    println!("из String:   {}", from_string.text);
    println!("исходная строка цела: {owned}");
```


*Сравнение.* Видимый результат одинаков — различия начинаются за пределами этих трёх строк. **Владеющая версия самодостаточна**: `Label` ни от кого не зависит, его можно положить в вектор, вернуть из функции, отправить в другой поток (глава 23), сохранить надолго — и ни один компилятор ни о чём не спросит, потому что аннотировать нечего. Плата — копирование: и литерал, и чужая строка переносятся в собственный буфер (`String::from`, `.clone()`), то есть на каждый `Label` приходится выделение памяти, а третья строка вывода показывает, что исходная строка при этом живёт своей жизнью — данные раздвоились. **Версия со ссылкой не копирует ничего** (это «вид» на чужую память, ровно как срезы §15.3), но платит связанностью: `Label<'a>` не переживёт источник, и всякий, кто захочет хранить такую метку в своей структуре, обязан будет протащить лайфтайм и через себя — «заражение», о котором предупреждает §19.3.2. Когда что: по умолчанию — владеющее поле (правило §16.1.1 остаётся в силе, и это же первый способ Г16.Ч1.З5); ссылка — когда копия действительно дорога или бессмысленна, а сам «вид» короткоживущ: разбор большого буфера, отчёт по чужому тексту, парсеры вроде `KeyValue` из Г19.Ч3.З8. Мера простая: если приходится долго думать, чью память вы храните, — это и есть сигнал хранить свою.

### Г19.Ч3.З4

**Условие.** *(понимание)* Не компилируя, примените три правила умолчаний к сигнатурам: (а) `fn trim_start(s: &str) -> &str`; (б) `fn pick(a: &str, b: &str) -> &str`; (в) `fn tail(&self) -> &str` (метод `Excerpt`); (г) `fn len_of(s: &str) -> usize`. Для каждой запишите развёрнутую форму (или вердикт «E0106») и объясните, какое правило сработало. Проверьте компилятором.

**Решение.** Напомним правила (§19.3.2): **1)** каждый параметр-ссылка получает своё время жизни; **2)** если входное время жизни ровно одно — оно присваивается всем выходным; **3)** если среди входов есть `&self`/`&mut self` — выходным присваивается время жизни `self`.

*(а) `fn trim_start(s: &str) -> &str`.* Правило 1 даёт единственному параметру `'a`. Входное время жизни одно — срабатывает правило 2 и присваивает его результату. Выход без времени жизни не остался, аннотации не нужны. Развёрнутая форма:

```rust
fn trim_start<'a>(s: &'a str) -> &'a str
```

*(б) `fn pick(a: &str, b: &str) -> &str`.* Правило 1 даёт `'a` и `'b` — **два** входных времени жизни. Правило 2 неприменимо (входное не одно). Правило 3 неприменимо (нет `&self`, это свободная функция). Выход остался без времени жизни — **вердикт: E0106**.

*(в) `fn tail(&self) -> &str` — метод `Excerpt`.* Правило 1 даёт `&self` своё время жизни. Входное здесь формально одно, но даже будь их больше, вступило бы правило 3: результат получает время жизни `self`. Развёрнутая форма (имя параметра произвольно, важно, что он тот же, что у `self`):

```rust
fn tail<'s>(&'s self) -> &'s str
```

Стоит отметить, что `'a` из объявления `Excerpt<'a>` — **другое** время жизни: `'a` описывает, сколько живёт строка, на которую смотрит поле `part`, а `'s` — сколько живёт заимствование самой структуры. Правило 3 привязывает результат ко второму, более короткому.

*(г) `fn len_of(s: &str) -> usize`.* Правило 1 даёт параметру `'a`. Выход — `usize`, не ссылка; связывать нечего, правила 2 и 3 просто не о чем применять. Аннотации не нужны, и писать их было бы шумом («лайфтаймы на всякий случай», §19.3.1):

```rust
fn len_of<'a>(s: &'a str) -> usize
```

*Проверка компилятором.* Три собирающиеся сигнатуры — файл `l4.rs`:

```rust

    let bytes = s.as_bytes();
    for i in 0..bytes.len() {
        if bytes[i] != b' ' {
            return &s[i..];
        }
    }
    ""
}

    // (в) есть &self → правило 3

        let bytes = self.part.as_bytes();
        for i in 0..bytes.len() {
            if bytes[i] == b' ' {
                return &self.part[i + 1..];
            }
        }
        ""
    }
}

// (г) выход не ссылка → связывать нечего

    s.len()
}
```

Собралось без единого предупреждения. (`len_of("абв")` даёт 6, а не 3, — снова байты, §17.1.4.)

**Ответ:** (а) `fn trim_start<'a>(s: &'a str) -> &'a str` — правило 1 дало единственное входное время жизни, правило 2 присвоило его результату; (б) **E0106** — правило 1 дало два входных времени жизни, правило 2 неприменимо (входное не одно), правило 3 неприменимо (нет `&self`), выход остался несвязанным; (в) `fn tail<'s>(&'s self) -> &'s str` — правило 3 привязало результат к `&self` (и это время жизни отлично от `'a` в `Excerpt<'a>`: `'a` — про строку за полем, `'s` — про заимствование структуры); (г) `fn len_of<'a>(s: &'a str) -> usize` — выход не ссылка, связывать нечего, аннотация была бы шумом. Проверено компилятором: `l4.rs` (а, в, г) собирается и печатает `"отступ"` / `"слова"` / `6`; `l4_bad.rs` (б) даёт E0106 с тем же `help`, что у `longest`; `l4_explicit.rs` с вручную выписанными аннотациями собирается и даёт побайтно тот же вывод — развёрнутые формы равносильны исходным.

### Г19.Ч3.З5

**Условие.** *(понимание)* В `longest_scope_bad.rs` замените `String::from("внутри блока")` на литерал `let inner = "внутри блока";`. Предскажите: соберётся ли теперь — и почему (`&'static str` против `&String`; кто владелец литерала?). Проверьте и объясните результат через «меньшее из времён жизни».

**Решение.** *Предсказание.* **Соберётся.** Рассуждение — по контракту `longest<'a>`: результат живёт не дольше *меньшего* из времён жизни входов. Раньше входами были `&outer` (живёт до конца `main`) и `&inner`, где `inner` — `String`, умирающая на закрывающей скобке блока; меньшим оказывалось второе, и `result`, использованный после блока, нарушал контракт. Теперь `inner` — строковый литерал, то есть `&'static str`: его данные живут всю программу. Минимум из «до конца `main`» и «всю программу» — первое, и оно с запасом покрывает `println!` после блока. Нарушать нечего.

Файл `l5.rs`:

```rust
fn main() {
    let outer = String::from("снаружи");
    let result;
    {
        let inner = "внутри блока";
        result = longest(&outer, inner);
    }
    println!("длиннее: {result}");
}
```

```
длиннее: внутри блока
```

Предсказание подтвердилось: программа собралась и напечатала кусок той самой строки, которая «умерла» вместе с блоком, — точнее, той, которая никогда там и не жила.

*Кто владелец литерала.* Никто из переменных — и в этом всё дело. Байты `"внутри блока"` лежат в самом исполняемом файле; переменная `inner` хранит не строку, а **ссылку** на эти байты (тип `&'static str` — указатель плюс длина, §15.3). Когда блок заканчивается, уничтожается переменная `inner`, то есть сама ссылка, — а данные, на которые она указывала, никуда не деваются: у них нет владельца, который мог бы их освободить. Сравните с прежней версией: там `inner: String` **владела** буфером в куче, и на закрывающей скобке буфер освобождался (`drop`, §15.1.1) — вот тогда ссылка и повисала.

Формально: `&outer` имеет тип `&'m str`, где `'m` — область жизни `outer` (до конца `main`); `inner` имеет тип `&'static str`. При вызове компилятор подбирает `'a` как общее — берётся меньшее, то есть `'m`. Результат получает `'m` и законно используется в `println!`, который тоже внутри `'m`. Ровно то же произошло бы, если бы обе строки были литералами (тогда `'a = 'static`).

*Побочный опыт: `&inner` тоже работает.* В исходном коде вызов был записан как `longest(&outer, &inner)`, и заменив тип `inner`, мы получаем `&&str` вместо `&str`. Файл `l5_amp.rs` — та же программа с сохранённым амперсандом:

```rust
        let inner = "внутри блока";
        result = longest(&outer, &inner);
```

```
длиннее: внутри блока
```

Тоже собирается и даёт тот же ответ: `&&str` приводится к `&str` разыменованием, и полученная ссылка наследует `'static` от самих данных, а не от переменной `inner`. Полезная деталь: местная переменная-ссылка не «укорачивает» то, на что смотрит.

*Мораль.* Ошибка E0597 в исходном сценарии была **не про блок и не про имя `inner`**, а про владение: там внутри блока умирал владелец данных. Убрали владельца — исчезла и ошибка, хотя область видимости переменной осталась прежней. Это тот самый практический совет §19.3.1: столкнувшись с лайфтаймом, спрашивайте не «где кончается область видимости», а **«чью память я возвращаю и кто ею владеет»**.

**Ответ:** соберётся — и собирается: `l5.rs` печатает `длиннее: внутри блока`. Причина: `inner` теперь `&'static str`, ссылка на байты, лежащие в исполняемом файле; владельца, который освободил бы данные на выходе из блока, не существует — уничтожается лишь сама переменная-ссылка. Через «меньшее из времён жизни»: входы имеют времена `'m` (область жизни `outer`, до конца `main`) и `'static`; `'a` берётся как меньшее, то есть `'m`, а использование результата в `println!` лежит внутри `'m` — контракт соблюдён. В прежней версии `inner: String` владела буфером, буфер освобождался на закрывающей скобке, меньшим оказывалось время жизни блока — отсюда E0597. Дополнительно проверено (`l5_amp.rs`), что запись `&inner` (то есть `&&str`) тоже собирается: разыменование даёт `&str` со временем жизни самих данных, а не переменной.

### Г19.Ч3.З6

**Условие.** *(понимание)* Сформулируйте, почему `fn dangle() -> &String { let s = String::from("hi"); &s }` не спасти **никакой** аннотацией (включая `'static`): каких фактов о коде потребовала бы каждая запись и почему они ложны. Сравните с судьбой `dangle_c.c` из §15.2.3 (собрался с предупреждением) и назовите главу тома I, в которой этот класс багов ловили только в рантайме.

**Решение.** ⛔ Исходная запись — файл `l6_bad.rs`:

```rust
fn dangle() -> &String {
    let s = String::from("hi");
    &s
}
```

```
error[E0106]: missing lifetime specifier
 --> l6_bad.rs:1:16
  |
1 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |

  |                 +++++++

  |

  |
```

Заметьте, чем этот E0106 отличается от того, что мы видели у `shortest`: там `help` гласил «сигнатура не говорит, у `x` или у `y` одолжено», здесь — **`there is no value for it to be borrowed from`**, «нет значения, у которого можно было бы одолжить». Не «непонятно, у кого», а «не у кого»: у функции нет ни одного параметра-ссылки. И компилятор сразу предлагает два выхода, причём второй — с прямым указанием на предпочтительность: `instead, you are more likely to want to return an owned value`.

*Почему не спасёт никакая аннотация.* Аннотация — это **утверждение о фактах**, которое компилятор проверяет (§19.3.1: «описывают, а не меняют»). Переберём все мыслимые записи и посмотрим, какой факт каждая утверждает и почему он ложен.

**Запись 1: `-> &'static String`.** Утверждает: «возвращаемая ссылка действительна всё время работы программы». Ложно: `s` — локальная переменная, владеющая буфером в куче; на выходе из функции она уничтожается, буфер освобождается (§15.1.1). Ссылка перестаёт быть действительной через несколько машинных команд после возврата, а не «никогда».

**Запись 2: `fn dangle<'a>() -> &'a String`.** Утверждает нечто ещё более сильное: «для **любого** времени жизни `'a`, которое выберет вызывающий, я верну действительную ссылку». Параметры объявляет вызывающая сторона — а значит, функция обязуется обслужить самый долгий запрос, включая `'static`. Ложно по той же причине.

**Запись 3: связать с входом** — `fn dangle<'a>(x: &'a str) -> &'a String`. Утверждает: «результат — часть памяти, одолженной у `x`». Ложно фактически: возвращается ссылка на `s`, к `x` отношения не имеющую. (И заметьте: сама по себе такая сигнатура законна — ошибка вылезет в теле, на строке `&s`.)

Общий знаменатель: **все три записи описывают память, которой не существует к моменту возврата**. Аннотация не продлевает жизнь и не переносит владение — она лишь называет связь, которую компилятор потом проверит. Назвать можно что угодно; пройти проверку — нет.

Проверим это, а не поверим. ⛔ Файл `l6_static_bad.rs` (запись 1) и ⛔ `l6_a_bad.rs` (запись 2) дают **одинаковый** ответ:

```
error[E0515]: cannot return reference to local variable `s`
 --> l6_static_bad.rs:3:5
  |
3 |     &s
  |     ^^ returns a reference to data owned by the current function
```

Ошибка сменилась: E0106 («не хватает аннотации») ушла — аннотация ведь появилась, — и обнажилась настоящая проблема, E0515 «cannot return reference to local variable», с исчерпывающей формулировкой `returns a reference to data owned by the current function`. Это и есть демонстрация тезиса: аннотация переводит разговор с «чего не хватает в сигнатуре» на «что не так с кодом», но кода не чинит. Единственное настоящее лечение — второй `help` компилятора: **вернуть владение**, `-> String` и `s` без амперсанда.

*Сравнение с `dangle_c.c`.* Тот же сюжет на C — файл `l6_c.c`, компилятор тома I:

```c
#include <stdio.h>

int *dangle(void) {
    int x = 42;
    return &x;
}

int main(void) {
    int *p = dangle();
    printf("%d\n", *p);
    return 0;
}
```

```

l6_c.c:5:12: warning: function returns address of local variable [-Wreturn-local-addr]
    5 |     return &x;
      |            ^~
```

Сборка завершилась **успешно** (код возврата 0) — предупреждение не остановило её. Запуск на эталонной машине:

```
Segmentation fault (код возврата 139)
```

Разница видна во всей полноте, и она в трёх пунктах.

1. **Статус диагностики.** GCC говорит «warning» — сообщение, которое можно не заметить в потоке сборки, отключить флагом или просто проигнорировать; артефакт при этом создаётся. Rust говорит «error» — исполняемого файла не появится, пока код не исправлен.
2. **Момент расплаты.** В C программа существует и запускается; расплата приходит при обращении по адресу — в этом запуске падением, но с равным успехом могло бы напечататься `42` (если стековая память ещё не переиспользована) или произвольный мусор. Это то самое «когда повезёт», которым том I описывал UB.
3. **Что вообще ловится.** `-Wreturn-local-addr` покрывает самый очевидный случай — возврат адреса локальной переменной прямо из функции. Стоит спрятать адрес в структуру, вернуть его через промежуточную функцию или отдать указатель на буфер, который вызывающий освободит раньше времени, — и предупреждение молчит (§19.3.1). Rust же проверяет не образец кода, а **контракт**: E0515 сработает независимо от того, насколько хитро адрес добирался до `return`.

*Глава тома I.* Класс багов «указатель пережил свою память» ловился **только в рантайме** — и главой, которая этим занималась, была **глава 13** («Неопределённое поведение»): там use-after-free, чтение за границей и возврат локального адреса демонстрировались запусками и разбирались как поведение, зависящее от везения (§13.1, `oob.c` — «три запуска, три разных мусора»). Инструментом были санитайзеры — ASan из §7.2.2, — то есть **посмертная** диагностика: программа собиралась, запускалась и падала уже под наблюдением. Rust переносит эту же проверку на этап компиляции, и в этом весь смысл главы 15 и части 19.3: контракт, который в C жил в комментарии к функции, переехал в сигнатуру и стал проверяемым.

**Ответ:** не спасёт ни одна аннотация, потому что аннотация — утверждение о фактах, а все возможные утверждения здесь ложны. `-> &'static String` заявляет «ссылка действительна всю программу» — ложь: `s` уничтожается на выходе из функции. `fn dangle<'a>() -> &'a String` заявляет «верну действительную ссылку для любого `'a`, выбранного вызывающим» — ложь по той же причине и в более сильной форме. Связывание с входом (`(x: &'a str) -> &'a String`) заявляет «результат одолжен у `x`» — ложь фактически: возвращается ссылка на `s`. Проверено: обе первые записи дают `E0515: cannot return reference to local variable `s`` / `returns a reference to data owned by the current function` — E0106 уходит, настоящая проблема остаётся. Лечение одно, и его предлагает сам компилятор: вернуть владение (`-> String`). В C (`l6_c.c`) тот же код собирается **успешно** с предупреждением `-Wreturn-local-addr`, а на запуске даёт Segmentation fault (код 139) — при этом мог бы и напечатать мусор: разница в статусе (warning против error), в моменте расплаты (рантайм против компиляции) и в охвате (предупреждение ловит лишь прямой возврат адреса локальной, borrow checker — любой путь). Класс багов ловился только в рантайме в **главе 13** (UB: use-after-free и возврат локального адреса), инструментом были санитайзеры из §7.2.2.

### Г19.Ч3.З7

**Условие.** *(понимание)* Метод `fn compare<'b>(&self, other: &'b str) -> &str` у `Excerpt<'a>` возвращает `self.part`. По какому правилу выведен лайфтайм результата? А если тело вернёт `other` — соберётся ли (предскажите по контракту сигнатуры, затем проверьте)? Объясните сообщение компилятора через «сигнатура обещает одно, тело делает другое».

**Решение.** Файл `l7.rs`:

```rust
impl<'a> Excerpt<'a> {
    fn compare<'b>(&self, other: &'b str) -> &str {
        if self.part.len() >= other.len() {
            println!("свой кусок не короче чужого");
        } else {
            println!("чужая строка длиннее");
        }
        self.part
    }
}
```

```
свой кусок не короче чужого
вернулось: "Влад"
чужая строка длиннее
вернулось: "Влад"
```

(В `main` `Excerpt` построен как `&book[..8]` — восемь **байтов** кириллицы, то есть четыре символа, §17.1.4; отсюда `"Влад"`.)

*По какому правилу выведен лайфтайм результата.* По **правилу 3**: среди входов есть `&self`, значит, всем выходным временам жизни присваивается время жизни `self` (§19.3.2). Развёрнутая форма сигнатуры:

```
fn compare<'s, 'b>(&'s self, other: &'b str) -> &'s str
```

Проследим порядок применения правил, потому что здесь он поучителен. Правило 1 раздаёт своё время жизни каждому параметру-ссылке: `&self` получает (назовём) `'s`, `other` — уже объявленное `'b`. Входных времён жизни, стало быть, **два** — правило 2 неприменимо. И вот тут вступает правило 3, которое и существует ради методов: наличие `&self` разрывает неоднозначность в его пользу. Не будь третьего правила, `compare` требовал бы явной аннотации ровно как `longest`.

Обратите внимание на три разных времени жизни, которые сошлись в одном методе: `'a` — сколько живёт строка, на которую смотрит `part`; `'s` — сколько живёт заимствование самой структуры; `'b` — сколько живёт чужая строка. Результат привязан к `'s`, то есть к самому короткому из «своих»: пока жив `&self`, жив и возвращённый кусок. Это безопасно и с запасом: `part` живёт `'a`, а `'a` заведомо не короче `'s` (иначе структура пережила бы свою ссылку, чего `Excerpt<'a>` не допускает).

*Если тело вернёт `other`.* **Предсказание: не соберётся.** Контракт сигнатуры после умолчаний гласит `-> &'s str` — «результат действителен столько же, сколько заимствование `self`». Тело же вернёт `other`, действительный `'b`. Компилятор не знает никакой связи между `'s` и `'b`: вызывающий волен передать строку, живущую **меньше**, чем структура, и тогда обещание сигнатуры окажется ложью.

⛔ Файл `l7_bad.rs` — то же самое с `other` вместо `self.part`:

```

  --> l7_bad.rs:12:9

   |                |
   |                lifetime `'b` defined here
...
12 |         other
   |         ^^^^^ method was supposed to return data with lifetime `'1` but it is returning data with lifetime `'b`
   |

   |
```

Предсказание подтверждено.

*Объяснение через «сигнатура обещает одно, тело делает другое».* Сообщение построено именно как сопоставление обещания и поступка, и читать его нужно в четыре шага.

1. **`lifetime `'b` defined here`** — компилятор называет первое из участвующих времён жизни: то, что мы объявили сами.
2. **`let's call the lifetime of this reference `'1``** — второе время жизни имени не имеет (мы его не писали, оно возникло по правилу 1 из `&self`), поэтому компилятор **даёт ему имя на ходу**: `'1`. Это чисто диагностический приём: чтобы говорить о безымянном, нужно как-то его назвать.
3. **`method was supposed to return data with lifetime `'1` but it is returning data with lifetime `'b`** — сердцевина. «Метод **обязан был** вернуть данные со временем жизни `'1`» — это про сигнатуру, где правило 3 привязало результат к `&self`. «Но возвращает данные со временем жизни `'b`» — это про тело. Обещание и поступок предъявлены рядом.
4. **`help: consider reusing a named lifetime parameter … -> &'b str`** — предложение привести **сигнатуру** в соответствие с телом: раз возвращаете чужую строку, так и обещайте. Обратите внимание на направление правки: компилятор не предлагает менять тело — он исходит из того, что автор знает, что хочет вернуть, и ошибся в описании.

Существенно, что ошибка — **не** E0106 и не E0597. Это не «не хватает аннотации» (аннотаций хватает) и не «значение не доживает» (никакого конкретного значения тут ещё нет — функция даже не вызвана ни разу). Это несоответствие двух описаний одного и того же: контракта и его исполнения. Проверка происходит **внутри** функции, независимо от вызовов, — ровно как проверка тела обобщённой функции в §19.1.1. Симметрия полная: там сигнатура обещала «`T` умеет только то, что перечислено», и тело обязано было уложиться; здесь сигнатура обещает «результат живёт столько-то», и тело обязано уложиться.

И последнее: правка из `help` **изменит контракт** для всех вызывающих — теперь результат будет жить не дольше переданной строки. Это законно, но это другой метод. Выбирать между «вернуть свой кусок» и «вернуть чужую строку» должен автор, а компилятор лишь настаивает, чтобы выбор был записан честно.

**Ответ:** лайфтайм результата выведен по **правилу 3** (среди входов есть `&self`, и выходные получают его время жизни); развёрнутая форма — `fn compare<'s, 'b>(&'s self, other: &'b str) -> &'s str`. Правило 2 здесь неприменимо: входных времён жизни два (`'s` от `&self` и объявленное `'b`), и без третьего правила метод требовал бы явной аннотации, как `longest`. При возврате `other` программа **не собирается**: `error: lifetime may not live long enough` с ключевой строкой `method was supposed to return data with lifetime `'1` but it is returning data with lifetime `'b``. Сообщение и есть сопоставление обещания с поступком: `'1` — имя, которое компилятор даёт на ходу безымянному времени жизни `&self` (сигнатура обещала результат с ним), `'b` — время жизни фактически возвращаемых данных. Ошибка обнаруживается внутри функции, без единого вызова, — симметрично проверке тела обобщённой функции в §19.1.1; `help` предлагает исправить **сигнатуру** (`-> &'b str`), то есть честно объявить новый контракт, а не подгонять тело.

### Г19.Ч3.З8

**Условие.** *(прикладное)* Структура-«вид» для разбора: `struct KeyValue<'a> { key: &'a str, value: &'a str }` и функция `fn split_kv(line: &str) -> KeyValue`, режущая строку вида `"host=local"` по первому `'='` (приём `first_word` из §15.3.2, разделитель другой). Аннотируйте всё, что потребует компилятор; прогоните на двух строках; затем воспроизведите E0597, дав строке умереть раньше `KeyValue`. Почему у `split_kv` аннотация в возвращаемом типе не понадобилась (какое правило)?

**Решение.** Файл `l8.rs`:

```rust
struct KeyValue<'a> {
    key: &'a str,
    value: &'a str,
}

fn split_kv(line: &str) -> KeyValue<'_> {
    let bytes = line.as_bytes();
    for i in 0..bytes.len() {
        if bytes[i] == b'=' {
            return KeyValue {
                key: &line[..i],
                value: &line[i + 1..],
            };
        }
    }
    KeyValue {
        key: line,
        value: "",
    }
}
```

```
ключ "host", значение "local"
ключ "port", значение "8080"
ключ "без-разделителя", значение ""
```

Прогон на двух строках из условия (одна — `String`, вторая — литерал) плюс контрольная строка без разделителя.

*Что потребовало аннотации, а что нет.* Аннотация обязательна ровно в одном месте — **в объявлении структуры**: `&str`-поле без времени жизни даёт E0106 (§16.1.1, долг закрыт в §19.3.2). Один параметр `'a` на оба поля здесь уместен: и ключ, и значение — куски одной и той же строки, их судьбы совпадают. Разводить их по `'a` и `'b` можно, но незачем: два параметра описывали бы возможность собрать `KeyValue` из кусков **разных** строк, чего наша функция не делает.

В сигнатуре `split_kv` времена жизни расставлять не пришлось — их вывели правила умолчаний (об этом ниже). Не потребовалось аннотаций и в теле: срезы `&line[..i]`, `&line[i + 1..]` наследуют время жизни `line` автоматически.

Устройство разбора — `first_word` из §15.3.2 с двумя правками: разделитель `b'='` вместо `b' '`, и вместо одного куска возвращаются два — до разделителя и после. Срез по байтам безопасен: `=` — однобайтовый ASCII-символ, поэтому граница `i + 1` заведомо попадает на начало символа и паники «not a char boundary» не будет даже на кириллице (третья строка прогона — тому подтверждение).

*Воспроизводим E0597.* ⛔ Файл `l8_bad.rs` — строка умирает раньше, чем `KeyValue`:

```rust
fn main() {
    let kv;
    {
        let line = String::from("host=local");
        kv = split_kv(&line);
    }
    println!("ключ {:?}, значение {:?}", kv.key, kv.value);
}
```

```
error[E0597]: `line` does not live long enough
  --> l8_bad.rs:26:23
   |
25 |         let line = String::from("host=local");
   |             ---- binding `line` declared here
26 |         kv = split_kv(&line);
   |                       ^^^^^ borrowed value does not live long enough
27 |     }
   |     - `line` dropped here while still borrowed
28 |     println!("ключ {:?}, значение {:?}", kv.key, kv.value);
   |                                          ------ borrow later used here
```

Те же четыре точки, что в Г19.Ч3.З2, — с одной существенной разницей: заимствование теперь **едет внутри структуры**. Никакой ссылки в коде `main` не видно, `kv` выглядит обычным значением, — но `'a` протащил контракт сквозь `KeyValue`, и borrow checker считает поля тем, чем они являются: ссылками на `line`. Это ровно то, что обещает аннотация в объявлении: экземпляр не может пережить строку, на которую смотрит.

*Почему аннотация в возвращаемом типе не понадобилась.* По **правилу 2**: у `split_kv` ровно один параметр-ссылка (`line: &str`), значит, входное время жизни одно, и оно присваивается всем выходным — в том числе спрятанному внутри `KeyValue`. Развёрнутая форма:

```
fn split_kv<'a>(line: &'a str) -> KeyValue<'a>
```

Тот же случай, что `first_word` в §19.3.2, только выходом служит не голая ссылка, а структура со ссылками внутри: правилам умолчаний всё равно, «завёрнуто» ли выходное время жизни в тип.

*Находка эталона: компилятор просит `'_` явно.* Наивная запись без всяких скобок — ⛔ (точнее, с предупреждением) файл `l8_bare.rs`:

```rust
fn split_kv(line: &str) -> KeyValue {
```

собирается и работает, но rustc 1.97 сопровождает её замечанием:

```
warning: hiding a lifetime that's elided elsewhere is confusing
 --> l8_bare.rs:6:19
  |
6 | fn split_kv(line: &str) -> KeyValue {
  |                   ^^^^     ^^^^^^^^ the same lifetime is hidden here
  |                   |
  |                   the lifetime is elided here
  |
  = help: the same lifetime is referred to in inconsistent ways, making the signature confusing
  = note: `#[warn(mismatched_lifetime_syntaxes)]` on by default
help: use `'_` for type paths
  |
6 | fn split_kv(line: &str) -> KeyValue<'_> {
  |                                    ++++
```

Смысл претензии — не в правилах вывода (они отработали и без скобок), а в **читаемости**: во входе время жизни хотя бы обозначено амперсандом, а в `KeyValue` спрятано целиком, и по сигнатуре не видно, что тип вообще заимствует. Предложенная запись `KeyValue<'_>` — «здесь есть время жизни, и его подставят правила» — возвращает эту информацию читателю, не заставляя придумывать имя. Значок `'_` вы уже писали, не задумываясь, в каждой реализации `Display`: `fmt::Formatter<'_>` (§19.2.3) — там он ровно об этом же.

В основном решении принята рекомендованная форма `KeyValue<'_>`; в этой записи предупреждений нет.

**Ответ:** код — листинг `l8.rs`, вывод `ключ "host", значение "local"` / `ключ "port", значение "8080"` (и `ключ "без-разделителя", значение ""` на строке без `=`). Аннотация обязательна только в объявлении структуры (`KeyValue<'a>`; одного параметра на оба поля достаточно — ключ и значение суть куски одной строки); в теле срезы наследуют время жизни `line` сами. E0597 воспроизведён (`l8_bad.rs`): те же четыре точки, что в Г19.Ч3.З2, но заимствование едет **внутри структуры** — `'a` протаскивает контракт сквозь `KeyValue`. Аннотация в возвращаемом типе не понадобилась по **правилу 2**: входное время жизни ровно одно и присваивается всем выходным, включая спрятанное в типе; развёрнутая форма — `fn split_kv<'a>(line: &'a str) -> KeyValue<'a>`. Замечание эталона: голая запись `-> KeyValue` собирается, но rustc 1.97 выдаёт предупреждение `mismatched_lifetime_syntaxes` («hiding a lifetime that's elided elsewhere is confusing») и предлагает `KeyValue<'_>` — ту же форму, что в знакомом `fmt::Formatter<'_>`; она и принята в решении.

**Вариант 2 (отсутствие разделителя — это `Option`, а не пустое значение).** Основное решение на строке без `=` возвращает «весь ввод как ключ, пустое значение» — решение спорное: пустое значение неотличимо от честного `"host="`. Честнее сказать «пары здесь нет». Файл `l8v2.rs`:

```rust
fn split_kv(line: &str) -> Option<KeyValue<'_>> {
    let bytes = line.as_bytes();
    for i in 0..bytes.len() {
        if bytes[i] == b'=' {
            return Some(KeyValue {
                key: &line[..i],
                value: &line[i + 1..],
            });
        }
    }
    None
}
```

```
"host=local": ключ "host", значение "local"
"port=8080": ключ "port", значение "8080"
"без-разделителя": разделителя '=' нет — не пара
"=пусто": ключ "", значение "пусто"
```

*Сравнение.* Разница — в том, кто и когда узнаёт о неудаче разбора. Основное решение **всегда** возвращает `KeyValue`, поэтому вызывающий обязан догадаться проверить `value` на пустоту — а такая проверка и неверна (строка `"host="` даёт пустое значение законно), и легко забывается: компилятор о ней не напомнит. Вариант 2 переносит различие в **тип**: `Option<KeyValue<'_>>` невозможно использовать, не разобрав (§16.2.2), поэтому «а что если разделителя нет» перестаёт быть вопросом дисциплины. Плата — обязательный `match` (или `if let`) на каждом вызове, даже там, где ввод заведомо корректен. Заметьте, что времена жизни в обеих версиях устроены одинаково: `Option<KeyValue<'_>>` — обычный обобщённый тип, и правило 2 подставляет время жизни внутрь него так же, как в голый `KeyValue<'_>`; последняя строка прогона (`"=пусто"`) показывает, что пустой **ключ** обе версии считают законным — вот его-то и стоило бы отсекать отдельно, если задача того требует. Когда что: `Option` — почти всегда, и особенно если разбираемые строки приходят извне (файл, ввод пользователя, сеть); «всё в ключ» — только для черновика или когда «строка без разделителя» действительно имеет осмысленную интерпретацию, и её стоит записать в комментарии.

### Г19.Ч3.З9

**Условие.** *(прикладное)* Синтез трёх частей: обобщённая функция `fn best<'a, T: PartialOrd + Display>(items: &'a [T], label: &str) -> &'a T` — печатает `label` и возвращает ссылку на максимум (тело — из `largest`). Объясните каждый элемент сигнатуры (два обобщённых параметра, два ограничения, связь времён жизни: почему результат привязан к `items`, а не к `label`). Прогоните на `Vec<i32>` и `Vec<String>`; попробуйте вызвать с `Vec<Point>` без нужных derive и почините по подсказкам.

**Решение.** Файл `l9.rs`:

```rust
use std::fmt::Display;

fn best<'a, T: PartialOrd + Display>(items: &'a [T], label: &str) -> &'a T {
    println!("ищем максимум: {label}");
    let mut best = &items[0];
    for item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    let temps = vec![19, 24, 21, 30];
    println!("итог: {}", best(&temps, "температуры"));

    let names = vec![
        String::from("Alice"),
        String::from("Bob"),
        String::from("Carol"),
    ];
    println!("итог: {}", best(&names, "имена"));
}
```

```
ищем максимум: температуры
итог: 30
ищем максимум: имена
итог: Carol
```

*Разбор сигнатуры по элементам.* Читаем слева направо, как учит §19.3.2.

**`<'a, T: …>` — два обобщённых параметра в одном списке.** `'a` — время жизни, `T` — тип. Они стоят рядом не по недосмотру: времена жизни и типы — обобщённые параметры **одной природы** (R1, гл. 10.3), просто отвечают на разные вопросы. `T` спрашивает «над чем работаем», `'a` — «как долго действительны ссылки». Порядок в списке принят такой: сначала времена жизни, потом типы.

**`T: PartialOrd` — первое ограничение.** Разрешает сравнение `item > best` в теле. Без него — E0369 в самом определении, как в Г19.Ч1.З2.

**`T: Display` — второе ограничение.** Здесь оно **не следует из тела**: `best` печатает только `label` (уже готовый `&str`), а сам `T` внутри лишь сравнивается. Проверено прямым опытом — файл `l9_nodisplay.rs`, та же программа с ограничением `<'a, T: PartialOrd>`, собирается и печатает **тот же вывод**: и `i32`, и `String` умеют `Display` независимо от наших требований, поэтому `println!` в `main` доволен и без них.

Зачем же оно тогда нужно? Это **декларация контракта**, а не техническая необходимость: сигнатура объявляет, что `best` работает с типами, пригодными к показу человеку, — функция для отчётов и не должна принимать то, что нельзя напечатать. Разница видна на типе без `Display` (наш `Point` ниже): с ограничением компилятор указывает на **вызов** `best` с нотой `required by a bound in `best`` — то есть на нарушение контракта функции; без него та же программа отказала бы только внутри `println!`, и разбираться пришлось бы уже в `main`. То есть ограничение переносит диагностику с места печати на место вызова. Формально это отступление от правила минимальности §19.1.3 — и осознанное: минимальность требует не просить лишнего у **тела**, но контракт API вправе быть строже тела, если строгость документирует назначение функции.

**`items: &'a [T]` — вход, помеченный `'a`.** Срез, время жизни которого мы назвали, чтобы связать с результатом.

**`label: &str` — вход без метки.** По правилу 1 он получает **своё**, отдельное время жизни, которое нам просто незачем называть.

**`-> &'a T` — результат, связанный с `items`.** Контракт: «возвращённая ссылка действительна ровно столько, сколько срез, который вы мне дали».

*Почему результат привязан к `items`, а не к `label`.* Потому что аннотация описывает **факт о теле**, а факт таков: возвращается `best`, инициализированный как `&items[0]` и переставляемый на другие элементы того же среза. Ни при каком исполнении наружу не выйдет ничего, связанного с `label`, — он только печатается и на этом заканчивает участие.

Что было бы, соври мы в сигнатуре, показала Г19.Ч3.З7: сигнатура обещает одно, тело делает другое — и компилятор ловит это внутри функции, без единого вызова. А что было бы, если бы правила умолчаний расставили метки сами? Ничего хорошего: правило 1 дало бы двум параметрам разные времена жизни, правила 2 и 3 не применились бы (входов два, `self` нет), и мы получили бы E0106 — тот же случай, что `longest` и `pick` (Г19.Ч3.З4, пункт «б»). Именно поэтому здесь и требуется ручная аннотация: из двух кандидатов компилятор выбрать не может, а мы — можем.

Практическое следствие связи видно, если дать `label` умереть раньше результата, — это делает вариант 2 ниже.

*Чиним по подсказкам.* ⛔ Шаг первый — послушались буквально, `#[derive(PartialOrd)]` (файл `l9_step_bad.rs`):

Знакомая цепочка супертрейта — третья встреча за главу (Г19.Ч1.З8, Г19.Ч2.З11): `PartialOrd` требует `PartialEq`.

Шаг второй — добавляем `PartialEq`, и остаётся `Display`, у которого **derive не существует** (§19.2.3, Г19.Ч2.З7): его пишем руками. Файл `l9_fix.rs`:

```rust
#[derive(PartialEq, PartialOrd)]
struct Point {
    x: i32,
    y: i32,
}

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}
```

```
ищем максимум: точки
итог: (3, 7)
```

Три точки на входе — `(1, 9)`, `(3, 4)`, `(3, 7)` — и победила последняя. Проверьте себя: почему не `(1, 9)` с наибольшим `y`? Потому что `derive(PartialOrd)` сравнивает поля **в порядке объявления**, лексикографически (§19.2.3): сначала `x` (3 больше 1 — отпадает первая точка), при равных `x` — `y` (7 больше 4). Порядок полей в объявлении структуры оказывается семантикой сравнения — стоит помнить, когда дерайвите `PartialOrd` на чём-то, кроме одного поля.

Заметим, чем чинится каждое из двух ограничений: `PartialOrd` — двумя derive (плюс базовый `PartialEq` по супертрейту), `Display` — ручной реализацией, потому что «как показать точку человеку» компилятор угадать не вправе. Вся глава уместилась в одну починку.

**Ответ:** код — листинг `l9.rs`; вывод `ищем максимум: температуры` / `итог: 30` и `ищем максимум: имена` / `итог: Carol`. Элементы сигнатуры: `<'a, T: …>` — два обобщённых параметра одной природы в одном списке (время жизни и тип); `T: PartialOrd` разрешает сравнение в теле (без него — E0369 в определении); `T: Display` — декларация контракта «результатом можно отчитываться»: телом оно не требуется (программа с ограничением `T: PartialOrd` собирается и даёт тот же вывод — `l9_nodisplay.rs`), но переносит диагностику с места печати на место вызова (`required by a bound in `best``); `items: &'a [T]` — вход с названным временем жизни; `label: &str` — вход, чьё время жизни по правилу 1 отдельное и нам неинтересно; `-> &'a T` — результат, связанный со срезом. Результат привязан к `items`, а не к `label`, потому что аннотация описывает факт о теле: наружу выходит `&items[0]` или другой элемент того же среза, а `label` только печатается. Без ручной аннотации была бы E0106: правило 1 даёт двум входам разные времена жизни, правила 2 и 3 неприменимы. `Vec<Point>` без derive даёт три ошибки (E0277 про `PartialOrd`, E0277 про `Display` от функции и от `println!`); починка: `#[derive(PartialOrd)]` → E0277 про `PartialEq` (супертрейт) → `#[derive(PartialEq, PartialOrd)]` + **ручной** `impl Display` (derive у него не существует). Итог `(3, 7)`: derive-сравнение лексикографично по порядку объявления полей.

**Вариант 2 (два времени жизни явно и `where`).** Связь «результат — от `items`, а не от `label`» можно не подразумевать, а выписать: дать второму входу собственное имя. Файл `l9v2.rs`:

```rust
fn best<'a, 'b, T>(items: &'a [T], label: &'b str) -> &'a T
where
    T: PartialOrd + Display,
{
    println!("ищем максимум: {label}");
    let mut best = &items[0];
    for item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    let temps = vec![19, 24, 21, 30];
    let winner;
    {
        let label = String::from("температуры (метка умрёт раньше результата)");
        winner = best(&temps, &label);
    }
    println!("итог: {winner}");
}
```

```
ищем максимум: температуры (метка умрёт раньше результата)
итог: 30
```

Программа собирается — и это главный результат опыта: метка умерла на закрывающей скобке, а результат прекрасно использован после. Сравните с Г19.Ч3.З2, где ровно такая конструкция давала E0597: там оба входа были связаны одним `'a`, и меньшее из времён жизни губило результат. Здесь `'b` ни к чему не привязано, поэтому смерть `label` никого не касается.

*Сравнение.* Обе сигнатуры описывают **одну и ту же** функцию: `'b` в варианте 2 — ровно то безымянное время жизни, которое правило 1 и так выдаёт `label` в основном решении. Разница чисто выразительная, и у каждой формы своя сильная сторона. Основная запись короче и не заставляет читателя следить за именем, которое употреблено единожды: неназванное время жизни само сообщает «этот вход к результату отношения не имеет». Вариант 2 делает то же самое утверждение **явным** — по сигнатуре видно, что параметров жизни два и результат связан только с первым; это ценно в учебном тексте и в чужом коде, где хочется прочитать контракт, не заглядывая в тело. Заодно вариант показывает `where`-форму (§19.1.3): при двух-трёх ограничениях она разгружает строку с параметрами, и сигнатура читается как «что принимаем — что возвращаем», а требования уезжают ниже. Правило выбора обычное: имя времени жизни заводят, когда оно **употребляется больше одного раза** (то есть что-то с чем-то связывает); `'b`, встречающееся в сигнатуре единожды, — такой же шум, как `fn f<'a>(s: &'a str) -> usize` из «подводных камней» §19.3.1. В боевом коде осталась бы основная форма; вариант 2 хорош как доказательство — он делает проверяемым утверждение, которое иначе пришлось бы принимать на слово.
