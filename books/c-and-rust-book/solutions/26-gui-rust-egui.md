# Решения. Глава 26. GUI на Rust: egui

> Сборник решений самоучителя «C, затем Rust». Условия заданий продублированы из `chapters/26-gui-rust-egui.md`. Глава обзорная и проектная: половина заданий — «сделайте и объясните», и ценность здесь в том, чтобы сначала собрать и прогнать своё, а потом сверяться. Все времена и размеры окон у вас будут свои — сходиться должны выводы.
>
> **Эталон верификации.** **rustc/cargo 1.97.0 (stable), host-триплет `x86_64-pc-windows-gnu`, издание 2024**; **eframe/egui 0.35.0**; замеры поиска — `--release`, поведение интерфейса — dev-сборка. Машина: 12 ядер / 24 логических процессора, масштаб экрана 100 % (клиентская область окна в пикселях совпала с логическими точками из `with_inner_size`). C-сторона для сравнения подсистем — **GCC 15.2.0 (MinGW-w64)**, `objdump` оттуда же.
>
> **Стенд — набор проектов, а не файлов** (приём глав 20 и 25): каждое состояние клиента живёт в своём каталоге, иначе листинг перестаёт быть куском реального файла. `minigrep` — библиотека главы 25 (99 строк, три теста), реконструирована по листингам §25.1.2–25.1.4 и **не менялась ни разу за главу**; `pargrep` — пакет с `ThreadPool` из §25.2.3 (нужен заданию Ч2.З9); `hello_egui`, `hello2` — Ч1.З1; `counter_egui`, `greet_egui` — примеры §26.1.3; `z1_2`…`z1_8` — задания части 26.1; `p2_sync` (пакет `gui_minigrep_v1`) — версия чекпоинта 1 и оба ⛔-бинарника; `p2_final` (пакет `gui_minigrep`) — финальная версия; `z2_3`, `z2_6a`…`z2_6d`, `z2_6ok`, `z2_7`, `z2_8`, `z2_9` — задания части 26.2; `z2_syncauto`/`z2_bgauto` — приборные копии обеих версий для замера закрытия; `v1_1`…`v2_9` — вторые варианты решений (`v1_7p`, `v1_8p` — их приборные копии); `bench` — консольный замер поиска; `data/big1.txt` (33 476 090 байт, 400 тыс. строк) и `data/big2.txt` (202 812 090 байт, 2,4 млн строк) — данные генератора `gen.rs` из §25.2.4.
>
> **Общий каталог сборки.** Все проекты собраны с `CARGO_TARGET_DIR` на один каталог (приём из Ч1.З1) — иначе каждый из двух десятков пакетов тянул бы свои 418 зависимостей. Один побочный эффект стоит знать заранее: **два пакета с одинаковым именем в общем каталоге затирают друг друга** — cargo кладёт готовый бинарник в `target/debug/<имя пакета>.exe`, и версия чекпоинта 1 (`gui_minigrep_v1`) поэтому названа иначе, чем финальная (`gui_minigrep`). Пока имена совпадали, под именем «финальной» запускался черновик — и замеры отзывчивости получались одинаковыми у обеих версий.
>
> **Как проверялся интерфейс.** Правило §2.3 для GUI-глав: сборку и поведение проверяет прогоном агент, ручная приёмка — за владельцем. Прогон ведёт служебный водитель на PowerShell + P/Invoke (приём главы 12): окно ищется перебором окон процесса, щелчки и ввод — `SendInput`, снимок клиентской области — `PrintWindow` с флагами `PW_CLIENTONLY | PW_RENDERFULLCONTENT`, закрытие — `WM_CLOSE` с замером времени. Там, где важно «когда именно нарисовался кадр», вместо снимков применена **приборная копия приложения**: те же строки плюс протокол кадров в `probe.txt`. Это честнее снимка (снимок отдаёт последний *показанный* кадр) и не требует трогать окно.
>
> **⛔** — программы, которые не компилируются; их «результат» — протокол опыта, а не образец кода. **⚠** — программы, которые собираются, но ведут себя не так, как хотелось.
>
> **Сокращения.** Строку `For more information about this error, try 'rustc --explain EXXXX'` опускаем, если код ошибки уже назван; строки `Compiling`/`Finished` от cargo — кроме случаев, где они и есть предмет разговора; абсолютные пути стенда сокращены до `...`. На вашей машине будут другими все времена, номера кадров и адреса.
>
> **Открытый пункт главы.** Ручная приёмка интерфейса (прокрутка 2400 строк, поведение на своих файлах, внешний вид) остаётся за владельцем — агент проверяет сборку, сценарии и замеры.

## Часть 26.1. Immediate mode и eframe

### Г26.Ч1.З1

**Условие.** Подключите eframe и соберите `hello_egui` из §26.1.2. Замерьте время первой и повторной сборки (правьте строку в `label` между запусками). Если работаете на gnu-тулчейне и поймали `-lshlwapi` — почините через `.cargo/config.toml` и объясните своими словами, что именно чинит флаг `-L`. Затем заведите второй проект и сравните время его первой сборки без общего каталога сборки и с `CARGO_TARGET_DIR`.

**Решение.** Задание про инструмент, а не про язык: три замера и одно объяснение.

**Подключение.** `cargo new hello_egui` и `cargo add eframe` — cargo сам вписывает версию и запирает граф зависимостей:

```text
$ cargo add eframe
    Updating crates.io index
     Locking 417 packages to latest Rust 1.97.0 compatible versions
```

Строка сообщает о **417** новых пакетах в замке; в самом `Cargo.lock` записей 418 — 417 зависимостей плюс сам `hello_egui` (`grep -c '^name = ' Cargo.lock` → 418). В главе названо число 418: это тот же граф, посчитанный по файлу замка. Число зависит от дня — индекс crates.io живёт своей жизнью, и требование `eframe = "0.35.0"` фиксирует только eframe, а не всё дерево.

**Первая сборка — и `-lshlwapi`.** На gnu-тулчейне первая сборка падает на компоновке. Ошибку стоит увидеть своими глазами, поэтому сначала соберём **без** `.cargo/config.toml`:

```text
$ cargo build
   Compiling hello_egui v0.1.0 (...\hello_egui)
error: linking with `x86_64-w64-mingw32-gcc` failed: exit code: 1
  |
  = note: "x86_64-w64-mingw32-gcc" ... "-lshlwapi" "-lkernel32" "-luser32" ...
  = note: some arguments are omitted. use `--verbose` to show all linker arguments
  = note: ld: cannot find -lshlwapi: No such file or directory

error: could not compile `hello_egui` (bin "hello_egui") due to 1 previous error
```

Прогон занял **1 м 49 с** и кончился кодом 101: все 417 зависимостей скомпилировались (они собираются в `.rlib` и не компонуются), и только последний шаг — сборка исполняемого файла — обнаружил недостачу.

**Что чинит `-L`.** В командной строке компоновщика видно три `-L` (каталоги поиска библиотек), и один из них — `...\lib\rustlib\x86_64-pc-windows-gnu\lib\self-contained`: собственный, урезанный комплект MinGW, который несёт с собой rustup. Пересчитаем его:

```text
$ ls "$(rustc --print sysroot)/lib/rustlib/x86_64-pc-windows-gnu/lib/self-contained" | wc -l
44
$ ls .../self-contained/*.a | wc -l
42
$ ls .../self-contained | grep -c -i shlwapi
0
$ ls /c/Users/Max/scoop/apps/gcc/current/x86_64-w64-mingw32/lib/libshlwapi.a
/c/Users/Max/scoop/apps/gcc/current/x86_64-w64-mingw32/lib/libshlwapi.a
```

Сорок четыре файла: сорок две библиотеки импорта (`.a`) плюс два объектных файла старта (`crt2.o`, `dllcrt2.o`). `libshlwapi.a` среди них нет, а в полном MinGW тома I — есть.

Отсюда и роль флага: **`-L` не добавляет ни одной библиотеки — он добавляет каталог, в котором компоновщик их ищет.** Компоновщику уже приказано «слинкуй `shlwapi`» (`-lshlwapi` пришёл от пакета работы с буфером обмена); он идёт по списку каталогов `-L` в порядке перечисления, в каждом ищет `libshlwapi.a` — и, не найдя, останавливается. Мы дописываем в этот список каталог полного MinGW из главы 1, и та же самая команда завершается успехом. Ровно та механика, что в §11.2.3 отвечала за порядок `-l` и `-L` у make: компоновщик ничего не угадывает, он берёт первое найденное по своим правилам.

Лечение — конфигурация cargo (R10), файл `.cargo/config.toml` рядом с проектами:

```toml
[target.x86_64-pc-windows-gnu]
rustflags = ["-L", "C:\\Users\\Max\\scoop\\apps\\gcc\\current\\x86_64-w64-mingw32\\lib"]
```

**Три замера.** С конфигурацией:

```text
$ cargo build          # первая успешная сборка
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1m 44s
$ cargo build          # ничего не менялось
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.46s
$ cargo build          # после правки строки в label
   Compiling hello_egui v0.1.0 (...\hello_egui)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4.41s
```

Заметьте, что первая сборка **с** конфигурацией снова заняла почти две минуты: `rustflags` входят в отпечаток каждой единицы компиляции, и смена флагов обесценивает весь кеш — не только вашего пакета, но и всех 417 зависимостей.

**Второй проект.** Копируем `hello_egui` в `hello2` (в `Cargo.toml` и `Cargo.lock` меняем имя пакета) и собираем сначала как обычно, а потом — в общий каталог:

```text
$ cargo build                                  # свой target у нового пакета
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1m 43s

$ export CARGO_TARGET_DIR=.../ch26/target-shared   # прогрев: собрали туда hello_egui (1 м 40 с)
$ cargo build                                  # тот же hello2 в общий каталог
   Compiling hello2 v0.1.0 (...\hello2)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4.48s
```

**Ответ.** Первая сборка — **1 м 44 с** (417 зависимостей), повторная без правок — **0,46 с** (cargo только сверяет отпечатки), после правки строки в `label` — **4,41 с** (пересобирается и компонуется один ваш crate). Второй проект со своим каталогом сборки — **1 м 43 с**, он же с общим `CARGO_TARGET_DIR` (уже прогретым) — **4,48 с**, то есть в двадцать три раза быстрее: артефакты зависимостей общие, заново компилируется только новый crate. Флаг `-L` не даёт компоновщику библиотеку — он даёт **каталог для поиска**: `-lshlwapi` требует файл `libshlwapi.a`, в урезанном комплекте rustup (44 файла, 42 библиотеки) его нет, в полном MinGW тома I есть, и `rustflags = ["-L", ...]` просто указывает, где смотреть.

**Вариант 2 (общий каталог сборки — не переменной окружения, а конфигурацией).** `CARGO_TARGET_DIR` живёт в окружении и забывается вместе с закрытым терминалом. Тот же эффект даёт ключ в уже заведённом `.cargo/config.toml` (R10):

```toml
[build]
target-dir = "C:\\...\\ch26\\target-shared"

[target.x86_64-pc-windows-gnu]
rustflags = ["-L", "C:\\Users\\Max\\scoop\\apps\\gcc\\current\\x86_64-w64-mingw32\\lib"]
```

Прогон подтверждает: локальный каталог `target/` у проекта не появился вовсе, готовый бинарник лёг в общий каталог. Но у этого опыта есть побочный результат, ради которого его стоило поставить:

```text
$ cargo build
   Compiling v1_1 v0.1.0 (...\v1_1)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 4m 13s
```

Четыре минуты вместо ожидаемых четырёх секунд — при том, что все 418 зависимостей в общем каталоге уже собраны. Причина видна в подробном выводе:

```text
$ cargo build -v ...
      2 -L 'C:\Users\Max\scoop\apps\gcc\current\x86_64-w64-mingw32\lib
```

Флаг `-L` попал в командную строку rustc **дважды**: cargo не заменяет настройки более общего файла, а **сливает** их с настройками ближнего (R10), и массив `rustflags` из корневого `.cargo/config.toml` сложился с массивом из проектного. Компоновщику лишний одинаковый каталог поиска безразличен, а вот отпечатку единицы компиляции — нет: набор флагов другой, значит, кеш общего каталога для этого проекта недействителен, и все зависимости пересобрались заново под новым хешем.

*Сравнение.* Переменная окружения удобна для разового опыта и легко отключается (`unset`), но её надо не забыть выставить в каждом новом терминале — и один забытый экспорт стоит двух минут. Ключ `build.target-dir` действует на все проекты внутри каталога с конфигурацией (cargo ищет `config.toml` вверх по дереву — R10) и переживает перезапуск терминала; зато он «невидим»: чужой человек, увидевший пустой `target/` в проекте, будет искать причину. И главный практический вывод опыта: **`rustflags` держите ровно в одном файле конфигурации** — дублирование не ломает сборку, но обесценивает общий кеш, то есть ровно то, ради чего общий каталог и заводился. Для стенда главы, где два десятка пакетов, правильнее один корневой `config.toml` с обоими ключами; для одного эксперимента — переменная окружения.

### Г26.Ч1.З2

**Условие.** Соберите счётчик из §26.1.3 и повторите контрольный прогон главы 12: три щелчка «+1» → «Значение: 3», «Сброс» → «Значение: 0». Добавьте кнопку «−1», которая не даёт значению уйти ниже нуля. Сколько строк добавилось? Найдите в своём коде места, где в Win32-версии понадобились бы новый `#define` и новая ветка `switch`.

**Решение.** Контрольный прогон повторяем на неизменённом `counter_egui` из §26.1.3 (водитель: три щелчка по «+1», снимок; щелчок по «Сброс», снимок): надпись прошла путь «Значение: 3» → «Значение: 0», закрытие — код 0. Тот же сценарий, что для `counter1.c` в §12.2.1, и тот же результат — это и была цель зеркала.

Теперь кнопка «−1». Всё изменение — три строки в `z1_2/src/main.rs` (полный текст файла — `counter_egui` плюс этот блок):

```rust
                if ui.button("−1").clicked() && self.count > 0 {
                    self.count -= 1;
                }
```

Прогон (щелчки водителем, снимки после каждой стадии): три «+1» → «Значение: 3»; одно «−1» → «Значение: 2»; ещё пять «−1» подряд → «Значение: 0» — счётчик встал на нуле и ниже не пошёл.

Почему условие стоит **после** `.clicked()`, а не вместо него: `clicked()` надо спрашивать в любом кадре, где кнопка нарисована, а `&&` вычисляется слева направо (§3.1.1 тома I, §14.2.2 — здесь та же ленивость) — щелчок опрашивается всегда, а уменьшение случается, только когда есть что уменьшать. Поменяйте местами (`self.count > 0 && ui.button("−1").clicked()`) — и при нулевом счётчике кнопка **перестанет рисоваться вообще**: правый операнд не вычисляется, а вычисление и есть отрисовка. Это первый случай в курсе, когда ленивость `&&` управляет не логикой, а картинкой на экране.

**Ответ.** Добавилось **три строки** (`if`, тело, закрывающая скобка) — 35 строк стали 38. Проверка «не ниже нуля» умещается в условие `&& self.count > 0`. В Win32-версии тем же трём строкам соответствовали бы: (1) новый `#define ID_BTN_MINUS 3` рядом с `ID_BTN_PLUS`/`ID_BTN_RESET`; (2) новый вызов `CreateWindowEx` с `WS_CHILD | WS_VISIBLE` и координатами в обработчике `WM_CREATE` — кнопку надо *создать* и не забыть про её место; (3) новая ветка `case ID_BTN_MINUS:` в `switch (LOWORD(wParam))` внутри `WM_COMMAND`; (4) после изменения счётчика — ручной вызов `show_count()`, потому что надпись сама себя не обновит. Четыре места вместо одного, и три из них — про диспетчеризацию, а не про смысл задачи. В egui нет ни ID, ни таблицы разбора, ни ручной синхронизации: кнопка, её ответ и действие лежат в одной строке, а надпись перерисовывается из состояния каждый кадр.

**Вариант 2 (кнопка выключается вместо молчаливого отказа).** Наш `&&` устроен так, что на нуле кнопка нажимается, но ничего не делает — пользователю не объяснили. Честнее показать состояние самой кнопкой (приём разбирается в Ч2.З8(б), сигнатура — R11):

```rust
                if ui
                    .add_enabled(self.count > 0, egui::Button::new("−1"))
                    .clicked()
                {
                    self.count -= 1;
                }
```

(Проект `v1_2`: собран без предупреждений, прогнан запуском — окно открывается и закрывается с кодом 0; как выглядит выключенная кнопка, видно на снимке основного решения Ч2.З8, где серыми становятся «Искать» и «Сохранить».)

*Сравнение.* Первый вариант — три строки и никаких новых понятий; поведение «щёлкнул — ничего» пользователь трактует как неисправность. `add_enabled` рисует кнопку серой и не пропускает щелчок: правило «ниже нуля нельзя» видно **до** попытки, а не после. Цена — виджет строится явным `egui::Button::new` вместо короткого `ui.button`, и условие переезжает из логики в описание интерфейса. Для счётчика разница косметическая, для кнопки «Удалить» — принципиальная.

### Г26.Ч1.З3

**Условие.** Доработайте `greet_egui`: кнопка «Очистить» опустошает журнал; пустое или состоящее из пробелов имя не приветствуется (подойдёт метод `str::trim`, обрезающий пробельные края, — R9, в курсе он ещё не встречался; `is_empty` — из гл. 18); в статусной панели вместе с числом приветствий покажите длину текущего ввода — и посмотрите, как она меняется прямо при наборе. Почему для этого не понадобилось никакого «события изменения»?

**Решение.** Три доработки — три места в состоянии и кадре. Состояние прирастает одним полем: почему не поздоровались, надо где-то хранить (`z1_3/src/main.rs`):

```rust
#[derive(Default)]
struct GreetApp {
    name: String,
    log: Vec<String>,
    hint: String, // почему не поздоровались
}
```

Верхняя панель: ряд с полем и ряд с кнопками (в один ряд «Поздороваться» и «Очистить» с полем ввода уже не помещаются — центральной панели тоже нужно место):

```rust
            ui.horizontal(|ui| {
                if ui.button("Поздороваться").clicked() {
                    let name = self.name.trim();
                    if name.is_empty() {
                        self.hint = String::from("пустое имя — не приветствуем");
                    } else {
                        self.log.push(format!("Привет, {name}!"));
                        self.hint.clear();
                        self.name.clear();
                    }
                }
                if ui.button("Очистить").clicked() {
                    self.log.clear();
                    self.hint.clear();
                }
            });
```

`trim` (R9) обрезает пробельные края и возвращает **ломтик** исходной строки (§15.3.1) — копии нет; `is_empty` знаком по §18.2.2. Приветствуем именно обрезанное имя: «  Аня  » превращается в «Привет, Аня!». Заметьте порядок: `self.log.push(format!(..., name))` стоит **до** `self.name.clear()` — `name` заимствует `self.name`, и очистить строку раньше, чем ломтик использован, borrow checker не даст (§15.2.2).

Статусная панель считает и приветствия, и длину ввода:

```rust
        egui::Panel::bottom("статус").show(ui, |ui| {
            ui.label(format!(
                "приветствий: {} · символов в поле: {}",
                self.log.len(),
                self.name.chars().count()
            ));
            if !self.hint.is_empty() {
                ui.label(&self.hint);
            }
        });
```

`chars().count()`, а не `len()`: `len()` у `String` — это **байты** (§17.1.3), и «Мир» дал бы 6 вместо 3. Прогон это и показывает.

Прогон (водитель: щелчок в поле, ввод «Мир», снимки после каждого шага):

- набрали «Мир» — в статусе «приветствий: 0 · символов в поле: 3», журнал пуст;
- «Поздороваться» — в журнале «Привет, Мир!», поле очищено, «приветствий: 1 · символов в поле: 0»;
- «Поздороваться» с пустым полем — журнал не вырос, под статусом появилось «пустое имя — не приветствуем»;

**Ответ.** Кнопка «Очистить» — это `self.log.clear()`; защита от пустого имени — `let name = self.name.trim(); if name.is_empty() { ... }`; длина ввода — `self.name.chars().count()` в статусной панели (в символах, не в байтах). Никакого «события изменения» не понадобилось **потому, что событий здесь вообще нет**: статусная панель не «узнаёт об изменении», она каждый кадр заново печатает длину текущей строки. Пользователь набрал символ — `text_edit_singleline` дописал его в *нашу* `self.name` (виджет получил `&mut String`, §15.2.2) и попросил перерисовку, а следующий кадр нарисовал новое число. В retained-мире §12.2.4 для этого понадобилось бы уведомление `EN_CHANGE` от EDIT-контрола, разбор `WM_COMMAND` и ручной `SetWindowText` на метке — три места, которые можно рассинхронизировать; здесь рассинхронизации нет по построению (§26.1.1).

**Вариант 2 (валидация до щелчка).** Вместо объяснения после отказа — не давать нажать:

```rust
                let ready = !self.name.trim().is_empty();
                if ui
                    .add_enabled(ready, egui::Button::new("Поздороваться"))
                    .clicked()
                {
                    self.log.push(format!("Привет, {}!", self.name.trim()));
                    self.name.clear();
                }
```

(Проект `v1_3`: собран без предупреждений, прогнан запуском — код 0.)

*Сравнение.* Вариант с подсказкой отвечает на вопрос «почему не сработало», вариант с выключенной кнопкой не доводит до вопроса: пока поле пусто (или в нём одни пробелы), кнопка серая и оживает прямо во время набора — состояние проверяется каждый кадр, вручную обновлять ничего не нужно. Зато исчезает текст объяснения: пользователь видит, что нельзя, но не читает, почему. Практика — совмещать: выключенная кнопка плюс подсказка рядом; для учебного примера достаточно любого из двух.

### Г26.Ч1.З4

**Условие.** Объясните по модели кадра (§26.1.1), почему счётчик из разобранного примера 2 (локальная `let mut count`) всегда показывает ноль или единицу, но никогда — два. В каком порядке в одном кадре происходят: щелчок, инкремент, отрисовка надписи? Проверьте рассуждение экспериментом.

**Решение.** Сначала рассуждение по модели §26.1.1, потом опыт.

Кадр — это один вызов `ui`. Внутри него код «проговаривает» интерфейс сверху вниз, и порядок событий такой:

1. eframe собрал ввод, накопившийся с прошлого кадра (в том числе «кнопка отпущена»), и вызвал ваш `ui`;
2. выполняется `let mut count = 0;` — переменная рождается заново, в ней ноль;
3. `ui.button("+1")` раскладывает кнопку, проверяет ввод и возвращает `Response`; `clicked()` истинно только в том кадре, где щелчок случился;
4. если истинно — `count += 1`, в переменной единица;
5. `ui.label(format!("Значение: {count}"))` кладёт в кадр надпись с *текущим* значением — «1» в кадре щелчка, «0» во всех остальных;
6. кадр закончился, `count` уничтожена; следующий кадр начнётся с пункта 2.

Двойки не бывает, потому что для неё нужно, чтобы в **одном** кадре щелчок случился дважды: инкремент прибавляет к нулю, а не к прошлому значению — прошлого значения не существует.

Опыт (`z1_4/src/main.rs`). Чтобы увидеть кадр щелчка глазами, добавим в *состояние* приложения то, что переживает кадр: счётчик кадров и протокол:

```rust
impl eframe::App for LocalCountApp {
    fn ui(&mut self, ui: &mut egui::Ui, _frame: &mut eframe::Frame) {
        self.frames += 1;
        let mut count = 0; // каждый кадр — заново!

        egui::CentralPanel::default().show(ui, |ui| {
            if ui.button("+1").clicked() {
                count += 1;
                self.protocol
                    .push(format!("кадр {}: после щелчка count = {count}", self.frames));
            }
            ui.label(format!("Значение: {count}"));
```

Три щелчка водителем, снимок:

```text
Значение: 0
кадр 15: после щелчка count = 1
кадр 18: после щелчка count = 1
кадр 21: после щелчка count = 1
```

Крупная надпись показывает ноль, а протокол — три записи, и в каждой единица. Обратите внимание на номера: 15, 18, 21 — между щелчками прошло по три кадра (egui рисует не постоянно, а на ввод: движение мыши, нажатие, отпускание), и каждый из этих кадров начинался с обнуления `count`.

**Ответ.** В одном кадре порядок такой: **отпускание кнопки мыши попадает во ввод кадра → выполняется тело `ui` → `let mut count = 0` обнуляет переменную → `ui.button(...)` возвращает `Response`, у которого `clicked()` истинно → `count += 1` даёт единицу → `ui.label` рисует «Значение: 1» → кадр завершается, `count` умирает.** В следующем кадре всё повторяется с нуля, поэтому на экране почти всегда «0», в кадре щелчка — «1», а «2» не появится никогда: чтобы прибавить дважды, нужны два щелчка **в одном кадре**, а второй щелчок уже попадёт в следующий. Проверка опытом: протокол, живущий в `self`, фиксирует «count = 1» в кадрах 15, 18 и 21, а надпись на снимке — «Значение: 0». Вывод по R11 и §26.1.1: всё, что должно пережить кадр, обязано лежать в структуре приложения — библиотека ваших значений не хранит.

### Г26.Ч1.З5

**Условие.** Проведите построчную «перепись» счётчиков: для каждого элемента `counter1.c` из §12.2.1 (`ID_BTN_PLUS`, `WM_CREATE` с `CreateWindowEx`, `WM_COMMAND`+`BN_CLICKED`, `snprintf`+`SetWindowText`, `WM_DESTROY`) укажите, что ему соответствует в `counter_egui` — или почему соответствие не нужно. Какие два ⛔-примера §12.2.1 в egui невоспроизводимы в принципе?

**Решение.** Перепись по элементам `counter1.c` (§12.2.1) и `counter_egui` (§26.1.3).

| `counter1.c` (Win32) | `counter_egui` | почему так |
|---|---|---|
| `#define ID_BTN_PLUS 1`, `#define ID_BTN_RESET 2` | соответствия нет | ID нужен, чтобы **опознать отправителя** уведомления. В egui уведомления не приходят: `ui.button("+1")` возвращает `Response` прямо на месте вызова, и «кто щёлкнут» известно из того, какая строка кода спросила `clicked()` |
| `case WM_CREATE:` с тремя `CreateWindowEx` (`WS_CHILD | WS_VISIBLE`, координаты, `hwnd` родителя, `(HMENU)(INT_PTR)ID_...`) | `ui.button("+1")`, `ui.button("Сброс")`, `ui.label(...)` внутри `ui` | в retained-мире виджет **создаётся один раз** и живёт у системы; в immediate он не существует между кадрами — «создание» и есть отрисовка. Координаты не нужны: раскладчик `Ui` ставит виджеты сам, `ui.horizontal` разворачивает ленту вбок |
| `case WM_COMMAND:` + `if (HIWORD(wParam) == BN_CLICKED)` + `switch (LOWORD(wParam))` | `if ui.button("+1").clicked() { ... }` | вся диспетчеризация — распаковка кода уведомления, поиск ID в `switch` — схлопнулась в возвращаемое значение |
| `snprintf(buf, sizeof buf, "%d", g_count)` + `SetWindowText(g_label, buf)` в `show_count()`, вызываемой руками после каждого изменения | `ui.label(format!("Значение: {}", self.count))` | надпись не «обновляется» — она **рождается заново** из состояния каждый кадр; забыть вызвать `show_count()` невозможно, потому что вызывать нечего |
| `case WM_DESTROY: PostQuitMessage(0);` | соответствия нет | цикл сообщений и его завершение — внутри eframe. Забытый `PostQuitMessage` из ⛔-примера §12.1.3 (процесс-зомби) здесь недостижим: этот код написан за нас и один раз |
| глобали `g_count`, `g_label` (позже — карман `GWLP_USERDATA`, §12.2.2) | поле `self.count`, метод получает `&mut self` | состояние приносит сигнатура трейта; приведения типов из кармана окна, а с ними и UB главы 13, просто нет |

**Ответ.** Соответствия: `ID_BTN_*` → **не нужны** (ответ виджета приходит на месте вызова); `WM_CREATE` + `CreateWindowEx` → вызовы `ui.button`/`ui.label` в теле кадра (виджет не создаётся, а рисуется); `WM_COMMAND` + `BN_CLICKED` + `switch` → `if ui.button("+1").clicked()`; `snprintf` + `SetWindowText` → `ui.label(format!(...))`, причём ручная синхронизация исчезает вместе с функцией `show_count`; `WM_DESTROY`/`PostQuitMessage` → **не нужны**, цикл сообщений живёт внутри eframe.

Невоспроизводимы в принципе два ⛔ из примера 3 §12.2.1 («Три способа не увидеть уведомление»): **неуникальные идентификаторы** — потому что идентификаторов у виджетов egui нет вовсе, и двум кнопкам нечем совпасть; и **перепутанные `LOWORD`/`HIWORD`** — потому что нет ни упаковки уведомления в машинное слово, ни его распаковки: `clicked()` возвращает `bool`, а не биты, которые можно прочитать не с того конца. Третий способ того же примера — забытый `WS_VISIBLE` — аналога не имеет по другой причине: «невидимого» виджета в immediate mode не бывает, не нарисовать его можно только не вызвав метод, и тогда его нет и в раскладке.

### Г26.Ч1.З6

**Условие.** Поменяйте в `greet_egui` порядок: покажите `CentralPanel` первой, панели — после. Опишите, что стало с раскладкой, и объясните через правило «центральной достаётся остаток» (§26.1.3). Верните порядок и вместо этого дайте обеим краевым панелям один и тот же ID — что предупреждение egui сообщает при запуске?

**Решение.** Два опыта, оба — в отдельных проектах (`z1_6a`, `z1_6b`), чтобы прогоны не мешали друг другу.

**(а) Центральная панель первой.** Порядок в `z1_6a/src/main.rs`: сначала `CentralPanel`, затем `Panel::top("ввод")` и `Panel::bottom("статус")`. Программа собирается без единого предупреждения и запускается. На снимке клиентской области — **пустое серое окно**: ни поля ввода, ни кнопки, ни строки статуса.

Объяснение — правило §26.1.3 «центральной достаётся остаток»: краевые панели откусывают по ломтю от свободного места, а `CentralPanel` занимает **всё, что осталось**. Показанная первой, она видит окно нетронутым и забирает его целиком; краевым панелям, вызванным следом, свободного места остаётся ноль, и они рисуются полосами нулевой высоты. Виджеты внутри них честно раскладываются — просто в отведённые им ноль пикселей. Отсюда и предупреждение документации (R11): `CentralPanel` добавляется **после** всех остальных панелей — не из вкусовых соображений, а потому что «остаток» вычисляется в момент вызова.

**(б) Одинаковые ID у краевых панелей.** В `z1_6b/src/main.rs` порядок правильный, но обе панели названы одинаково: `Panel::top("панель")` и `Panel::bottom("панель")`. Программа тоже собирается молча — и при запуске egui рисует поверх интерфейса **красные надписи с огоньком** и обводит обе панели красными линиями:

```text
🔥 First use of Panel ID 0877
🔥 Second use of Panel ID 0877
```

Первая надпись стоит под верхней панелью, вторая — над нижней; сам интерфейс при этом работает. Библиотека не может знать, какая из двух панелей «правильная», поэтому не падает и не молчит, а показывает обе точки столкновения прямо на экране — отладчик встроен в кадр.

**Ответ.** (а) Раскладка исчезает: центральная панель, вызванная первой, забирает всё окно, и обеим краевым достаётся нулевая высота — на экране пустой прямоугольник, хотя код виджетов выполняется. Это прямое следствие правила «центральной достаётся остаток»: остаток считается в момент вызова, поэтому `CentralPanel` обязана идти последней. (б) При одинаковых ID egui показывает в окне красные предупреждения **«🔥 First use of Panel ID 0877»** и **«🔥 Second use of Panel ID 0877»** (число — хеш строкового идентификатора, у вас будет своё) и подчёркивает красным обе панели. Причина — те самые «крохи retained» из §26.1.1: по ID библиотека хранит между кадрами геометрию панели, и два разных объекта, назвавшихся одинаково, претендуют на одну ячейку памяти состояния. Рифма с ⛔-примером «неуникальные ID кнопок» из §12.2.1 полная, но с важной разницей: Win32 в этом случае **молчит** и просто путает отправителей, а egui — сообщает.

### Г26.Ч1.З7

**Условие.** Напишите конвертер температур: поле для градусов Цельсия, кнопка «→ °F», результат или ошибка — в надписи. Разбор ввода — `parse::<f64>()` с `match` по `Result` (§19.2.3, §18.1.2): мусор в поле должен давать человеческое сообщение, а не панику. Добавьте флажок «округлять до целых».

**Решение.** Состояние конвертера — три поля: текст ввода, флажок и **готовая надпись** результата (`z1_7/src/main.rs`):

```rust
#[derive(Default)]
struct TempApp {
    celsius: String, // ввод пользователя — текст, а не число
    round: bool,
    result: String, // готовая надпись: ответ или сообщение об ошибке
}
```

Хранить именно строку, а не `Option<f64>`, — сознательное решение: на экране всё равно текст, а два случая (ответ и ошибка) отличаются только его содержимым. Разбор — `parse::<f64>()` (§19.2.3) с `match` по `Result` (§18.1.2):

```rust
                if ui.button("→ °F").clicked() {
                    self.result = match self.celsius.trim().parse::<f64>() {
                        Ok(c) => {
                            let f = c * 9.0 / 5.0 + 32.0;
                            if self.round {
                                format!("{c:.0} °C = {f:.0} °F")
                            } else {
                                format!("{c} °C = {f} °F")
                            }
                        }
                        Err(e) => format!("не число: {e}"),
                    };
                }
```

Округление сделано **форматом** (`{:.0}` — §22.1.1), а не арифметикой: значение остаётся точным, меняется только представление. Прогон (ввод «36.6», щелчок; затем флажок; затем стирание и ввод «abc»):

```text
36.6 °C = 97.88000000000001 °F      ← флажок снят
37 °C = 98 °F                       ← флажок поставлен
не число: invalid float literal     ← в поле «abc»
```

Три наблюдения из прогона.

Первое — **97.88000000000001**. Это не ошибка конвертера и не причуда egui: `36.6` не представимо в двоичной плавающей точке точно (§2.1.2 тома I — та же арифметика, что у `float` в C), и `Display` для `f64` печатает кратчайшую запись, которая читается обратно в то же самое число. Умножение и сложение накопили младший бит — он и вылез. Правильный ответ здесь не «избавиться от погрешности», а **не показывать пользователю больше знаков, чем есть смысла**.

Второе — паники нет ни при каком вводе: `parse` возвращает `Result`, а `match` обязывает разобрать обе ветви (§18.1.2). Сообщение `invalid float literal` — это `Display` типа `ParseFloatError` (R9).

Третье — **тофу**. Стрелка «→» (U+2192) в комплекте шрифтов egui 0.35 по умолчанию отсутствует: и заголовок, и надпись на кнопке показывают на её месте пустой прямоугольник — «Цельсий □ Фаренгейт», «□ °F». Кириллица, «°», «·» и длинное тире рисуются, а стрелка — нет (сравните с §26.1.2, где кириллица «работает из коробки»: из коробки работает не всё). Лечение — либо ASCII-подпись (`-> °F`), либо свой шрифт через `egui::FontDefinitions`; в решении оставлена стрелка из условия, чтобы находка не потерялась.

**Ответ.** Конвертер: поле `celsius: String`, флажок `round: bool`, готовая надпись `result: String`; по щелчку — `self.celsius.trim().parse::<f64>()`, ветка `Ok(c)` считает `c * 9.0 / 5.0 + 32.0` и форматирует (`{:.0}` при поставленном флажке, иначе как есть), ветка `Err(e)` кладёт в надпись `format!("не число: {e}")`. Прогон: «36.6» → **«36.6 °C = 97.88000000000001 °F»**, с флажком → **«37 °C = 98 °F»**, «abc» → **«не число: invalid float literal»**, паники нет ни разу. Две находки прогона: длинный хвост `...0001` — двоичное представление `f64`, а не ошибка расчёта; символ «→» шрифтами egui 0.35 не покрыт и рисуется пустым прямоугольником.

**Вариант 2 (число вместо строки в состоянии).** Хранить разобранное значение, а надпись собирать в кадре (`v1_7/src/main.rs`):

```rust
#[derive(Default)]
struct TempApp {
    celsius: String,
    round: bool,
    parsed: Option<f64>, // None — ещё не считали или ввод не число
    error: String,
}
```

Кнопка теперь только разбирает ввод, ничего не форматируя:

```rust
                if ui.button("-> °F").clicked() {
                    match self.celsius.trim().parse::<f64>() {
                        Ok(c) => {
                            self.parsed = Some(c);
                            self.error.clear();
                        }
                        Err(e) => {
                            self.parsed = None;
                            self.error = format!("не число: {e}");
                        }
                    }
                }
```

А надпись собирается каждый кадр из текущего состояния — вместе с флажком:

```rust
            match self.parsed {
                Some(c) if self.round => {
                    ui.label(format!("{c:.0} °C = {:.0} °F", c * 9.0 / 5.0 + 32.0));
                }
                Some(c) => {
                    ui.label(format!("{c} °C = {} °F", c * 9.0 / 5.0 + 32.0));
                }
                None if !self.error.is_empty() => {
                    ui.label(&self.error);
                }
                None => {
                    ui.label("введите число и нажмите кнопку");
                }
            }
```

(Стрелка в подписях заменена на ASCII `->` — по находке основного решения.) Проверяется этот вариант без единого щелчка: приборная копия (`v1_7p`) сама подставляет число на первом кадре, на третьем **трогает только флажок** и записывает, что нарисовала:

```text
кадр 1: флажок=false надпись = 36.6 °C = 97.88000000000001 °F
кадр 2: флажок=false надпись = 36.6 °C = 97.88000000000001 °F
кадр 3: флажок=true надпись = 37 °C = 98 °F
кадр 4: флажок=true надпись = 37 °C = 98 °F
```

Кнопку после первого кадра никто не нажимал — надпись пересчиталась на том же кадре, где сменился флажок.

*Сравнение.* Строка в состоянии проще и печатается «как есть» — но она **застывает**: `self.result` присваивается только внутри обработчика кнопки, поэтому флажок, поставленный после расчёта, вступит в силу лишь при следующем щелчке (в прогоне флажок и нажимался перед повторным щелчком — иначе надпись осталась бы прежней). Числовое состояние пересчитывает надпись каждый кадр, поэтому флажок действует немедленно, и это ближе к духу §26.1.1 «интерфейс — функция от состояния». Цена — ошибка ввода перестаёт быть значением состояния: под неё нужно либо отдельное поле, либо `Result<f64, String>` вместо `Option<f64>`.

### Г26.Ч1.З8

**Условие.** Спроектируйте «светофор»: перечисление `enum Phase { Red, Yellow, Green }` (§16.2.1), кнопка «Переключить» ведёт фазы по кругу, надпись показывает текущую фазу и совет пешеходу (`match` — §16.2.2). Добавьте счётчик полных кругов. Обоснуйте, почему состояние здесь — перечисление, а не пара `bool`.

**Решение.** Фазы — перечисление, переходы — метод, круги — счётчик в состоянии (`z1_8/src/main.rs`):

```rust
enum Phase {
    Red,
    Yellow,
    Green,
}

impl Default for Phase {
    fn default() -> Phase {
        Phase::Red
    }
}

impl Phase {
    fn next(&self) -> Phase {
        match self {
            Phase::Red => Phase::Yellow,
            Phase::Yellow => Phase::Green,
            Phase::Green => Phase::Red,
        }
    }
```

`Default` реализован руками: `#[derive(Default)]` на структуре приложения требует, чтобы **все** поля умели `default()`, а перечислению нужно указать, какой вариант считать умолчанием. Красный — разумное начало.

Имя и совет — тоже `match`, оба возвращают `&'static str`: строковые литералы живут в бинарнике вечно (§15.3.2), копировать их незачем.

Кадр:

```rust
            if ui.button("Переключить").clicked() {
                self.phase = self.phase.next();
                // круг замкнулся ровно тогда, когда снова загорелся красный
                if let Phase::Red = self.phase {
                    self.circles += 1;
                }
            }

            ui.label(format!("сигнал: {} — {}", self.phase.name(), self.phase.advice()));
            ui.label(format!("полных кругов: {}", self.circles));
```

Прогон (шесть щелчков со снимками): красный → **жёлтый — приготовьтесь** → **зелёный — идите** → красный, «полных кругов: 1» → ... → после шестого щелчка «сигнал: красный — стойте», «полных кругов: 2».

**Ответ.** `enum Phase { Red, Yellow, Green }`, метод `next` с `match` по кругу, `Default` руками (красный), счётчик `circles: u32` растёт в момент возврата к красному (`if let Phase::Red = self.phase`), надписи собираются `match`-методами `name`/`advice`. Прогон: 6 щелчков → «сигнал: красный — стойте», «полных кругов: 2».

Почему перечисление, а не пара `bool`: тремя состояниями пара логических значений описывается только с **лишним четвёртым** — комбинация вроде `(red = true, green = true)` синтаксически возможна, а физически бессмысленна, и защищать от неё пришлось бы дисциплиной, то есть комментариями (том I именно так и жил — §8.2.1). Перечисление делает недопустимое состояние **непредставимым**: значение всегда ровно одно из трёх. Дальше это окупается на `match`: компилятор проверяет исчерпывающесть (E0004, §16.2.2), и добавление четвёртой фазы (мигающий зелёный) немедленно даёт ошибки во всех местах, где её забыли учесть, — с парой `bool` эти места пришлось бы искать глазами. Это ровно тот довод, которым в §16.2.1 `enum` с данными победил связку «`union` + тег» из §8.2.2.

**Вариант 2 (фаза — индекс в таблице).** Хранить номер и держать данные фаз в массиве (`v1_8/src/main.rs`):

```rust
const PHASES: [(&str, &str); 3] = [
    ("красный", "стойте"),
    ("жёлтый", "приготовьтесь"),
    ("зелёный", "идите"),
];

#[derive(Default)]
struct TrafficApp {
    phase: usize,
    circles: u32,
}
```

Переход — арифметика по модулю, круг — возврат к нулевому индексу:

```rust
            if ui.button("Переключить").clicked() {
                self.phase = (self.phase + 1) % PHASES.len();
                if self.phase == 0 {
                    self.circles += 1;
                }
            }

            let (name, advice) = PHASES[self.phase];
            ui.label(format!("сигнал: {name} — {advice}"));
            ui.label(format!("полных кругов: {}", self.circles));
```

Приборная копия (`v1_8p`) переключает фазы сама, по одной за кадр, и записывает результат — он совпадает с прогоном основного решения строка в строку:

```text
кадр 2: сигнал: жёлтый — приготовьтесь; полных кругов: 0
кадр 3: сигнал: зелёный — идите; полных кругов: 0
кадр 4: сигнал: красный — стойте; полных кругов: 1
кадр 5: сигнал: жёлтый — приготовьтесь; полных кругов: 1
кадр 6: сигнал: зелёный — идите; полных кругов: 1
кадр 7: сигнал: красный — стойте; полных кругов: 2
```

*Сравнение.* Табличная версия короче и переход считается арифметикой (`% 3`), а не тремя рукавами `match`; добавить фазу — дописать строку массива. Но тип состояния стал `usize`, то есть снова допускает недопустимое: `self.phase = 7` компилируется, и обвалится программа уже на индексации (паника, §15.3.1). Компилятор больше не проверит, что вы разобрали все случаи, — исчерпывающесть заменена договорённостью «индекс всегда меньше `PHASES.len()`». Для трёх фиксированных сигналов светофора это приемлемо, для состояний, которые несут разные *данные* (как `Circle(f64)` и `Rect{..}` из §16.2.1), — уже нет: таблица однородна, перечисление нет.

**Граница проверена первой.** До единой строки клиента:

Маленький файл, запрос `rust`, флажок снят:

— строки прошлого поиска с экрана **исчезли**: в ветке ошибки стоит `self.results.clear()`, и это не украшение, а требование честности — иначе под сообщением об ошибке остались бы результаты другого файла.

**Почему у клиента нет юнит-тестов.** Разделение §25.1.2 «логика — в библиотеке, церемония — в клиенте» здесь доведено до предела. Тестируемое — то, что можно вызвать функцией и сравнить с ожидаемым: `search`, `search_case_insensitive`, разбор конфигурации. Всё это лежит в `minigrep` и покрыто тремя тестами; клиент не добавил **ни одной** такой функции: `run_search` только склеивает чтение файла, вызов библиотеки и форматирование статуса.

Нетестируемое обычными средствами — то, что происходит внутри кадра: «кнопка нажата», «строки показаны в прокрутке», «панель внизу». Чтобы проверить это, нужен не `cargo test`, а живой оконный сервер, синтетический ввод и разбор картинки — то, что делает наш водитель на PowerShell (и что глава 12 делала для Win32). Такие проверки не запускаются на любой машине по `cargo test`, они медленные и требуют экрана; в промышленных проектах их выносят в отдельный слой (UI-тесты), а не в юнит-тесты crate.

**Ответ.** Проект собирается двумя пакетами с path-зависимостью; `cargo test` в `minigrep` — три зелёных теста, библиотека не изменилась ни на строку. Сценарии: `text.txt` + `rust` без флажка → «найдено строк: 1 за 237.4µs», с флажком → «найдено строк: 2 за 159.8µs», `nofile.txt` → «nofile.txt: The system cannot find the file specified. (os error 2)» при очищенном списке результатов. Своих юнит-тестов у GUI-клиента не появилось потому, что **вся тестируемая логика осталась в библиотеке**: клиент содержит только церемонию — чтение файла, склейку статуса и рисование виджетов. Проверять в нём нечего функцией: «нажалась ли кнопка» и «видна ли строка в прокрутке» проверяются прогоном интерфейса (наш водитель), а не `cargo test`; ровно поэтому граница «библиотека ↔ клиент» из §25.1.2 и ценна — она отделяет проверяемое от показываемого.

**Грабли, из-за которых этот замер сначала не сошёлся.** Первая версия замера дала 2,6 с у **обеих** версий — и едва не отправила в главу правку. Причина оказалась не в коде, а в стенде: оба пакета назывались `gui_minigrep`, cargo кладёт готовый бинарник в `target/debug/<имя пакета>.exe`, и под этим именем в общем каталоге остался **старый синхронный** бинарник. Поймать это удалось только поиском строк прямо в исполняемом файле: `grep -a "поток поиска прервался" gui_minigrep.exe` — в фоновой версии такая строка есть, в синхронной её нет и быть не может. Урок дороже замера: **если два пакета одноимённы, «свежий» бинарник в общем каталоге сборки может оказаться чужим**, и никакая пересборка об этом не скажет — cargo честно соберёт нужный `deps/gui_minigrep-<хеш>.exe`, а копия в `debug/` останется прежней. Проверка занимает секунду, стоит недоверия к целому дню замеров.

Но «долго закрывается» и «заморожено» — разные вещи, и вторую проверяет приборная копия приложения (протокол кадров в файл; полностью разобрана в З6). Она показывает, что у фоновой версии **интерфейс во время поиска жив**:

```text
кадр 1: поиск запущен
кадр 1: идёт поиск (#1) через 542.5µs
кадр 2: идёт поиск (#2) через 292.6919ms
кадр 3: идёт поиск (#3) через 302.3201ms
кадр 417: результат на экране через 2.8202552s после запуска (кадров за поиск: 416)
```

**416 кадров за время поиска** — интерфейс перерисовывался всё это время (спиннер просит перерисовку каждый кадр), статус показывал «ищем…», снимок это застал. У синхронной версии кадр не завершается вовсе: пока `run_search` не вернулся, ни ввод, ни перерисовка не обрабатываются.

**Что происходит с процессом после закрытия.** Фоновая задача в момент закрытия обычно ещё считает — и остаётся недосчитанной: `thread::spawn` без `join` отсоединяет поток, а завершение `main` уносит процесс вместе со всеми потоками (§23.1.1). Для поиска это ровно то, что нужно: результат больше некому показывать. Заметьте разницу с пулом главы 25, где `Drop` дожидался воркеров: там незавершённая задача означала потерянную работу, здесь — сэкономленное время.

**Ответ.** Таблица (эталонная машина): 33 МБ — dev 191 мс / 452 мс, release 9,2 мс / 241 мс; 193 МиБ — dev 1,20 с / 2,75 с, release 56 мс / 1,45 с; чтение 26 мс и 145 мс соответственно. Выводы совпали с главой: регистронезависимый поиск в 2,4–4 раза дороже, релиз ускоряет обычный поиск на порядок, а тяжёлый — вдвое. Главный замер отзывчивости: в покое окно закрывается за 59–79 мс; во время поиска по 193-мегабайтному файлу синхронная версия закрывается за **2,44–2,47 с** (команда ждёт конца кадра), фоновая — за **59–99 мс**, то есть неотличимо от покоя. Вывод главы воспроизведён. Фоновая версия при этом не просто «быстро закрывается»: за время поиска она нарисовала 416 кадров, показывала «ищем…» и спиннер, тогда как синхронная не нарисовала ни одного.

### Г26.Ч2.З4

**Условие.** Разберите ⛔-пример чекпоинта 1 по сообщению компилятора: чей лайфтайм `'a`, почему присваивание «requires that `contents` is borrowed for `'a`» и почему это невыполнимо. Затем ответьте на вопрос проектировщика: а *мог* бы `GrepApp` владеть текстом (`contents: String` в состоянии) и хранить `Vec<&str>` в него? Какая пара полей получилась бы и почему Rust запрещает такую структуру (подсказка: §19.3.2 — ссылка на соседнее поле)?

**Решение.** ⛔-пример собран как отдельный бинарник пакета (`p2_sync/src/bin/borrowed_results.rs`), чтобы номера строк совпадали с главой:

```text
$ cargo build --bin borrowed_results
error[E0597]: `contents` does not live long enough
  --> src\bin\borrowed_results.rs:9:48
   |
 6 | impl<'a> GrepApp<'a> {
   |      -- lifetime `'a` defined here
 7 |     fn run_search(&mut self, query: &str, path: &str) {
 8 |         let contents = std::fs::read_to_string(path).unwrap();
   |             -------- binding `contents` declared here
 9 |         self.results = minigrep::search(query, &contents);
   |         ------------                           ^^^^^^^^^ borrowed value does not live long enough
   |         |
   |         assignment requires that `contents` is borrowed for `'a`
10 |     }
   |     - `contents` dropped here while still borrowed

error: could not compile `gui_minigrep_v1` (bin "borrowed_results") due to 1 previous error
```

**Чей лайфтайм `'a`.** Компилятор указывает пальцем: «lifetime `'a` defined here» — строка 6, `impl<'a> GrepApp<'a>`. Это параметр **типа приложения**, а не метода: объявив `struct GrepApp<'a> { results: Vec<&'a str> }`, мы сказали «в этой структуре лежат ломтики, живущие не меньше `'a`», и каждое значение `GrepApp` выбирает своё `'a` в момент создания — снаружи, в вызывающем коде. Метод `run_search` его не выбирает и изменить не может: для него `'a` — данность, «столько, сколько потребовал тот, кто нас создал».

**Почему присваивание требует `'a`.** Слева от `=` — поле типа `Vec<&'a str>`. Что бы ни стояло справа, после присваивания в поле окажутся ломтики, которые обязаны жить `'a`. Справа — `minigrep::search(query, &contents)`, и сигнатура `search<'a>(query: &str, contents: &'a str) -> Vec<&'a str>` (§25.1.3) честно говорит: результат живёт ровно столько, сколько `contents`. Компилятор соединяет две половины: чтобы присваивание было законно, `contents` должна прожить `'a`. Отсюда дословная формулировка «assignment requires that `contents` is borrowed for `'a`».

**Почему это невыполнимо.** `contents` — локальная переменная функции: она рождается в строке 8 и умирает в строке 10 («`contents` dropped here while still borrowed»). А `'a` — время жизни, выбранное **снаружи** и заведомо не короче самого значения `GrepApp`, которое переживёт вызов метода (иначе метод незачем и звать). Требование «локальная переменная должна прожить дольше объекта, которому она отдаёт ссылки» неисполнимо ни при каком `'a`: это ровно висячая ссылка из §15.2.3, только собранная не возвратом из функции, а присваиванием в поле.

**Мог бы `GrepApp` владеть текстом?** Соблазн понятен: раз ломтики требуют живого текста — пусть текст лежит в самой структуре:

```rust
// так не бывает
struct GrepApp {
    contents: String,        // владеем текстом
    results: Vec<&str>,      // ...и ломтиками в него же
}
```

Пара полей получилась бы такая: `contents: String` — владелец, и `results: Vec<&'? str>` — ссылки **внутрь соседнего поля**. И вот на `'?` всё и останавливается: указать здесь нечего. Любой лайфтайм в объявлении структуры — это параметр, который выбирает **создатель** значения снаружи (§19.3.2); а нам нужно время жизни, привязанное к другому полю **того же** значения, — понятия «время жизни соседнего поля» в языке нет. Формально: попытка написать `Vec<&str>` без параметра даст E0106 («missing lifetime specifier», знакомую по §15.2.3), а попытка ввести `struct GrepApp<'a> { contents: String, results: Vec<&'a str> }` компилируется, но пользоваться ей нельзя — чтобы заполнить `results`, надо заимствовать `self.contents`, то есть заимствовать часть значения на всё время его жизни; после этого любое изменение `contents` (и сам переезд структуры) запрещены заимствованием.

Такие структуры называют самоссылочными, и Rust их не поддерживает намеренно: переезд значения (move, §15.1.2) физически копирует байты, и ссылка, указывавшая внутрь старого места, стала бы висячей. Именно здесь проходит граница, за которой в реальных проектах берут `Rc`/арену/индексы вместо ссылок — или, как мы, **платят копию**.

**Ответ.** `'a` — параметр времени жизни **самой структуры** `GrepApp<'a>` (строка 6, `impl<'a> GrepApp<'a>`), выбираемый снаружи при создании значения. Присваивание `self.results = minigrep::search(query, &contents)` требует, чтобы `contents` была заимствована на `'a`, потому что поле объявлено как `Vec<&'a str>`, а `search` возвращает ломтики ровно того же времени жизни, что и её аргумент `contents`. Выполнить это невозможно: `contents` — локальная переменная, умирающая в конце `run_search`, а `'a` не короче времени жизни всего приложения. Владеть текстом `GrepApp` тоже не может: пара полей была бы `contents: String` + `results: Vec<&'a str>`, где ссылки указывают **внутрь соседнего поля того же значения**; в языке нет способа назвать такое время жизни (§19.3.2 — лайфтайм структуры выбирается снаружи), а самоссылочные структуры запрещены потому, что переезд значения сделал бы такие ссылки висячими. Отсюда решение главы: `Vec<String>` — копия найденного, один раз за поиск.

### Г26.Ч2.З5

**Условие.** Разберите второй ⛔ (чекпоинт 3): объясните пометку «lifetime `'1` appears in the type of `tx`» — как время жизни локального `contents` «заразило» тип канала — и почему `Vec<String>` разрывает эту связь. Сравните с рассуждением §25.2.4 о том же запрете: что даёт формулировка через тип канала, чего не давала формулировка «замыкание обязано быть 'static»?

**Решение.** Второй ⛔ (`p2_sync/src/bin/chan_slices.rs`) — тот же E0597, но диагностика указывает в другое место:

```text
$ cargo build --bin chan_slices
error[E0597]: `contents` does not live long enough
  --> src\bin\chan_slices.rs:10:46
   |
 6 |     let (tx, rx) = mpsc::channel();
   |          -- lifetime `'1` appears in the type of `tx`
...
 9 |         let contents = std::fs::read_to_string("text.txt").unwrap();
   |             -------- binding `contents` declared here
10 |         let found = minigrep::search("Rust", &contents);
   |                                              ^^^^^^^^^ borrowed value does not live long enough
11 |         tx.send(found).unwrap();
   |         -------------- argument requires that `contents` is borrowed for `'1`
12 |     });
   |     - `contents` dropped here while still borrowed
```

**Как время жизни попало в тип `tx`.** `mpsc::channel()` — обобщённая функция: `channel::<T>() -> (Sender<T>, Receiver<T>)`, и `T` компилятор выводит из того, что вы в канал шлёте. Мы отправляем `found`, то есть `Vec<&str>`, — а всякий `&str` несёт время жизни, здесь безымянное, и компилятор зовёт его `'1`. Значит, выведенный тип передатчика — `Sender<Vec<&'1 str>>`: **время жизни стало частью типа канала**. Отсюда первая пометка: «lifetime `'1` appears in the type of `tx`».

Дальше — та же арифметика, что в З4, но с другой стороны. `tx` создан **до** потока (строка 6) и живёт в `main`; чтобы отправка была законна, значение должно годиться его типу, то есть ломтики обязаны жить `'1` — время, привязанное к переменной из внешней области. А `contents` рождается **внутри** замыкания (строка 9) и умирает на строке 12. «argument requires that `contents` is borrowed for `'1`» — и невозможность.

Важно, что это не про потоки: тот же код без `thread::spawn`, просто с `contents` в отдельном блоке, отвергается по той же причине. Канал, однажды повёзший ломтик, **типом** привязывается к тексту одной конкретной задачи — и перестаёт быть каналом «для любых поисков».

**Почему `Vec<String>` разрывает связь.** `String` владеет своими байтами и не ссылается ни на что: в её типе нет параметра времени жизни. Тип канала становится `Sender<Vec<String>>` — тип без единого лайфтайма, а значит, и без обязательств перед чьей-либо локальной переменной. Задача читает файл, ищет, **копирует найденное во владение** (`found.into_iter().map(String::from).collect()`) и отправляет; `contents` спокойно умирает в конце задачи, потому что в канал уехали данные, а не виды на них.

**Что даёт формулировка через тип канала.** В §25.2.4 тот же запрет объясняли требованием `'static`: «замыкание, уезжающее в поток, обязано владеть всем, что использует, — ссылки на чужой стек через границу потока не проходят». Это верно, но объясняет только **поточную** половину. Новая формулировка сильнее в двух отношениях.

Во-первых, она называет виновника точнее: дело не в потоке, а в **типе канала**, который выводится из первого отправленного значения и с этого момента фиксируется. Даже в однопоточной программе `Sender<Vec<&'1 str>>` останется каналом для ломтиков ровно одного текста; никакая «межпоточность» тут ни при чём.

Во-вторых, она подсказывает лечение. Требование `'static` звучит как «сделайте всё вечным» — и толкает к `Box::leak`, `Arc<String>` и прочим тяжёлым приёмам. Формулировка «время жизни просочилось в тип» указывает на настоящую задачу: **уберите лайфтайм из типа сообщения**. Способ ровно один и он дешёвый — везти владеющее значение.

**Ответ.** Пометка «lifetime `'1` appears in the type of `tx`» означает, что параметр `T` канала выведен из отправляемого значения `Vec<&str>`, и безымянное время жизни ломтиков `'1` стало частью типа передатчика `Sender<Vec<&'1 str>>`. Передатчик создан во внешней области, поэтому `'1` привязано к ней; `contents` же — локальная переменная задачи, умирающая раньше, отсюда «argument requires that `contents` is borrowed for `'1`». `Vec<String>` разрывает связь потому, что `String` владеет данными и в её типе лайфтайма нет вовсе: тип канала перестаёт что-либо обещать о чужих переменных. По сравнению с рассуждением §25.2.4 («замыкание обязано быть `'static`») формулировка через тип канала (а) показывает, что запрет не про потоки, а про вывод типов — тот же канал непригоден и в однопоточном коде; (б) прямо указывает лечение: не «сделать данные вечными», а **убрать время жизни из типа сообщения**, то есть отправлять владеющее значение.

### Г26.Ч2.З6

**Условие.** Уберите из фоновой задачи строку `ctx.request_repaint()` и опишите наблюдаемое поведение: когда именно появляется результат и почему «оживить» окно может любое движение мыши (модель перерисовки — §26.1.1). Поиск стартует сам, из аргументов командной строки, так что **интерфейс во время опыта никто не трогает** — а это и есть условие чистоты: любое движение мыши разбудило бы кадр и подменило результат.

Первое (в `z2_6c`) — **спиннер**: пока он в кадре, перерисовка идёт непрерывно, и промах одного пробуждения ничего не стоит — следующий кадр придёт через миллисекунды сам.

Второе (в `z2_6d`, где спиннера нет) — **разница масштабов**. Между `ctx.request_repaint()` и `tx.send(outcome)` в коде задачи проходят наносекунды: это две соседние строки. А пробуждение — дорога через границу потоков: `request_repaint` помечает контекст и будит цикл событий, тот просыпается, обрабатывает очередь, вызывает `ui`. К моменту, когда разбуженный кадр доберётся до `try_recv`, сообщение давно на месте — задержка результата в прогонах 0,15–0,4 с сверх времени поиска, тогда как «окно гонки» шириной в две строки кода. Гонка **возможна** — но неправдоподобна, и полагаться на это нельзя: планировщик вправе снять поток задачи ровно между этими строками, и тогда результат зависнет до следующего события, как в `z2_6b`.

Отсюда практическое правило, которое глава и формулирует одной фразой в §26.2.3: сначала положить результат, потом будить. Порядок стоит копейку, а неправильный порядок отлаживается по жалобе «иногда результат появляется, только когда двину мышью» — самый неприятный сорт ошибок.

**Ответ.** Без `ctx.request_repaint()` результат появляется **не тогда, когда он готов, а при первом же событии окна**: в опыте без спиннера поиск закончился через 2,6 с, а на экран результат попал через **7,8 с** — в момент встряски окна; кадров между третьим и этим не было ни одного. Оживить окно может любое движение мыши потому, что egui перерисовывается только на ввод или по явной просьбе (§26.1.1), а всякое событие — повод вызвать кадр, кадр же начинается с `poll_search`. Важная оговорка: **если в кадре есть спиннер, пропажу `request_repaint` не заметить** — анимированный виджет сам просит перерисовку каждый кадр (387 кадров за поиск), и результат появляется вовремя. Если перенести `request_repaint` **до** `tx.send(...)`, возможна гонка: разбуженный кадр опросит пустой канал, нарисует «ищем…» и уснёт, а результат дождётся следующего события. В четырёх прогонах она не выстрелила — спасают спиннер (непрерывные кадры) и разница масштабов: между пробуждением и отправкой в коде наносекунды, а дорога пробуждения до кадра занимает миллисекунды. Гарантией это не является: планировщик вправе снять поток именно между этими строками, поэтому правильный порядок — сначала `send`, потом `request_repaint`.

### Г26.Ч2.З7

**Условие.** В `poll_search` мы присваиваем `self.search = None` внутри `if let Some(rx) = &self.search`. Объясните, почему это компилируется (где кончается заимствование `rx` — §15.2.2), и постройте контрпример: измените код так, чтобы `rx` использовался *после* присваивания, получите ошибку заимствования и почините её через `Option::take` (§25.2.3). Сформулируйте правило: когда опрос обходится ссылкой, а когда нужен `take`.

**Решение.** Почему компилируется исходный `poll_search`: заимствование `&self.search` живо ровно до последнего **использования** ссылки `rx`, а не до конца блока `if let`. Последнее использование — вызов `rx.try_recv()` в заголовке `match`; дальше в рукавах `rx` не встречается, заимствование мертво, и присваивание `self.search = None` законно. Это нелексические времена жизни (NLL, §15.2.2): область заимствования определяется потоком управления, а не фигурными скобками.

Контрпример строится ровно нарушением этого условия — использовать `rx` **после** присваивания (`z2_7/src/bin/nll_bad.rs`, сокращён до сути):

```rust
impl App {
    fn poll(&mut self) {
        if let Some(rx) = &self.search {
            if let Ok(v) = rx.try_recv() {
                self.last = v;
                self.search = None;
                // ещё один взгляд в канал — уже после присваивания
                if rx.try_recv().is_err() {
                    self.last = -1;
                }
            }
        }
    }
}
```

```text
$ cargo build --bin nll_bad
error[E0506]: cannot assign to `self.search` because it is borrowed
  --> src\bin\nll_bad.rs:14:17
   |
11 |         if let Some(rx) = &self.search {
   |                           ------------ `self.search` is borrowed here
...
14 |                 self.search = None;
   |                 ^^^^^^^^^^^ `self.search` is assigned to here but it was already borrowed
15 |                 // ещё один взгляд в канал — уже после присваивания
16 |                 if rx.try_recv().is_err() {
   |                    -- borrow later used here

error: could not compile `z2_7` (bin "nll_bad") due to 1 previous error
```

Диагностика читается как учебник по NLL: вот где заимствовали (11), вот где присвоили (14), а вот **почему это важно** — «borrow later used here» (16). Уберите строку 16 — программа соберётся; в этом и разница между «переменная в области видимости» и «заимствование живо».

Лечение — `Option::take()` (§25.2.3): забрать приёмник во владение, оставив в поле `None` (`z2_7/src/bin/nll_take.rs`):

```rust
    fn poll(&mut self) {
        if let Some(rx) = self.search.take() {
            match rx.try_recv() {
                Ok(v) => {
                    self.last = v;
                    // приёмник наш: пользуемся им после того, как поле уже None
                    if rx.try_recv().is_err() {
                        self.last = v * 10;
                    }
                    // self.search остаётся None — работа окончена
                }
                Err(mpsc::TryRecvError::Empty) => {
                    self.search = Some(rx); // ещё ждём: кладём приёмник обратно
                }
                Err(mpsc::TryRecvError::Disconnected) => {
                    self.last = -1;
                }
            }
        }
    }
```

Прогон:

```text
$ ../target-shared/debug/nll_take.exe
после пустого опроса: last = 0, поиск идёт = true
после приёма: last = 70, поиск идёт = false
```

Первая строка — самое поучительное: канал был пуст, приёмник забрали `take`-ом и **вернули на место**, поле снова `Some`, работа продолжается. Забыть этот возврат — типичная ошибка приёма: поиск молча «потеряется», потому что приёмник уничтожится в конце `poll`, а `self.search` останется `None`.

Та же правка в настоящем клиенте (`z2_7/src/main.rs`) выглядит так: `if let Some(rx) = self.search.take()`, три строки `self.search = None` из рукавов исчезают (поле уже пусто), а рукав `Empty` вместо пустого блока возвращает приёмник:

```rust
                // ещё ищем: приёмник забрали take-ом — вернуть его на место
                Err(mpsc::TryRecvError::Empty) => self.search = Some(rx),
```

**Ответ.** Исходный код компилируется потому, что заимствование `&self.search` заканчивается на последнем использовании `rx` — вызове `try_recv()` в заголовке `match`; к моменту `self.search = None` оно уже мертво (NLL, §15.2.2). Контрпример — обратиться к `rx` после присваивания; тогда компилятор отвечает **E0506 «cannot assign to `self.search` because it is borrowed»** и прямо показывает виновника строкой «borrow later used here». Лечится `Option::take()`: приёмник переходит во владение (`if let Some(rx) = self.search.take()`), поле сразу становится `None`, и пользоваться `rx` можно сколько угодно; в ветке «ещё ищем» приёмник обязательно кладётся обратно (`self.search = Some(rx)`).

Правило: **опрос обходится ссылкой, пока приёмник не нужен после изменения поля.** Если тело опроса только читает канал и, разобравшись, обнуляет поле — достаточно `&self.search`, и это дешевле: ничего не перемещается. Если приёмник нужен и после (второй `try_recv`, передача в другую функцию, сохранение в другое место) или если поле меняется не в конце, а в середине работы, — берите `take` и не забудьте вернуть значение в ветках, где работа продолжается.

**Вариант 2 (решение сначала, присваивание потом).** Не забирать владение, а вынести изменение поля из области заимствования: в блоке только вычислить, что делать, а сделать — после (`v2_7/src/main.rs`, собран без предупреждений):

```rust
    fn poll_search(&mut self) {
        // Что делать — решаем под заимствованием; делаем — вне его.
        enum Step {
            Nothing,
            Done(Vec<String>, Duration),
            Failed(String),
            Broken,
        }

        let step = match &self.search {
            None => Step::Nothing,
            Some(rx) => match rx.try_recv() {
                Ok(Ok((lines, took))) => Step::Done(lines, took),
                Ok(Err(msg)) => Step::Failed(msg),
                Err(mpsc::TryRecvError::Empty) => Step::Nothing,
                Err(mpsc::TryRecvError::Disconnected) => Step::Broken,
            },
        };

        // Заимствование кончилось вместе с выражением — поле свободно.
        match step {
            Step::Nothing => {}
            Step::Done(lines, took) => {
                self.status = format!("найдено строк: {} за {took:?}", lines.len());
                self.results = lines;
                self.search = None;
            }
            Step::Failed(msg) => {
                self.results.clear();
                self.status = msg;
                self.search = None;
            }
            Step::Broken => {
                self.results.clear();
                self.status = String::from("поток поиска прервался");
                self.search = None;
            }
        }
    }
```

Обратите внимание на объявление `enum Step` **внутри функции**: перечисление нужно только ей, и в языке ничто не мешает объявить тип локально (§16.2.1 — там же, где мы впервые увидели `enum`; область видимости у типов та же, что у любых имён, §20.1.1).

*Сравнение.* `take` короче и естественнее, когда приёмник действительно больше не нужен; зато он требует помнить о возврате в ветке «ещё ищем» — забыли, и поиск потерян без единого предупреждения компилятора. Вариант с промежуточным перечислением ничего не перемещает и не может «потерять» приёмник: поле правится ровно в одном месте, после того как заимствование заведомо кончилось. Цена — лишний тип и лишний `match`, то есть заметно больше кода ради того же результата. Приём стоит помнить не ради этого случая, а как общий способ разрубать конфликты заимствований: **вычислить решение под заимствованием, применить — вне его**.

### Г26.Ч2.З8

**Условие.** Три продуктовые доработки: (а) защитите поиск от пустого запроса — кнопка не запускает поиск, статус объясняет почему (вспомните факт `contains("") == true` из чекпоинта 1 — что «нашла» бы фоновая версия на большом файле?); (б) заблокируйте кнопку на время поиска по-настоящему: `ui.add_enabled(!searching, egui::Button::new("Искать"))` вместо проверки внутри `if` (сигнатура — R11, docs.rs/egui: `Ui::add_enabled`); (в) добавьте кнопку «Сохранить», пишущую найденные строки в файл `results.txt` (`fs::write` — §25.2.4; не забудьте: ошибки записи — в статус, успех — тоже).

**Решение.** Три доработки, каждая — в своём месте (`z2_8/src/main.rs`).

**(а) Пустой запрос.** Проверка стоит на входе, до всякой работы, и объясняет отказ в статусе:

```rust
    /// Кнопка «Искать»: пустой запрос до потока не доходит.
    fn on_search_clicked(&mut self, ctx: &egui::Context) {
        if self.query.trim().is_empty() {
            self.results.clear();
            self.status = String::from("пустой запрос: contains(\"\") истинно для любой строки — нашлись бы все строки файла");
            let s = self.status.clone();
            self.note(format!("кадр {}: поиск не запущен — {s}", self.frame));
            return;
        }
        self.start_search(ctx);
    }
```

Что «нашла» бы фоновая версия на большом файле без этой защиты, считается точно. `contains("")` истинно для любой строки (факт чекпоинта 1, R9), значит `search` вернула бы **все** строки файла: для `big2.txt` — 2 400 000 ломтиков, которые затем копируются во владение (`map(String::from)`), то есть двести мегабайт текста превращаются в два с половиной миллиона отдельных `String` со своими заголовками и выделениями кучи. Дальше их получает `Vec<String>` в состоянии, и каждый кадр `ScrollArea` обходит `for line in &self.results`. Практический итог — секунды работы, сотни мегабайт памяти и заваленный интерфейс вместо ответа на бессмысленный вопрос. Проверка в одну строку избавляет от всего этого.

**(б) Настоящая блокировка кнопки.** Вместо `if ui.button("Искать").clicked() && !searching` — виджет, который сам знает, что он выключен (R11, `Ui::add_enabled`):

```rust
                // Кнопка не «проверяет флаг внутри», а выключена по-настоящему:
                // серая и не реагирует на щелчок.
                if ui.add_enabled(!searching, egui::Button::new("Искать")).clicked() {
                    let ctx = ui.ctx().clone();
                    self.on_search_clicked(&ctx);
                }
                if ui
                    .add_enabled(!self.results.is_empty(), egui::Button::new("Сохранить"))
                    .clicked()
                {
                    self.save_results();
                }
```

Разница не косметическая. С проверкой внутри `if` кнопка выглядит обычной: пользователь жмёт её во время поиска и не получает никакого отклика — программа кажется сломанной. `add_enabled(false, ...)` рисует кнопку серой и не пропускает щелчок: правило видно **до** нажатия. Снимок во время поиска по большому файлу это и показывает: «Искать» и «Сохранить» серые, рядом крутится спиннер, в статусе «ищем…».

**(в) Кнопка «Сохранить».** Успех и ошибка одинаково уходят в статус — у окна нет stderr (§26.2.1):

```rust
    /// Кнопка «Сохранить»: успех и ошибка одинаково уходят в статус.
    fn save_results(&mut self) {
        let text = self.results.join("\n");
        self.status = match fs::write("results.txt", text) {
            Ok(()) => format!("сохранено строк: {} в results.txt", self.results.len()),
            Err(e) => format!("results.txt: {e}"),
        };
```

`join("\n")` (§17.1.1) собирает вектор в одну строку, `fs::write` пишет её целиком (§25.2.4). Кнопка выключена, пока результатов нет, — сохранять пустоту незачем.

**Прогоны.** Чтобы проверить логику без единого щелчка, приложение умеет запускать поиск из аргументов (`<запрос> <файл> [save]`) и пишет протокол в `probe.txt`. Пустой запрос:

```text
$ z2_8.exe "   " text.txt
кадр 1: поиск не запущен — пустой запрос: contains("") истинно для любой строки — нашлись бы все строки файла
```

Строка из пробелов отсечена именно `trim` — без него `"   ".is_empty()` было бы ложью, и в поиск ушёл бы запрос из трёх пробелов.

Поиск с сохранением:

```text
$ z2_8.exe rust text.txt save
кадр 1: поиск запущен
кадр 2: найдено строк: 2 за 196.3µs
кадр 2: сохранено строк: 2 в results.txt

$ cat results.txt
Затем пришёл Rust — и владение
Не доверяй — проверяй: rustc не спит.
```

Обратите внимание: приём результата и сохранение случились в **одном кадре** (кадр 2) — результат пришёл, `poll_search` его разобрал, и тут же отработала запись.

**Ответ.** (а) Проверка `self.query.trim().is_empty()` в начале обработчика кнопки: поиск не запускается, статус объясняет причину. Без неё фоновая версия на `big2.txt` «нашла» бы **все 2 400 000 строк** (потому что `contains("")` истинно для любой строки), скопировала бы их в `Vec<String>` — сотни мегабайт и секунды работы вместо ответа. (б) `ui.add_enabled(!searching, egui::Button::new("Искать")).clicked()` — кнопка становится серой и не принимает щелчок, в отличие от проверки внутри `if`, при которой нажатие просто молча игнорируется; снимок во время поиска показывает обе кнопки выключенными и крутящийся спиннер. (в) `save_results` собирает `self.results.join("\n")` и пишет `fs::write("results.txt", ...)`, отправляя в статус и успех («сохранено строк: 2 в results.txt»), и ошибку («results.txt: <текст ошибки>»); кнопка выключена, пока результатов нет. Проверено прогоном: файл `results.txt` содержит ровно две найденные строки.

**Вариант 2 (сохранение — тоже в фоне).** Запись — такой же ввод-вывод, как чтение, и на большом результате она так же заморозит кадр: 2400 строк пишутся мгновенно, а 2 400 000 — уже нет. Лечение то же, что для поиска, и код почти дословно повторяет `start_search`:

```rust
    fn start_save(&mut self, ctx: &egui::Context) {
        let text = self.results.join("\n");
        let n = self.results.len();
        let ctx = ctx.clone();
        let (tx, rx) = mpsc::channel();
        self.save = Some(rx);
        self.status = String::from("сохраняем…");

        thread::spawn(move || {
            let msg = match fs::write("results.txt", text) {
                Ok(()) => format!("сохранено строк: {n} в results.txt"),
                Err(e) => format!("results.txt: {e}"),
            };
            let _ = tx.send(msg);
            ctx.request_repaint();
        });
    }
```

Прогон варианта (`v2_8`, автозапуск из аргументов, протокол в файл):

```text
кадр 1: поиск запущен
кадр 2: найдено строк: 2 за 933.2µs
кадр 3: сохранено строк: 2 в results.txt
```

Разница с основным решением видна по номерам кадров: там приём результата и запись случились в **одном** кадре (кадр 2), здесь запись уехала в поток и отчиталась **на следующем** — лишний кадр как раз и есть цена асинхронности. Файл на диске в обоих случаях один и тот же.

*Сравнение.* Синхронная запись проще на десяток строк и честна для типичного результата поиска (единицы тысяч строк — микросекунды). Фоновая повторяет уже освоенный узор «поток → канал → опрос → `request_repaint`» и снимает последний источник заморозки, но за это в состоянии появляется **второй** `Option<Receiver<…>>` и второй опрос в кадре, а с ними — вопрос, что делать, если пользователь нажмёт «Искать» во время сохранения (нужна общая машина состояний, а не два независимых флага). Правило выбора то же, что в чекпоинте 2: пока работа заведомо короче кадра — делайте в кадре; как только она зависит от размера данных — в поток.

### Г26.Ч2.З9

**Условие.** Финальный аккорд курса: научите приложение искать в *нескольких* файлах разом. Подключите `ThreadPool` из §25.2 path-зависимостью; файлы задаются в одном поле через точку с запятой; каждая задача пула ищет в своём файле и шлёт в общий канал кортеж с именем файла, как в `pargrep` (§25.2.4); интерфейс копит результаты по мере прихода, а конец работы определяет по числу полученных ответов (сколько файлов — столько сообщений; почему здесь не сработает трюк «канал закрылся — работа кончена» из §25.2.4 и что с этим делать — ваше проектное решение, обоснуйте его). У вас есть всё: пул, канал, опрос, спиннер.

**Решение.** Финальный аккорд собирается из готовых деталей: пул из §25.2 подключается path-зависимостью рядом с библиотекой поиска (`z2_9/Cargo.toml`):

```toml
[dependencies]
eframe = "0.35.0"
minigrep = { path = "../minigrep" }
pargrep = { path = "../pargrep" }
```

**Состояние.** К полям клиента добавляются пул, приёмник и два счётчика:

```rust
    rx: Option<mpsc::Receiver<FileOutcome>>,
    pool: Option<ThreadPool>,
    expected: usize,
    received: usize,
```

`ThreadPool` живёт в состоянии, а не в локальной переменной, ровно по той же причине, по которой там живёт приёмник: он должен пережить кадр. Тип сообщения — кортеж с именем файла, как в `pargrep` (§25.2.4), и, конечно, владеющий (урок З5):

```rust
/// Ответ одной задачи: имя файла и найденные строки — или текст ошибки.
type FileOutcome = (String, Result<Vec<String>, String>);
```

**Запуск.** Поле пути разбирается по точке с запятой, пустые куски отбрасываются; пул получает столько воркеров, сколько файлов (но не больше восьми — лишние простаивали бы):

```rust
        // Воркеров не больше, чем файлов: лишние всё равно простаивали бы.
        let pool = ThreadPool::new(files.len().min(8));
        let (tx, rx) = mpsc::channel();

        for file in files {
            let tx = tx.clone();
            let query = self.query.clone();
            let ignore_case = self.ignore_case;
            let ctx = ctx.clone();

            pool.execute(move || {
                let outcome = match fs::read_to_string(&file) {
                    Ok(contents) => {
                        let found = if ignore_case {
                            minigrep::search_case_insensitive(&query, &contents)
                        } else {
                            minigrep::search(&query, &contents)
                        };
                        Ok(found.into_iter().map(String::from).collect())
                    }
                    Err(e) => Err(e.to_string()),
                };
                let _ = tx.send((file, outcome));
                ctx.request_repaint();
            });
        }
        drop(tx); // оригинал больше не нужен: живы клоны внутри задач
```

Каждая задача получает свои копии запроса и имени файла и **свой клон передатчика** (§23.1.3) — та же схема, что в `pargrep`, плюс клон контекста, чтобы разбудить интерфейс: результат первого файла должен появиться на экране сразу, а не после последнего.

**Опрос.** Отличие от одиночного поиска принципиальное: за один кадр может прийти **несколько** ответов, поэтому канал вычерпывается циклом, а не одним `try_recv`:

```rust
        if let Some(rx) = &self.rx {
            // За кадр может прийти несколько ответов — вычерпываем все.
            loop {
                match rx.try_recv() {
                    Ok(item) => arrived.push(item),
                    Err(mpsc::TryRecvError::Empty) => break,
                    Err(mpsc::TryRecvError::Disconnected) => {
                        done = true;
                        break;
                    }
                }
            }
        }
```

Пришедшее сразу попадает в список результатов — интерфейс копит их по мере прихода, а не ждёт последнего файла.

**Как узнать, что работа кончилась.** Здесь и лежит проектное решение задания. В §25.2.4 признаком конца был **конец канала**: `for (file, result) in rx` — цикл заканчивается сам, когда умирает последний клон передатчика. В кадре этот приём неприменим буквально, потому что `for ... in rx` **блокирующий**: он ждёт следующего сообщения, а ждать в кадре — это ровно та заморозка, которую мы лечили весь чекпоинт 3. Неблокирующий брат сообщает о закрытии канала отдельным значением `TryRecvError::Disconnected`, и им можно пользоваться — мы и пользуемся, но как **страховкой**, а не как основным признаком:

```rust
        if self.rx.is_some() && (self.received == self.expected || done) {
```

Основной признак — счёт: сколько файлов, столько ответов. Два довода в пользу счётчика.

Первый — **надёжность**. Канал закрывается, когда умирает последний передатчик, а это случается и тогда, когда задача **паникует**, не отправив ничего (§23.1.1: паника потока не роняет остальных, но её `Sender` при этом уничтожается). По закрытию канала мы объявили бы работу успешно законченной, недосчитавшись файла и не заметив этого; со счётчиком видно, что `received < expected`, и можно честно сказать пользователю, сколько файлов не ответило.

Второй — **прогресс**. Пользователю нужно не только «готово», но и «сколько осталось»: пара `received`/`expected` — это готовая надпись «3 из 8» рядом со спиннером, а закрытие канала не даёт ничего, кроме однократного «всё».

Что канал говорит на самом деле, когда все ответы приняты, стоит проверить, а не предполагать, — приложение спрашивает его прямо в момент завершения:

```rust
            let tail = match self.rx.as_ref().unwrap().try_recv() {
                Ok(_) => "ещё сообщение",
                Err(mpsc::TryRecvError::Empty) => "Empty (отправители живы)",
                Err(mpsc::TryRecvError::Disconnected) => "Disconnected (отправителей нет)",
            };
```

**Прогон** — три файла разом: большой (33 МБ), маленький и несуществующий:

```text
$ z2_9.exe rust "../data/big1.txt;text.txt;nofile.txt"
кадр 1: запущено задач: 3
кадр 1: принят ответ 1 из 3
кадр 1: принят ответ 2 из 3
кадр 19: принят ответ 3 из 3
кадр 19: все ответы приняты; канал отвечает: Disconnected (отправителей нет)
```

Читается как расписание: маленький файл и несуществующий (ошибка чтения возвращается мгновенно) ответили **в том же кадре**, где запустились, — вот зачем цикл вычерпывания; большой файл ответил на кадре 19. Канал в этот момент действительно закрыт, то есть приём «канал закрылся — работа кончена» технически работал бы и здесь; неприменимо — именно блокирующее `for ... in rx`.

На экране (снимок после завершения) — результаты в порядке прихода, каждый со своим заголовком, и статус внизу:

```text
== text.txt: найдено 2
Затем пришёл Rust — и владение
Не доверяй — проверяй: rustc не спит.
== nofile.txt: ошибка — The system cannot find the file specified. (os error 2)
== ../data/big1.txt: найдено 400
строка 999: здесь спрятан Rust
...
готово: 3 файлов, строк 405 за 387.1669ms
```

405 строк — это 2 + 400 найденных плюс три строки-заголовка. И последнее: `self.pool = None` в конце опроса роняет пул, а его `Drop` (§25.2.3) проводит воркеров по протоколу — в консоли dev-сборки видно знакомое:

```text
ждём воркера 0
воркер 2: канал закрыт, завершаюсь
воркер 1: канал закрыт, завершаюсь
воркер 0: канал закрыт, завершаюсь
ждём воркера 1
ждём воркера 2
```

Пул уничтожается **после** приёма всех ответов, поэтому `join` внутри `Drop` не ждёт ни секунды — задачи давно готовы, и кадр не спотыкается.

**Ответ.** Многофайловый поиск = пул из §25.2 (path-зависимость `pargrep`) + один общий канал с сообщением `(String, Result<Vec<String>, String>)` + опрос в кадре, вычерпывающий **все** накопившиеся ответы, + `request_repaint` из каждой задачи. Конец работы определяется **счётом ответов** (`received == expected`), а закрытие канала (`TryRecvError::Disconnected`) оставлено страховкой. Приём «канал закрылся — работа кончена» из §25.2.4 не переносится сюда буквально потому, что там он реализован блокирующим `for (file, result) in rx`, а блокировать кадр нельзя — это возвращает заморозку чекпоинта 2. Даже в неблокирующем виде закрытие канала как единственный признак хуже счётчика по двум причинам: паника задачи убивает её передатчик, не отправив ответа (по закрытию канала мы объявили бы успех, недосчитавшись файла), и закрытие не даёт прогресса «3 из 8», который нужен интерфейсу. Прогон на трёх файлах: два ответа приняты в кадре 1, третий (33 МБ) — в кадре 19, «готово: 3 файлов, строк 405 за 387.1669ms»; в момент завершения канал отвечает `Disconnected` — то есть страховка и счётчик сработали согласованно.

Расплата — потеря информации: нет прогресса «3 из 8» и, главное, нет разницы между «все ответили» и «часть задач погибла, не ответив»: паника внутри задачи закрывает её клон передатчика молча, и приложение покажет «готово» с неполным списком. Счётчик эту разницу видит; поэтому в основном решении он основной, а закрытие канала — страховка на случай, если ответов уже не будет.
