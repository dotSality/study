## Часть 24.1. unsafe Rust

### Г24.Ч1.З1

**Условие.** Заведите переменную `let mut temp = 36.6_f64;`. Получите на неё два сырых указателя — `*const f64` (через `&raw const`) и `*mut f64` (через `&raw mut`). Напечатайте оба указателя через `{:?}`, затем в `unsafe`-блоке увеличьте значение через изменяющий указатель на 0.4 и прочитайте через константный. Убедитесь, что печатается 37.0 (форматируйте `{:.1}` — гл. 22).

**Решение.** Операторы сырого заимствования `&raw const` / `&raw mut` (§24.1.2) берут адрес *места* — переменной `temp` — и отдают его как сырой указатель, не создавая ссылки. Это важно: будь у нас `&temp` и `&mut temp` одновременно, borrow checker выдал бы E0502 (§15.2.2); сырые указатели живут вне этой бухгалтерии, и два «права доступа» на одну переменную здесь законны.

Обе строки с указателями — **безопасный код**: создание и передача сырого указателя ничего не нарушают, небезопасен только доступ (§24.1.2, «ключевая асимметрия»). Поэтому `unsafe` нужен ровно вокруг двух операций — записи через `pm` и чтения через `pc`. Файл `p1/u1_temp.rs`:

```rust
fn main() {
    let mut temp = 36.6_f64;

    let pc = &raw const temp; // *const f64 -- только читать
    let pm = &raw mut temp; // *mut f64 -- читать и писать

    println!("pc = {pc:?}");
    println!("pm = {pm:?}");

    // SAFETY: оба указателя взяты от живой локальной temp; она не
    // переезжает и жива до конца main, выравнивание даёт компилятор.
    // Ссылок на temp в это время не существует, поток один -- запись
    // и чтение упорядочены текстом программы.
    unsafe {
        *pm += 0.4;
        println!("temp = {:.1}", *pc);
    }
}
```

```
$ rustc --edition 2024 u1_temp.rs
$ ./u1_temp.exe
pc = 0x65501ff8a0
pm = 0x65501ff8a0
temp = 37.0
```

Адреса — представительный прогон (на вашей машине будут другими, как `%p` в §6.1.1), но **оба одинаковы**: `&raw const` и `&raw mut` смотрят на одно и то же место, различаясь только типом — то есть только тем, что ими разрешено делать. Написали через `pm` — прочитали через `pc`: перед нами обычный C-указатель из главы 6, просто в резервации.

Почему условие настаивает на `{:.1}`? Печать `{}` для этой же величины даёт `37`: `Display` у `f64` не дописывает нулевую дробную часть. А заодно — маленький сюрприз про вещественные числа: ни `36.6`, ни `0.4` в двоичном `f64` точно не представимы (`{:.20}` показывает `36.60000000000000142109` и `0.40000000000000002220`), но их сумма округлилась **ровно** к 37.0 — проверка `sum == 37.0` даёт `true`. Так что `{:.1}` здесь не маскирует погрешность, а просто выбирает форму записи.

**Ответ.** Указатели получаются операторами `let pc = &raw const temp;` и `let pm = &raw mut temp;` — обе операции безопасны и `unsafe` не требуют. Печать `{:?}` даёт один и тот же адрес для обоих (значение адреса машинозависимо). Разыменование — только внутри `unsafe`-блока: `*pm += 0.4;` и чтение `*pc`, которое с форматом `{:.1}` печатает `temp = 37.0`. Блок обнимает ровно две опасные операции и снабжён `SAFETY`-комментарием: указатели взяты от живой невыехавшей переменной, других ссылок на неё нет, поток один.

### Г24.Ч1.З2

**Условие.** Дан массив `let a = [1.5_f64, 2.5, 3.5, 4.5];`. Через `as_ptr()` и `add` напечатайте первый и последний элементы, затем вычислите шаг адреса между соседними элементами (переводите указатели в `usize` оператором `as`). Какое число вы ожидаете и почему (`double` в C и `f64` в Rust занимают 8 байт — таблица соответствий §14.2.2)?

**Решение.** `as_ptr()` у массива даёт `*const f64` на первый элемент — тот самый «массив распадается в указатель на нулевой элемент» из §6.2.1, только записанный явно. Последний элемент — `p.add(len - 1)`: `add` шагает **элементами**, а не байтами (§24.1.2, полное соответствие `p + i` из §6.2.2).

Шаг адреса меряем переводом указателей в `usize` оператором `as` — это чистая арифметика над числом, разыменования нет. Файл `p1/u2_step.rs`:

```rust
fn main() {
    let a = [1.5_f64, 2.5, 3.5, 4.5];
    let p = a.as_ptr();
    let len = a.len();

    // SAFETY: p получен от живого массива a из len элементов;
    // индексы 0 и len-1 лежат внутри этого выделения.
    unsafe {
        println!("first = {}", *p);
        println!("last  = {}", *p.add(len - 1));
    }

    // SAFETY: p.add(1) -- второй элемент, внутри массива;
    // здесь указатель только переводится в число, без чтения.
    let addr0 = p as usize;
    let addr1 = unsafe { p.add(1) } as usize;
    println!("step = {} bytes", addr1 - addr0);
    println!("size_of::<f64>() = {}", size_of::<f64>());
}
```

```
$ rustc --edition 2024 u2_step.rs
$ ./u2_step.exe
first = 1.5
last  = 4.5
step = 8 bytes
size_of::<f64>() = 8
```

Ожидание было именно таким. `f64` — 64-битное вещественное число, то есть 8 байт; таблица соответствий §14.2.2 ставит ему в пару `double` из C, а §2.1.2 подтверждал, что `double` на нашей платформе — те же 8 байт. Арифметика указателей в обоих языках шагает в размер элемента, поэтому разность соседних адресов обязана равняться `size_of::<f64>()` — программа печатает оба числа рядом, чтобы это было видно без веры на слово.

Обратите внимание на второй `unsafe`-блок: он нужен **не** для `as usize`, а для самого `add`. Контракт `add` (R9) требует, чтобы и исходный, и результирующий указатель оставались внутри одного выделения, — за это отвечаем мы, даже когда читать не собираемся (§24.1.2: «сам `add` за границу уже UB»).

**Ответ.** `first = 1.5`, `last = 4.5`, шаг адреса — **8 байт**. Ожидать следовало именно 8: `f64` занимает 8 байт (`size_of::<f64>()` печатает то же число), в C ему соответствует `double` той же ширины (§14.2.2, §2.1.2), а `add(1)` в Rust — как `p + 1` в C — сдвигает адрес на *размер элемента*, а не на байт.

### Г24.Ч1.З3

**Условие.** Объявите `union Word { w: u32, bytes: [u8; 4] }`. Запишите `w: 0x01020304`, прочитайте в `unsafe` поле `bytes` и напечатайте его через `{:?}`. Сверьте результат с порядком байтов из §8.2.2 и §10.2.1 (little-endian). Почему чтение поля требует `unsafe`, а инициализация — нет?

**Решение.** `union` в Rust — прямой родственник объединения из §8.2.2: все участники лежат по одному адресу, размер — по самому большому. Здесь оба участника ровно по 4 байта, поэтому `size_of::<Word>()` обязан дать 4. Файл `p1/u3_union.rs`:

```rust
union Word {
    w: u32,
    bytes: [u8; 4],
}

fn main() {
    let x = Word { w: 0x01020304 }; // инициализация -- safe

    // SAFETY: последним записан участник w, а [u8; 4] занимает те же
    // 4 байта; любая комбинация битов -- валидное значение [u8; 4],
    // поэтому прочитанное не может оказаться недопустимым значением.
    let b = unsafe { x.bytes };

    println!("bytes = {b:?}");
    println!("size_of::<Word>() = {}", size_of::<Word>());
}
```

```
$ rustc --edition 2024 u3_union.rs
$ ./u3_union.exe
bytes = [4, 3, 2, 1]
size_of::<Word>() = 4
```

Порядок совпал с §8.2.2 и §10.2.1: на x86-64 — **little-endian**, младший байт по младшему адресу. Число `0x01020304` записано так: `04` (младший) по смещению 0, затем `03`, `02`, и `01` (старший) по смещению 3. Именно поэтому «сериализовать структуру побайтово и прочитать её на другой машине» из §10.2.3 — плохой протокол: порядок байтов не переносится.

**Почему инициализация безопасна, а чтение — нет.** Записывая `Word { w: ... }`, мы кладём в память конкретный, полностью инициализированный `u32` — компилятор точно знает, что происходит, никаких обязательств на нас не ложится. А при чтении поля компилятор **не отслеживает, какой участник актуален** (§24.1.3): единственный, кто знает, что последним писали `w`, — программист. Отсюда и формулировка E0133 для union-полей: «the field may not be properly initialized». Опасность не теоретическая: прочитай мы через union поле типа `bool` или `char`, там мог бы оказаться битовый узор, недопустимый для этого типа, — а невалидное значение это уже UB (R7, «Behavior considered undefined»). Наш случай безопасен именно потому, что у `[u8; 4]` недопустимых битовых узоров не бывает — это и записано в `SAFETY`-комментарии.

**Ответ.** `bytes = [4, 3, 2, 1]`, `size_of::<Word>() = 4`. Порядок обратный записи числа `0x01020304`, потому что платформа little-endian (§8.2.2, §10.2.1): младший байт `04` лежит по младшему адресу. Инициализация `union` безопасна — программист явно указывает, какой участник записывается, и значение полностью определено; чтение поля требует `unsafe`, потому что компилятор не знает, какой участник актуален, и не может гарантировать, что байты образуют допустимое значение читаемого типа. Ответственность за «читаю то, что писал» — на программисте.

**Вариант 2 (без union и без unsafe).** Ту же таблицу байтов даёт метод `to_le_bytes` (R9), а обратное преобразование — `from_le_bytes`. Файл `p1/u3_bytes.rs`:

```rust
fn main() {
    let w: u32 = 0x01020304;

    let b = w.to_le_bytes();
    println!("to_le_bytes = {b:?}");
    println!("to_be_bytes = {:?}", w.to_be_bytes());
    println!("from_le_bytes = {:#010x}", u32::from_le_bytes(b));
}
```

```
$ rustc --edition 2024 u3_bytes.rs
$ ./u3_bytes.exe
to_le_bytes = [4, 3, 2, 1]
to_be_bytes = [1, 2, 3, 4]
from_le_bytes = 0x01020304
```

*Сравнение.* Результат совпадает с union-версией, но кода без `unsafe` вообще, а порядок байтов теперь **выбирается явно**, а не наследуется от машины: `to_le_bytes` даст `[4, 3, 2, 1]` и на big-endian платформе — это то, чего не хватало сериализации из §10.2.3. Значит, для задач «разложить число на байты» и «записать число в файл или в сеть» правильный инструмент — именно эта пара, а не union. У union остаётся своя ниша, ради которой он в языке и оставлен (§24.1.3): FFI, где C-сторона прислала настоящий `union`, и битовая хирургия над чужой раскладкой, которую нельзя описать иначе.

### Г24.Ч1.З4

**Условие.** Программа не компилируется:

```rust
fn main() {
    let x = 7;
    let p = &x as *const i32;
    println!("{}", *p);
}
```

Назовите код ошибки не компилируя, объясните причину и почините двумя способами: (а) добавив минимальный `unsafe`-блок с `SAFETY`-комментарием; (б) вовсе избавившись от сырого указателя. В каком случае какой вариант уместен?

**Решение.** Код ошибки называется, не запуская компилятор: разыменование сырого указателя — сверхспособность №1 из списка §24.1.1, а любая сверхспособность вне `unsafe`-контекста даёт **E0133**. Это единственный код на все пять дверей.

Проверяем себя (файл `p1/u4_err.rs`):

```
$ rustc --edition 2024 u4_err.rs
error[E0133]: dereference of raw pointer is unsafe and requires unsafe block
 --> u4_err.rs:5:20
  |
5 |     println!("{}", *p);
  |                    ^^ dereference of raw pointer
  |
  = note: raw pointers may be null, dangling or unaligned; they can violate aliasing rules and cause data races: all of these are undefined behavior

error: aborting due to 1 previous error
```

Причина — в note: указатель может быть нулевым, висячим, невыровненным, может нарушать правила алиасинга и участвовать в гонке данных, и всё это UB. Компилятор не в состоянии проверить ни одного из этих условий, поэтому требует подпись — `unsafe`-блок.

**Починка (а) — минимальный блок с обоснованием.** Файл `p1/u4_fix_unsafe.rs`:

```rust
fn main() {
    let x = 7;
    let p = &x as *const i32;
    // SAFETY: p получен из ссылки на живую локальную x, которая жива
    // до конца main; выравнивание и инициализация обеспечены самим
    // объявлением let x = 7. Значит, чтение допустимо.
    println!("{}", unsafe { *p });
}
```

Обратите внимание, где стоит блок: он обнимает **одно выражение** `*p`, а не всю строку с `println!`. Это правило гигиены §24.1.3: чем уже блок, тем очевиднее, какая именно операция потребовала пропуска.

**Починка (б) — сырой указатель здесь вообще не нужен.** Файл `p1/u4_fix_safe.rs`:

```rust
fn main() {
    let x = 7;
    let r = &x; // обычная ссылка: разыменование безопасно
    println!("{}", *r);
}
```

```
$ ./u4_fix_unsafe.exe
7
$ ./u4_fix_safe.exe
7
```

Обе программы печатают `7`. Разница не в выводе, а в том, кто отвечает за корректность: в (а) — мы, комментарием; в (б) — компилятор, лайфтаймами.

**Когда какой вариант уместен.** Вариант (б) — по умолчанию: данные свои, время жизни известно компилятору, ссылка выражает ровно то, что нужно. Правило §24.1.3 п. 5 прямо запрещает брать `unsafe` в спорах с borrow checker'ом: сперва ищем безопасную формулировку. Вариант (а) остаётся там, где ссылку сделать **нельзя или не из чего**: указатель пришёл из C через FFI (часть 24.2), получен из `Box::into_raw`, добыт арифметикой `add` внутри безопасной обёртки (Г24.Ч1.З8) или нужно намеренное «два писателя» (Г24.Ч1.З7). Иными словами, (а) — когда сырой указатель есть суть задачи, а не способ обойти проверку.

**Ответ.** Ошибка — **E0133**, «dereference of raw pointer is unsafe and requires unsafe block»: разыменование сырого указателя — одна из пяти операций, требующих `unsafe`-контекста, потому что компилятор не может проверить ни живость, ни выравнивание, ни отсутствие алиасинга и гонок. Починка (а): обернуть **только** `*p` в `unsafe { }` и написать `SAFETY`-комментарий («p взят из ссылки на живую локальную `x`»). Починка (б): заменить сырой указатель ссылкой `let r = &x;` — тогда `*r` безопасно. Обе печатают `7`. По умолчанию правилен (б) — unsafe не должен появляться там, где безопасная формулировка существует; (а) уместен, когда сырой указатель приходит извне (FFI, `Box::into_raw`) или является сутью задачи.

### Г24.Ч1.З5

**Условие.** Программа не компилируется (издание 2024):

```rust
static mut TOTAL: i64 = 0;

fn main() {
    unsafe {
        TOTAL += 10;
        println!("итог: {}", TOTAL);
    }
}
```

Объясните, на какую строку и почему ругается компилятор (подсказка: как макрос `println!` принимает аргументы), и почините программу копией значения. Каким безопасным типом из главы 23 стоило бы заменить `static mut` в многопоточной программе?

**Решение.** Программа выглядит безупречно: доступ к `static mut` — сверхспособность №3, `unsafe`-блок на месте. Но издание 2024 закрутило гайки сильнее (§24.1.3): **ссылку на изменяемый статик брать нельзя вовсе, даже разделяемую**. Файл `p1/u5_err.rs`:

```
$ rustc --edition 2024 u5_err.rs
error: creating a shared reference to mutable static
 --> u5_err.rs:7:30
  |
7 |         println!("итог: {}", TOTAL);
  |                              ^^^^^ shared reference to mutable static
  |
  = note: shared references to mutable statics are dangerous; it's undefined behavior if the static is mutated or if a mutable reference is created for it while the shared reference lives
  = note: for more information, see <https://doc.rust-lang.org/edition-guide/rust-2024/static-mut-references.html>
  = note: `#[deny(static_mut_refs)]` (part of `#[deny(rust_2024_compatibility)]`) on by default

error: aborting due to 1 previous error
```

Ругань — **на строку 7**, на `println!`, а не на `TOTAL += 10`. Вот в чём подсказка условия: макросы печати берут аргументы **по ссылке** (в главе 15 мы этому радовались — печать не забирала владение; здесь та же механика оборачивается ошибкой). Строка `TOTAL += 10` ссылки не создаёт: это чтение-изменение-запись самого места, разрешённое внутри `unsafe`. А `println!("{}", TOTAL)` под капотом делает `&TOTAL` — разделяемую ссылку на изменяемый статик, которую линт `static_mut_refs` запрещает по умолчанию (`deny`, а не `warn`). Логика запрета в первой note: пока живёт разделяемая ссылка, любое изменение статика — UB, и уследить за этим в программе с глобалью невозможно.

**Починка копией.** Забираем значение, а не ссылку: `i64` — `Copy`-тип, копия ничем не связана со статиком. Файл `p1/u5_fix.rs`:

```rust
static mut TOTAL: i64 = 0;

fn main() {
    // SAFETY: программа однопоточная, других обращений к TOTAL
    // в это время не существует; наружу уходит копия числа,
    // ссылки на статик не создаётся.
    let now = unsafe {
        TOTAL += 10;
        TOTAL // i64: Copy -- забираем значение, не ссылку
    };
    println!("итог: {now}");
}
```

```
$ rustc --edition 2024 u5_fix.rs
$ ./u5_fix.exe
итог: 10
```

`println!` теперь печатает локальную `now`, до статика ему дела нет — и `unsafe`-блок сжался до двух строк, где действительно есть чем рисковать. (Второй законный способ — `&raw const TOTAL` и чтение через сырой указатель; компилятор сам предлагает его в `help` из §24.1.3. Копия проще и честнее там, где значение маленькое и `Copy`.)

**Чем заменить `static mut` в многопоточной программе.** Ответ главы 23 — **`Mutex`** (§23.2.1): он даёт и изменяемость, и синхронизацию, а `Mutex::new` можно вызвать прямо в объявлении статика. Файл `p1/u5_mutex.rs`:

```rust
use std::sync::Mutex;
use std::thread;

static TOTAL: Mutex<i64> = Mutex::new(0); // ни одного unsafe во всей программе

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..1000 {
                    *TOTAL.lock().unwrap() += 10;
                }
            });
        }
    });

    println!("итог: {}", TOTAL.lock().unwrap());
}
```

```
$ rustc --edition 2024 u5_mutex.rs
$ ./u5_mutex.exe
итог: 40000
```

Четыре потока по тысяче прибавлений каждый — и **устойчивые** 40000 в каждом прогоне (два подряд дали один результат), никакого `unsafe`, никаких `SAFETY`-комментариев. Сравните с §23.2.2, где ровно этот же приём собирал счётчик из потоков: разница лишь в том, что здесь данные лежат в статике, а не передаются через `Arc`. Со `static mut` та же программа была бы гонкой данных — компилятор от неё не защищает, потому и требует `unsafe` на каждый доступ.

**Ответ.** Компилятор ругается на **строку с `println!`** (в исходном тексте — `println!("итог: {}", TOTAL);`), а не на `TOTAL += 10`: макросы форматирования принимают аргументы по ссылке, то есть создают `&TOTAL` — разделяемую ссылку на изменяемый статик, а издание 2024 это запрещает (линт `static_mut_refs`, уровень `deny`; сообщение — `error: creating a shared reference to mutable static`). Причина запрета: пока такая ссылка жива, любое изменение статика — UB. Починка: прочитать значение в локальную переменную внутри `unsafe`-блока (`let now = unsafe { TOTAL += 10; TOTAL };`) и печатать копию — `i64` реализует `Copy`, ссылка не создаётся; программа печатает `итог: 10`. В многопоточной программе `static mut` следует заменить на **`Mutex`** из §23.2.1 — например `static TOTAL: Mutex<i64> = Mutex::new(0);`: он даёт изменяемость через разделяемый доступ и синхронизацию, и `unsafe` исчезает из программы совсем.

### Г24.Ч1.З6

**Условие.** Найдите изъян в контракте и почините:

```rust
/// Возвращает элемент i (функция объявлена как safe).
fn get_unchecked_bad(v: &[i32], i: usize) -> i32 {
    unsafe { *v.as_ptr().add(i) }
}
```

Объясните, при каком вызове наступит UB и почему это нарушение правил §24.1.3. Предложите два честных варианта: safe-функцию с проверкой (что вернуть при неверном `i` — гл. 16?) и `unsafe fn` с документированным контрактом.

**Решение.** Изъян виден по одной строке сигнатуры: функция объявлена **safe**, а её корректность зависит от значения `i`, которое приходит **снаружи**. Никакой проверки внутри нет: `v.as_ptr().add(i)` шагает на `i` элементов от начала среза, и при `i >= v.len()` адрес уходит за выделение. UB наступает при любом таком вызове — причём уже на самой арифметике `add`, не дожидаясь чтения (контракт `add`, R9; §24.1.2).

Это ровно то, что §24.1.3 называет «худшим из двух миров»: пользователь не видит слова `unsafe`, не подозревает, что подписался под контрактом, — а контракт есть. Правило параграфа гласит: интерфейс объявляется safe только там, где инвариант обеспечивает **сама абстракция** — проверкой (`assert!` в `split_at_mut`), приватностью полей или дисциплиной модуля. Здесь не обеспечивает ничто.

Смотрим, как это выглядит вживую. Файл `p1/u6_bad.rs` — ⛔ программа собирается и работает, и в этом вся беда:

```rust
/// Возвращает элемент i (функция объявлена как safe).
fn get_unchecked_bad(v: &[i32], i: usize) -> i32 {
    unsafe { *v.as_ptr().add(i) }
}

fn main() {
    let v = [10, 20, 30];
    println!("i = 1: {}", get_unchecked_bad(&v, 1));
    println!("i = 7: {}", get_unchecked_bad(&v, 7)); // UB: за границей массива
}
```

```
$ rustc --edition 2024 u6_bad.rs
$ ./u6_bad.exe
i = 1: 20
i = 7: 32759
```

Ни ошибки, ни предупреждения, ни паники — программа напечатала соседний мусор со стека и вышла с кодом 0. Дежавю §13.1.3 в чистом виде: сравните с `v[7]`, который дал бы честную панику `index out of bounds` (§15.3.1). Число `32759` — с эталонной машины, у вас будет другое; на пяти прогонах подряд оно не менялось, что делает такую ошибку особенно коварной: «у меня работает».

**Miri видит то, чего не видит глаз.** Кладём ту же программу в cargo-пакет `p1/u6_miri` и запускаем интерпретатор (§24.1.2):

```
$ cargo +nightly miri run
i = 1: 20
error: Undefined Behavior: in-bounds pointer arithmetic failed: attempting to offset pointer by 28 bytes, but got alloc169 which is only 12 bytes from the end of the allocation
 --> src\main.rs:3:15
  |
3 |     unsafe { *v.as_ptr().add(i) }
  |               ^^^^^^^^^^^^^^^^^ Undefined Behavior occurred here
  |
help: alloc169 was allocated here:
 --> src\main.rs:7:9
  |
7 |     let v = [10, 20, 30];
  |         ^
```

Отчёт подтверждает обе вещи, о которых говорил §24.1.2. Во-первых, UB — **в арифметике**: «in-bounds pointer arithmetic failed», а не «чтение по плохому адресу»; байты сходятся — 7 × 4 = 28 при выделении в 12 байт. Во-вторых, Miri показывает место выделения, как Valgrind в §7.2.2.

**Два честных варианта.** Файл `p1/u6_fix.rs`:

```rust
/// Безопасный вариант: проверка внутри, «нет элемента» -- значением (гл. 16).
fn get_checked(v: &[i32], i: usize) -> Option<i32> {
    if i < v.len() {
        // SAFETY: i < v.len() проверено строкой выше, значит адрес
        // v.as_ptr().add(i) лежит внутри выделения среза; элементы
        // среза инициализированы и выровнены по построению.
        Some(unsafe { *v.as_ptr().add(i) })
    } else {
        None
    }
}

/// Честная unsafe-функция: проверки нет, контракт назван.
///
/// SAFETY: вызывающий обязан гарантировать `i < v.len()`.
unsafe fn get_unchecked(v: &[i32], i: usize) -> i32 {
    // SAFETY: контракт функции требует i < v.len(), значит адрес
    // внутри выделения; за это отвечает вызывающий.
    unsafe { *v.as_ptr().add(i) }
}

fn main() {
    let v = [10, 20, 30];

    println!("get_checked(1) = {:?}", get_checked(&v, 1));
    println!("get_checked(7) = {:?}", get_checked(&v, 7));

    // SAFETY: 2 < v.len() == 3 -- контракт выполнен здесь, на месте вызова.
    let last = unsafe { get_unchecked(&v, 2) };
    println!("get_unchecked(2) = {last}");
}
```

```
$ rustc --edition 2024 u6_fix.rs
$ ./u6_fix.exe
get_checked(1) = Some(20)
get_checked(7) = None
get_unchecked(2) = 30
```

Что вернуть при неверном `i` — подсказывает глава 16: **`Option<i32>`**, `None` вместо элемента (§16.2.3). Не паника и не «магическое» `-1`: отсутствие значения выражается типом, и вызывающий обязан его разобрать. Так устроен и штатный `slice::get` (R9).

Вторая функция — зеркальное решение: проверки нет ради скорости, зато сигнатура честно кричит `unsafe fn`, а документация называет контракт. Обратите внимание на два `SAFETY`-комментария разного назначения (§24.1.1): у **объявления** — что обязан обеспечить вызывающий; у **вызова** — почему обязательство выполнено. Именно так документирован `get_unchecked` в стандартной библиотеке (R9).

**Ответ.** UB наступит при любом вызове с `i >= v.len()` (в нашем прогоне `get_unchecked_bad(&v, 7)` напечатал мусор `32759` без единого предупреждения; Miri сообщает «in-bounds pointer arithmetic failed: attempting to offset pointer by 28 bytes, but got alloc169 which is only 12 bytes from the end of the allocation»). Нарушено главное правило §24.1.3: safe-интерфейс обязан сам обеспечивать инварианты, делающие unsafe-ядро корректным, — а здесь корректность зависит от аргумента вызывающего, который об этом даже не предупреждён. Два честных варианта: (1) safe-функция `fn get_checked(v: &[i32], i: usize) -> Option<i32>` — проверка `i < v.len()` внутри, при неверном `i` возвращается `None` (глава 16: отсутствие значения — это тип, а не паника и не спец-число); (2) `unsafe fn get_unchecked(v: &[i32], i: usize) -> i32` — без проверки, но с документированным контрактом «вызывающий гарантирует `i < v.len()`», который подтверждается `SAFETY`-комментарием на каждом месте вызова.

### Г24.Ч1.З7

**Условие.** Ниже два фрагмента. Первый не компилируется (E0499, §15.2.2), второй — компилируется и работает:

```rust
let r1 = &mut x; let r2 = &mut x; *r1 += 1; *r2 += 1; // ⛔
let p1 = &raw mut x; let p2 = &raw mut x; unsafe { *p1 += 1; *p2 += 1; } // ok
```

Объясните: почему для сырых указателей компилятор молчит; что взамен проверки обязан гарантировать программист; в каком параграфе главы 23 та же самая свобода (два писателя) становится гонкой данных.

**Решение.** Проверим оба фрагмента отдельными программами. Файл `p1/u7_err.rs` — ⛔:

```
$ rustc --edition 2024 u7_err.rs
error[E0499]: cannot borrow `x` as mutable more than once at a time
 --> u7_err.rs:5:14
  |
4 |     let r1 = &mut x;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut x;
  |              ^^^^^^ second mutable borrow occurs here
6 |     *r1 += 1;
  |     -------- first borrow later used here

error: aborting due to 1 previous error
```

Файл `p1/u7_raw.rs` — та же логика сырыми указателями:

```rust
fn main() {
    let mut x = 1;
    let p1 = &raw mut x;
    let p2 = &raw mut x;

    // SAFETY: оба указателя ведут на живую локальную x; поток один,
    // записи идут строго по очереди и не перекрываются во времени,
    // ссылок на x в это время не существует.
    unsafe {
        *p1 += 1;
        *p2 += 1;
        println!("x = {}", *p1);
    }
}
```

```
$ rustc --edition 2024 u7_raw.rs
$ ./u7_raw.exe
x = 3
```

**Почему компилятор молчит.** Правило «читатели XOR писатель» (§15.2.2) — это правило про **ссылки**. Borrow checker отслеживает время жизни ссылок и запрещает второе изменяющее заимствование, пока живо первое; на этом стоит вся система гарантий. Сырой указатель ссылкой не является: его время жизни не отслеживается, алиасинг не проверяется, и в таблице §24.1.2 напротив строки «алиасинг двух писателей» у сырых указателей стоит «разрешён». Проверять там нечего — компилятор и не проверяет. Это не поблажка, а честное разделение: `unsafe` не отключает borrow checker, просто сырые указатели изначально вне его юрисдикции.

**Что обязан гарантировать программист.** Ровно то, что перестал проверять компилятор, — и список известен по note из §24.1.2: указатель не null, не висячий, выровнен, целевые данные инициализированы, конфликтующие доступы не пересекаются во времени и через них не возникает гонки. В нашем случае доказательство умещается в три строки `SAFETY`: `x` жива всю функцию, поток один, записи идут по очереди. Правило XOR никуда не делось — оно стало **нашим обязательством** вместо компиляторского.

**Где та же свобода становится гонкой данных.** В §23.1.2. Там замыкания двух потоков пытались одолжить одну переменную изменяемо — и получили тот же самый **E0499**, только через захваты замыканий; глава прямо подчёркивает, что это не новый многопоточный запрет, а «второй `&mut` при живом первом» из §15.2.2. Разница с нашим случаем ровно одна: там доступы шли **из разных потоков без синхронизации**, то есть выполнялось третье условие гонки данных из §13.1.4 — и запрет спасал от UB. Стоит унести пару сырых указателей на одну переменную в два потока — и компилятор не скажет ни слова, а мы получим `race.c` из §13.1.4 обратно, теперь уже на Rust. Именно это §23.2.4 называет границей бесстрашия: система типов ловит гонки только там, где данные проходят через ссылки и маркеры `Send`/`Sync`.

**Ответ.** Для сырых указателей компилятор молчит потому, что правило «читатели XOR писатель» — правило про **ссылки**: borrow checker следит за временем жизни ссылок, а у сырых указателей оно не отслеживается и алиасинг двух «писателей» разрешён по определению типа (таблица §24.1.2). Взамен программист обязан гарантировать всё, что перестал проверять компилятор: указатель не null, не висячий, выровнен, данные инициализированы, конфликтующие доступы не пересекаются во времени и не образуют гонки, — и записать это доказательство в `SAFETY`-комментарии. Второй фрагмент печатает `x = 3`. Та же свобода превращается в гонку данных в **§23.1.2**: там два потока пытались одолжить одну переменную изменяемо и получили тот самый E0499 (через захваты замыканий), потому что при доступе из разных потоков без синхронизации выполняется третье условие гонки данных из §13.1.4; сырые указатели этой проверки не проходят вовсе, и ответственность целиком на программисте (§23.2.4 — «границы бесстрашия»).

### Г24.Ч1.З8

**Условие.** Напишите safe-функцию `fn ends(v: &[i32]) -> Option<(i32, i32)>`, возвращающую первый и последний элементы среза, — внутри прочитайте их *только* через `as_ptr()` и `add` в `unsafe`-блоке (учебное ограничение). Пустой срез → `None`. Обоснуйте `SAFETY`-комментарием, почему обе операции в границах. Напишите три проверки в `main` (или тестами, гл. 20): пустой срез, один элемент, много элементов.

**Решение.** Задача — построить маленькую безопасную абстракцию по канону §24.1.3: снаружи обычная функция, внутри `unsafe`-ядро, а инвариант обеспечивает сама функция. Инвариант здесь один: **срез непуст**. Проверив это в начале, мы получаем право на оба чтения — по индексам `0` и `len - 1`, которые при `len >= 1` заведомо внутри выделения.

Файл `p1/u8_ends.rs`:

```rust
fn ends(v: &[i32]) -> Option<(i32, i32)> {
    let len = v.len();
    if len == 0 {
        return None; // пустой срез -- читать нечего
    }
    let p = v.as_ptr();

    // SAFETY: len > 0 проверено выше, поэтому индексы 0 и len-1
    // лежат внутри одного выделения, из которого получен p;
    // элементы среза инициализированы и выровнены, а срез жив
    // всё время работы функции (за это отвечает заимствование &[i32]).
    unsafe { Some((*p, *p.add(len - 1))) }
}

fn main() {
    let empty: [i32; 0] = [];
    println!("[]              -> {:?}", ends(&empty));
    println!("[7]             -> {:?}", ends(&[7]));
    println!("[1, 2, 3, 4, 5] -> {:?}", ends(&[1, 2, 3, 4, 5]));
}
```

```
$ rustc --edition 2024 u8_ends.rs
$ ./u8_ends.exe
[]              -> None
[7]             -> Some((7, 7))
[1, 2, 3, 4, 5] -> Some((1, 5))
```

Три проверки покрывают все интересные случаи. Пустой срез — ранний выход `None`, до всякого `unsafe`. Один элемент — граница, где первый и последний совпадают: `len - 1 == 0`, оба чтения по одному адресу, ответ `Some((7, 7))`. Много элементов — обычный случай.

Разберём `SAFETY`-обоснование по пунктам, потому что в нём вся ценность задания:

- **указатель валиден** — `p` получен из `v.as_ptr()`, то есть из живого среза; заимствование `&[i32]` гарантирует, что данные живы всё время работы функции (это и есть то, чего нет у сырых указателей из §24.1.2 и что здесь даёт нам ссылка на входе);
- **обе арифметики в границах** — `add(len - 1)` при `len >= 1` даёт индекс от 0 до `len - 1`, ни разу не выходя за выделение; ранний выход отсёк единственный случай, где `len - 1` ушло бы в переполнение `usize` (при `len == 0` это `usize::MAX`);
- **значения валидны** — элементы среза инициализированы и выровнены по построению `[i32]`;
- **алиасинга нет** — мы только читаем и не создаём ни одной ссылки внутрь.

Порядок в коде принципиален: проверка **до** взятия указателя и до арифметики. Поменяй мы местами `add` и `if`, обоснование рухнуло бы — `add` за границу уже UB (§24.1.2).

Заодно проверим себя интерпретатором: тот же код в пакете `p1/u8_miri` под Miri отрабатывает молча —

```
$ cargo +nightly miri run
[]              -> None
[7]             -> Some((7, 7))
[1, 2, 3, 4, 5] -> Some((1, 5))
```

— ни одного диагноза, в отличие от Г24.Ч1.З6. Оговорка §24.1.2 в силе: молчание Miri не доказательство корректности, оно лишь означает «на этих входах UB не исполнилось». Доказательство — `SAFETY`-комментарий выше.

**Ответ.** Функция сначала проверяет `v.len() == 0` и возвращает `None`, а затем — в одном `unsafe`-блоке — читает `*p` и `*p.add(len - 1)`, где `p = v.as_ptr()`. Обоснование: заимствование `&[i32]` гарантирует живость данных, проверка `len > 0` делает индексы `0` и `len - 1` заведомо внутренними (и заодно защищает `len - 1` от переполнения `usize`), элементы среза инициализированы и выровнены, ссылок внутрь не создаётся. Три проверки печатают `None` для пустого среза, `Some((7, 7))` для одноэлементного (первый и последний совпадают) и `Some((1, 5))` для `[1, 2, 3, 4, 5]`.

**Вариант 2 (без единого unsafe, проверки — тестами).** Учебное ограничение снято: `first()` и `last()` из стандартной библиотеки возвращают `Option<&i32>` (R9), а `match` по паре разбирает оба случая сразу. Файл `p1/u8_safe.rs`:

```rust
fn ends(v: &[i32]) -> Option<(i32, i32)> {
    match (v.first(), v.last()) {
        (Some(&a), Some(&b)) => Some((a, b)),
        _ => None, // пустой срез: first() и last() дали None
    }
}
```

Проверки оформлены тестами (гл. 20) в том же файле:

```rust
#[cfg(test)]

    use super::ends;

    #[test]
    fn empty_slice() {
        assert_eq!(ends(&[]), None);
    }

    #[test]
    fn one_element() {
        assert_eq!(ends(&[7]), Some((7, 7)));
    }

    #[test]
    fn many_elements() {
        assert_eq!(ends(&[1, 2, 3, 4, 5]), Some((1, 5)));
    }
}
```

```

test tests::many_elements ... ok

```

*Сравнение.* Результаты совпадают, но обоснования корректности не нужно вовсе: `first`/`last` сами возвращают `Option`, и пустой случай разбирается образцом, а не проверкой длины. Именно этот вариант следует писать в жизни — правило §24.1.3 п. 5 («unsafe — последний довод») здесь действует в полную силу, а `unsafe`-версия оправдана только учебным ограничением задания. Обратная сторона: сопоставление с образцом по паре `Option`ов заставляет описывать невозможный случай («первый есть, последнего нет») — его закрывает ветка `_`. Порядок строк `test ... ok` меняется от прогона к прогону (тесты идут в потоках, §23.1.1), устойчива итоговая строка `test result: ok. 3 passed`.

### Г24.Ч1.З9

**Условие.** На базе `MyCell` из §24.1.3 постройте `struct HitCounter { hits: MyCell<u32> }` с методами `fn hit(&self)` (увеличить) и `fn total(&self) -> u32`. Продемонстрируйте подсчёт через разделяемую ссылку `&HitCounter` у двух «читателей» (две функции, принимающие `&HitCounter`). Затем объясните письменно: почему для `HitCounter` **нельзя** писать `unsafe impl Sync` (что произойдёт при `set` из двух потоков — §23.2.2) и какой готовый тип главы 23 решает ту же задачу честно.

**Решение.** `MyCell` из §24.1.3 берём дословно и надстраиваем счётчик. Ключевое в задании — сигнатуры: `hit(&self)` и `total(&self)` принимают **разделяемую** ссылку, то есть счётчик изменяется через `&HitCounter`. Обычному полю `u32` такое запрещено (§15.2.2: изменять можно только через `&mut`), а `MyCell` умеет — за счёт `UnsafeCell` внутри. Файл `p1/u9_hits.rs`:

```rust
use std::cell::UnsafeCell;

struct MyCell<T> {
    value: UnsafeCell<T>,
}

impl<T: Copy> MyCell<T> {
    fn new(value: T) -> Self {
        MyCell { value: UnsafeCell::new(value) }
    }

    fn get(&self) -> T {
        // SAFETY: MyCell не выдаёт наружу ни одной ссылки внутрь,
        // а T: Copy -- мы возвращаем копию, не ссылку.
        unsafe { *self.value.get() }
    }

    fn set(&self, value: T) {
        // SAFETY: см. get -- ссылок внутрь не существует,
        // конфликт записи с чтением невозможен (один поток).
        unsafe { *self.value.get() = value; }
    }
}

struct HitCounter {
    hits: MyCell<u32>,
}

impl HitCounter {
    fn new() -> Self {
        HitCounter { hits: MyCell::new(0) }
    }

    fn hit(&self) {
        // читаем копию, увеличиваем, кладём назад -- всё через &self
        self.hits.set(self.hits.get() + 1);
    }

    fn total(&self) -> u32 {
        self.hits.get()
    }
}

// два "читателя": обе функции берут счётчик по разделяемой ссылке
fn render_page(c: &HitCounter) {
    c.hit();
    c.hit();
}

fn render_sidebar(c: &HitCounter) {
    c.hit();
}

fn main() {
    let counter = HitCounter::new();
    println!("start          = {}", counter.total());

    render_page(&counter);
    println!("after page     = {}", counter.total());

    render_sidebar(&counter);
    println!("after sidebar  = {}", counter.total());
}
```

```
$ rustc --edition 2024 u9_hits.rs
$ ./u9_hits.exe
start          = 0
after page     = 2
after sidebar  = 3
```

Обе функции получили `&HitCounter` — ни одна не может ни забрать владение, ни объявить себя единственным писателем, — и всё же счётчик вырос до 3. Это и есть внутренняя изменяемость: `HitCounter` выглядит снаружи неизменяемым, а внутри ведёт учёт. Ровно так работает `Rc` (§22.1.4), считая владельцев через разделяемые ручки.

Заметьте, чего в этом коде нет: слова `unsafe` за пределами трёх строк `MyCell`. Инвариант держит сам тип — наружу не выходит ни одной ссылки внутрь ячейки, только копии `u32`. Клиенту `HitCounter` не нужно ни знать про `UnsafeCell`, ни писать `SAFETY`-комментарии.

**Почему `unsafe impl Sync` для `HitCounter` писать нельзя.** `Sync` означает «на этот тип можно одновременно смотреть из нескольких потоков через `&T`» (§23.2.3). Наш `hit()` — это последовательность «прочитать копию → прибавить единицу → записать обратно», то есть классический `counter++` из §13.1.4, а вовсе не одна неделимая операция. Два потока, вызвавшие `hit()` через `&HitCounter`, могут прочитать одно и то же значение и записать одно и то же — часть работы испарится; хуже того, конфликтующие доступы к одной памяти без синхронизации — это **гонка данных**, а гонка данных — UB (§13.1.4, R7). Подпись `unsafe impl Sync` была бы ложным обещанием: мы утверждали бы то, что заведомо неверно, — тот самый «`unsafe impl` чтобы скомпилилось» из списка ошибок §24.1.3.

И компилятор действительно останавливает нас без такой подписи. Файл `p1/u9_sync_err.rs` — ⛔ те же типы плюс попытка раздать счётчик двум потокам через `thread::scope` (§23.1.2):

```

Корень назван точно: **`UnsafeCell<T>` явно отказывается от `Sync`** (R9), и всё, что построено на внутренней изменяемости — `Cell`, `RefCell`, наш `MyCell`, — наследует этот отказ. Тот же механизм, что отказывал `Rc` в §23.2.2, — только там виновником было поле счётчика.

**Готовый тип, решающий задачу честно, — `Mutex<u32>`** (§23.2.1). Он делает `hit()` неделимым: пока замок у одного потока, второй ждёт. Файл `p1/u9_mutex.rs` — тот же `HitCounter`, но с `Mutex` внутри:

```rust
use std::sync::Mutex;
use std::thread;

struct HitCounter {
    hits: Mutex<u32>,
}

impl HitCounter {
    fn new() -> Self {
        HitCounter { hits: Mutex::new(0) }
    }

    fn hit(&self) {
        *self.hits.lock().unwrap() += 1;
    }

    fn total(&self) -> u32 {
        *self.hits.lock().unwrap()
    }
}

fn main() {
    let counter = HitCounter::new();

    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..1000 {
                    counter.hit();
                }
            });
        }
    });

    println!("total = {}", counter.total());
}
```

```
$ rustc --edition 2024 u9_mutex.rs
$ ./u9_mutex.exe

```

Четыре потока по тысяче — и устойчивые 4000. Сигнатуры методов не изменились (`hit(&self)`, `total(&self)`): `Mutex` — та же внутренняя изменяемость, только с очередью вместо честного слова. И `Sync` он получает не подписью, а по праву: `Mutex<T>` реализует `Sync` при `T: Send`, и это уже гарантия стандартной библиотеки (R9), а не наше обещание.

**Ответ.** `HitCounter` строится как `struct HitCounter { hits: MyCell<u32> }`; `hit(&self)` делает `self.hits.set(self.hits.get() + 1)`, `total(&self)` возвращает `self.hits.get()`. Две функции, принимающие `&HitCounter`, вместе доводят счётчик до 3 (`start = 0`, `after page = 2`, `after sidebar = 3`) — изменение идёт через разделяемую ссылку, потому что `MyCell` стоит на `UnsafeCell`. Писать `unsafe impl Sync for HitCounter` **нельзя**: `hit()` — это неатомарное «прочитал → прибавил → записал», и два потока, вызвав его одновременно через `&HitCounter`, устроят гонку данных (потерянные инкременты в лучшем случае, UB — по определению §13.1.4); подпись `unsafe impl` была бы обещанием того, чего тип не обеспечивает. Без такой подписи компилятор отказывает сам: E0277 «`UnsafeCell<u32>` cannot be shared between threads safely» — `UnsafeCell` не `Sync`, значит не `Sync` и `MyCell`, и `HitCounter`, а `&HitCounter` не `Send` (§23.2.3). Честное решение той же задачи — **`Mutex<u32>`** из §23.2.1: сигнатуры методов те же, `hit()` становится неделимым, четыре потока по 1000 инкрементов дают устойчивые 4000, а `Sync` у `Mutex<T>` — гарантия стандартной библиотеки, а не наша подпись.

## Часть 24.2. FFI: мост между C и Rust

### Г24.Ч2.З1

**Условие.** Объявите в `unsafe extern "C"`-блоке две функции стандартной библиотеки C: `sqrt(x: c_double) -> c_double` (из `<math.h>`) и `labs(x: c_long) -> c_long` (из `<stdlib.h>`). Первую пометьте `safe`, вторую тоже — и обоснуйте комментарием, почему обе пометки честны. Напечатайте `sqrt(2.0)` и `labs(-42)`. Каким Rust-типам соответствуют `c_double` и `c_long` на нашей платформе (§2.1.2, §14.2.2)?

**Решение.** Обе функции живут в стандартной библиотеке C, которая прилинкована к каждой Rust-программе (§24.2.1), — значит, хватит объявления, никаких `-L` и `#[link]`. Типы берём из `std::ffi`: `c_double` для `double`, `c_long` для `long`. Файл `p2/f1_libm.rs`:

```rust
use std::ffi::{c_double, c_long};

unsafe extern "C" {
    // SAFETY: sqrt определена для любого double: у отрицательного
    // аргумента результат NaN (доменная ошибка), а не UB; указателей
    // и памяти функция не касается -- сломать её нечем.
    safe fn sqrt(x: c_double) -> c_double;

    // SAFETY: labs -- чистая арифметика над числом, без указателей.
    // Единственная точка внимания -- c_long::MIN (см. решение).
    safe fn labs(x: c_long) -> c_long;
}

fn main() {
    println!("sqrt(2.0)  = {}", sqrt(2.0));
    println!("labs(-42)  = {}", labs(-42));

    // граничные значения -- проверяем обоснование пометок
    println!("sqrt(-1.0) = {}", sqrt(-1.0));
    println!("sqrt(0.0)  = {}", sqrt(0.0));

    println!("size_of::<c_double>() = {}", size_of::<c_double>());
    println!("size_of::<c_long>()   = {}", size_of::<c_long>());
}
```

```
$ rustc --edition 2024 f1_libm.rs
$ ./f1_libm.exe
sqrt(2.0)  = 1.4142135623730951
labs(-42)  = 42
sqrt(-1.0) = NaN
sqrt(0.0)  = 0
size_of::<c_double>() = 8
size_of::<c_long>()   = 4
```

Ни одного `unsafe`-блока в `main` — пометка `safe` сняла пропуск на вызов (сам блок объявлений при этом обязан быть `unsafe extern`, издание 2024).

**Чем обоснована пометка `safe`.** Квалификатор — заявление «эту функцию не сломать никакими аргументами» (§24.2.1). Для `sqrt` это правда без оговорок: у отрицательного аргумента результат — `NaN` (наш прогон печатает именно `NaN`), это доменная ошибка, а не UB; функция не принимает указателей, не пишет в память вызывающего и не зависит от внешнего состояния. Любое значение `f64` — законный вход.

Для `labs` обоснование почти такое же — чистая арифметика, ни указателей, ни памяти, — но с одной оговоркой, которую честнее назвать вслух. Стандарт C (C5, §7.24.6.1) пишет: «The abs, labs, and llabs functions compute the absolute value of an integer j. **If the result cannot be represented, the behavior is undefined**». А модуль `c_long::MIN` не представим в `c_long`: диапазон несимметричен (§2.1.2). То есть на одном-единственном входе `labs` формально нарушает обещание «безвредна при любых аргументах». Файл `p2/f1_labs_min.rs` показывает, что делает наша реализация:

```
$ rustc --edition 2024 f1_labs_min.rs
$ ./f1_labs_min.exe
c_long::MIN      = -2147483648
labs(c_long::MIN) = -2147483648
labs(-1)          = 1
```

«Модуль» отрицательного числа оказался отрицательным — обычное поведение реализации, в которой отрицание `MIN` даёт само `MIN`, — но с точки зрения стандарта это UB, и опираться на него нельзя. Практический вывод: пометка `safe` для `labs` честна ровно настолько, насколько мы готовы поручиться, что `c_long::MIN` в неё не придёт. Строгая формулировка — либо оставить `unsafe fn` и проверять на месте вызова, либо (что проще и лучше) не звать `labs` вовсе: у Rust есть свой `i32::abs`, который на `MIN` не творит UB, а честно паникует в отладочной сборке.

**Типы-мостики.** `size_of` подтверждает таблицу §2.1.2 и §14.2.2: `c_double` — 8 байт, то есть **`f64`**; `c_long` — 4 байта, то есть **`i32`** (наша платформа LLP64, где `long` — 32-битный). Именно поэтому в сигнатурах FFI пишут `c_long`, а не `i64`: на LP64-Linux тот же `c_long` раскроется в `i64`, и код переедет без правок, тогда как жёстко записанный тип сломает одну из платформ.

**Ответ.** Объявление — `unsafe extern "C" { safe fn sqrt(x: c_double) -> c_double; safe fn labs(x: c_long) -> c_long; }`; вызовы идут без `unsafe`-блоков, программа печатает `sqrt(2.0) = 1.4142135623730951` и `labs(-42) = 42`. Пометка `safe` у `sqrt` честна безоговорочно: функция не принимает указателей и определена на всём множестве `double` — отрицательный аргумент даёт `NaN` (доменная ошибка), а не UB. У `labs` обоснование то же (чистая арифметика без памяти и указателей), но с оговоркой: по C5 §7.24.6.1 поведение не определено, если результат непредставим, то есть на `c_long::MIN`; на эталонной машине вызов возвращает сам `-2147483648`. На нашей платформе `c_double` — это `f64` (8 байт), `c_long` — `i32` (4 байта, LLP64: §2.1.2, §14.2.2); алиасы `c_*` пишут именно затем, чтобы на LP64-платформе `c_long` раскрылся в `i64` без правок кода.

### Г24.Ч2.З2

**Условие.** Напишите C-файл с функцией `int clampi(int x, int lo, int hi)` — ограничить `x` диапазоном `[lo, hi]`, — соберите `libclamp.a` (`gcc -c` + `ar rcs`), вызовите из Rust с квалификатором `safe` и напечатайте `clampi(15, 0, 10)`, `clampi(-3, 0, 10)`, `clampi(5, 0, 10)`. Вход/выход: только целые, библиотека — статическая, предупреждений — ноль с обеих сторон.

**Решение.** Конвейер — дословно из §11.2.3, только на выходе линкера стоит rustc. C-сторона, файл `p2/clamp/clampi.c`:

```c
/* clampi.c -- ограничить x диапазоном [lo, hi] */
int clampi(int x, int lo, int hi) {
    if (x < lo) {
        return lo;
    }
    if (x > hi) {
        return hi;
    }
    return x;
}
```

```
$ gcc -std=c17 -Wall -Wextra -c clampi.c -o clampi.o
$ ar rcs libclamp.a clampi.o
```

Обе команды молчат — предупреждений ноль, как требует условие. Имя файла библиотеки не случайно: `#[link(name = "clamp")]` заставит линкер искать `libclamp.a` (правило имён из §11.2.3 действует и здесь).

Rust-сторона, файл `p2/clamp/f2_clamp.rs`:

```rust
use std::ffi::c_int;

#[link(name = "clamp", kind = "static")]
unsafe extern "C" {
    // SAFETY: три числа на входе, число на выходе -- ни указателей,
    // ни памяти, ни глобального состояния. Любые аргументы допустимы,
    // поэтому пометка safe честна.
    safe fn clampi(x: c_int, lo: c_int, hi: c_int) -> c_int;
}

fn main() {
    println!("clampi(15, 0, 10) = {}", clampi(15, 0, 10));
    println!("clampi(-3, 0, 10) = {}", clampi(-3, 0, 10));
    println!("clampi(5, 0, 10)  = {}", clampi(5, 0, 10));
}
```

```
$ rustc --edition 2024 f2_clamp.rs -L .
$ ./f2_clamp.exe
clampi(15, 0, 10) = 10
clampi(-3, 0, 10) = 0
clampi(5, 0, 10)  = 5
```

Три случая — выше диапазона, ниже диапазона и внутри — дают 10, 0 и 5. Предупреждений нет ни от gcc, ни от rustc.

Почему `safe` здесь бесспорна (в отличие от `labs` из Г24.Ч2.З1): `clampi` принимает три `int` и возвращает `int`, не касаясь ни памяти, ни указателей, ни глобального состояния; ни одна комбинация аргументов не приводит к неопределённому поведению — даже бессмысленный вызов с `lo > hi` просто вернёт `hi` по второму `if`. Переполнения тоже не случится: сравнения и возврат значений арифметики не делают.

Ключ `kind = "static"` говорит линкеру, что это **статическая** библиотека — код `clampi` целиком вошёл в `f2_clamp.exe`, и exe-файл ни от чего внешнего не зависит (§11.2.3 про разницу со статической и динамической компоновкой). Забудьте `-L .` — получите `undefined reference to 'clampi'`, диагноз из §11.2.1.

**Ответ.** C-функция собирается в объектник (`gcc -std=c17 -Wall -Wextra -c clampi.c -o clampi.o`) и упаковывается архиватором (`ar rcs libclamp.a clampi.o`). Rust объявляет её в `unsafe extern "C"`-блоке под атрибутом `#[link(name = "clamp", kind = "static")]` с квалификатором `safe` — пометка честна, потому что функция принимает и возвращает только целые числа, не трогает память и не имеет входа, на котором её можно сломать. Сборка — `rustc --edition 2024 f2_clamp.rs -L .`; вывод: `clampi(15, 0, 10) = 10`, `clampi(-3, 0, 10) = 0`, `clampi(5, 0, 10) = 5`. Предупреждений ноль с обеих сторон.

**Вариант 2 (без `#[link]`: библиотека названа в командной строке).** Атрибут — не единственный способ сообщить линкеру о библиотеке; то же самое говорится ключом `-l` (R7, external blocks). Тогда объявление остаётся голым. Файл `p2/clamp/f2_clamp_nolink.rs`:

```rust
use std::ffi::c_int;

unsafe extern "C" {
    safe fn clampi(x: c_int, lo: c_int, hi: c_int) -> c_int;
}
```

```
$ rustc --edition 2024 f2_clamp_nolink.rs -L . -l static=clamp
$ ./f2_clamp_nolink.exe
clampi(15, 0, 10) = 10
clampi(-3, 0, 10) = 0
clampi(5, 0, 10)  = 5
```

*Сравнение.* Вывод тот же, различие — в том, где записано знание о библиотеке. `#[link]` держит его **в исходнике**: файл самодостаточен, любой, кто его собирает, получит нужную библиотеку автоматически. Ключ `-l static=clamp` держит знание **в команде сборки**: исходник ничего не знает о том, откуда возьмётся `clampi`, зато библиотеку можно подменить, не трогая код (например, собрать тот же файл против другой реализации при переносе на другую платформу). Для одного файла удобнее первый; в настоящем проекте оба способа обычно вытесняются третьим — `build.rs` из §24.2.4, который печатает cargo указания на линковку сам.

### Г24.Ч2.З3

**Условие.** Объявите структуру `Point3 { x: f64, y: f64, z: f64 }` дважды: в C (`double x, y, z;`) и в Rust с `#[repr(C)]`. Напечатайте с обеих сторон размер и все три смещения (`offsetof` / `offset_of!`) и сверьте. Затем объясните: почему у этой структуры совпадут и размеры без `repr(C)` (подсказка: одинаковое выравнивание всех полей — паддинг не нужен), и почему полагаться на это всё равно нельзя (R7).

**Решение.** Меряем обе стороны. C, файл `p2/point3/point3.c`:

```c
#include <stdio.h>
#include <stddef.h>

struct Point3 {
    double x, y, z;
};

int main(void) {
    printf("C: sizeof = %zu\n", sizeof(struct Point3));
    printf("C: offset x = %zu\n", offsetof(struct Point3, x));
    printf("C: offset y = %zu\n", offsetof(struct Point3, y));
    printf("C: offset z = %zu\n", offsetof(struct Point3, z));
    printf("C: alignof  = %zu\n", _Alignof(struct Point3));
    return 0;
}
```

```
$ gcc -std=c17 -Wall -Wextra point3.c -o point3.exe
$ ./point3.exe
C: sizeof = 24
C: offset x = 0
C: offset y = 8
C: offset z = 16
C: alignof  = 8
```

Rust, файл `p2/point3/f3_point3.rs` — с `#[repr(C)]` и, для сравнения, без него:

```rust
use std::mem::offset_of;

#[repr(C)]
struct Point3 {
    x: f64,
    y: f64,
    z: f64,
}

// та же структура без атрибута -- для сравнения
struct Point3Default {
    x: f64,
    y: f64,
    z: f64,
}
```

```
$ rustc --edition 2024 f3_point3.rs
$ ./f3_point3.exe
Rust repr(C): sizeof = 24
Rust repr(C): offset x = 0
Rust repr(C): offset y = 8
Rust repr(C): offset z = 16
Rust repr(C): alignof  = 8
Rust default: sizeof = 24
Rust default: offset x = 0
Rust default: offset y = 8
Rust default: offset z = 16
```

Замеры сошлись байт в байт: 24 байта, смещения 0, 8, 16, выравнивание 8.

**Почему совпало даже без `repr(C)`.** Раскладка по умолчанию отличалась от C-шной в §24.2.2 (`MixedC` против `MixedRust`) потому, что там были *разные* по размеру и выравниванию поля: компилятору было что переставлять — он поднял `int` вперёд и сжал структуру с 12 байт до 8, убрав паддинг. Здесь переставлять нечего: три поля одного типа `f64`, у всех выравнивание 8 и размер 8. Любой порядок даёт одну и ту же плотную укладку без единого байта паддинга — оптимизировать нечего, и компилятор оставляет поля как есть. Считать по правилам §8.2.3: смещение 0 кратно 8, следующее поле кладётся на 8, затем на 16, итог 24 — уже кратен выравниванию 8, хвостового паддинга не требуется.

**Почему полагаться на это всё равно нельзя.** Совпадение — наблюдение об одной сборке одного компилятора, а не обещание. R7 (Type layout) прямо говорит, что у репрезентации по умолчанию **нет гарантий** ни на порядок полей, ни на размер: компилятор вправе менять раскладку между версиями, между профилями сборки и даже между двумя структурами с одинаковым набором полей. Стоит кому-то дописать в `Point3` поле `tag: u8` — и совпадение немедленно кончится, а поймать это будет некому: линкер сверяет имена, не раскладки (Г24.Ч2.З5). Отсюда железное правило §24.2.2: **каждая структура, пересекающая границу языков, — `#[repr(C)]`**, независимо от того, «и так совпадает» или нет. Атрибут стоит ноль байт и ноль тактов, а страхует от целого класса ошибок, которые проявляются молча.

**Ответ.** Обе стороны дают одинаковый замер: размер 24, смещения `x = 0`, `y = 8`, `z = 16`, выравнивание 8. Размеры и смещения совпадают и без `#[repr(C)]`, потому что все три поля — `f64` с одинаковым размером и выравниванием 8: паддинг не нужен ни при каком порядке полей, переставлять компилятору нечего, и раскладка по умолчанию вырождается в C-шную. Полагаться на это нельзя: R7 не даёт **никаких** гарантий для репрезентации по умолчанию — раскладка может измениться с версией компилятора, профилем сборки или после добавления единственного поля, а несовпадение проявится не ошибкой сборки, а неверными данными в рантайме. Правило §24.2.2 остаётся безусловным: структура, пересекающая границу, объявляется `#[repr(C)]` всегда.

### Г24.Ч2.З4

**Условие.** Программа должна передать строку пользователя C-функции `strlen`. Кандидат написал: `let p = s.as_ptr();` (где `s: String`) — и получил неправильные длины. Объясните обе беды (`'\0'`; когда результат *случайно* совпадёт) и перепишите через `CString`. Что вернёт `CString::new("ab\0cd")` — и почему такая защита необходима именно на границе с C (§5.2.1)?

**Решение.** Первая беда — **терминатор**. `String` хранит «байты + длину» (§17.1.3), терминатора в буфере нет; `strlen` же не знает никакой длины и читает память, пока не встретит `'\0'` (§5.2.1). Поэтому `strlen(s.as_ptr())` считает не длину строки, а расстояние до первого нулевого байта, который случайно окажется дальше в памяти, — то есть залезает **за пределы буфера**. Это UB со всеми последствиями §13.1.3, а не «неправильное число».

Смотрим на опыт. Файл `p2/f4_string_bad.rs` — ⛔:

```rust
fn main() {
    let s = String::from("hello");
    let p = s.as_ptr() as *const c_char; // у буфера String нет '\0'

    // SAFETY: НЕ ВЫПОЛНЕНА -- контракт strlen требует NUL-строку,
    // а буфер String терминатора не содержит. Это опыт, не образец.
    let n = unsafe { strlen(p) };

    println!("s.len()   = {}", s.len());
    println!("strlen(p) = {n}");
}
```

```
$ rustc --edition 2024 f4_string_bad.rs
$ ./f4_string_bad.exe
s.len()   = 5
strlen(p) = 6
```

Пять байт против шести: за концом буфера в куче оказался один ненулевой байт, а следующий — нулевой. Программа не упала, ничего не заметила и выдала правдоподобное, но неверное число — точно как `oob.c` в §13.1.3.

Вторая беда — **случайное совпадение**. Иногда сразу за буфером лежит нулевой байт, и `strlen` вернёт ровно `s.len()`. Ответ окажется «правильным» — но по-прежнему добытым чтением за границей выделения. Такой код проходит тесты, живёт в продакшене и падает после невинного изменения соседнего кода, которое переставило данные в куче. Именно поэтому «работает» не является доказательством: UB не обязано проявляться (§13.1.3, §24.1.2 — с той же release-сборкой, печатавшей мусор).

**Как надо.** `CString` (§24.2.2) строит владеющую C-строку: копирует байты, дописывает `'\0'` и проверяет, что внутри нулей нет. Файл `p2/f4_strings.rs`:

```rust
use std::ffi::{CString, c_char};

unsafe extern "C" {
    // указатель -- значит unsafe: контракт «валидная NUL-строка»
    unsafe fn strlen(s: *const c_char) -> usize;
}

/// Безопасная обёртка: строим C-строку и держим её живой на время вызова.
fn c_strlen(s: &str) -> Result<usize, std::ffi::NulError> {
    let owned = CString::new(s)?; // владелец живёт до конца функции
    // SAFETY: owned жив в этой области, as_ptr даёт указатель на
    // NUL-терминированный буфер без внутренних нулей -- ровно то,
    // что требует контракт strlen.
    Ok(unsafe { strlen(owned.as_ptr()) })
}
```

```
$ rustc --edition 2024 f4_strings.rs
$ ./f4_strings.exe
c_strlen("hello")     = Ok(5)
c_strlen("")          = Ok(0)
c_strlen("ab\0cd")    = Err(NulError(2, [97, 98, 0, 99, 100]))
CString::new("ab\0cd") = Err(NulError(2, [97, 98, 0, 99, 100]))
```

Теперь `hello` — честные 5. Обратите внимание на две детали обёртки. Во-первых, `owned` — **именованная переменная**: живёт до конца функции, и указатель не виснет (ловушка `CString::new("hi").unwrap().as_ptr()` из §24.2.2 — временное значение умирает по концу выражения). Во-вторых, ошибка не проглатывается, а уезжает наверх оператором `?` (§18.1.3): невозможность построить C-строку — это ошибка данных, а не повод паниковать.

**Что вернёт `CString::new("ab\0cd")`.** Не строку, а `Err(NulError(2, [97, 98, 0, 99, 100]))`: ноль обнаружен по индексу 2, а в ошибке возвращены **все** исходные байты — включая нулевой (97, 98 — это `a` и `b`, затем 0, затем 99, 100 — `c` и `d`). Владение байтами не теряется: их можно забрать из ошибки и починить строку.

Почему такая защита нужна именно на границе с C: строка C заканчивается **первым** нулём (§5.2.1) — иного способа узнать её длину у C-стороны нет. Отдай мы туда `ab\0cd`, C увидел бы строку `ab` длиной 2, а хвост `cd` молча исчез бы — данные потерялись бы без единого сообщения об ошибке. `CString` превращает эту тихую потерю в явный `Result`, который нельзя не заметить (глава 18).

**Ответ.** Первая беда: у буфера `String` нет терминатора `'\0'`, а `strlen` считает байты до первого нуля — значит, чтение уходит **за границу выделения**, это UB (§13.1.3), а не просто неверная длина; в нашем прогоне `s.len() = 5`, а `strlen(p) = 6`. Вторая: если сразу за буфером случайно окажется нулевой байт, результат совпадёт с настоящей длиной — код будет «работать», оставаясь неправильным, и сломается от любой перестановки данных в куче. Правильно — через `CString::new(s)?`: она копирует байты, дописывает `'\0'` и проверяет отсутствие внутренних нулей; владелец обязан жить в **именованной** переменной, пока C пользуется указателем. `CString::new("ab\0cd")` возвращает `Err(NulError(2, [97, 98, 0, 99, 100]))` — позиция нуля и все исходные байты. Защита необходима потому, что C-строка кончается первым нулём (§5.2.1): такая строка молча превратилась бы для C-стороны в `ab`, а хвост потерялся бы без всякой диагностики.

### Г24.Ч2.З5

**Условие.** В `unsafe extern "C"`-блоке для `c_add` из §24.2.1 кандидат ошибся: объявил `fn c_add(a: c_int) -> c_int` (потерял параметр). Ответьте: (а) поймает ли это компилятор Rust; (б) поймает ли линкер (сравните с §11.2.1 — что именно сверяет линкер); (в) что случится в рантайме (термин из §24.1.1); (г) какой инструмент из §24.2.4 снимает эту проблему в больших проектах.

**Решение.** Соберём опыт целиком. C-сторона (файл `p2/mylib/mylib.c`) — функция из §24.2.1 без изменений:

```c
int c_add(int a, int b) {
    return a + b;
}
```

```
$ gcc -std=c17 -Wall -Wextra -c mylib.c -o mylib.o
$ ar rcs libmylib.a mylib.o
```

Rust-сторона с ошибкой кандидата (файл `p2/mylib/f5_wrong.rs`) — ⛔ по смыслу, хотя собирается:

```rust
use std::ffi::c_int;

#[link(name = "mylib", kind = "static")]
unsafe extern "C" {
    safe fn c_add(a: c_int) -> c_int; // в C: int c_add(int a, int b)
}

fn main() {
    println!("c_add(2) = {}", c_add(2));
    println!("c_add(2) = {}", c_add(2));
    println!("c_add(7) = {}", c_add(7));
}
```

```
$ rustc --edition 2024 f5_wrong.rs -L .
$ ./f5_wrong.exe
c_add(2) = 2
c_add(2) = 3
c_add(7) = 8
```

Вот и ответ на все четыре вопроса сразу — в трёх строках вывода.

**(а) Поймает ли компилятор Rust?** Нет. Компилятор не видит C-заголовков и вообще не имеет доступа к определению функции: `extern`-блок — это **декларация под вашу подпись** (§24.2.1), тот самый `unsafe extern` издания 2024. Rust проверил лишь то, что вызов `c_add(2)` согласован с *объявлением*, — и претензий у него нет.

**(б) Поймает ли линкер?** Тоже нет — и это ровно урок §11.2.1: линкер сверяет **имена символов**, а не сигнатуры. В объектнике `mylib.o` лежит символ `c_add`; Rust просит символ `c_add`; имена совпали — компоновка прошла молча. Ни число параметров, ни их типы, ни тип возврата в объектнике не записаны и сверке не подлежат. Это буквально «прототип разъехался с определением» из §11.2.2, только там хотя бы один компилятор видел оба файла, а здесь — ни один.

**(в) Что случится в рантайме?** **Неопределённое поведение** (термин §24.1.1; R7 относит вызов с неверным ABI к UB). Механика видна невооружённым глазом: по C-ABI x86-64 аргументы едут в регистрах, `a` — в первом, `b` — во втором. Наш вызов кладёт только первый, второй регистр содержит то, что там осталось от предыдущего кода. C-функция честно складывает `a` с этим мусором. Смотрите на вывод: **два одинаковых вызова `c_add(2)` дали разные ответы — 2 и 3**. Функция перестала быть функцией: результат зависит не от аргументов, а от того, что лежало в регистре. Прогон повторён четыре раза подряд — тройка `2, 3, 8` воспроизводится устойчиво, что делает диагноз ещё сложнее: «у меня стабильно неправильно» выглядит как логическая ошибка где угодно, только не в объявлении.

Для контраста — правильное объявление (файл `p2/mylib/f5_right.rs`, `safe fn c_add(a: c_int, b: c_int) -> c_int`):

```
$ ./f5_right.exe
c_add(2, 3) = 5
c_add(7, 0) = 7
```

Отдельно стоит заметить: в сломанной программе **нет ни одного слова `unsafe`** — кандидат пометил функцию `safe`, и вызовы выглядят совершенно обычно. Это то самое «`safe` без оснований» из списка ошибок §24.2.1: пометка перенесла ответственность на объявление, а объявление оказалось ложным.

**(г) Какой инструмент снимает проблему.** **bindgen** (§24.2.4): он читает настоящий `.h`-файл C-библиотеки и генерирует `extern`-блоки автоматически, так что сигнатуры не переписываются руками и не могут разъехаться. Для обратного направления есть cbindgen, печатающий `.h` из Rust-экспортов.

**Ответ.** (а) Компилятор Rust ошибку не поймает: `extern`-блок — декларация под подпись программиста, C-заголовков компилятор не видит и сверять сигнатуру не с чем. (б) Линкер тоже не поймает: он сверяет только **имена символов** (§11.2.1), а число и типы параметров в объектнике не хранятся — имя `c_add` совпало, компоновка прошла молча. (в) В рантайме наступает **неопределённое поведение** (нарушение ABI-договора): второй аргумент не передан, C-функция складывает `a` с мусором из регистра — в нашем прогоне два одинаковых вызова `c_add(2)` дали **2 и 3**, а `c_add(7)` дал 8. Программа не падает и выглядит рабочей. (г) В больших проектах проблему снимает **bindgen** — генератор `extern`-блоков из `.h`-файлов (§24.2.4); обратное направление закрывает cbindgen.

### Г24.Ч2.З6

**Условие.** Разберите `rust_checked_div` из §24.2.3: почему при `b == 0` процесс аварийно останавливается, а не возвращает ошибку в C? Спроектируйте безопасный API этой же функции для C-клиента: код возврата + выходной параметр (§6.1.3), без единой возможной паники. Реализуйте и проверьте из C оба случая (успех и деление на ноль).

**Решение.** Сначала воспроизведём беду. Библиотека `p2/divlib/divlib.rs` содержит обе функции — исходную из §24.2.3 и нашу новую; C-клиент `p2/divlib/main_panic.c` зовёт первую:

```c
#include <stdio.h>

int rust_checked_div(int a, int b);

int main(void) {
    printf("rust_checked_div(10, 3) = %d\n", rust_checked_div(10, 3));
    printf("rust_checked_div(10, 0) = %d\n", rust_checked_div(10, 0));
    printf("control never gets here\n");
    return 0;
}
```

```
$ rustc --edition 2024 --crate-type=staticlib divlib.rs -o libdivlib.a
$ rustc --print native-static-libs --crate-type=staticlib divlib.rs -o probe.a
note: native-static-libs: -lkernel32 -lntdll -luserenv -lws2_32 -ldbghelp
$ gcc -std=c17 -Wall -Wextra main_panic.c -L . -ldivlib -lkernel32 -lntdll -luserenv -lws2_32 -ldbghelp -o app_panic.exe
$ ./app_panic.exe

attempt to divide by zero
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

thread '<unnamed>' (10072) panicked at ...core\src\panicking.rs:225:5:
panic in a function that cannot unwind
stack backtrace:
   ...
  19:     0x7ff7fb461573 - rust_checked_div
  20:     0x7ff7fb4614f0 - main
   ...
thread caused non-unwinding panic. aborting.
--- exit=127 ---
```

**Почему аварийная остановка, а не возврат ошибки.** Паника в Rust по умолчанию **разматывает стек** (§18.1.1): идёт вверх по кадрам, вызывая деструкторы. Но кадры C-кода размотке не поддаются — в них нет ни таблиц раскрутки, ни деструкторов, и попытка пройти через них была бы UB (R8: сквозь границу могут идти только паники по специальному ABI `"C-unwind"`, за рамками курса). Поэтому компилятор ставит на границе `extern "C"`-функции барьер: паника, добежавшая до него, превращается во **вторую** панику — «panic in a function that cannot unwind», — и та уже не разматывает ничего, а завершает процесс. Строка `thread caused non-unwinding panic. aborting.` — приговор всему процессу. Возвращать «ошибку» некуда: C-сторона узнаёт о случившемся только по факту смерти процесса.

Заодно наблюдение, которого нет в главе: **успешная строка тоже пропала**. Первый `printf` отработал, но его текст остался в буфере stdio, а `abort` буферы не сбрасывает (§10.1.1: при аварийном завершении сброс не гарантируется — C5 §7.23.3). При перенаправлении вывода в файл на stdout не приходит вообще ничего — только stderr с диагностикой паники. Мораль ровно та же, что у правила «экспортируемая функция не должна паниковать»: авария на границе уносит и уже сделанную работу.

**Безопасный API.** Проектируем по-сишному (§6.1.3): функция возвращает **код результата**, а само частное отдаёт через **выходной параметр**. Тогда «деление на ноль» — обычное значение, а не катастрофа. Файл `p2/divlib/divlib.rs` целиком — обе функции, паникующая и новая:

```rust
use std::ffi::c_int;

/// Вариант из §24.2.3: паника доезжает до границы с C.
#[unsafe(no_mangle)]
pub extern "C" fn rust_checked_div(a: c_int, b: c_int) -> c_int {
    a / b // при b == 0 -- паника Rust на границе с C
}

/// Безопасный API для C: код возврата + выходной параметр.
/// 0 -- успех (частное записано в out), 1 -- деление на ноль,
/// 2 -- частное непредставимо (c_int::MIN / -1).
///
/// SAFETY-контракт: out -- либо null, либо адрес доступного
/// для записи, правильно выровненного c_int.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn rust_div(a: c_int, b: c_int, out: *mut c_int) -> c_int {
    if b == 0 {
        return 1;
    }
    if a == c_int::MIN && b == -1 {
        return 2;
    }

    let q = a / b; // обе опасные ситуации отсеяны выше -- паники быть не может

    if !out.is_null() {
        // SAFETY: указатель не null; по контракту функции он указывает
        // на доступный для записи c_int.
        unsafe { *out = q };
    }
    0
}
```

Двух проверок достаточно, чтобы паника стала невозможной: деление на ноль и **переполнение** `c_int::MIN / -1` — единственные две ситуации, в которых `a / b` паникует (частное `2147483648` не помещается в `i32`). Второй случай легко забыть, и тогда «функция без паник» запаникует ровно один раз в жизни — на самом неудобном входе.

C-клиент, файл `p2/divlib/main_div.c`:

```c
#include <stdio.h>
#include <limits.h>

int rust_div(int a, int b, int *out);

static void try_div(int a, int b) {
    int q = -999; /* заведомо чужое значение: увидим, тронул ли его Rust */
    int rc = rust_div(a, b, &q);
    printf("rust_div(%d, %d): rc = %d, q = %d\n", a, b, rc, q);
}

int main(void) {
    try_div(10, 3);
    try_div(10, 0);
    try_div(INT_MIN, -1);

    /* out можно не передавать: контракт разрешает null */
    printf("rust_div(9, 3, NULL): rc = %d\n", rust_div(9, 3, NULL));
    return 0;
}
```

```
$ gcc -std=c17 -Wall -Wextra main_div.c -L . -ldivlib -lkernel32 -lntdll -luserenv -lws2_32 -ldbghelp -o app_div.exe
$ ./app_div.exe
rust_div(10, 3): rc = 0, q = 3
rust_div(10, 0): rc = 1, q = -999
rust_div(-2147483648, -1): rc = 2, q = -999
rust_div(9, 3, NULL): rc = 0
--- exit=0 ---
```

Оба требуемых случая на месте: успех (`rc = 0`, частное 3) и деление на ноль (`rc = 1`). Заметьте `q = -999` в неуспешных строках — выходной параметр **не тронут**, и это часть договора: при ненулевом коде значение не записывается, C-сторона не должна его читать. Третья строка показывает переполнение, четвёртая — что `out` разрешено не передавать вовсе.

Почему функция всё-таки `unsafe extern`: она принимает указатель, а проверить, что он ведёт на доступную для записи память, Rust не может — это классический контракт FFI (§24.2.1). Проверка `is_null()` спасает от единственного случая, который проверить *можно*.

**Ответ.** При `b == 0` `rust_checked_div` паникует, паника доходит до границы `extern "C"` и не может пройти дальше: размотка стека через кадры C невозможна (R8), поэтому среда превращает её во вторую, «неразматывающуюся» панику — `panic in a function that cannot unwind` — и процесс аварийно останавливается (`thread caused non-unwinding panic. aborting.`); вернуть ошибку в C некуда, и даже уже напечатанное C-стороной теряется вместе с несброшенным буфером stdio. Безопасный API устроен по-сишному: `int rust_div(int a, int b, int *out)` возвращает код (0 — успех, 1 — деление на ноль, 2 — непредставимое частное `INT_MIN / -1`), а результат кладёт в выходной параметр только при успехе; паника исключена конструктивно — обе паникующие ситуации отсеяны проверками до деления, а `out` проверяется на null. Прогон из C: `rust_div(10, 3)` даёт `rc = 0, q = 3`, `rust_div(10, 0)` — `rc = 1`, и `q` остаётся нетронутым.

**Вариант 2 (выходной параметр как `Option<&mut c_int>`).** Nullable-указатель C можно принять честным типом Rust: нишевая оптимизация гарантирует, что `Option<&mut T>` занимает ровно указатель, а `None` кодируется нулём (§16.2.3, §24.2.2). Тогда null разбирается образцом, а не проверкой `is_null()`, — и функция получается **safe**. Файл `p2/divlib/divopt.rs`:

```rust
use std::ffi::c_int;

/// 0 -- успех, 1 -- деление на ноль, 2 -- частное непредставимо.
/// Функция safe: null со стороны C приезжает как None (§16.2.3).
#[unsafe(no_mangle)]
pub extern "C" fn rust_div_opt(a: c_int, b: c_int, out: Option<&mut c_int>) -> c_int {
    if b == 0 {
        return 1;
    }
    if a == c_int::MIN && b == -1 {
        return 2;
    }

    if let Some(slot) = out {
        *slot = a / b;
    }
    0
}
```

Со стороны C ничего не меняется — прототип тот же `int rust_div_opt(int a, int b, int *out);` (файл `p2/divlib/main_opt.c`):

```
$ rustc --edition 2024 --crate-type=staticlib divopt.rs -o libdivopt.a
$ gcc -std=c17 -Wall -Wextra main_opt.c -L . -ldivopt -lkernel32 -lntdll -luserenv -lws2_32 -ldbghelp -o app_opt.exe
$ ./app_opt.exe
rust_div_opt(10, 3): rc = 0, q = 3
rust_div_opt(10, 0): rc = 1, q = -999
rust_div_opt(-2147483648, -1): rc = 2, q = -999
rust_div_opt(9, 3, NULL): rc = 0
--- exit=0 ---
```

*Сравнение.* Вывод совпадает до символа, а кода стало меньше: исчезли `unsafe`-блок, проверка `is_null()` и половина `SAFETY`-контракта — их работу делает система типов. Тип `Option<&mut c_int>` выражает «указатель, который может быть нулём» точнее, чем `*mut c_int`, и разбор `None` забыть невозможно: без `if let` компилятор не даст записать в `out`. Цена в том, что обязательство никуда не делось, а стало **тише**: `&mut c_int` обещает не только ненулевой адрес, но и валидную, выровненную, никем не разделяемую память — если C передаст мусорный ненулевой указатель, UB наступит без единого слова `unsafe` в файле, а сигнатура будет выглядеть безобидно. Поэтому первый вариант предпочтительнее в «недоверенных» границах, где хочется, чтобы контракт был виден глазами; второй — в аккуратных обёртках, где C-клиент свой и договор соблюдается.

### Г24.Ч2.З7

**Условие.** Дан замер из §24.2.2: раскладка по умолчанию разместила поля `MixedRust` со смещениями `b=0, a=4, c=5` (размер 8). Объясните: чем руководствовался компилятор (сравните с ручной перестановкой полей в §8.2.3); почему передача такой структуры в `reading_total`-подобную C-функцию — UB, а не «просто неправильные числа»; каким одним атрибутом чинится.

**Решение.** Повторим замер (файл `p2/f7_layout.rs`), чтобы разговор шёл о числах, а не о памяти:

```
$ rustc --edition 2024 f7_layout.rs
$ ./f7_layout.exe
repr(C):  size = 12, a = 0, b = 4, c = 8
default:  size = 8, a = 4, b = 0, c = 5
```

**Чем руководствовался компилятор.** Ровно тем же соображением, что и мы в §8.2.3, когда переставляли поля руками: паддинг возникает из-за выравнивания, и его можно убрать, положив «широкие» поля первыми. У `c_int` выравнивание 4, у `c_char` — 1. При порядке объявления `a, b, c` C-раскладка обязана вставить 3 байта паддинга после `a` (чтобы `b` встал на адрес, кратный 4) и ещё 3 хвостовых (чтобы размер был кратен 4): 1 + 3 + 4 + 1 + 3 = 12. Компилятор Rust, не связанный порядком объявления, кладёт сначала `b` (смещение 0, 4 байта), затем `a` (4) и `c` (5) — оба по одному байту, — и получает 6 байт значащих плюс 2 хвостовых до кратности 4: итого 8. Та самая ручная оптимизация из §8.2.3, только выполненная за нас и без права голоса.

**Почему передача такой структуры в C-функцию — UB, а не «просто неправильные числа».** Различие принципиальное. «Неправильные числа» были бы, если бы обе стороны читали одну и ту же память по-разному, но в её пределах: C прочёл бы по смещению 4 не то поле, получил бы мусорное значение — неприятно, но это ещё «просто ошибка». Беда в том, что расходятся не только смещения, но и **размер**: C-функция считает, что элемент занимает 12 байт, Rust отдал массив с шагом 8. При обходе `arr[i]` C-сторона шагает по 12 байт и на втором же элементе выходит **за пределы выделения** — читает чужую память, а это в точности UB (§13.1.2, §24.1.2). Плюс любое чтение поля по неверному смещению может вернуть битовый узор, недопустимый для типа поля, — тоже UB (R7). И дополнительно: сам вызов с сигнатурой, не соответствующей фактической раскладке аргумента, R7 относит к нарушению ABI-договора, то есть к UB, независимо от того, что получится прочитать. Наконец, гарантий на раскладку по умолчанию нет вовсе — R7 не обещает даже, что два прогона *одного* компилятора дадут одинаковый результат, — так что «неправильные числа» не будут даже стабильно неправильными.

**Чем чинится.** Одним атрибутом `#[repr(C)]` над определением структуры. Он переключает раскладку на алгоритм C (§8.2.3, §24.2.2): поля в порядке объявления, паддинг по выравниванию — и замер немедленно совпадает с C-шным (12, 0, 4, 8).

**Ответ.** Компилятор руководствовался экономией памяти: у репрезентации по умолчанию нет обязательств по порядку полей, поэтому он положил `b` (`c_int`, выравнивание 4) на смещение 0, а два однобайтовых `c_char` — следом, на 4 и 5, убрав внутренний паддинг; размер сжался с 12 до 8 байт. Это та самая ручная перестановка полей из §8.2.3, сделанная автоматически. Передача такой структуры в C-функцию — UB, а не просто неверные числа, потому что расходится и **шаг элемента**: C обходит массив с шагом 12 байт, а выделено по 8 — уже на втором элементе чтение уходит за границу выделения; вдобавок чтение поля по чужому смещению может дать значение, недопустимое для его типа, а сам вызов с раскладкой, не соответствующей объявленной, R7 квалифицирует как нарушение ABI-договора. Чинится одним атрибутом — `#[repr(C)]` над структурой.

### Г24.Ч2.З8

**Условие.** Напишите C-функцию `int imax_at(const int *data, size_t len)`, возвращающую *индекс* максимального элемента (для пустого массива — `-1`), и безопасную Rust-обёртку `fn max_index(v: &[c_int]) -> Option<usize>` над ней (`None` для пустого среза — не спрашивая C). Соберите статическую библиотеку, напишите три проверки: пустой срез, один элемент, максимум в середине. Ограничение: unsafe — только внутри обёртки, `SAFETY`-комментарий обязателен.

**Решение.** C-сторона, файл `p2/imax/imax.c`. Договор «пустой массив → −1» — обычный сишный приём «спец-значение вместо отсутствия» (§10.1.2 с его `EOF`, §13.2.2 про цену такого договора):

```c
#include <stddef.h>

int imax_at(const int *data, size_t len) {
    if (len == 0) {
        return -1;
    }

    size_t best = 0;
    for (size_t i = 1; i < len; i++) {
        if (data[i] > data[best]) {
            best = i;
        }
    }
    return (int)best;
}
```

```
$ gcc -std=c17 -Wall -Wextra -c imax.c -o imax.o
$ ar rcs libimax.a imax.o
```

Rust-сторона, файл `p2/imax/f8_max.rs`. Обёртка строится по канону §24.1.3: `unsafe` живёт ровно в одной строке, инвариант «указатель и длина описывают один живой срез» обеспечивает сама функция, а наружу выходит `Option<usize>` — тип, а не спец-значение:

```rust
use std::ffi::c_int;

#[link(name = "imax", kind = "static")]
unsafe extern "C" {
    unsafe fn imax_at(data: *const c_int, len: usize) -> c_int;
}

/// Безопасная обёртка: пустой срез отсекаем сами, не спрашивая C.
fn max_index(v: &[c_int]) -> Option<usize> {
    if v.is_empty() {
        return None;
    }

    // SAFETY: указатель и длина взяты из одного живого среза, поэтому
    // C-функция прочитает ровно v.len() инициализированных элементов
    // внутри выделения; ничего не пишет и указатель у себя не хранит.
    let idx = unsafe { imax_at(v.as_ptr(), v.len()) };

    // срез непуст -- значит C вернул индекс, а не -1
    Some(idx as usize)
}

fn main() {
    let empty: [c_int; 0] = [];
    println!("[]              -> {:?}", max_index(&empty));
    println!("[42]            -> {:?}", max_index(&[42]));
    println!("[1, 4, 9, 2, 5] -> {:?}", max_index(&[1, 4, 9, 2, 5]));
}
```

```
$ rustc --edition 2024 f8_max.rs -L .
$ ./f8_max.exe
[]              -> None
[42]            -> Some(0)
[1, 4, 9, 2, 5] -> Some(2)
```

Три проверки: пустой срез, один элемент и максимум в середине (`9` стоит третьим, индекс 2).

Разберём три решения, из которых состоит обёртка.

- **Пустой срез отсекается на стороне Rust.** Условие требует именно этого — и не из недоверия к C, а ради типов: если бы `None` получался из «C вернул −1», нам пришлось бы преобразовывать `-1` в `Option` уже после вызова, а до этого молча полагаться на договор о спец-значении. Отсекая пустоту заранее, мы получаем сильное утверждение: **после проверки C не может вернуть −1**, и приведение `idx as usize` заведомо корректно. Так «отсутствие значения — это тип» (§16.2.3) вытесняет «отсутствие значения — это −1» прямо на границе.
- **Срез разбирается на указатель и длину.** Целиком `&[c_int]` через границу не поедет: «указатель + длина» — внутреннее представление Rust (§15.3.1), у C такого типа нет. Пара `as_ptr()` / `len()` — канонический разбор (§24.2.2), и именно то, что оба значения взяты **из одного среза**, делает `SAFETY`-обоснование правдой: рассогласовать их невозможно, потому что между ними ничего не происходит.
- **`size_t` ↔ `usize`.** Длина едет как `usize` — соответствие «размерных» целых платформы (§24.2.1). Возврат `int` мы принимаем как `c_int` и переводим в `usize` уже после проверки.

**Ответ.** C-функция `int imax_at(const int *data, size_t len)` линейно ищет индекс максимума и возвращает −1 для пустого массива; сборка — `gcc -c` + `ar rcs libimax.a`. Rust-обёртка `fn max_index(v: &[c_int]) -> Option<usize>` сама возвращает `None` для пустого среза (не спрашивая C), а иначе вызывает `imax_at(v.as_ptr(), v.len())` в единственном `unsafe`-блоке с `SAFETY`-обоснованием «указатель и длина взяты из одного живого среза; C только читает `len` инициализированных элементов и указатель не сохраняет» — после проверки непустоты возврат −1 невозможен, поэтому `idx as usize` корректно. Проверки печатают `None`, `Some(0)` и `Some(2)`; unsafe встречается ровно в одной строке обёртки, снаружи его нет.

### Г24.Ч2.З9

**Условие.** «Счётчик наоборот»: C-сторона владеет памятью. Напишите на C `struct Stats` (поля `long long sum; int n;`) и функции `stats_new` (через `malloc`, §7.1.2), `stats_add(struct Stats *, int)`, `stats_mean(const struct Stats *) -> double`, `stats_free`. Из Rust: объявите непрозрачный тип (пустая структура — приём §24.2.3 наоборот), постройте безопасную обёртку-структуру `Stats` с методами `new/add/mean` и **реализуйте для неё `Drop`** (§22.1.2), зовущий `stats_free`, — чтобы Rust-клиент не мог забыть освобождение. Продемонстрируйте: среднее для 10, 20, 30 равно 20.0, и утечки нет (drop зовётся сам).

**Решение.** Это зеркало §24.2.3: там памятью владел Rust и отдавал C сырой указатель, здесь память выделяет `malloc` (§7.1.2), а Rust получает ручку, которой не имеет права распоряжаться иначе как через C-функции.

C-сторона, файл `p2/stats/stats.c`. Кроме четырёх функций из условия добавлена пятая, `stats_live` — счётчик живых объектов: без него «утечки нет» пришлось бы принимать на веру:

```c
#include <stdlib.h>

struct Stats {
    long long sum;
    int n;
};

static int live = 0; /* сколько объектов сейчас живо -- для проверки утечки */

struct Stats *stats_new(void) {
    struct Stats *s = malloc(sizeof(struct Stats));
    if (s == NULL) {
        return NULL;
    }
    s->sum = 0;
    s->n = 0;
    live++;
    return s;
}

void stats_add(struct Stats *s, int x) {
    s->sum += x;
    s->n += 1;
}

double stats_mean(const struct Stats *s) {
    if (s->n == 0) {
        return 0.0;
    }
    return (double)s->sum / (double)s->n;
}

void stats_free(struct Stats *s) {
    if (s != NULL) {
        free(s);
        live--;
    }
}

int stats_live(void) {
    return live;
}
```

```
$ gcc -std=c17 -Wall -Wextra -c stats.c -o stats.o
$ ar rcs libstats.a stats.o
```

Rust-сторона, файл `p2/stats/f9_stats.rs`. Непрозрачный тип объявляется структурой без полей — Rust знает только имя, размер ему не нужен, потому что работаем исключительно указателем (тот же приём, что `FILE *` в §10.1.1 и `struct Counter` в C-клиенте §24.2.3, только направление обратное):

```rust
use std::ffi::{c_double, c_int};

/// Непрозрачный тип: содержимое знает только C (приём §24.2.3 наоборот).
#[repr(C)]
struct CStats {
    _private: [u8; 0],
}

#[link(name = "stats", kind = "static")]
unsafe extern "C" {
    unsafe fn stats_new() -> *mut CStats;
    unsafe fn stats_add(s: *mut CStats, x: c_int);
    unsafe fn stats_mean(s: *const CStats) -> c_double;
    unsafe fn stats_free(s: *mut CStats);
    safe fn stats_live() -> c_int;
}

/// Безопасная обёртка: владеет указателем C-стороны и сама его освобождает.
struct Stats {
    raw: *mut CStats,
}

impl Stats {
    fn new() -> Option<Stats> {
        // SAFETY: у stats_new нет аргументов; она возвращает либо
        // валидный указатель, либо null (malloc не удался).
        let raw = unsafe { stats_new() };
        if raw.is_null() {
            None
        } else {
            Some(Stats { raw })
        }
    }

    fn add(&mut self, x: i32) {
        // SAFETY: raw получен из stats_new, ещё не освобождён (освобождение
        // только в Drop) и наружу не выдавался -- других ручек не существует.
        unsafe { stats_add(self.raw, x) }
    }

    fn mean(&self) -> f64 {
        // SAFETY: см. add.
        unsafe { stats_mean(self.raw) }
    }
}

impl Drop for Stats {
    fn drop(&mut self) {
        // SAFETY: raw жив ровно до этой точки; Drop вызывается один раз
        // (§22.1.2), поэтому двойного освобождения быть не может.
        unsafe { stats_free(self.raw) }
    }
}

fn main() {
    println!("live before = {}", stats_live());

    {
        let mut s = Stats::new().expect("malloc failed");
        println!("live inside = {}", stats_live());

        s.add(10);
        s.add(20);
        s.add(30);
        println!("mean = {}", s.mean());
    } // здесь Drop зовёт stats_free -- клиент об этом не думает

    println!("live after  = {}", stats_live());
}
```

```
$ rustc --edition 2024 f9_stats.rs -L .
$ ./f9_stats.exe
live before = 0
live inside = 1
mean = 20
live after  = 0
```

Среднее для 10, 20 и 30 — ровно 20 (печать `{}` не дописывает нулевую дробную часть, как в Г24.Ч1.З1). А `live`, пройдя через 1, вернулся в 0 **сам** — блок закончился, `Stats` вышел из области, `Drop` позвал `stats_free`. Клиент не написал ни строчки освобождения и не мог бы её забыть при всём желании.

Что здесь работает:

- **`Drop` превращает договор в инвариант.** Дисциплина §7.1.2 «кто выделил, тот и освобождает» осталась в силе — освобождает по-прежнему C-сторона (`free` из `stats_free`), Rust не смеет трогать чужой аллокатор (§24.2.3: `free()` на `Box`-указателе и наоборот — верный способ падать по вторникам). Но *момент* вызова теперь определяет система типов: конец области видимости (§22.1.2). Это и есть RAII, до которого C-код дотягивается только руками.
- **Непрозрачность защищает обе стороны.** `CStats` без полей нельзя ни создать, ни разыменовать по ошибке — на нём не выполнить ничего, кроме передачи в C-функции; раскладка `struct Stats` остаётся частным делом C и может меняться, не ломая Rust.
- **`new` возвращает `Option`.** `malloc` может вернуть `NULL` (§7.1.1) — и это единственная ошибка, которую обёртка обязана показать наружу; она выражена типом, а не спец-значением.
- **Двойное освобождение невозможно.** `Drop` вызывается ровно один раз для каждого значения, а `raw` наружу не выдаётся — «C дважды позвал `counter_free`» из списка ошибок §24.2.3 здесь просто нечем повторить.

**Ответ.** C-сторона выделяет `struct Stats` через `malloc` в `stats_new` (и возвращает `NULL` при неудаче), изменяет её в `stats_add`, считает среднее в `stats_mean` и освобождает `free`-ом в `stats_free`. Rust объявляет непрозрачный тип пустой структурой `#[repr(C)] struct CStats { _private: [u8; 0] }`, а поверх строит владеющую обёртку `struct Stats { raw: *mut CStats }` с методами `new` (возвращает `Option<Stats>`, отсеивая null), `add` и `mean` — каждый метод содержит одну unsafe-строку с `SAFETY`-обоснованием «указатель получен из `stats_new`, не освобождён, других ручек нет». Освобождение перенесено в `impl Drop for Stats`, вызывающий `stats_free`, поэтому клиент не может забыть его вызвать. Прогон: `mean = 20` для 10, 20 и 30, а счётчик живых объектов C-стороны идёт 0 → 1 → 0 — утечки нет, `Drop` сработал сам на выходе из блока.

**Вариант 2 (структура прозрачна для Rust).** Раскладку C-структуры можно повторить на стороне Rust с `#[repr(C)]` — тогда поля читаются напрямую, без вызова через границу. Файл `p2/stats/f9_transparent.rs`:

```rust
/// Раскладка повторена на стороне Rust -- значит, стала частью договора.
#[repr(C)]
struct StatsRaw {
    sum: i64,
    n: c_int,
}
```

Функция `stats_mean` при этом не нужна вовсе — среднее считает Rust:

```rust
    /// Среднее считает Rust: поля читаются напрямую, вызова в C нет.
    fn mean(&self) -> f64 {
        // SAFETY: raw жив и указывает на структуру C с раскладкой StatsRaw
        // (это и есть цена варианта: раскладка -- часть контракта).
        let s = unsafe { &*self.raw };
        if s.n == 0 { 0.0 } else { s.sum as f64 / s.n as f64 }
    }
```

```
$ rustc --edition 2024 f9_transparent.rs -L .
$ ./f9_transparent.exe
size_of::<StatsRaw>() = 16
live before = 0
n    = 3
mean = 20
live after  = 0
```

*Сравнение.* Ответ тот же, но появилось новое: Rust видит поля — можно прочитать `n` без отдельной C-функции, посчитать что угодно на месте и не платить за вызов через границу. Размер 16 сходится с ручным счётом §8.2.3: `long long` (8) + `int` (4) + 4 байта хвостового паддинга до выравнивания 8. Цена — **раскладка стала частью договора**: теперь любое изменение `struct Stats` на стороне C (добавили поле, поменяли `int` на `long long`) обязано быть повторено в `StatsRaw`, иначе Rust начнёт читать чужие байты, и никто об этом не предупредит — линкер сверяет имена, а не структуры (Г24.Ч2.З5). Непрозрачный вариант такой связи не создаёт вовсе, поэтому по умолчанию правилен он; прозрачный оправдан, когда обе стороны развиваются вместе (общий репозиторий, общая сборка) и лишние вызовы через границу действительно мешают.

## Уточнения к тексту главы

Три наблюдения, полученные на прогонах, расходятся с текстом главы или условия — фиксируем их здесь, чтобы учесть при сквозной ревизии.

**1. Условие Г24.Ч2.З1: `safe fn labs` честна с оговоркой.** Условие просит обосновать, «почему обе пометки честны». Для `sqrt` обоснование безоговорочно: функция определена на всём множестве `double`, отрицательный аргумент даёт `NaN` — доменную ошибку, а не UB. Для `labs` — почти: стандарт C прямо оговаривает, что при непредставимом результате поведение не определено (C5, §7.24.6.1: «If the result cannot be represented, the behavior is undefined»), а модуль `c_long::MIN` в `c_long` непредставим. Прогон `p2/f1_labs_min.rs` показывает, что наша реализация возвращает само `-2147483648`. Значит, пометка `safe` у `labs` опирается на дополнительное обещание вызывающего («`c_long::MIN` сюда не придёт»), которого у `sqrt` не требуется, — и условие стоило бы либо сформулировать как «объясните, при каком единственном входе пометка `safe` у `labs` становится обещанием, а не фактом», либо взять вместо `labs` другую тотальную функцию. Разобрано в решении Г24.Ч2.З1.

**2. §24.2.3: вывод паники на границе приведён сокращённо.** Глава показывает пять строк — две пары `panicked at` и `thread caused non-unwinding panic. aborting.`. Фактический вывод (наш `p2/divlib/app_panic.exe`) содержит между ними ещё две вещи: строку `note: run with 'RUST_BACKTRACE=1' environment variable to display a backtrace` после первой паники и **полный блок `stack backtrace:`** после второй — вторая, неразматывающая паника печатает трассу всегда, независимо от переменной окружения (в трассе видны кадры `rust_checked_div` и `main`). Сокращение уместно, но подпись «Проверено:» рядом с листингом читается как «вывод приведён дословно». Стоит либо оговорить сокращение, либо привести вывод целиком.

**3. Терминология: «niche-оптимизация» против «нишевой».** §16.2.3 вводит термин в форме «**niche**-оптимизация» (R6), §24.2.2 ссылается на тот же параграф словами «**нишевая** оптимизация». Расхождение косметическое, но чеклист ревизии требует единой терминологии между главами — форму стоит выбрать одну.

**Дополнение (не расхождение): `abort` уносит несброшенный вывод C-стороны.** В опыте Г24.Ч2.З6 C-клиент успел выполнить `printf` до вызова паникующей функции, но текст до консоли не дошёл: аварийное завершение не сбрасывает буферы stdio (§10.1.1, C5 §7.23.3), и при перенаправлении в файл на stdout не приходит ничего. Это усиливает правило главы «экспортируемая Rust-функция не должна паниковать»: авария на границе уносит не только управление, но и уже сделанную C-стороной работу.
