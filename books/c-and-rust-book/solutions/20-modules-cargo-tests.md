## Часть 20.1. Модули, crates и Cargo

### Г20.Ч1.З1

**Условие.** Создайте пакет `phrases` (`cargo new phrases`). В `src/main.rs` объявите inline-модуль `greetings` с публичной функцией `hello(name: &str) -> String` (соберите строку через `format!`). Вызовите её из `main` дважды: абсолютным путём и относительным. Предскажите вывод до запуска.

**Решение.** Начинаем с пакета — и читаем, что именно сообщает Cargo:

```
$ cargo new phrases
    Creating binary (application) `phrases` package
note: see more `Cargo.toml` keys and their definitions at https://doc.rust-lang.org/cargo/reference/manifest.html
```

Слово `binary (application)` — это §20.1.1: создан **пакет** с одним **бинарным crate**, корень которого — `src/main.rs`:

```
phrases
phrases/Cargo.toml
phrases/src
phrases/src/main.rs
```

плюс `.gitignore` из одной строки `/target` и инициализированный git-репозиторий (пакет создавался вне существующего репозитория).

*Предсказание.* Модуль `greetings` объявляется прямо в корне crate, значит текущий модуль для `main` — тот же корень. Абсолютный путь `crate::greetings::hello` и относительный `greetings::hello` обязаны привести к одной функции, поэтому вывод — две строки приветствия, отличающиеся только именем; ошибок видимости быть не должно, раз `hello` помечена `pub`.

Файл `p1/phrases/src/main.rs`:

```rust
// Г20.Ч1.З1: inline-модуль в корне бинарного crate.
mod greetings {
    // pub — иначе функция видна только внутри greetings (§20.1.2).
    pub fn hello(name: &str) -> String {
        format!("Hello, {name}!")
    }
}

fn main() {
    // Абсолютный путь: от корня crate.
    let absolute = crate::greetings::hello("Anna");
    // Относительный путь: от текущего модуля (здесь текущий модуль — тот же корень).
    let relative = greetings::hello("Boris");
    println!("{absolute}");
    println!("{relative}");
}
```

```
$ cargo run
   Compiling phrases v0.1.0 (...\p1\phrases)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.77s
     Running `target\debug\phrases.exe`
Hello, Anna!
Hello, Boris!
```

Предсказание совпало. Три детали, которые стоит проговорить:

1. **`pub` нужен только на `hello`,** а не на `mod greetings`: модуль объявлен в том же модуле, откуда его зовут (в корне), а «своё» видно без всяких разрешений (§20.1.2, правило 1). Стоило бы `main` переехать в другой модуль — и понадобился бы `pub mod`.
2. **`format!` возвращает `String`** — новую строку с собственным буфером (§17.1.3), поэтому возвращать её из функции безопасно: владение уезжает вызывающему, ничьих ссылок за собой не тянет (§15.3).
3. **Обе формы пути одинаково законны** в этой точке, потому что текущий модуль совпадает с корнем. Разница появится, как только вызов переедет вглубь дерева: относительный путь поедет вместе с кодом, абсолютный — нет (Г20.Ч1.З5).

**Ответ:** вывод — две строки, `Hello, Anna!` и `Hello, Boris!`; предсказание совпало. `crate::greetings::hello` и `greetings::hello` в корне crate — один и тот же элемент, записанный от корня и от текущего модуля; `pub` требуется на функции, но не на самом модуле, пока обращение идёт из его собственного родителя.

### Г20.Ч1.З2

**Условие.** Дано дерево: в корне crate — модуль `net`, в нём — публичный модуль `http` с публичными функциями `get` и `post`, рядом с `net` — функция `log`. Выпишите на бумаге: (а) абсолютные пути ко всем четырём элементам; (б) относительный путь из тела `get` к `post`; (в) два пути из тела `get` к `log` (через `super` и через `crate`). Затем постройте дерево в одном файле (тела функций — по одному `println!`) и проверьте все свои пути вызовами.

**Решение.** Сначала — бумага. Дерево:

```
   crate ─┬─ net ─── http ─┬─ get
          │                └─ post
          └─ log
```

**(а) Абсолютные пути** (от корня, звенья через `::`) — четыре элемента поддерева `net` плюс сама функция `log`, о которой отдельно спрашивает пункт (в):

| Элемент | Абсолютный путь |
|---|---|
| модуль `net` | `crate::net` |
| модуль `http` | `crate::net::http` |
| функция `get` | `crate::net::http::get` |
| функция `post` | `crate::net::http::post` |
| функция `log` | `crate::log` |

**(б) Из тела `get` к `post`.** Обе функции лежат в одном модуле `http`, а элементы своего модуля доступны по короткому имени: `post()`. Полная форма того же относительного пути — `self::post()`; `self` здесь ровно то же, что `.` в путях файловой системы.

**(в) Из тела `get` к `log`.** Функция `log` лежит в корне, а `get` — на два этажа глубже (`crate → net → http`), поэтому «наверх» подниматься дважды: `super::super::log(...)`. Абсолютная форма короче и от глубины не зависит: `crate::log(...)`.

Строим дерево. Файл `p1/m2_tree.rs`:

```rust
// Г20.Ч1.З2: дерево модулей и все формы путей.
//
//   crate ─┬─ net ─── http ─┬─ get
//          │                └─ post
//          └─ log

fn log(event: &str) {
    println!("log: {event}");
}

mod net {
    pub mod http {
        pub fn get() {
            println!("http::get");
            post(); // (б) сосед по модулю: короткое имя, оно же self::post
            super::super::log("get via super"); // (в) http → net → корень
            crate::log("get via crate"); // (в) сразу от корня
        }

        pub fn post() {
            println!("http::post");
        }
    }
}

// Ярлык только на http: `use crate::net;` в этой же области — E0255,
// имя net уже занято объявлением модуля.
use crate::net::http;

fn main() {
    http::get(); // crate::net::http::get через ярлык
    crate::net::http::post(); // тот же элемент полным абсолютным путём
    crate::log("main done"); // crate::log
}
```

```
http::get
http::post
log: get via super
log: get via crate
http::post
log: main done
```

Читается сверху вниз: `http::get` напечатал себя, изнутри позвал соседа (`http::post`) и дважды достучался до корня — обеими формами; затем `main` вызвал `post` полным путём и `log`. Все шесть путей из таблицы проверены: `crate::net` и `crate::net::http` — вызовом `crate::net::http::post()` (он проходит через оба звена) и ярлыком `use crate::net::http`, остальные — напрямую.

*Грабли, которых не было в условии.* Первая версия файла — ⛔ `p1/m2_tree_bad.rs` — начиналась с двух ярлыков, «чтобы проверить и путь к `net`»:

```rust
use crate::net; // (а) путь к модулю net
use crate::net::http; // (а) путь к модулю http
```

Этот файл не собирается:

```
error[E0255]: the name `net` is defined multiple times
  --> m2_tree_bad.rs:26:5
   |
11 | mod net {
   | ------- previous definition of the module `net` here
...
26 | use crate::net; // (а) путь к модулю net
   |     ^^^^^^^^^^ `net` reimported here
   |
   = note: `net` must be defined only once in the type namespace of this module
help: you can use `as` to change the binding name of the import
   |
26 | use crate::net as other_net; // (а) путь к модулю net
   |                ++++++++++++
```

Ярлык — это **имя в области видимости**, а не «пометка о существовании пути»: `use crate::net;` пытается завести в корне второе имя `net`, которое уже занято объявлением `mod net`. Отсюда E0255 и совет `as` (§20.1.3 — переименование при конфликте). Урок: до модуля, объявленного здесь же, ярлык не нужен — его имя и так в области видимости.

**Ответ:** (а) `crate::net`, `crate::net::http`, `crate::net::http::get`, `crate::net::http::post`, `crate::log`; (б) `post()`, в полной форме `self::post()`; (в) `super::super::log(...)` — по два звена вверх — и `crate::log(...)`. Все пути проверены прогоном `m2_tree.rs`, вывод — шесть строк, приведён выше. Побочно установлено: `use crate::net;` рядом с `mod net` в одной области — **E0255** «the name `net` is defined multiple times», лечится `as` или отказом от ненужного ярлыка.

### Г20.Ч1.З3

**Условие.** Перенесите модуль `greetings` из З1 в файл `src/greetings.rs`, оставив в `main.rs` объявление `mod greetings;`. Убедитесь, что поведение не изменилось. Затем, не удаляя `src/greetings.rs`, добавьте файл `src/greetings/mod.rs` с тем же содержимым и соберите. Запишите код и текст ошибки; объясните, из чего выбирает компилятор и почему отказывается выбирать сам.

**Решение.** Переезд механический (§20.1.4): в родителе остаётся объявление с точкой с запятой, тело уезжает в одноимённый файл. Файл `p1/phrases_file/src/main.rs`:

```rust
// Г20.Ч1.З3: тело модуля переехало в src/greetings.rs,
// здесь осталось только объявление — «дырка» в дереве модулей.
mod greetings;

fn main() {
    let absolute = crate::greetings::hello("Anna");
    let relative = greetings::hello("Boris");
    println!("{absolute}");
    println!("{relative}");
}
```

Файл `p1/phrases_file/src/greetings.rs`:

```rust
// Тело модуля greetings: файл — «заплатка» к объявлению mod greetings; в main.rs.
// Само слово mod здесь не повторяется: файл уже и есть модуль.
pub fn hello(name: &str) -> String {
    format!("Hello, {name}!")
}
```

```
$ cargo run
   Compiling phrases_file v0.1.0 (...\p1\phrases_file)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.65s
     Running `target\debug\phrases_file.exe`
Hello, Anna!
Hello, Boris!
```

Поведение не изменилось — и это главное наблюдение задания: **дерево модулей не зависит от того, как код разложен по файлам**. Пути в `main` остались прежними, хотя тело переехало. Обратите внимание и на то, чего в `greetings.rs` **нет**: слова `mod greetings { ... }`. Файл уже является телом модуля; повторить объявление внутри — значит завести `greetings::greetings`.

Теперь вторая половина. Кладём рядом старый стиль — `p1/phrases_dup/src/greetings/mod.rs` с тем же содержимым, не удаляя `p1/phrases_dup/src/greetings.rs`:

```
$ cargo build
   Compiling phrases_dup v0.1.0 (...\p1\phrases_dup)
error[E0761]: file for module `greetings` found at both "src\greetings.rs" and "src\greetings\mod.rs"
 --> src\main.rs:3:1
  |
3 | mod greetings;
  | ^^^^^^^^^^^^^^
  |
  = help: delete or rename one of them to remove the ambiguity
```

Код — **E0761**, процесс завершился с кодом 101. *Из чего выбирает компилятор.* Объявление `mod greetings;` — это поручение «найди тело». Правил поиска для модуля, объявленного в корне crate, два (§20.1.4): современное `src/greetings.rs` и старое `src/greetings/mod.rs`. Оба существуют — поручение имеет два одинаково законных исполнения.

*Почему не выбирает сам.* Любой автоматический выбор здесь — это молчаливое решение за автора, у которого половина кода уедет в игнорируемый файл. Ошибка называет **оба** пути и предлагает удалить или переименовать один: компилятор отказывается угадывать намерение, когда цена ошибки — потерянный без предупреждений код. Сравните с C: там двусмысленности не было, потому что не было и поиска — `#include "greetings.h"` называет файл явно; зато и структура проекта не следовала из кода, её приходилось дублировать в Makefile (§11.2.3).

**Ответ:** после переезда программа печатает те же `Hello, Anna!` / `Hello, Boris!` — дерево модулей от раскладки по файлам не зависит. Два файла-кандидата сразу дают **E0761** `file for module 'greetings' found at both "src\greetings.rs" and "src\greetings\mod.rs"` с подсказкой `delete or rename one of them to remove the ambiguity`; компилятор выбирает между современным стилем (`имя.rs`) и старым (`имя/mod.rs`) и отказывается решать сам, потому что молчаливый выбор оставил бы половину кода несобранной.

### Г20.Ч1.З4

**Условие.** *(понимание)* Не запуская, найдите ошибку и предскажите её код:

```rust
mod bank {
    fn vault_code() -> u32 {
        1234
    }

    pub fn balance() -> i64 {
        9000
    }
}

fn main() {
    println!("баланс: {}", bank::balance());
    println!("код: {}", bank::vault_code());
}
```

Проверьте сборкой. Почините двумя способами: (а) `pub` на `vault_code`; (б) не открывая `vault_code`, добавьте в `bank` публичную функцию, которая пользуется кодом внутри. Какой способ лучше и почему? Сравните с единственным инструментом C — `static` на уровне файла (§11.2.2): что умеет модуль, чего не умел файл?

**Решение.** *Предсказание.* Ошибка одна и она во второй строке `main`: `balance` помечена `pub`, а `vault_code` — нет, значит приватна по умолчанию и видна только внутри `bank` и его потомков (§20.1.2, правило 1). Обращение из корня crate — снаружи модуля, ждём **E0603** «function `vault_code` is private». Первая строка соберётся: `balance` открыта. Заметьте, что сам `mod bank` объявлен в корне без `pub`, но это не мешает — зовут его из его же родителя.

⛔ Файл `p1/m4_bank_bad.rs` — код условия дословно:

```
error[E0603]: function `vault_code` is private
  --> m4_bank_bad.rs:14:31
   |
14 |     println!("код: {}", bank::vault_code());
   |                               ^^^^^^^^^^ private function
   |
note: the function `vault_code` is defined here
  --> m4_bank_bad.rs:3:5
   |
 3 |     fn vault_code() -> u32 {
   |     ^^^^^^^^^^^^^^^^^^^^^^
```

Предсказание совпало: E0603, одна ошибка, и компилятор вдобавок показывает **место объявления** — чтобы не искать, где именно не хватает `pub`.

*Починка (а) — открыть функцию.* Файл `p1/m4_bank_pub.rs` отличается от предыдущего одним словом:

```rust
mod bank {
    pub fn vault_code() -> u32 {
        1234
    }
```

```
баланс: 9000
код: 1234
```

*Починка (б) — открыть операцию, а не данные.* Код остаётся приватным, наружу выходит то, ради чего он нужен. Файл `p1/m4_bank_api.rs`:

```rust
// Г20.Ч1.З4, починка (б): код остаётся приватным,
// наружу выходит операция, которой код нужен внутри.
mod bank {
    fn vault_code() -> u32 {
        1234
    }

    pub fn balance() -> i64 {
        9000
    }

    // Проверка кода: сравнение происходит внутри модуля,
    // сам код за границу модуля не выходит.
    pub fn code_matches(guess: u32) -> bool {
        guess == vault_code()
    }
}

fn main() {
    println!("баланс: {}", bank::balance());
    println!("код верный: {}", bank::code_matches(1234));
    println!("код верный: {}", bank::code_matches(1111));
}
```

```
баланс: 9000
код верный: true
код верный: false
```

*Какой способ лучше.* Второй, и разница не стилистическая. `pub fn vault_code()` — это обещание внешнему миру: «код хранилища всегда можно получить числом». Обещание придётся держать при любом рефакторинге: заведёте вы завтра хеш вместо числа или полезете за кодом в файл — сигнатура `-> u32` останется в чужом коде. `code_matches` обещает несравнимо меньше — «умею проверять догадку», — и внутри может измениться как угодно. Плюс к тому сам секрет физически не покидает модуль: наружу уходит `bool`, а не 1234.

Правило §20.1.2 формулирует это одной строкой: **каждый `pub` — обещание**; начинайте со всего приватного и открывайте ровно то, что просит компилятор, а не то, что удобно позвать.

*Сравнение с C.* В C единственный инструмент сокрытия — `static` на уровне файла (§11.2.2): имя либо видно всей программе, либо только своей единице трансляции. Модуль Rust умеет три вещи, которых `static` не умел:

1. **Границы на любом уровне.** Модулей может быть сколько угодно и вложены они как угодно; сокрытие живёт не «на файл», а на каждый узел дерева. «Спрятать функцию внутри половины файла» в C нельзя, в Rust — обычное дело (вложенный `mod`).
2. **Промежуточные ступени.** `pub(crate)` — «видно всему моему crate, но не пользователям библиотеки» (§20.1.2). В C такого нет вовсе: между `static` и глобальным именем пусто.
3. **Раскладка по файлам отвязана от видимости.** В C граница сокрытия совпадает с границей файла; в Rust модуль может переехать в файл, а видимость не изменится ни на йоту (Г20.Ч1.З3, Г20.Ч1.З5).

**Ответ:** ошибка — во второй строке `main`, код **E0603** `function 'vault_code' is private` (плюс `note` с местом объявления); первая строка законна. Починка (а) — `pub fn vault_code`, программа печатает `баланс: 9000` / `код: 1234`. Починка (б) — приватный `vault_code` плюс публичная `code_matches(guess: u32) -> bool`, вывод `баланс: 9000` / `код верный: true` / `код верный: false`. Лучше (б): наружу уходит операция, а не секрет, и обещание пользователям минимально. Против `static` из C модуль даёт границы на каждом уровне дерева, промежуточную ступень `pub(crate)` и независимость видимости от раскладки по файлам.

**Вариант 2 (безопасное представление вместо предиката).** Публичной можно сделать не проверку, а **представление** секрета — то, что показывать не жалко. Файл `p1/m4_bank_masked.rs`:

```rust
// Г20.Ч1.З4, вариант 2: наружу выдаётся не решение «да/нет»,
// а безопасное представление кода — последние две цифры под маской.
mod bank {
    fn vault_code() -> u32 {
        1234
    }

    pub fn balance() -> i64 {
        9000
    }

    pub fn masked_code() -> String {
        let code = vault_code();
        format!("**{}", code % 100)
    }
}

fn main() {
    println!("баланс: {}", bank::balance());
    println!("код: {}", bank::masked_code());
}
```

```
баланс: 9000
код: **34
```

*Сравнение.* Оба варианта оставляют `vault_code` приватной, но отвечают на разные вопросы пользователя. `code_matches` отвечает на «я угадал?» и не даёт ничего, кроме `true`/`false`, — это форма для проверки доступа. `masked_code` отвечает на «что показать в интерфейсе?» и отдаёт часть секрета сознательно и в безопасном виде — форма для отображения (так печатают хвост номера карты). Предикат строже: по нему код нельзя восстановить вовсе, тогда как маска сужает перебор с 10 000 до 100. Выбирать надо по задаче, а не по вкусу: если оба применения нужны, в модуле живут обе публичные функции, и обе — вместо одного `pub` на сам код.

### Г20.Ч1.З5

**Условие.** *(понимание)* Вернитесь к ⛔-примеру 4 из §20.1.3 (`use` в корне, вызов в модуле `report`). Объясните по тексту диагностик, почему компилятор выдал **обе**: ошибку E0433 и предупреждение unused import — как они связаны. Почините тремя способами, названными в тексте, и ответьте: какой из них продолжит работать, если модуль `report` переедет в отдельный файл `src/report.rs`?

**Решение.** ⛔ Воспроизводим пример дословно — файл стенда так и назван, `p1/use_scope.rs`:

```rust
use crate::stats::words; // ярлык действует только в этой области — корне crate

mod report {
    pub fn print_stats(text: &str) {
        // ⛔ внутри модуля report ярлык из корня не действует
        println!("слов: {}", words::count(text));
    }
}
```

```
error[E0433]: cannot find module or crate `words` in this scope
  --> use_scope.rs:24:30
   |
24 |         println!("слов: {}", words::count(text));
   |                              ^^^^^ use of unresolved module or unlinked crate `words`
   |
   = help: you might be missing a crate named `words`
help: consider importing this module through its public re-export
   |
22 +     use crate::words;
   |

warning: unused import: `crate::stats::words`
  --> use_scope.rs:19:5
   |
19 | use crate::stats::words; // ярлык действует только в этой области — корне crate
   |     ^^^^^^^^^^^^^^^^^^^
   |

```

*Почему диагностик две и как они связаны.* Это две проекции одного факта — «ярлык и место вызова оказались в разных областях видимости».

- Со стороны **вызова** (модуль `report`): имени `words` в этой области нет, и компилятор честно перечисляет, чем оно могло бы быть, — модулем или crate («use of unresolved module or unlinked crate»). Отсюда E0433 и предположение `help: you might be missing a crate named 'words'`: снаружи `report` компилятор не знает, что вы имели в виду соседний модуль.
- Со стороны **объявления** (корень crate): ярлык завёл имя `words`, но в корне им никто не воспользовался. Отсюда `warning: unused import`.

Иными словами: ошибка означает «здесь имени нет», предупреждение — «а там, где оно есть, оно никому не понадобилось». Эта пара в одной сборке — характерная подпись именно этой ошибки; увидели её вместе — ищите `use` не в той области.

Полезная деталь нашего прогона: rustc 1.97 добавляет к E0433 ещё и `help: consider importing this module through its public re-export` с готовой строкой `use crate::words;` — потому что ярлык в корне сам по себе создаёт путь `crate::words` (правда, приватный: чтобы совет сработал, ярлык пришлось бы объявить как `pub use`). В §20.1.3 вывод примера приведён без этого блока — при чтении главы имейте в виду, что компилятор скажет чуть больше.

*Три починки.* Все три названы в тексте главы; собираем их в одном файле `p1/m5_fixes.rs`, по модулю на способ:

```rust
// Починка 1: ярлык объявлен там, где им пользуются.
mod report_use {
    use crate::stats::words;

    pub fn print_stats(text: &str) {
        println!("слов (use внутри): {}", words::count(text));
    }
}

// Починка 2: путь от родителя — родитель report_super — корень crate.
mod report_super {
    pub fn print_stats(text: &str) {
        println!("слов (super): {}", super::stats::words::count(text));
    }
}

// Починка 3: абсолютный путь от корня.
mod report_crate {
    pub fn print_stats(text: &str) {
        println!("слов (crate): {}", crate::stats::words::count(text));
    }
}
```

```
слов (use внутри): 4
слов (super): 4
слов (crate): 4
```

*Что будет после переезда в файл.* Проверяем экспериментом, а не рассуждением: пакет `p1/report_pkg` раскладывает те же три модуля по файлам — `src/report_use.rs`, `src/report_super.rs`, `src/report_crate.rs`, а `src/stats.rs` держит счётчик. Корень `p1/report_pkg/src/main.rs`:

```rust
// Г20.Ч1.З5, вторая половина: те же три починки, но каждый report — в своём файле.
// Вопрос задания: какая из починок переживёт переезд модуля в отдельный файл.
mod stats;

mod report_crate;
mod report_super;
mod report_use;

fn main() {
    let text = "во поле берёза стояла";
    report_use::print_stats(text);
    report_super::print_stats(text);
    report_crate::print_stats(text);
}
```

```
$ cargo run
   Compiling report_pkg v0.1.0 (...\p1\report_pkg)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.61s
     Running `target\debug\report_pkg.exe`
слов (use внутри): 4
слов (super): 4
слов (crate): 4
```

**Работают все три** — и это ровно тот вывод, ради которого задание задано. Переезд тела модуля в файл не двигает модуль по дереву: `report_use` как был потомком корня, так им и остался. Поэтому:

- ярлык `use crate::stats::words;` переезжает **вместе с телом** и продолжает действовать в своей (той же самой) области;
- `super::` по-прежнему означает корень crate, потому что родитель не изменился;
- `crate::` вообще ни от чего не зависит.

А вот от чего каждая форма зависит на самом деле — видно, если двигать модуль **по дереву**, а не по файлам: вложите `report_super` внутрь другого модуля, и `super::` начнёт указывать на этот модуль, а не на корень; `crate::` переживёт и это. Отсюда и совет §20.1.3 предпочитать абсолютные пути: код чаще меняет место в дереве, чем вызываемая функция.

**Ответ:** E0433 говорит «в области видимости `report` имени `words` нет», предупреждение unused import — «в корне, где ярлык объявлен, им не воспользовались»; это две стороны одной ошибки — ярлык и вызов в разных областях. Все три починки (перенести `use` внутрь `report`, писать `super::stats::words::count`, писать `crate::stats::words::count`) дают `слов: 4` и **все три переживают переезд `report` в `src/report.rs`**: раскладка по файлам не меняет положения модуля в дереве. Разница между ними проявляется при переносе модуля по дереву, где `crate::`-путь единственный не требует правок.

### Г20.Ч1.З6

**Условие.** *(понимание)* «`mod` — это `#include` на новый лад» — опровергните тремя различиями, с опорой на §11.1.1/§11.1.4 и §20.1.4. Обязательные пункты: что физически делает препроцессор (§11.1.1) и что — `mod`; почему заголовкам C нужны стражи включения, а модулям Rust — нет; что случится при повторном `mod` (код ошибки) и при повторном `#include` без стража.

**Решение.** Три различия — и каждое подтверждено опытом на стенде.

**Различие 1: что физически происходит.** `#include` — директива **препроцессора**: он берёт содержимое файла и вставляет его в текущую единицу трансляции как текст (§11.1.1), после чего компилятор видит один сплошной поток. Измерение на стенде: файл `p1/c6_main.c` — 10 строк, после `gcc -E` от него остаётся 1073 строки. Файл вырос в сто раз, и почти всё это — вставленный `<stdio.h>`.

`mod` не вставляет ничего. Это **объявление узла дерева модулей**: компилятор находит файл по правилам поиска (§20.1.4) и подключает его как отдельный узел — с собственной областью видимости и собственным именем. Ни один символ никуда не копируется; текстовой фазы у Rust нет вовсе.

**Различие 2: почему C нужны стражи, а Rust — нет.** Раз `#include` вставляет текст, два включения одного заголовка вставляют текст **дважды**, и объявления типов оказываются продублированы. Проверяем: `p1/c6_main.c` включает `c6_point.h` двумя строками подряд.

```c
/* Г20.Ч1.З6: два #include одного заголовка без стража — текстовая вставка дважды. */
#include <stdio.h>
#include "c6_point.h"
#include "c6_point.h" /* вторая вставка того же текста */
```

```
$ gcc -std=c17 -Wall -Wextra c6_main.c -o c6_main.exe
In file included from c6_main.c:4:
c6_point.h:2:8: error: redefinition of 'struct Point'
    2 | struct Point {
      |        ^~~~~
In file included from c6_main.c:3:
c6_point.h:2:8: note: originally defined here
    2 | struct Point {
      |        ^~~~~
```

Считаем сами определения после препроцессора: `grep -c 'struct Point {'` даёт **2** для версии без стража и **1** для версии со стражем (`p1/c6_guard.h`, `p1/c6_guard_main.c` — та же пара `#include`, но заголовок обёрнут в `#ifndef/#define/#endif`). Со стражем программа собирается и печатает `point: 1 2`.

Обратите внимание, как выглядит диагностика: ошибка указывает на **строку заголовка**, а «виновата» строка `#include` в другом файле — её приходится искать по служебным строкам `In file included from`. Это цена текстовой вставки: сообщение приходит в чужих координатах.

Модулям Rust страж не нужен, потому что подключать дважды нечего: файл привязывается к дереву **ровно одним** объявлением `mod`, а все остальные обращения идут путями и ярлыками `use` (§20.1.4). `use` при этом ничего не подключает и не компилирует — только заводит короткое имя.

**Различие 3: что бывает при повторе.** Повторный `#include` без стража — ошибка **в чужом коде и с трассой препроцессора** (см. выше). Повторный `mod` — ошибка **в самом объявлении**. Файл `p1/m6_mod_twice.rs`:

```rust
mod stats {
    pub fn answer() -> u32 {
        1
    }
}

mod stats { // ⛔ повторное объявление модуля с тем же именем
    pub fn answer() -> u32 {
        2
    }
}
```

```
error[E0428]: the name `stats` is defined multiple times
 --> m6_mod_twice.rs:8:1
  |
2 | mod stats {
  | --------- previous definition of the module `stats` here
...
8 | mod stats { // ⛔ повторное объявление модуля с тем же именем
  | ^^^^^^^^^ `stats` redefined here
  |
  = note: `stats` must be defined only once in the type namespace of this module
```

Компилятор показывает **оба** места и объясняет правило: имя в пространстве типов модуля должно быть определено один раз. Никакого «ритуала защиты» при этом не существует — защищать не от чего, потому что дублирования текста не бывает.

Отдельно стоит назвать и **не-ошибку**: если один и тот же файл объявить `mod`-ом в двух разных crate одного пакета (например, и в `lib.rs`, и в `main.rs`), ошибки не будет вовсе — файл просто скомпилируется дважды, дав два независимых типа-двойника. Что из этого выходит, разобрано в Г20.Ч1.З8.

**Ответ:** (1) препроцессор физически вставляет текст файла в единицу трансляции — 10 строк `c6_main.c` превращаются в 1073, — а `mod` вставляет ноль символов: он объявляет узел дерева модулей и подключает файл как отдельную область видимости; (2) стражи нужны потому, что двойная вставка дублирует объявления (после `-E` — два `struct Point` против одного со стражем), а в Rust дублировать нечего: файл входит в дерево ровно одним `mod`, остальное — пути и `use`; (3) повторный `#include` без стража — `error: redefinition of 'struct Point'` в координатах заголовка, с трассой `In file included from`; повторный `mod` — **E0428** `the name 'stats' is defined multiple times` прямо на втором объявлении, с указанием первого.

### Г20.Ч1.З7

**Условие.** *(понимание)* Дана структура в модуле `config`:

```rust
mod config {
    pub struct Config {
        pub retries: u32,
        timeout_ms: u32,
    }

    pub fn default() -> Config {
        Config { retries: 3, timeout_ms: 500 }
    }
}
```

Для каждой из четырёх строк в `main` — `let c = config::default();`, `println!("{}", c.retries);`, `println!("{}", c.timeout_ms);`, `let d = config::Config { retries: 1, timeout_ms: 100 };` — предскажите: соберётся или нет, и с каким кодом ошибки. Проверьте. Объясните, почему литерал структуры не собрался, хотя сама структура `pub`, — и как это же свойство защищает инвариант `len ≤ cap` у `Vec` (§17.1.1, §20.1.2).

**Решение.** *Предсказание по строкам.*

| Строка | Предсказание |
|---|---|
| `let c = config::default();` | соберётся: `default` — `pub`, `Config` — `pub` |
| `println!("{}", c.retries);` | соберётся: поле помечено `pub` |
| `println!("{}", c.timeout_ms);` | ⛔ **E0616** — поле приватно (§20.1.2, пример 3) |
| `let d = config::Config { ... };` | ⛔ ошибка: литерал требует **все** поля, а `timeout_ms` снаружи не виден; кода ошибки не знаем — ждём отдельный |

⛔ Файл `p1/m7_config.rs` — модуль условия и все четыре строки:

```
error[E0616]: field `timeout_ms` of struct `Config` is private
  --> m7_config.rs:16:22
   |
16 |     println!("{}", c.timeout_ms);
   |                      ^^^^^^^^^^ private field

error: aborting due to 1 previous error
```

Ошибка **одна**: компилятор доложил про чтение приватного поля и остановился, до литерала проверка не дошла. Чтобы увидеть вторую диагностику, третью строку из `main` надо убрать — тогда очередь доходит до четвёртой. ⛔ Файл `p1/m7_config_lit.rs`:

```rust
fn main() {
    let c = config::default();
    println!("{}", c.retries);
    let d = config::Config { retries: 1, timeout_ms: 100 };
    println!("{}", d.retries);
}
```

```
warning: field `timeout_ms` is never read
 --> m7_config_lit.rs:6:9
  |
4 |     pub struct Config {
  |                ------ field in this struct
5 |         pub retries: u32,
6 |         timeout_ms: u32,
  |         ^^^^^^^^^^
  |
  = note: `#[warn(dead_code)]` (part of `#[warn(unused)]`) on by default

error[E0451]: field `timeout_ms` of struct `Config` is private
  --> m7_config_lit.rs:17:42
   |
17 |     let d = config::Config { retries: 1, timeout_ms: 100 };
   |                                          ^^^^^^^^^^ private field
```

Итог по строкам: 1 — собирается, 2 — собирается, 3 — **E0616**, 4 — **E0451**. Предсказание совпало, включая догадку, что код будет отдельный: компилятор различает *чтение* приватного поля (E0616) и *построение значения* с приватным полем (E0451). Заодно видно `dead_code`-предупреждение: поле, которое никто законно не читает, компилятор считает мёртвым — ещё один намёк, что приватное поле без методов доступа бессмысленно.

*Почему литерал не собрался, хотя структура `pub`.* Публичность типа и публичность полей — разные вещи (§20.1.2, правило 1 с исключениями). `pub struct Config` разрешает **называть тип** снаружи: писать `config::Config` в сигнатурах, принимать и возвращать значения. Литерал `Config { ... }` — не упоминание типа, а **построение значения**, и оно требует перечислить все поля до единого. Раз одно из полей снаружи не видно, снаружи невозможно и построение — какое бы значение вы ни написали для `timeout_ms`, вы обращаетесь к имени, которого для вас не существует.

Отсюда практический вывод, знакомый по §16.1.2: если у типа есть хоть одно приватное поле, снаружи его создают **только** через функцию-конструктор модуля (здесь — `config::default`). Это не ограничение, а точка контроля.

*Как это защищает инвариант `Vec`.* У `Vec` (§17.1.1) длина и ёмкость связаны обещанием: `len ≤ cap`, и первые `len` ячеек буфера инициализированы. Обещание держится ровно потому, что `len` — приватное поле: изменить его можно только кодом самого `Vec` (`push`, `pop`, `truncate`), а этот код инвариант поддерживает. Будь поле публичным, законной была бы строка `v.len = 100` — и следующее же чтение `v[50]` полезло бы в неинициализированную память, то есть в неопределённое поведение (§13.1). E0451 — это тот же самый запрет, только с другой стороны: снаружи нельзя не только *испортить* поле, но и *задать* его при создании, минуя конструктор.

В C (§9.1.1) обе двери были открыты: наш `Vec` из главы 9 держался на договорённости «не трогайте поля напрямую», а компилятор в этой договорённости не участвовал.

**Ответ:** строки 1 и 2 собираются; строка 3 — **E0616** `field 'timeout_ms' of struct 'Config' is private`; строка 4 — **E0451** с тем же текстом, но другим кодом (и увидеть её можно, только убрав строку 3: сборка обрывается на первой ошибке приватности). Литерал не собирается потому, что построение значения требует всех полей, а `pub` на структуре открывает лишь имя типа, но не его поля; единственный законный путь снаружи — конструктор модуля. Тем же механизмом `Vec` защищает `len ≤ cap`: приватность полей делает невозможными и порчу (`v.len = 100`), и создание в обход конструктора, поэтому инвариант поддерживается кодом, который за него отвечает.

**Вариант 2 (конструктор с проверкой вместо публичного поля).** Раз приватность — это точка контроля, ею можно воспользоваться: закрыть **оба** поля и выдать наружу метод чтения и конструктор, который чинит недопустимые значения. Файл `p1/m7_config_ok.rs`:

```rust
mod config {
    pub struct Config {
        pub retries: u32,
        timeout_ms: u32,
    }

    impl Config {
        // Метод доступа: наружу отдаём значение, а не право его менять.
        pub fn timeout_ms(&self) -> u32 {
            self.timeout_ms
        }
    }

    pub fn default() -> Config {
        Config { retries: 3, timeout_ms: 500 }
    }

    // Конструктор с проверкой: ноль вместо таймаута не пропускаем.
    pub fn with_timeout(retries: u32, timeout_ms: u32) -> Config {
        let timeout_ms = if timeout_ms == 0 { 1 } else { timeout_ms };
        Config { retries, timeout_ms }
    }
}
```

```

```

Четыре строки вывода: `retries` и `timeout_ms()` у значения из `default` (3 и 500), затем у значения из `with_timeout(1, 0)` — `retries` равен 1, а нулевой таймаут превратился в 1.

*Сравнение.* Публичное поле (`pub retries`) — самая дешёвая форма: ни метода, ни проверки, чтение и запись напрямую. Она годится, пока у поля **нет инварианта**: любое значение `u32` для числа повторов осмысленно. Приватное поле с методом доступа дороже на одну строку, но покупает два права: запретить запись (метод отдаёт копию, а не `&mut`) и в любой момент изменить внутреннее представление, не трогая пользователей — хоть хранить длительность в наносекундах. Конструктор `with_timeout` добавляет к этому третье право: **не дать построить недопустимое значение** — ровно то, чем `Vec` защищает `len ≤ cap`. Правило выбора простое: поле без инварианта можно открыть, поле с инвариантом — только через методы.

### Г20.Ч1.З8

**Условие.** *(прикладное)* Библиотека переводов единиц: пакет `units` с библиотечным и бинарным crate. В библиотеке — модули `length` (`m_to_cm`, `cm_to_m`) и `mass` (`kg_to_g`, `g_to_kg`), все функции над `f64`; в корне — реэкспорт самой ходовой: `pub use length::m_to_cm;`. Бинарник печатает три строки перевода (одну — через реэкспорт, две — через модули). Модули — в отдельных файлах. Ожидаемый вывод при значениях 2.5 м, 42 см, 1.5 кг:

```
2.5 м = 250 см
42 см = 0.42 м
1.5 кг = 1500 г
```

**Решение.** Пакет с двумя crate — та самая форма из §20.1.1: в `src/` лежат и `lib.rs`, и `main.rs`. Создаём библиотекой (`cargo new --lib units`) и дописываем бинарник.

Корень библиотеки, `p1/units/src/lib.rs` — «оглавление» и ничего больше:

```rust
// Г20.Ч1.З8: корень библиотеки — «оглавление» пакета units.
pub mod length;
pub mod mass;

// Реэкспорт самой ходовой функции: снаружи она доступна как units::m_to_cm.
pub use length::m_to_cm;
```

`p1/units/src/length.rs`:

```rust
// Переводы длины.

pub fn m_to_cm(m: f64) -> f64 {
    m * 100.0
}

pub fn cm_to_m(cm: f64) -> f64 {
    cm / 100.0
}
```

`p1/units/src/mass.rs`:

```rust
pub fn kg_to_g(kg: f64) -> f64 {
    kg * 1000.0
}

pub fn g_to_kg(g: f64) -> f64 {
    g / 1000.0
}
```

Бинарный crate, `p1/units/src/main.rs`, пользуется библиотекой **по имени пакета** — как посторонний код (§20.1.1):

```rust
// Бинарный crate пакета units: библиотека подключается по имени пакета.
use units::{length, mass};

fn main() {

    let cm = 42.0;
    let kg = 1.5;

    // Через реэкспорт из корня библиотеки.
    println!("{m} м = {} см", units::m_to_cm(m));
    // Через модули.
```


Вывод совпал с ожидаемым посимвольно, и по дороге подтвердились две вещи из ранних глав. Первая: `Display` для `f64` печатает **кратчайшую запись, которая читается обратно в то же число**, поэтому `250.0` выводится как `250`, а не `250.0`. Вторая: `42.0 / 100.0` даёт ровно тот же `f64`, что литерал `0.42` (деление в IEEE-754 округляется корректно, §2.3), — иначе мы увидели бы хвост вида `0.42000000000000004`.

Три границы видимости, ради которых задание и задано:

- `pub mod length;` и `pub mod mass;` — модули открыты, значит их `pub fn` доступны снаружи crate по путям `units::length::cm_to_m` и `units::mass::kg_to_g`. Уберите `pub` у `mod` — и функции пропадут для внешнего мира, оставаясь публичными «внутри забора» (§20.1.2, правило 2).
- `pub use length::m_to_cm;` в корне даёт **второе** имя той же функции — `units::m_to_cm`. Внутренняя планировка (в каком модуле она живёт) перестаёт быть частью публичного договора: перенесёте функцию в другой модуль — поправите одну строку реэкспорта, пользователи не заметят.
- `use units::{length, mass};` в `main.rs` — вложенный список ярлыков (§20.1.3). Идиома «функции зовём через родительский модуль» соблюдена: в коде стоит `length::cm_to_m(cm)`, и сразу видно, что функция не местная.

*Типичная неверная попытка.* Бинарнику «неудобно» писать имя пакета, и рука сама тянется подключить файл модуля напрямую — `mod length;` в `main.rs`. Файл `p1/units_modmain/src/main.rs` показывает, чем это кончается (в `length.rs` того же пакета для наглядности заведён собственный тип):

Ошибка стоит того, чтобы её увидеть один раз в жизни: типы называются **одинаково**, объявлены в **одном и том же файле** (компилятор дважды показывает `src\length.rs:2:1` — как «ожидаемый» и как «найденный» тип), и всё равно несовместимы. Файл, объявленный и в `lib.rs`, и в `main.rs`, компилируется дважды и даёт два независимых узла в двух разных crate — двойников с несовпадающими типами. Реэкспорт даёт короткое имя `units::m_to_cm`, не привязывая пользователя к внутренней планировке. Подключать файл модуля библиотеки вторым `mod` из `main.rs` нельзя: получаются два crate-двойника и **E0308** на типах с одинаковыми именами.

**Вариант 2 (старый стиль файлов-модулей).** Ту же раскладку можно записать вторым способом из §20.1.4: не `src/length.rs`, а `src/length/mod.rs`. Пакет `p1/units_oldstyle` отличается от основного только расположением файлов:

```
units_oldstyle/src/main.rs
```

Содержимое файлов и текст `lib.rs` не меняются ни на символ, вывод — тот же:

*Сравнение.* Стили равноправны для компилятора и различаются эргономикой. Современный (`length.rs`) короче и лучше виден в дереве файлов: имя модуля — имя файла, никаких одинаковых `mod.rs` в списке вкладок редактора. Старый (`length/mod.rs`) заранее готовит место под подмодули: если завтра у `length` появится потомок `imperial`, ему всё равно нужен каталог `length/`, и при современном стиле рядом окажутся и файл `length.rs`, и каталог `length/` — раскладка, которую многие считают некрасивой. Смешивать стили в одном проекте не стоит (а для одного и того же модуля — прямо запрещено: E0761, Г20.Ч1.З3); выбирать — по тому, ожидаются ли подмодули.

### Г20.Ч1.З9

**Условие.** *(прикладное)* Статистика двух кубиков: в пакете с зависимостью `rand` бросьте пару кубиков 1000 раз и посчитайте `HashMap`-ом частоту каждой суммы (2–12); напечатайте частоты по возрастанию суммы (обход `for sum in 2..=12` + `get`, чтобы порядок не зависел от `HashMap` — §17.2.1). До запуска предскажите, какая сумма встретится чаще всего и почему. Затем объясните: зачем понадобилась строка `use rand::RngExt;` — воспроизведите E0599 без неё и найдите в тексте ошибки прямой ответ (§19.2, §20.1.4).

**Решение.** *Предсказание.* Сумма двух костей — не равномерная величина. Способов получить каждую сумму столько, сколько пар `(a, b)` её дают: 2 — одна пара (1+1), 3 — две (1+2, 2+1), …, 7 — **шесть** (1+6, 2+5, 3+4, 4+3, 5+2, 6+1), затем симметрично вниз до 12 — одна. Всего пар 36, поэтому вероятность семёрки 6/36 ≈ 0,167, а двойки и двенадцатки — 1/36 ≈ 0,028. На 1000 бросков ждём около 167 семёрок и около 28 двоек; **чаще всего должна выпасть сумма 7**, а картина частот — «домик» с вершиной посередине.

Пакет `p1/dice2`; зависимость добавлена командой `cargo add rand`, которая вписала в `Cargo.toml` строку `rand = "0.10.2"`. Файл `p1/dice2/src/main.rs`:

```rust
// Г20.Ч1.З9: пара кубиков, 1000 бросков, частоты сумм.
use rand::RngExt; // трейт: без него нет метода random_range (§19.2, §20.1.4)
use std::collections::HashMap;

fn main() {
    let mut rng = rand::rng();
    let mut freq: HashMap<u32, u32> = HashMap::new();

    for _ in 0..1000 {
        let a: u32 = rng.random_range(1..=6);
        let b: u32 = rng.random_range(1..=6);
        *freq.entry(a + b).or_insert(0) += 1;
    }

    // Обход по возрастанию суммы: порядок не зависит от HashMap (§17.2.1).
    for sum in 2..=12 {
        println!("{sum}: {}", freq.get(&sum).unwrap_or(&0));
    }
}
```

```
11: 45
12: 29
```

*Сравнение.* `HashMap` платит за общность: хеширование ключа на каждом обращении, выделение буфера в куче, недетерминированный порядок обхода (§17.2.1) — и всё это ради возможности иметь **произвольные** ключи. Массив ничего этого не требует: 13 ячеек на стеке, доступ по индексу за одно сложение, порядок обхода естественный. Цена — жёсткие предположения: ключи обязаны быть небольшими неотрицательными целыми, идущими подряд, а любое значение вне 0…12 даст панику по выходу за границу (§15.3.2) вместо тихого добавления новой записи. Правило выбора: плотный и заранее известный диапазон ключей — массив; разреженные, заранее неизвестные или нечисловые ключи (слова, символы) — `HashMap`. Заметьте и мелочь, из-за которой пришлось поменять тип: индекс в Rust имеет тип `usize`, поэтому броски объявлены `usize`, а не `u32`.

```rust
pub fn word_count(text: &str) -> usize {
```

*От какой ошибки защищает `expected`.* От **ложного зелёного**. `#[should_panic]` без параметра засчитывает тесту любую панику — в том числе такую, которая к проверяемому поведению отношения не имеет:

- опечатка в настроечном коде теста (`v[10]` на векторе из трёх элементов) — паника есть, тест «прошёл»;
- функция начала паниковать раньше и по другой причине (например, из-за переполнения при подсчёте), а мы думаем, что проверили пустой текст;
- сообщение осталось прежним, но **условие** паники изменили — тест этого не заметит.

С `expected` тест проверяет не только факт паники, но и её причину — по подстроке сообщения. Обратная сторона: сообщение становится частью контракта. Поэтому подстроку берут короткую и смысловую (`"слов нет"`), а не копируют целиком: переформулировка «пустой текст» в «в тексте нет слов» не должна ронять тест, а вот исчезновение слов «слов нет» — должна.

**Ответ:** тесты — `avg_len_on_known_text` (`avg_word_len("кот на крыше") == 3`: 10 непробельных символов на 3 слова, деление целочисленное) и `avg_len_panics_on_punctuation_only` с `#[should_panic(expected = "слов нет")]`; оба проходят, в отчёте у второго стоит `- should panic`. С испорченным `expected` тест падает, отчёт печатает `note: panic did not contain expected string`, `panic message: "пустой текст: слов нет"` и `expected substring: "деление на ноль"`, код выхода 101. Параметр `expected` защищает от ложного зелёного: без него тест засчитывает **любую** панику, включая случайную ошибку в самом тесте или панику по чужой причине.

**Решение.** Всё нужное есть в самом отчёте — читаем его как протокол.

*Сколько тестов всего.* Последняя строка: `1 passed; 1 failed; ... 3 filtered out`. Отсеянные фильтром — тоже тесты этой секции, значит в библиотеке **5** тестов: 1 + 1 + 3. *Ошибка в коде или в ожидании.* В ожидании. Слева стоит `12.566370614359172` — это π·2² с точностью `f64`; справа `12.56` — округление, записанное руками. Функция считает верно; неверен тест.

Второе годится, когда ожидание выражается точно; первое — общий случай.

Здесь же прячется и ловушка наоборот: сравнение `f64` через `assert_eq!` **иногда** законно — когда обе стороны получаются одинаковой последовательностью точных операций (Г20.Ч2.З8 проверяет так «туда-обратно» на степенях десятки). Различать эти случаи и есть навык.

### Г20.Ч2.З5

**Условие.** *(понимание)* Объясните работу атрибута `#[cfg(test)]`: что и когда компилируется. Проверьте экспериментом из §20.2.1: уберите атрибут у `mod tests` в `clean.rs` и выполните `cargo build` — объясните появившееся предупреждение (почему «unused», если тесты используют `super::*`?). Почему файлам в `tests/` этот атрибут не нужен?

**Решение.** *Что делает атрибут.* `#[cfg(test)]` — условная компиляция: помеченный элемент попадает в сборку **только тогда, когда включена конфигурация `test`**, то есть при `cargo test` (компилятор вызывается с `--test`). При обычной `cargo build`/`cargo run` модуля с этим атрибутом в crate нет вовсе — ни его кода, ни его зависимостей, ни времени на его сборку. Отсюда конвенция §20.2.1: тесты модуля живут в его же файле, рядом с проверяемым кодом, и ничего не стоят готовой программе.

*Эксперимент.* В файле `p2/textstat_nocfg/src/clean.rs` у `mod tests` атрибут снят:

```rust
// #[cfg(test)] снят намеренно: модуль попадает и в обычную сборку.
mod tests {
    use super::*;

    #[test]
    fn junk_detection() {
        assert!(is_junk('!'));
        assert!(!is_junk('а'));
    }
```

```
$ cargo build
   Compiling textstat v0.1.0 (...\p2\textstat_nocfg)
warning: unused import: `super::*`
  --> src\clean.rs:19:9
   |
19 |     use super::*;
   |         ^^^^^^^^
   |
   = note: `#[warn(unused_imports)]` (part of `#[warn(unused)]`) on by default

warning: `textstat` (lib) generated 1 warning (run `cargo fix --lib -p textstat` to apply 1 suggestion)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.62s
```

Сборка проходит — и в этом главная неприятность: без атрибута ошибки нет, есть только предупреждение, которое легко не заметить.

*Почему «unused», если `super::*` используется тестами.* Потому что тестов в этой сборке нет. Атрибут `#[test]` сам по себе тоже условный: **функции, помеченные `#[test]`, включаются в сборку только в тестовом режиме** — их собирает и регистрирует прогонщик. Убрав `#[cfg(test)]` с модуля, мы оставили в обычной сборке **оболочку** — модуль `tests` со всем его содержимым, кроме самих тестовых функций. Внутри остаётся один `use super::*`, которым теперь никто не пользуется: единственные его потребители исчезли. Отсюда `unused import` — и это ровно тот симптом, по которому забытый `#[cfg(test)]` опознаётся с одного взгляда.

Цена ошибки растёт с проектом: модуль тестов может тянуть тестовые зависимости и вспомогательный код, и всё это будет собираться (а иногда и попадать в бинарник) при каждой обычной сборке.

*Почему файлам в `tests/` атрибут не нужен.* Потому что для них условие уже выполнено самим устройством каталога (§20.2.2): `tests/` — это **отдельные тестовые crate**, которые Cargo собирает только по команде `cargo test`. При `cargo build` он туда не заглядывает вовсе, так что помечать нечего и не от чего защищать. Иными словами, `#[cfg(test)]` нужен там, где тестовый код лежит **вперемешку** с рабочим (в файлах `src/`), и не нужен там, где он уже отделён физически.

**Ответ:** `#[cfg(test)]` — условная компиляция: помеченный модуль собирается только в режиме `cargo test`, а при `cargo build` его в crate нет. Со снятым атрибутом сборка проходит, но выдаёт `warning: unused import: 'super::*'` — потому что сами `#[test]`-функции в обычную сборку всё равно не попадают: остаётся пустая оболочка модуля, где ярлык `use super::*` больше некому использовать. Это и есть опознавательный признак забытого атрибута. Файлам в `tests/` атрибут не нужен: каждый из них — отдельный crate, который Cargo собирает только при `cargo test`.

### Г20.Ч2.З6

**Условие.** *(понимание)* Коллега предлагает: «чтобы протестировать `clean::normalize` интеграционным тестом, сделаем модуль `clean` публичным». Возразите по существу: (а) воспроизведите ⛔-пример 2 из §20.2.2 и покажите, где та же проверка уже живёт в юнит-тестах; (б) объясните, чем открытие внутренностей «ради теста» обернётся при будущем рефакторинге (§20.1.2 — «каждый pub — обещание»); (в) назовите случай, когда функцию действительно стоит поднять в публичный API.

```rust
// ⛔ Интеграционный тест — внешний crate: приватный модуль ему не виден.
```

Теперь главное возражение по существу: проверка, которую коллега хочет добавить, **уже существует** — юнит-тестом внутри `p2/textstat/src/clean.rs`, где модуль виден целиком:

```rust
    use super::*;

    // Приватную функцию можно тестировать: тесты — обычный код того же crate.
    #[test]
    fn junk_detection() {
        assert!(is_junk('!'));
        assert!(!is_junk('а'));

        assert_eq!(normalize("тише, мыши!"), "тише мыши");

```

```

```

Девять отсеянных — остальные тесты библиотеки: фильтр `normalize` пропустил один. Более того, юнит-тест покрывает и `is_junk` — функцию, которую наружу не поднять никаким `pub` на модуле, потому что она приватна и внутри него. То есть предложение коллеги не только не нужно: оно ещё и слабее того, что уже есть.

*(б) Чем обернётся `pub` «ради теста».* Тем, что тестовое удобство станет **публичным обещанием** (§20.1.2). Как только `pub mod clean;` попадает в релиз:

- любой пользователь библиотеки вправе написать `textstat::clean::normalize(...)` — и написать в своём коде, который вы не видите;
- удаление `clean`, переименование `normalize`, изменение её сигнатуры или семантики (скажем, добавление второго параметра-настройки) становится **ломающим изменением**: по правилам SemVer (§20.1.4) такое требует смены мажорной версии, а на практике — извинений перед пользователями;
- внутренняя перестройка, ради которой `clean` и заводился отдельным модулем, оказывается заперта: слить его со `stats`, разбить на два или заменить другой реализацией нельзя, не сломав чужой код.

Плата за один тест выходит несоразмерной: тест мы получили бы бесплатно (см. пункт «а»), а фасад библиотеки расширили навсегда.

*(в) Когда функцию действительно стоит поднять.* Когда она нужна **пользователю**, а не тесту. Признаки, по которым это видно:

- у функции есть самостоятельная ценность в терминах предметной области: `normalize` — «убрать пунктуацию из текста» — сама по себе полезна тому, кто хочет почистить текст перед своей обработкой, а не считать слова;
- о ней приходится рассказывать в документации crate («перед подсчётом текст нормализуется — вот эта функция»), то есть она уже проступает в публичном договоре;
- пользователи иначе вынуждены переписывать её у себя, что и есть признак пропущенного API.

Тогда решение принимается сознательно и по-другому оформляется: функция получает `pub` **вместе** с doc-комментарием и примером (§20.2.3), обязательствами по совместимости и, если того требует фасад, реэкспортом в корне (`pub use clean::normalize;`) — чтобы фасад не зависел от внутренней планировки. Это не «открыть ради теста», а «расширить API», и цена такого шага обдумывается заранее.

**Ответ:** (а) `textstat::clean::normalize` из `tests/` не собирается — **E0603** `module 'clean' is private`, и это преимущество, а не помеха; та же проверка уже живёт юнит-тестом `clean::tests::normalize_strips_punct` внутри `src/clean.rs`, который вдобавок покрывает приватную `is_junk`. (б) `pub` ради теста превращает внутреннюю деталь в публичное обещание: пользователи получают право на неё опереться, а рефакторинг (переименование, слияние, смена сигнатуры) становится ломающим изменением. (в) Поднимать в API стоит тогда, когда функция имеет самостоятельную ценность для пользователя — тогда её открывают осознанно, с doc-комментарием, примером-тестом и, как правило, реэкспортом в корне crate.

- **Стиль Result.** Одна строка — `Error: "ожидалось 5 слов, получено 4"`, то есть `Debug`-представление возвращённой ошибки. Ни места в файле, ни значений, кроме тех, что вы сами положили в сообщение. Зато сообщение — ваше и может быть каким угодно осмысленным.

Отсюда практический вывод: в Result-стиле **текст ошибки писать обязательно** и с диагностикой (мы вставили в него полученное число), иначе отчёт скажет только «что-то не так».

*Почему Result-тест нельзя сочетать с `#[should_panic]`.* Потому что эти два механизма отвечают на вопрос «прошёл ли тест» по-разному и одновременно неприменимы (R1, гл. 11.1). Обычный тест проваливается паникой; `#[should_panic]` **выворачивает** этот критерий: паника = успех, её отсутствие = провал. Result-тест сообщает вердикт **возвращаемым значением** — `Ok(())` или `Err(e)`. Если пометить его `#[should_panic]`, прогонщику пришлось бы одновременно ждать паники и читать возвращённое значение: тест, вернувший `Err`, ещё не паниковал — засчитывать провал или ждать паники дальше? Комбинация запрещена именно потому, что не имеет непротиворечивого смысла. Проверять ожидаемую панику в Result-стиле нечем — для этого и существует `#[should_panic(expected = ...)]` (Г20.Ч2.З2).

*Где удобнее цепочка шагов.* В Result-стиле — и ровно по той причине, ради которой `?` вводился в §18.2.2. Тест из цепочки шагов, каждый из которых может не получиться (разобрать строку, открыть файл, найти запись), в стиле паники превращается в лесенку `unwrap`/`expect`, где каждый шаг обязан сам объяснить, что случилось. В Result-стиле шаги пишутся линейно, а `?` сам прерывает тест на первом неудавшемся шаге и отдаёт его ошибку в отчёт (схема, а не файл стенда — функций `step_one`/`step_two` у нас нет):

```rust
#[test]
fn pipeline() -> Result<(), String> {
    let n = step_one()?;
    let m = step_two(n)?;
    if m == 42 { Ok(()) } else { Err(format!("ожидалось 42, получено {m}")) }
}
```

Стиль паники, наоборот, удобнее для простой сверки одного значения: `assert_eq!` короче любого `if`/`else` и печатает обе стороны сам, без ручного `format!`.

**Ответ:** переписанные тесты — листинг `p2/textstat_styles/src/stats.rs`, оба проходят. При провале стиль паники печатает полный протокол — поток, файл и строку (`src\stats.rs:48:9`), `assertion 'left == right' failed` и оба значения; стиль Result печатает одну строку `Error: "<ваше сообщение>"` и больше ничего, поэтому сообщение обязано нести диагностику. Сочетать Result-тест с `#[should_panic]` нельзя, потому что вердикт брался бы одновременно из двух несовместимых источников — возвращённого значения и факта паники. Цепочку шагов удобнее писать в Result-стиле: `?` прерывает тест на первом неудачном шаге и передаёт ошибку в отчёт; для сверки одного значения короче и информативнее `assert_eq!`.

```rust
///
/// Длина считается в символах; при равенстве длин побеждает первое слово.
///

///
/// Паникует, если в тексте нет ни одного слова.
pub fn longest_word(text: &str) -> String {
    let mut best = String::new();
    let mut best_len = 0;
    let mut current = String::new();
    let mut current_len = 0;

    for c in text.chars() {
        if c.is_whitespace() {
            // конец слова: сверяем накопленное и начинаем заново
            if current_len > best_len {
                best_len = current_len;
                best = current.clone();
            }
            current.clear();
            current_len = 0;
        } else {
            current.push(c);
            current_len += 1;
        }
    }

    // текст мог кончиться словом, а не пробелом — досверяем хвост
    if current_len > best_len {
        best_len = current_len;
        best = current.clone();
    }

    if best_len == 0 {
        panic!("в тексте нет слов");
    }
    best
}
```

```rust
pub fn longest_word(text: &str) -> String {
    let mut best = "";
    let mut best_len = 0;

    // split_whitespace сам режет текст на слова-срезы (§17.2.1),
    // а длину в символах считает chars().count() (§17.1.4).
    for word in text.split_whitespace() {
        let len = word.chars().count();

            best_len = len;
            best = word;
        }

        panic!("в тексте нет слов");

    String::from(best)
}
```


*Сравнение.* Вариант вдвое короче и заметно дешевле по памяти: `best` — это `&str`, **срез внутри исходного текста** (§15.3.2), никаких копий по ходу дела; единственная `String` создаётся один раз, в конце, из победившего среза. Основное решение на каждом рекорде выполняет `current.clone()` — то есть выделяет память и копирует байты столько раз, сколько раз обновлялся рекорд. Кроме того, здесь исчезают обе типовые ошибки основного варианта: «хвост» обрабатывать не нужно (нарезка уже отдала последнее слово), а пустой текст естественно даёт ноль итераций. Взамен вариант опирается на две готовые функции и потому хуже показывает **механику**: в основном решении видно, как из потока символов вообще получаются слова. Ещё различие в определении слова: `split_whitespace` режет по любому пробельному символу и пропускает пустые куски — ровно наша семантика, но если правило станет сложнее (например, слова разделяются ещё и дефисом), придётся возвращаться к ручному разбору. То, что оба варианта проходят один и тот же набор тестов без правок, — лучшая иллюстрация мысли §20.2.1: тесты фиксируют **поведение**, а не реализацию, и потому позволяют её менять.

Тишина достигнута. Вывод изменился ровно в оговоренном месте: было `12.566` (π = 3.1415 → 3.1415·4 = 12.566), стало `12.566370614359172` — то есть точность выросла.

*Почему один лint — ошибка, а другой — предупреждение.* Уровень назначает не строгость вкуса, а **цена пропуска**.

- `approx_constant` — из группы **корректности**: самопальная константа π означает, что все вычисления с ней **систематически неверны**. Ошибка тихая — программа считает и печатает правдоподобные числа, — а накапливается тем сильнее, чем больше умножений. Автоматически «починить» это нельзя (только автор знает, сколько знаков ему нужно), зато можно не дать собрать: `#[deny]` по умолчанию, отсюда `error:` и провал сборки.
- `len_zero` — из группы **стиля**: `s.len() == 0` и `s.is_empty()` вычисляют одно и то же, программа работает правильно. Лучше вторая запись (короче, честнее выражает намерение, а для некоторых типов ещё и дешевле), но заставлять — не за что: `#[warn]`, сборка идёт дальше.

*Когда деление уровней спасает от реального бага.* Ровно в том сюжете, который мы наблюдали в Г20.Ч2.З4: программа считает площадь круга с `pi = 3.1415`, тест сверяет её со значением, посчитанным той же константой, — и всё зелёное. Ошибка в четвёртом знаке не проявится ни в сборке, ни в тестах, ни на глаз; она вылезет там, где результат сравнивают с чужим — с расчётом смежной системы, с эталонными данными, с ответом другой библиотеки, — и разбираться будут долго, потому что «код-то работает». Запрещающий лint останавливает это в момент написания строки, а не через полгода в отчёте о расхождении. Стилевой `len_zero` такого шанса на тихий баг не даёт вовсе — потому и уровень другой.

Отсюда и смысл ритуала `cargo fmt` → `cargo clippy` → `cargo test` (§20.2.3): каждый шаг ловит свой класс проблем — запись, идиоматику и корректность, — и все три бесплатны и одинаковы у всех.

**Ответ:** ритуал пройден. `cargo fmt` привёл скомканный файл к канону, не изменив смысла: `cargo run` печатает `слов: 2` до и после. `cargo clippy` до правки даёт **две** диагностики: `error: approximate value of 'f{32, 64}::consts::PI' found` (уровень `#[deny(clippy::approx_constant)]`, сборка провалена) и `warning: length comparison to zero` с готовой заменой `s.is_empty()` (`#[warn(clippy::len_zero)]`); после замены константы на `std::f64::consts::PI` и сравнения на `is_empty()` clippy молчит, а вывод меняется только в точности: `площадь круга: 12.566370614359172`. `approx_constant` — запрещающий лint, потому что это группа корректности: неточная константа даёт систематически неверные, но правдоподобные результаты, которые не поймают ни компилятор, ни собственные тесты (они считают той же константой); расхождение вскроется только при сверке с внешним расчётом. `len_zero` — стилевой: обе записи работают одинаково, речь лишь о ясности.

## Итоги главы

Двадцать заданий этой главы почти не добавили языка — они добавили **инженерной формы**. Что стоит унести:

- **Дерево модулей не зависит от файлов.** Переезд модуля в файл (Г20.Ч1.З3) и переезд его починок (Г20.Ч1.З5) ничего не меняют в путях: `mod` объявляет узел дерева, а не вставляет текст (Г20.Ч1.З6 — измерено: 10 строк C превращаются препроцессором в 1073, `mod` не вставляет ни символа).
- **Видимость — набор разных запретов, а не один.** E0603 (элемент или звено пути), E0616 (чтение приватного поля), E0451 (построение значения с приватным полем), E0255 (ярлык поверх занятого имени), E0428 (двойное объявление), E0761 (два файла на один модуль), E0433 (имени нет в области или зависимость не объявлена) — семь разных кодов, каждый со своим поводом.
- **Тест провален ровно тогда, когда паникует** — и потому `#[should_panic]` без `expected` опасен: он засчитывает любую панику, в том числе `todo!()` из ненаписанной реализации (Г20.Ч2.З9).
- **Юнит-тесты смотрят изнутри, интеграционные — снаружи.** Первое даёт доступ к приватному, второе — гарантию, что фасад работает и что тест не привяжется к внутренностям (Г20.Ч2.З6).
- **Документация проверяется машиной.** Пример в `///` — исполняемый тест, который пишется от лица пользователя, полными путями (Г20.Ч2.З3).
- **Ритуал `fmt` → `clippy` → `test`** ловит три разных класса проблем, и clippy при этом умеет учить: `manual_clamp` в Г20.Ч2.З1 сам назвал стандартную функцию, которой в курсе ещё не было.
