## Часть 21.1. Замыкания

### Г21.Ч1.З1

**Условие.** Запишите операцию «куб числа» четырьмя способами по образцу §21.1.1: функцией `fn`, замыканием в полной форме, замыканием без аннотаций с блоком и замыканием-выражением. Вызовите все четыре с аргументом `3`, предскажите вывод, затем проверьте компилятором. Какому из четырёх вариантов понадобилась подсказка типа и почему?

**Решение.** Четыре формы записи одной операции. Файл `p1/c1_cube.rs`:

```rust
// Г21.Ч1.З1: «куб числа» в четырёх формах записи.
fn cube_v1(x: i32) -> i32 {
    x * x * x
}

fn main() {
    let cube_v2 = |x: i32| -> i32 { x * x * x };
    let cube_v3 = |x| { x * x * x };
    let cube_v4 = |x| x * x * x;

    println!("{}", cube_v1(3));
    println!("{}", cube_v2(3));
    println!("{}", cube_v3(3i32));
    println!("{}", cube_v4(3i32));
}
```

*Предсказание.* Все четыре записи вычисляют одно и то же, аргумент один и тот же — четыре строки `27`. Различия чисто синтаксические: `v1` — функция (`fn`, имя, обязательные аннотации), `v2` — замыкание в полной форме (аннотации параметра и результата, тело-блок), `v3` — без аннотаций, но с блоком, `v4` — тело-выражение без скобок.

```
$ rustc --edition 2024 c1_cube.rs
$ ./c1_cube.exe
27
27
27
27
```

Предсказание совпало. Теперь — главный вопрос задания: **кому понадобилась подсказка типа?** Мы написали `3i32` в двух последних вызовах, повторяя приём §21.1.1 (`add_one_v3(30u32)`). Проверим, обязателен ли суффикс. Файл `p1/c1_nohint.rs`:

```rust
// Г21.Ч1.З1, опыт 2: те же замыкания без подсказки типа у аргумента.
fn main() {
    let cube_v3 = |x| { x * x * x };
    let cube_v4 = |x| x * x * x;

    println!("{}", cube_v3(3));
    println!("{}", cube_v4(3));
}
```

```
$ rustc --edition 2024 c1_nohint.rs
$ ./c1_nohint.exe
27
27
```

Собралось и посчитало. Причина — умолчание языка из §14.2.2: целочисленный литерал без суффикса остаётся `{integer}` до согласования, а если согласовывать его не с чем, компилятор берёт **`i32`**. Вывод типа замыкания идёт из первого использования, и это использование дало `x: i32` по умолчанию.

Значит, суффикс нужен не «чтобы вывод состоялся», а **чтобы вывод дал нужный тип**. Убедимся, что вывод действительно `i32`, приёмом «спроси компилятор» (§18.1.2, §21.2.3) — файл `p1/c1_ask.rs`:

```rust
// Г21.Ч1.З1, опыт 3: спрашиваем компилятор, какой тип он вывел без подсказки.
fn main() {
    let cube_v4 = |x| x * x * x;
    let () = cube_v4(3); // ⛔ намеренная ошибка: покажи выведенный тип
}
```

```
error[E0271]: type mismatch resolving `<i32 as Mul>::Output == ()`
 --> c1_ask.rs:3:29
  |
3 |     let cube_v4 = |x| x * x * x;
  |                             ^ expected `()`, found `i32`
```

`<i32 as Mul>::Output` — компилятор проговаривает: умножение он разбирал для `i32`. А когда согласовывать не с чем **вообще** (замыкание ни разу не вызвано), вывод честно останавливается. Файл `p1/c1_uncalled.rs`:

```rust
// Г21.Ч1.З1, опыт 4: замыкание без аннотаций, которое ни разу не вызвали.
fn main() {
    let cube = |x| x * x * x; // ⛔ выводить тип не из чего
    let _ = cube;
    println!("closure defined");
}
```

```
error[E0284]: type annotations needed
 --> c1_uncalled.rs:3:17
  |
3 |     let cube = |x| x * x * x; // ⛔ выводить тип не из чего
  |                 ^    - type must be known at this point
  |
  = note: cannot satisfy `<_ as Mul<_>>::Output == _`
help: consider giving this closure parameter an explicit type
  |
3 |     let cube = |x: /* Type */| x * x * x; // ⛔ выводить тип не из чего
  |                  ++++++++++++
```

Вот когда аннотация обязательна: E0284 «type annotations needed» с готовым шаблоном `|x: /* Type */|`. Первое использование — единственный источник типов для замыкания; нет использования — нет типов.

**Замечание о примере §21.1.1.** Глава пишет про свой `add_one_v3`: «мы подсказали тип литералом `30u32` — иначе компилятору не из чего вывести тип `x`». Проверим и это — файл `p1/c1_addone_nohint.rs` повторяет пример главы с `30` вместо `30u32`:

```rust
// Г21.Ч1.З1, опыт 5: пример §21.1.1 с литералом без суффикса u32.
fn add_one_v1(x: u32) -> u32 {
    x + 1
}

fn main() {
    let add_one_v2 = |x: u32| -> u32 { x + 1 };
    let add_one_v3 = |x| x + 1;

    println!("{}", add_one_v1(10));
    println!("{}", add_one_v2(20));
    println!("{}", add_one_v3(30)); // без 30u32
}
```

```
$ rustc --edition 2024 c1_addone_nohint.rs
$ ./c1_addone_nohint.exe
11
21
31
```

Программа компилируется и печатает то же самое: без суффикса вывод не останавливается, а срабатывает умолчание `i32` — и `add_one_v3` оказывается замыканием над `i32`, тогда как `add_one_v1` и `add_one_v2` работают с `u32`. Суффикс `30u32` в примере §21.1.1 **выравнивает типы трёх записей**, а не спасает вывод, — так глава об этом и говорит.

**Ответ:** все четыре записи печатают `27`; синтаксически различаются только объём аннотаций и наличие блока. Строго обязательной подсказка типа не была ни одной из четырёх: без суффикса `x` получает `i32` по умолчанию языка (§14.2.2) — это подтверждено запуском `c1_nohint.rs` и подтверждено E0271 из `c1_ask.rs` (`<i32 as Mul>::Output`). Подсказка нужна в двух случаях: (1) нужный тип отличается от умолчания — тогда `3u32`/`|x: u32|` не «помогают вывести», а **задают** тип (именно эту роль играет `30u32` в §21.1.1); (2) замыкание не вызвано ни разу — тогда выводить не из чего и компилятор требует аннотацию, E0284.

### Г21.Ч1.З2

**Условие.** Не запуская, выпишите порядок строк вывода программы из §21.1.1 с `expensive_default` (пример с `unwrap_or`/`unwrap_or_else`), если `present` заменить на `None`, а `absent` — на `Some(7)`. Проверьте запуском. Сформулируйте правило: когда аргумент `unwrap_or` вычисляется, а когда — замыкание `unwrap_or_else`.

**Решение.** Программа главы с обменом значениями. Файл `p1/c2_swapped.rs`:

```rust
// Г21.Ч1.З2: программа §21.1.1 с обменом: present = None, absent = Some(7).
fn expensive_default() -> u32 {
    println!("  ...дорогое вычисление запущено...");
    42
}

fn main() {
    let present: Option<u32> = None;
    let absent: Option<u32> = Some(7);

    println!("unwrap_or, значение есть:");
    let a = present.unwrap_or(expensive_default());
    println!("unwrap_or_else, значение есть:");
    let b = present.unwrap_or_else(|| expensive_default());
    println!("unwrap_or_else, значения нет:");
    let c = absent.unwrap_or_else(|| expensive_default());

    println!("{a} {b} {c}");
}
```

*Предсказание — по строкам.* Имена `present`/`absent` теперь лгут (в `present` лежит `None`), но нас интересует механика, а не подписи.

1. `println!("unwrap_or, значение есть:")` — печатается.
2. `present.unwrap_or(expensive_default())` — обычный вызов: аргумент вычисляется **до** входа в метод, значит печать из `expensive_default` будет **всегда**, независимо от содержимого `present`. Строка «дорогое вычисление» есть. `present` — `None`, поэтому умолчание пригодилось: `a = 42`.
3. Вторая метка печатается.
4. `present.unwrap_or_else(|| expensive_default())` — замыкание запускается **только при `None`**; здесь как раз `None`, значит печать есть. `b = 42`.
5. Третья метка печатается.
6. `absent.unwrap_or_else(...)` — в `absent` лежит `Some(7)`, замыкание не запускается: печати нет. `c = 7`.
7. Последняя строка: `42 42 7`.

Итого предсказание — шесть строк, из них две «дорогих», причём вторая «дорогая» стоит между второй и третьей метками (а не после третьей, как в главе).

```
$ rustc --edition 2024 c2_swapped.rs
$ ./c2_swapped.exe
unwrap_or, значение есть:
  ...дорогое вычисление запущено...
unwrap_or_else, значение есть:
  ...дорогое вычисление запущено...
unwrap_or_else, значения нет:
42 42 7
```

Совпало построчно. Сравните с выводом главы: там «дорогая» строка стояла после первой и после третьей метки, здесь — после первой и второй. Единственная строка, которая не сдвинулась, — первая «дорогая»: `unwrap_or` печатает её при любом содержимом `Option`.

**Ответ:** вывод — шесть строк:

```
unwrap_or, значение есть:
  ...дорогое вычисление запущено...
unwrap_or_else, значение есть:
  ...дорогое вычисление запущено...
unwrap_or_else, значения нет:
42 42 7
```

Правило: **аргумент `unwrap_or` вычисляется всегда** — это обычный аргумент обычного вызова, он готов ещё до входа в метод, и `Some` внутри просто выбрасывает готовое значение. **Замыкание `unwrap_or_else` вычисляется только при `None`** — метод получает не значение, а рецепт, и запускает его лишь тогда, когда умолчание действительно понадобилось (R9). Отсюда практическое правило чтения API: суффикс `_else` = «принимает замыкание, вычисляет лениво»; дорогое умолчание (запрос к файлу, выделение памяти, вычисление) отдавайте через `_else`-форму, дешёвую константу — через `unwrap_or`.

### Г21.Ч1.З3

**Условие.** Для каждого из замыканий определите режим захвата (разделяемое заимствование / изменяющее / перенос) и полный список реализуемых трейтов (`Fn`?, `FnMut`?, `FnOnce`?): (а) `|| v.len()`, (б) `|| v.push(1)`, (в) `move || v`, (г) `|x: i32| x * x` (ничего не захватывает). Проверьте себя пробниками `probe_fn`/`probe_fn_mut`/`probe_fn_once` из §21.1.3: какие вызовы компилируются?

**Решение.** Сначала — разбор на бумаге по правилу минимальной достаточности (§21.1.2: захват выбирается первым режимом, совместимым с использованием в теле; трейты — по тому, что тело делает с захваченным):

| Замыкание | Что делает тело | Режим захвата | `Fn` | `FnMut` | `FnOnce` |
|---|---|---|---|---|---|
| (а) `\|\| v.len()` | читает длину | разделяемое заимствование `&Vec<i32>` | да | да | да |
| (б) `\|\| v.push(1)` | изменяет вектор | изменяющее заимствование `&mut Vec<i32>` | нет | да | да |
| (в) `move \|\| v` | отдаёт захваченное наружу | перенос владения `Vec<i32>` | нет | нет | да |
| (г) `\|x: i32\| x * x` | ничего не захватывает | захвата нет | да | да | да |

Теперь проверка пробниками — и первая же ловушка. Пробники из §21.1.3 объявлены как `F: Fn()`, `F: FnMut()`, `F: FnOnce()`, то есть требуют замыкание **без аргументов и с результатом `()`**. Замыкание (а) возвращает `usize` — предъявим его как есть. Файл `p1/c3_len_bad.rs`:

```rust
// Г21.Ч1.З3: ⛔ замыкание (а) как есть — результат usize вместо ().
fn probe_fn<F: Fn()>(f: F) {
    f();
    f();
}

fn main() {
    let v = vec![1, 2, 3];
    probe_fn(|| v.len()); // ⛔ Fn() обещает результат ()
}
```

```
error[E0308]: mismatched types
 --> c3_len_bad.rs:9:17
  |
9 |     probe_fn(|| v.len()); // ⛔ Fn() обещает результат ()
  |                 ^^^^^^^ expected `()`, found `usize`
  |
help: consider using a semicolon here
  |
9 |     probe_fn(|| { v.len(); }); // ⛔ Fn() обещает результат ()
  |                 +        +++
```

Это **не** про трейты: `Fn()` — сокращение от `Fn() -> ()`, и несовпал результат, а не право на вызов. Компилятор сам подсказывает лечение — точка с запятой выбрасывает значение, тело становится `()`. Точно так же (в) возвращает `Vec<i32>`, а (г) вообще принимает аргумент, поэтому под пробники их надо подогнать: результат выбросить, а для (г) — завести пробники с нужной сигнатурой. **Режим захвата от этой подгонки не меняется**: `{ v.len(); }` по-прежнему только читает, `drop(u)` по-прежнему выносит.

Файл `p1/c3_probes.rs` — все проходящие комбинации:

```rust
// Г21.Ч1.З3: четыре замыкания под пробниками §21.1.3.
fn probe_fn<F: Fn()>(f: F) {
    f();
    f();
}

fn probe_fn_mut<F: FnMut()>(mut f: F) {
    f();
    f();
}

fn probe_fn_once<F: FnOnce()>(f: F) {
    f();
}

// Пробники для замыкания с аргументом: сигнатура другая.
fn probe_fn_i32<F: Fn(i32) -> i32>(f: F) -> i32 {
    f(f(2))
}

fn probe_fn_mut_i32<F: FnMut(i32) -> i32>(mut f: F) -> i32 {
    // Вложить вызовы нельзя: каждый занимает f изменяющим заимствованием (E0499).
    let once = f(2);
    f(once)
}

fn probe_fn_once_i32<F: FnOnce(i32) -> i32>(f: F) -> i32 {
    f(2)
}

fn main() {
    // (а) тело только читает: годится во все три пробника.
    let v = vec![1, 2, 3];
    probe_fn(|| {
        v.len();
    });
    probe_fn_mut(|| {
        v.len();
    });
    probe_fn_once(|| {
        v.len();
    });
    println!("a: v alive, len = {}", v.len());

    // (б) тело изменяет: FnMut и FnOnce.
    let mut w = vec![1, 2, 3];
    probe_fn_mut(|| w.push(1));
    println!("b after probe_fn_mut: {w:?}");
    probe_fn_once(|| w.push(1));
    println!("b after probe_fn_once: {w:?}");

    // (в) тело выносит захваченное: только FnOnce.
    let u = vec![1, 2, 3];
    probe_fn_once(move || drop(u));
    println!("c: u consumed");

    // (г) ничего не захватывает, но принимает аргумент.
    println!("d: {}", probe_fn_i32(|x: i32| x * x));
    println!("d: {}", probe_fn_mut_i32(|x: i32| x * x));
    println!("d: {}", probe_fn_once_i32(|x: i32| x * x));
}
```

```
$ rustc --edition 2024 c3_probes.rs
$ ./c3_probes.exe
a: v alive, len = 3
b after probe_fn_mut: [1, 2, 3, 1, 1]
b after probe_fn_once: [1, 2, 3, 1, 1, 1]
c: u consumed
d: 16
d: 16
d: 4
```

Разбор вывода. Строка `a` — вектор жив после трёх пробников: читающий захват никого не блокирует. Строка `b` первая: `probe_fn_mut` зовёт замыкание **дважды**, отсюда два новых элемента; вторая: `probe_fn_once` зовёт один раз — третий элемент. Строка `c`: замыкание съело `u`, и после этого вектора нет (обратиться к `u` мы уже не пробуем). Строка `d`: `probe_fn_i32` и `probe_fn_mut_i32` считают `(2²)² = 16`, `probe_fn_once_i32` — один раз, `2² = 4`; одно и то же незахватывающее замыкание прошло во все три пробника — иерархия `Fn ⊂ FnMut ⊂ FnOnce` в действии.

Теперь отрицательные опыты. Замыкание (б) там, где ждут `Fn` — файл `p1/c3_push_fn_bad.rs`:

```rust
// Г21.Ч1.З3: ⛔ замыкание (б) там, где ждут Fn.
fn probe_fn<F: Fn()>(f: F) {
    f();
    f();
}

fn main() {
    let mut w = vec![1, 2, 3];
    probe_fn(|| w.push(1)); // ⛔ изменяющий захват под Fn
    println!("{w:?}");
}
```

### Г21.Ч1.З4

**Условие.** Программа из §21.1.1 с `let id = |x| x;` не компилируется при вызовах с `String` и с числом (E0308). Объясните, почему компилятор ссылается на *первый* вызов. Почините двумя способами: (а) двумя отдельными замыканиями; (б) обобщённой функцией из §19.1.1 — и объясните, почему (б) — не замыкание: что теряется, что приобретается.

**Решение.** Воспроизведём ошибку. Файл `p1/c4_id_bad.rs`:

```rust
// Г21.Ч1.З4: ⛔ тип замыкания фиксируется первым вызовом.
fn main() {
    let id = |x| x;
    let s = id(String::from("привет"));
    let n = id(5);
    println!("{s} {n}");
}
```

```

  |             -- ^ expected `String`, found integer
  |             |

 --> c4_id_bad.rs:4:16
  |
4 |     let s = id(String::from("привет"));
  |             -- ^^^^^^^^^^^^^^^^^^^^^^ expected because this argument is of type `String`

  |                 ++++++++++++
```

**Почему ссылка на первый вызов.** У замыкания `|x| x` тип параметра не написан, но он **есть** — компилятор обязан его вывести, и выводит из первого использования (§21.1.1). После строки 4 в записи типа замыкания стоит `String` — не «пока String», а окончательно: у замыкания один конкретный тип на всю программу, параметров типа у него не бывает. Поэтому диагностика построена как у любой функции с неверным аргументом: ошибка — в строке 5 (`expected String, found integer`), а `note` показывает, **откуда взялось ожидание**: `expected because the closure was earlier called with an argument of type String`. Третья `note` указывает на сам параметр `x` — место, где тип был выведен. Компилятор даже предлагает `5.to_string()`: с его точки зрения проблема в аргументе, а не в замыкании.

Стоит подчеркнуть асимметрию: если поменять вызовы местами, «виноватой» окажется строка со `String` — обвиняется всегда **второй** вызов, потому что первый и определил тип.

**Починка (а) — два замыкания.** Файл `p1/c4_two.rs`:

```rust
// Г21.Ч1.З4, починка (а): по замыканию на каждый тип.
fn main() {
    let id_str = |x: String| x;
    let id_num = |x: i32| x;

    let s = id_str(String::from("привет"));
    let n = id_num(5);
    println!("{s} {n}");
}
```

```
$ rustc --edition 2024 c4_two.rs
$ ./c4_two.exe

```

Каждое замыкание получило свой тип — конфликта нет. Аннотации здесь не обязательны (тип вывелся бы из вызова), но они документируют намерение: «это тождество для строк, а это — для чисел».

**Починка (б) — обобщённая функция.** Файл `p1/c4_generic.rs`:

```rust
// Г21.Ч1.З4, починка (б): обобщённая функция (§19.1.1) вместо замыкания.
fn identity<T>(x: T) -> T {
    x
}

fn main() {
    let s = identity(String::from("привет"));
    let n = identity(5);
    let f = identity(2.5);
    println!("{s} {n} {f}");
}
```

```
$ rustc --edition 2024 c4_generic.rs
$ ./c4_generic.exe
привет 5 2.5
```

Одно определение работает с тремя разными типами — и с любым другим: компилятор мономорфизирует `identity` под каждое использование (§19.1.3), получая три отдельные функции в машинном коде.

**Что теряется и что приобретается.** Приобретается ровно то, чего не хватало замыканию: **параметр типа**. `identity<T>` — не одно значение, а семейство функций, порождаемое по мере вызовов; `|x| x` — одно значение с одним типом. Теряется главное свойство замыкания — **захват окружения**: `fn` не видит локальные переменные (E0434, §21.1.1), поэтому весь контекст ей нужно передавать параметрами, как функции C. Теряется и «размещение по месту»: обобщённая функция — элемент верхнего уровня со своим именем, её нельзя написать внутри выражения. Практический вывод: нужна одна операция над разными типами — обобщённая функция; нужна операция, знающая локальный контекст, — замыкание; нужно и то и другое — обобщённая функция, принимающая замыкание (`fn twice<F: Fn(i32) -> i32>` из §21.1.3 — ровно такая конструкция).

**Ответ:** компилятор ссылается на первый вызов потому, что именно он зафиксировал тип параметра: у замыкания нет параметров типа, и вывод происходит один раз, по первому использованию (`note: expected because the closure was earlier called with an argument of type String`); ошибку получает второй вызов, а первый предъявляется как источник ожидания. Починка (а) — `let id_str = |x: String| x;` и `let id_num = |x: i32| x;`, печатает `привет 5`. Починка (б) — `fn identity<T>(x: T) -> T`, печатает `привет 5 2.5`; это не замыкание, потому что обобщённая функция получает параметр типа `T` (одно определение — много типов, мономорфизация под каждый), но теряет захват окружения и запись внутри выражения.

### Г21.Ч1.З5

**Условие.** В примере 2 §21.1.2 (E0502) коллега предлагает починку: «просто перенесите `let mut borrows_mutably = ...` *после* `println!`». Сработает ли она? А починка «перенесите `println!` после вызова `borrows_mutably()`»? Объясните обе через интервал жизни изменяющего займа (от определения замыкания до последнего вызова) и правило «читатели XOR писатель» §15.2.2.

**Решение.** Напомним обстановку: в §21.1.2 конфликтуют изменяющий заём, который замыкание держит на `list`, и `println!`, читающий `list` внутри интервала этого займа. Интервал — от **определения** замыкания (тогда заём и берётся) до его **последнего вызова** (NLL: заём живёт, пока может понадобиться, §15.2.2). Обе предложенные починки убирают печать из этого интервала, но с разных сторон.

**Починка 1 — определение замыкания после `println!`.** Файл `p1/c5_def_after.rs`:

```rust
// Г21.Ч1.З5, починка 1: определение замыкания — после println!.
fn main() {
    let mut list = vec![1, 2, 3];

    println!("между определением и вызовом: {list:?}");

    let mut borrows_mutably = || list.push(7);
    borrows_mutably();

    println!("после вызова: {list:?}");
}
```

```
$ rustc --edition 2024 c5_def_after.rs
$ ./c5_def_after.exe
между определением и вызовом: [1, 2, 3]
после вызова: [1, 2, 3, 7]
```

Работает. Печать теперь **до** начала интервала: когда она исполняется, изменяющего займа ещё нет — в этот момент у `list` единственный пользователь-читатель, и правило «читатели XOR писатель» не нарушено. Заметьте, что подпись строки перестала быть правдой: печать больше не «между определением и вызовом», она перед определением. Это не придирка к тексту, а суть починки: чтобы конфликт исчез, чтение пришлось вынести за пределы интервала.

**Починка 2 — `println!` после последнего вызова.** Файл `p1/c5_print_after.rs`:

```rust
// Г21.Ч1.З5, починка 2: println! — после последнего вызова замыкания.
fn main() {
    let mut list = vec![1, 2, 3];

    let mut borrows_mutably = || list.push(7);

    borrows_mutably();
    println!("после вызова: {list:?}");
}
```

```
$ rustc --edition 2024 c5_print_after.rs
$ ./c5_print_after.exe
после вызова: [1, 2, 3, 7]
```

Тоже работает — и это в точности пример 2 главы, который у неё компилируется. Печать стоит **после** конца интервала: последний вызов замыкания позади, `borrows_mutably` больше нигде не используется, значит изменяющий заём завершён (NLL), и читатель приходит на свободное место.

**Итого о двух починках.** Обе законны, но они не равноценны по смыслу:

| | Починка 1 (определение позже) | Починка 2 (печать позже) |
|---|---|---|
| Что видит `println!` | состояние **до** изменения: `[1, 2, 3]` | состояние **после**: `[1, 2, 3, 7]` |
| Где стоит относительно интервала | до начала займа | после конца займа |
| Когда уместна | нужно зафиксировать «как было» | нужно проверить результат работы замыкания |

Третий, не предложенный коллегой способ — сузить интервал, а не двигать печать: если убрать вызов `borrows_mutably()` совсем, заём кончится сразу после определения и печать между строками станет законной. Глава упоминает именно это («уберите вызов в строке 7 — и печать станет законной»), но польза от замыкания, которое никогда не вызывают, сомнительная, поэтому в рабочем коде выбирают из двух починок выше.

**Ответ:** сработают **обе**. Изменяющий заём на `list` живёт от определения замыкания до его последнего вызова; конфликт был в том, что `println!` (читатель) попадал внутрь этого интервала, а правило §15.2.2 разрешает или читателей, или одного писателя. Починка 1 переносит чтение **до** начала интервала — печатает `[1, 2, 3]` (состояние до изменения); починка 2 переносит чтение **за** конец интервала (после последнего вызова заём завершён по NLL) — печатает `[1, 2, 3, 7]`. Выбор между ними определяется не компилятором, а тем, какое состояние вектора вы хотите увидеть.

### Г21.Ч1.З6

**Условие.** Предскажите для каждого фрагмента: компилируется? что печатает? (а) `let s = String::from("а"); let c = move || println!("{s}"); c(); println!("{s}");` (б) то же с `let n = 5;` вместо `String`. (в) вариант (а) без `move`. ### Г21.Ч1.З7

**Условие.** Объясните ошибку E0507 из примера 3 §21.1.3 (вынос `value` в `sort_by_key`): почему требование «FnMut» несовместимо с переносом захваченного значения? Почините тремя способами и сравните их: (а) `value.clone()` — как советует компилятор; какова цена на большом числе вызовов? (б) счётчик вызовов — как в тексте; (в) вектор срезов: `sort_operations: Vec<&str>` и `push(value.as_str())` — почему заимствование вместо выноса устраивает `FnMut`?

**Почему `FnMut` несовместим с выносом.** `sort_by_key` требует `F: FnMut(&T) -> K`, потому что зовёт замыкание-ключ **по одному разу на сравнение** — сколько именно раз, зависит от алгоритма и данных. Контракт `FnMut` (§21.1.3) — «вызывать можно многократно»: вызов идёт через `&mut` самого замыкания, но содержимое рюкзака после вызова обязано остаться на месте, чтобы следующий вызов нашёл его целым. `push(value)` перемещает `String` из рюкзака наружу — после первого вызова рюкзак опустел бы, и второй вызов читал бы аннулированное значение. Компилятор запрещает это на этапе типов, не дожидаясь второго вызова, — и говорит прямо: `Fn` и `FnMut` требуют, чтобы захваченное можно было «потребить» многократно, а «один раз» — это `FnOnce`. Вторая половина help-строки указывает на источник требования — `library\alloc\src\slice.rs`, то есть на объявление `sort_by_key` в стандартной библиотеке: ограничение пришло от приёмника, а не от нашего кода.

**Починка (а) — клон.** Файл `p1/c7_clone.rs`:

```rust

#[derive(Debug)]
struct Rect {
    width: u32,
    height: u32,
}

        Rect { width: 10, height: 1 },
        Rect { width: 3, height: 5 },
        Rect { width: 7, height: 12 },
    ];

    let mut sort_operations = Vec::new();
    let value = String::from("замыкание вызвано");

    list.sort_by_key(|r| {
        sort_operations.push(value.clone()); // клон вместо выноса
        r.width
    });

    println!("{list:?}");
    println!("narrowest: {} (height {})", list[0].width, list[0].height);
    println!("clones made: {}", sort_operations.len());
    println!("value still alive: {value}");
}
```

Работает: `clone` создаёт **новую** строку, рюкзак не пустеет, `value` жив и после сортировки. Цена видна в третьей строке: на трёх элементах ключ вызван 6 раз — значит 6 выделений в куче и 6 копирований содержимого (§17.1.3). Клон здесь пропорционален не числу элементов, а числу **сравнений**: для сортировки это порядка n·log n, и на большом массиве строк такая починка превращает «посчитать вызовы» в заметную работу с кучей. Замыкание захватывает `value` **разделяемым заимствованием** (тело только читает) и на каждом вызове копирует ссылку — а ссылка `Copy` (§15.1.3), её копирование ничего не выносит из рюкзака. Владелец буфера остаётся один — переменная `value`, поэтому она жива и после сортировки (последняя строка вывода). Требование «захваченное переживает многократные вызовы» выполнено буквально: рюкзак вообще не меняется.

Тонкость времён жизни: `Vec<&str>` привязан к `value` (§19.3.1) — вектор срезов не может пережить строку, из которой они нарезаны. Здесь оба живут до конца `main`, поэтому проверка проходит молча.

**Сравнение трёх починок.**

| Починка | Что попадает в рюкзак | Работы на вызов | Что даёт | Когда выбирать |
|---|---|---|---|---|
| (а) `clone` | `&String` (читается) + `&mut Vec<String>` | выделение в куче + копирование | 6 независимых строк | нужны **владеющие** копии (уедут дальше, переживут `value`) |
| (б) счётчик | `&mut i32` | одно сложение | число вызовов | нужен только счёт (наш случай) |
| (в) срезы | `&String` + `&mut Vec<&str>` | копирование ссылки | 6 срезов на один буфер | нужны сами данные, но копии избыточны, и `value` жива |

**Ответ:** E0507 возникает потому, что `sort_by_key` требует `FnMut` — «вызывать можно многократно», — а `push(value)` выносит `String` из рюкзака: после первого вызова захваченного значения там уже не было бы. Три починки: (а) `value.clone()` — работает, но платит выделением в куче на **каждое сравнение** (в нашем опыте 6 клонов на 3 элемента, то есть порядка n·log n на больших данных); (б) счётчик `num_sort_operations += 1` — изменение вместо выноса, одна операция на вызов, ровно то, что нужно, если интересен факт вызова; (в) `Vec<&str>` + `value.as_str()` — замыкание захватывает `value` разделяемым заимствованием и копирует **ссылку** (а ссылка `Copy`), поэтому рюкзак не пустеет и `FnMut` соблюдён; ограничение — вектор срезов не может пережить строку-источник.

### Г21.Ч1.З8

**Условие.** Фабрика счётчиков. Напишите `make_counter() -> impl FnMut() -> u32`: каждый вызов возвращённого замыкания выдаёт 1, 2, 3, … Программа должна завести **два независимых** счётчика и продемонстрировать независимость (вывод: `1 2 3`, затем `1` у второго, затем `4` у первого). Сравните со `static`-счётчиком из §4.2.2: сколько независимых счётчиков позволял тот подход? Почему здесь обязателен `move`?

**Решение.** Файл `p1/c8_counter.rs`:

```rust
// Г21.Ч1.З8: фабрика независимых счётчиков.
fn make_counter() -> impl FnMut() -> u32 {
    let mut count = 0;
    move || {
        count += 1;
        count
    }
}

fn main() {
    let mut c1 = make_counter();
    let mut c2 = make_counter();

    println!("{} {} {}", c1(), c1(), c1());
    println!("{}", c2());
    println!("{}", c1());
}
```

```
$ rustc --edition 2024 c8_counter.rs
$ ./c8_counter.exe
1 2 3
1
4
```

Требуемый вывод получен. Разберём конструкцию по частям.

**Тип результата.** `impl FnMut() -> u32` (§19.2.2): «здесь один конкретный тип, реализующий `FnMut() -> u32`; какой именно — знает компилятор». Написать его руками нельзя — у замыканий нет имён (§21.2.3 покажет это на луковице адаптеров). Почему именно `FnMut`, а не `Fn`: тело изменяет захваченное `count`, поэтому `Fn` замыкание не реализует (это тот же диагноз, что E0594/E0596 в §21.1.3). И не `FnOnce`: ничего не выносится, звать можно сколько угодно — а объяви мы `impl FnOnce() -> u32`, вызывающий имел бы право лишь на один вызов.

**`let mut` у переменных `c1`/`c2`.** Вызов `FnMut`-замыкания — изменяющее использование самого замыкания, поэтому переменная обязана быть `mut` (§21.1.2). Без `mut` — E0596 с подсказкой добавить `mut`.

**Независимость.** Каждый вызов `make_counter()` создаёт **свою** переменную `count` и переносит её в **своё** замыкание. Два замыкания — два рюкзака, между ними нет ничего общего; поэтому `c2()` начинает с 1, а `c1()` продолжает с 4. Первая строка вывода заодно доказывает порядок вычисления аргументов `println!`: слева направо, `1 2 3`.

**Почему обязателен `move`.** Без него замыкание захватило бы локальную `count` изменяющим **заимствованием**, а `count` умирает вместе с вызовом `make_counter` — возвращённое замыкание ссылалось бы на исчезнувшую переменную (§15.2.3). Компилятор ловит это ещё в определении. Файл `p1/c8_nomove_bad.rs`:

```rust

        count
    } // ⛔ замыкание заимствует локальную count
```


E0373 — тот самый страж «замыкание переживает окружение» из §21.1.3, с точным диагнозом (`note: closure is returned here`) и готовым лекарством. Обратите внимание: `move` здесь не «усиление на всякий случай», а единственный способ отдать состояние наружу вместе с замыканием.

**Сравнение со `static`-счётчиком C (§4.2.2).** В C «память между вызовами» давала `static`-переменная внутри функции: она инициализируется один раз и живёт до конца программы. Но она **одна на функцию** — сколько бы раз вы её ни вызвали, счётчик общий; двух независимых счётчиков из одной такой функции получить нельзя. Чтобы завести второй, приходилось либо копировать функцию, либо выносить состояние в структуру и передавать указатель на неё каждым вызовом (по сути — руками собирать «рюкзак» и таскать его отдельно от кода). Замыкание же — **значение**: фабрика печёт их сколько закажете, каждое со своим состоянием, а состояние ездит вместе с кодом и не видно снаружи. Это и есть та самая «функция + контекст в одном значении», которой не хватало указателю на функцию (§6.3.2).

**Ответ:** `make_counter` — три строки:

```rust
fn make_counter() -> impl FnMut() -> u32 {
    let mut count = 0;
    move || {
        count += 1;
        count
    }
}
```

вывод программы — `1 2 3`, затем `1`, затем `4`: счётчики независимы, потому что каждый вызов фабрики создаёт отдельную `count` и переносит её в отдельное замыкание. `static`-подход §4.2.2 давал **ровно один** счётчик на функцию (переменная одна на программу); независимые счётчики требовали ручного выноса состояния в структуру. `move` обязателен потому, что `count` — локальная переменная фабрики: без переноса замыкание заимствовало бы уже мёртвую переменную, и компилятор отвергает это как E0373 «closure may outlive the current function».

**Вариант 2 (состояние в структуре).** То же поведение без замыканий вообще — на материале §16.1.1: структура с полем-состоянием и метод, продвигающий его. Файл `p1/c8_struct.rs`:

```rust
// Г21.Ч1.З8, вариант 2: состояние в структуре (§16.1.1) вместо рюкзака.
struct Counter {
    count: u32,
}

impl Counter {
    fn new() -> Counter {
        Counter { count: 0 }
    }

    fn tick(&mut self) -> u32 {
        self.count += 1;
        self.count
    }
}

fn main() {
    let mut c1 = Counter::new();
    let mut c2 = Counter::new();

    println!("{} {} {}", c1.tick(), c1.tick(), c1.tick());
    println!("{}", c2.tick());
    println!("{}", c1.tick());
}
```

```
$ rustc --edition 2024 c8_struct.rs
$ ./c8_struct.exe
1 2 3
1
4
```

Вывод совпал с основным решением до символа. Независимость здесь очевидна из типов: `c1` и `c2` — два разных значения `Counter`, у каждого своё поле `count`. `&mut self` у `tick` — та же причина, по которой переменная замыкания требовала `mut`.

*Сравнение.* Различие — в том, что видно снаружи. Замыкание скрывает состояние **полностью**: тип непроизносим, поля недоступны, «счётчик» существует только как вызываемое значение; зато и способ применения один — позвать. Структура делает состояние **явным**: `count` можно прочитать, добавить `reset`, `peek`, `Debug`-печать, реализовать трейт (в §21.2.3 ровно такой `Counter` станет итератором, и весь арсенал адаптеров достанется ему бесплатно). Ещё одна практическая разница: замыкание нельзя положить в `Vec` вместе с другим замыканием — у каждого свой уникальный тип (§21.1.3), а `Vec<Counter>` собирается без затей. Правило выбора: одноразовая «функция с памятью», которую надо куда-то передать, — замыкание; долгоживущая сущность с несколькими операциями и понятным именем — структура.

### Г21.Ч1.З9

**Условие.** Таблица результатов: `Vec<(&str, u32)>` — имя и балл. Отсортируйте `sort_by` с замыканием: по убыванию балла, при равенстве — по алфавиту имени. Подсказка: сравните сначала баллы (`b.1.cmp(&a.1)`), затем разберите `Ordering` match-ем — рукав `Equal` сравнивает имена, остальные рукава возвращают результат как есть (§16.2.2). Для данных `[("Вера", 78), ("Аня", 92), ("Глеб", 92), ("Боря", 85)]` приведите ожидаемый и фактический порядок.

**Решение.** *Ожидаемый порядок.* Главный ключ — балл по убыванию: 92, 92, 85, 78. Первые две записи — ничья (`Аня` и `Глеб`), её разрешает второй ключ: имя по алфавиту, `Аня` < `Глеб`. Итого ожидаем `Аня 92`, `Глеб 92`, `Боря 85`, `Вера 78`.

Файл `p1/c9_sort.rs`:

```rust
// Г21.Ч1.З9: двухключевой порядок через sort_by и разбор Ordering.
use std::cmp::Ordering;

fn main() {
    let mut table: Vec<(&str, u32)> = vec![("Вера", 78), ("Аня", 92), ("Глеб", 92), ("Боря", 85)];

    table.sort_by(|a, b| match b.1.cmp(&a.1) {
        Ordering::Equal => a.0.cmp(b.0),
        other => other,
    });

    for (name, score) in &table {
        println!("{score:>3} {name}");
    }
}
```

```
$ rustc --edition 2024 c9_sort.rs
$ ./c9_sort.exe
 92 Аня
 92 Глеб
 85 Боря
 78 Вера
```

Фактический порядок совпал с ожидаемым. Разбор компаратора по частям:

- `b.1.cmp(&a.1)` — **баллы в обратном порядке аргументов**: обычное возрастание дал бы `a.1.cmp(&b.1)`, а перестановка `a` и `b` переворачивает результат, давая убывание. Это стандартный приём «сортировать по убыванию без отрицаний» (§21.1.3).
- `match` по результату (§16.2.2): рукав `Ordering::Equal` — ничья по главному ключу, решает второй: `a.0.cmp(b.0)`, имена **в прямом** порядке, то есть по алфавиту. Обратите внимание на `&` в `b.1.cmp(&a.1)` (метод берёт ссылку на `u32`) и на его отсутствие в `a.0.cmp(b.0)` — `a.0` уже `&str`, ссылка на строковые данные, и `cmp` для `&str` принимает `&&str`, который здесь получается автоматически из `b.0`.
- рукав `other => other` — «Less и Greater пропускаем как есть». Записать его как `_ => ...` не вышло бы: значение нужно вернуть, а не отбросить; `other` — именованный образец, который связывает и возвращает.
- **Тип замыкания.** `sort_by` требует `FnMut(&T, &T) -> Ordering` (R9), поэтому `a` и `b` внутри — ссылки на элементы `(&str, u32)`; `a.1` работает без разыменования благодаря автоматической разыменовке при доступе к полю.

Порядок кириллицы: сравнение `&str` — лексикографическое по байтам UTF-8 (§17.1.4), а у русского алфавита в UTF-8 байтовый порядок совпадает с алфавитным для строчных и для прописных по отдельности. `Аня` (`А` = U+0410) < `Боря` (`Б` = U+0411) < `Вера` < `Глеб` — то, что мы и ожидали. (Со смешанным регистром совпадение сломалось бы: все прописные идут раньше всех строчных.)

**Разбор типичного сомнения.** «А нельзя ли двумя простыми сортировками — сначала по имени, потом по баллу? Ведь вторая сортировка перемешает результат первой». Проверим. Файл `p1/c9_naive_bad.rs`:

```rust
// Г21.Ч1.З9: типичная неверная попытка — два независимых sort_by.
fn main() {
    let mut table: Vec<(&str, u32)> = vec![("Вера", 78), ("Аня", 92), ("Глеб", 92), ("Боря", 85)];

    table.sort_by(|a, b| a.0.cmp(b.0)); // сначала по имени
    table.sort_by(|a, b| b.1.cmp(&a.1)); // потом по баллу — не отменит ли первый?

    for (name, score) in &table {
        println!("{score:>3} {name}");
    }
}
```

```
$ rustc --edition 2024 c9_naive_bad.rs
$ ./c9_naive_bad.exe
 92 Аня
 92 Глеб
 85 Боря
 78 Вера
```

Сомнение не подтвердилось: результат правильный. Причина — **`sort` и `sort_by` стабильны** (R9): элементы, которые компаратор считает равными, сохраняют взаимный порядок. Второй проход сравнивает только баллы, для `Аня`/`Глеб` он возвращает `Equal` — и они остаются в том порядке, который навёл первый проход. Так что это не «неверная попытка», а рабочий приём «сначала второстепенный ключ, потом главный»; его цена — два прохода вместо одного (в варианте 2 задания Г21.Ч2.З10 мы применим его сознательно). Ловушка тут одна и обратная: тот же трюк с `sort_unstable_by`, которая стабильность не обещает, сломался бы — молча и не на всех данных.

**Ответ:** ожидаемый и фактический порядок совпадают:

```
 92 Аня
 92 Глеб
 85 Боря
 78 Вера
```

Компаратор — `|a, b| match b.1.cmp(&a.1) { Ordering::Equal => a.0.cmp(b.0), other => other }`: перестановка аргументов у главного ключа даёт убывание балла, рукав `Equal` передаёт решение второму ключу (имя по возрастанию), рукав `other` пропускает готовый ответ. Проверено и то, что двухпроходная сортировка (сначала по имени, затем по баллу) даёт тот же результат — благодаря стабильности `sort_by`.

**Вариант 2 (ключ-кортеж вместо компаратора).** Кортежи сравниваются лексикографически — сначала первые элементы, при их равенстве вторые (R9, реализация `Ord` для кортежей). Значит двухключевой порядок можно выразить одним **ключом**, без разбора `Ordering`. Единственная сложность — «по убыванию»: `sort_by_key` всегда сортирует ключи по возрастанию, поэтому балл надо перевернуть арифметически. Файл `p1/c9_tuple_key.rs`:

```rust
// Г21.Ч1.З9, вариант 2: один ключ-кортеж вместо компаратора.
fn main() {
    let mut table: Vec<(&str, u32)> = vec![("Вера", 78), ("Аня", 92), ("Глеб", 92), ("Боря", 85)];

    // Кортежи сравниваются лексикографически: сначала минус-балл, потом имя.
    table.sort_by_key(|&(name, score)| (-(score as i64), name));

    for (name, score) in &table {
        println!("{score:>3} {name}");
    }
}
```

```
$ rustc --edition 2024 c9_tuple_key.rs
$ ./c9_tuple_key.exe
 92 Аня
 92 Глеб
 85 Боря
 78 Вера
```

Вывод тот же. Детали: образец `&(name, score)` в параметре разбирает ссылку на элемент сразу (§16.2.2), оба поля `Copy`, поэтому копируются; `score as i64` — приведение (§14.2.3) перед отрицанием, потому что `u32` беззнаковый и `-score` для него не имеет смысла (в отладочной сборке это была бы паника переполнения, а `as i64` расширяет диапазон заведомо без потерь); `name` попадает в ключ как `&str` — ссылка на строковые данные живёт независимо от того, как мы перекладываем элементы вектора.

*Сравнение.* Компаратор из основного решения описывает **правила сравнения** (что с чем и в каком направлении), ключ-кортеж — **сортируемое представление** элемента. Кортеж короче, читается почти как формулировка задачи и не даёт забыть рукав; но переворот порядка приходится выражать арифметикой (`-(score as i64)`), а это работает только для чисел: убывание по строке или по типу без арифметики так не запишешь, и для `f64` (нет `Ord`, §19.2.3) ключ-кортеж тоже не соберётся. Ещё одно отличие в цене: `sort_by_key` вызывает замыкание-ключ на каждое сравнение и строит кортеж заново, компаратор же ничего не конструирует. Практический выбор: числовые ключи и простые направления — кортеж; хитрые правила (регистронезависимость, свои шкалы, `partial_cmp` у вещественных) — компаратор.

```rust
pub fn apply_n<F: Fn(i32) -> i32>(f: F, x: i32, n: u32) -> i32 {

    for _ in 0..n {

    }
    acc
}
```

**Почему ограничение `Fn`, а не `FnMut`/`FnOnce`.** Приёмник зовёт `f` в цикле — многократно, и ничего не меняет в захваченном. По правилу §21.1.3 (просить минимум, который нужен вызову) это `Fn`. `FnOnce` не подошёл бы вовсе: со «разовым пропуском» цикл собрать нельзя. `FnMut` подошёл бы и принимал бы больше замыканий (в том числе меняющих окружение), но потребовал бы `mut f` в сигнатуре и разрешил бы функции-приёмнику неожиданные для вызывающего побочные эффекты; для «применить чистое преобразование n раз» строгий `Fn` — честный контракт.

**Случай `n = 0`.** Цикл `for _ in 0..0` не делает ни одного шага, `acc` остаётся `x` — тождество получается само, без отдельной ветки. **Захват из окружения.** `let step = 5; apply_n(|x| x + step, 0, 4)` — замыкание берёт `step` разделяемым заимствованием (тело только читает), это законно и не мешает `Fn`: 0 → 5 → 10 → 15 → 20. Обратите внимание, что `apply_n` про захват ничего не знает — она видит только «нечто, реализующее `Fn(i32) -> i32`». Именно это и было невозможно с указателем на функцию в C (§6.3.2): контекст пришлось бы передавать через глобальную переменную.

**Вариант 2 (рекурсия вместо цикла).** Определение «применить n раз» рекурсивно по своей природе: применить нуль раз — тождество, применить n раз — применить один раз и повторить n−1 раз. Файл `p1/applyn_rec/src/lib.rs` (тесты дословно те же, меняется только тело функции):

```rust
// Библиотека applyn, вариант 2: рекурсия вместо цикла (Г21.Ч1.З10).

/// Применяет f к x ровно n раз: f(f(...f(x))). При n = 0 возвращает x.
pub fn apply_n<F: Fn(i32) -> i32>(f: F, x: i32, n: u32) -> i32 {
    if n == 0 {
        x
    } else {
        let next = f(x);
        apply_n(f, next, n - 1)
    }
}
```

Читаемость — вопрос вкуса: рекурсия ближе к формулировке «f(f(...f(x)))», цикл — к машине. Для библиотечной функции общего назначения предпочтителен цикл; рекурсивная запись хороша как проверка понимания (и как напоминание, что `F` — обычное значение со своим владением).

### Г21.Ч2.З1

**Условие.** Дан `let v = vec!["мир", "труд", "май"];` и `let mut it = v.iter();`. Выпишите, не запуская, результат каждого из пяти подряд вызовов `it.next()` (в форме `Some(...)`/`None`), затем проверьте программой с `{:?}`-печатью. Каков точный тип значения, возвращаемого `it.next()`? Почему печать не показывает ссылочность?

**Решение.** *Предсказание.* Итератор — турникет с позицией (§21.2.1): три элемента, три `Some`, дальше поток кончился. Ожидаем `Some("мир")`, `Some("труд")`, `Some("май")`, `None`, `None` — последний потому, что итератор вектора после исчерпания продолжает выдавать `None` (общий контракт `Iterator` этого не обещает, но у итератора среза это так).

Файл `p2/i1_next.rs`:

```rust
// Г21.Ч2.З1: пять подряд вызовов next у итератора вектора.
fn main() {
    let v = vec!["мир", "труд", "май"];
    let mut it = v.iter();

    println!("{:?}", it.next());
    println!("{:?}", it.next());
    println!("{:?}", it.next());
    println!("{:?}", it.next());
    println!("{:?}", it.next());
}
```

```
$ rustc --edition 2024 i1_next.rs
$ ./i1_next.exe
Some("мир")
Some("труд")
Some("май")
None
None
```

Предсказание совпало. Теперь — **точный тип**. Элементы вектора имеют тип `&str` (строковые литералы, §17.1.4), метод `iter()` выдаёт **ссылки на элементы** (§21.2.1), то есть `&&str`; результат `next` — `Option<&&str>`. Спросим компилятор (приём §18.1.2), файл `p2/i1_ask.rs`:

```rust
// Г21.Ч2.З1: ⛔ спрашиваем компилятор про точный тип результата next.
fn main() {
    let v = vec!["мир", "труд", "май"];
    let mut it = v.iter();
    let () = it.next(); // ⛔ намеренная ошибка
}
```

```
error[E0308]: mismatched types
 --> i1_ask.rs:5:9
  |
5 |     let () = it.next(); // ⛔ намеренная ошибка
  |         ^^   --------- this expression has type `Option<&&str>`
  |         |
  |         expected `Option<&&str>`, found `()`
  |
  = note:   expected enum `Option<&&str>`
          found unit type `()`
```

`Option<&&str>` — двойная ссылка, как и предсказано: одну добавил сам тип элемента (`&str` — уже ссылка на строковые данные), вторую — `iter()`. Это ровно тот механизм, который в §21.2.2 создаёт `&&i32` в предикатах `filter` (задание Г21.Ч2.З7).

**Почему печать не показывает ссылочность.** `{:?}` вызывает реализацию трейта `Debug`, а для ссылок она **делегирует** печать тому, на что ссылка указывает (R9: `impl Debug for &T` пересылает вызов в `T::fmt`). Никакого «адреса» в выводе не появится ни при одной вложенности ссылок: `&&str` печатается как `&str`, то есть как строка в кавычках. Кавычки, кстати, — тоже работа `Debug` (у `Display`, то есть `{}`, их бы не было).

Убедиться в ссылочности можно в форме, где типы сравниваются, а не печатаются, — `assert_eq!` (§20.2.1). Файл `p2/i1_assert.rs`:

```rust
// Г21.Ч2.З1: ссылочность видна в assert_eq!.
fn main() {
    let v = vec!["мир", "труд", "май"];
    let mut it = v.iter();

    assert_eq!(it.next(), Some(&"мир"));
    assert_eq!(it.next(), Some(&"труд"));
    assert_eq!(it.next(), Some(&"май"));
    assert_eq!(it.next(), None);
    println!("all asserts passed");
}
```

```
$ rustc --edition 2024 i1_assert.rs
$ ./i1_assert.exe
all asserts passed
```

Здесь `&` писать обязательно: `Some("мир")` имело бы тип `Option<&str>` и не сравнилось бы с `Option<&&str>` — E0308. Именно так глава §21.2.1 показывает ссылочность на числах (`Some(&1)`).

**Ответ:** пять вызовов дают `Some("мир")`, `Some("труд")`, `Some("май")`, `None`, `None`. Точный тип результата — `Option<&&str>`: тип элемента вектора уже ссылка (`&str`), а `iter()` добавляет свою (`&T`); подтверждено ошибкой E0308 из `i1_ask.rs` и тестовой формой `Some(&"мир")`. Печать `{:?}` не показывает ссылочность, потому что `Debug` для ссылки перенаправляет форматирование на значение под ней — сколько бы `&` ни было в типе, напечатается сама строка.

### Г21.Ч2.З2

**Условие.** Перепишите каждый фрагмент одной итераторной цепочкой без изменяемых переменных, сверьте результаты с цикловой версией: (а) сумма квадратов чётных чисел от 1 до 10 (ответ 220); (б) количество слов длиннее трёх символов в строке `"то ли дождик то ли снег то ли будет то ли нет"` (символы считайте `chars().count()`); (в) вектор длин всех слов той же строки.

**Решение.** Обе версии в одной программе — так сверка получается машинной, а не на глаз: `assert_eq!` уронит программу при расхождении (§20.2.1). Файл `p2/i2_chains.rs`:

```rust
// Г21.Ч2.З2: три ручных цикла и три цепочки — с проверкой совпадения.
fn main() {
    let text = "то ли дождик то ли снег то ли будет то ли нет";

    // (а) сумма квадратов чётных чисел от 1 до 10
    let mut sum_loop = 0;
    for x in 1..=10 {
        if x % 2 == 0 {
            sum_loop += x * x;
        }
    }
    let sum_chain: i32 = (1..=10).filter(|x| x % 2 == 0).map(|x| x * x).sum();
    assert_eq!(sum_loop, sum_chain);
    println!("a: {sum_chain}");

    // (б) количество слов длиннее трёх символов
    let mut long_loop: usize = 0;
    for w in text.split_whitespace() {
        if w.chars().count() > 3 {
            long_loop += 1;
        }
    }
    let long_chain = text
        .split_whitespace()
        .filter(|w| w.chars().count() > 3)
        .count();
    assert_eq!(long_loop, long_chain);
    println!("b: {long_chain}");

    // (в) вектор длин всех слов
    let mut lens_loop = Vec::new();
    for w in text.split_whitespace() {
        lens_loop.push(w.chars().count());
    }
    let lens_chain: Vec<usize> = text.split_whitespace().map(|w| w.chars().count()).collect();
    assert_eq!(lens_loop, lens_chain);
    println!("c: {lens_chain:?}");
}
```

```
$ rustc --edition 2024 i2_chains.rs
$ ./i2_chains.exe
a: 220
b: 3
c: [2, 2, 6, 2, 2, 4, 2, 2, 5, 2, 2, 3]
```

Все три `assert_eq!` прошли молча — цепочки и циклы согласны. Разбор:

**(а)** `(1..=10).filter(|x| x % 2 == 0).map(|x| x * x).sum()` — три звена: источник (диапазон — сам себе итератор, §21.2.1), отбор, преобразование, агрегат. Ответ 220 = 4 + 16 + 36 + 64 + 100 совпал с обещанным в условии. Аннотация `sum_chain: i32` обязательна: тип суммы `sum()` из типа элементов однозначно не выводится (§21.2.2), без неё — «type annotations needed». Порядок звеньев важен по смыслу: `map` перед `filter` возводил бы в квадрат все числа, а фильтр по чётности квадрата дал бы тот же набор, но лишнюю работу; в общем случае «сначала отсеять, потом преобразовывать» и дешевле, и понятнее.

Тонкость типов: `filter` даёт замыканию **ссылку** на элемент (`&i32`), поэтому внутри `x % 2` работает с `&i32` — арифметика для ссылок реализована стандартной библиотекой (§21.2.2), и лишних разыменований не нужно; а `map` получает элемент как есть (`i32`), потому что элементы диапазона — значения, а не ссылки.

**(б)** `text.split_whitespace().filter(|w| w.chars().count() > 3).count()` — «счётчик совпадений» из словаря перевода §21.2.2 (`filter(...).count()`). Слова: `то`(2), `ли`(2), `дождик`(6), `то`, `ли`, `снег`(4), `то`, `ли`, `будет`(5), `то`, `ли`, `нет`(3). Длиннее трёх — `дождик`, `снег`, `будет`: ответ 3. Слово `нет` ровно из трёх символов и в счёт не идёт — граница «строго больше» проверяется именно этим словом.

Почему `chars().count()`, а не `len()`: `len()` у `&str` — длина в **байтах** (§17.1.4), а кириллическая буква в UTF-8 занимает два байта, поэтому `"дождик".len()` дало бы 12. Условие требует символы — считаем итератором `chars()`.

Тип счётчика в цикловой версии пришлось объявить явно (`let mut long_loop: usize = 0;`): `count()` возвращает `usize`, и без аннотации `assert_eq!` сравнивал бы `i32` с `usize` — E0308.

**(в)** `text.split_whitespace().map(|w| w.chars().count()).collect()` — «преобразовать каждый элемент» плюс сбор. Аннотация `Vec<usize>` нужна `collect`, иначе E0283 (§21.2.2): собрать можно во многое, компилятор не угадывает. Результат — двенадцать чисел, по числу слов; в нём видна структура текста: чередование `2, 2` (то, ли) с длинами «содержательных» слов 6, 4, 5, 3.

**Ответ:** три цепочки, изменяемых переменных ни в одной:

```rust
let sum_chain: i32 = (1..=10).filter(|x| x % 2 == 0).map(|x| x * x).sum();
let long_chain = text.split_whitespace().filter(|w| w.chars().count() > 3).count();
let lens_chain: Vec<usize> = text.split_whitespace().map(|w| w.chars().count()).collect();
```

Результаты: (а) `220`, (б) `3`, (в) `[2, 2, 6, 2, 2, 4, 2, 2, 5, 2, 2, 3]`; совпадение с цикловыми версиями проверено `assert_eq!` в той же программе. Аннотации типа обязательны у `sum` (тип суммы) и у `collect` (тип-приёмник); длину слова считаем `chars().count()`, а не `len()`, потому что `len()` меряет байты.

Кстати, все три задачи выражаются и через один универсальный потребитель — `fold` (§21.2.2). Файл `p2/i2_fold.rs`:

```rust
// Г21.Ч2.З2: те же три ответа через fold — для сверки.
fn main() {
    let text = "то ли дождик то ли снег то ли будет то ли нет";

    let a = (1..=10)
        .filter(|x| x % 2 == 0)
        .fold(0, |acc, x| acc + x * x);
    let b = text
        .split_whitespace()
        .fold(0, |acc, w| if w.chars().count() > 3 { acc + 1 } else { acc });
    let c = text.split_whitespace().fold(Vec::new(), |mut acc, w| {
        acc.push(w.chars().count());
        acc
    });

    println!("a: {a}");
    println!("b: {b}");
    println!("c: {c:?}");
}
```

```
$ rustc --edition 2024 i2_fold.rs
$ ./i2_fold.exe
a: 220
b: 3
c: [2, 2, 6, 2, 2, 4, 2, 2, 5, 2, 2, 3]
```

Те же три ответа. Видно, чем платят за универсальность: `fold` заставляет писать накопление руками (и даже принимать `mut acc` в третьем случае — изменяемая переменная вернулась, только теперь она параметр замыкания), тогда как `sum`/`count`/`collect` называют намерение одним словом. Правило: специализированный потребитель, если он есть; `fold` — когда нужной свёртки в библиотеке нет.

### Г21.Ч2.З3

**Условие.** Одними адаптерами (без индексной арифметики): (а) напечатайте список покупок `["хлеб", "молоко", "сыр"]` с нумерацией с единицы; (б) постройте `Vec<(&str, u32)>` из `["пн", "вт", "ср"]` и `[12, 17, 9]`; (в) соберите вектор `[8, 6, 4, 2]` из диапазона `1..=8` (подсказка: `filter` + `rev`); (г) выдайте элементы диапазона `1..=100` с 4-го по 7-й включительно (`skip` + `take`).

**Решение.** Файл `p2/i3_adapters.rs`:

```rust
// Г21.Ч2.З3: четыре задачи одними адаптерами.
fn main() {
    // (а) нумерация с единицы
    let shopping = ["хлеб", "молоко", "сыр"];
    for (i, item) in shopping.iter().enumerate() {
        println!("{}. {item}", i + 1);
    }

    // (б) пары из двух массивов
    let days = ["пн", "вт", "ср"];
    let counts = [12u32, 17, 9];
    let table: Vec<(&str, u32)> = days
        .iter()
        .zip(counts.iter())
        .map(|(d, c)| (*d, *c))
        .collect();
    println!("{table:?}");

    // (в) чётные задом наперёд
    let evens_back: Vec<u32> = (1..=8).filter(|x| x % 2 == 0).rev().collect();
    println!("{evens_back:?}");

    // (г) элементы с 4-го по 7-й включительно
    let window: Vec<u32> = (1..=100).skip(3).take(4).collect();
    println!("{window:?}");
}
```

```
$ rustc --edition 2024 i3_adapters.rs
$ ./i3_adapters.exe
1. хлеб
2. молоко
3. сыр
[("пн", 12), ("вт", 17), ("ср", 9)]
[8, 6, 4, 2]
[4, 5, 6, 7]
```

Разбор по пунктам.

**(а)** `enumerate` нумерует **с нуля** (R9) — это не настройка, а определение адаптера. Человеческая нумерация получается сдвигом в момент печати: `i + 1`. Образец `(i, item)` в заголовке цикла разбирает пару прямо на месте (§16.2.2) — отдельного `let` не нужно. Обратите внимание, что индекс здесь используется как **номер строки в выводе**, а не для доступа к элементу: доступ даёт сам итератор. Это и есть «индекс, когда он правда нужен» из §14.2.4.

**(б)** `zip` идёт по двум последовательностям в ногу, выдавая пары. Длины совпали (по 3), поэтому пар ровно три. Звено `map(|(d, c)| (*d, *c))` нужно из-за ссылочности: `days.iter()` даёт `&&str`, `counts.iter()` даёт `&u32`, значит `zip` выдаёт `(&&str, &u32)`, а нам заказан `Vec<(&str, u32)>` — разыменование в `map` снимает по одному уровню с каждого элемента пары. Образец `|(d, c)|` разбирает пару-аргумент; `*d` и `*c` копируют значения (обе — `Copy`). Аннотация типа у `table` обязательна для `collect`.

Тип массива `counts` пришлось задать явно (`[12u32, 17, 9]`): без суффикса числа получили бы умолчание `i32` (§14.2.2), и `collect` в `Vec<(&str, u32)>` не собрался бы.

**(в)** `(1..=8).filter(|x| x % 2 == 0).rev()` — сначала отбор чётных `[2, 4, 6, 8]`, потом разворот. `rev` требует, чтобы итератор умел ходить с обоих концов (`DoubleEndedIterator`, R9); у диапазона это есть, и `filter` над ним свойство сохраняет — поэтому цепочка законна. Порядок звеньев можно поменять (`.rev().filter(...)`) — результат тот же; выбор диктует читаемость.

**(г)** `skip(3).take(4)`: «пропустить первые три» ставит турникет на 4-й элемент, «взять четыре» отсчитывает 4, 5, 6, 7. Перевод «с 4-го по 7-й» в `skip`/`take` — вычитание единицы один раз (номер первого нужного минус один) и подсчёт количества (7 − 4 + 1 = 4); никакой индексной арифметики по коллекции при этом не возникает. Важное следствие ленивости: из ста чисел диапазона реально произведено семь — потребитель `collect` перестаёт дёргать цепочку, как только `take` выдаёт `None`.

**Ответ:** четыре цепочки:

```rust
for (i, item) in shopping.iter().enumerate() { println!("{}. {item}", i + 1); }
let table: Vec<(&str, u32)> = days.iter().zip(counts.iter()).map(|(d, c)| (*d, *c)).collect();
let evens_back: Vec<u32> = (1..=8).filter(|x| x % 2 == 0).rev().collect();
let window: Vec<u32> = (1..=100).skip(3).take(4).collect();
```

Вывод: `1. хлеб` / `2. молоко` / `3. сыр`; `[("пн", 12), ("вт", 17), ("ср", 9)]`; `[8, 6, 4, 2]`; `[4, 5, 6, 7]`. Ключевые детали: `enumerate` считает с нуля (сдвиг `i + 1` — на печати), `zip` требует снятия ссылок через `map`, `rev` работает потому, что диапазон двусторонний, `skip(3).take(4)` — прямой перевод «с 4-го по 7-й включительно».

### Г21.Ч2.З4

**Условие.** Программа `v.iter().map(|x| println!("{x}"));` ничего не печатает. Объясните через ленивость и предупреждение компилятора (какой атрибут стандартной библиотеки его вызывает — §18.1.2?). Приведите три починки: потребитель `for_each`, потребитель `collect` (что и куда собирать?), обычный цикл `for` — и укажите, какая из них идиоматична для «просто выполнить действие для каждого» (R9).

**Решение.** Файл `p2/i4_lazy.rs`:

```rust
// Г21.Ч2.З4: цепочка без потребителя.
fn main() {
    let v = vec![1, 2, 3];

    v.iter().map(|x| println!("{x}")); // ничего не печатает

    println!("map did not run");
}
```

**Почему тихо.** `map` — адаптер: он не выполняет работу, а строит новый итератор (значение типа `Map<...>`), который **описывает** будущую работу (§21.2.2). Тело замыкания запускается только тогда, когда кто-то дёргает `next` — то есть при появлении потребителя. Потребителя нет, значение `Map` создано и тут же выброшено, замыкание не вызвано ни разу; программа печатает только собственную строку.

**Какой атрибут даёт предупреждение.** `#[must_use]` — тот самый, что в §18.1.2 охранял `Result` от молчаливого игнорирования. Тип `Map` (как и прочие адаптеры) им помечен, отсюда и `unused Map that must be used`, и группа предупреждений в примечании: `#[warn(unused_must_use)]`. Формулировка `iterators are lazy and do nothing unless consumed` — часть текста атрибута, написанная авторами стандартной библиотеки специально для этого случая.

```
  |              |   called `Iterator::map` with callable that returns `()`

  |
  = note: `Iterator::map`, like many of the methods on `Iterator`, gets executed lazily, meaning that its effects won't be visible until it is iterated
  = note: `#[warn(map_unit_fn)]` (part of `#[warn(unused)]`) on by default
help: you might have meant to use `Iterator::for_each`
  |
5 -     v.iter().map(|x| println!("{x}")); // ничего не печатает
5 +     v.iter().for_each(|x| println!("{x}")); // ничего не печатает
  |
```

Это `map_unit_fn` — линт про «`map` с замыканием, возвращающим `()`»: раз преобразование ничего не возвращает, единственное, что несёт получившийся итератор, — количество элементов. Компилятор прямо предлагает `for_each`, то есть подсказывает и диагноз (используете `map` ради побочного эффекта), и лечение.

**Три починки.** Файл `p2/i4_fixes.rs`:

```rust
// Г21.Ч2.З4: три починки.
fn main() {
    let v = vec![1, 2, 3];

    // 1) потребитель for_each
    v.iter().for_each(|x| println!("for_each: {x}"));

    // 2) потребитель collect: собирать нечего — тип элемента ()
    let units: Vec<()> = v.iter().map(|x| println!("collect: {x}")).collect();
    println!("collected {} units", units.len());

    // 3) обычный цикл for — идиоматичный вариант
    for x in &v {
        println!("for: {x}");
    }
}
```

```
$ rustc --edition 2024 i4_fixes.rs
$ ./i4_fixes.exe

for_each: 2
for_each: 3
collect: 1
collect: 2
collect: 3
collected 3 units
for: 1
for: 2
for: 3
```

Все три печатают. Разбор:

1. **`for_each`** — потребитель, созданный ровно для побочных эффектов: он крутит `next` до конца и зовёт замыкание на каждом элементе, ничего не возвращая. Цепочка сработала.
2. **`collect`** — тоже потребитель, но он обязан **куда-то** собрать элементы. Что собирать? Замыкание `|x| println!(...)` возвращает `()`, значит элементы итератора — единичные значения; тип-приёмник `Vec<()>` (в него собираются три пустых кортежа, ровно по числу элементов). Аннотация обязательна: без неё E0283 (§21.2.2). Вывод `collected 3 units` показывает, что вектор из «ничего» действительно построен — и это исчерпывающе объясняет, почему такая починка нелепа: мы платим вектором за то, что нам не нужно.
3. **Цикл `for`** — никакой ленивости: `for` сам берёт итератор и крутит его до `None` (§21.2.1).

**Что идиоматично.** Для «просто выполнить действие для каждого элемента» — обычный `for` (R9 прямо советует его вне цепочек). `for_each` уместен как **конец цепочки**, когда всё остальное уже выражено адаптерами: `v.iter().filter(...).map(...).for_each(...)` читается лучше, чем `for x in v.iter().filter(...).map(...)`. `collect` в `Vec<()>` — не починка, а демонстрация механизма: он выделяет память под результат, который никому не нужен.

**Ответ:** программа молчит, потому что `map` — ленивый адаптер: он только строит значение `Map`, а тело замыкания выполняется лишь по требованию потребителя, которого в цепочке нет. Предупреждение вызывает атрибут **`#[must_use]`** (тот же, что охраняет `Result`, §18.1.2), текст — `unused Map that must be used` + `iterators are lazy and do nothing unless consumed`; вдобавок 1.97 выдаёт линт `map_unit_fn` с прямым советом заменить `map` на `for_each`. Три починки: `v.iter().for_each(|x| println!("{x}"))`; `let units: Vec<()> = v.iter().map(|x| println!("{x}")).collect();` (собирать приходится единичные значения `()` — по одному на элемент); и обычный `for x in &v { println!("{x}"); }`. Идиоматичен для «просто выполнить действие» цикл `for`; `for_each` — когда действие завершает уже существующую цепочку; `collect` в `Vec<()>` работает, но выделяет память впустую.

### Г21.Ч2.З5

**Условие.** Ещё раз о ⛔-примере §17.1.2: `for s in v` по `Vec<String>`, после цикла `v.len()` — E0382. Объясните ошибку через десахаризацию `for` (§21.2.1): какой метод вызывается, что происходит с владением? Почему замена на `for s in &v` чинит программу, и какой тип получает `s` в каждом варианте? Когда обход по значению — правильный выбор (приведите сценарий из §17.1.2)?

**Решение.** Воспроизведём. Файл `p2/i5_moved_bad.rs`:

**Десахаризация.** Компилятор сам называет виновника: `v moved due to this implicit call to .into_iter()`. По арбитру R7 (loop expressions) запись `for s in v { тело }` раскрывается в

```rust
let mut it = IntoIterator::into_iter(v);
loop {
    match it.next() {
        Some(s) => { тело }
        None => break,
    }
}
```

Ключевое — **`into_iter(v)` принимает `self` по значению** (об этом вторая `note`: `into_iter takes ownership of the receiver self`). Владение вектором уезжает в итератор ещё до первой итерации; после цикла итератор уничтожен вместе со всем, что не успело быть выдано, а имя `v` аннулировано (§15.1.2). Отсюда E0382 на любом последующем обращении — даже на безобидном `v.len()`, которому хватило бы ссылки: спорить не о чем, значения больше нет.

**Почему `&v` чинит.** С амперсандом в `into_iter` уезжает не вектор, а **ссылка** на него: `IntoIterator` реализован и для `&Vec<T>`, и его `into_iter` эквивалентен `v.iter()` (§21.2.1). Вектор остаётся у переменной `v`, итератор лишь заимствует его на время цикла (заём кончается вместе с циклом — NLL, §15.2.2), поэтому `v.len()` после цикла законен. Файл `p2/i5_ref.rs`:

```rust
// Г21.Ч2.З5: починка — обход по ссылке.
fn main() {
    let v = vec![String::from("раз"), String::from("два")];

    for s in &v {
        println!("{s}");

    println!("{}", v.len());
}
```

**Когда обход по значению правилен.** Когда коллекция **разбирается насовсем**: элементы нужны целиком и переживут её, а сам вектор дальше не нужен. Пример из §17.1.2 — разбор строки таблицы (`Vec` перечислений) по значению: «строка таблицы разбирается целиком, вектор после цикла не нужен». Тот же мотив в чистом виде — перекладывание строк без единого клона. Файл `p2/i5_consume.rs`:

```rust

    let rows = vec![
        String::from("раз"),
        String::from("два"),
        String::from("четыре"),
    ];

    let mut kept = Vec::new();
    for s in rows {
        // s принадлежит нам целиком — строку можно переложить без clone
        if s.chars().count() == 3 {
            kept.push(s);
        }
    }

    println!("{kept:?}");
}
```


Ни одного выделения памяти под копии строк: буферы просто сменили владельца. С `&rows` тот же код потребовал бы `s.clone()` на каждый отобранный элемент — и оставил бы нас с двумя копиями данных вместо одной.

**Ответ:** `for s in v` раскрывается в `IntoIterator::into_iter(v)`, а этот метод принимает получатель **по значению** — вектор перемещается в итератор ещё до первой итерации, поэтому после цикла имени `v` не существует и `v.len()` даёт E0382 (компилятор так и пишет: `v moved due to this implicit call to .into_iter()`). Замена на `for s in &v` отдаёт в `into_iter` ссылку (это `v.iter()`), вектор остаётся у владельца, заём кончается вместе с циклом. Типы: `for s in v` → `s: String`; `for s in &v` → `s: &String` (проверено ошибками E0308 из `i5_ask_value.rs` и `i5_ask_ref.rs`). Обход по значению правилен, когда коллекция разбирается насовсем: сценарий §17.1.2 — разбор строки таблицы, где элемент нужен целиком, а вектор после цикла не нужен; в нашем опыте это перенос отобранных строк в другой вектор без единого `clone`.

### Г21.Ч2.З6

**Условие.** Протрассируйте `(1..=5).fold(1, |acc, x| acc * x)` таблицей шагов: значения `acc` и `x` на каждом шаге, итог (факториал 5 = 120). Затем выразите через `fold`: (а) `count` (старт и замыкание?); (б) максимум последовательности `[3, 7, 1, 9, 4]` (подсказка: старт `i32::MIN`, в замыкании — сравнение). Проверьте программой, что ваши `fold`-версии совпадают с `count()` и `max()`.

**Решение.** *Трассировка на бумаге.* Начальный аккумулятор — 1 (нейтральный элемент умножения), затем для каждого элемента слева направо `acc = acc * x`:

| Шаг | `acc` до | `x` | `acc` после |
|---|---|---|---|
| 1 | 1 | 1 | 1 |
| 2 | 1 | 2 | 2 |
| 3 | 2 | 3 | 6 |
| 4 | 6 | 4 | 24 |
| 5 | 24 | 5 | 120 |

Итог — последний аккумулятор, 120 = 5!.

Проверим трассировку печатью изнутри свёртки и заодно построим `fold`-версии `count` и `max`. Файл `p2/i6_fold.rs`:

```rust
// Г21.Ч2.З6: трассировка fold и выражение count/max через fold.
fn main() {
    let product = (1..=5).fold(1, |acc, x| {
        let next = acc * x;
        println!("acc = {acc}, x = {x} -> {next}");
        next
    });
    println!("factorial 5 = {product}");

    let v = vec![3, 7, 1, 9, 4];

    // (а) count через fold
    let count_fold = v.iter().fold(0, |acc, _| acc + 1);
    println!("count: fold {count_fold}, method {}", v.iter().count());
    assert_eq!(count_fold, v.iter().count());

    // (б) максимум через fold
    let max_fold = v
        .iter()
        .fold(i32::MIN, |acc, x| if *x > acc { *x } else { acc });
    println!("max: fold {max_fold}, method {:?}", v.iter().max());
    assert_eq!(max_fold, *v.iter().max().unwrap());
}
```

Пять строк трассировки совпали с таблицей до цифры, оба `assert_eq!` прошли.

**(а) `count` через `fold`.** Старт — `0` (пустая последовательность содержит ноль элементов), замыкание — `|acc, x| acc + 1`, то есть **элемент игнорируется**: считаем не значения, а факты появления. В коде параметр назван `_` — общепринятый способ сказать «значение не нужно» (§16.2.2), иначе компилятор предупредил бы о неиспользуемой переменной. Тип аккумулятора здесь `usize`: его навязал `assert_eq!` со сравнением против `count()`.

**(б) `max` через `fold`.** Старт — `i32::MIN`: «худший возможный кандидат», который проиграет любому реальному элементу. Замыкание сравнивает и оставляет большее: `if *x > acc { *x } else { acc }`. Разыменования обязательны: `v.iter()` выдаёт `&i32`, а `acc` у нас `i32` — сравнивать и присваивать надо значения (можно было бы, наоборот, вести аккумулятор в ссылках, но тогда старт `&i32::MIN` потребовал бы временного значения).

**Где `fold`-версия хуже библиотечной.** У `max()` результат — `Option<i32>` (в выводе `Some(9)`), потому что у пустой последовательности максимума **нет** (§16.2.3). `fold` же тотален: он всегда возвращает аккумулятор, и на пустом входе выдаст стартовое значение — то есть соврёт. Файл `p2/i6_fold_empty.rs`:

```rust

    let empty: Vec<i32> = Vec::new();

    let max_fold = empty
        .iter()
        .fold(i32::MIN, |acc, x| if *x > acc { *x } else { acc });

    println!("fold: {max_fold}");
    println!("max(): {:?}", empty.iter().max());
}
```


`fold` уверенно сообщает `-2147483648` — значение-сигнал в духе тома I (сравните с `EOF` и «магическими» кодами возврата, §10.1.2), а `max()` честно отвечает `None`. Это ровно та разница, ради которой в Rust заведён `Option`: свёртка со стартовым значением прячет случай «данных не было», библиотечный потребитель — предъявляет. С `count` такой беды нет: ноль — честный ответ для пустой последовательности.

**Ответ:** трассировка — пять шагов, `acc`: 1 → 1 → 2 → 6 → 24 → 120; итог `120`. (а) `count` через `fold`: старт `0`, замыкание `|acc, _| acc + 1` — элемент не используется. (б) максимум: старт `i32::MIN`, замыкание `|acc, x| if *x > acc { *x } else { acc }`. Обе версии совпали с библиотечными (`count()` = 5, `max()` = `Some(9)`), совпадение проверено `assert_eq!`. Существенная оговорка: на **пустой** последовательности `fold`-максимум вернёт стартовое `i32::MIN`, тогда как `max()` вернёт `None` — специализированный потребитель отличает «нет данных» от «значение», свёртка со стартом — нет.

### Г21.Ч2.З7

**Условие.** `v.iter().filter(|x| x > 2)` по `Vec<i32>` не компилируется: E0308 «expected `&&_`, found integer». Объясните, откуда берётся *двойная* ссылка (кто добавил первую? кто вторую?). Приведите две починки из §21.2.2 и третью — `filter(|x| **x > 2)` против `filter(|&&x| x > 2)`: покажите, что обе дают `[5, 8]` на `vec![1, 5, 2, 8]`. Почему у `map(|x| x + 1)` на том же векторе проблемы нет?

**Решение.** Воспроизведём ошибку. Файл `p2/i7_bad.rs`:

```rust
// Г21.Ч2.З7: ⛔ двойная ссылка в предикате filter.
fn main() {
    let v = vec![1, 5, 2, 8];

    let big: Vec<&i32> = v.iter().filter(|x| x > 2).collect(); // ⛔

    println!("{big:?}");
}
```

```
error[E0308]: mismatched types
 --> i7_bad.rs:5:50
  |
5 |     let big: Vec<&i32> = v.iter().filter(|x| x > 2).collect(); // ⛔
  |                                                  ^ expected `&&_`, found integer
  |
  = note: expected reference `&&_`
                  found type `{integer}`
```

**Откуда две ссылки.**

- **Первую добавил `iter()`**: он ходит по коллекции, ничего не забирая, поэтому выдаёт элементы как `&T` — здесь `&i32` (§21.2.1). Это тип **элемента** итератора.
- **Вторую добавил `filter`**: его предикат по сигнатуре `P: FnMut(&Self::Item) -> bool` получает **ссылку на элемент** (R9). Элемент уже `&i32`, значит замыкание получает `&&i32`.

Почему `filter` устроен именно так: предикат не должен иметь возможности забрать элемент — иначе `filter` не смог бы пропустить его дальше по конвейеру. Ссылка гарантирует, что элемент остаётся у итератора.

Компилятор указывает на `2`, а не на `x`: он вывел, что левая часть сравнения имеет тип `&&_`, и требует того же справа, а справа — целочисленный литерал. Отсюда формулировка `expected &&_, found integer`.

**Две починки.** Файл `p2/i7_fixes.rs`:

```rust
// Г21.Ч2.З7: две починки предиката и map для сравнения.
fn main() {
    let v = vec![1, 5, 2, 8];

    // починка 1: разыменовать дважды
    let a: Vec<&i32> = v.iter().filter(|x| **x > 2).collect();
    // починка 2: снять обе ссылки образцом
    let b: Vec<&i32> = v.iter().filter(|&&x| x > 2).collect();
    println!("{a:?} {b:?}");

    // у map той же проблемы нет: элемент приходит как есть, одной ссылкой
    let plus: Vec<i32> = v.iter().map(|x| x + 1).collect();
    println!("{plus:?}");
}
```


Обе починки дают `[5, 8]` — как и требовало условие.

**`**x > 2` против `|&&x| x > 2`.** Разница в том, **где** снимаются ссылки:

| | `filter(\|x\| **x > 2)` | `filter(\|&&x\| x > 2)` |
|---|---|---|
| Тип параметра | `x: &&i32` | образец разбирает `&&i32`, `x: i32` |
| Где снимаются ссылки | в теле, оператором `*` | в заголовке, образцом (§16.2.2) |
| Тело читается как | «дважды разыменуй и сравни» | «сравни» |
| Если ссылок станет больше/меньше | правится тело | правится образец |

Механика второго варианта — сопоставление с образцом: `&&x` — это образец, зеркальный типу `&&i32`, он «снимает» обе ссылки и связывает `x` с копией значения (`i32` — `Copy`, поэтому копия законна и бесплатна). Для не-`Copy` элементов такой образец не прошёл бы: он попытался бы вынести значение из-под ссылки — E0507 (§17.1.1). Оба варианта одинаково эффективны (ссылки существуют только в типах, в машинном коде их снятие ничего не стоит); выбор — стилистический, и большинство кода в экосистеме предпочитает образец, потому что тело предиката остаётся чистым.

Результат `[5, 8]` собран как `Vec<&i32>` — ссылки, а не числа: `filter` не преобразует элементы, а только отбирает, поэтому наружу выходят те же `&i32`, что дал `iter()`.

**Почему у `map` проблемы нет.** У `map` сигнатура другая: `F: FnMut(Self::Item) -> B` — замыкание получает **сам элемент**, а не ссылку на него (R9). Элемент здесь `&i32`, значит `x: &i32`, одна ссылка. А `x + 1` для `&i32` работает без разыменований, потому что стандартная библиотека реализует арифметику и для ссылок на числа (§21.2.2). Результат — `i32`, поэтому `plus` собирается в `Vec<i32>`: `[2, 6, 3, 9]`.

Логика асимметрии: `map` **потребляет** элемент (он всё равно исчезает, преобразуясь в новый), поэтому может взять его по значению; `filter` элемент **пропускает дальше**, поэтому обязан ограничиться ссылкой. Та же двойная ссылка есть у `find` (в §21.2.2 — `**x > 5`), а у `position` и `map` — одинарная.

**Ответ:** первую ссылку добавляет `iter()` (элементы приходят как `&i32` — итератор ничего не забирает у коллекции), вторую — сам `filter`: его предикат по сигнатуре получает `&Self::Item`, чтобы не иметь возможности забрать элемент, который надо пропустить дальше; итого `&&i32`, а литерал `2` — не ссылка, отсюда E0308 `expected &&_, found integer`. Две починки: `filter(|x| **x > 2)` (снять ссылки в теле) и `filter(|&&x| x > 2)` (снять их образцом в заголовке); обе дают `[5, 8]` на `vec![1, 5, 2, 8]`, различаются только местом разыменования — образец предпочтительнее стилистически, но требует `Copy`-элементов. У `map(|x| x + 1)` проблемы нет, потому что `map` передаёт замыканию **элемент**, а не ссылку на него (одна ссылка, `&i32`), а арифметика для `&i32` реализована; результат — `[2, 6, 3, 9]`.

Тесты дали рефакторингу критерий успеха, не зависящий от внимательности автора: они фиксируют поведение (включая края — пустой текст, пунктуацию, текст паники) и превращают вопрос «ничего не сломалось?» в прогон длиной в секунду; правильный режим — менять по одной функции и прогонять тесты после каждой правки.

### Г21.Ч2.З9

**Условие.** Обратный отсчёт. Реализуйте `Countdown` — итератор, выдающий `from, from-1, ..., 1` и затем `None` (`Countdown::new(3)` → 3, 2, 1). Оформите cargo-пакетом; тестами покройте: сбор в вектор, `new(0)` — пустая последовательность, ручной протокол (`next` четырежды для `new(2)` — включая поведение после конца), работу с адаптерами (`sum`, `chain` с диапазоном, `enumerate`). **Решение.** Файл `p2/countdown/src/lib.rs`:

```rust
// Библиотека countdown: обратный отсчёт как собственный итератор (Г21.Ч2.З9).

pub struct Countdown {
    left: u32,
}

impl Countdown {
    pub fn new(from: u32) -> Countdown {
        Countdown { left: from }
    }
}

impl Iterator for Countdown {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.left == 0 {
            None
        } else {
            let out = self.left;
            self.left -= 1;
            Some(out)
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn collects_in_order() {
        let v: Vec<u32> = Countdown::new(3).collect();
        assert_eq!(v, vec![3, 2, 1]);
    }

    #[test]
    fn zero_gives_empty_sequence() {
        let v: Vec<u32> = Countdown::new(0).collect();
        assert!(v.is_empty());
    }

    #[test]
    fn manual_protocol() {
        let mut c = Countdown::new(2);
        assert_eq!(c.next(), Some(2));
        assert_eq!(c.next(), Some(1));
        assert_eq!(c.next(), None);
        assert_eq!(c.next(), None); // после конца — снова None
    }

    #[test]
    fn works_with_adaptors() {
        assert_eq!(Countdown::new(4).sum::<u32>(), 10);

        let chained: Vec<u32> = Countdown::new(2).chain(7..=8).collect();
        assert_eq!(chained, vec![2, 1, 7, 8]);

        let numbered: Vec<(usize, u32)> = Countdown::new(3).enumerate().collect();
        assert_eq!(numbered, vec![(0, 3), (1, 2), (2, 1)]);
    }
}
```

Разбор реализации:

- **Состояние** — одно поле `left`: сколько ещё осталось выдать. Оно же и есть очередное выдаваемое число, поэтому отдельного счётчика не нужно.
- **`type Item = u32`** — ассоциированный тип: «элементы этой последовательности — `u32`» (§21.2.1).
- **Порядок в `next`** важен так же, как в `Fib` из §21.2.3: сначала сохранить выдаваемое (`let out = self.left;`), потом изменить состояние. Напишите наоборот — и отсчёт начнётся с `from - 1`; тест `collects_in_order` поймает это первым же сравнением.
- **Условие остановки** — `self.left == 0`. Именно поэтому `new(0)` даёт пустую последовательность, а не панику вычитания: до `-= 1` дело не доходит. С `u32` это не мелочь: `0u32 - 1` — переполнение, в отладочной сборке паника (§14.2.3).
- **Поведение после конца.** Наш итератор «залипает» на `None`: `left` уже 0 и меняться не будет. Общий контракт `Iterator` этого не требует (§21.2.1), но раз тест `manual_protocol` спрашивает про четвёртый вызов — мы это свойство фиксируем как часть контракта **нашего** типа.
- **Адаптеры достаются бесплатно.** Мы не писали ни `sum`, ни `chain`, ни `enumerate` — это методы трейта с реализацией по умолчанию поверх `next` (§19.2.1, §21.2.3). `sum::<u32>()` — турбо-рыба вместо аннотации переменной (§14.2.2), потому что результат сразу уходит в `assert_eq!`. `chain(7..=8)` пришивает диапазон: `[2, 1, 7, 8]` — сначала весь наш итератор, потом весь второй. `enumerate` нумерует с нуля: `(0, 3), (1, 2), (2, 1)` — номер и значение движутся навстречу друг другу, что хорошо видно в отсчёте.
- **`for` тоже работает** без единой дополнительной строки: стандартная библиотека реализует `IntoIterator` для всякого итератора (§21.2.3).

### Г21.Ч2.З10

**Условие.** Топ слов. Напишите библиотечную функцию `top_words(text: &str, k: usize) -> Vec<(String, usize)>`: k самых частых слов текста, по убыванию частоты, при равенстве — по алфавиту. Конвейер: `split_whitespace` → счётчик частот в `HashMap` (`entry`/`or_insert`, §17.2.3; ключи — `String::from(word)`, §17.2.2) → `into_iter().collect()` в вектор пар → `sort_by` с двухключевым компаратором (§21.1.3) → `take(k)` → `collect`. Тесты: выбор самых частых, разрешение ничьей по алфавиту, `k` больше словаря, пустой текст. Все зелёные; приведите строку `test result`.

**Решение.** Файл `p2/topwords/src/lib.rs`:

```rust
// Библиотека topwords: k самых частых слов текста (Г21.Ч2.З10).

use std::cmp::Ordering;
use std::collections::HashMap;

/// k самых частых слов: по убыванию частоты, при равенстве — по алфавиту.
/// Если разных слов меньше k, возвращает все.
pub fn top_words(text: &str, k: usize) -> Vec<(String, usize)> {
    // 1. Частоты: entry/or_insert (§17.2.3), ключи — собственные String (§17.2.2).
    let mut freq: HashMap<String, usize> = HashMap::new();
    for word in text.split_whitespace() {
        *freq.entry(String::from(word)).or_insert(0) += 1;
    }

    // 2. Таблица отдаёт владеющие пары — собираем их в вектор.
    let mut pairs: Vec<(String, usize)> = freq.into_iter().collect();

    // 3. Двухключевой порядок: частота по убыванию, при равенстве — слово.
    pairs.sort_by(|a, b| match b.1.cmp(&a.1) {
        Ordering::Equal => a.0.cmp(&b.0),
        other => other,
    });

    // 4. Первые k — и обратно в вектор.
    pairs.into_iter().take(k).collect()
}

#[cfg(test)]
mod tests {
    use super::*;

    const TEXT: &str = "то ли дождик то ли снег то ли будет то ли нет";

    #[test]
    fn picks_most_frequent() {
        let top = top_words(TEXT, 2);
        assert_eq!(top, vec![(String::from("ли"), 4), (String::from("то"), 4)]);
    }

    #[test]
    fn ties_are_resolved_alphabetically() {
        let top = top_words(TEXT, 6);
        let words: Vec<&str> = top.iter().map(|(w, _)| w.as_str()).collect();
        assert_eq!(words, vec!["ли", "то", "будет", "дождик", "нет", "снег"]);
    }

    #[test]
    fn k_larger_than_vocabulary() {
        let top = top_words("раз два раз", 10);
        assert_eq!(
            top,
            vec![(String::from("раз"), 2), (String::from("два"), 1)]
        );
    }

    #[test]
    fn empty_text_gives_empty_result() {
        assert!(top_words("", 3).is_empty());
    }
}
```

Разбор конвейера по шагам.

**Шаг 1 — частоты.** `*freq.entry(String::from(word)).or_insert(0) += 1` — счётчик из §17.2.3 дословно. Почему ключ `String`, а не `&str`: функция возвращает `Vec<(String, usize)>`, то есть **владеющие** пары; если бы ключами были срезы `&str`, результат оказался бы привязан ко времени жизни аргумента `text` (§19.3.1) и сигнатура потребовала бы явных времён жизни. `String::from(word)` копирует слово в собственный буфер — цена за независимость результата от источника.

**Шаг 2 — таблица в вектор.** `freq.into_iter()` съедает таблицу и выдаёт владеющие пары `(String, usize)` (§21.2.1), `collect` складывает их в `Vec`. Порядок обхода `HashMap` не определён (§17.2.1) — потому шаг 3 и обязателен: без него результат менялся бы от запуска к запуску.

**Шаг 3 — порядок.** Компаратор из Г21.Ч1.З9: `b.1.cmp(&a.1)` (частота по убыванию — аргументы переставлены), рукав `Equal` передаёт решение слову (`a.0.cmp(&b.0)`, по возрастанию), рукав `other` пропускает готовый ответ. Здесь `&b.0` со ссылкой — в отличие от Г21.Ч1.З9, где элементы были `&str`: у `String` метод `cmp` принимает `&String`.

**Шаг 4 — срез верхушки.** `into_iter().take(k)` — «не более k» без всякой проверки длины: `take` молча заканчивается, когда кончается сам итератор (R9). Это и обслуживает случай «k больше словаря» — тест `k_larger_than_vocabulary` просит 10 при двух словах и получает два. Обход по значению здесь именно тот случай, о котором говорилось в Г21.Ч2.З5: вектор разбирается насовсем, строки переезжают в результат без клонирования.

**О тестах.** `picks_most_frequent` фиксирует и частоты, и порядок ничьей: `ли` и `то` встречаются по 4 раза, `ли` раньше по алфавиту. `ties_are_resolved_alphabetically` проверяет весь словарь: после двух четвёрок идут четыре слова с частотой 1 — `будет`, `дождик`, `нет`, `снег` — строго по алфавиту (сравнение `String` лексикографическое по байтам UTF-8, и для строчной кириллицы байтовый порядок совпадает с алфавитным, §17.1.4). Проверка сделана по именам слов: сравнивать полные пары было бы шумно, а `map(|(w, _)| w.as_str())` вытаскивает ровно то, что проверяется. `empty_text_gives_empty_result` — край: `split_whitespace` по пустой строке не даёт ни одного слова, таблица пуста, результат пуст (и `take(3)` от пустого итератора не создаёт проблем).

**Ответ:** функция — четыре шага (частоты через `entry`/`or_insert` с ключами-`String`, `into_iter().collect()` в вектор пар, `sort_by` с двухключевым компаратором, `into_iter().take(k).collect()`), четыре теста зелёные:

Ключевые решения: ключи-`String`, чтобы результат не зависел от времени жизни аргумента; сортировка обязательна, потому что порядок обхода `HashMap` не определён; `take(k)` сам обслуживает случай «k больше словаря».

**Вариант 2 (два стабильных прохода вместо компаратора).** `sort` и `sort_by` **стабильны** (R9): элементы, равные с точки зрения компаратора, сохраняют взаимный порядок. Значит двухключевой порядок можно навести двумя простыми сортировками — сначала по **второстепенному** ключу, потом по главному (приём, проверенный в разборе Г21.Ч1.З9).
```rust
// Библиотека topwords, вариант 2: два стабильных прохода (Г21.Ч2.З10).

use std::collections::HashMap;

/// k самых частых слов: по убыванию частоты, при равенстве — по алфавиту.
/// Если разных слов меньше k, возвращает все.
pub fn top_words(text: &str, k: usize) -> Vec<(String, usize)> {
    let mut freq: HashMap<String, usize> = HashMap::new();
    for word in text.split_whitespace() {
        *freq.entry(String::from(word)).or_insert(0) += 1;
    }

    let mut pairs: Vec<(String, usize)> = freq.into_iter().collect();

    // Проход 1 — второстепенный ключ: слово по алфавиту.
    pairs.sort();
    // Проход 2 — главный ключ: частота по убыванию. sort стабилен,
    // поэтому внутри равных частот алфавитный порядок сохранится.
    pairs.sort_by(|a, b| b.1.cmp(&a.1));

    pairs.into_iter().take(k).collect()
}
```

Второй проход смотрит только на частоту — и оставляет ничьи в алфавитном порядке, наведённом первым.

*Сравнение.* Компаратор описывает порядок **целиком, в одном месте**: читая его, видно оба ключа и оба направления; работает он за один проход и не зависит от свойств алгоритма сортировки. Двухпроходный вариант короче в каждой отдельной строке и хорош, когда ключей много или они добавляются по ходу (каждый новый ключ — ещё одна строка, а не ещё один рукав `match`), но платит вторым проходом и — главное — **молча полагается на стабильность**: замените `sort_by` на `sort_unstable_by` (её иногда советуют «для скорости»), и ничьи начнут разрешаться произвольно, причём не на всех данных и не при каждом запуске. Поэтому в библиотечном коде я оставил бы компаратор, а двухпроходный приём держал бы для разовых скриптов и для случаев, где ключи вычисляются в разных местах программы. Если выбираете его — комментарий про стабильность обязателен, иначе следующий читатель «оптимизирует» сортировку и сломает контракт.

## Итог главы

Двадцать заданий главы 21 закрывают полный переход к идиоматическому Rust — от «функции-значения с рюкзаком» до конвейеров, заменивших ручные циклы тома I.

**Часть 21.1** прошла путь от синтаксиса к контракту: четыре формы записи и границы вывода типов (З1, З4), ленивость `unwrap_or_else` (З2), три режима захвата и их отражение в трейтах `Fn`/`FnMut`/`FnOnce` (З3, З6), интервал жизни изменяющего займа замыкания (З5), совместимость «многократный вызов» с содержимым рюкзака (З7), возврат замыкания наружу через `impl Fn` + `move` (З8), сортировка с ключом и компаратором (З9) и приём замыканий обобщённой функцией (З10). Сквозная нить — та же, что в §15.2.2: замыкание не привилегированная конструкция, а обычное значение, к которому применяются обычные правила владения.

**Часть 21.2** собрала конвейер: протокол `next` и точные типы элементов (З1, З7), перевод трёх типовых циклов в цепочки (З2, З3), ленивость и цена её непонимания (З4), десахаризация `for` и выбор формы обхода по владению (З5), `fold` как универсал и его отличие от специализированных потребителей (З6), рефакторинг живой библиотеки под защитой неизменённых тестов (З8), собственный итератор и альтернатива в виде `-> impl Iterator` (З9), полный конвейер «текст → частоты → порядок → верхушка» (З10).

Шесть заданий получили вторые варианты решения: проверка трейтов статическими утверждениями вместо пробников (Ч1.З3), состояние в структуре вместо рюкзака (Ч1.З8), ключ-кортеж вместо компаратора (Ч1.З9), рекурсия вместо цикла (Ч1.З10), `-> impl Iterator` вместо своего типа (Ч2.З9), два стабильных прохода вместо двухключевого компаратора (Ч2.З10).

Три факта, которые стоит унести из прогонов этой главы:

1. **Вывод типа замыкания не «останавливается» на литерале без суффикса** — срабатывает умолчание `i32` (§14.2.2). Аннотация обязательна лишь тогда, когда выводить не из чего вовсе (E0284) или когда нужный тип отличается от умолчания (замечание к З1: формулировка §21.1.1 в этом месте неточна).
2. **Стабильность `sort`/`sort_by`** — не деталь реализации, а обещание стандартной библиотеки, на котором держится приём «сначала второстепенный ключ, потом главный» (Ч1.З9, Ч2.З10).
3. **Ошибка выбирается контрактом приёмника, а не «неправильностью» замыкания**: одно и то же замыкание даёт E0596 под `Fn`, работает под `FnMut` и проходит под `FnOnce`; а «несовпадение с `Fn()`» вообще может оказаться не про трейт, а про тип результата (E0308 в Ч1.З3).
