## Часть 11.1. Препроцессор

### Г11.Ч1.З1

**Условие.** Напишите программу с тремя макросами-константами: `MAX_ITEMS` (размер массива), `UNIT_PRICE` (цена, `double`), `LABEL` (строка-название). Программа заполняет массив стоимостями `(i + 1) * UNIT_PRICE`, суммирует их и печатает строку вида `cart: 4 items, total = 25.00` (для `MAX_ITEMS` 4 и `UNIT_PRICE` 2.5). Пересоберите с другими значениями констант, не меняя ничего, кроме строк `#define`. Затем прогоните `gcc -E -P` и найдите в выводе строку заполнения массива — убедитесь, что имени `UNIT_PRICE` в ней уже нет (ожидается `items[i] = (i + 1) * 2.5;`).

**Решение.** Три макроса — три разных применения подстановки, и каждый работает в своём контексте.

1. `MAX_ITEMS` попадает сразу в три места: размер массива, границу цикла и аргумент `printf`. Размер массива — контекст, требующий **константного выражения**, и макрос его даёт: подстановка происходит до компиляции. Обычная `const int` здесь не подошла бы (§11.1.2).
2. `UNIT_PRICE` — вещественная константа; её тип возникнет уже после подстановки, из самого литерала `2.5`.
3. `LABEL` — строковый литерал; подставляется в `printf` как есть.

Ни `=`, ни `;` в директивах нет — всё, что стоит после имени, стало бы частью текста замены (§11.1.2, примеры 2–3).

```c
#include <stdio.h>

#define MAX_ITEMS  4
#define UNIT_PRICE 2.5
#define LABEL      "cart"

int main(void)
{
    double items[MAX_ITEMS];
    double total = 0.0;

    for (int i = 0; i < MAX_ITEMS; i++) {
        items[i] = (i + 1) * UNIT_PRICE;   /* стоимость позиции i */
        total += items[i];
    }
    printf("%s: %d items, total = %.2f\n", LABEL, MAX_ITEMS, total);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra cart.c -o cart.exe
./cart.exe
```

```
cart: 4 items, total = 25.00
```

Сумма `(1 + 2 + 3 + 4) * 2.5 = 25.00` — как и обещано условием.

**Пересборка с другими константами.** Меняем ровно три строки — `MAX_ITEMS` на 6, `UNIT_PRICE` на 1.25, `LABEL` на `"box"` (для воспроизводимости этот вариант сохранён отдельным файлом `cart2.c`); тело `main` не тронуто ни одним символом:

```
gcc -std=c17 -Wall -Wextra cart2.c -o cart2.exe
./cart2.exe
```

```
box: 6 items, total = 26.25
```

`(1 + 2 + 3 + 4 + 5 + 6) * 1.25 = 26.25`. Массив, цикл и печать перестроились сами — в этом и смысл именованной константы: число живёт в одном месте.

**Что видит компилятор.** Прогоняем препроцессор. Первый сюрприз: `-E -P` печатает не только наш `main`, но и весь вклеенный `stdio.h` — на эталонной машине это 738 строк, наши десять из них в самом конце. Поэтому смотрим хвост:

```
gcc -std=c17 -E -P cart.c | tail -n 14
```

```
  __attribute__ ((__dllimport__)) int __attribute__((__cdecl__)) _swscanf_l(const wchar_t *_Src,const wchar_t *_Format,_locale_t _Locale,...);
  __attribute__ ((__dllimport__)) int __attribute__((__cdecl__)) _snwscanf_l(const wchar_t *_Src,size_t _MaxCount,const wchar_t *_Format,_locale_t _Locale,...);
  __attribute__ ((__dllimport__)) int __attribute__((__cdecl__)) _wscanf_l(const wchar_t *_Format,_locale_t _Locale,...);
int main(void)
{
    double items[4];
    double total = 0.0;
    for (int i = 0; i < 4; i++) {
        items[i] = (i + 1) * 2.5;
        total += items[i];
    }
    printf("%s: %d items, total = %.2f\n", "cart", 4, total);
    return 0;
}
```

Прицельно — искомая строка:

```
gcc -std=c17 -E -P cart.c | grep "items\[i\]"
```

```
        items[i] = (i + 1) * 2.5;
        total += items[i];
```

Ожидание условия подтвердилось дословно: имени `UNIT_PRICE` в тексте нет, на его месте — токен `2.5`. То же случилось со всеми тремя макросами: `double items[4]`, `i < 4`, `"cart"`, `4`. Компилятор никогда не видел ни одного из наших имён — он получил числа и строку.

**⛔ Типичная неверная попытка: «та же цена, но дробью».** Соблазн записать цену «точнее» — `5/2` вместо `2.5`:

```c
#define UNIT_PRICE 5/2      /* та же цена 2.5 -- но текстом */
```

```
gcc -std=c17 -Wall -Wextra cart_bad.c -o cart_bad.exe
./cart_bad.exe
```

```
cart: 4 items, total = 24.00
```

Ни ошибки, ни предупреждения — и неверный итог. Разгадка в препроцессированном тексте:

```
gcc -std=c17 -E -P cart_bad.c | grep "items\[i\]"
```

```
        items[i] = (i + 1) * 5/2;
        total += items[i];
```

Подставились **буквы** `5/2`, а не число: выражение `(i + 1) * 5 / 2` целочисленное, и каждая стоимость округляется вниз (`2, 5, 7, 10` вместо `2.5, 5.0, 7.5, 10.0`). Правило-профилактика: в теле макроса-константы пишите завершённый литерал того типа, который вам нужен (`2.5`, а если делить — то `5.0/2`), а составные выражения ещё и заключайте в скобки — по тем же причинам, что и в §11.1.3.

**Ответ:** программа с макросами `#define MAX_ITEMS 4`, `#define UNIT_PRICE 2.5`, `#define LABEL "cart"` печатает `cart: 4 items, total = 25.00`; после правки только трёх строк `#define` (6, 1.25, `"box"`) — `box: 6 items, total = 26.25`, тело `main` при этом не меняется вовсе. В выводе `gcc -E -P` строка заполнения массива выглядит как `items[i] = (i + 1) * 2.5;` — имени `UNIT_PRICE` в ней уже нет: макрос исчез вместе с директивой, компилятор получает готовые токены `4`, `2.5`, `"cart"`. Заодно видно, что `-E -P` печатает и всё содержимое `stdio.h` (738 строк на эталонной машине), поэтому свой код удобнее искать `grep`-ом или в хвосте вывода.

**Вариант 2 (значения задаёт команда сборки).** Если конфигурацию хочется менять, не трогая исходник вообще, макросы объявляют «со значением по умолчанию» — под `#ifndef` (§11.1.4), а нужные значения передают ключом `-D`:

```c
#include <stdio.h>

#ifndef MAX_ITEMS
#define MAX_ITEMS  4
#endif
#ifndef UNIT_PRICE
#define UNIT_PRICE 2.5
#endif
#ifndef LABEL
#define LABEL      "cart"
#endif

int main(void)
{
    double items[MAX_ITEMS];
    double total = 0.0;

    for (int i = 0; i < MAX_ITEMS; i++) {
        items[i] = (i + 1) * UNIT_PRICE;
        total += items[i];
    }
    printf("%s: %d items, total = %.2f\n", LABEL, MAX_ITEMS, total);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra cart_cfg.c -o cart_cfg.exe
./cart_cfg.exe
gcc -std=c17 -Wall -Wextra -DMAX_ITEMS=6 -DUNIT_PRICE=1.25 -DLABEL="\"box\"" cart_cfg.c -o cart_cfg2.exe
./cart_cfg2.exe
```

```
cart: 4 items, total = 25.00
box: 6 items, total = 26.25
```

(Кавычки вокруг `box` экранированы дважды: одни нужны C, вторые защищают их от оболочки.)

*Сравнение.* Первый вариант проще и честнее для константы, которая по смыслу принадлежит программе: значение видно в исходнике, в истории правок остаётся след, а `grep` по проекту находит его сразу. Второй вариант — для того, что по смыслу принадлежит **сборке**: одна и та же программа собирается в нескольких конфигурациях без единой правки файла, а `#ifndef` гарантирует разумное поведение, если ключ забыли. Плата за гибкость — то, что по исходнику больше нельзя сказать, с какими константами собран конкретный бинарник (лечится печатью конфигурации при старте — или, как в Г11.Ч1.З9, страховкой `#error`). Правило выбора: значения, от которых зависит смысл программы, — в исходник; значения, которыми управляет тот, кто собирает, — в командную строку.

### Г11.Ч1.З2

**Условие.** Воспроизведите пример 1 §11.1.1 (`answer.h` + `small.c`): прогоните `gcc -E -P small.c` и объясните происхождение каждой строки вывода (что и откуда вклеено, что и чем заменено). Затем возьмите программу с единственным `#include <stdio.h>` и посчитайте строки препроцессированного текста (`gcc -E hello.c | wc -l` в bash-подобной оболочке или подсчёт строк любым способом). Сравните с числом строк исходника и объясните разницу одним предложением.

**Решение.** Оба файла — из §11.1.1, дословно:

```c
/* answer.h */
#define ANSWER 42

int twice(int x);
```

```c
/* small.c */
#include "answer.h"

int twice(int x) { return 2 * x; }

int main(void) {
    return twice(ANSWER) - 84; /* 0 */
}
```

```
gcc -std=c17 -E -P small.c
```

```
int twice(int x);
int twice(int x) { return 2 * x; }
int main(void) {
    return twice(42) - 84;
}
```

**Происхождение каждой строки.**

| Строка вывода | Откуда взялась |
|---|---|
| `int twice(int x);` | Вклеена из `answer.h` на место директивы `#include "answer.h"`. Сама директива исчезла, как и строка `#define ANSWER 42` — директивы в единицу трансляции не попадают. |
| `int twice(int x) { return 2 * x; }` | Строка 3 самого `small.c`, перенесена без изменений: ни одного макроса в ней нет. |
| `int main(void) {` | Строка 5 `small.c`, без изменений. |
| `    return twice(42) - 84;` | Строка 6 `small.c`, в которой имя `ANSWER` заменено текстом замены `42`. Комментарий `/* 0 */` исчез: комментарии удаляются ещё до макрозамены (фаза 3, §11.1.1). |
| `}` | Закрывающая скобка `main`. |

Итого преобразований ровно три: вклейка файла, замена макроса, удаление комментария; плюс пропали пустые строки — их убрал ключ `-P` вместе со служебными маркерами. Маркеры видно без `-P`:

```
gcc -std=c17 -E small.c | head -8
```

```
# 0 "small.c"
# 0 "<built-in>"
# 0 "<command-line>"
# 1 "small.c"
# 1 "answer.h" 1
```

Пятая строка — «дальше идёт строка 1 файла `answer.h`»: по этим пометкам компилятор сообщает об ошибках в терминах ваших файлов (§11.1.1, пример 3).

**Сколько строк вклеивает `<stdio.h>`.** Файл `hello.c` — шесть строк:

```c
#include <stdio.h>

int main(void) {
    puts("hi");
    return 0;
}
```

```
gcc -std=c17 -E hello.c | wc -l
wc -l hello.c
gcc -std=c17 -E -P hello.c | wc -l
```

```
1057
6 hello.c
731
```

Шесть строк исходника превратились в 1057 строк текста (731 без служебных маркеров — их в выводе 90 штук, они и составляют разницу).

Числа зависят от реализации стандартной библиотеки, а не от языка: тот же `hello.c` на Linux-контуре (gcc 13.3, glibc) дал вдвое меньше —

```
gcc -std=c17 -E hello.c | wc -l : 547
gcc -std=c17 -E -P hello.c | wc -l : 220
```

— заголовки MinGW-w64 объявляют, помимо стандартных функций, ещё и семейства `_l`-вариантов Microsoft CRT. Вывод `-E -P small.c` при этом на обеих платформах совпал до символа: там нет ничего, кроме нашего текста.

**Ответ:** `gcc -E -P small.c` печатает четыре строки: `int twice(int x);` — это прототип, вклеенный из `answer.h` вместо директивы `#include`; затем три строки самого `small.c` (определение `twice`, заголовок `main` и `return twice(42) - 84;`), в последней из которых имя `ANSWER` заменено на `42`, а комментарий удалён. Директивы `#include` и `#define` в вывод не попадают вовсе — их работа и есть эти изменения. Для `hello.c` из шести строк препроцессор выдал **1057** строк (731 без маркеров строк; на Linux — 547 и 220): разница — это целиком вклеенный `stdio.h` со всеми объявлениями функций, типами (`FILE`), макросами (`NULL`, `EOF`) и заголовками, которые он включает сам, — то есть цена одной строки `#include <stdio.h>`, и одновременно ответ на вопрос, откуда компилятор «знает» сигнатуру `printf`.

### Г11.Ч1.З3

**Условие.** Напишите программу, печатающую `__FILE__`, `__LINE__` (из двух разных мест — значения должны отличаться), `__DATE__`, `__TIME__` и `__STDC_VERSION__`. Соберите с `-std=c17`. Какое значение `__STDC_VERSION__` напечаталось и почему (что кодируют цифры)? Каким оно станет по стандарту C23 (см. §11.1.4)?

**Решение.** Все пять — предопределённые макросы (C5 §6.10.10): три строковых (`__FILE__`, `__DATE__`, `__TIME__`), два целочисленных (`__LINE__`, `__STDC_VERSION__`). Формат печати выбирается по типу текста замены: `%s` для строк, `%d` для номера строки и `%ld` для `__STDC_VERSION__` — у неё суффикс `L`, то есть тип `long`.

```c
#include <stdio.h>

int main(void)
{
    printf("file: %s\n", __FILE__);
    printf("line here: %d\n", __LINE__);
    printf("line there: %d\n", __LINE__);
    printf("compiled on: %s at %s\n", __DATE__, __TIME__);
    printf("C standard: %ld\n", __STDC_VERSION__);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra predef.c -o predef.exe
./predef.exe
```

```
file: predef.c
line here: 6
line there: 7
compiled on: Jul 26 2026 at 19:19:23
C standard: 201710
```

(Дата и время — с эталонной машины, у вас будут свои.) Два `__LINE__` дали `6` и `7` — соседние строки файла: макрос раскрывается **в месте использования**, и его значение — номер той строки, где он написан. Это и делает его пригодным для диагностики (задание Г11.Ч1.З8).

**Что кодируют цифры.** `201710` — это `yyyymm`: год `2017` и месяц `10`, октябрь. Так стандарт помечает свою редакцию: C99 — `199901L`, C11 — `201112L`, C17 — `201710L`. Суффикс `L` в печати не виден, но он есть в тексте замены и задаёт тип `long`. Число называет не «версию компилятора», а **редакцию стандарта, по правилам которой ведётся трансляция**, — то есть прямое следствие ключа `-std=`.

Проверка последнего утверждения — та же программа, собранная по C23:

```
gcc -std=c23 -Wall -Wextra predef.c -o predef23.exe && ./predef23.exe
```

```
file: predef.c
line here: 6
line there: 7
compiled on: Jul 26 2026 at 19:19:23
C standard: 202311
```

Ни одного символа в исходнике не изменилось — изменился только ключ сборки.

**Ответ:** программа печатает `file: predef.c`, `line here: 6` и `line there: 7` (разные номера — `__LINE__` подставляется в месте использования), дату и время компиляции (`compiled on: Jul 26 2026 at 19:19:23` на эталонной машине) и `C standard: 201710`. Цифры `__STDC_VERSION__` кодируют редакцию стандарта в формате `yyyymm` плюс суффикс `L` (тип `long`): `201710L` — стандарт C17 (октябрь 2017), выбранный ключом `-std=c17`. По C23 значение равно `202311L` (ноябрь 2023) — проверено пересборкой той же программы с `-std=c23`: печатается `202311`.

### Г11.Ч1.З4

**Условие.** *(понимание)* Даны макросы `#define TWICE_BAD(x) 2*x` и `#define TWICE(x) (2*(x))`. **Не компилируя**, выпишите текст подстановки и предскажите значение каждого выражения: `TWICE_BAD(3+4)`, `TWICE(3+4)`, `10-TWICE_BAD(2)`, `100/TWICE_BAD(5)`, `100/TWICE(5)` (ожидается 10, 14, 6, 250, 10). Затем проверьте программой. Объясните: какое из правил скобок §11.1.3 нарушает `TWICE_BAD`; почему `10-TWICE_BAD(2)` тем не менее дало «правильные» 6 и чем такие случайные совпадения опасны.

**Решение.** Подстановка — чисто текстовая: на место `x` встаёт **текст** аргумента, после чего получившееся выражение читает компилятор по обычным правилам приоритетов.

| Выражение | Текст после подстановки | Значение | Почему |
|---|---|---|---|
| `TWICE_BAD(3+4)` | `2*3+4` | **10** | `*` приоритетнее `+`: сначала `2*3`, потом `+4`. |
| `TWICE(3+4)` | `(2*(3+4))` | **14** | Скобки вокруг параметра сохранили сумму целой. |
| `10-TWICE_BAD(2)` | `10-2*2` | **6** | `2*2` вычисляется первым, `10-4`. |
| `100/TWICE_BAD(5)` | `100/2*5` | **250** | `/` и `*` равноприоритетны и идут слева направо: `(100/2)*5`. |
| `100/TWICE(5)` | `100/(2*(5))` | **10** | Скобки вокруг тела удержали «удвоение» единым знаменателем. |

Проверка программой:

```c

#define TWICE_BAD(x) 2*x
#define TWICE(x)     (2*(x))

int main(void)
{

    printf("TWICE(3+4)       = %d\n", TWICE(3+4));
    printf("10-TWICE_BAD(2)  = %d\n", 10-TWICE_BAD(2));
    printf("100/TWICE_BAD(5) = %d\n", 100/TWICE_BAD(5));
    printf("100/TWICE(5)     = %d\n", 100/TWICE(5));

}
```

    printf("100/TWICE(5)     = %d\n", 100/(2*(5)));

**Какое правило нарушено.** Оба (§11.1.3): в `2*x` нет ни скобок вокруг **тела** макроса, ни скобок вокруг **параметра**. Каждое нарушение бьёт по-своему, и результаты это разделяют: `TWICE_BAD(3+4) = 10` — следствие голого параметра (аргумент-сумма разорвался приоритетом умножения); `100/TWICE_BAD(5) = 250` — следствие голого тела (внешнее деление вклинилось внутрь «удвоения»). Чтобы сломать первый случай, достаточно составного аргумента; чтобы сломать второй — достаточно, чтобы вокруг макроса стояла операция не ниже приоритетом.

**Почему `10-TWICE_BAD(2)` дало верные 6.** Аргумент здесь — одиночный токен `2`, разрывать в нём нечего; а снаружи стоит `-`, приоритет которого **ниже** умножения, поэтому `10-2*2` группируется именно так, как задумано: `10 - (2*2)`. Совпало всё: и простой аргумент, и слабая соседняя операция.

**Чем опасны такие совпадения.** Тем, что они делают ошибочный макрос «проверенным». Автор пишет `TWICE_BAD`, прогоняет на `10-TWICE_BAD(2)`, получает 6 и закрывает тему. Мина срабатывает позже и не у него: достаточно, чтобы кто-то передал составной аргумент (`TWICE_BAD(a+b)`) или поставил макрос под деление либо умножение (`100/TWICE_BAD(n)`) — и результат станет неверным **без единого предупреждения компилятора**, потому что с точки зрения C всё это законные выражения. Отсюда практическое правило: правильность макроса определяется не удачным тестом, а видом текста замены — и проверяется глазами по двум правилам скобок либо прогоном `gcc -E`.

**Ответ:** тексты подстановки и значения — `TWICE_BAD(3+4)` → `2*3+4` = **10**; `TWICE(3+4)` → `(2*(3+4))` = **14**; `10-TWICE_BAD(2)` → `10-2*2` = **6**; `100/TWICE_BAD(5)` → `100/2*5` = **250**; `100/TWICE(5)` → `100/(2*(5))` = **10**; прогон программы дал ровно эти числа. `TWICE_BAD` нарушает **оба** правила скобок §11.1.3 — нет скобок ни вокруг тела, ни вокруг параметра: первое проявляется в `100/TWICE_BAD(5)`, второе — в `TWICE_BAD(3+4)`. Выражение `10-TWICE_BAD(2)` дало правильные 6 случайно: аргумент — одиночный токен, разрывать нечего, а соседняя операция `-` слабее умножения, поэтому группировка совпала с задуманной. Опасность таких совпадений в том, что они создают ложную уверенность: макрос «протестирован», а ломается он позже, в чужом коде, при первом составном аргументе или первом делении — и молча, без диагностики компилятора.

### Г11.Ч1.З5

**Условие.** *(понимание)* Найдите ошибку в каждой директиве: (а) `#define SIZE = 8`; (б) `#define COUNT 10;`. Для каждой выпишите точный текст замены и результат подстановки в `int a[SIZE];` и `int n = COUNT;` соответственно. Почему вариант (б) в контексте `int n = COUNT;` компилируется без предупреждений и что при этом «заложено» в программу (в каком контексте мина взорвётся)? Сверьте свои ответы с примерами 2–3 §11.1.2, затем проверьте компилятором.

**Решение.** Общая причина обеих ошибок одна: `#define` — не присваивание и не инструкция. Всё, что стоит после имени макроса до конца строки, целиком становится текстом замены.

**(а) `#define SIZE = 8`.** Текст замены — `= 8` (знак равенства и восьмёрка). Подстановка в `int a[SIZE];` даёт `int a[= 8];` — синтаксический мусор: там, где грамматика ждёт выражение-размер, стоит знак операции.

Диагностика двухадресная, как в §11.1.2: `error` указывает на **директиву** (там настоящая ошибка), а `note: in expansion of macro` — на место использования. Убедиться в тексте замены можно и напрямую:

Компилятору не на что жаловаться: код синтаксически корректен и семантически безобиден. Предупреждать было бы не о чем — пустые инструкции пишут и намеренно.

**Что заложено.** В программе живёт макрос, текст замены которого содержит завершающий разделитель. Пока `COUNT` используют в позиции, где лишняя `;` законна (инициализация, отдельная инструкция), всё работает. Мина взрывается в любом контексте, где `;` недопустима: размер массива, аргумент функции, выражение в скобках, часть условия. Самый частый случай — тот же, что в (а):

```

    1 | #define COUNT 10;
      |                 ^

    5 |     int a[COUNT];
      |           ^~~~~
count_mine.c:6:5: error: 'a' undeclared (first use in this function)
    6 |     a[0] = 1;
      |     ^
```

Обратите внимание на вторую ошибку: `'a' undeclared`. Сломанное объявление массива утащило за собой всё, что от него зависит, — одна лишняя `;` в директиве породила каскад. И, что хуже всего, взорвётся она у того, кто первым напишет `int a[COUNT];`, — возможно, в другом файле и через полгода, а виновная строка будет выглядеть невинно.

**Ответ:** (а) `#define SIZE = 8` — текст замены `= 8`, подстановка даёт `int a[= 8];`, компилятор сообщает `error: expected expression before '=' token` с пометкой `in expansion of macro 'SIZE'`; лечится удалением знака `=`. Заложена при этом отложенная ошибка: макрос несёт в себе разделитель, поэтому в любом контексте, где `;` недопустима, он разваливает синтаксис — в `int a[COUNT];` GCC выдаёт `error: expected ']' before ';' token` и следом каскад `'a' undeclared`. Обе директивы иллюстрируют одно правило: в `#define` нет ни `=`, ни `;`, а ошибки в тексте замены компилятор находит не там, где они написаны, а там, где макрос использован.

### Г11.Ч1.З6

**Условие.** *(понимание)* Вернитесь к примеру 2 §11.1.3 (функция `next()` со счётчиком). Объясните каждое из четырёх чисел вывода: почему `SQUARE(next())` равен `2`, а вызовов — `2`; почему `MAX(next(), next())` равен `3` — числу, которого не было среди сравнивавшихся значений, — а вызовов — `3`. Что вернула бы обычная функция `int max2(int a, int b)` на тех же данных? Сформулируйте правило: какие аргументы делают макрос обязанным стать функцией.

**Решение.** К программе §11.1.3 добавлена третья проба — та же пара вызовов `next()`, но переданная обычной функции:

```c
#include <stdio.h>

#define SQUARE(x)  ((x) * (x))
#define MAX(a, b)  ((a) > (b) ? (a) : (b))

static int counter = 0;

int next(void) { return ++counter; }        /* каждый вызов -- новое число */

int max2(int a, int b) { return a > b ? a : b; }

int main(void)
{
    int sq = SQUARE(next());
    printf("SQUARE(next()) = %d, calls: %d\n", sq, counter);

    counter = 0;
    int m = MAX(next(), next());
    printf("MAX(next(), next()) = %d, calls: %d\n", m, counter);

    counter = 0;
    int f = max2(next(), next());
    printf("max2(next(), next()) = %d, calls: %d\n", f, counter);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra effects.c -o effects.exe
./effects.exe
```

```
SQUARE(next()) = 2, calls: 2
MAX(next(), next()) = 3, calls: 3
max2(next(), next()) = 2, calls: 2
```

Разбор проще всего вести по препроцессированному тексту — он показывает, что именно получил компилятор:

```
    int sq = ((next()) * (next()));
    int m = ((next()) > (next()) ? (next()) : (next()));
    int f = max2(next(), next());
```

**`SQUARE(next()) = 2` при двух вызовах.** Параметр `x` упомянут в теле макроса дважды, значит текст аргумента вставлен дважды: `((next()) * (next()))`. Это **два разных вызова** функции: первый вернул `1`, второй `2`, произведение `1 * 2 = 2`, счётчик дошёл до `2`. «Квадратом» результат не является ни для одного из этих чисел — перемножены разные значения.

**`MAX(next(), next()) = 3` при трёх вызовах.** Тело `((a) > (b) ? (a) : (b))` упоминает `a` дважды и `b` дважды, поэтому текст обоих аргументов вставлен по два раза. Но выполняются не все четыре вызова: условный оператор вычисляет условие, а затем **только одну** ветвь. Хронология:

1. вычисляется `(a)` в условии → `next()` → `1`;
2. вычисляется `(b)` в условии → `next()` → `2`;
3. условие `1 > 2` ложно, выбрана ветвь `: (b)` → ещё один `next()` → `3`.

Итого три вызова, результат — `3`. Число `3` не участвовало в сравнении вовсе: сравнивались `1` и `2`, а вернулось значение, полученное уже **после** сравнения. Максимум из `1` и `2` равен `2`; макрос вернул то, чего среди сравнивавшихся не было, — и это не «странность `MAX`», а прямое следствие того, что аргумент вставлен текстом и вычисляется в каждом упоминании заново.

**Что вернула бы функция.** `max2(next(), next())` вернула `2` при двух вызовах — как и должно быть. Аргументы функции вычисляются **до** входа в неё, ровно по одному разу каждый, и внутрь попадают уже значения `1` и `2`; какая из двух проб `next()` выполнится первой, стандарт не фиксирует (порядок вычисления аргументов не определён, C3 §4.6), но на результат `max2` это не влияет: множество аргументов в любом случае `{1, 2}`, максимум `2`. Это и есть содержательная разница: у функции число вычислений аргумента задано вызовом, у макроса — числом упоминаний параметра в теле.

**Правило.** Макрос обязан стать функцией, если аргумент может быть **выражением с побочным эффектом** — то есть таким, для которого «вычислить дважды» ≠ «вычислить один раз»:

- вызовы функций, меняющих состояние или читающих ввод (`next()`, `getchar()`, `rand()`);
- инкремент и декремент (`i++`, `--n`) — здесь ещё хуже: `SQUARE(i++)` разворачивается в `((i++) * (i++))`, два изменения одной переменной в одном выражении, то есть неопределённое поведение;
- присваивания внутри аргумента (`SQUARE(x = f())`);
- а также — по другой причине — дорогие вычисления: двойная подстановка удваивает работу молча.

Практически это правило применяют с двух сторон: тот, кто **пишет** макрос, обязан упоминать каждый параметр в теле не более раза (иначе — функция); тот, кто **вызывает** макрос, обязан передавать выражения без побочных эффектов. И, поскольку стандартная библиотека имеет право реализовать функцию макросом (например, `getc`, §11.1.3), второе правило распространяется и на вызовы библиотечных функций.

**Ответ:** `SQUARE(next())` равен `2` при двух вызовах, потому что параметр упомянут в теле дважды и текст `next()` вставлен дважды — `((next()) * (next()))`: перемножены **разные** значения `1` и `2`. `MAX(next(), next())` равен `3` при трёх вызовах, потому что условный оператор сначала вычислил оба аргумента в условии (`1` и `2`), а затем вычислил выбранную ветвь ещё раз — третий `next()` вернул `3`; сравнивались `1` и `2`, а вернулось число, полученное после сравнения. Обычная функция `max2(next(), next())` на тех же данных вернула `2` при двух вызовах: её аргументы вычисляются по одному разу до входа в тело (порядок между ними не определён, но на результат не влияет). Правило: если аргумент может содержать побочный эффект — вызов функции с состоянием, `++`/`--`, присваивание — или дорогое вычисление, задачу решает функция, а не макрос; макрос допустим лишь тогда, когда каждый параметр упомянут в теле ровно один раз либо аргументы заведомо «чистые».

### Г11.Ч1.З7

**Условие.** *(понимание)* Дан макрос `#define LOG_AND_COUNT(msg) puts(msg); log_count++` и фрагмент `if (verbose) LOG_AND_COUNT("saving");` при `verbose == 0`. Предскажите: что напечатается и чему будет равен `log_count` (проверено: сообщение не печатается, а счётчик равен 1 — объясните этот разнобой текстом подстановки). Какое предупреждение выдаёт GCC с `-Wall`? Перепишите макрос через `do { } while (0)` и покажите, что стало `log_count == 0`. Объясните, почему простые фигурные скобки — не решение (случай `if/else`).

**Решение.** Текст замены содержит **две** инструкции, разделённые точкой с запятой, а `if` без фигурных скобок управляет ровно **одной**. После подстановки

```c
if (verbose) puts("saving"); log_count++;
```

это читается так: `if (verbose) puts("saving");` — условная часть, и `log_count++;` — самостоятельная инструкция, выполняющаяся всегда. Отступ в исходнике ничего не значит: компилятор смотрит на грамматику, а не на форматирование.

```c
#include <stdio.h>

#define LOG_AND_COUNT(msg) puts(msg); log_count++

static int log_count = 0;

int main(void)
{
    int verbose = 0;
    if (verbose) LOG_AND_COUNT("saving");
    printf("log_count = %d\n", log_count);
    return 0;
}
```

...
    if (verbose) LOG_AND_COUNT("saving"); else puts("quiet");
```

⛔ Такая сборка падает:

```
gcc -std=c17 -Wall -Wextra log_braces.c -o log_braces.exe
```

```
log_braces.c: In function 'main':
log_braces.c:10:43: error: 'else' without a previous 'if'
   10 |     if (verbose) LOG_AND_COUNT("saving"); else puts("quiet");
      |                                           ^~~~
```

Раскрытие даёт `if (verbose) { ... }; else ...`: блок уже завершил условную часть `if`, следом идёт пустая инструкция `;`, и `else` остаётся без своего `if`. Вариант «писать вызов без `;`» не годится: макрос перестанет выглядеть как вызов функции, и об этом придётся помнить каждому пользователю.

**Лечение — `do { } while (0)`.** Эта форма одновременно является **одной** инструкцией (поэтому целиком уходит под `if`) и **требует** завершающей `;` (поэтому `if/else` не ломается):

```c
#include <stdio.h>

#define LOG_AND_COUNT(msg) do { puts(msg); log_count++; } while (0)

static int log_count = 0;

int main(void)
{
    int verbose = 0;
    if (verbose) LOG_AND_COUNT("saving"); else puts("quiet");
    printf("log_count = %d\n", log_count);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra log_good.c -o log_good.exe
./log_good.exe
```

```
quiet
log_count = 0
```

Ни предупреждений при сборке, ни расхождения при работе: обе инструкции макроса теперь под `if`, ветка `else` на месте, счётчик остался нулевым. Цикл, выполняющийся ровно один раз и с ложным условием продолжения, компилятор устраняет — в машинном коде остаётся только тело.

**Ответ:** при `verbose == 0` сообщение `saving` не печатается, а `log_count` равен **1**: подстановка даёт `if (verbose) puts("saving"); log_count++;`, где под `if` попала только первая инструкция, а инкремент стал самостоятельной инструкцией и выполняется всегда. GCC с `-Wall` предупреждает: `warning: macro expands to multiple statements [-Wmultistatement-macros]` и уточняет `note: some parts of macro expansion are not guarded by this 'if' clause`. Переписанный через `do { puts(msg); log_count++; } while (0)` макрос даёт `quiet` и `log_count = 0` — обе инструкции ушли под `if`. Простые фигурные скобки решением не являются: `if (...) { ... }; else ...` — после блока стоит точка с запятой, она завершает `if`, и компоновать `else` уже не с чем — сборка падает с `error: 'else' without a previous 'if'`; `do { } while (0)` — единственная форма, которая и объединяет инструкции в одну, и сохраняет обязательную `;` в месте вызова.

### Г11.Ч1.З8

**Условие.** *(прикладное)* Создайте заголовок `debug.h` (со стражем включения): при определённом `DEBUG` макрос `DBG(msg)` печатает в `stderr` строку вида `файл:строка: сообщение` (используйте `__FILE__` и `__LINE__`), при неопределённом — разворачивается в пустышку `((void)0)`. Напишите программу с вызовами `DBG` в `main` и хотя бы в одной другой функции; предъявите обе сборки: без `-DDEBUG` (диагностики нет) и с `-DDEBUG` (каждая строка диагностики указывает файл и номер строки **места вызова**). Объясните, почему такой `DBG` нельзя заменить функцией.

**Решение.** Заголовок собирает вместе три механизма главы: страж включения, условную компиляцию и предопределённые макросы. `#include <stdio.h>` стоит внутри заголовка сознательно: `DBG` пользуется `fprintf` и `stderr`, значит интерфейс без `<stdio.h>` нечитаем — по правилу «включай то, чем пользуешься» (§11.2.2) заголовок обязан подтянуть его сам.

```c
#ifndef DEBUG_H
#define DEBUG_H

#include <stdio.h>

#ifdef DEBUG
#define DBG(msg) fprintf(stderr, "%s:%d: %s\n", __FILE__, __LINE__, (msg))
#else
#define DBG(msg) ((void)0)
#endif

#endif /* DEBUG_H */
```

Пустышка `((void)0)` выбрана не случайно: это **выражение**, поэтому `DBG("x");` остаётся синтаксически правильной инструкцией и в «боевой» сборке; приведение к `void` гасит возможные предупреждения о неиспользуемом значении. Пустое тело (`#define DBG(msg)`) тоже собралось бы, но оставило бы висеть одинокие `;` в неожиданных местах — например, в `if (x) DBG("a"); else ...` ветка `if` стала бы пустой инструкцией и смысл кода изменился бы незаметно.

```c
#include <stdio.h>
#include "debug.h"

static int square(int x)
{
    DBG("square called");
    return x * x;
}

int main(void)
{
    DBG("start");
    printf("square(7) = %d\n", square(7));
    DBG("done");
    return 0;
}
```

```

Каждая строка указывает **место вызова**: `start` — строка 12 (`main`), `square called` — строка 6 (тело `square`), `done` — строка 14. **⛔ Почему не функция.** Попробуем сделать то же функцией — вынесем печать в модуль `dbg_fn.c`:

```

Все три строки указывают на одно и то же место — на строку 6 файла `dbg_fn.c`, где написан сам `fprintf`. Иначе и быть не может: `__FILE__` и `__LINE__` раскрываются там, где **написаны**, а написаны они внутри функции; функция получает только значения своих аргументов и понятия не имеет, откуда её позвали. Чтобы функция печатала место вызова, файл и строку пришлось бы передавать ей руками при каждом вызове (`dbg(__FILE__, __LINE__, "start")`) — то есть писать в каждой точке вызова ровно то, что макрос подставляет сам. Плюс второе, менее заметное преимущество макроса: в «боевой» сборке от `DBG` не остаётся ни вызова, ни аргументов, тогда как функцию пришлось бы либо оставлять (с проверкой флага при выполнении), либо всё равно прятать за макросом.

**Ответ:** `debug.h` под стражем `DEBUG_H` содержит `#include <stdio.h>` и две ветки условной компиляции: при определённом `DEBUG` — `#define DBG(msg) fprintf(stderr, "%s:%d: %s\n", __FILE__, __LINE__, (msg))`, иначе — `#define DBG(msg) ((void)0)`. Сборка без ключа печатает только `square(7) = 49`, а в препроцессированном тексте на месте вызовов стоят три `((void)0);` — диагностики в программе нет физически. Сборка с `-DDEBUG` даёт в `stderr` три строки — `prog.c:12: start`, `prog.c:6: square called`, `prog.c:14: done`, — и каждая называет файл и строку **места вызова**. Функцией такой `DBG` заменить нельзя: `__FILE__` и `__LINE__` раскрываются там, где написаны, поэтому функция-аналог печатает собственные координаты — проверено, все три строки вышли как `dbg_fn.c:6`; передать место вызова функции можно только вручную в каждой точке, что и делает за вас макрос.

**Вариант 2 (`do { } while (0)` в обеих ветках).** Форма из задания — выражение, и в `if/else` она безопасна. Но стоит захотеть в отладочной ветке две инструкции (например, ещё и `fflush(stderr)`), как выражение перестанет годиться, — а привычка оформлять макрос-инструкцию идиомой Г11.Ч1.З7 избавляет от этого раз и навсегда:

```c

#define DEBUG2_H

#define DBG(msg) do { fprintf(stderr, "%s:%d: %s\n", __FILE__, __LINE__, (msg)); } while (0)
#else
#define DBG(msg) do { } while (0)
#endif

#endif /* DEBUG2_H */
```

}
```

Вариант с `do { } while (0)` жертвует этой возможностью (макрос становится строго инструкцией), но получает устойчивость к росту: в отладочную ветку можно добавить сколько угодно инструкций, не думая о том, где макрос вызывается, и обе ветки останутся одной инструкцией, требующей `;`. Практическое правило: если макрос по смыслу «действие» (лог, проверка, освобождение ресурса) — сразу `do { } while (0)`; если по смыслу «значение» — тогда выражение, и тогда за многооператорностью придётся следить самому.

### Г11.Ч1.З9

**Условие.** *(прикладное)* «Уровни журнала»: программа суммирует массив чисел. Макрос `LOG_LEVEL` по умолчанию равен 1 (задайте через `#ifndef`/`#define`); при `LOG_LEVEL >= 1` печатается итог, при `LOG_LEVEL >= 2` — ещё и каждый шаг суммирования; страховка `#if LOG_LEVEL < 0` → `#error`. Предъявите четыре сборки: по умолчанию (только итог), `-DLOG_LEVEL=0` (тишина), `-DLOG_LEVEL=2` (шаги + итог), `-DLOG_LEVEL=-1` (сборка обязана упасть с вашим сообщением). Объясните, чем этот механизм лучше `if (log_level >= 2)` с обычной переменной — и чем хуже.

**Решение.** Идиома «значение по умолчанию» — `#ifndef ИМЯ` / `#define ИМЯ значение` / `#endif`: если макрос уже задан ключом `-D`, блок пропускается, иначе действует значение из исходника. Страховка `#error` идёт **после** этого блока — иначе она проверяла бы ещё не заданный уровень.

```c
#include <stdio.h>

#ifndef LOG_LEVEL
#define LOG_LEVEL 1                 /* уровень по умолчанию */
#endif

#if LOG_LEVEL < 0
#error LOG_LEVEL must be >= 0: build with -DLOG_LEVEL=0, 1 or 2
#endif

int main(void)
{
    int data[5] = {3, 1, 4, 1, 5};
    int sum = 0;

    for (int i = 0; i < 5; i++) {
        sum += data[i];
#if LOG_LEVEL >= 2
        printf("step %d: += %d -> sum = %d\n", i, data[i], sum);
#endif
    }
#if LOG_LEVEL >= 1
    printf("sum = %d\n", sum);
#endif
    return 0;
}
```

**Чем условная компиляция лучше обычного `if`.**

- В «боевой» сборке выключенных строк **нет в программе**: они не попали в единицу трансляции, не породили ни машинного кода, ни строковых литералов, ни вычисления аргументов `printf`. Обычный `if` оставил бы всё это в бинарнике (даже если оптимизатор уберёт мёртвый код, литералы формата и решение об этом остаются на его усмотрение).
- Работает там, где `if` невозможен: можно выключать объявления, поля структур, включения заголовков, целые функции.
- Ошибку конфигурации ловит **на сборке** (`#error`), а не при работе программы.

**Чем хуже.**

- Выключенная ветка не компилируется, а значит, не проверяется: в ней спокойно живут опечатки и устаревшие обращения, и обнаружатся они лишь при сборке с другим ключом (в наших заданиях поэтому и требуется предъявлять **все** конфигурации).
- Уровень фиксируется в момент сборки: чтобы поднять подробность журнала у пользователя, программу надо пересобрать и доставить заново, тогда как переменная меняется ключом командной строки или файлом настроек в любой момент.
- Читаемость: `#if` разрывает код по вертикали и не подчиняется отступам; при трёх-четырёх вложенных условиях текст быстро становится нечитаемым.
- Инструменты (отладчик, статический анализатор, поиск по коду) видят только выбранную конфигурацию.

**Ответ:** программа с блоком `#ifndef LOG_LEVEL` / `#define LOG_LEVEL 1` / `#endif`, страховкой `#if LOG_LEVEL < 0` → `#error` и двумя условными печатями даёт четыре обещанные сборки: по умолчанию — `sum = 14`; с `-DLOG_LEVEL=0` — пустой вывод; с `-DLOG_LEVEL=2` — пять строк `step ...` и `sum = 14`; с `-DLOG_LEVEL=-1` сборка падает сообщением `error: #error LOG_LEVEL must be >= 0: build with -DLOG_LEVEL=0, 1 or 2`. Механизм лучше переменной тем, что выключенные строки физически отсутствуют в программе (нулевая цена в «боевой» сборке), что так можно выключать не только инструкции, но и объявления, и что неверная конфигурация ловится на сборке, а не при работе. Хуже — тем, что выключенные ветки не проверяются компилятором и незаметно «гниют», уровень нельзя изменить без пересборки, а сам код становится менее читаемым и хуже поддаётся инструментам.

**Вариант 2 (обычный `if` по константе-макросу).** Промежуточная форма: уровень остаётся макросом (задаётся ключом `-D`), но проверяется обычным `if` — код при этом компилируется весь, при любом уровне:

Условие `LOG_LEVEL >= 2` при подстановке превращается в `0 >= 2` — константу, и оптимизатор выбрасывает мёртвую ветку, так что цена по скорости обычно нулевая. Проигрыш — в том, что гарантии «этого кода нет в программе» больше нет: строковые литералы и вызовы остаются в единице трансляции, и удалит ли их оптимизатор, зависит от ключей сборки; кроме того, так нельзя выключать объявления и включения — только инструкции. Разумная практика — комбинация: сообщения журнала прятать под `if` по макросу-константе (чтобы код всегда компилировался), а под `#if` держать то, что иначе не выключается: тяжёлые проверки, отладочные структуры данных, платформенные ветки.

### Г11.Ч1.З10

**Условие.** *(прикладное)* Соберите заголовок-минибиблиотеку `temps.h`: страж включения; тип `struct TempRange { double lo, hi; };`; макросы `C_TO_F(c)`, `F_TO_C(f)` и `IN_RANGE(t, r)` (принадлежность температуры диапазону; параметр `r` — структура, обращайтесь к полям как `(r).lo`). Все макросы — по обоим правилам скобок. Программа печатает таблицу перевода 0…40 °C с шагом 10 (ожидается 32.0, 50.0, 68.0, 86.0, 104.0 °F), `F_TO_C(212)` (ожидается 100.0) и проверку `IN_RANGE` для 36.6 и 38.2 при диапазоне {36.0, 37.0} (ожидается 1 и 0). Включите `temps.h` в программу **дважды** и убедитесь, что страж делает это безвредным; затем временно уберите страж и предъявите ошибку компилятора (какая сущность заголовка её вызвала — макросы или структура? почему?).

**Решение.** Заголовок содержит ровно то, что заголовку положено (§11.2.2): страж, определение типа и макросы — и ни одного определения функции или переменной.

```c
#ifndef TEMPS_H
#define TEMPS_H

struct TempRange {
    double lo;
    double hi;
};

#define C_TO_F(c)      (((c) * 9.0 / 5.0) + 32.0)
#define F_TO_C(f)      (((f) - 32.0) * 5.0 / 9.0)
#define IN_RANGE(t, r) (((t) >= (r).lo) && ((t) <= (r).hi))

#endif /* TEMPS_H */
```

Скобки расставлены по обоим правилам §11.1.3: всё тело в скобках и каждый параметр в скобках. Для `IN_RANGE` второе правило особенно важно: параметр `r` используется как `(r).lo` — без скобок запись `r.lo` сломалась бы на любом составном аргументе (скажем, `IN_RANGE(t, ranges[i])` дала бы `ranges[i].lo` — тут повезло бы, а `IN_RANGE(t, *p)` превратилось бы в `*p.lo`, то есть `*(p.lo)`, — и это уже ошибка компиляции). Числа в теле вещественные (`9.0`, `5.0`, `32.0`), иначе `9 / 5` посчиталось бы целочисленно — той же ловушкой, что в Г11.Ч1.З1.

```c
#include <stdio.h>
#include "temps.h"
#include "temps.h"          /* второй раз -- страж делает вклейку безвредной */

int main(void)
{
    for (int c = 0; c <= 40; c += 10)
        printf("%3d C = %5.1f F\n", c, C_TO_F(c));

    printf("F_TO_C(212) = %.1f\n", F_TO_C(212));

    struct TempRange fever = {36.0, 37.0};
    printf("IN_RANGE(36.6) = %d\n", IN_RANGE(36.6, fever));
    printf("IN_RANGE(38.2) = %d\n", IN_RANGE(38.2, fever));
    return 0;
}
```

```

./temps.exe
```

```

Все ожидаемые значения совпали. Двойное включение не дало ни ошибки, ни предупреждения: первая вклейка определила `TEMPS_H` и внесла содержимое, вторая наткнулась на определённый макрос, и `#ifndef` спрятал от компилятора всё до `#endif`.

**⛔ Без стража.** Убираем три служебные строки (файл сохранён как `temps_noguard.h`) и включаем такой заголовок дважды:

```
gcc -std=c17 -Wall -Wextra temps_noguard_main.c -o temps_noguard.exe
```

```
In file included from temps_noguard_main.c:3:
temps_noguard.h:1:8: error: redefinition of 'struct TempRange'
    1 | struct TempRange {
      |        ^~~~~~~~~
In file included from temps_noguard_main.c:2:
temps_noguard.h:1:8: note: originally defined here
    1 | struct TempRange {
      |        ^~~~~~~~~
```

**Какая сущность виновата.** Ошибку вызвала **структура**, а не макросы — и сообщение называет её прямо: `redefinition of 'struct TempRange'`. Причина в разных правилах для этих двух видов сущностей:

- **Тип** в одной единице трансляции определяется ровно один раз (§8.1.1). Второе определение `struct TempRange` — ошибка, даже если оно текстуально совпадает с первым: компилятор не сравнивает определения, он их запрещает.
- **Макрос** можно определять повторно, если текст замены **в точности тот же** (C5 §6.10.5). Вторая вклейка приносит буквально те же три `#define`, поэтому препроцессор молчит. Именно поэтому ошибка ровно одна и относится к строке 1 заголовка — до макросов компилятор просто не дошёл бы, но и с ними всё было бы тихо.

Отсюда практический вывод: заголовок из одних макросов «прощает» отсутствие стража — и тем опаснее, что привычка не сформируется; стоит добавить в него первый `typedef` или `struct`, и всё немедленно сломается у первого же пользователя, включившего заголовок дважды (в том числе через цепочку чужих включений, как в примере 4 §11.1.4). Страж пишется при создании файла.

Диагностика на Linux-контуре совпала дословно (с точностью до вида кавычек в сообщениях gcc 13.3).

**Ответ:** `temps.h` под стражем `TEMPS_H` содержит `struct TempRange { double lo; double hi; };` и три макроса, полностью экранированных скобками: `C_TO_F(c)` → `(((c) * 9.0 / 5.0) + 32.0)`, `F_TO_C(f)` → `(((f) - 32.0) * 5.0 / 9.0)`, `IN_RANGE(t, r)` → `(((t) >= (r).lo) && ((t) <= (r).hi))`. Программа печатает таблицу `32.0, 50.0, 68.0, 86.0, 104.0` градусов Фаренгейта, `F_TO_C(212) = 100.0` и `1`/`0` для 36.6 и 38.2 при диапазоне {36.0, 37.0}. Двойное `#include "temps.h"` безвредно: страж пропускает содержимое при повторной вклейке. Без стража сборка падает с `error: redefinition of 'struct TempRange'` — виновата **структура**: тип в одной единице трансляции определяется единожды, тогда как повторные `#define` с тем же самым текстом замены стандарт разрешает, поэтому макросы заголовка ошибки не вызывают. Практический вывод: заголовок из одних макросов может годами работать без стража и сломается в тот день, когда в него добавят первый тип.

### Г11.Ч2.З1

**Условие.** Напишите в одном файле программу с функциями `int min2(int a, int b)`, `int max2(int a, int b)` и `main`, печатающим `min2(3,7) = 3, max2(3,7) = 7`. Затем разнесите её на `minmax.c` (определения) и `main.c` (использование; объявления впишите руками, без заголовка). Соберите по шагам: два запуска `gcc -c`, затем компоновка; перечислите все порождённые файлы и их роли. Убедитесь, что однокомандная сборка `gcc main.c minmax.c -o app` даёт тот же вывод. На каком этапе и по какой информации компилятор проверил корректность вызова `min2` из `main.c`?

**Решение.** Начинаем с монолита — той формы, в которой мы писали десять глав:

```c
#include <stdio.h>

int min2(int a, int b) { return a < b ? a : b; }
int max2(int a, int b) { return a > b ? a : b; }

int main(void)
{
    printf("min2(3,7) = %d, max2(3,7) = %d\n", min2(3, 7), max2(3, 7));
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra single.c -o single.exe
./single.exe
```

```
min2(3,7) = 3, max2(3,7) = 7
```

Теперь разносим. В `minmax.c` уходят **определения** — и больше ничего: `<stdio.h>` этому файлу не нужен, он ничего не печатает.

```c
/* minmax.c */
int min2(int a, int b) { return a < b ? a : b; }
int max2(int a, int b) { return a > b ? a : b; }
```

В `main.c` остаётся использование, а вместо определений появляются **объявления** — по заданию вписанные руками:

```c
/* main.c */
#include <stdio.h>

int min2(int a, int b);   /* объявления: «такие функции существуют» */
int max2(int a, int b);

int main(void)
{
    printf("min2(3,7) = %d, max2(3,7) = %d\n", min2(3, 7), max2(3, 7));
    return 0;
}
```

**Сборка по шагам.**

```

gcc -std=c17 -Wall -Wextra -c minmax.c
ls -1
```

```

main_nodecl.c
main_wrongdecl.c

```

**Порождённые файлы и их роли** (в каталоге, кроме исходников, появились):

| Файл | Чем порождён | Роль |
|---|---|---|
| `main.o` | `gcc -c main.c` | Объектный файл: машинный код `main` плюс таблица символов — **определяет** `main`, **требует** `min2`, `max2`, `printf`. Запустить нельзя. |
| `minmax.o` | `gcc -c minmax.c` | Объектный файл: код обеих функций; **определяет** `min2` и `max2`, ничего не требует. |
| `app.exe` | `gcc main.o minmax.o -o app.exe` | Исполняемый файл: компоновщик соединил требования с определениями и добавил стартовый код и библиотеку. |

Однокомандная сборка делает ровно то же самое, только промежуточные `.o` не сохраняет:

```

./app_one.exe
```

```

**На каком этапе проверен вызов.** На этапе **компиляции `main.c`** — то есть до того, как о существовании `minmax.c` вообще зашла речь, — и по единственной доступной компилятору информации: по **объявлению** `int min2(int a, int b);`, вписанному в тот же файл. Из объявления компилятор знает число и типы параметров (проверить `min2(3, 7)`) и тип результата (проверить, что `%d` получает `int`). Тела он не видит и видеть не обязан: единица трансляции компилируется независимо от остальных (§11.2.1). Существование тела — забота компоновщика.

Проверяется это одной строкой: уберём объявления —

```
gcc -std=c17 -Wall -Wextra -c main_nodecl.c
```

```
main_nodecl.c: In function 'main':
main_nodecl.c:5:32: error: implicit declaration of function 'min2' [-Wimplicit-function-declaration]
    5 |     printf("min2(3,7) = %d\n", min2(3, 7));   /* объявления нет */
      |                                ^~~~
```

Ошибка возникла **при компиляции** и относится к `main.c`, хотя функция `min2` в программе есть и прекрасно определена в соседнем файле: без объявления компилятору не с чем сверять вызов.

**⛔ Обратная сторона независимости.** Компилятор верит объявлению на слово, а компоновщик сверяет только **имена**, не типы. Достаточно объявлению разъехаться с определением —

```c
double min2(double a, double b);   /* объявление разъехалось с определением */
```

— и обе фазы промолчат:

```
gcc -std=c17 -Wall -Wextra -c main_wrongdecl.c
gcc main_wrongdecl.o minmax.o -o app_wrong.exe
```

Обе команды завершились успешно, без единого сообщения. Полученную программу мы **не запускаем**: она вызывает функцию не с теми типами аргументов и не с тем типом результата — это неопределённое поведение, и показательного результата у него нет. Именно эту дыру закрывает заголовок (Г11.Ч2.З2): когда объявление лежит в `.h`, а реализация включает свой `.h`, разъехаться сигнатурам негде — компилятор поймает расхождение в самом `minmax.c`.

**Ответ:** после разнесения программы получаются `minmax.c` (только определения `min2`/`max2`) и `main.c` (`#include <stdio.h>`, два объявления-прототипа и `main`); сборка по шагам — `gcc -c main.c`, `gcc -c minmax.c`, затем `gcc main.o minmax.o -o app.exe` — порождает `main.o` (код `main`, определяет `main`, требует `min2`, `max2`, `printf`), `minmax.o` (код обеих функций, определяет `min2` и `max2`) и `app.exe` (готовая программа); однокомандная `gcc main.c minmax.c -o app` даёт тот же вывод `min2(3,7) = 3, max2(3,7) = 7`, просто не сохраняет `.o`. Корректность вызова `min2` компилятор проверил **при компиляции `main.c`** по вписанному руками **объявлению** — числу и типам параметров и типу результата; ни `minmax.c`, ни `minmax.o` ему для этого не нужны. Без объявления файл не компилируется вовсе (`error: implicit declaration of function 'min2'`), а если объявление разойдётся с определением (например, `double min2(double, double)`), то и компилятор, и компоновщик промолчат — программа соберётся с неопределённым поведением; это и есть причина держать объявления в общем заголовке.

### Г11.Ч2.З2

**Условие.** Воспроизведите vec-модуль из §11.2.2: `vec.h` (страж, `typedef`, три прототипа), `vec.c` (реализация §9.1.1, включающая свой заголовок), `main.c` (клиент). Соберите тремя командами и сверьте вывод с §9.1.1 (`len=5 cap=8: 10 20 30 40 50`). Ответьте по одному предложению: что придётся пересобрать после правки только `vec.c` (например, начальная ёмкость 4)? а после правки `vec.h` (например, новое поле структуры)? Почему ответы разные?

**Решение.** Интерфейс модуля — тип и три прототипа под стражем; ни одного `#include` в нём не нужно: `Vec` описывается через `int *`, ничего чужого в объявлениях нет.

```c
#ifndef VEC_H
#define VEC_H

typedef struct {
    int *data;   /* блок в куче */
    int len;     /* сколько занято */
    int cap;     /* сколько выделено */
} Vec;

int  vec_init(Vec *v);
int  vec_push(Vec *v, int x);
void vec_free(Vec *v);

#endif /* VEC_H */
```

Реализация — код §9.1.1 без единого изменения плюс два включения: `<stdlib.h>` нужен ей самой, `"vec.h"` — для сверки сигнатур (§11.2.2).

```c
#include <stdlib.h>   /* malloc, realloc, free -- нужны реализации */
#include "vec.h"      /* свой интерфейс -- самопроверка сигнатур */

int vec_init(Vec *v)
{
    v->len = 0;
    v->cap = 2;
    v->data = malloc(v->cap * sizeof *v->data);
    return v->data == NULL ? -1 : 0;
}

int vec_push(Vec *v, int x)
{
    if (v->len == v->cap) {                    /* места нет -- удваиваем */
        int *tmp = realloc(v->data, 2 * v->cap * sizeof *v->data);
        if (tmp == NULL) return -1;            /* v->data ещё жив */
        v->data = tmp;
        v->cap *= 2;
    }
    v->data[v->len++] = x;
    return 0;
}

void vec_free(Vec *v)
{
    free(v->data);
    v->data = NULL;
    v->len = v->cap = 0;
}
```

Клиент включает `<stdio.h>` (нужен ему) и `"vec.h"` (пользуется модулем) — и ничего не знает о `<stdlib.h>`:

```c
#include <stdio.h>
#include "vec.h"

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;
    for (int i = 1; i <= 5; i++) {
        if (vec_push(&v, i * 10) != 0) { vec_free(&v); return 1; }
    }
    printf("len=%d cap=%d:", v.len, v.cap);
    for (int i = 0; i < v.len; i++)
        printf(" %d", v.data[i]);
    printf("\n");
    vec_free(&v);
    return 0;
}
```

gcc -std=c17 -Wall -Wextra -c main.c
gcc main.o vec.o -o app.exe
./app.exe
```

**Что пересобирать после правки `vec.c`.** Только `vec.o` — и перелинковать. Проверяем: меняем начальную ёмкость с 2 на 4 и пересобираем **один** файл, `main.o` не трогаем вовсе:

**Что пересобирать после правки `vec.h`.** Всё, что этот заголовок включает: и `vec.o`, и `main.o`. Новое поле меняет размер и раскладку `Vec`, а раскладку каждая единица трансляции вычисляет **сама**, вклеив заголовок. Оставить старый `main.o` — значит соединить в одной программе два несовпадающих представления одной структуры; чем это кончается, показано в Г11.Ч2.З7.

**Почему ответы разные.** Потому что разное вклеивается. `vec.c` в клиента не вклеивается никогда — клиент про реализацию не знает ничего, кроме имён и сигнатур; поэтому её правка на `main.o` не влияет. `vec.h` вклеивается в **каждую** включившую его единицу трансляции, становясь её частью, — и его правка делает устаревшими все такие `.o`. Это и есть граница «интерфейс/реализация», выраженная в файлах: реализацию можно переписать целиком, не трогая клиентов; интерфейс нельзя изменить, никого не потревожив. В Makefile (Г11.Ч2.З3) та же граница записывается строкой `main.o: main.c vec.h` — с `vec.h`, но без `vec.c`.

**⛔ Типичная неверная попытка: `#include "vec.c"`.** Соблазн «подключить реализацию» вместо возни с раздельной компиляцией:

```c
#include <stdio.h>
#include "vec.c"          /* ⛔ вклеена РЕАЛИЗАЦИЯ, а не интерфейс */
```

Пока пользователь один, всё «работает». Но стоит появиться второму файлу, которому тоже нужен вектор (`other_incl.c` с функцией `vec_sum`, включивший `vec.c` тем же способом), — и:

```
gcc -std=c17 -Wall -Wextra -c main_incl.c
gcc -std=c17 -Wall -Wextra -c other_incl.c
gcc main_incl.o other_incl.o -o app_incl.exe
```

```
ld.exe: other_incl.o:other_incl.c:(.text+0x0): multiple definition of `vec_init'; main_incl.o:main_incl.c:(.text+0x54): first defined here
ld.exe: other_incl.o:other_incl.c:(.text+0x5f): multiple definition of `vec_push'; main_incl.o:main_incl.c:(.text+0xb3): first defined here
ld.exe: other_incl.o:other_incl.c:(.text+0x102): multiple definition of `vec_free'; main_incl.o:main_incl.c:(.text+0x156): first defined here
collect2.exe: error: ld returned 1 exit status
```

Обе компиляции прошли (каждая единица трансляции внутренне непротиворечива), упала компоновка: определения размножились по объектным файлам. Заодно потеряна и раздельная компиляция — правка `vec.c` теперь требует пересборки всех, кто её «включил». Включают только заголовки.

**Ответ:** модуль собирается тремя командами — `gcc -c vec.c`, `gcc -c main.c`, `gcc main.o vec.o -o app.exe` — и печатает `len=5 cap=8: 10 20 30 40 50`, дословно как монолит §9.1.1 (ASan на Linux-контуре чист). После правки только `vec.c` (начальная ёмкость 4) пересобрать нужно `vec.o` и перелинковать программу — `main.o` остаётся годным, что и проверено сборкой со старым `main.o`. После правки `vec.h` (новое поле) пересобирать нужно **оба** объектных файла, потому что заголовок вклеен в обе единицы трансляции и каждая вычисляет раскладку `Vec` сама. Ответы разные потому, что `vec.c` в клиента не вклеивается никогда (он знает только имена и сигнатуры), а `vec.h` вклеивается в каждого, кто его включил, и его правка делает устаревшими все такие `.o`.

### Г11.Ч2.З3

**Условие.** Возьмите Makefile из примера 1 §11.2.3 для vec-проекта и воспроизведите весь прогон: `make` (полная сборка), `make` повторно (`up to date`), `touch vec.c` → `make` (точечная пересборка), `touch vec.h` → `make` (оба `.o`), `./app`, `make clean`. К каждому выводу make — одно предложение: почему пересобралось именно это. Чем `touch` имитирует правку?

**Решение.** Makefile — из §11.2.3, с поправкой из Windows-примечания: цель называется `app.exe`, как и результат, иначе make будет перелинковывать программу при каждом запуске.

```make
CC = gcc
CFLAGS = -std=c17 -Wall -Wextra

app.exe: main.o vec.o
	$(CC) main.o vec.o -o app.exe

main.o: main.c vec.h
	$(CC) $(CFLAGS) -c main.c

vec.o: vec.c vec.h
	$(CC) $(CFLAGS) -c vec.c

.PHONY: clean
clean:
	rm -f app.exe main.o vec.o
```

(Рецепты начинаются символом табуляции. Прогон — GNU Make 4.4.1 из Git Bash: `rm` в рецепте `clean` — оттуда же.)

**Полный прогон.**

```
make
```

```
gcc -std=c17 -Wall -Wextra -c main.c
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main.o vec.o -o app.exe
```

Целей-файлов нет ни одной, поэтому make строит всё: чтобы получить `app.exe`, нужны `main.o` и `vec.o`, а их нет — значит, сначала оба правила компиляции, затем компоновка.

```
make
```

```
make: 'app.exe' is up to date.
```

Все три файла на месте, и каждый новее своих пререквизитов — делать нечего; make сообщает об этом и не запускает ни одной команды.

```
touch vec.c
make
```

```
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main.o vec.o -o app.exe
```

`vec.c` стал новее `vec.o` — правило `vec.o: vec.c vec.h` сработало; следом устарел и `app.exe` (его пререквизит `vec.o` обновился), поэтому перелинковка. `main.o` не тронут: ни `main.c`, ни `vec.h` не менялись, а от `vec.c` он не зависит.

```
touch vec.h
make
```

```
gcc -std=c17 -Wall -Wextra -c main.c
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main.o vec.o -o app.exe
```

`vec.h` записан в пререквизиты **обоих** правил компиляции, поэтому устарели оба объектных файла — и оба пересобраны, а затем перелинкована программа. Это и есть формализованное «правка интерфейса задевает всех, кто его включил» из Г11.Ч2.З2.

```
./app.exe
```

```
len=5 cap=8: 10 20 30 40 50
```

```
make clean
```

```
rm -f app.exe main.o vec.o
```

Цель `clean` — в `.PHONY`, файла с таким именем нет и не предполагается; make просто выполняет рецепт. После уборки в каталоге остаются только исходники и `Makefile`.

**Чем `touch` имитирует правку.** Make не читает содержимое файлов — он сравнивает **отметки времени** (§11.2.3): цель устарела, если она старше хотя бы одного пререквизита. `touch` обновляет отметку времени файла, не трогая ни байта содержимого, — то есть создаёт для make ровно ту ситуацию, которую создаёт настоящая правка, но воспроизводимо и без риска что-нибудь сломать. Обратная сторона той же механики: файл, перезаписанный старым содержимым (например, откатом правки), для make всё равно «изменился» — и наоборот, правка, не изменившая отметку времени, останется незамеченной.

**Windows-примечание (проверено на машине курса).** GNU Make 4.4.1 на Windows сравнивает отметки времени с точностью до **секунды**. Если `touch` и предыдущая сборка попали в одну и ту же секунду — а при таком маленьком проекте это обычное дело, — make ответит `up to date` и ничего не пересоберёт:

```
$ stat -c '%y %n' vec.c app.exe
2026-07-26 19:30:28.795001100 +0200 vec.c
2026-07-26 19:30:28.707778300 +0200 app.exe
$ make
make: 'app.exe' is up to date.
```

Формально `vec.c` новее на 87 миллисекунд, но в пределах секунды make этой разницы не видит. Лечение простое: между сборкой и `touch` выждать секунду (в приведённом выше протоколе так и сделано) — тогда всё работает как описано. На Linux-контуре (GNU Make 4.3) отметки времени сравниваются с наносекундной точностью, и пауза не нужна.

**Ответ:** прогон Makefile из §11.2.3 (с целью `app.exe`) даёт: первый `make` — три команды, потому что нет ни одного из целевых файлов; второй `make` — `make: 'app.exe' is up to date.`, потому что каждая цель новее своих пререквизитов; после `touch vec.c` — пересборка только `vec.o` и перелинковка, потому что `main.o` от `vec.c` не зависит; после `touch vec.h` — пересборка **обоих** `.o` и перелинковка, потому что `vec.h` записан в пререквизиты обоих правил; `./app.exe` печатает `len=5 cap=8: 10 20 30 40 50`; `make clean` выполняет `rm -f app.exe main.o vec.o` (цель в `.PHONY`, поэтому файла с именем `clean` она не требует). `touch` имитирует правку потому, что make смотрит не на содержимое файлов, а на отметки времени: `touch` обновляет отметку, не меняя содержимого, и цель становится устаревшей ровно так же, как после настоящей правки. На Windows у GNU Make 4.4.1 разрешение отметок — одна секунда, поэтому между сборкой и `touch` нужна пауза, иначе правка «в ту же секунду» останется незамеченной.

### Г11.Ч2.З4

**Условие.** *(понимание)* Перед вами четыре сообщения сборки. Для каждого назовите, **кто** его выдал (компилятор / компоновщик / make), в чём причина и что чинить:
(а) `error: unknown type name 'Vec'`;
(б) ``undefined reference to `vec_init'``;
(в) ``multiple definition of `helper'``;
(г) `Makefile:5: *** missing separator.  Stop.`
Для (а) и (б) отдельно объясните, почему `#include "vec.h"` лечит первое, но бесполезен для второго.

**Решение.** Все четыре сообщения воспроизведены на эталонной машине; по каждому — кто говорит, что случилось, что чинить.

**(а) `error: unknown type name 'Vec'` — компилятор.** Клиент забыл включить заголовок:

```
gcc -std=c17 -Wall -Wextra -c main_noinc.c
```

```
main_noinc.c: In function 'main':
main_noinc.c:6:5: error: unknown type name 'Vec'
    6 |     Vec v;
      |     ^~~
main_noinc.c:7:9: error: implicit declaration of function 'vec_init' [-Wimplicit-function-declaration]
    7 |     if (vec_init(&v) != 0) return 1;
      |         ^~~~~~~~
main_noinc.c:8:25: error: request for member 'len' in something not a structure or union
    8 |     printf("len=%d\n", v.len);
      |                         ^
main_noinc.c:9:5: error: implicit declaration of function 'vec_free' [-Wimplicit-function-declaration]
    9 |     vec_free(&v);
      |     ^~~~~~~~
```

**Почерк**: слова `error`/`warning`, имя вашего `.c`-файла, номер строки и колонки, стрелка под виновным местом; сообщение приходит на этапе `-c`, то есть до всякой компоновки. **Причина**: в этой единице трансляции нет объявления типа — компилятор про `Vec` не знает ничего. **Чинить**: добавить `#include "vec.h"`. Проверка: файл `main.c`, отличающийся от `main_noinc.c` только наличием этой строки, компилируется молча:

```
gcc -std=c17 -Wall -Wextra -c main.c
```

**(б) ``undefined reference to `vec_init'`` — компоновщик.** Тот же, уже успешно скомпилированный `main.o` линкуем в одиночку:

```
gcc main.o -o app.exe
```

```
ld.exe: main.o:main.c:(.text+0x69): undefined reference to `vec_init'
ld.exe: main.o:main.c:(.text+0x9a): undefined reference to `vec_push'
ld.exe: main.o:main.c:(.text+0xaa): undefined reference to `vec_free'
ld.exe: main.o:main.c:(.text+0x123): undefined reference to `vec_free'
collect2.exe: error: ld returned 1 exit status
```

**Почерк**: имя `ld.exe`, имена `.o`-файлов, смещения в секциях (`.text+0x69`), слово `reference`, завершающая строка `collect2.exe: error: ld returned 1 exit status`. **Причина**: символ требуется, но ни в одном поданном объектном файле не определён. **Чинить**: добавить в команду компоновки недостающий объектный файл или библиотеку:

```
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main.o vec.o -o app.exe
./app.exe
```

```
len=5 cap=8: 10 20 30 40 50
```

**Почему `#include "vec.h"` лечит (а), но бесполезен для (б).** Потому что заголовок и объектный файл — это ответы на разные вопросы, задаваемые на разных фазах.

- Вопрос компилятора: «что это за имя и как с ним обращаться?» Ответ — **объявление**: тип, сигнатура, размер структуры. Всё это лежит в `vec.h`, поэтому включение заголовка снимает (а).
- Вопрос компоновщика: «где машинный код этой функции?» Ответ — **определение**, то есть тело, скомпилированное в `vec.o`. В заголовке тела нет и быть не должно (иначе получится (в) — см. ниже), поэтому сколько заголовков ни включай, ни один недостающий символ не появится. Более того, в (б) компиляция уже прошла успешно **потому**, что заголовок был включён: объявления хватило.

Отсюда практическое различение: ошибка со строкой исходника — ищите объявление (`#include`, прототип, опечатка в имени типа); ошибка от `ld` — ищите файл (`.o`, `.a`, ключ `-l`) в команде компоновки.

**(в) ``multiple definition of `helper'`` — компоновщик.** Два модуля определили одноимённую вспомогательную функцию, каждый свою (пример 4 §11.2.1, но без `static`):

```c
/* m1.c */                             /* m2.c */
int helper(int x) { return x * 10; }   int helper(int x) { return x + 1; }
```

```
gcc -std=c17 -Wall -Wextra -c m1.c
gcc -std=c17 -Wall -Wextra -c m2.c
gcc -std=c17 -Wall -Wextra -c main15.c
gcc m1.o m2.o main15.o -o app15.exe
```

```
ld.exe: m2.o:m2.c:(.text+0x0): multiple definition of `helper'; m1.o:m1.c:(.text+0x0): first defined here
collect2.exe: error: ld returned 1 exit status
```

**Почерк**: снова `ld.exe` и `.o`-файлы, но теперь названы **оба** места — второе определение и первое (`first defined here`). **Причина**: внешнее имя определено более одного раза на программу (§11.2.1). **Чинить**: решить, кто здесь лишний. Если функция — приватный помощник модуля (наш случай), пометить её `static` в обоих файлах: имена станут внутренними и перестанут конфликтовать. Если это одна и та же функция, нужная всем, — оставить одно определение в одном `.c`, а остальным дать объявление через заголовок.

```
gcc -std=c17 -Wall -Wextra -c m1s.c
gcc -std=c17 -Wall -Wextra -c m2s.c
gcc m1s.o m2s.o main15.o -o app15s.exe
./app15s.exe
```

```
tens(4) = 40, inc(4) = 5
```

**(г) `Makefile:5: *** missing separator.  Stop.` — make.** Рецепт начат пробелами вместо табуляции:

```
make -f Makefile.bad
```

```
Makefile.bad:5: *** missing separator.  Stop.
```

**Почерк**: имя файла правил и номер строки, три звёздочки, финальное `Stop.` — так говорит только make. **Причина**: строка не распознана ни как правило (нет `:`), ни как рецепт (не начинается табуляцией). **Чинить**: заменить ведущие пробелы на символ табуляции в указанной строке; в редакторе полезно включить отображение табов. (Сообщение бывает и от других синтаксических огрехов — например, от продолжения строки, потерявшего `\`, — но первый подозреваемый всегда табуляция.)

На Linux-контуре все три сообщения о компоновке те же по сути и другие по форме — с префиксом `/usr/bin/ld:` и отдельной строкой `in function 'main':`:

```
/usr/bin/ld: main.o: in function `main':
main.c:(.text+0x23): undefined reference to `vec_init'
/usr/bin/ld: m2.o: in function `helper':
m2.c:(.text+0x0): multiple definition of `helper'; m1.o:m1.c:(.text+0x0): first defined here
```

**Ответ:** (а) `error: unknown type name 'Vec'` — **компилятор**, единица трансляции не видит объявления типа; чинится включением `vec.h` в этот `.c`. (б) ``undefined reference to `vec_init'`` — **компоновщик** (`ld.exe`, имена `.o`, смещения в `.text`), символ требуется, но нигде не определён; чинится добавлением `vec.o` (или библиотеки) в команду компоновки. (в) ``multiple definition of `helper'`` — **компоновщик**, внешнее имя определено дважды; чинится либо `static` у приватных помощников (после чего программа собирается и печатает `tens(4) = 40, inc(4) = 5`), либо оставлением ровно одного определения плюс объявление в заголовке. (г) `Makefile:5: *** missing separator.  Stop.` — **make**, рецепт начат не с табуляции; чинится заменой ведущих пробелов на таб в строке 5. `#include "vec.h"` лечит (а) и бесполезен для (б) потому, что заголовок отвечает на вопрос компилятора «как обращаться с этим именем» (объявление), а компоновщику нужен ответ на другой вопрос — «где машинный код» (определение), которого в заголовке нет и не должно быть; в случае (б) компиляция как раз и прошла успешно благодаря включённому заголовку.

### Г11.Ч2.З5

**Условие.** *(понимание)* Дан `counter.c`: `int counter = 0;` и `void bump(void) { counter++; }`. Главный файл вызывает `bump(); bump();` и печатает `counter`. Рассмотрите три варианта строки в главном файле: (а) `extern int counter;` (б) `int counter;` (в) `static int counter;`. Предскажите судьбу каждого варианта — соберётся ли и что напечатает (проверено: 2; ошибка `multiple definition` на компоновке; собирается и печатает **0**). Проверьте все три и объясните вариант (в): сколько переменных `counter` существует в программе, какую менял `bump`, какую читал `printf`.

**Решение.** Модуль общий для всех трёх проб:

```c
/* counter.c */
int counter = 0;      /* определение: память выделена здесь */

void bump(void)
{
    counter++;
}
```

**(а) `extern int counter;` — объявление-ссылка.** Слово `extern` говорит: «память под эту переменную выделена не здесь, ищи в другой единице трансляции». Определение остаётся ровно одно — в `counter.c`.

```
gcc -std=c17 -Wall -Wextra -c counter.c
gcc -std=c17 -Wall -Wextra -c main_a.c
gcc counter.o main_a.o -o app_a.exe
./app_a.exe
```

```
counter = 2
```

Обе единицы трансляции говорят об одном и том же объекте: `bump` увеличил его дважды, `printf` прочитал `2`.

**(б) `int counter;` — ⛔ второе определение.** Без `extern` эта строка на уровне файла — не ссылка, а **предварительное определение** (C5 §6.9.3): компилятор обязан выделить под неё память, если в единице трансляции не найдётся определения с инициализатором. Компилируется такой файл без единого замечания, а падает компоновка:

```
gcc -std=c17 -Wall -Wextra -c main_b.c
gcc counter.o main_b.o -o app_b.exe
```

```
ld.exe: main_b.o:main_b.c:(.bss+0x0): multiple definition of `counter'; counter.o:counter.c:(.bss+0x0): first defined here
```

Секция `.bss` в сообщении — там живут неинициализированные (обнулённые) объекты; обе единицы принесли по своему `counter`, и компоновщик отказался выбирать. Разница с (а) — ровно одно слово `extern`.

**(в) `static int counter;` — собственная переменная.** Собирается и запускается — и печатает ноль:

```
gcc -std=c17 -Wall -Wextra -c main_c.c
gcc counter.o main_c.o -o app_c.exe
./app_c.exe
```

```
counter = 0
```

**Разбор варианта (в).** В программе существуют **две** переменные с именем `counter`:

1. `counter` из `counter.c` — с **внешним** связыванием (§11.2.1): определена там, инициализирована нулём, видна всей программе по имени;
2. `counter` из главного файла — со **внутренним** связыванием: `static` на уровне файла прячет имя внутрь своей единицы трансляции, наружу оно не выставляется вовсе. Поэтому конфликта имён нет и компоновщик молчит — для него это два разных объекта, из которых один даже не имеет внешнего имени.

Менял `bump` первую: он скомпилирован в составе `counter.c` и видит только её. Читал `printf` вторую: он скомпилирован в составе главного файла, где имя `counter` разрешается в локальный `static`-объект. Тот, кого увеличивали, никогда не печатался; тот, кого печатали, никогда не увеличивался — отсюда `0` (статические объекты инициализируются нулём).

Это самый неприятный из трёх вариантов: он не даёт ни ошибки компиляции, ни ошибки компоновки — только неверный результат. Диагностический признак — «переменная не меняется, хотя функция её точно увеличивает»; лечение — убрать `static` и написать `extern`, то есть вариант (а).

**Ответ:** (а) `extern int counter;` — программа собирается и печатает `counter = 2`: объявление-ссылка связывает обе единицы трансляции с единственным определением из `counter.c`. (б) `int counter;` — компиляция проходит, компоновка падает с `multiple definition of 'counter'` (`.bss`): на уровне файла эта строка является предварительным **определением**, а определение внешнего имени должно быть ровно одно на программу. (в) `static int counter;` — собирается и печатает **0**. В программе при этом существуют две переменные `counter`: одна в `counter.c` с внешним связыванием, вторая в главном файле с внутренним (`static` прячет имя внутрь единицы трансляции, поэтому конфликта нет). `bump` увеличивал первую — он скомпилирован вместе с ней; `printf` читал вторую — она видна в его единице трансляции и осталась нулём. Вариант (в) опаснее (б) именно тем, что не даёт никакой диагностики, а только тихо неверный результат.

### Г11.Ч2.З6

**Условие.** *(понимание)* В примере 2 §11.2.2 определение `int twice(int x) { ... }` в заголовке со стражем всё равно обрушило сборку. Объясните: от чего именно защищает страж включения и почему он бессилен против этой ошибки (в терминах «одна единица трансляции — несколько единиц»). Составьте таблицу-памятку: пять сущностей, которым место в `.h` (прототип, тип, макрос, `extern`-объявление, вложенный `#include`), и две, которым не место (определение функции, определение переменной), — с одной строкой обоснования на каждую.

**Решение.** Воспроизводим ошибку. Заголовок со стражем — и с определением внутри:

```c
#ifndef BAD_UTIL_H
#define BAD_UTIL_H

int twice(int x) { return 2 * x; } /* ОПРЕДЕЛЕНИЕ в заголовке -- так нельзя */

#endif /* BAD_UTIL_H */
```

Его включают два файла — `u1.c` (с `main`) и `u2.c` (с функцией `four`):

```
gcc -std=c17 -Wall -Wextra -c u1.c
gcc -std=c17 -Wall -Wextra -c u2.c
gcc u1.o u2.o -o app17.exe
```

```
ld.exe: u2.o:u2.c:(.text+0x0): multiple definition of `twice'; u1.o:u1.c:(.text+0x54): first defined here
collect2.exe: error: ld returned 1 exit status
```

**От чего защищает страж.** Ровно от одного: от **повторной вклейки заголовка в одну и ту же единицу трансляции**. Макрос-страж живёт внутри единицы трансляции; он определяется при первой вклейке и заставляет `#ifndef` спрятать содержимое при второй. Это лечит «ромб включений» (`main.c` включил `point.h` и `shapes.h`, а `shapes.h` — снова `point.h`, пример 4 §11.1.4) и любое дублирование внутри одного `.c`.

**Почему он бессилен здесь.** Потому что вклеек-то и было по одной. `u1.c` — отдельная единица трансляции: её страж не определён, содержимое вклеилось один раз, `u1.o` унёс с собой определение `twice`. `u2.c` — **другая** единица трансляции, компилируемая независимо и с чистого листа: её собственный страж тоже не был определён, содержимое вклеилось один раз, `u2.o` унёс своё определение `twice`. Ни один из двух компиляторных запусков не сделал ничего дважды — и ни один не мог узнать о существовании другого. Дублирование возникло уровнем выше, **между** объектными файлами, где страж не действует по определению: это уже не текст, а таблицы символов, и разбирается с ними компоновщик, у которого правило одно — «определение внешнего имени ровно одно на программу».

Формула для запоминания: страж — защита **внутри** единицы трансляции; правило «одно определение» — требование **между** единицами. Первое — работа препроцессора, второе — работа компоновщика; заголовок с определением нарушает второе, и первое ему не помощник.

Правильный модуль (тот же интерфейс, но с объявлением) собирается и работает:

```c
/* util.h */
#ifndef UTIL_H
#define UTIL_H

int twice(int x);      /* объявление -- вклеивается сколько угодно раз */

#endif /* UTIL_H */
```

```
gcc -std=c17 -Wall -Wextra -c g1.c
gcc -std=c17 -Wall -Wextra -c g2.c
gcc -std=c17 -Wall -Wextra -c util.c
gcc g1.o g2.o util.o -o app_good.exe
./app_good.exe
```

```
twice(21) = 42, four(5) = 20
```

Объявление размножилось по обеим единицам трансляции — и ничего не случилось: объявлений может быть сколько угодно.

**Таблица-памятка.**

| Сущность | Место в `.h`? | Обоснование |
|---|---|---|
| Прототип функции | **Да** | Объявлений может быть сколько угодно; каждому пользователю нужен один и тот же прототип — держать его в одном месте дешевле, чем копировать. |
| Определение типа (`struct`, `typedef`, `enum`) | **Да** | Без описания типа пользователь не сможет ни объявить переменную, ни обратиться к полю; тип не порождает символов, поэтому размножение по единицам трансляции безвредно (внутри одной — страж). |
| Макрос (`#define`) | **Да** | Существует только на этапе препроцессирования, машинного кода не порождает; повторное определение с тем же текстом замены разрешено. |
| `extern`-объявление переменной | **Да** | Это ссылка, а не определение: памяти не выделяет, поэтому вклеивается во всех пользователей; само определение живёт ровно в одном `.c`. |
| Вложенный `#include` (то, без чего интерфейс не читается) | **Да** | Заголовок обязан быть самодостаточным: если в объявлениях встречается `FILE` или `size_t`, нужный заголовок подтягивает он сам, а не его пользователь. |
| Определение функции | **Нет** | Вклеивается в каждую включившую единицу трансляции и порождает символ в каждом `.o` — компоновщик остановит сборку с `multiple definition` (проверено выше). |
| Определение переменной | **Нет** | То же самое: память выделится в каждой единице трансляции, и компоновщик предъявит `multiple definition` (Г11.Ч2.З5, вариант (б)). В `.h` — `extern`-объявление, в одном `.c` — определение. |

**Ответ:** страж включения защищает **только** от повторной вклейки заголовка в одну и ту же единицу трансляции: макрос-страж живёт внутри единицы, и при втором `#include` в том же `.c` содержимое прячется. Против ошибки примера 2 он бессилен потому, что вклеек было по одной в каждой из **двух** единиц трансляции: `u1.c` и `u2.c` компилируются независимо, каждая со своим чистым набором макросов, — и каждая унесла в свой `.o` собственное определение `twice`; дублирование возникло между объектными файлами, где страж не действует, а действует правило компоновщика «определение внешнего имени ровно одно на программу» (`multiple definition of 'twice'`). Памятка: в `.h` уместны прототип (объявлений может быть сколько угодно), определение типа (не порождает символов), макрос (существует лишь до компиляции), `extern`-объявление (ссылка, а не память) и вложенный `#include` (заголовок обязан быть самодостаточным); неуместны определение функции и определение переменной — оба порождают символ в каждом включившем `.o` и приводят к `multiple definition`.

### Г11.Ч2.З7

**Условие.** *(понимание)* «Make-детектив». В Makefile проекта у правила `main.o: main.c` забыт пререквизит `vec.h`. Разработчик изменил в `vec.h` структуру `Vec` (переставил поля), запустил `make` — пересобрался только `vec.o`, — и программа собралась без единой ошибки. Опишите: почему make не тронул `main.o`; чем опасна получившаяся программа (два `.o` с разными представлениями об одной структуре — ср. §8.2.3); почему эта ошибка коварнее ошибки компиляции. Как чинится Makefile и каким прогоном проверить починку (образец — пример 1 §11.2.3, шаг `touch vec.h`)?

**Решение.** Сцена преступления — Makefile, в котором у правила для `main7.o` записан только исходник:

```make
CC = gcc
CFLAGS = -std=c17 -Wall -Wextra

app.exe: main7.o vec.o
	$(CC) main7.o vec.o -o app.exe

main7.o: main7.c
	$(CC) $(CFLAGS) -c main7.c

vec.o: vec.c vec.h
	$(CC) $(CFLAGS) -c vec.c

.PHONY: clean
clean:
	rm -f app.exe main7.o vec.o
```

Клиент `main7.c` заполняет вектор пятью числами и печатает длину и ёмкость:

```c
#include <stdio.h>
#include "vec.h"

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;
    for (int i = 1; i <= 5; i++) {
        if (vec_push(&v, i * 10) != 0) { vec_free(&v); return 1; }
    }
    printf("len=%d cap=%d\n", v.len, v.cap);
    vec_free(&v);
    return 0;
}
```

Исходное состояние — всё правильно:

```

./app.exe
```

```
gcc -std=c17 -Wall -Wextra -c main7.c
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main7.o vec.o -o app.exe
len=5 cap=8
```

Теперь «разработчик наводит порядок» в `vec.h` — меняет местами поля `len` и `cap`, ничего больше не трогая:

```c
typedef struct {
    int *data;   /* блок в куче */
    int cap;     /* сколько выделено   <-- поля переставлены */
    int len;     /* сколько занято */
} Vec;
```

```
make
```

```
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main7.o vec.o -o app.exe
```

```
./app.exe
```

```
len=8 cap=5
```

⛔ Программа собралась без единого сообщения — и печатает чепуху: длина и ёмкость поменялись местами. (Результат устойчив от запуска к запуску на эталонной машине, но опирается он на неопределённое поведение — см. ниже; на другой платформе или при других полях числа будут другими или программа рухнет.)

**Почему make не тронул `main7.o`.** Make ничего не знает о языке C и о том, что `main7.c` включает `vec.h`: список зависимостей ему сообщает Makefile, и в правиле `main7.o: main7.c` заголовка нет. Значит, единственный пререквизит `main7.o` — файл `main7.c`, который не менялся; цель новее его — работы нет. Правило же `vec.o: vec.c vec.h` заголовок упоминает, поэтому `vec.o` честно пересобран, а следом перелинкован `app.exe`. С точки зрения make всё сделано верно: он выполнил ровно то, что записано.

**Чем опасна получившаяся программа.** В ней сосуществуют два несовместимых представления одного типа. `vec.o` скомпилирован с новым заголовком: для него `cap` лежит по смещению 8, `len` — по 12. `main7.o` скомпилирован со старым: для него `len` по 8, `cap` по 12. Функции модуля добросовестно записывают длину и ёмкость по своим смещениям, а `printf` в клиенте читает их по своим — и получает значения перепутанными: `len=8 cap=5` вместо `len=5 cap=8` (§8.2.3: раскладка структуры — свойство единицы трансляции, компилятор вычисляет её из объявления). Это неопределённое поведение: стандарт требует, чтобы во всех единицах трансляции тип был описан согласованно. Нам «повезло» получить безобидную перестановку двух чисел, потому что оба поля одного типа и размера; переставь мы `data` с `len` — и клиент читал бы указатель как число, а число как указатель, что означает обращение по случайному адресу.

**Почему это коварнее ошибки компиляции.** Ошибка компиляции останавливает сборку в момент её появления, называет файл и строку и не даёт получить неправильную программу. Здесь всё наоборот:

- нет ни ошибки, ни предупреждения — ни от компилятора (каждая единица трансляции внутренне непротиворечива), ни от компоновщика (он сверяет имена, а не типы: `vec_init` есть и там, и там), ни от make (он выполнил записанное);
- дефект проявляется как «странное поведение» вдали от причины: смотреть будут на `printf` или на логику `vec_push`, а виноват пропущенный пререквизит в Makefile;
- воспроизводимость плохая: у коллеги, собиравшего с нуля (`make clean && make` или свежий клон), всё работает — его `main7.o` собран с новым заголовком. Классическое «на моей машине не воспроизводится»;
- «лечится» случайно — любой следующей правкой `main7.c`, после чего дефект исчезает, не будучи понятым, и возвращается при следующей правке заголовка.

**Как чинится и как проверяется.** Чинится одной строкой — каждый `.o` зависит от всех заголовков, которые включает его исходник:

```make
main7.o: main7.c vec.h
	$(CC) $(CFLAGS) -c main7.c
```

Проверка — шагом `touch vec.h` из примера 1 §11.2.3: после правки заголовка должны пересобраться **оба** объектных файла.

```
touch vec.h
make
./app.exe
```

```
gcc -std=c17 -Wall -Wextra -c main7.c
gcc -std=c17 -Wall -Wextra -c vec.c
gcc main7.o vec.o -o app.exe
len=5 cap=8
```

Обе компиляции на месте — значит, зависимость записана; программа снова печатает правильное `len=5 cap=8`, потому что теперь обе единицы трансляции видят одну и ту же раскладку `Vec`. (Аварийное средство на случай, когда что-то подобное уже подозревается, — `make clean && make`: пересборка с нуля не зависит ни от каких пререквизитов. Но это лечение симптома, а не Makefile.)

**Ответ:** make не тронул `main7.o` потому, что зависимости ему известны только из Makefile, а в правиле `main7.o: main7.c` заголовок не указан — единственный пререквизит не менялся, значит цель считается свежей; о том, что `main7.c` включает `vec.h`, make не догадывается. Получившаяся программа опасна тем, что её объектные файлы содержат **разные раскладки** одной структуры: `vec.o` пишет поля по новым смещениям, `main7.o` читает по старым — вывод `len=8 cap=5` вместо `len=5 cap=8`; формально это неопределённое поведение (тип обязан быть описан согласованно во всех единицах трансляции, ср. §8.2.3), и при перестановке полей разных размеров вместо перепутанных чисел получилось бы обращение по мусорному адресу. Коварнее ошибки компиляции она тем, что не даёт никакой диагностики (компилятор доволен, компоновщик сверяет только имена, make выполнил записанное), проявляется вдали от причины и не воспроизводится у того, кто собирал с нуля. Чинится добавлением заголовка в пререквизиты: `main7.o: main7.c vec.h`; проверяется прогоном `touch vec.h && make` — после починки пересобираются **оба** `.o`, и программа снова печатает `len=5 cap=8`.

### Г11.Ч2.З8

**Условие.** *(прикладное)* Соберите модуль **стека символов** `stack.h`/`stack.c`: структура `{ char *data; int len; int cap; }`, функции `stack_init`, `stack_push` (рост удвоением, по образцу вектора §9.1.1), `stack_pop` (через выходной параметр, `-1` на пустом), `stack_empty`, `stack_free`. Клиент `brackets.c`: функция `balanced(const char *s)` проверяет сбалансированность скобок `()[]{}` (алгоритм §9.2.1: открывающая — в стек, закрывающая — сверить с вершиной) и `main` с тестами: `"([]{})"` → OK, `"([)]"` → FAIL, `"(("` → FAIL, `"int a[N];"` → OK. Сборка — раздельной компиляцией; вспомогательные функции клиента (`match`, `balanced`) пометьте `static` и объясните зачем. AddressSanitizer обязан быть чист.

**Решение.** Интерфейс модуля — пять функций и тип; `stack_empty` принимает `const Stack *`, потому что ничего не меняет, а `stack_pop` отдаёт снятый символ через выходной параметр и разделяет «снял» и «пусто» кодом возврата (приём §9.2.1).

```c
#ifndef STACK_H
#define STACK_H

typedef struct {
    char *data;   /* блок в куче */
    int len;      /* сколько занято */
    int cap;      /* сколько выделено */
} Stack;

int  stack_init(Stack *s);
int  stack_push(Stack *s, char c);
int  stack_pop(Stack *s, char *out);   /* -1 -- стек пуст */
int  stack_empty(const Stack *s);
void stack_free(Stack *s);

#endif /* STACK_H */
```

Реализация — вектор §9.1.1 с элементом `char` и урезанным до стековых операций интерфейсом:

```c
#include <stdlib.h>
#include "stack.h"

int stack_init(Stack *s)
{
    s->len = 0;
    s->cap = 2;
    s->data = malloc(s->cap * sizeof *s->data);
    return s->data == NULL ? -1 : 0;
}

int stack_push(Stack *s, char c)
{
    if (s->len == s->cap) {                     /* рост удвоением */
        char *tmp = realloc(s->data, 2 * s->cap * sizeof *s->data);
        if (tmp == NULL) return -1;
        s->data = tmp;
        s->cap *= 2;
    }
    s->data[s->len++] = c;
    return 0;
}

int stack_pop(Stack *s, char *out)
{
    if (s->len == 0) return -1;                 /* пусто -- значения нет */
    *out = s->data[--s->len];
    return 0;
}

int stack_empty(const Stack *s)
{
    return s->len == 0;
}

void stack_free(Stack *s)
{
    free(s->data);
    s->data = NULL;
    s->len = s->cap = 0;
}
```

Клиент — алгоритм §9.2.1 поверх этого модуля:

```c
#include <stdio.h>
#include "stack.h"

static int match(char open, char close)      /* парная ли пара скобок */
{
    return (open == '(' && close == ')') ||
           (open == '[' && close == ']') ||
           (open == '{' && close == '}');
}

static int balanced(const char *s)           /* 1 -- скобки согласованы */
{
    Stack st;
    if (stack_init(&st) != 0) return 0;
    int ok = 1;
    for (int i = 0; ok && s[i] != '\0'; i++) {
        char c = s[i];
        if (c == '(' || c == '[' || c == '{') {
            if (stack_push(&st, c) != 0)
                ok = 0;                      /* нет памяти */
        } else if (c == ')' || c == ']' || c == '}') {
            char open;
            if (stack_pop(&st, &open) != 0 || !match(open, c))
                ok = 0;                      /* закрыли то, чего не открывали */
        }
    }
    if (!stack_empty(&st))
        ok = 0;                              /* остались незакрытые */
    stack_free(&st);
    return ok;
}

int main(void)
{
    const char *tests[] = { "([]{})", "([)]", "((", "int a[N];" };
    for (size_t i = 0; i < sizeof tests / sizeof tests[0]; i++)
        printf("%-10s -> %s\n", tests[i], balanced(tests[i]) ? "OK" : "FAIL");
    return 0;
}
```

**Зачем `static` у `match` и `balanced`.** Обе функции — внутренняя кухня клиента, а не часть чьего-либо интерфейса. `static` на уровне файла даёт им **внутреннее связывание** (§11.2.1): имена не попадают в таблицу внешних символов `brackets.o` и не видны компоновщику. Отсюда три выгоды:

1. **Нет конфликтов имён.** `match` и `balanced` — слова слишком общие; в проекте из десятка модулей вероятность, что кто-то ещё определит свой `match`, велика, и без `static` это дало бы `multiple definition` (ровно как `helper` в Г11.Ч2.З4). Со `static` одноимённые функции в разных файлах не мешают друг другу.
2. **Честный интерфейс.** Читающий модуль видит: наружу торчит только `main`, всё остальное — детали, которые можно свободно менять, не задев никого.
3. **Больше свободы компилятору.** Функция с внутренним связыванием заведомо не вызывается извне, поэтому её проще встроить, а если она перестанет использоваться — компилятор об этом ещё и предупредит.

Правило (C4, гл. 10; C3, гл. 10): всё, что не входит в интерфейс модуля, помечается `static` сразу, а не после первого конфликта.

**Ответ:** модуль `stack.h`/`stack.c` — структура `{ char *data; int len; int cap; }` и пять функций (инициализация с ёмкостью 2, `stack_push` с ростом удвоением через `realloc`, `stack_pop` через выходной параметр и `-1` на пустом стеке, `stack_empty`, `stack_free`); клиент `brackets.c` реализует алгоритм §9.2.1 и печатает `([]{}) -> OK`, `([)] -> FAIL`, `(( -> FAIL`, `int a[N]; -> OK`. Сборка раздельная: `gcc -c stack.c`, `gcc -c brackets.c`, `gcc brackets.o stack.o -o brackets.exe`. Отчёт AddressSanitizer чист — ни ошибок доступа, ни утечек: единственный выход из `balanced` проходит через `stack_free`. Вспомогательные `match` и `balanced` помечены `static` потому, что они не входят в интерфейс: внутреннее связывание убирает их имена из таблицы внешних символов, снимая риск `multiple definition` с такими общими именами, делая интерфейс модуля честным (наружу видна только `main`) и давая компилятору больше свободы.

**Вариант 2 (в стек кладём ожидаемую закрывающую скобку).** Вместо того чтобы хранить открывающую скобку и потом сверять пару, можно сразу класть в стек тот символ, которым эту скобку **обязаны** закрыть. Тогда проверка становится сравнением двух символов, а таблица пар нужна только в одном месте:

```c
#include <stdio.h>
#include "stack.h"

static char closing_for(char open)      /* какая скобка закроет открытую */
{
    if (open == '(') return ')';
    if (open == '[') return ']';
    return '}';
}

static int balanced(const char *s)      /* 1 -- скобки согласованы */
{
    Stack st;
    if (stack_init(&st) != 0) return 0;
    int ok = 1;
    for (int i = 0; ok && s[i] != '\0'; i++) {
        char c = s[i];
        if (c == '(' || c == '[' || c == '{') {
            if (stack_push(&st, closing_for(c)) != 0)   /* кладём ОЖИДАЕМУЮ закрывающую */
                ok = 0;
        } else if (c == ')' || c == ']' || c == '}') {
            char expected;
            if (stack_pop(&st, &expected) != 0 || expected != c)
                ok = 0;                 /* закрыли не тем или не открывали */
        }
    }
    if (!stack_empty(&st))
        ok = 0;                         /* остались незакрытые */
    stack_free(&st);
    return ok;
}

int main(void)
{
    const char *tests[] = { "([]{})", "([)]", "((", "int a[N];" };
    for (size_t i = 0; i < sizeof tests / sizeof tests[0]; i++)
        printf("%-10s -> %s\n", tests[i], balanced(tests[i]) ? "OK" : "FAIL");
    return 0;
}
```

*Сравнение.* Первый вариант буквально повторяет формулировку задания («открывающая — в стек, закрывающая — сверить с вершиной») и хранит в стеке то, что реально встретилось во входной строке, — это удобно, если потом понадобится диагностика («не закрыта скобка `[`, открытая на позиции 7»): нужный символ уже лежит в стеке. Второй короче в горячем месте — сравнение `expected != c` вместо вызова `match` с тремя парами условий — и переносит все знания о парности в одну функцию `closing_for`: добавить пару `<>` в первом варианте значит дописать строку и в `match`, и в оба списка условий, во втором — в `closing_for` и в списки. Расплата: в стеке лежит не то, что было в тексте, поэтому для сообщения об ошибке символ придётся преобразовывать обратно. Практическое правило: если по стеку потом строится диагностика — храните исходные символы; если стек нужен только для проверки — храните ожидание, это короче и меньше ветвлений.

### Г11.Ч2.З9

**Условие.** *(прикладное)* Напишите Makefile для проекта З8: переменные `CC`/`CFLAGS`, цель `brackets` (на Windows — `brackets.exe`), у обоих `.o` в пререквизитах `stack.h`, цель `clean` в `.PHONY`. Объясните, почему `stack.h` обязан стоять в пререквизитах **обоих** объектных файлов (последствия — в З7).

**Почему `stack.h` обязан стоять в пререквизитах обоих `.o`.** Потому что заголовок вклеивается в **обе** единицы трансляции, и обе от него зависят по-настоящему:

- `stack.c` берёт из него прототипы — по ним компилятор сверяет реализацию с интерфейсом; поменяется сигнатура — реализация обязана перекомпилироваться, иначе рассогласование дойдёт до компоновщика (а при совпадении имён — и дальше);
- `brackets.c` берёт из него и прототипы, и **определение типа** `Stack` — по нему компилятор вычисляет размер структуры и смещения полей прямо в машинном коде клиента.

Если `stack.h` забыт в правиле `brackets.o`, повторяется история Г11.Ч2.З7: правка структуры пересоберёт только `stack.o`, клиент останется со старым представлением, и программа соберётся без единой ошибки — с двумя несовместимыми раскладками одной структуры внутри. Диагностики не будет ни от компилятора, ни от компоновщика, ни от make; дефект проявится как необъяснимо неверные данные и исчезнет при первой же сборке с нуля. Отсюда общее правило: **каждый `.o` зависит от всех заголовков, которые включает его исходник** (в больших проектах эти списки не пишут руками, а генерируют компилятором — но принцип тот же).

**Ответ:** Makefile содержит `CC = gcc`, `CFLAGS = -std=c17 -Wall -Wextra`, цель `brackets.exe: brackets.o stack.o` с рецептом компоновки, правила `brackets.o: brackets.c stack.h` и `stack.o: stack.c stack.h` и `clean` в `.PHONY`. Протокол: первый `make` собирает всё тремя командами; повторный отвечает `make: 'brackets.exe' is up to date.`; после `touch stack.c` пересобирается только `stack.o` и перелинковывается программа; после `touch stack.h` пересобираются **оба** `.o`; `./brackets.exe` печатает четыре строки с `OK`/`FAIL`; `make clean` удаляет программу и объектные файлы. `stack.h` обязан стоять в пререквизитах обоих объектных файлов потому, что вклеивается в обе единицы трансляции: `stack.c` сверяет по нему реализацию с прототипами, а `brackets.c` вычисляет из него размер и раскладку `Stack` прямо в свой машинный код. Забытый пререквизит даёт сценарий Г11.Ч2.З7 — молчаливую сборку программы, в которой два объектных файла по-разному понимают одну структуру.

### Г11.Ч2.З10

**Условие.** *(прикладное)* Соберите статическую библиотеку `libds.a` из `vec.o` и `stack.o` (`ar rcs`; опись — `ar t`, ожидается два имени). Напишите клиента `main_ds.c`, использующего **обе** структуры: вектор с элементами 1 2 3 (печать `vec: 1 2 3`) и стек с символами `a`, `b`, `c`, выталкиваемыми до пустоты (печать `stack pops: c b a`). Слинкуйте `gcc main_ds.o -L. -lds`; затем предъявите ⛔-вариант `gcc -L. -lds main_ds.o` и объясните ошибку через порядок разрешения символов (§11.2.3, пример 3; проверено и на MinGW, и на Linux). ASan-сборка клиента чиста.

**Решение.** В каталоге собраны оба модуля предыдущих заданий — `vec.h`/`vec.c` (Г11.Ч2.З2) и `stack.h`/`stack.c` (Г11.Ч2.З8) — без единого изменения: в том и смысл модулей, что они переиспользуются как есть. Клиент включает оба интерфейса:

```c
#include <stdio.h>
#include "vec.h"
#include "stack.h"

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;
    for (int i = 1; i <= 3; i++) {
        if (vec_push(&v, i) != 0) { vec_free(&v); return 1; }
    }
    printf("vec:");
    for (int i = 0; i < v.len; i++)
        printf(" %d", v.data[i]);
    printf("\n");
    vec_free(&v);

    Stack s;
    if (stack_init(&s) != 0) return 1;
    for (char c = 'a'; c <= 'c'; c++) {
        if (stack_push(&s, c) != 0) { stack_free(&s); return 1; }
    }
    printf("stack pops:");
    char top;
    while (stack_pop(&s, &top) == 0)
        printf(" %c", top);
    printf("\n");
    stack_free(&s);
    return 0;
}
```

Цикл выталкивания управляется кодом возврата `stack_pop`: он же и сообщает, что стек опустел, — отдельная проверка `stack_empty` не нужна (тот же приём, что с `fgets` в §10.1.3).

**Почему.** Компоновщик обрабатывает аргументы **слева направо**, ведя список ещё не разрешённых символов, и с архивом обращается иначе, чем с объектным файлом:

- объектный файл, указанный в команде, включается в программу **целиком и безусловно** — вместе со всеми своими определениями и требованиями;
- из архива берутся **только те** объектники, которые в момент его просмотра закрывают хотя бы один символ из текущего списка недостающих; остальные пропускаются и больше не рассматриваются — к этому архиву компоновщик не возвращается.

В правильном порядке (`main_ds.o -L. -lds`) к моменту просмотра `libds.a` список недостающих уже содержит `vec_init`, `stack_push` и остальные — компоновщик достаёт из архива `vec.o` и `stack.o` и всё разрешает. В неправильном (`-L. -lds main_ds.o`) архив просматривается **первым**: недостающих символов ещё нет вообще, ни один объектник из коробки не нужен, архив пропускается целиком. Затем добавляется `main_ds.o`, который приносит девять требований — и закрывать их уже нечем. Отсюда правило: **библиотеки указывают после тех объектных файлов, которые ими пользуются** (а если библиотеки зависят друг от друга — то в порядке «пользователь раньше поставщика»).

main_ds.c:(.text+0x23): undefined reference to `vec_init'
/usr/bin/ld: main_ds.c:(.text+0x4b): undefined reference to `vec_push'
/usr/bin/ld: main_ds.c:(.text+0x5b): undefined reference to `vec_free'
```

**ASan.** Клиент, использующий обе структуры (и обе кучи), под санитайзером чист:

```
gcc -std=c17 -Wall -Wextra -fsanitize=address -g -c vec.c stack.c main_ds.c
ar rcs libds.a vec.o stack.o
gcc -fsanitize=address main_ds.o -L. -lds -o app_ds_asan.out
./app_ds_asan.out
```

```
vec: 1 2 3
stack pops: c b a
```

Ни одного сообщения: оба блока освобождены (`vec_free`, `stack_free`), за границы никто не выходил. Обратите внимание, что ключ `-fsanitize=address` нужен и при компиляции, и при компоновке — санитайзер добавляет свою библиотеку времени выполнения.

**Ответ:** библиотека собирается командой `ar rcs libds.a vec.o stack.o`, её опись (`ar t libds.a`) содержит два имени — `vec.o` и `stack.o`; клиент `main_ds.c`, включающий оба заголовка, после линковки `gcc main_ds.o -L. -lds -o app_ds.exe` печатает `vec: 1 2 3` и `stack pops: c b a` (ASan-сборка того же клиента чиста). Вариант `gcc -L. -lds main_ds.o` падает с девятью `undefined reference` — по одной на каждый вызов модулей: компоновщик просматривает аргументы слева направо и берёт из архива только те объектники, которые закрывают **уже накопленные** недостающие символы; когда архив стоит первым, недостающих символов ещё нет, архив пропускается целиком и больше не рассматривается, а пришедший следом `main_ds.o` приносит требования, закрывать которые нечем. Правило: библиотеки указываются **после** объектных файлов, которые ими пользуются; проверено и на MinGW (`ld.exe: ... undefined reference`), и на Linux (`/usr/bin/ld: ...`).

**Вариант 2 (архив указан явным именем).** Ключи `-L`/`-l` — не единственный способ подать компоновщику архив: его можно назвать файлом, как обычный объектник:

```
gcc main_ds.o libds.a -o app_ar.exe
./app_ar.exe
```

```
vec: 1 2 3
stack pops: c b a
```

*Сравнение.* Явное имя короче в одноразовой команде и не требует помнить про соглашение `lib…​.a`: видно ровно тот файл, который берётся, — удобно, когда архив лежит рядом и один. Форма `-L. -lds` абстрагирует от имени файла и пути: тот же ключ `-lds` найдёт библиотеку в любом из каталогов поиска — системном или добавленном `-L`, — и именно она обязательна для системных библиотек, у которых полного пути вы обычно не знаете (`-luser32`, `-lm`). Правило порядка одинаково для обеих форм: и явный архив, и `-l` просматриваются в том месте команды, где написаны, — поставьте их перед `main_ds.o`, и получите те же `undefined reference`.
