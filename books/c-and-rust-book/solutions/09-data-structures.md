## Часть 9.1. Динамический массив и связный список

### Г9.Ч1.З1

**Условие.** Возьмите `Vec` из §9.1.1 и добавьте в него 6 элементов `1..6`, печатая `len` и `cap` после каждого `push`. Выпишите последовательность значений `cap` и объясните, на каких именно вставках происходят удвоения и почему.

**Решение.** Ёмкость меняет только `vec_push`, и только в одном случае — когда очередной элемент не помещается, то есть когда на входе в функцию `len == cap`. Тогда блок перевыделяется вдвое большим (`realloc`), `cap` удваивается, и лишь после этого элемент записывается. Значит, предсказать последовательность можно, не запуская программу: начальная ёмкость `cap = 2` (её ставит `vec_init`), и «упереться» в неё можно на 3-м элементе, потом на 5-м, потом на 9-м — то есть на элементе с номером `cap + 1` для текущей ёмкости.

```c
/* Vec, vec_init, vec_push, vec_free — как в §9.1.1 */

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;
    for (int i = 1; i <= 6; i++) {
        if (vec_push(&v, i) != 0) { vec_free(&v); return 1; }
        printf("push %d: len=%d cap=%d\n", i, v.len, v.cap);
    }
    vec_free(&v);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra vec6.c -o vec6
./vec6
```

```
push 1: len=1 cap=2
push 2: len=2 cap=2
push 3: len=3 cap=4
push 4: len=4 cap=4
push 5: len=5 cap=8
push 6: len=6 cap=8
```

Разберём по шагам. `push 1` и `push 2`: `len` (0, затем 1) меньше `cap == 2` — свободное место есть, куча не тревожится вовсе. `push 3`: на входе `len == 2 == cap`, места нет — `realloc` на 4 элемента, `cap` становится 4, элемент записывается. `push 4`: снова есть запас (`len == 3 < 4`). `push 5`: `len == 4 == cap` — второе удвоение, `cap` = 8. `push 6` укладывается в запас.

**Ответ:** последовательность ёмкости — `2, 2, 4, 4, 8, 8`. Удвоения произошли на **третьей** и **пятой** вставках: только на них выполнялось условие `len == cap`, при котором свободного места в блоке не остаётся. Из шести вставок дорогими (с перевыделением и копированием) оказались две, остальные четыре — одна запись в готовую ячейку; это и есть амортизированная дешевизна стратегии удвоения (§9.1.1): чем больше вектор, тем реже случается перевыделение (следующее ждало бы 9-го элемента).

### Г9.Ч1.З2

**Условие.** Постройте список тремя вызовами `push_front(&list, …)` со значениями `5`, `10`, `15` (в этом порядке). Не запуская, предскажите вывод `print_list`; затем проверьте. Объясните, почему порядок обратный порядку вставки, и освободите список.

**Решение.** Предсказание строится по определению `push_front`: новый узел получает `next` = старая голова и **сам становится головой**. Прорисуем стрелки после каждого вызова:

```
push_front(&list, 5):   list ─▶ [5] ─▶ NULL
push_front(&list, 10):  list ─▶ [10] ─▶ [5] ─▶ NULL
push_front(&list, 15):  list ─▶ [15] ─▶ [10] ─▶ [5] ─▶ NULL
```

Значит, `print_list` должен напечатать `15 -> 10 -> 5 -> NULL`. Проверяем:

```c
/* Node, push_front, print_list, list_free — как в §9.1.2 */

int main(void)
{
    Node *list = NULL;
    if (push_front(&list, 5) != 0)  { list_free(list); return 1; }
    if (push_front(&list, 10) != 0) { list_free(list); return 1; }
    if (push_front(&list, 15) != 0) { list_free(list); return 1; }
    print_list(list);
    list_free(list);
    list = NULL;          /* после освобождения — сразу NULL */
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra list3.c -o list3
./list3
```

```
15 -> 10 -> 5 -> NULL
```

Освобождение — `list_free(list)`, дальше `list = NULL` (привычка §7.2.1: переменная не должна хранить адрес освобождённой памяти). Прогон под ASan чист: три `malloc` — три `free`.

**Ответ:** печатается `15 -> 10 -> 5 -> NULL` — порядок обратен порядку вставки, потому что каждая вставка происходит **в начало**: новый узел встаёт перед всеми ранее вставленными и «обгоняет» их. Голова списка — это всегда последний добавленный узел; чтобы порядок совпадал с порядком вставки, нужна вставка в конец (`push_back`, Г9.Ч1.З9) или очередь (§9.2.2).

### Г9.Ч1.З3

**Условие.** Напишите функцию `int list_sum(const Node *head)`, возвращающую сумму значений списка обходом. Постройте список `2 -> 4 -> 6 -> 8`, напечатайте длину (`list_length`) и сумму, освободите список.

**Решение.** `list_sum` — это канонический цикл-обход из §9.1.2 с накоплением в теле; функция только читает список, поэтому параметр — `const Node *` (значение головы, менять её не нужно — см. Г9.Ч1.З7). Список `2 -> 4 -> 6 -> 8` собирается тремя вставками в начало в **обратном** порядке (8, 6, 4, 2) — по логике З2.

```c
/* Node, push_front, print_list, list_length, list_free — как в §9.1.2 */

int list_sum(const Node *head)         /* сумма значений обходом */
{
    int sum = 0;
    for (const Node *cur = head; cur != NULL; cur = cur->next)
        sum += cur->value;
    return sum;
}

int main(void)
{
    Node *list = NULL;
    for (int x = 8; x >= 2; x -= 2)    /* кладём 8, 6, 4, 2 -> список 2 4 6 8 */
        if (push_front(&list, x) != 0) { list_free(list); return 1; }
    print_list(list);
    printf("length = %d\n", list_length(list));
    printf("sum    = %d\n", list_sum(list));
    list_free(list);
    list = NULL;
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra sum.c -o sum
./sum
```

```
2 -> 4 -> 6 -> 8 -> NULL
length = 4
sum    = 20
```

Обратите внимание: на пустом списке (`head == NULL`) функция корректна без единой дополнительной проверки — цикл просто не выполнится, вернётся 0. Это общее свойство обхода: пустой список не особый случай, а вырожденный обычный.

**Ответ:** `list_sum` — тот же обход, что и `list_length`, только с накоплением в теле: `for (cur = head; cur != NULL; cur = cur->next) sum += cur->value;`. На списке `2 -> 4 -> 6 -> 8` программа печатает `length = 4` и `sum = 20`. Параметра `const Node *` достаточно, потому что функция только читает список и не переставляет голову (правило — Г9.Ч1.З7); пустой список обрабатывается тем же кодом и даёт 0.

**Вариант 2 (рекурсивный обход).** Список — рекурсивная структура («узел + список поменьше»), поэтому сумма естественно выражается рекурсией (§4.3): база — пустой список, шаг — значение головы плюс сумма хвоста.

```c
/* Node, push_front, print_list, list_length, list_free — как в §9.1.2 */

int list_sum(const Node *head)         /* та же сумма рекурсией */
{
    if (head == NULL) return 0;                    /* базовый случай: пустой список */
    return head->value + list_sum(head->next);     /* шаг: голова + сумма хвоста */
}
```

```
gcc -std=c17 -Wall -Wextra sumrec.c -o sumrec
./sumrec
```

```
2 -> 4 -> 6 -> 8 -> NULL
length = 4
sum    = 20
```

*Сравнение.* Результат тот же, а разница — в цене: цикл работает в одном кадре и на списке любой длины расходует фиксированное количество памяти, рекурсия же кладёт на стек вызовов по кадру на узел. На четырёх элементах это незаметно, на миллионе — переполнение стека (§4.3; тот же довод прозвучит в §9.3.2 про вырожденное дерево). Рекурсивная запись короче и ближе к определению структуры — она хороша как формулировка идеи и в «кустистых» структурах вроде дерева, где глубина мала; для линейного списка практический выбор — цикл.

### Г9.Ч1.З4

**Условие.** *(понимание)* В `list_free` следующий адрес запоминается **до** `free`. Программист «упростил»: `while (head != NULL) { free(head); head = head->next; }`. Назовите класс ошибки (§7.2.1), объясните, что именно читается неверно, и что покажет AddressSanitizer на таком коде.

**Решение.** Класс ошибки — **use-after-free** (обращение к освобождённой памяти, §7.2.1), точнее — чтение по висячему указателю. Разберём один виток цикла. `free(head)` возвращает системе весь блок узла — вместе с обоими полями, `value` и `next`. Следующая строка `head = head->next` **читает поле `next` из этого блока**: указатель `head` ещё цел (переменная-то своя, в кадре функции), но память, на которую он смотрит, уже не принадлежит программе. Прочитанное значение — что угодно: старый адрес, если аллокатор не успел ничего перезаписать, или служебные данные аллокатора, которые он кладёт в свободные блоки. При «повезло» цикл пройдёт до конца и внешне сработает; при «не повезло» — освободит мусорный адрес и упадёт. Это ровно то UB, о котором предупреждает §7.2.1: программа не обязана падать сразу, но правильной она от этого не становится.

Первым здесь высказывается сам компилятор — оба события (`free` и использование) видны ему в одной функции:

```c
void list_free_bad(Node *head)         /* «упрощённая» версия — сломанная */
{
    while (head != NULL) {
        free(head);
        head = head->next;             /* чтение поля из освобождённого узла */
    }
}
```

AddressSanitizer же ловит ошибку не по тексту, а по факту доступа: в момент `free` он «отравляет» блок и проверяет каждое последующее обращение. Прогон трёхэлементного списка (Linux-контур):

Отчёт читается как протокол: **READ of size 8** — читались 8 байт (указатель `next`) по адресу, отстоящему на 8 байт от начала 16-байтного блока узла, то есть именно поле `next`; ниже — где блок был освобождён (строка 22, предыдущий виток) и где выделен (`push_front`). Программа после этого аварийно завершается (`ABORTING`) — ASan останавливает выполнение на первой же ошибке.

**Ответ:** это use-after-free (§7.2.1): после `free(head)` выражение `head->next` читает поле `next` **из уже освобождённого узла** — 8 байт, которые программе больше не принадлежат; значение оттуда произвольно, и дальнейший цикл может освободить мусорный адрес. GCC 15.2 предупреждает об этом статически (`-Wuse-after-free`, оба события в одной функции), а AddressSanitizer сообщает `heap-use-after-free`, показывая `READ of size 8` по адресу «8 байт внутри 16-байтного блока», строку чтения (`head = head->next`), строку освобождения и строку выделения — и аварийно завершает программу. Правильный порядок — «запомнить `next` → освободить узел → шагнуть», как в `list_free` из §9.1.2.

### Г9.Ч1.З5

**Условие.** *(понимание)* В `insert_after` поменяли строки местами: сначала `pos->next = n;`, потом `n->next = pos->next;`. Нарисуйте стрелки после каждого присваивания и опишите два последствия (что стало с хвостом списка; что произойдёт при следующем обходе). Почему AddressSanitizer здесь может и не сработать?

**Решение.** Пусть список `[1] ─▶ [2] ─▶ [3]`, `pos` — узел `[2]`, вставляем `25`. Прорисуем стрелки.

```
исходно:            [1] ─▶ [2] ─▶ [3] ─▶ NULL
                            ▲
                           pos          новый узел [25] (next ещё не задан)

шаг 1: pos->next = n
                    [1] ─▶ [2] ─▶ [25]           а [3] больше НИКТО не держит
                                    (next мусор)

шаг 2: n->next = pos->next
       но pos->next — это уже [25]!
                    [1] ─▶ [2] ─▶ [25] ─┐
                                    ▲───┘   узел замкнулся сам на себя
```

Ключ к ошибке — во втором присваивании: `pos->next` вычисляется **после** первого, а там уже лежит адрес нового узла. Поэтому `n->next = pos->next` означает `n->next = n`. Оба последствия видны на схеме:

1. **Хвост потерян.** Адрес узла `[3]` хранился ровно в одном месте — в `pos->next`; первое присваивание его затёрло. Узел жив в куче, но недостижим — классическая утечка (§7.1.4), и с ним утёк бы весь хвост, будь он длиннее.
2. **Обход зацикливается.** `[25].next == [25]`, поэтому `for (cur = head; cur != NULL; cur = cur->next)` никогда не встретит `NULL`: дойдя до `[25]`, он будет вечно печатать `25`. `list_length` не вернётся, `list_free` зациклится (а если бы дошёл до `free`, освободил бы один и тот же узел дважды — double free).

Проверяем на программе; полный обход заменён обходом с ограничителем, иначе печать не закончилась бы:

```c
/* Node, push_front — как в §9.1.2 */

int insert_after_bad(Node *pos, int x)     /* строки переставлены местами */
{
    Node *n = malloc(sizeof *n);
    if (n == NULL) return -1;
    n->value = x;
    pos->next = n;         /* сначала pos цепляется к новому */
    n->next = pos->next;   /* ...и новый подхватывает УЖЕ СЕБЯ */
    return 0;
}

void print_first(const Node *head, int limit)   /* обход с ограничителем */
{
    const Node *cur = head;
    for (int i = 0; i < limit && cur != NULL; i++, cur = cur->next)
        printf("%d -> ", cur->value);
    printf("...\n");
}
```

./badorder
```

```

pos->next->next   = node 25 itself
1 -> 2 -> 25 -> 25 -> 25 -> 25 -> ...
```

Теперь про санитайзер. AddressSanitizer следит за **доступами к памяти**: чтение или запись вне блока, обращение к освобождённому блоку. Здесь ничего этого нет: все узлы выделены и живы, все чтения и записи идут по своим полям. Ошибка — чисто логическая: неправильное значение указателя. Единственное, что ASan (точнее, встроенный в него LeakSanitizer) заметит на выходе, — неосвобождённые блоки; и то лишь потому, что зациклённый список нельзя корректно освободить. Valgrind на той же программе классифицирует их точнее:

```
$ valgrind --leak-check=full ./badorder
```

==...==

Ни строчки об `Invalid read`/`Invalid write` — только утечка (`definitely lost` — недостижимый узел `[3]` и голова списка; `indirectly lost` — то, что висело на них).

**Ответ:** после первого присваивания `pos->next` указывает на новый узел, поэтому второе присваивание читает уже новое значение и даёт `n->next = n`. Последствия: (1) хвост `[3]` отцеплен и недостижим — утечка (при длинном хвосте утекает весь остаток списка); (2) узел `25` замкнут сам на себя, и любой обход по `next` не находит `NULL` — бесконечный цикл, а `list_free` на таком списке зациклится (или дважды освободит один узел). AddressSanitizer здесь может смолчать, потому что **ошибочных обращений к памяти нет**: все узлы живы, все поля свои; он ловит нарушения доступа, а не неверную логику связывания. Проявится ошибка лишь косвенно — как утечка на выходе (`definitely lost`/`indirectly lost` у Valgrind) или как зависание программы. Правильный порядок — «сначала новый подхватывает хвост, потом старый цепляется к новому».

### Г9.Ч1.З6

**Условие.** *(понимание)* Заполните таблицу «вектор против списка» для операций: доступ по индексу, вставка в начало, вставка в конец, вставка после найденного узла, поиск по значению. Для каждой клетки — краткое обоснование в одно предложение (что именно приходится делать).

**Решение.** Считаем «шаги» так же, как §9.1.3: сколько элементов приходится потрогать; `n` — число элементов, `i` — номер позиции.

| операция | вектор | список |
|---|---|---|
| доступ по индексу `i` | **1 шаг** — адрес элемента вычисляется арифметикой `data + i` (§6.2), трогать соседей не нужно | **~`i` шагов** — адреса `i`-го узла нигде нет, к нему идут по цепочке `next` от головы |
| вставка в начало | **~`n` шагов** — все элементы сдвигаются на ячейку вправо, чтобы освободить нулевую | **2 присваивания** — новый узел смотрит на старую голову, голова становится новой; существующие узлы не трогаются |
| вставка в конец | **1 шаг в среднем** — запись в `data[len]`, изредка `realloc` с копированием (амортизированно дёшево, Г9.Ч1.З1) | **~`n` шагов** — надо дойти по `next` до последнего узла (1 шаг, если хранить отдельный указатель на хвост, — так делает очередь §9.2.2) |
| вставка после найденного узла/индекса | **~`n − i` шагов** — весь хвост правее позиции сдвигается на ячейку | **2 присваивания** — новый узел подхватывает `pos->next`, `pos` цепляется к новому (§9.1.3) |
| поиск по значению | **до `n` шагов** — сравнение подряд, пока не совпадёт | **до `n` шагов** — тот же перебор, только шаг делается по `next` |

Две вещи стоит проговорить отдельно. Первая: в строках «вставка» у списка написано «2 присваивания» — при условии, что узел `pos` **уже найден**; если его ещё надо найти, к цене добавляется поиск (до `n` шагов), и суммарно список не выигрывает. Именно поэтому список хорош там, где позиция известна заранее (итератор, указатель на узел), а не там, где к ней всякий раз приходится идти. Вторая: таблица считает шаги, а не время. У вектора элементы лежат подряд и попадают в кеш процессора целыми пачками, у списка узлы разбросаны по куче — на равном числе шагов вектор нередко оказывается быстрее (§9.1.3, последний подводный камень).

**Ответ:** сведено в таблицу выше. Правило выбора: **доступ по номеру и добавление в конец — вектор; частые вставки и удаления у известного места — список**; поиск по значению одинаково линеен у обоих и потому не является аргументом. По умолчанию (когда профиль операций заранее не известен) берут вектор — за счёт непрерывной памяти он выигрывает на практике даже там, где формально равен.

### Г9.Ч1.З7

**Условие.** *(понимание)* Почему `push_front` принимает `Node **head`, а `list_length` — достаточно `const Node *head`? Сформулируйте правило: когда функции списка нужен адрес головы, а когда — только её значение. Что молча сломается, если `push_front` принять `Node *head`?

**Решение.** Разница ровно в том, что функция делает с самой переменной-головой. `list_length` только **читает** список: ей нужен адрес первого узла, чтобы начать обход, — то есть значение головы; менять переменную вызывающего она не собирается, поэтому `const Node *` (const заодно фиксирует в сигнатуре: список не будет изменён, §6.3.1). `push_front` же **переставляет саму голову**: после вставки переменная `list` в `main` обязана указывать на новый узел. Аргументы в C передаются по значению (§4.2.1) — функция получает копию; чтобы изменить переменную вызывающего, нужен её адрес, то есть `Node **head`, и запись `*head = n` (§6.3.2).

Правило: **адрес головы (`Node **`) нужен тогда и только тогда, когда операция может изменить сам указатель-голову** — вставка в начало, удаление (если удаляется первый узел), очистка списка «в NULL». Если операция лишь ходит по узлам (длина, сумма, печать, поиск) или меняет **поля** узлов, но не голову, достаточно значения — `Node *`, а при чтении и вовсе `const Node *`.

Что сломается в версии по значению — не догадка, а прогон:

```c
int push_front_bad(Node *head, int x)      /* принимает КОПИЮ головы */
{
    Node *n = malloc(sizeof *n);
    if (n == NULL) return -1;
    n->value = x;
    n->next = head;
    head = n;                              /* меняется только локальная копия */
    return 0;
}

int main(void)
{
    Node *list = NULL;
    if (push_front_bad(list, 1) != 0) return 1;
    if (push_front_bad(list, 2) != 0) return 1;
    printf("list == NULL: %s\n", list == NULL ? "yes" : "no");
    print_list(list);
    return 0;
}
```

./byvalue
```

```

```

Программа собирается **без единого предупреждения** и не падает — в этом и коварство: `push_front_bad` честно возвращает 0 («успех»), а список остаётся пустым. Каждый выделенный узел при этом теряется вместе с локальной копией: LeakSanitizer на двух вставках сообщает

```

```

```

    #0 … in malloc …
    #1 … in push_front_bad byvalue.c:11
    #2 … in main byvalue.c:30
    …
SUMMARY: AddressSanitizer: 32 byte(s) leaked in 2 allocation(s).
```

**Ответ:** `push_front` меняет саму переменную-голову вызывающего, а параметры в C — копии, поэтому ей нужен адрес этой переменной (`Node **head`, присваивание `*head = n`); `list_length` только читает узлы, начиная с головы, и ей хватает значения — `const Node *head` (const дополнительно обещает, что список не изменится). Правило: **`Node **` — если операция способна переставить голову** (вставка в начало, удаление первого узла, очистка); `Node *`/`const Node *` — если операция только ходит по списку или правит поля узлов. Приняв `Node *head`, `push_front` изменит лишь свою копию: список вызывающего останется прежним (в примере — пустым), функция при этом отрапортует об успехе, компилятор промолчит, а каждый выделенный узел утечёт (`32 byte(s) leaked in 2 allocation(s)`) — ошибка тихая, и находится она санитайзером либо тестом «после вставки список не пуст».

### Г9.Ч1.З8

**Условие.** *(прикладное)* Допишите вектору операции `int vec_last(const Vec *v, int *out)` (посмотреть последний элемент, не снимая) и `int vec_pop(Vec *v, int *out)` (снять последний), обе возвращают `-1` на пустом векторе. Продемонстрируйте: `push` 1..4, `last`, два `pop` — печатая значения и `len`.

**Решение.** Обе операции — про **последний занятый** элемент, а он лежит по индексу `len - 1` (не `len`: там начинается неиспользуемый запас, §9.1.1). Отличие только в том, трогают ли они `len`: `vec_last` не меняет структуру вовсе (потому `const Vec *`), `vec_pop` уменьшает длину — элемент «снят», хотя байты в блоке остались (ёмкость не сокращается, память под вектором не перевыделяется). Пустота проверяется первой строкой: `len == 0` — возвращаем `-1`, ничего не записав в `*out`. Значение уходит через выходной параметр, а `return` отдан под код результата — приём §7.1.2.

```c
/* Vec, vec_init, vec_push, vec_free — как в §9.1.1 */

int vec_last(const Vec *v, int *out)   /* посмотреть последний, не снимая */
{
    if (v->len == 0) return -1;
    *out = v->data[v->len - 1];        /* верхушка — len-1, не len */
    return 0;
}

int vec_pop(Vec *v, int *out)          /* снять последний */
{
    if (v->len == 0) return -1;
    *out = v->data[--v->len];          /* уменьшили длину и отдали бывший последний */
    return 0;
}

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;

    int empty;
    printf("last on empty: %d\n", vec_last(&v, &empty));
    printf("pop  on empty: %d\n", vec_pop(&v, &empty));

    for (int i = 1; i <= 4; i++)
        if (vec_push(&v, i) != 0) { vec_free(&v); return 1; }
    printf("after push 1..4: len=%d cap=%d\n", v.len, v.cap);

    int x;
    if (vec_last(&v, &x) == 0) printf("last = %d, len=%d\n", x, v.len);
    if (vec_pop(&v, &x) == 0)  printf("pop  = %d, len=%d\n", x, v.len);
    if (vec_pop(&v, &x) == 0)  printf("pop  = %d, len=%d\n", x, v.len);

    vec_free(&v);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra veclast.c -o veclast
./veclast
```

```
last on empty: -1
pop  on empty: -1
after push 1..4: len=4 cap=4
last = 4, len=4
pop  = 4, len=3
pop  = 3, len=2
```

Видно главное различие: `last` вернул 4 и оставил `len = 4`, а `pop` вернул то же 4 и уменьшил `len` до 3 — «посмотреть» и «снять» это разные операции (смешивать их — типичная ошибка §9.2.1). Ёмкость всё время остаётся 4: `pop` не освобождает память, блок вернётся системе только в `vec_free`.

**Ответ:** обе функции работают с индексом `len - 1` и первой же строкой проверяют пустоту, возвращая `-1`; `vec_last` не меняет ничего (сигнатура с `const Vec *`), `vec_pop` дополнительно уменьшает `len` (`v->data[--v->len]`). Демонстрация: на пустом векторе обе дали `-1`; после `push 1..4` — `last = 4` при `len = 4`, затем `pop = 4` (`len = 3`) и `pop = 3` (`len = 2`). Ёмкость `cap` при снятии не уменьшается: `pop` двигает только границу занятого.

### Г9.Ч1.З9

**Условие.** *(прикладное)* Напишите `int push_back(Node **head, int x)` — вставку в **конец** списка (отдельно обработайте пустой список; иначе дойдите до хвоста обходом). Постройте список `1 -> 2 -> 3` тремя `push_back` и напечатайте. Какова цена такой вставки по таблице З6?

**Решение.** Новый узел в любом случае становится последним, поэтому его `next` — `NULL`. Дальше два случая. Пустой список: цеплять узел не к чему, он сам становится головой — и это меняет переменную вызывающего, ради чего функции и нужен `Node **head` (Г9.Ч1.З7). Непустой: голову менять не надо, но нужно найти последний узел — обходом «пока `cur->next != NULL`». Обратите внимание на условие цикла: оно останавливает нас **на** последнем узле, а не за ним (`cur != NULL` увёл бы `cur` в `NULL`, и цеплять было бы некуда).

```c
/* Node, push_front, print_list, list_free — как в §9.1.2 */

int push_back(Node **head, int x)      /* вставка в конец */
{
    Node *n = malloc(sizeof *n);
    if (n == NULL) return -1;
    n->value = x;
    n->next = NULL;                    /* новый узел — последний */

    if (*head == NULL) {               /* особый случай: список пуст */
        *head = n;
        return 0;
    }
    Node *cur = *head;                 /* иначе доходим до хвоста обходом */
    while (cur->next != NULL)
        cur = cur->next;
    cur->next = n;
    return 0;
}

int main(void)
{
    Node *list = NULL;
    for (int x = 1; x <= 3; x++)
        if (push_back(&list, x) != 0) { list_free(list); return 1; }
    print_list(list);
    list_free(list);
    list = NULL;
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra pushback.c -o pushback
./pushback
```

```

Порядок теперь совпадает с порядком вставки — в отличие от `push_front` (Г9.Ч1.З2).

**Ответ:** `push_back` создаёт узел с `next == NULL`, а дальше различает два случая: пустой список (`*head = n` — голова переставляется, для этого и нужен `Node **`) и непустой (обход `while (cur->next != NULL)` до последнего узла, затем `cur->next = n`). Три вызова дают `1 -> 2 -> 3 -> NULL` — порядок совпадает с порядком вставки. Цена по таблице Г9.Ч1.З6: **~`n` шагов** — сама перецепка стоит одно присваивание, но добраться до хвоста можно только пройдя весь список; вставка `n` элементов подряд таким способом обойдётся примерно в `n²/2` шагов. Лечится это не переписыванием функции, а хранением указателя на хвост — так устроена очередь §9.2.2, где `enqueue` стоит 2 присваивания.

**Вариант 2 (через готовые операции главы).** Обе ветки — это уже написанные операции: пустой список — `push_front`, непустой — `insert_after` по последнему узлу (§9.1.3). Остаётся найти хвост:

```c
/* Node, push_front, insert_after, print_list, list_free — как в §9.1.2–§9.1.3 */

Node *list_last(Node *head)            /* последний узел или NULL для пустого */
{
    if (head == NULL) return NULL;
    while (head->next != NULL)
        head = head->next;
    return head;
}

int push_back(Node **head, int x)      /* через готовые операции главы */
{
    Node *tail = list_last(*head);
    if (tail == NULL)                  /* список пуст — это вставка в начало */
        return push_front(head, x);
    return insert_after(tail, x);      /* иначе — вставка после хвоста (§9.1.3) */
}
```

*Сравнение.* Вариант 2 не содержит ни одного `malloc` и ни одной перецепки — вся работа с памятью и стрелками спрятана в проверенных функциях, а `push_back` выражает только логику «в конец = после последнего». Это дешевле в сопровождении: исправление в `insert_after` автоматически достаётся и `push_back`, а нового места для ошибки в порядке присваиваний (Г9.Ч1.З5) просто нет. Плата — лишняя польза от `list_last` как отдельной функции и один дополнительный вызов; по числу шагов оба варианта одинаковы (проход до хвоста в обоих). Первый вариант предпочтителен, когда таких готовых операций ещё нет или когда важно видеть всю механику в одном месте; второй — в растущем коде, где переиспользование ценнее.

### Г9.Ч1.З10

**Условие.** *(прикладное)* Напишите `int remove_all(Node **head, int x)` — удалить **все** узлы со значением `x`, вернуть их число. Постройте `1 -> 3 -> 1 -> 2 -> 1`, удалите все единицы (ожидается счётчик 3 и список `3 -> 2`), напечатайте до и после. Внимание на пары «голова/середина» и «запомнить `next` до `free`»; проверьте под санитайзером.

**Решение.** Отличие от `list_remove` (§9.1.3) — цикл не прерывается на первом совпадении, а идёт до конца списка; отсюда два требования. Первое: адрес следующего узла нужно взять **до** возможного `free` — иначе на следующем витке мы читали бы `cur->next` из освобождённой памяти (ровно ошибка Г9.Ч1.З4). Второе: `prev` двигается **только на уцелевших** узлах — если сдвинуть его на удаляемый, следующая перецепка пойдёт через освобождённый узел. Голова обрабатывается той же веткой, что и в §9.1.3: `prev == NULL` означает «удаляется первый узел», и переставляется сам `*head` — а при `1 -> 3 -> 1 -> 2 -> 1` это случается сразу, на первом же элементе.

```c
/* Node, push_front, print_list, list_free — как в §9.1.2 */

int remove_all(Node **head, int x)     /* удалить все узлы со значением x */
{
    int removed = 0;
    Node *prev = NULL;
    Node *cur = *head;
    while (cur != NULL) {
        Node *next = cur->next;        /* запомнить ДО возможного free */
        if (cur->value == x) {
            if (prev == NULL)
                *head = next;          /* удаляется голова */
            else
                prev->next = next;     /* перецепка мимо cur */
            free(cur);
            removed++;
        } else {
            prev = cur;                /* prev двигается только на уцелевших */
        }
        cur = next;
    }
    return removed;
}

int main(void)
{
    Node *list = NULL;
    int init[] = {1, 2, 1, 3, 1};      /* push_front в обратном порядке */
    for (int i = 0; i < 5; i++)
        if (push_front(&list, init[i]) != 0) { list_free(list); return 1; }

    printf("before:  ");
    print_list(list);
    int n = remove_all(&list, 1);
    printf("removed: %d\n", n);
    printf("after:   ");
    print_list(list);

    list_free(list);
    list = NULL;
    return 0;
}
```

**Ответ:** однопроходный цикл с парой `prev`/`cur`, где на каждом витке первым делом сохраняется `next`, удаляемый узел перецепляется (через `*head` для головы или `prev->next` для остальных) и освобождается, а `prev` двигается только на уцелевших узлах. На списке `1 -> 3 -> 1 -> 2 -> 1` функция вернула **3** и оставила `3 -> 2` — совпадает с ожиданием условия. AddressSanitizer молчит, Valgrind сообщает `All heap blocks were freed -- no leaks are possible`: удалённые узлы освобождены сразу, уцелевшие — финальным `list_free`.

**Вариант 2 (повторным вызовом `list_remove`).** Удаление одного узла уже написано в §9.1.3 — можно просто повторять его, пока оно находит совпадения:

```c
/* Node, push_front, print_list, list_remove, list_free — как в §9.1.2–§9.1.3 */

int remove_all(Node **head, int x)     /* повторяем готовое удаление одного */
{
    int removed = 0;
    while (list_remove(head, x) == 1)  /* пока находится хоть один */
        removed++;
    return removed;
}
```

```
gcc -std=c17 -Wall -Wextra removeall2.c -o removeall2
./removeall2
```

```
before:  1 -> 3 -> 1 -> 2 -> 1 -> NULL
removed: 3
after:   3 -> 2 -> NULL
```

*Сравнение.* Вариант 2 короче втрое и не может ошибиться ни в `prev`, ни в порядке «запомнить → освободить»: всё это уже отлажено в `list_remove`. Плата — цена: каждый вызов начинает поиск заново от головы, поэтому при `k` удалениях список просматривается `k + 1` раз (~`k·n` шагов против одного прохода ~`n` у основного варианта). На пяти узлах разница неощутима, на списке в миллион узлов, где удаляется половина, — катастрофична. Правило выбора обычное: переиспользование, пока данных мало или удаления редки; однопроходная версия — когда удаления массовые. Заодно вариант 2 — хорошая иллюстрация к тому, что «переиспользовать готовое» не всегда бесплатно.

## Часть 9.2. Стек и очередь

### Г9.Ч2.З1

**Условие.** Со стеком из §9.2.1: `push` 1, 2, 3, затем `pop` до пустоты, печатая снятое. Выпишите вывод заранее, проверьте программой; напечатайте `stack_empty` до первого `push` и после последнего `pop`.

**Решение.** Предсказание — прямо из инварианта LIFO: `pop` отдаёт элементы в порядке, обратном `push`, значит после `push` 1, 2, 3 снятие даст 3, 2, 1. `stack_empty` до первого `push` — 1 (стек только что инициализирован, `len == 0`), после последнего `pop` — снова 1 (все элементы сняты). Промежуточных значений быть не может: `pop` пустого стека возвращает `-1`, и цикл `while (stack_pop(...) == 0)` на этом останавливается.

```c
/* Stack, stack_init, stack_push, stack_pop, stack_empty, stack_free —
   как в §9.2.1 */

int main(void)
{
    Stack s;
    if (stack_init(&s) != 0) return 1;
    printf("empty before push: %d\n", stack_empty(&s));

    for (int i = 1; i <= 3; i++)
        if (stack_push(&s, i) != 0) { stack_free(&s); return 1; }

    int x;
    while (stack_pop(&s, &x) == 0)
        printf("pop %d\n", x);

    printf("empty after pops: %d\n", stack_empty(&s));
    stack_free(&s);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra stack3.c -o stack3
./stack3
```

```

pop 3
pop 2
pop 1
empty after pops: 1
```

Предсказание совпало. Стоит заметить, где именно «спрятан» порядок: `stack_push` пишет в `data[len++]`, `stack_pop` читает `data[--len]` — обе операции работают с одним и тем же концом массива, и потому последний записанный элемент оказывается первым прочитанным. Никаких сдвигов при этом не происходит: элементы лежат на своих местах, двигается только граница `len`.

**Ответ:** вывод — `empty before push: 1`, затем `pop 3`, `pop 2`, `pop 1`, затем `empty after pops: 1`. Порядок снятия обратен порядку добавления (LIFO), потому что обе операции работают с верхушкой `data[len-1]`; `stack_empty` равен 1 и до первого `push`, и после последнего `pop` — оба раза `len == 0`, хотя во втором случае ёмкость уже выделена (память вернёт только `stack_free`).

### Г9.Ч2.З3

**Условие.** Для кольцевого буфера `CAP = 3` выполните на бумаге: `put 1`, `put 2`, `put 3`, `get`, `put 4` — после каждой операции выписывая массив `data`, `head`, `len` и вычисленный индекс хвоста `(head+len)%CAP`. Затем напечатайте эти поля программой и сверьте.

**Решение.** На бумаге. Старт — `Ring r = {0}`: `data = [0 0 0]`, `head = 0`, `len = 0`, хвост `(0+0)%3 = 0`. Дальше каждая операция затрагивает ровно одно число и одну ячейку:

| операция | что делает | `data` | `head` | `len` | хвост `(head+len)%3` |
|---|---|---|---|---|---|
| — (старт) | — | `[0 0 0]` | 0 | 0 | 0 |
| `put 1` | пишет в ячейку 0, `len++` | `[1 0 0]` | 0 | 1 | 1 |
| `put 2` | пишет в ячейку 1, `len++` | `[1 2 0]` | 0 | 2 | 2 |
| `put 3` | пишет в ячейку 2, `len++` | `[1 2 3]` | 0 | 3 | **0** (заворот) |
| `get` | отдаёт `data[0]` = 1, `head++`, `len--` | `[1 2 3]` | 1 | 2 | 0 |
| `put 4` | пишет в ячейку `(1+2)%3 = 0`, `len++` | `[4 2 3]` | 1 | 3 | 1 |

Два места, где легко ошибиться. Первое: после `put 3` буфер полон, и вычисленный «хвост» равен 0 — тому же индексу, что и голова; сам по себе он ничего не значит, класть по нему нельзя, потому что `len == CAP` (именно поэтому «полон» и «пуст» различаются по `len`, а не по совпадению индексов, — §9.2.2). Второе: `get` **не стирает** `data[0]`: единица остаётся в массиве, но перестаёт быть частью очереди — логическое содержимое задают `head` и `len`, а не байты. Затрётся она только следующей записью — что и происходит на `put 4`.

```c
/* Ring, ring_put, ring_get — как в §9.2.2 (пример 2), но CAP = 3 */

void dump(const Ring *r, const char *op)
{
    printf("%-7s data = [%d %d %d]  head=%d len=%d  tail=(head+len)%%CAP=%d\n",
           op, r->data[0], r->data[1], r->data[2],
           r->head, r->len, (r->head + r->len) % CAP);
}

int main(void)
{
    Ring r = {0};                 /* всё обнулено: data, head, len */
    dump(&r, "start");

    ring_put(&r, 1); dump(&r, "put 1");
    ring_put(&r, 2); dump(&r, "put 2");
    ring_put(&r, 3); dump(&r, "put 3");

    int x;
    ring_get(&r, &x);
    printf("get -> %d\n", x);
    dump(&r, "get");

    ring_put(&r, 4); dump(&r, "put 4");
    return 0;
}
```

### Г9.Ч2.З5

**Условие.** *(понимание)* Уберите из очереди §9.2.2 поле `tail` (остался только `head`). Как теперь реализовать `enqueue` и сколько шагов он стоит на очереди из `n` элементов? Почему для очереди это плохо, а для стека на списке «хвост» не нужен вовсе?

**Решение.** Без `tail` адреса последнего узла в структуре нет, и получить его можно единственным способом — пройти по цепочке `next` от головы до узла, у которого `next == NULL`. То есть `enqueue` превращается в `push_back` из Г9.Ч1.З9: особый случай пустой очереди (узел становится головой) плюс обход до хвоста. Замерим цену счётчиком пройденных узлов:

```c
typedef struct {
    Node *head;        /* поля tail больше нет */
} Queue1;

int enqueue1(Queue1 *q, int x, int *steps)   /* steps — счётчик пройденных узлов */
{
    Node *n = malloc(sizeof *n);
    if (n == NULL) return -1;
    n->value = x;
    n->next = NULL;

    if (q->head == NULL) {                   /* пустая очередь — узел становится головой */
        q->head = n;
        return 0;
    }
    Node *cur = q->head;                     /* иначе идём до хвоста ПО ВСЕЙ очереди */
    while (cur->next != NULL) {
        cur = cur->next;
        (*steps)++;
    }
    (*steps)++;
    cur->next = n;
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra notail.c -o notail
./notail
```

```
enqueue 1 into queue of 0: steps = 0
enqueue 2 into queue of 1: steps = 1
enqueue 3 into queue of 2: steps = 2
enqueue 4 into queue of 3: steps = 3
enqueue 5 into queue of 4: steps = 4
dequeue 1
dequeue 2
dequeue 3
dequeue 4
dequeue 5
```

Счётчик подтверждает: вставка в очередь из `n` элементов стоит ровно `n` шагов, тогда как с полем `tail` — два присваивания независимо от длины. Для очереди это плохо системно: `enqueue` — не разовая, а **основная** её операция, и цена, растущая вместе с длиной очереди, отравляет весь сценарий использования. Наполнение очереди `n` элементами обойдётся в `0 + 1 + … + (n−1) ≈ n²/2` шагов: тысяча элементов — полмиллиона шагов вместо двух тысяч присваиваний. Хуже того, дорожает именно длинная очередь, то есть ровно тот случай, ради которого структура и заводится (накопился поток задач — обработка стала квадратично медленной).

Стеку на списке хвост не нужен по другой причине: у стека **оба** конца операций совпадают. `push` — вставка в начало (`push_front`, §9.1.2, 2 присваивания), `pop` — снятие первого узла (голова переставляется на `next`, узел освобождается). Обе операции трогают только голову, до которой всегда есть прямой указатель; последний узел стека — это его «дно», к которому обращаться просто незачем. Очередь же по определению работает с двумя разными концами — оттого и нуждается во втором указателе.

**Ответ:** без `tail` `enqueue` вынужден каждый раз доходить до последнего узла обходом (плюс отдельная ветка для пустой очереди) — это `n` шагов на очереди из `n` элементов, что подтверждает счётчик (0, 1, 2, 3, 4 при последовательном наполнении); наполнение `n` элементами стоит ~`n²/2` шагов вместо ~`n`. Для очереди это плохо потому, что вставка в хвост — её штатная, самая частая операция, и её цена растёт с длиной очереди (тем сильнее, чем очередь длиннее). Стеку на списке хвост не нужен вовсе: и `push`, и `pop` работают с головой — вторая «точка входа» ему просто не требуется.

### Г9.Ч2.З6

**Условие.** *(понимание)* В `dequeue` удалили строку `if (q->head == NULL) q->tail = NULL;`. Постройте минимальную последовательность операций, приводящую к use-after-free, и объясните по шагам, где именно происходит запись в освобождённую память. Каким инструментом из §7.2.2 это ловится и как будет помечено в отчёте?

**Решение.** Минимальная последовательность — **три** операции: `enqueue(10)`, `dequeue`, `enqueue(20)`. Меньше не выйдет: нужно опустошить очередь (иначе `tail` остаётся на живом узле) и после этого положить хотя бы один элемент (иначе висячий указатель никто не потревожит).

По шагам, с состоянием обоих указателей:

1. `enqueue(&q, 10)` — очередь была пуста (`tail == NULL`), поэтому оба указателя ставятся на новый узел `A`: `head == tail == A`.
2. `dequeue(&q, &x)` — берётся голова `A`, `q->head = A->next`, то есть `NULL`. **Пропущенная строка** должна была заметить это и сбросить `q->tail`; без неё `tail` продолжает хранить адрес `A`. Затем `free(A)` — блок возвращён системе. Состояние: `head == NULL` (очередь «пуста»), `tail == A` — **висячий указатель** (§7.2.1).
3. `enqueue(&q, 20)` — проверка `if (q->tail == NULL)` не срабатывает (там адрес `A`!), поэтому исполняется ветка «очередь не пуста»: `q->tail->next = n`. Это и есть **запись в освобождённую память** — 8 байт по адресу поля `next` внутри блока `A`, который уже не принадлежит программе. Дальше `q->tail = n`, и очередь остаётся в рассогласованном состоянии: `head == NULL` при непустом `tail`, то есть узел `20` потерян (утечка) и никогда не будет извлечён.

Обратите внимание: ломается не `dequeue`, где убрали строку, а **следующий** `enqueue` — типичная отложенная авария, из-за которой такие ошибки трудно связать с их причиной без инструментов.

```c
int dequeue_bad(Queue *q, int *out)    /* строка сброса tail удалена */
{
    if (q->head == NULL) return -1;
    Node *n = q->head;
    *out = n->value;
    q->head = n->next;
    /* if (q->head == NULL) q->tail = NULL;  <-- УДАЛЕНО */
    free(n);
    return 0;
}

int main(void)
{
    Queue q;
    queue_init(&q);

    int x;
    if (enqueue(&q, 10) != 0) return 1;    /* head = tail = узел A */
    if (dequeue_bad(&q, &x) != 0) return 1;/* head = NULL, tail — на освобождённом A */
    printf("dequeued %d\n", x);
    if (enqueue(&q, 20) != 0) return 1;    /* q->tail->next = ... — запись в A */
    printf("done\n");
    return 0;
}
```

Компилятор на этой программе молчит: `free` и обращение разнесены по разным функциям, и статический анализ след теряет (разбор — Г7.Ч2.З4). Ловится ошибка **рантайм-инструментами из §7.2.2** — AddressSanitizer или Valgrind. ASan:

### Г9.Ч2.З7

**Условие.** *(понимание)* Протрассируйте `balanced` из §9.2.1 на строках `"({[]})"` и `"([)]"`: для каждого символа выпишите операцию (push/pop/сверка) и содержимое стека после неё. В какой момент второй тест проваливается? Почему очередь вместо стека здесь не сработала бы (какая скобка должна закрываться первой)?

**Решение.** Трассировка вручную; содержимое стека пишем снизу вверх.

`"({[]})"`:

| символ | операция | стек после |
|---|---|---|
| `(` | push `(` | `(` |
| `{` | push `{` | `({` |
| `[` | push `[` | `({[` |
| `]` | pop → `[`, сверка `[`/`]` — совпало | `({` |
| `}` | pop → `{`, сверка `{`/`}` — совпало | `(` |
| `)` | pop → `(`, сверка `(`/`)` — совпало | пусто |

Конец строки: стек пуст, незакрытых нет → результат 1.

`"([)]"`:

| символ | операция | стек после |
|---|---|---|
| `(` | push `(` | `(` |
| `[` | push `[` | `([` |
| `)` | pop → `[`, сверка `[`/`)` — **не совпало** | `(` |
| `]` | не рассматривается: цикл уже остановлен | — |

Инструментированная версия (тот же алгоритм плюс печать) подтверждает трассировку дословно:

```c
/* Stack и его операции, match, balanced — как в §9.2.1;
   добавлена печать стека после каждого шага */

void show(const Stack *st)             /* содержимое стека снизу вверх */
{
    printf("stack \"");
    for (int i = 0; i < st->len; i++)
        printf("%c", st->data[i]);
    printf("\"");
}
```

gcc -std=c17 -Wall -Wextra trace.c -o trace
./trace
```

```

  '(': push  -> stack "("
  '{': push  -> stack "({"
  '[': push  -> stack "({["
  ']': pop '[', match=1 -> stack "({"
  '}': pop '{', match=1 -> stack "("
  ')': pop '(', match=1 -> stack ""
result = 1
"([)]":
  '(': push  -> stack "("
  '[': push  -> stack "(["
  ')': pop '[', match=0 -> stack "("

```

Второй тест проваливается на **третьем символе** — закрывающей `)`: снятая с верхушки скобка это `[`, а закрывают круглой, `match` возвращает 0, флаг `ok` сбрасывается и цикл прекращается (оставшийся символ `]` даже не рассматривается).

Теперь про очередь. Вложенность означает: **последняя открытая скобка должна закрыться первой**. В строке `"([)]"` последней открыли `[`, значит первой обязана закрыться `]`; встретив `)`, алгоритм и обнаруживает нарушение. Стек отдаёт именно последний положенный элемент — то есть ровно ту скобку, которую сейчас и надо закрыть. Очередь отдала бы **первую** открытую: на `"([)]"` она вернула бы `(`, сверка `(`/`)` совпала бы, потом на `]` она вернула бы `[` — и совпало бы снова; неправильная строка была бы объявлена правильной. Хуже того, на корректной `"({[]})"` очередь выдала бы `(` против `]` и забраковала бы верную строку. Очередь помнит порядок поступления, а вложенность требует памяти о порядке **вложения** — это и есть LIFO.

**Ответ:** трассировки приведены в таблицах и подтверждены прогоном. `"({[]})"`: три `push` (стек `(`, `({`, `({[`), затем три `pop` со сверками, каждая совпадает, стек пустеет — результат 1. `"([)]"`: `push (`, `push [`, затем на **третьем символе** `)` снимается `[`, сверка `[`/`)` не проходит — тест проваливается именно здесь, результат 0. Очередь вместо стека не сработала бы, потому что первой обязана закрыться **последняя открытая** скобка (в `"([)]"` это `[`, ожидается `]`), а очередь отдаёт самую раннюю — она сочла бы `"([)]"` правильной строкой и, наоборот, забраковала бы корректную `"({[]})"`.

### Г9.Ч2.З8

**Условие.** *(прикладное)* Напишите `int reverse_in_place(char *s)`: затолкать все символы строки в стек, затем снять их обратно в ту же строку (стек перевернёт порядок). Проверьте на `"hello"` (ожидается `olleh`); не забудьте `stack_free` и прогон под санитайзером.

**Решение.** Алгоритм прямо следует из свойства LIFO: если сложить символы в стек по порядку и снимать до опустошения, они выйдут задом наперёд — остаётся класть их обратно в строку с нулевого индекса. Три детали. Первая: строку нужно менять на месте, поэтому в `main` она объявлена **массивом** `char word[] = "hello"` — строковый литерал править нельзя (§5.2.1, это UB). Вторая: символы кладутся в стек через `(unsigned char)` — на платформах со знаковым `char` символы с кодом > 127 иначе стали бы отрицательными числами (та же страховка, что в хеш-функции §9.3.1). Третья: `stack_free` вызывается на **каждом** пути выхода, включая ошибочный (нет памяти) — иначе редкая ветка утекала бы.

```c
/* Stack, stack_init, stack_push, stack_pop, stack_empty, stack_free —
   как в §9.2.1 */

int reverse_in_place(char *s)          /* перевернуть строку на месте через стек */
{
    Stack st;
    if (stack_init(&st) != 0) return -1;

    for (int i = 0; s[i] != '\0'; i++)              /* все символы — в стек */
        if (stack_push(&st, (unsigned char)s[i]) != 0) {
            stack_free(&st);
            return -1;
        }

    int c;
    for (int i = 0; stack_pop(&st, &c) == 0; i++)   /* обратно: LIFO переворачивает */
        s[i] = (char)c;

    stack_free(&st);
    return 0;
}

int main(void)
{
    char word[] = "hello";             /* массив, а не строковый литерал: правим на месте */
    printf("before: %s\n", word);
    if (reverse_in_place(word) != 0) return 1;
    printf("after:  %s\n", word);

    char empty[] = "";                 /* краевой случай: пустая строка */
    if (reverse_in_place(empty) != 0) return 1;
    printf("empty:  \"%s\"\n", empty);
    return 0;
}
```

```

```

Терминатор `'\0'` в стек не попадает (цикл останавливается на нём) и потому остаётся на своём месте в конце строки — длина не меняется, и запись символов ровно до неё безопасна. Пустая строка обрабатывается без единой особой проверки: первый цикл не выполняется, второй сразу получает `-1` от `stack_pop`. Прогон под ASan чист — стек освобождён.

**Ответ:** функция кладёт все символы строки в стек, затем снимает их и записывает обратно с начала — LIFO даёт разворот; `stack_free` вызывается на всех путях выхода, включая отказ по нехватке памяти. `"hello"` → `olleh`, пустая строка обрабатывается корректно (циклы вырождаются), терминатор `'\0'` не участвует и остаётся на месте. Под AddressSanitizer прогон чист.

**Вариант 2 (без стека, двумя индексами навстречу).** Разворот строки не требует вспомогательной структуры: достаточно менять местами симметричные символы, двигаясь с двух концов к середине.

```c
int reverse_in_place(char *s)          /* тот же результат двумя индексами навстречу */
{
    int n = 0;
    while (s[n] != '\0')               /* длина без string.h — как в гл. 5 */
        n++;
    for (int i = 0, j = n - 1; i < j; i++, j--) {
        char t = s[i];
        s[i] = s[j];
        s[j] = t;
    }
    return 0;
}

Практически он и есть правильный способ перевернуть строку. Ценность стековой версии — в другом: она демонстрирует LIFO в чистом виде и, в отличие от обмена индексами, обобщается на структуры, где «дойти до конца и пойти обратно» невозможно, — например, на односвязный список, который назад не читается. Задание намеренно требует стек: строка здесь — учебная модель такой структуры.

### Г9.Ч2.З9

**Условие.** *(прикладное)* Напишите `int is_palindrome(const char *s)`: каждый символ положить **и** в стек, **и** в очередь, затем попарно снимать (`pop` против `dequeue`) и сравнивать — стек читает слово с конца, очередь с начала. Проверьте на `"level"`, `"abba"`, `"hello"`. Освобождение обеих структур — на всех путях выхода.

**Решение.** Идея задания — стек и очередь как две «читалки» одной последовательности: заполняем их одинаково, а извлекаем — и получаем слово, прочитанное с конца (стек) и с начала (очередь). Палиндром — это в точности совпадение этих двух прочтений. Сравнивать достаточно все `n` пар: середина при нечётной длине сравнится сама с собой, что верно всегда.

Аккуратности требует освобождение: структур две, путей выхода три (нехватка памяти при заполнении, несовпадение, успех). Поэтому решение построено на флаге `ok` и единственной точке выхода после очистки — приём из `balanced` §9.2.1.

```c
/* Stack (§9.2.1) и Queue (§9.2.2) со своими операциями */

int is_palindrome(const char *s)       /* 1 — палиндром, 0 — нет, -1 — нет памяти */
{
    Stack st;
    Queue q;
    if (stack_init(&st) != 0) return -1;
    queue_init(&q);

    for (int i = 0; s[i] != '\0'; i++)              /* каждый символ — и туда, и туда */
        if (stack_push(&st, (unsigned char)s[i]) != 0 ||
            enqueue(&q, (unsigned char)s[i]) != 0) {
            stack_free(&st);
            queue_free(&q);
            return -1;
        }

    int ok = 1;
    int from_end, from_start;
    while (ok && stack_pop(&st, &from_end) == 0 && dequeue(&q, &from_start) == 0)
        if (from_end != from_start)                 /* стек — с конца, очередь — с начала */
            ok = 0;

    stack_free(&st);                   /* освобождение на любом пути выхода */
    queue_free(&q);
    return ok;
}

int main(void)
{
    const char *tests[] = {"level", "abba", "hello"};
    for (int i = 0; i < 3; i++) {
        int r = is_palindrome(tests[i]);
        if (r < 0) return 1;
        printf("%-6s -> %d\n", tests[i], r);
    }
    return 0;
}
```

```

```

Разберём `"hello"`: стек отдаёт `o, l, l, e, h`, очередь — `h, e, l, l, o`; первая же пара (`o` против `h`) различается, `ok` обнуляется и цикл прекращается. В стеке и очереди при этом остаются четыре неизвлечённых символа — и именно поэтому важно, что `stack_free` и `queue_free` вызываются безусловно после цикла: `queue_free` дочищает оставшиеся узлы (`dequeue` в цикле до опустошения), `stack_free` возвращает блок. Под ASan прогон чист на всех трёх словах.

**Ответ:** символы кладутся и в стек, и в очередь, затем извлекаются попарно: `pop` даёт слово с конца, `dequeue` — с начала, любое несовпадение обнуляет флаг. Результаты: `level -> 1`, `abba -> 1`, `hello -> 0` (различие обнаруживается на первой же паре `o`/`h`). Обе структуры освобождаются после цикла безусловно — в том числе когда цикл оборван досрочно и в них остались элементы; санитайзер чист.

**Вариант 2 (только стек: строка сама себе очередь).** Очередь в этой задаче дублирует то, что уже есть, — исходную строку, которую можно читать с начала обычным индексом:

```c
int is_palindrome(const char *s)       /* только стек: строка сама читается с начала */
{

        if (stack_push(&st, (unsigned char)s[i]) != 0) {

            return -1;

    int ok = 1;

    for (int i = 0; ok && stack_pop(&st, &from_end) == 0; i++)

### Г9.Ч2.З10

**Условие.** *(прикладное)* Считалка: `n` участников стоят по кругу, выбывает каждый `k`-й. Смоделируйте очередью: `k-1` раз «взять из головы и вернуть в хвост», затем «взять» — выбывший. Для `n = 7`, `k = 3` напечатайте порядок выбывания и уцелевшего (ожидается: выбывают `3 6 2 7 5 1`, уцелел `4`).

**Решение.** Очередь моделирует круг буквально: «взять из головы и вернуть в хвост» — это шаг по кругу мимо участника (он остаётся в игре, но уходит в конец), а `k`-е «взять» без возврата — выбывание. Круг не нужно хранить отдельно: он и есть очередь, замкнутая этим правилом. Цикл продолжается, пока не останется один участник, — счётчик `remaining` для этого достаточен (у нашей очереди нет операции «сколько элементов»).

```c
/* Node, Queue, queue_init, enqueue, dequeue, queue_free — как в §9.2.2 */

int main(void)
{
    enum { N = 7, K = 3 };
    Queue q;
    queue_init(&q);
    for (int i = 1; i <= N; i++)              /* участники встают в круг */
        if (enqueue(&q, i) != 0) { queue_free(&q); return 1; }

    int x;
    int remaining = N;
    printf("out:");
    while (remaining > 1) {
        for (int i = 0; i < K - 1; i++) {      /* k-1 человек: из головы — в хвост */
            if (dequeue(&q, &x) != 0 || enqueue(&q, x) != 0) { queue_free(&q); return 1; }
        }
        if (dequeue(&q, &x) != 0) { queue_free(&q); return 1; }   /* k-й выбывает */
        printf(" %d", x);
        remaining--;
    }
    printf("\n");
    if (dequeue(&q, &x) == 0)
        printf("survivor: %d\n", x);
    queue_free(&q);
    return 0;
}
```

Дальше круг продолжается с 4 — и следующим выбывает 6. Заметьте, что каждый выбывший освобождается сразу (`dequeue` делает `free` узла), а уцелевший в конце — финальным `dequeue`; `queue_free` в конце ничего уже не находит, но оставлен как страховка на путях ошибок.

**Вариант 2 (кольцевой буфер вместо очереди на списке).** Число участников известно заранее и в игре не растёт — значит, куча не нужна вовсе: круг помещается в кольцевой буфер ёмкости `N` (§9.2.2, пример 2), где «взять и вернуть» — это `ring_get` + `ring_put`.

```c
/* Ring, ring_put, ring_get — как в §9.2.2 (пример 2), CAP = N */

int main(void)
{
    Ring r = {0};
    for (int i = 1; i <= N; i++)              /* ёмкости ровно на всех участников */
        if (ring_put(&r, i) != 0) return 1;

    int x;
    printf("out:");
    while (r.len > 1) {
        for (int i = 0; i < K - 1; i++) {
            if (ring_get(&r, &x) != 0 || ring_put(&r, x) != 0) return 1;
        }
        if (ring_get(&r, &x) != 0) return 1;
        printf(" %d", x);
    }
    printf("\n");
    if (ring_get(&r, &x) == 0)
        printf("survivor: %d\n", x);
    return 0;                                  /* ни одного malloc — освобождать нечего */
}
```

### Г9.Ч3.З1

**Условие.** Вычислите вручную `hash("ab")` для функции §9.3.1 (`h = 31·h + код`, `NBUCKETS = 8`; коды: `a` = 97, `b` = 98), показав каждую итерацию. Проверьте программой.

### Г9.Ч3.З2

**Условие.** Вставьте в пустое BST по очереди `4, 2, 6, 1, 3, 5, 7`. Нарисуйте дерево (кто чей потомок), выпишите ожидаемый inorder-вывод, затем проверьте программой (`bst_inorder`). Какова высота получившегося дерева?

**Решение.** Каждая вставка — спуск от корня по сравнениям до свободного места. Проследим: `4` попадает в пустое дерево и становится корнем. `2 < 4` — влево, там пусто: левый потомок корня. `6 > 4` — вправо: правый потомок. `1`: `< 4` влево, `< 2` влево — левый потомок узла 2. `3`: `< 4` влево, `> 2` вправо — правый потомок узла 2. `5`: `> 4` вправо, `< 6` влево — левый потомок узла 6. `7`: `> 4` вправо, `> 6` вправо — правый потомок узла 6.

### Г9.Ч3.З3

**Условие.** Постройте BST из `5, 3, 8` и вызовите `bst_insert(&root, 3)` ещё раз. Что вернёт вызов и почему? Покажите программой, что inorder-вывод не изменился.

**Решение.** Наш вариант BST дубликаты не хранит — это решение проектировщика, зафиксированное в коде §9.3.2: спуск идёт, пока `x < value` (влево) или `x > value` (вправо), а если не выполнено ни то ни другое — значит, `x` равен значению узла, и функция возвращает `0`, ничего не изменив. Повторная вставка `3` спустится от корня `5` влево, встретит узел `3`, обнаружит равенство и остановится: ни `malloc`, ни изменения полей.

```c
/* TNode, bst_insert, bst_inorder, bst_free — как в §9.3.2 */

int main(void)
{
    TNode *root = NULL;
    int keys[] = {5, 3, 8};
    for (int i = 0; i < 3; i++)
        if (bst_insert(&root, keys[i]) < 0) { bst_free(root); return 1; }

    printf("inorder before: ");
    bst_inorder(root);
    printf("\n");

    int r = bst_insert(&root, 3);          /* дубликат */
    printf("bst_insert(&root, 3) = %d\n", r);

    printf("inorder after:  ");
    bst_inorder(root);
    printf("\n");

    printf("3 is still a leaf: %d\n",
           root->left->left == NULL && root->left->right == NULL);

    bst_free(root);
    return 0;
}
```

Это важно понимать буквально: `0` означает не ошибку, а «такое значение уже есть» (в отличие от `-1` — нехватки памяти и `1` — успешной вставки). Если бы задача требовала считать повторы, дерево пришлось бы проектировать иначе — с счётчиком в узле (§9.3.2, «типичные ошибки»).

Inorder до и после одинаков — `3 5 8`, узел `3` остался листом. Код возврата здесь несёт смысл: `1` — вставлен, `0` — уже был, `-1` — нет памяти; молчаливое игнорирование равных значений должно быть задокументированным решением, иначе «пропавшие» вставки станут сюрпризом.

### Г9.Ч3.З4

**Условие.** *(понимание)* Зачем в хеш-функции `% NBUCKETS`? Что станет с таблицей при `NBUCKETS = 1` — куда попадут все записи, во что выродится `table_get` и сколько шагов будет стоить поиск? Как связаны число корзин и длина средней цепочки?

**Решение.** Накопление `h = 31·h + код` даёт число, разбросанное по всему диапазону `unsigned` (для трёхбуквенного слова это уже десятки тысяч, для длинного — любое 32-битное значение). Использовать его как индекс массива `bucket[NBUCKETS]` нельзя: обращение `bucket[98262]` при восьми корзинах — выход далеко за пределы массива, то есть неопределённое поведение и порча чужой памяти. `% NBUCKETS` укладывает произвольное беззнаковое число в диапазон `0 … NBUCKETS-1` — ровно множество допустимых индексов. Это и есть единственная роль остатка: **преобразование «хеш-значения» в «номер корзины»**. Отсюда же требование беззнаковости (§9.3.1): у отрицательного `int` остаток мог бы оказаться отрицательным — снова индекс вне массива.

При `NBUCKETS = 1` остаток от деления на 1 равен нулю **всегда** — для любого ключа. Значит, все записи попадают в единственную корзину `bucket[0]`, и таблица превращается в один связный список (§9.1.2), а `table_get` — в линейный поиск по нему со сравнением `strcmp` на каждом шаге. Проверим на той же пятёрке ключей, добавив счётчик вызовов `strcmp`:

```c
/* Entry, Table, str_dup, table_put, table_free — как в §9.3.1, но NBUCKETS = 1;
   table_get дополнен счётчиком сравнений */

int *table_get_counted(Table *t, const char *key, int *cmp)   /* со счётчиком strcmp */
{
    for (Entry *e = t->bucket[hash(key)]; e != NULL; e = e->next) {
        (*cmp)++;
        if (strcmp(e->key, key) == 0)
            return &e->value;
    }
    return NULL;
}
```

```

Все пять ключей — в корзине 0 (в обратном порядке вставки: каждая новая запись встаёт в начало цепочки). Поиск `"cat"`, вставленного первым, стоил 5 сравнений — весь список; поиск отсутствующего `"moo"` — тоже 5, полный перебор. Это в точности стоимость поиска в списке из §9.1.3: до `n` шагов. Никакого выигрыша перед обычным списком у такой «таблицы» нет — только накладные расходы на хеш.

Связь числа корзин и длины цепочки прямая: при `n` записях, `B` корзинах и **равномерном** хеше в каждой корзине оказывается примерно `n / B` записей — это и есть средняя длина цепочки, а с ней и средняя цена поиска. Отсюда обе крайности: `B = 1` даёт цепочку длиной `n` (наш случай), `B ≥ n` — цепочки длиной около единицы, то есть поиск за «хеш плюс пара сверок» почти независимо от `n`. Поэтому промышленные таблицы **растят число корзин вместе с данными** (rehash при превышении порога заполнения, §9.3.1): фиксированное `B` рано или поздно превращает таблицу в набор длинных списков. Оговорка «равномерный хеш» существенна: плохая функция, сваливающая ключи в одну корзину, даёт тот же `NBUCKETS = 1` при любом числе корзин.

**Ответ:** `% NBUCKETS` переводит хеш-значение (произвольное число из всего диапазона `unsigned`) в допустимый индекс массива корзин `0 … NBUCKETS-1`; без него индекс вышел бы за границы массива — UB. При `NBUCKETS = 1` остаток всегда 0, все записи ложатся в единственную корзину, таблица вырождается в один связный список, а `table_get` — в линейный перебор со `strcmp` на каждом узле: поиск стоит до `n` шагов (прогон: 5 сравнений на пяти ключах и для существующего, и для отсутствующего ключа). Средняя длина цепочки при равномерном хеше — `n / NBUCKETS`, поэтому цена поиска обратно пропорциональна числу корзин; ради этого реальные таблицы увеличивают число корзин по мере роста числа записей.

### Г9.Ч3.З5

**Условие.** *(понимание)* Почему `table_get`, найдя корзину по хешу, всё равно сверяет каждый ключ через `strcmp`? Приведите пару строк из §9.3.1 с одинаковой корзиной и объясните, что вернул бы поиск без сверки ключей.

**Решение.** Хеш-функция отображает бесконечное множество строк в восемь номеров — совпадение номеров неизбежно и ничего не доказывает. Равенство корзин — лишь **необходимое** условие равенства ключей: одинаковые ключи всегда дают одинаковый номер (функция детерминирована), но одинаковый номер могут дать и разные ключи. Утверждение «нашлась запись в нужной корзине — значит, это наш ключ» неверно, и единственный способ убедиться — сравнить строки целиком, то есть `strcmp` (гл. 5). В этом и состоит разделение труда: хеш **сужает** поиск до одной цепочки, `strcmp` **подтверждает** попадание.

Готовая пара с одинаковой корзиной есть в самой главе: `hash("cat") = 6` и `hash("tac") = 6` (§9.3.1, пример 1) — анаграммы, у которых суммирующая формула совпала. Посмотрим, что вернёт «поиск», доверяющий одному хешу:

```c
/* Entry, Table, hash, str_dup, table_init, table_get, table_put, table_free —
   как в §9.3.1 */

int *table_get_nocmp(Table *t, const char *key)   /* «поиск» без сверки ключей */
{
    Entry *e = t->bucket[hash(key)];
    return e == NULL ? NULL : &e->value;           /* первая запись корзины — и всё */
}
```

Записи `cat=1` и `tac=3` живут в одной цепочке, причём `tac`, вставленный позже, стоит первым (новая запись добавляется в начало цепочки — `push_front`). Настоящий `table_get` проходит цепочку и сверяет ключи: `"tac"` не подходит, `"cat"` подходит — возвращается 1. Версия без сверки берёт **первую попавшуюся** запись корзины и возвращает 3 — значение чужого ключа. Заметьте, что ошибка ещё и неустойчивая: она зависит от порядка вставки (вставь `cat` последним — и «сработало бы»), потому такие дефекты особенно неприятны. Последняя строка вывода показывает вторую сторону: отсутствующий ключ `"cow"` попал в пустую корзину 3 и дал `NULL` — то есть без сверки поиск иногда «работает», и это лишь вопрос везения: попади `"cow"` в занятую корзину, он «нашёл» бы чужую запись.

**Ответ:** равенство номеров корзин не означает равенства ключей — разные строки могут хешироваться в одну корзину (коллизия), и без полной сверки таблица начнёт возвращать чужие записи. Пара из §9.3.1: `"cat"` и `"tac"` — обе в корзине 6. Поиск без `strcmp` вернул бы первую запись этой корзины, то есть значение `tac` (**3**) вместо значения `cat` (**1**), а несуществующий ключ, попавший в непустую корзину, был бы объявлен найденным. Хеш только сужает область поиска до одной цепочки; окончательное решение принимает `strcmp`.

### Г9.Ч3.З6

**Условие.** *(понимание)* Объясните, почему inorder-обход BST печатает значения по возрастанию. Рассуждение стройте от инварианта: где относительно узла лежит всё меньшее, где всё большее, и в каком порядке обход посещает «левое — узел — правое» на каждом уровне.

**Решение.** Соберём рассуждение из двух посылок.

Первая — **инвариант BST**: для любого узла `X` в его левом поддереве лежат **только** значения меньше `X`, в правом — **только** значения больше. Причём это верно не для непосредственных потомков, а для всех узлов поддерева на всех уровнях (§9.3.2): в левом поддереве нет ни одного значения, которое было бы больше `X`, как бы глубоко оно ни лежало.

Вторая — **порядок обхода**: `bst_inorder` для каждого узла делает ровно три вещи в фиксированном порядке — целиком обходит левое поддерево, печатает сам узел, целиком обходит правое поддерево.

Соединяем. Раз обход левого поддерева завершается **до** печати `X`, все напечатанные до `X` значения — это в точности содержимое левого поддерева, а по инварианту все они меньше `X`. Раз обход правого поддерева начинается **после** печати `X`, все напечатанные после — содержимое правого поддерева, и все они больше `X`. Значит, для узла `X` выполняется: сначала всё меньшее, потом `X`, потом всё большее — то есть `X` встаёт в вывод на своё место относительно всего дерева.

Осталось убедиться, что и внутри поддеревьев порядок верный, — и здесь работает индукция по структуре (§4.3): пустое дерево печатает пустую последовательность, которая тривиально отсортирована (база); если оба поддерева печатаются по возрастанию (предположение), то конкатенация «отсортированное левое → `X` → отсортированное правое» тоже отсортирована, поскольку левое целиком меньше `X`, а правое целиком больше. Инвариант BST обеспечивает именно то условие, при котором склейка трёх кусков не нарушает порядка.

Наблюдать это удобно на дереве Г9.Ч3.З2 (корень 4): обход печатает левое поддерево `1 2 3` (всё меньше 4), затем `4`, затем правое `5 6 7` (всё больше 4) — и то же правило рекурсивно объясняет порядок внутри каждой тройки. Проверено прогоном: `1 2 3 4 5 6 7`.

Полезно проговорить и обратное: если инвариант нарушен (скажем, узел со значением 9 подвешен в левое поддерево корня 4), inorder напечатает `… 9 … 4 …` — вывод перестанет быть отсортированным. Упорядоченность вывода — не свойство обхода самого по себе, а следствие инварианта; обход лишь «читает» дерево в правильном направлении.

**Ответ:** по инварианту всё, что меньше узла, лежит в его левом поддереве, всё, что больше, — в правом (на всех уровнях). Inorder обходит левое поддерево **целиком до** узла, печатает узел и обходит правое поддерево **целиком после**, — значит, перед каждым значением выводятся все меньшие его значения дерева, а после — все большие. По индукции то же верно внутри каждого поддерева (база — пустое дерево), поэтому весь вывод отсортирован по возрастанию. Упорядоченность обеспечивает именно инвариант: при его нарушении тот же обход дал бы неотсортированную последовательность.

### Г9.Ч3.З7

**Условие.** *(понимание)* Вставьте (мысленно) в пустое BST значения `1, 2, 3, 4, 5` по порядку. Нарисуйте результат. Чему равна высота? Сколько сравнений теперь стоит `bst_search(root, 5)` и чем это отличается от поиска в списке из §9.1.2? Как называется этот случай?

**Решение.** Каждое следующее значение больше всех вставленных ранее, поэтому спуск на каждой вставке идёт **только вправо** и заканчивается свободным местом у самого нижнего узла:

```
   [1]
      \
      [2]
         \
         [3]
            \
            [4]
               \
               [5]

   все левые указатели — NULL
```

Высота (число узлов на самом длинном пути от корня вниз) равна **5** — числу узлов: дерево вытянулось в цепочку. Поиск `bst_search(root, 5)` вынужден пройти её всю: на каждом узле `5` больше значения — шаг вправо; узлов посещается 5 (на каждом делаются два сравнения значений, `x < value` и `x > value`, — итого 10 сравнений). Проверяем счётчиком:

```c
/* TNode, bst_insert, bst_inorder, bst_free — как в §9.3.2;
   bst_search дополнен счётчиком посещённых узлов */

const TNode *bst_search_counted(const TNode *root, int x, int *steps)
{
    if (root == NULL) return NULL;
    (*steps)++;                        /* один посещённый узел — один шаг спуска */
    if (x < root->value) return bst_search_counted(root->left, x, steps);
    if (x > root->value) return bst_search_counted(root->right, x, steps);
    return root;
}
```

Все левые указатели пусты, поиск худшего элемента стоит 5 шагов, лучшего (корня) — 1. Для сравнения: в сбалансированном дереве из Г9.Ч3.З2 любой из семи узлов достижим не более чем за 3 шага.

Чем это отличается от поиска в списке §9.1.2? По **числу шагов** — ничем: там тоже до `n` узлов. Отличия в остальном, и все не в пользу дерева: (1) каждый узел дерева хранит **два** указателя вместо одного, причём половина из них — впустую (`left` везде `NULL`), то есть памяти тратится больше; (2) поиск в списке — цикл, а `bst_search` рекурсивен, и на цепочке из миллиона узлов рекурсия углубляется на миллион кадров — переполнение стека вызовов (§4.3), которого у списка нет; то же касается `bst_insert` и `bst_free`. Иными словами, вырожденное дерево — это список, который платит за структуру дерева, ничего не получая взамен. Inorder, впрочем, по-прежнему честно печатает `1 2 3 4 5`: инвариант не нарушен, нарушена только форма.

**Ответ:** получается цепочка `1 → 2 → 3 → 4 → 5`, где каждый узел имеет только правого потомка, а все левые указатели — `NULL`; **высота 5** (равна числу узлов). `bst_search(root, 5)` посещает все 5 узлов (по два сравнения значений на узел — 10 сравнений), тогда как в сбалансированном дереве того же размера хватило бы трёх шагов. От поиска в списке это не отличается по стоимости (до `n` шагов), но обходится дороже: узлы вдвое «толще» из-за неиспользуемых указателей `left`, а рекурсивный спуск на длинной цепочке грозит переполнением стека вызовов, чего у циклического обхода списка нет. Случай называется **вырожденным деревом** (дерево, вырожденное в список); возникает он при вставке отсортированных данных и служит главным доводом в пользу самобалансирующихся деревьев (§9.3.2).

### Г9.Ч3.З8

**Условие.** *(прикладное)* Подсчёт частот: дан набор слов (например, `"a", "bb", "a", "ccc", "bb", "a"` в двумерном массиве `char words[6][4]`). Для каждого слова: если оно уже в таблице — увеличить значение через указатель из `table_get`; иначе `table_put(…, 1)`. Напечатайте все пары «слово: счётчик» обходом корзин (ожидается `a: 3`, `bb: 2`, `ccc: 1` — в порядке корзин). Освободите таблицу; санитайзер должен быть чист.

**Решение.** Задача показывает, зачем `table_get` возвращает **адрес** значения, а не его копию: найдя запись, счётчик можно увеличить прямо на месте — `(*v)++`, без повторного поиска и без вызова `table_put`. Логика на каждое слово укладывается в три строки: спросили адрес; если есть — увеличили; если нет — завели запись со значением 1. Печать идёт обходом массива корзин, а внутри каждой — по цепочке.

Про `char words[6][4]`: это шесть строк по 4 байта, и `"ccc"` занимает их полностью (три символа плюс терминатор) — самое длинное слово, которое сюда влезает.

```c
/* Entry, Table, hash, str_dup, table_init, table_get, table_put, table_free —
   как в §9.3.1 (NBUCKETS = 8) */

int main(void)
{
    char words[6][4] = {"a", "bb", "a", "ccc", "bb", "a"};
    Table t;
    table_init(&t);

    for (int i = 0; i < 6; i++) {
        int *v = table_get(&t, words[i]);
        if (v != NULL)
            (*v)++;                                  /* правим значение через указатель */
        else if (table_put(&t, words[i], 1) != 0) {  /* первое появление слова */
            table_free(&t);
            return 1;
        }
    }

    for (int i = 0; i < NBUCKETS; i++)               /* обход всех корзин */
        for (const Entry *e = t.bucket[i]; e != NULL; e = e->next)
            printf("bucket %d -> %s: %d\n", i, e->key, e->value);

    table_free(&t);
    return 0;
}
```

Так что вывод идёт в порядке `bb`, `a`, `ccc` — это и есть «в порядке корзин», просто корзины расположили слова не по алфавиту. Никакого порядка, кроме «по номеру корзины, внутри корзины — от последней вставленной записи к первой», хеш-таблица не гарантирует в принципе: нужен упорядоченный вывод — нужна другая структура (BST §9.3.2 и его inorder) или сортировка выгруженных пар.

### Г9.Ч3.З9

**Условие.** *(прикладное)* Напишите `int bst_size(const TNode *root)` (число узлов) и `int bst_height(const TNode *root)` (узлов на самом длинном пути от корня вниз; пустое дерево — 0), обе рекурсивно. Проверьте на дереве из `5, 3, 8, 1, 4` (ожидается size 5, height 3) и на вырожденном из `1..5` (ожидается size 5, height 5).

**Решение.** Обе функции — рекурсия по структуре дерева с общей базой «пустое дерево — 0» и разным способом соединить результаты поддеревьев. Размер: сам узел плюс размеры обоих поддеревьев (складываем). Высота: сам узел плюс высота **более глубокого** из поддеревьев (берём максимум) — путь ведь один, и он идёт либо влево, либо вправо. Ни та ни другая не нуждается в инварианте BST: они работают на любом двоичном дереве.

```c
/* TNode, bst_insert, bst_free — как в §9.3.2 */

int bst_size(const TNode *root)        /* число узлов */
{
    if (root == NULL) return 0;                              /* пустое дерево — 0 */
    return 1 + bst_size(root->left) + bst_size(root->right); /* сам узел + оба поддерева */
}

int bst_height(const TNode *root)      /* узлов на самом длинном пути вниз */
{
    if (root == NULL) return 0;
    int hl = bst_height(root->left);
    int hr = bst_height(root->right);
    return 1 + (hl > hr ? hl : hr);    /* сам узел + более глубокое из поддеревьев */
}

int build(TNode **rootp, const int *keys, int n)
{
    for (int i = 0; i < n; i++)
        if (bst_insert(rootp, keys[i]) < 0) return -1;
    return 0;
}

int main(void)
{
    int bushy[] = {5, 3, 8, 1, 4};
    int chain[] = {1, 2, 3, 4, 5};

    TNode *a = NULL;
    if (build(&a, bushy, 5) != 0) { bst_free(a); return 1; }
    printf("bushy {5,3,8,1,4}: size = %d, height = %d\n", bst_size(a), bst_height(a));
    bst_free(a);

    TNode *b = NULL;
    if (build(&b, chain, 5) != 0) { bst_free(b); return 1; }
    printf("degenerate {1..5}: size = %d, height = %d\n", bst_size(b), bst_height(b));
    bst_free(b);

    printf("empty tree: size = %d, height = %d\n", bst_size(NULL), bst_height(NULL));
    return 0;
}
```

Ожидания условия подтвердились. Пара чисел «размер и высота» — по сути, диагноз формы дерева: при одинаковом размере 5 высота 3 против 5 показывает, насколько дерево далеко от вырождения. Полезные ориентиры: минимально возможная высота для `n` узлов — около `log₂ n` (для 5 узлов это 3), максимальная — ровно `n` (цепочка Г9.Ч3.З7); именно за приближение высоты к первому пределу и борются самобалансирующиеся деревья. Обратите внимание на `bst_height(NULL)` — 0 по условию задачи; это не «нет узлов на пути», а соглашение, которое делает формулу `1 + max(...)` верной для листа (у листа оба поддерева пусты, высота получается 1).

**Ответ:** обе функции строятся на базе «пустое дерево — 0»: `bst_size` возвращает `1 + size(left) + size(right)`, `bst_height` — `1 + max(height(left), height(right))`; инвариант BST им не нужен, они верны для любого двоичного дерева. Прогон: дерево из `5, 3, 8, 1, 4` — size 5, height 3; вырожденное из `1..5` — size 5, height 5; пустое — 0 и 0. Совпадает с ожиданиями условия. Одинаковый размер при разной высоте — это и есть численная мера «кустистости»: чем ближе высота к `log₂ n`, тем дешевле поиск, чем ближе к `n` — тем дерево ближе к списку.

### Г9.Ч3.З10

**Условие.** *(прикладное)* Напишите `const TNode *bst_min(const TNode *root)` и `bst_max` **итеративно** (циклом): минимум — самый левый узел, максимум — самый правый; для пустого дерева — `NULL`. Проверьте на дереве из `5, 3, 8, 1, 4, 7, 9` (ожидается 1 и 9). Почему здесь не нужна рекурсия?

**Решение.** По инварианту BST всё меньшее лежит слева — значит, минимум там, где идти влево уже некуда: у самого левого узла (`left == NULL`). Симметрично максимум — самый правый узел. Никаких сравнений значений при этом не делается вовсе: направление известно заранее, и весь алгоритм — «спускайся, пока есть куда». Пустое дерево обрабатывается отдельной первой строкой: `NULL` на входе — `NULL` на выходе.

Обратите внимание на приём в цикле: параметр `root` — собственная копия указателя функции (§4.2.1), поэтому его можно двигать самим, не заводя отдельного «бегунка»; на дерево вызывающего это не влияет, а `const` в типе гарантирует, что узлы не изменятся.

```c
/* TNode, bst_insert, bst_free — как в §9.3.2 */

const TNode *bst_min(const TNode *root)    /* самый левый узел */
{
    if (root == NULL) return NULL;
    while (root->left != NULL)             /* спуск — простой цикл, без ветвлений */
        root = root->left;
    return root;
}

const TNode *bst_max(const TNode *root)    /* самый правый узел */
{
    if (root == NULL) return NULL;
    while (root->right != NULL)
        root = root->right;
    return root;
}

int main(void)
{
    TNode *root = NULL;
    int keys[] = {5, 3, 8, 1, 4, 7, 9};
    for (int i = 0; i < 7; i++)
        if (bst_insert(&root, keys[i]) < 0) { bst_free(root); return 1; }

    const TNode *lo = bst_min(root);
    const TNode *hi = bst_max(root);
    printf("min = %d\n", lo->value);
    printf("max = %d\n", hi->value);
    printf("empty: min is NULL: %d, max is NULL: %d\n",
           bst_min(NULL) == NULL, bst_max(NULL) == NULL);

    bst_free(root);
    return 0;
}
```

```

Почему рекурсия здесь не нужна. Рекурсия оправдана, когда задача **ветвится**: `bst_size` и `bst_height` (Г9.Ч3.З9) обязаны обойти оба поддерева, и «запомнить, куда вернуться» без стека вызовов не выйдет. Поиск минимума не ветвится: на каждом шаге есть ровно одно продолжение — влево, — и после спуска возвращаться никуда не надо, результат готов на дне. Такой «линейный спуск» — это обычный цикл, и записывать его рекурсией значит платить кадром стека за каждый уровень без всякой выгоды: на вырожденном дереве (Г9.Ч3.З7) из миллиона узлов цикл отработает спокойно, а рекурсия рискует переполнить стек вызовов.

**Ответ:** `bst_min` и `bst_max` — спуск циклом `while (root->left != NULL) root = root->left;` (соответственно по `right`), с проверкой пустого дерева первой строкой; сравнений значений не требуется, направление задано инвариантом BST. На дереве из `5, 3, 8, 1, 4, 7, 9` получено `min = 1`, `max = 9`, на пустом — `NULL` в обеих функциях. Рекурсия здесь не нужна потому, что спуск **не ветвится**: на каждом уровне есть единственное продолжение и возвращаться после него некуда — вся работа рекурсии свелась бы к трате кадра стека на уровень (на вырожденном дереве — до `n` кадров). Рекурсия остаётся оправданной там, где обход раздваивается: размер, высота, inorder, освобождение.

**Вариант 2 (рекурсивная запись — для сравнения).** Тот же спуск можно записать рекурсией: база — пустое дерево и узел без левого потомка, шаг — переход на уровень ниже.

```c
const TNode *bst_min(const TNode *root)    /* тот же спуск рекурсией */
{
    if (root == NULL) return NULL;             /* пустое дерево */
    if (root->left == NULL) return root;       /* левее некуда — это минимум */
    return bst_min(root->left);                /* хвостовой вызов: спуск на уровень */
}
```

```
gcc -std=c17 -Wall -Wextra minmax2.c -o minmax2
./minmax2
```

```
min = 1
max = 9
empty: min is NULL: 1, max is NULL: 1
```

*Сравнение.* Результаты идентичны, и по числу шагов версии равны — разница в расходе стека вызовов: цикл работает в одном кадре, рекурсия занимает кадр на каждый уровень, то есть до `n` кадров на вырожденном дереве. Рекурсивный вызов здесь **хвостовой** (его результат сразу возвращается наружу), и оптимизирующий компилятор может превратить его в цикл сам — но язык этого не гарантирует, а на `-O0` (учебная сборка) кадры реально расходуются. Читаемость же у обеих версий одинаковая. Вывод общий: там, где спуск линеен, цикл — не «оптимизация», а более честная запись; рекурсию берегут для ветвящихся обходов, где она незаменима (`bst_size`, `bst_height`, `bst_inorder`, `bst_free`).
