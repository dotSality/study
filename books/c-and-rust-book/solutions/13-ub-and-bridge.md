# Решения. Глава 13. Неопределённое поведение и безопасность: мост к Rust

> Сборник решений самоучителя «C, затем Rust». Условия заданий продублированы из `chapters/13-ub-and-bridge.md`. Пользуйтесь сборником только после самостоятельной попытки.
>
> **Два контура проверки.** Код на C собран и запущен на эталоне тома I — **GCC 15.2.0 (MinGW-w64), `gcc -std=c17 -Wall -Wextra`**; всё, что требует санитайзеров и valgrind, прогнано в **WSL Ubuntu 24.04 (gcc 13.3.0, valgrind 3.22.0)**, как и предписано преамбулой практики 13.1. Выводы программ, отчёты инструментов, предупреждения компилятора и ассемблерные листинги — дословные результаты реального прогона; для каждого указано, на каком контуре он получен.
>
> **Особенность главы: половина программ здесь неисправна намеренно.** Такие программы помечены ⛔ — их предъявление входит в условие задания. Никакие их результаты не «правильные»: у программы с неопределённым поведением правильных результатов не бывает (§13.1.1), и приведённые числа — это только протокол одного прогона на одной машине, а не свойство программы. Числа, зависящие от машины и от расположения данных в памяти (мусор из-за границы массива, адреса, значения счётчика в гонке), приведены с оговоркой «на эталонной машине» и от запуска к запуску меняются — это и есть предмет изучения.
>
> **Фрагменты на Rust (часть 13.2)** — витрина: их разбор не требует установленного Rust, все нужные сообщения компилятора приведены в главе. Для этого сборника они тем не менее **проверены запуском** — `rustc 1.97.0, --edition 2024` на Windows, отладочная и релизная (`-O`) сборки; там, где вывод отличается от приведённого в §13.2 (глава собиралась на rustc 1.75), это оговорено.
>
> **Три подробности прогона, которые стоит держать в голове** (все три разобраны в решениях соответствующих заданий):
> 1. У программы `oob.c` из §13.1.2 **нет** запуска, при котором UBSan молчит: `i = argc + 3`, а `argc >= 1` при любом обычном запуске, значит `i >= 4` всегда. «Чистый» вход появляется после правки одной цифры (`argc + 2`) — так и решается Г13.Ч1.З6.
> 2. `-fsanitize=address` и `-fsanitize=undefined` на GCC 13.3 **совместимы**: собираются и работают вместе (проверено). Несовместимы ASan и TSan — их сообщение приведено в Г13.Ч1.З8.
> 3. Номера строк в отчётах UBSan — свойство файла: наши листинги и листинги §13.1.4 набраны с первой строкой-комментарием, поэтому номера совпадают; без комментария они на единицу меньше (Г13.Ч1.З3).

## Часть 13.1. Неопределённое поведение в C

### Г13.Ч1.З1

**Условие.** Классифицируйте каждый фрагмент по категориям §13.1.1: *определено стандартом*, *implementation-defined*, *unspecified*, *UB* (все переменные типа `int`, кроме оговорённых; значения — как указано):

а) `unsigned u = UINT_MAX; u + 1`
б) `int i = INT_MAX; i + 1`
в) `printf("%d %d", f(), g())` — порядок вызова `f` и `g`
г) значение `sizeof(long)`
д) `int a[3]; a[3]`
е) `x % 0`
ж) `i++ + i++`
з) `1 << 35` (при 32-битном `int`)

Для каждого пункта укажите строку каталога §13.1.2 или причину, по которой фрагмент в каталог не попадает.

**Решение.** Классификация делается в два приёма: сначала по определениям §13.1.1 (кто выбирает результат), затем — попадает ли фрагмент в ядро каталога §13.1.2.

1. **«а» — определено стандартом.** Беззнаковая арифметика не переполняется: результат приводится по модулю 2ᴺ (N3220 §3.28, мы пользовались этим в §2.2.5). `UINT_MAX + 1` — это ровно 0, на любой платформе и при любых флагах. В каталог **не попадает**: там перечислено неопределённое поведение, а здесь поведение определено — это тот самый контрпример, который §13.1.2 приводит специально.
2. **«б» — UB, строка 5** (знаковое переполнение; N3220 §6.5.1¶5). Та же по виду строка `x + 1`, что и в «а», но для `int` — мина: именно на ней построены обе демонстрации §13.1.3.
3. **«в» — unspecified.** Порядок вычисления аргументов функции стандарт оставляет на выбор компилятора, не требуя ни постоянства, ни документирования (§13.1.1; наблюдали в §4.2.2). В каталог **не попадает**: программа остаётся корректной, просто её вывод — один из нескольких допустимых. Важно не путать с пунктом «ж»: там неупорядочены не *вызовы*, а *побочные эффекты над одним объектом*, и это уже UB.
4. **«г» — implementation-defined.** Платформа обязана выбрать размер и задокументировать его; проверяется программой. В каталог **не попадает**: программа корректна, но непереносима.
5. **«д» — UB, строка 1.** У массива из трёх элементов допустимые индексы 0, 1, 2; `a[3]` — чтение за границей (N3220 §6.5.7, J.2(46)). Тонкость: вычислить адрес `&a[3]` (указатель «за последним») стандарт разрешает — UB даёт именно **разыменование**.
6. **«е» — UB, строка 6.** N3220 §6.5.6¶6 говорит о нуле как о втором операнде и `/`, и `%`: остаток от деления на ноль неопределён ровно так же, как частное.
7. **«ж» — UB, строка 8** (N3220 §6.5.1¶2). Подробный разбор — Г13.Ч1.З5.
8. **«з» — UB, строка 7.** Сдвиг на величину, не меньшую ширины левого операнда, — UB (N3220 §6.5.8¶3); при 32-битном `int` запрещены сдвиги на 32 и больше, 35 — за пределом.

**Проверка на машине.** Пункты «а» и «г» проверяются одной программой (эталон, MinGW):

```c
/* uwrap.c — беззнаковый заворот определён стандартом, знаковое переполнение — нет */
#include <limits.h>
#include <stdio.h>

int main(void)
{
    unsigned u = UINT_MAX;
    printf("UINT_MAX + 1 = %u\n", u + 1);   /* определено: заворот по модулю 2^32 */
    printf("sizeof(long) = %zu\n", sizeof(long));  /* implementation-defined */
    return 0;
}
```

```
UINT_MAX + 1 = 0
sizeof(long) = 4
```

Пункт «з» полезно предъявить отдельно — он показывает, как UB маскируется под правдоподобный ответ. Индекс сдвига берём из `argc`, чтобы компилятор не вычислил выражение заранее (⛔ программа неисправна намеренно):

```c
/* shift35.c — сдвиг на 35 при 32-битном int (строка 7 каталога) */
#include <stdio.h>

int main(int argc, char **argv)
{
    (void)argv;
    int n = argc + 34;             /* без аргументов n == 35 */
    printf("1 << %d = %d\n", n, 1 << n);
    return 0;
}
```

Сборка эталонными флагами проходит **без единого предупреждения**, программа печатает:

```
1 << 35 = 8
```

Восемь — это `1 << 3`: процессор x86 берёт из счётчика сдвига только младшие 5 бит, то есть 35 mod 32 = 3. Ответ выглядит осмысленным и потому особенно опасен. UBSan в WSL показывает, что произошло на самом деле:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined shift35.c -o shift_ub
./shift_ub
shift35.c:8:35: runtime error: shift exponent 35 is too large for 32-bit type 'int'
1 << 35 = 8
```

А если написать тот же сдвиг **константой**, ответ будет уже другой — и компилятор предупредит:

```c
    printf("1 << 35 = %d\n", 1 << 35);
```

```
shift_const.c:6:32: warning: left shift count >= width of type [-Wshift-count-overflow]
1 << 35 = 0
```

Одно и то же выражение даёт 8 или 0 в зависимости от того, вычислено оно на этапе компиляции или на процессоре. Обещаний нет ни на то, ни на другое — это и означает «UB».

**Ответ:**

| Пункт | Категория §13.1.1 | Каталог §13.1.2 |
|---|---|---|
| а) `unsigned u = UINT_MAX; u + 1` | **определено стандартом** (результат 0) | не попадает: беззнаковая арифметика заворачивается по модулю 2ᴺ (N3220 §3.28) |
| б) `int i = INT_MAX; i + 1` | **UB** | **строка 5** (§6.5.1¶5) |
| в) порядок вызова `f` и `g` | **unspecified** | не попадает: программа корректна, вариант выбирает компилятор |
| г) `sizeof(long)` | **implementation-defined** | не попадает: платформа выбирает и документирует (у нас 4) |
| д) `int a[3]; a[3]` | **UB** | **строка 1** (§6.5.7, J.2(46)) |
| е) `x % 0` | **UB** | **строка 6** (§6.5.6¶6) |
| ж) `i++ + i++` | **UB** | **строка 8** (§6.5.1¶2) |
| з) `1 << 35` при 32-битном `int` | **UB** | **строка 7** (§6.5.8¶3) |

Пять пунктов из восьми — UB; три «безобидных» (а, в, г) относятся к трём разным категориям, и путать их нельзя: «а» одинаково ведёт себя везде, «г» — предсказуемо на каждой платформе по отдельности, «в» — может различаться даже в двух местах одной программы.

### Г13.Ч1.З2

**Условие.** Воспроизведите демонстрации 1 и 2 из §13.1.3: соберите `wraps.c` и `loop31.c` с `-O0`, `-O2` и `-O2 -fwrapv`, сведите результаты в таблицу «файл × флаги → вывод». Для каждой клетки укажите, гарантирован ли её результат стандартом, флагом компилятора или не гарантирован ничем.

**Решение.** Обе программы ⛔ неисправны намеренно: в первой знаковое переполнение в `always_true`, во второй — в счётчике цикла. Берём их из §13.1.3 дословно.

```c
/* wraps.c */
#include <limits.h>
#include <stdio.h>

int always_true(int x)
{
    return x + 1 > x;
}

int main(void)
{
    printf("INT_MAX+1 > INT_MAX: %d\n", always_true(INT_MAX));
    return 0;
}
```

```c
/* loop31.c */
#include <stdio.h>

int main(void)
{
    int n = 0;
    for (int i = 1; i > 0; i *= 2)
        n++;
    printf("n = %d\n", n);
    return 0;
}
```

Шесть сборок на эталоне (MinGW GCC 15.2, все — без предупреждений):

```
gcc -std=c17 -Wall -Wextra -O0            wraps.c   -o w0.exe
gcc -std=c17 -Wall -Wextra -O2            wraps.c   -o w2.exe
gcc -std=c17 -Wall -Wextra -O2 -fwrapv    wraps.c   -o wv.exe
gcc -std=c17 -Wall -Wextra -O0            loop31.c  -o l0.exe
gcc -std=c17 -Wall -Wextra -O2            loop31.c  -o l2.exe
gcc -std=c17 -Wall -Wextra -O2 -fwrapv    loop31.c  -o lv.exe
```

Одну из шести программ нельзя запустить обычным образом — она не завершается, поэтому запускаем через ограничитель времени (`timeout 5` из Git Bash), чтобы получить протокол, а не зависший терминал:

```
./w0.exe            INT_MAX+1 > INT_MAX: 1
./w2.exe            INT_MAX+1 > INT_MAX: 1
./wv.exe            INT_MAX+1 > INT_MAX: 0
./l0.exe            n = 31
timeout 5 ./l2.exe  (нет вывода; exit=124 — прерван по тайм-ауту)
timeout 5 ./lv.exe  n = 31
```

Ассемблер `l2.exe` объясняет пустой вывод — тело `main` после пролога состоит из одной инструкции (`gcc -std=c17 -O2 -S loop31.c`):

```asm
main:
	subq	$40, %rsp
	call	__main
.L2:
	jmp	.L2
```

Ни цикла, ни счётчика, ни `printf`: оптимизатор доказал, что при отсутствии знакового переполнения `i > 0` — инвариант, и заменил всю программу вечным циклом. Заодно проверим ещё одну клетку, которой нет в условии, — она пригодится в выводе: `-O0 -fwrapv` для `wraps.c` тоже печатает `0`.

Теперь главный вопрос задания — чем гарантирована каждая клетка. Разбираем по трём источникам гарантий:

- **Стандартом** гарантировано то, что следует из правил языка для корректной программы. Обе программы содержат UB, поэтому стандарт не требует от них **ничего** — таких клеток в таблице нет ни одной.
- **Флагом компилятора** гарантированы клетки с `-fwrapv`: этот флаг документирован в руководстве GCC (C17) как «предполагать, что знаковое переполнение сложения, вычитания и умножения заворачивается по правилам дополнительного кода». Он локально доопределяет то, что стандарт оставил неопределённым, — но только для GCC и только для этой сборки.
- **Ничем** гарантированы остальные клетки. Заметьте: «ничем» — это не «случайно совпало». Клетки `-O0` и `-O2` у `wraps.c` дали один и тот же ответ `1`, и от запуска к запуску он не меняется. Устойчивость наблюдения не превращает его в обещание: любая перекомпиляция другой версией GCC, любой добавленный флаг, любое изменение соседнего кода вправе изменить результат — как это и произошло у `loop31.c` при переходе с `-O0` на `-O2`.

**Ответ:**

| Файл | Флаги | Вывод (эталон, MinGW GCC 15.2) | Чем гарантирован |
|---|---|---|---|
| `wraps.c` | `-O0` | `INT_MAX+1 > INT_MAX: 1` | **ничем** (UB: строка 5 каталога) |
| `wraps.c` | `-O2` | `INT_MAX+1 > INT_MAX: 1` | **ничем** |
| `wraps.c` | `-O2 -fwrapv` | `INT_MAX+1 > INT_MAX: 0` | **флагом компилятора** (`-fwrapv`, C17) |
| `loop31.c` | `-O0` | `n = 31` | **ничем** (UB: строка 5 каталога) |
| `loop31.c` | `-O2` | программа не завершается (прервана по тайм-ауту, код 124) | **ничем** |
| `loop31.c` | `-O2 -fwrapv` | `n = 31` | **флагом компилятора** |

Стандартом не гарантирована ни одна клетка таблицы: обе программы за пределами контракта §13.1.1. Два практических вывода. Первый: `-O0` не «безопаснее» — свёртка `x + 1 > x` в истину произошла и там (это видно по клетке `-O0`: честный машинный заворот дал бы `0`, и он появляется только под `-fwrapv`, в том числе на `-O0`). Второй: одна и та же строка `i *= 2` даёт `n = 31` или вечный цикл в зависимости от ключа сборки — то есть от решения, которое обычно принимает не автор кода, а сборочный конвейер.

### Г13.Ч1.З3

**Условие.** Соберите `addover.c` и `divzero.c` из §13.1.2/§13.1.4 в WSL с `-fsanitize=undefined`, получите оба отчёта UBSan. Разберите формат отчёта по полям: что означают `имя_файла:строка:столбец`, текст диагноза, почему `addover` после отчёта продолжил работу и напечатал `-2147483648`, а `divzero` — упал.

**Решение.** `divzero.c` берём из §13.1.2 дословно; `addover.c` в главе приведён только своим отчётом, поэтому пишем программу по описанию из §13.1.4 — «`x + 1` при `x`, прочитанном из ввода как 2147483647». Ввод здесь принципиален: если написать константу, компилятор вычислит выражение сам и выдаст предупреждение (мы это видели в Г13.Ч1.З1 на сдвиге), а нам нужно UB, случающееся **во время выполнения**, — именно его и ловит динамический инструмент. Обе программы ⛔ неисправны намеренно.

```c
/* addover.c — знаковое переполнение: x берётся из ввода */
#include <stdio.h>

int main(void)
{
    int x = 0;
    if (scanf("%d", &x) != 1) return 1;
    x++;                       /* при x == INT_MAX это UB (строка 5 каталога) */
    printf("%d\n", x);
    return 0;
}
```

```c
/* divzero.c */
#include <stdio.h>

int main(int argc, char **argv)
{
    (void)argv;
    int z = argc - 1;              /* при запуске без аргументов z == 0 */
    printf("%d\n", 10 / z);
    return 0;
}
```

Сборка и прогон в WSL (Ubuntu 24.04, gcc 13.3.0); поток ошибок и поток вывода разведены, чтобы не перемешивались:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined addover.c -o addover_ub
gcc -std=c17 -Wall -Wextra -fsanitize=undefined divzero.c -o divzero_ub

printf '2147483647\n' | ./addover_ub
addover.c:8:6: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648
код завершения: 0

./divzero_ub
divzero.c:8:23: runtime error: division by zero
код завершения: 136   (процесс убит сигналом SIGFPE: 128 + 8)
```

**Разбор формата.** Строка отчёта устроена одинаково у всех санитайзеров (сравните с ASan в §7.2.2):

```
addover.c : 8 : 6 : runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
    │       │   │        │                     │
    │       │   │        │                     └─ диагноз: класс нарушения и конкретные числа
    │       │   │        └─ метка «ошибка времени выполнения», а не компиляции
    │       │   └─ столбец: позиция оператора в строке (здесь ++ в `x++`)
    │       └─ строка исходного файла
    └─ имя файла единицы трансляции
```

- **`имя_файла:строка:столбец`** — точка исходного текста, где инструментация обнаружила нарушение. Это координаты **исходника**, а не машинного кода: компилятор при сборке с `-fsanitize=undefined` вставляет проверку рядом с подозрительной операцией и запоминает её место (C18: инструмент «модифицирует программу на этапе компиляции, чтобы ловить UB во время выполнения»). Поэтому отчёт указывает на `x++`, а не на адрес инструкции.
- **Диагноз** состоит из класса нарушения (`signed integer overflow`, `division by zero`) и, где это осмысленно, из фактических значений: `2147483647 + 1 cannot be represented in type 'int'`. Значения делают отчёт самодостаточным — видно и что произошло, и с какими данными.

**Замечание о номерах строк.** Наши номера совпадают с §13.1.4, потому что и там, и здесь программы набраны с первой строкой-комментарием. Уберите её — и все номера уменьшатся на единицу (проверено: `divzero.c:7:23`, `nullref.c:6:5`, `oob.c:8:32`), а столбцы останутся прежними. Это хорошая иллюстрация к тому, что номер строки — свойство конкретного файла, а не программы: сверяйте отчёт со своим исходником, а не с чужим.

**Почему `addover` продолжил, а `divzero` упал.** Причины совершенно разные, и в этом вся соль.

1. **UBSan по умолчанию — «сообщи и продолжай».** Отчёт печатает вставленная проверка; она не прерывает выполнение (у инструмента есть режимы `-fsanitize-trap` и `halt_on_error`, но по умолчанию — recover). Поэтому после диагноза управление возвращается в программу.
2. **`addover`: продолжать нечему мешать.** Сложение выполняется обычной машинной инструкцией, которая при переполнении не сигнализирует ничего — она просто даёт заворот в дополнительном коде. Программа печатает `-2147483648` и завершается кодом 0. Отчёт UBSan — единственный признак беды; уберите санитайзер, и программа выдаст то же самое число молча.
3. **`divzero`: падение устраивает не санитайзер, а процессор.** После отчёта выполняется реальная инструкция целочисленного деления, а деление на ноль на x86 — аппаратное исключение. Операционная система превращает его в сигнал SIGFPE, процесс умирает с кодом 136 (128 + номер сигнала 8). Проверяется просто: та же программа **без санитайзера** падает точно так же и с тем же кодом 136 — то есть падение не имеет к UBSan никакого отношения.

Кстати, о коде завершения `addover`: он равен нулю, то есть «успех». Автоматический тест, проверяющий только код возврата, счёл бы прогон удачным — отчёт UBSan нужно **читать** (или включать `UBSAN_OPTIONS=halt_on_error=1`).

Для полноты — обходной путь Windows-контура из §13.1.4 на той же программе:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined -fsanitize-trap=undefined addover.c -o addover_trap
printf '2147483647\n' | ./addover_trap
Illegal instruction (core dumped)      # код 132, никакого вывода
```

Вместо вызова библиотеки компилятор вставляет аварийную инструкцию: программа останавливается на месте нарушения, но не сообщает ни строки, ни диагноза. Видно, *что* случилось (программа рухнула), но не видно, *где* и *почему*, — потому диагностику и делаем в WSL.

**Ответ:** формат отчёта — `файл:строка:столбец: runtime error: <класс нарушения>: <фактические значения>`, где координаты указывают точку **исходного текста**, около которой компилятор поставил проверку. `addover` продолжил работу и напечатал `-2147483648`, потому что UBSan по умолчанию только сообщает о нарушении, а машинное сложение при переполнении не прерывает выполнение — оно даёт заворот; код завершения при этом 0. `divzero` упал не из-за санитайзера, а потому что после отчёта выполнилась настоящая инструкция деления, а деление на ноль на x86 — аппаратное исключение (SIGFPE, код 136); без санитайзера программа падает точно так же. Общий вывод: UBSan **добавляет диагноз**, но не меняет судьбу программы — он не «чинит» UB и не превращает его в контролируемый останов (сравните с паникой Rust — §13.2.2).

### Г13.Ч1.З4

**Условие.** По трём ассемблерным листингам `first.c` из §13.1.3 объясните: (а) какие именно инструкции соответствуют проверке `if (p == 0)` и куда они исчезли на `-O2`; (б) почему рассуждение оптимизатора корректно по стандарту; (в) почему `-fno-delete-null-pointer-checks` — не исправление ошибки. Перепишите `first` так, чтобы она была корректна при любых флагах, и словами обоснуйте, почему теперь оптимизатор не вправе удалить проверку.

**Решение.** Исходная функция (⛔ неисправна намеренно) и три сборки на эталоне — MinGW GCC 15.2, соглашение о вызовах Windows x64: первый аргумент приходит в регистре `%rcx`.

```c
/* first.c */
int first(int *p)
{
    int v = *p;        /* разыменование ДО проверки */
    if (p == 0)        /* «страховочная» проверка   */
        return -1;
    return v;
}
```

**(а) Где проверка и куда она делась.** На `-O0` (`gcc -std=c17 -S -O0 first.c`) тело функции содержит и чтение, и сравнение, и обе ветки:

```asm
first:
	...
	movq	%rcx, 16(%rbp)   ; аргумент p сохранён в кадре
	movq	16(%rbp), %rax
	movl	(%rax), %eax     ; v = *p            ← разыменование
	movl	%eax, -4(%rbp)
	cmpq	$0, 16(%rbp)     ; if (p == 0)       ← ПРОВЕРКА: сравнение
	jne	.L2              ;                   ← и условный переход
	movl	$-1, %eax        ; return -1         ← ветка «указатель нулевой»
	jmp	.L3
.L2:
	movl	-4(%rbp), %eax   ; return v
.L3:
	...
```

Проверке соответствуют ровно две инструкции — `cmpq $0, 16(%rbp)` (сравнить сохранённый `p` с нулём) и `jne .L2` (перепрыгнуть ветку `return -1`, если не равен); третья, `movl $-1, %eax`, — тело самой ветки.

На `-O2` от функции остаются две инструкции:

```asm
first:
	movl	(%rcx), %eax     ; v = *p
	ret                      ; return v
```

Ни `cmpq`, ни `jne`, ни `movl $-1` — проверка и вся её ветка **удалены**, а не перенесены: искать их в другом месте листинга бесполезно, кода для них не сгенерировано вовсе. Контрольный опыт — та же сборка с отключённым допущением:

```asm
; gcc -std=c17 -S -O2 -fno-delete-null-pointer-checks first.c
first:
	testq	%rcx, %rcx       ; if (p == 0)   — проверка вернулась
	je	.L3
	movl	(%rcx), %eax
	ret
.L3:
	movl	$-1, %eax
	ret
```

Проверка та же по смыслу, но записана иначе: `testq %rcx, %rcx` вместо `cmpq $0, …`. Это обычная замена — «И» регистра с самим собой выставляет флаг нуля ровно тогда, когда регистр нулевой, и инструкция короче сравнения с константой. Полезная привычка: узнавать проверку на ноль в обеих формах.

**(б) Почему рассуждение оптимизатора корректно.** Цепочка из трёх шагов, каждый — по §13.1.1 и §13.1.3:

1. В функции `*p` выполняется **до** сравнения. Если бы `p` был нулевым, это разыменование было бы неопределённым поведением (строка 2 каталога, N3220 §6.5.4.2).
2. Стандарт не налагает **никаких** требований на выполнение программы с UB. Значит, для любой программы, которую стандарт обязывает работать правильно, случай `p == 0` до строки `int v = *p;` не доходит.
3. Следовательно, генерируя код в предположении «`p != 0` после разыменования», компилятор не нарушает контракт **ни для одной корректной программы** — а некорректные контрактом не защищены. Ветка `if (p == 0)` в этом предположении недостижима, и удалить недостижимый код — обычная, полностью законная оптимизация.

Это не самодеятельность: допущение документировано в руководстве GCC как `-fdelete-null-pointer-checks` (C17), включено по умолчанию, и формулировка там ровно наша — «если указатель проверяется после того, как уже был разыменован, он не может быть нулевым».

**(в) Почему `-fno-delete-null-pointer-checks` — не исправление.** Три довода, от частного к общему:

1. **Флаг не меняет исходный текст.** UB — свойство программы, а не сборки (§13.1.3). Функция `first` останется ошибочной для другого компилятора, другой версии того же компилятора и для любой сборки, где флаг забыли. Исправление, действующее лишь при одном наборе ключей, — не исправление, а настройка окружения.
2. **Флаг лечит симптом, а не болезнь.** Он возвращает проверку, но не делает разыменование нулевого указателя безопасным: при `p == NULL` программа теперь честно попытается прочитать по нулевому адресу и, если повезёт, упадёт. Мы всего лишь поменяли одно проявление UB на другое.
3. **Цена — по всей программе.** Допущение отключается глобально для единицы трансляции: оптимизатор перестаёт использовать его и там, где код написан правильно. Платит вся программа, чинится — ничего.

Руководство GCC (C17) и относит такие ключи к средствам совместимости со старым кодом, а рекомендация CERT MSC15-C (C10) формулирует настоящее решение: **проверять предусловия до операции, а не последствия после**.

**Исправление.** Достаточно поменять местами две строки:

```c
/* first_ok.c — проверка предусловия ДО разыменования */
int first_ok(int *p)
{
    if (p == 0)        /* сначала проверка...        */
        return -1;
    return *p;         /* ...и только потом чтение   */
}
```

Ассемблер на `-O2` (эталон) — проверка на месте, при **включённом** по умолчанию `-fdelete-null-pointer-checks`:

```asm
first_ok:
	testq	%rcx, %rcx       ; if (p == 0)
	je	.L3
	movl	(%rcx), %eax     ; return *p
	ret
.L3:
	movl	$-1, %eax        ; return -1
	ret
```

**Почему теперь оптимизатор не вправе её удалить.** Рассуждение из пункта (б) больше не запускается: оно начиналось со слов «разыменование уже произошло, значит…». Теперь на пути к `*p` стоит проверка, и вход `p == 0` ведёт в ветку `return -1`, **не** разыменовывая ничего. Значит, в этой функции нет ни одного выполнения с UB — а раз нет UB, то нет и предположения, из которого можно вывести «`p != 0`». Обе ветки достижимы в корректных программах, обе обязаны работать по правилам языка, и убрать любую из них компилятор не может: это изменило бы наблюдаемое поведение программы, которую стандарт обязывает выполнять как написано.

Прогон (эталон; функция вызвана на трёх входах):

```
first_ok(&x)         = 42
first_ok(&minus_one) = -1
first_ok(NULL)       = -1
```

**Ответ:** (а) проверке соответствуют `cmpq $0, 16(%rbp)` и `jne .L2` (в форме с `testq` — `testq %rcx, %rcx` и `je`), плюс ветка `movl $-1, %eax`; на `-O2` они не перемещены, а **удалены** — тело функции сводится к `movl (%rcx), %eax; ret`. (б) Оптимизатор корректен: разыменование до проверки делает случай `p == 0` неопределённым поведением, поведение программ с UB стандартом не регламентировано, поэтому предположение «`p != 0`» не может навредить ни одной корректной программе; допущение документировано как `-fdelete-null-pointer-checks`. (в) `-fno-delete-null-pointer-checks` не исправляет ошибку, потому что не меняет исходный текст (UB остаётся для любого другого компилятора и любой другой сборки), не делает разыменование нуля безопасным и отключает допущение по всей единице трансляции. Правильное исправление — перенести `if (p == 0)` **выше** `*p`; после этого ни одно выполнение функции не содержит UB, предположения «`p != 0`» взяться неоткуда, обе ветки достижимы, и проверка остаётся в коде даже на `-O2` (подтверждено листингом).

**Вариант 2 (предусловие в контракте, а не в проверке).** У исправления выше есть неприятное свойство, которое видно прямо в прогоне: `first_ok(&minus_one)` и `first_ok(NULL)` вернули **одно и то же** значение `-1`. Функция смешала в одном `int` две разные вещи — «значение элемента» и «значения нет», а `-1` вполне может быть настоящим значением. Второй подход разделяет их: функция объявляет предусловие и не проверяет ничего, а «есть ли указатель» решает вызывающий — там, где эта информация действительно есть.

```c
/* contract.c — предусловие вынесено в контракт: проверяет вызывающий */
#include <stdio.h>

/* ТРЕБУЕТ: p != NULL. Значение и признак «есть значение» разделены. */
int first_val(const int *p)
{
    return *p;
}

static void show(const int *p)
{
    if (p != NULL)                       /* проверка — на стороне вызывающего */
        printf("value = %d\n", first_val(p));
    else
        printf("no value\n");
}

int main(void)
{
    int x = 42;
    int minus_one = -1;

    show(&x);
    show(&minus_one);
    show(NULL);
    return 0;
}
```

Прогон (эталон):

```
value = 42
value = -1
no value
```

Теперь `-1` — это просто число, а отсутствие значения выражено отдельно и ни с чем не путается.

*Сравнение.* Первый вариант **самодостаточен**: функция безопасна при любом входе, и её нельзя применить неправильно — за это его и выбирают для границ подсистемы, где вызывающий чужой и доверять ему нечего. Плата — перегруженное возвращаемое значение: `-1` означает и ошибку, и законное число, а различить их вызывающий не может (ровно та беда, к которой мы вернёмся в §13.2.2, когда `Option<T>` разведёт эти случаи по типам). Второй вариант **честен по типам**: функция делает одно дело, признак наличия живёт отдельно, а проверка стоит там, где решение о `NULL` действительно принимается, — и не повторяется на каждом уровне вызова, экономя и код, и время. Плата — контракт держится на дисциплине: компилятор C не потребует от вызывающего проверить указатель (в отличие от Rust, где ветка `None` обязательна), и забытая проверка снова даёт строку 2 каталога. Практическое правило: на внешней границе модуля — самодостаточная проверка внутри функции; во внутренних, «горячих» функциях, вызываемых из проверенного кода, — контракт, записанный в комментарии к сигнатуре, и проверка один раз наверху.

### Г13.Ч1.З5

**Условие.** Запуск `unseq.c` (`int r = i++ + i++;` при `i = 5`) на нашей машине напечатал `r = 11, i = 7`; компилятор при этом выдал предупреждение `-Wsequence-point`. Объясните: (а) почему полагаться на `11` и `7` нельзя; (б) чем этот случай *категориально* отличается от порядка вычисления аргументов из §4.2.2 — там программа оставалась корректной, здесь нет (обе ссылки — на §13.1.1); (в) почему это UB ловится компилятором статически, а выход за границы из `oob.c` — нет.

**Решение.** Воспроизведём протокол (⛔ программа неисправна намеренно):

```c
/* unseq.c — два неупорядоченных изменения одной переменной (строка 8 каталога) */
#include <stdio.h>

int main(void)
{
    int i = 5;
    int r = i++ + i++;
    printf("r = %d, i = %d\n", r, i);
    return 0;
}
```

Сборка на эталоне даёт предупреждение и работающий исполняемый файл:

```
gcc -std=c17 -Wall -Wextra unseq.c -o unseq.exe
unseq.c: In function 'main':
unseq.c:7:20: warning: operation on 'i' may be undefined [-Wsequence-point]
    7 |     int r = i++ + i++;
      |                   ~^~

./unseq.exe
r = 11, i = 7
```

Та же сборка с `-O2` печатает то же самое: `r = 11, i = 7`.

**(а) Почему на `11` и `7` полагаться нельзя.** Норматив — N3220 §6.5.1¶2 (строка 8 каталога): если побочный эффект над скалярным объектом не упорядочен относительно другого побочного эффекта над тем же объектом или чтения его значения, поведение **не определено**. В выражении `i++ + i++` два побочных эффекта (два инкремента `i`) и два чтения `i`, и стандарт не задаёт между ними никакого порядка — значит, это UB, а не «одно из нескольких допустимых значений».

Отсюда три следствия, каждое из которых по отдельности запрещает опираться на наблюдение:

1. **Стандарт не обещает ни `11`, ни `7`, ни вообще какого-либо результата.** Совпадение вывода на `-O0` и `-O2` — свойство одной сборки одного компилятора, а не программы (та же логика, что в Г13.Ч1.З2: устойчивость наблюдения не есть гарантия).
2. **Пострадать может не только `r`.** Примечание 3 к N3220 §3.5.3 гарантирует наблюдаемое поведение лишь **до** первой операции с UB; всё, что дальше, может быть искажено — в том числе значение `i`, вывод `printf`, соседние переменные.
3. **Компилятор сам предупреждает осторожно:** `operation on 'i' may be undefined` — «может быть неопределена». Это не «результат будет 11», а «я вижу конструкцию, у которой результата может не быть вовсе».

Если инкременты нужны оба — их надо **упорядочить**, разбив выражение на две инструкции (`;` — точка следования): `int r = i++; r += i++;`. Тогда результат определён и равен тем же `11` и `7` — но уже по правилам языка, а не по милости компилятора.

**(б) Категориальное отличие от §4.2.2.** Оба случая — про «порядок», но категории разные, и различие ровно то, что вводит §13.1.1:

| | §4.2.2: `printf("%d %d %d", f(), f(), f())` | §13.1.4/здесь: `i++ + i++` |
|---|---|---|
| Категория | **unspecified behavior** | **undefined behavior** |
| Что не определено | порядок вычисления аргументов | порядок побочных эффектов над одним объектом |
| Множество исходов | конечное множество допустимых: любая перестановка результатов | никакого множества нет: требований к программе не предъявляется вообще |
| Корректна ли программа | **да** — она корректна, просто её вывод зависит от невидимого выбора | **нет** — программа не имеет смысла с точки зрения стандарта |
| Что можно гарантировать | что напечатаны будут именно значения, возвращённые тремя вызовами `f` | ничего, в том числе и о том, что случится после этой строки |

Разница практическая, а не терминологическая. Программу из §4.2.2 можно починить, не меняя её сути: достаточно вычислить вызовы в отдельные переменные, и все допустимые исходы схлопнутся в один — при этом даже «нечинёная» версия не может, например, испортить память. Программа с `i++ + i++` нечинима в этом смысле: пока выражение в тексте, у программы нет определённого поведения, и границ ущерба нет. Формулируя коротко: unspecified — это «результат один из нескольких», UB — это «результата нет».

**(в) Почему одно ловится статически, а другое нет.** Потому что это утверждения разной природы.

- **`i++ + i++` — свойство текста.** Чтобы его увидеть, не нужно знать ни одного значения времени выполнения: достаточно заметить два побочных эффекта над одним и тем же объектом внутри одного выражения без точек следования между ними. Такой анализ компилятор делает по дереву разбора всегда и для всех входов сразу — это и есть `-Wsequence-point`. Заметьте, впрочем, и его границы: он честно говорит `may be undefined`, потому что «один и тот же объект» компилятор надёжно узнаёт лишь тогда, когда это видно синтаксически; спрячьте один из инкрементов за указателем в другой функции — предупреждение исчезнет, а UB останется.
- **`a[i]` в `oob.c` — свойство пары «программа + вход».** Индекс `i = argc + 3` известен только при запуске. Чтобы вынести вердикт на этапе компиляции, компилятор должен был бы доказать утверждение о **всех** возможных значениях `argc`, то есть проанализировать не текст, а множество всех выполнений. В общем случае такая задача неразрешима: границы могут прийти из файла, из сети, из другой единицы трансляции. Поэтому GCC ловит лишь частные случаи (константный индекс в массиве известного размера — предупреждение `-Warray-bounds`), а общий случай оставляет динамическим инструментам (§13.1.4) — со всеми их ограничениями (Г13.Ч1.З6).

**Ответ:** (а) `i++ + i++` — неупорядоченные побочные эффекты над одним объектом (N3220 §6.5.1¶2, строка 8 каталога), то есть UB: стандарт не обещает ни `11`, ни `7`, а по примечанию 3 к N3220 §3.5.3 искажено может быть и всё, что следует за этой строкой; совпадение вывода на `-O0` и `-O2` — свойство сборки, а не программы, и сам компилятор пишет `may be undefined`. (б) В §4.2.2 порядок вычисления аргументов — **unspecified**: программа корректна, а её результат — один из нескольких допустимых; здесь — **UB**: программа некорректна, множества допустимых исходов не существует, и ущерб ничем не ограничен. Кратко: «результат один из нескольких» против «результата нет». (в) `i++ + i++` — свойство исходного текста, видимое по дереву выражения без каких-либо значений времени выполнения, поэтому проверяется статически (`-Wsequence-point`); выход за границы в `oob.c` — свойство пары «программа + вход» (`i` зависит от `argc`), и его статическая проверка потребовала бы доказательства для всех возможных входов, что в общем случае невозможно.

### Г13.Ч1.З6

**Условие.** Объясните, почему «программа прошла все тесты под UBSan и ASan» не означает «в программе нет UB». Проверьте на опыте, есть ли у `oob.c` из §13.1.2 запуск, при котором UBSan молчит: переберите оба осмысленных входа (без аргумента и с аргументом) и приведите обе командные строки с отчётами. Затем измените в программе одну цифру так, чтобы «чистый» запуск появился, и покажите оба прогона исправленной версии. Сформулируйте, чем принципиально ограничен любой динамический инструмент, — и какое свойство должен иметь инструмент, лишённый этого ограничения.

**Решение.** Начнём с главного утверждения, затем — с эксперимента, который упирается в занятную подробность.

**Почему «чисто под санитайзерами» ≠ «нет UB».** Санитайзеры — **динамические** инструменты: компилятор вставляет проверки в код, и эти проверки срабатывают только тогда, когда управление до них дошло и данные оказались «теми самыми» (C18). Из этого следуют три ограничения, и все три мы уже наблюдали в этой главе:

1. **Виден только выполненный путь.** Ветка, не выбранная на этом прогоне, не проверяется вовсе.
2. **Виден только данный вход.** UB — свойство пары «программа + вход» (§13.1.2, «типичные ошибки»): одна и та же строка `a[i]` безупречна при `i = 3` и фатальна при `i = 4`.
3. **У каждого инструмента свой список классов.** Даже случившееся UB может остаться незамеченным, если оно не в списке. Мы видели это дважды: UBSan **не заметил** чтения `a[5]` через параметр-указатель в Г13.Ч1.З7 (размер массива не виден в типе), а ASan **не заметил** чтения `data[len]` в векторе из Г13.Ч1.З8 (адрес попал в запас ёмкости, то есть внутрь выделенного блока).

Чистый вердикт означает ровно одно: «на этих прогонах, с этими входами, проверки этого инструмента не сработали».

**Эксперимент с `oob.c`: запуска, при котором UBSan молчит, у этой программы нет.** Условие просит перебрать оба входа — перебираем, и арифметика программы отвечает сразу:

```c
/* oob.c — чтение элемента 4 массива из четырёх элементов (индексы 0..3) */
    int a[4] = {10, 20, 30, 40};
    int i = argc + 3;              /* при запуске без аргументов i == 4 */
```

Допустимые индексы — 0…3, а `i = argc + 3`, причём при обычном запуске `argc >= 1` (имя программы всегда передаётся). Значит, `i >= 4` **всегда**, и каждый лишний аргумент только уводит индекс дальше за границу. Проверка в WSL — два запуска, оба с отчётом:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined oob.c -o oob_ub

./oob_ub
oob.c:9:32: runtime error: index 4 out of bounds for type 'int [4]'
oob.c:9:5: runtime error: load of address 0x7fffe3914030 with insufficient space for an object of type 'int'
a[4] = -477019952

./oob_ub x
oob.c:9:32: runtime error: index 5 out of bounds for type 'int [4]'
oob.c:9:5: runtime error: load of address 0x7fffdd198d84 with insufficient space for an object of type 'int'
a[5] = 32767
```

(Отчёт UBSan об индексе состоит из двух строк: первая — про сам индекс, вторая — про чтение по получившемуся адресу; после второй инструмент печатает ещё дамп байтов вокруг адреса, он здесь опущен.)

Обратите внимание и на вывод без санитайзера — три запуска подряд, три разных числа: `a[4] = -25105104`, `-865634656`, `-192607184`. Программа не падает и «работает».

**Программа, на которой демонстрация получается.** Нужен индекс, который *зависит от входа* и *может быть допустимым*, — правки одной цифры достаточно:

```c
/* oob2.c — индекс зависит от ввода и МОЖЕТ быть допустимым (правка одной цифры) */
#include <stdio.h>

int main(int argc, char **argv)
{
    (void)argv;
    int a[4] = {10, 20, 30, 40};
    int i = argc + 2;              /* без аргументов i == 3, с одним — 4 */
    printf("a[%d] = %d\n", i, a[i]);
    return 0;
}
```

Два запуска одного и того же исполняемого файла, собранного с UBSan (WSL):

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined oob2.c -o oob2_ub

./oob2_ub
a[3] = 40                     ← UBSan молчит: индекс 3 допустим

./oob2_ub x
oob2.c:9:32: runtime error: index 4 out of bounds for type 'int [4]'
a[4] = -733139856             ← тот же файл, тот же инструмент, другой вход
```

Вот и вся демонстрация: **инструмент не изменился, программа не изменилась — изменился вход**. Первый прогон — «чисто», второй — отчёт. Если бы в наборе тестов был только первый, вердикт «UB нет» был бы получен, подписан и ошибочен.

**Чем принципиально ограничен динамический инструмент и что нужно вместо него.** Динамическая проверка — это наблюдение за **одним** выполнением: она отвечает на вопрос «случилось ли нарушение сейчас?». Вопрос же, который нас интересует, — «может ли нарушение случиться когда-нибудь?» — квантифицирован по **всем** входам и всем путям, а их бесконечно много. Никакое конечное число прогонов не покрывает бесконечное множество; отсюда классическая формула: тестирование (и санитайзеры как его усиление) способно показать **наличие** ошибок, но не их **отсутствие**.

Инструмент, лишённый этого ограничения, должен работать **по тексту программы, а не по её прогону**, и делать утверждения сразу обо всех возможных выполнениях. Практически это означает три свойства:

- **статичность** — вердикт выносится на этапе компиляции, без запуска и без входных данных;
- **универсальность по входам** — утверждение вида «ни при каких значениях `argc` этот индекс не выйдет за границу», а не «при `argc == 1` не вышел»;
- **консервативность** — раз доказать безопасность в общем случае невозможно (мы обсуждали это в Г13.Ч1.З5), инструмент обязан отвергать подозрительное, а не пропускать сомнительное; ценой становятся отказы на некоторых корректных программах.

Именно так устроен ответ, которым заканчивается том I: компилятор Rust проверяет владение, времена жизни и правила ссылок **статически**, а то, что статически проверить нельзя дёшево (индекс массива), превращает не в UB, а в проверку на каждом доступе с гарантированной паникой (§13.2.2). Первое — свойство «для всех входов», второе — «для каждого доступа каждого прогона»; санитайзеры не дают ни того, ни другого.

**Ответ:** «чисто под UBSan и ASan» означает лишь «на выполненных путях, с использованными входами, проверки этих инструментов не сработали»: динамическая проверка видит только реально случившееся UB, а UB — свойство пары «программа + вход». У `oob.c` из §13.1.2 запуска с молчащим UBSan **не существует**: `i = argc + 3`, `argc >= 1`, значит `i >= 4` при любой командной строке, тогда как допустимы 0…3 (проверено: `./oob_ub` → `index 4 out of bounds`, `./oob_ub x` → `index 5 out of bounds`). Демонстрация получается на программе с индексом, который может оказаться допустимым, — `oob2.c` с `int i = argc + 2`: командная строка **`./oob2_ub`** (без аргументов) даёт `a[3] = 40` и полное молчание UBSan, а `./oob2_ub x` на том же файле — `runtime error: index 4 out of bounds for type 'int [4]'`. Принципиальное ограничение любого динамического инструмента: он проверяет одно выполнение, а вопрос «есть ли в программе UB» квантифицирован по всем входам и путям — конечное число прогонов не покрывает бесконечного множества, поэтому такие инструменты показывают наличие ошибок, но не их отсутствие. Инструмент без этого ограничения обязан быть **статическим**: выносить вердикт по тексту программы до запуска, утверждать сразу обо всех возможных выполнениях и быть консервативным (отвергать подозрительное) — именно эти свойства у проверок компилятора Rust из части 13.2.

### Г13.Ч1.З7

**Условие.** *(прикладное)* Проведите аудит функции по каталогу §13.1.2 — найдите **все четыре** класса UB, укажите номера строк каталога и исправьте каждый (сигнатуру можно менять):

```c
/* среднее значение элементов между first и last включительно */
int avg_range(const int *a, int n, int first, int last)
{
    int sum = 0;
    for (int i = first; i <= last; i++)   /* границы не проверяются   */
        sum += a[i];                      /* сумма может переполниться */
    return sum / (last - first + 1);      /* а если диапазон пуст?     */
}
/* вызов: avg_range(arr, 5, 0, 5) при int arr[5] */
```

(Считайте: четвёртый класс — в самом вызове из комментария.)

**Решение.** Аудит начнём не с чтения, а с компиляции: эталонные флаги уже дают первую зацепку (⛔ программа неисправна намеренно; массив в `main` инициализирован — иначе к разбираемым классам добавился бы ещё один, чтение неопределённого значения, которого в каталоге §13.1.2 нет).

```
gcc -std=c17 -Wall -Wextra avg_bad.c -o avg_bad.exe
avg_bad.c: In function 'avg_range':
avg_bad.c:5:33: warning: unused parameter 'n' [-Wunused-parameter]
    5 | int avg_range(const int *a, int n, int first, int last)
      |                             ~~~~^
```

Функция принимает размер массива и **ни разу его не смотрит**. Это ключ ко всему аудиту: единственный параметр, который знает, где кончается массив, в теле не участвует.

**Четыре класса по каталогу §13.1.2.**

1. **Строка 1 — выход за границы массива.** Тот самый класс, который, как подсказывает условие, виден именно в вызове. В теле дефект пока лишь *возможен*: функция не знает границ, и корректность целиком зависит от аргументов. Вызов `avg_range(arr, 5, 0, 5)` при `int arr[5]` делает его *неизбежным*: цикл идёт `i = 0…5` и на последней итерации читает `a[5]` — шестой элемент пятиэлементного массива (N3220 §6.5.7, J.2(46)). Симметричная беда — отрицательный `first`: `a[-1]` тоже за границей.
2. **Строка 5 — знаковое переполнение.** `sum += a[i]`: сумма пяти-шести `int` переполнится легко, а знаковое переполнение — UB (§6.5.1¶5), со всеми последствиями §13.1.3. В той же строке каталога — ещё два скрытых экземпляра: выражение `last - first + 1` при экстремальных аргументах (например, `first = INT_MIN`, `last = INT_MAX`) и счётчик `i++` при `last == INT_MAX` (после последней итерации инкремент переполнится).
3. **Строка 6 — деление на ноль.** `sum / (last - first + 1)`: при `last == first - 1` (пустой диапазон — цикл не выполнится ни разу) знаменатель равен нулю (§6.5.6¶6).
4. **Строка 2 — разыменование инвалидного указателя.** Функция не проверяет `a`: вызов `avg_range(NULL, 5, 0, 4)` разыменует нулевой указатель на первой же итерации (§6.5.4.2). Контракта, который запрещал бы такой вызов, у функции нет — ни в сигнатуре, ни в комментарии.

**Предъявляем первый класс запуском.** Три запуска подряд одного и того же файла (эталон, MinGW):

```
./avg_bad.exe    avg = 113
./avg_bad.exe    avg = 86
./avg_bad.exe    avg = 99
```

Массив `{1, 2, 3, 4, 5}`, среднее пяти элементов равно 3 — а печатаются трёхзначные числа, каждый раз новые: в сумму попадает мусор из-за границы, да ещё и делится она на 6 вместо 5. Программа не падает.

Санитайзеры в WSL расставляют роли:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined avg_bad.c -o avg_bad_ub
./avg_bad_ub
avg = 5421                     ← UBSan МОЛЧИТ

gcc -std=c17 -Wall -Wextra -fsanitize=address avg_bad.c -o avg_bad_as
./avg_bad_as
==141==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f065def9034 ...
READ of size 4 at 0x7f065def9034 thread T0
    #0 ... in avg_range
    #1 ... in main
Address 0x7f065def9034 is located in stack of thread T0 at offset 52 in frame
    #0 ... in main
  This frame has 1 object(s):
    [32, 52) 'arr' (line 15) <== Memory access at offset 52 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow ... in avg_range
```

ASan называет всё поимённо: чтение 4 байт, кадр `main`, объект `arr` занимает байты 32…52, а обращение пришлось на смещение 52 — первый байт **за** массивом. Молчание UBSan тоже поучительно: его проверка границ работает по типу, а внутри функции массив известен лишь как `const int *` — размера в типе нет, проверять не с чем. Это прямо перекликается с Г13.Ч1.З8: у каждого инструмента свой список того, что он вообще способен увидеть.

**Исправление.** Меняем сигнатуру: результат уходит в выходной параметр, а возвращаемое значение становится кодом успеха — иначе «среднее» и «ошибка» не разделить (та же беда с перегруженным `-1`, что и в Г13.Ч1.З4). Все проверки — **предусловия до операции**, по MSC15-C (§13.1.3).

```c
/* avg_fix1.c — все четыре класса закрыты: предусловия + расширенный аккумулятор */
#include <limits.h>
#include <stdio.h>

/* Среднее a[first..last] включительно.
   Возвращает 0 и кладёт результат в *out; при недопустимых аргументах — -1. */
int avg_range(const int *a, int n, int first, int last, int *out)
{
    if (a == NULL || out == NULL)                 /* строка 2 каталога */
        return -1;
    if (n <= 0 || first < 0 || last >= n)         /* строка 1 каталога */
        return -1;
    if (first > last)                             /* строка 6 каталога */
        return -1;

    long long sum = 0;                            /* строка 5 каталога */
    for (int i = first; i <= last; i++)
        sum += a[i];

    *out = (int)(sum / (last - first + 1));       /* среднее всегда влезает в int */
    return 0;
}
```

Как закрыт каждый класс:

- **Строка 2** — явная проверка `a == NULL` (и `out == NULL`, раз уж результат отдаётся по указателю).
- **Строка 1** — `first >= 0` и `last < n`: теперь параметр `n` работает, и предупреждение `-Wunused-parameter` исчезает само.
- **Строка 6** — `first > last` отвергается, значит `last - first + 1 >= 1`: знаменатель никогда не ноль. Заодно исчезает и переполнение самого выражения `last - first + 1`: после проверок `0 <= first <= last < n`, так что разность лежит в диапазоне `0…n-1`.
- **Строка 5** — аккумулятор `long long`. Слагаемых не больше `n <= INT_MAX ≈ 2³¹`, каждое по модулю не больше `2³¹`, значит сумма по модулю меньше `2⁶²` и в 64-битный тип помещается с запасом. Переполнения счётчика `i++` тоже больше нет: `last < n <= INT_MAX`, поэтому после последней итерации `i` доходит максимум до `last + 1 <= INT_MAX`.
- Обратное преобразование `(int)` безопасно: среднее арифметическое лежит между наименьшим и наибольшим элементами, а они — `int`.

Прогон (эталон; те же результаты в WSL под UBSan и под ASan — оба чисты):

```
arr[0..4]: avg = 3
arr[0..5]: rejected
arr[3..2]: rejected
arr[-1..2]: rejected
NULL: rejected
big[0..2]: avg = 2147483647
```

Первая строка — корректный ответ на корректный вход (среднее `{1,2,3,4,5}` равно 3, а не 113). Четыре следующие — отвергнутые вызовы, каждый на своём классе. Последняя — массив `{INT_MAX, INT_MAX, INT_MAX}`: сумма `3 · 2147483647` в `int` не поместилась бы, а в `long long` считается точно, и среднее верное.

**Отдельно — про логику.** В исходной функции есть и пятый дефект, но **не** UB: при вызове с `last == n` она делит на `last - first + 1`, то есть на 6, тогда как элементов пять. После исправления такой вызов отвергается, и вопрос снимается, — но заметьте разницу категорий: неправильный делитель у корректной по памяти функции был бы «просто» неверным ответом, и ни один санитайзер его бы не нашёл. Эту границу мы ещё раз проведём в Г13.Ч2.З6: инструменты (и Rust) закрывают класс *неопределённого поведения*, а не класс *ошибок*.

**Ответ:** четыре класса каталога §13.1.2 — **строка 1** (выход за границы: цикл идёт до `last`, не глядя на `n`; вызов `avg_range(arr, 5, 0, 5)` при `int arr[5]` читает `a[5]`), **строка 5** (знаковое переполнение в `sum += a[i]`, а также в `last - first + 1` и в счётчике `i++` при `last == INT_MAX`), **строка 6** (деление на ноль при пустом диапазоне `last == first - 1`) и **строка 2** (разыменование инвалидного указателя: `a` не проверяется на `NULL`). Компилятор подсказывает главное уже при сборке: `warning: unused parameter 'n'` — функция получает размер массива и не использует его. Исправление меняет сигнатуру на `int avg_range(const int *a, int n, int first, int last, int *out)` и ставит **предусловия до операций**: `a != NULL && out != NULL`, `n > 0 && first >= 0 && last < n`, `first <= last`; аккумулятор — `long long`. После этого все четыре класса закрыты (проверено запусками и обоими санитайзерами в WSL), а корректный вход даёт корректный ответ `avg = 3` вместо трёх разных трёхзначных чисел у исходной версии.

**Вариант 2 (аккумулятор остаётся `int`, переполнение проверяется до сложения).** Расширение типа — не единственный способ закрыть строку 5. Можно оставить `int` и применить тот же приём, что и ко всем остальным классам: проверять **предусловие** каждого сложения, как предписывает MSC15-C (§13.1.3, «`if (x > INT_MAX - step)` — до сложения, а не `if (x + step < x)` — после»).

```c
/* avg_fix2.c — то же, но аккумулятор остаётся int: переполнение ловится ДО сложения */
int avg_range(const int *a, int n, int first, int last, int *out)
{
    if (a == NULL || out == NULL)                 /* строка 2 каталога */
        return -1;
    if (n <= 0 || first < 0 || last >= n)         /* строка 1 каталога */
        return -1;
    if (first > last)                             /* строка 6 каталога */
        return -1;

    int sum = 0;
    for (int i = first; i <= last; i++) {
        int x = a[i];
        if ((x > 0 && sum > INT_MAX - x) ||       /* строка 5 каталога: */
            (x < 0 && sum < INT_MIN - x))         /* предусловие ДО сложения */
            return -1;
        sum += x;
    }

    *out = sum / (last - first + 1);
    return 0;
}
```

Условие проверки читается так: прибавлять положительное `x` безопасно, пока `sum` не превысил `INT_MAX - x`; прибавлять отрицательное — пока `sum` не опустился ниже `INT_MIN - x`. Обе границы вычисляются **вычитанием**, которое здесь заведомо не переполняется (из максимума вычитается положительное, из минимума — отрицательное), так что сама проверка UB не содержит.

Прогон (эталон; в WSL под обоими санитайзерами — чисто):

```
arr[0..4]: avg = 3
arr[0..5]: rejected
arr[3..2]: rejected
arr[-1..2]: rejected
NULL: rejected
big[0..2]: rejected          ← отличие от варианта 1
```

*Сравнение.* Пять строк из шести совпадают, и различие ровно в последней. Вариант с `long long` **считает** сумму трёх `INT_MAX` и выдаёт правильное среднее `2147483647`; вариант с проверками **отказывается** её считать, хотя ответ существует и представим в `int`. Это цена подхода: проверка консервативна — она отвергает по промежуточной сумме, ничего не зная о том, что дальше в массиве идут отрицательные числа, которые вернули бы её в диапазон. Зато у него есть свойство, которого нет у первого: он **не опирается на соотношение ширин типов**. Вариант 1 корректен, пока `long long` шире `int`, — на нашей платформе (`int` = 4 байта, `long long` = 8) это так, но сама ширина типов, как мы выяснили в Г13.Ч1.З1, категория implementation-defined, и на платформе с 64-битным `int` расширять было бы нечем. Вариант 2 переносим абсолютно: он пользуется только `INT_MAX`/`INT_MIN` из `<limits.h>`, то есть значениями, которые платформа обязана объявить сама. Есть и разница в стоимости: вариант 1 — одно сложение на элемент, вариант 2 — сложение плюс пара сравнений и вычитание; на длинных массивах это заметно. Практическое правило: если под рукой заведомо более широкий тип и требуется **точный ответ** — расширяйте аккумулятор; если код должен переносимо работать где угодно или переполнение по смыслу задачи означает «данные испорчены, считать нечего» — проверяйте предусловие и отказывайте. И то и другое лучше третьего варианта, который встречается чаще обоих: сложить и посмотреть, что получилось.

### Г13.Ч1.З8

**Условие.** *(прикладное)* Возьмите ваш вектор из §9.1.1 (или эталонное решение) и прогоните его тестовую программу в WSL двумя санитайзерами: `-fsanitize=undefined` и `-fsanitize=address`. Заодно выясните на опыте, дружат ли санитайзеры между собой: соберите программу с обоими ключами сразу, а потом попробуйте пару `-fsanitize=address -fsanitize=thread` — и приведите сообщение оттуда, где сборка не проходит. Отчёт: команды сборки, вердикты, и объяснение — какие строки каталога §13.1.2 покрывает каждый из двух прогонов и какие не покрывает ни один.

**Решение.** Берём вектор из §9.1.1 целиком, как эталонное решение: `vec_init`, `vec_push` с удвоением через `realloc`, `vec_free`, и тестовая программа — пять `push` с печатью `len`/`cap`, затем печать содержимого и освобождение.

**Команды сборки и вердикты** (WSL Ubuntu 24.04, gcc 13.3.0):

```
push 20: len=2 cap=2

push 40: len=4 cap=4

код завершения: 0, отчётов нет
```

Оба вердикта чистые, вывод совпадает с §9.1.1 дословно. ASan не сообщил и об утечках — на Linux он включает LeakSanitizer по умолчанию (§7.2.2); проверено от противного: если убрать вызов `vec_free`, тот же прогон даёт `ERROR: LeakSanitizer: detected memory leaks` и `Direct leak of 32 byte(s) in 1 object(s)` с кадром `vec_push` (блок, полученный последним `realloc`), а код завершения меняется на 1. Для полноты — тот же файл под Memcheck: `valgrind --leak-check=full -q ./vec_plain` тоже молчит, а версия без `vec_free` даёт `32 bytes in 1 blocks are definitely lost`.

**Проверка совместимости флагов.** Условие просит выяснить это на опыте — выясняем:

```
gcc -std=c17 -Wall -Wextra -fsanitize=address -fsanitize=undefined vec_test.c -o vec_both
(собралось без единого сообщения)
./vec_both
(тот же вывод, код завершения 0)
```

На нашем контуре **ASan и UBSan совместимы**: собираются и работают вместе. Более того, комбинированная сборка честно ловит ошибки: та же связка на `avg_bad.c` из Г13.Ч1.З7 выдала полный отчёт ASan о `stack-buffer-overflow`. Несовместимая пара — другая:

```
gcc -std=c17 -Wall -Wextra -fsanitize=address -fsanitize=thread vec_test.c -o vec_at
cc1: error: '-fsanitize=thread' is incompatible with '-fsanitize=address'
```

Вот то сообщение, которое просит привести условие: не дружат **ASan и TSan**, а вовсе не ASan с UBSan. Причина понятна из §13.1.4: ASan и TSan оба перестраивают раскладку адресного пространства и перехватывают одни и те же функции работы с памятью и потоками; ужиться в одном процессе они не могут. UBSan устроен иначе — он лишь вставляет проверки вокруг арифметики и обращений, чужую раскладку памяти не трогает, поэтому уживается с обоими. Практический вывод не меняется: **TSan-прогон — всегда отдельная сборка** (что мы и делаем в Г13.Ч1.З9).

**Какие строки каталога покрывает каждый прогон.** Чистый вердикт стоит чего-то, только если понимать, что инструмент вообще способен увидеть. Проверим это тремя намеренно испорченными копиями вектора (все ⛔).

*Опыт 1 — use-after-free (строка 3).* Печать перенесена за `vec_free`, указатель сохранён в отдельной переменной:

```c
    int *saved = v.data;                  /* копия указателя переживёт vec_free */
    vec_free(&v);
    printf("%d\n", saved[0]);             /* ⛔ use-after-free */
```

```
под ASan:   ==91==ERROR: AddressSanitizer: heap-use-after-free on address 0x503000000040
            READ of size 4 at 0x503000000040 thread T0
            0x503000000040 is located 0 bytes inside of 32-byte region [...)
            freed by thread T0 here:  #1 ... in vec_free  #2 ... in main
            код завершения: 1
под UBSan:  отчётов нет, напечатано -78976, код завершения: 0
```

ASan называет и место освобождения (`vec_free`, вызванный из `main`), и размер блока; UBSan не видит ничего — обращения к освобождённой памяти не в его списке.

*Опыт 2 — выход за границы через параметр-указатель (строка 1).* Это `avg_bad.c` из Г13.Ч1.З7: ASan сообщает `stack-buffer-overflow`, UBSan молчит, потому что размер массива в типе `const int *` не записан.

*Опыт 3 — «промах на единицу» внутри ёмкости.* Цикл печати идёт `i <= v.len` вместо `i < v.len`:

```
под UBSan:    10 20 30 40 50 0              — молчит
под ASan:     10 20 30 40 50 -1094795586    — молчит
под valgrind: Conditional jump or move depends on uninitialised value(s)
              Use of uninitialised value of size 8   ← поймал
```

Самый поучительный из трёх. После пяти `push` ёмкость равна восьми, значит `data[5]` лежит **внутри** выделенного блока — с точки зрения ASan никакого выхода за границы нет, он следит за границами блоков, а не за полем `len` нашей структуры. UB здесь по строке 1 каталога (чтение элемента за пределами занятой части — за границами объекта, который мы туда положили), но инструменту оно не видно; поймал его только Memcheck, и то по косвенному признаку — чтению неинициализированной памяти. Отсюда важный вывод для чистого вердикта из начала решения: он получен на **корректной** программе, но, будь в ней такая ошибка, оба санитайзера промолчали бы.

Сводим наблюдения в таблицу (строки — из каталога §13.1.2):

| Строка каталога | UBSan (`-fsanitize=undefined`) | ASan (`-fsanitize=address`) |
|---|---|---|
| 1 — выход за границы массива | **частично**: только если размер известен из типа (`int a[4]`); через `int *` не видит (опыты 2 и 3) | **частично**: ловит выход за границы **блока** (heap/stack/global); промах внутри запаса ёмкости не видит (опыт 3) |
| 2 — разыменование `NULL`/инвалидного указателя | **да**: `load of null pointer of type 'int'` — до обращения (Г13.Ч1.З3) | **частично**: перехватывает уже случившееся падение — `SEGV on unknown address 0x000000000000` (проверено) |
| 3 — use-after-free, объект вне времени жизни | нет | **да**: `heap-use-after-free` с местом освобождения (опыт 1) |
| 4 — double free, `free` не-malloc-адреса | нет | **да**: `attempting double-free` (§7.2.2) и `attempting free on address which was not malloc()-ed` — оба проверены |
| 5 — знаковое переполнение | **да** (Г13.Ч1.З3) | нет |
| 6 — деление/остаток на ноль | **да** (Г13.Ч1.З3) | нет |
| 7 — сдвиг на ≥ ширины типа | **да** (Г13.Ч1.З1) | нет |
| 8 — неупорядоченные `i++ + i++` | нет | нет |
| 9 — гонка данных | нет | нет |

Заметьте, что часть строки 4 достаётся вообще не санитайзерам: на прямолинейных случаях (`free(p); free(p);` подряд и `free(&x)` для локальной переменной) GCC 13.3 предупреждает ещё при компиляции — `-Wuse-after-free` и `-Wfree-nonheap-object` (проверено). Это верхняя строка таблицы инструментов §13.1.4 в действии: что можно проверить статически и дёшево, проверяется статически.

**Чего не покрывает ни один из двух прогонов.**

- **Строка 9 (гонки данных)** — нужен TSan, и только отдельной сборкой (сообщение выше). В нашем векторе гонок нет по построению — программа однопоточная.
- **Строка 8 (неупорядоченные изменения)** — это свойство текста, а не выполнения: его ловит компилятор предупреждением `-Wsequence-point` (Г13.Ч1.З5), санитайзерам там ловить нечего.
- **Промахи «внутри своего блока»** — опыт 3: логическая граница `len` инструментам неизвестна.
- **И главное — всё, что не случилось на этом прогоне.** Наш тест делает ровно пять `push` и ни одного `pop`; ветка `realloc`, вернувшего `NULL`, не выполнялась ни разу. Чистый вердикт покрывает пройденный путь и данные, а не программу (Г13.Ч1.З6).
- Плюс то, что вообще не UB: утечки (их отдельно ловит LeakSanitizer/Memcheck) и логические ошибки (не ловит никто).

**Ответ:** команды — `gcc -std=c17 -Wall -Wextra -fsanitize=undefined vec_test.c -o vec_ub` и `gcc -std=c17 -Wall -Wextra -fsanitize=address vec_test.c -o vec_as`; оба прогона **чисты** (код завершения 0, ни одного отчёта, вывод совпадает с §9.1.1, утечек нет). Проверка совместимости даёт результат, отличный от ожидаемого условием: **ASan и UBSan на GCC 13.3 работают вместе** (комбинированная сборка собирается, запускается и ловит ошибки); несовместимы **ASan и TSan** — `cc1: error: '-fsanitize=thread' is incompatible with '-fsanitize=address'`, потому что оба перестраивают раскладку памяти и перехватывают одни и те же вызовы. Покрытие: UBSan — строки 5, 6, 7 и 2, а строка 1 только там, где размер массива виден в типе; ASan — строки 3, 4, 1 (в пределах границ выделенного блока) и, как побочный эффект, утечки. Ни один из двух не покрывает строку 9 (нужен TSan), строку 8 (это статическое свойство текста, `-Wsequence-point`), промахи внутри запаса ёмкости вектора (проверено: `data[5]` при `cap == 8` не увидели оба, поймал только Memcheck) и — принципиально — любое UB на путях, которые данный прогон не выполнил.

**Вариант 2 (UBSan + Valgrind в одном прогоне вместо двух сборок).** Раз ASan с чем-то не уживается, а пересобирать проект дважды не всегда удобно, есть другая комбинация: Memcheck работает **без пересборки**, поверх готового исполняемого файла (§7.2.2), — значит, его можно натравить прямо на сборку с UBSan и получить оба класса проверок за один запуск:

```
gcc -std=c17 -Wall -Wextra -fsanitize=undefined vec_bad.c -o vb_ub
valgrind -q ./vb_ub
==220== Conditional jump or move depends on uninitialised value(s)
==220==    at 0x4EE00CB: __printf_buffer (vfprintf-process-arg.c:58)
==220==    by 0x4ED61B2: printf (printf.c:33)
==220==    by 0x109AC4: main (in /root/ch13/z8/vb_ub)
==220== Use of uninitialised value of size 8
...
10 20 30 40 50 0
```

Один прогон, один исполняемый файл — и проверки UBSan (арифметика, сдвиги, NULL), и проверки Memcheck (ошибки памяти плюс чтение неинициализированного). Заметьте, что поймано здесь именно то, что в основном варианте не увидел никто, — опыт 3.

*Сравнение.* Две отдельные сборки (основной вариант) — быстрее в работе и точнее в диагностике памяти: ASan знает про кучу изнутри, поэтому в отчёте есть стек места освобождения, размер блока и смещение внутри него (опыт 1), а замедление обычно двукратное. Связка «UBSan + Valgrind» экономит одну сборку и одну итерацию, не конфликтует ни с чем и покрывает **больше** классов: Memcheck умеет то, чего нет у ASan, — видит чтение неинициализированной памяти, а значит, ловит промахи внутри уже выделенного блока. Плата — скорость: Valgrind исполняет программу на своей виртуальной машине и замедляет её в десятки раз, что на длинных тестах превращает минуты в часы, а отчёты его показывают адреса и кадры библиотек (`__printf_buffer`), из которых до своей строки нужно ещё добраться взглядом. Правило выбора простое: в цикле разработки и в CI, где важна скорость, — две сборки с санитайзерами по очереди; при разборе «непонятного» дефекта, особенно если данные выглядят мусором и есть подозрение на неинициализированную память, — Valgrind, при желании поверх UBSan-сборки.

### Г13.Ч1.З9

**Условие.** *(прикладное)* Воспроизведите `race.c`: три запуска без санитайзера (приведите разброс), затем отчёт TSan. Почините гонку **без** средств синхронизации: каждый поток копит **свой** счётчик (например, через массив `long partial[2]` и передачу потоку указателя на его элемент — параметр `arg` из §13.1.4 вам в помощь), а `main` складывает частные суммы после обоих `pthread_join`. Убедитесь: результат ровно 2 000 000, TSan чист. Сформулируйте одним предложением, *почему* гонка исчезла (подсказка: у кого какие данные и в какие моменты времени).

**Решение.** Программа `race.c` берётся из §13.1.4 дословно (⛔ гонка намеренная). Все прогоны — WSL Ubuntu 24.04, gcc 13.3.0.

**Три запуска без санитайзера:**

```

./race    counter = 1579857 (expected 2000000)
./race    counter = 1151599 (expected 2000000)
```

Разброс — от 1 013 475 до 1 579 857 при ожидаемых 2 000 000: потерялось от четверти до половины инкрементов, и каждый запуск даёт своё число. Ни один прогон не «правильный» и не «почти правильный»: это UB (строка 9 каталога), а потерянные инкременты — лишь одно из его возможных проявлений.

**Отчёт TSan** (отдельная сборка — совмещать с ASan нельзя, см. Г13.Ч1.З8):

```

    #0 work (race_tsan+0x127d)

    #0 work (race_tsan+0x1297)

    #0 pthread_create   #1 main
```

Два предупреждения, а не одно: конфликтуют и «чтение против записи», и «запись против записи» — обе пары обращений неупорядочены. Служебные кадры в отчёте сокращены, как в §7.2.2.

И самое интересное — **последняя строка вывода**: под TSan программа напечатала ровно 2 000 000. Инструмент так замедлил и перетасовал выполнение, что инкременты в этот раз не потерялись. Если бы мы судили о наличии гонки по результату, вердикт был бы «всё в порядке» — а TSan всё равно сообщил о гонке, потому что определяет её **по конфликту обращений** (§5.1.2.5: два конфликтующих действия, ни одно не атомарно, ни одно не «происходит-до» другого), а не по испорченному значению. Ровно об этом предупреждает §13.1.4: «больше не воспроизводится» ≠ «исправлено».

**Починка без средств синхронизации.** Ни мьютексов, ни атомиков — только перераспределение данных: каждому потоку своя ячейка, слияние — после обоих `pthread_join`.

```c
/* race_fix.c — у каждого потока свой счётчик; main складывает после обоих join */
#include <pthread.h>
#include <stdio.h>

void *work(void *arg)
{
    long *my = arg;            /* указатель на СВОЙ элемент partial */
    for (int i = 0; i < 1000000; i++)
        (*my)++;               /* пишет только этот поток и никто больше */
    return NULL;
}

int main(void)
{
    pthread_t t1, t2;
    long partial[2] = {0, 0};

    pthread_create(&t1, NULL, work, &partial[0]);
    pthread_create(&t2, NULL, work, &partial[1]);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    /* сложение — после обоих join: к этому моменту потоков уже нет */
    printf("counter = %ld (expected 2000000)\n", partial[0] + partial[1]);
    return 0;
}
```

Параметр `arg`, который в `race.c` не использовался, здесь несёт адрес персональной ячейки — приём знакомый: указатель как способ сказать функции, где её данные (§6.1). Три запуска и прогон под TSan:

```
gcc -std=c17 -Wall -Wextra -pthread race_fix.c -o race_fix
./race_fix    counter = 2000000 (expected 2000000)
./race_fix    counter = 2000000 (expected 2000000)
./race_fix    counter = 2000000 (expected 2000000)

gcc -std=c17 -Wall -Wextra -pthread -fsanitize=thread race_fix.c -o race_fix_tsan
./race_fix_tsan
counter = 2000000 (expected 2000000)
код завершения: 0, ни одного предупреждения
```

Ровно 2 000 000 в каждом запуске, TSan чист.

**Почему гонка исчезла.** Определение гонки требует **двух конфликтующих неупорядоченных обращений**; мы разрушили обе половины этого требования сразу. Во-первых, пока потоки работают, каждый пишет только в свою ячейку `partial[i]`, а к чужой не притрагивается — конфликтующих обращений (двух обращений к одной памяти, из которых хотя бы одно запись) просто нет. Во-вторых, единственное общее чтение — сложение `partial[0] + partial[1]` в `main` — выполняется **после** обоих `pthread_join`, а `join` упорядочивает: он гарантирует, что поток завершился, значит все его записи «происходят-до» кода, идущего за `join`. Обращения остались, но перестали быть одновременными.

Полезно заметить, что `partial[0]` и `partial[1]` — соседние элементы одного массива, то есть лежат в памяти вплотную. На скорости это сказаться может (два ядра пишут в близкие адреса), но на корректности — нет: с точки зрения стандарта это **разные объекты**, а одновременная запись в разные объекты гонкой не является. TSan это подтверждает молчанием.

**Ответ:** три запуска без санитайзера дали 1 013 475, 1 579 857 и 1 151 599 при ожидаемых 2 000 000 — разброс в сотни тысяч и ни одного повторения. TSan выдаёт **два** предупреждения `data race` на глобальной `counter` (чтение против записи и запись против записи), указывая обе нити, обе точки в `work` и место переменной; при этом сам прогон под TSan напечатал правильные 2 000 000 — гонка определяется по конфликту обращений, а не по испорченному результату. Починка без синхронизации: `long partial[2]`, каждому потоку через `arg` передан адрес своего элемента, сложение — после обоих `pthread_join`; результат ровно 2 000 000 в трёх запусках, TSan чист. Одним предложением: **гонка исчезла потому, что во время работы потоков у каждого своя память и общих обращений нет вовсе, а единственное общее чтение сделано после `pthread_join`, который упорядочивает записи потока и последующий код `main`, — то есть исчезли обе составляющие определения гонки: конфликт и неупорядоченность.**

**Вариант 2 (поток возвращает свою сумму, владение переходит в `main`).** Массив `partial` — не единственный способ дать потоку «своё». У функции потока есть возвращаемое значение, а у `pthread_join` — второй параметр, через который это значение забирают. Тогда `main` вообще не готовит потокам память заранее: каждый поток выделяет блок под свой результат сам и отдаёт его вместе с ответственностью за освобождение — ровно дисциплина владения из §7.1.2.

```c
/* race_fix2.c — поток отдаёт свою сумму как результат: владение переходит в main */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

void *work(void *arg)
{
    (void)arg;
    long *sum = malloc(sizeof *sum);   /* блок принадлежит потоку... */
    if (sum == NULL)
        return NULL;
    *sum = 0;
    for (int i = 0; i < 1000000; i++)
        (*sum)++;
    return sum;                        /* ...и передаётся тому, кто сделает join */
}

int main(void)
{
    pthread_t t1, t2;
    void *r1 = NULL, *r2 = NULL;

    pthread_create(&t1, NULL, work, NULL);
    pthread_create(&t2, NULL, work, NULL);
    pthread_join(t1, &r1);             /* забрали результат — и владение блоком */
    pthread_join(t2, &r2);

    if (r1 == NULL || r2 == NULL) {
        free(r1);
        free(r2);
        printf("out of memory\n");
        return 1;
    }
    printf("counter = %ld (expected 2000000)\n", *(long *)r1 + *(long *)r2);
    free(r1);
    free(r2);
    return 0;
}
```

Прогоны:

```
./race_fix2    counter = 2000000 (expected 2000000)   (три раза подряд — одинаково)

gcc -std=c17 -Wall -Wextra -pthread -fsanitize=thread race_fix2.c -o race_fix2_tsan
./race_fix2_tsan
counter = 2000000 (expected 2000000)
код завершения: 0, ни одного предупреждения
```

(`free(NULL)` в ветке ошибки безвреден — §7.1.2, поэтому проверять каждый указатель по отдельности не нужно.)

*Сравнение.* Вариант с `partial[2]` проще и дешевле: память под результаты — обычный массив в кадре `main`, ни одного обращения к куче, поток получает готовый адрес и ничего не решает. Он удобен, когда число потоков известно заранее и невелико, — а его слабое место в том, что владение остаётся размазанным: `main` создаёт ячейки и обязан помнить, кому какую отдал, и не трогать их до `join` (ошибка здесь — не отказ компиляции, а снова гонка). Вариант с возвратом через `pthread_join` **связывает результат с потоком**: поток сам выделяет ровно то, что ему нужно, и отдаёт блок вместе с ответственностью — `main` не должен ничего знать заранее, а число потоков может определяться во время выполнения (массив из `n` дескрипторов, цикл `join`, суммирование по ходу). Плата — обращение к куче на каждый поток, обязательный `free` на всех путях (включая путь ошибки) и приведение `void *` к нужному типу при чтении. Практическое правило: фиксированное, небольшое число потоков и простые результаты — массив частных сумм; переменное число потоков или результат, размер которого известен только самому потоку, — возврат через `join` с передачей владения. Заметьте, что второй вариант — почти дословно та схема, которую Rust делает единственно возможной: значение принадлежит потоку, а по завершении **перемещается** к тому, кто его дождался (§13.2.1, §13.2.3).

**Источники части 13.1 (решения):** C5 (N3220: §3.5.1–3.5.4, §3.28, §5.1.2.5, §6.2.4, §6.5.1, §6.5.4.2, §6.5.6–6.5.8, J.2); C10 (SEI CERT C, MSC15-C); C17 (GCC Manual: `-fwrapv`, `-fdelete-null-pointer-checks`, `-fsanitize=*`, `-fsanitize-trap`, `-S`); C18 (UBSan); C19 (TSan); C13, C14 (Valgrind, ASan); C3, C4.

### Г13.Ч2.З1

**Условие.** По таблице §13.2.3 определите судьбу в safe Rust каждого из восьми фрагментов задания Г13.Ч1.З1 (а–з): ошибка компиляции / паника / определённое значение (какое?) / не воспроизводится / остаётся возможным. Для пунктов «а» и «з» дополнительно укажите, чем ответ Rust отличается от ответа C по существу.

**Решение.** Идём по пунктам Г13.Ч1.З1, сверяясь со строками таблицы §13.2.3.

1. **«а» `unsigned u = UINT_MAX; u + 1`.** Аналог — `u32::MAX + 1`. По строке «знаковое переполнение» таблицы §13.2.3 ответ Rust одинаков для знаковых и беззнаковых типов: **паника** в отладочной сборке, **определённое значение** (заворот, 0) в релизной. Проверено на `u8` (та же арифметика, короче числа): в отладке — `thread 'main' panicked: attempt to add with overflow`, в релизе — `0`; явные `wrapping_add`/`checked_add` дают `0` и `None` в обеих сборках.
2. **«б» `int i = INT_MAX; i + 1`.** Та же строка таблицы: **паника** (debug) / **определённое значение** `-2147483648` (release). Проверено дословно на фрагменте из §13.2.2.
3. **«в» порядок вызова `f` и `g` в аргументах.** **Не воспроизводится.** Неуточнённого порядка в Rust нет: справочник (R7, «Expressions») требует, чтобы операнды вычислялись до применения самой операции, а выражения с несколькими операндами — **слева направо в порядке записи в исходном тексте**; правило распространяется и на вызовы функций. Проверено: три вызова со счётчиком-побочным эффектом в одном `println!` дали `1 2 3`. Заметьте: в каталоге §13.1.2 этого пункта и не было — unspecified behavior не UB, программа на C с ним корректна.
4. **«г» `sizeof(long)`.** **Определённое значение**, заданное самим именем типа: `i32` — всегда 4 байта, `i64` — всегда 8, независимо от платформы (проверено). Категории «implementation-defined размер целого» в Rust не возникает вовсе; платформенно-зависимая ширина осталась ровно у двух типов — `usize`/`isize` (размер указателя; на нашей машине 8), и они названы так, что зависимость видна в имени.
5. **«д» `int a[3]; a[3]`.** Индекс здесь — константа, известная при компиляции, поэтому **ошибка компиляции**: `error: this operation will panic at runtime — index out of bounds: the length is 4 but the index is 4`, с пометкой `#[deny(unconditional_panic)] on by default` (проверено на массиве из четырёх элементов из §13.2.2). Если бы индекс приходил из данных — **паника** на этом доступе.
6. **«е» `x % 0`.** **Паника**: `attempt to calculate the remainder with a divisor of zero`. Отличие от переполнения: здесь паника и в отладочной, и в **релизной** сборке (проверено обеими) — «тихого» варианта у деления и остатка на ноль нет.
7. **«ж» `i++ + i++`.** **Не воспроизводится**: постфиксного инкремента в языке нет. Компилятор отвечает `error: Rust has no postfix increment operator` и предлагает `help: use += 1 instead` (проверено) — ровно строка таблицы §13.2.3.
8. **«з» `1 << 35` при 32-битном типе.** Константное выражение — **ошибка компиляции** (тот же `unconditional_panic`); выражение с величиной сдвига из данных — **паника** в отладке (`attempt to shift left with overflow`) и **определённое значение** в релизе: проверено, получилось `8`.

**Отличие от C по существу — пункт «а».** В C беззнаковый заворот **определён** (N3220 §3.28) и даёт 0 при любой сборке: это законный, повсеместно используемый приём (хеши, циклические буферы, арифметика по модулю). Rust здесь **строже C, а не мягче**: он считает заворот по умолчанию признаком ошибки и в отладочной сборке останавливает программу, требуя, чтобы намеренная модульная арифметика была написана явно — `wrapping_add`, `checked_add`, `saturating_add`. Меняется не «определённость» (она есть в обоих языках), а **умолчание**: C молча заворачивает и надеется, что вы этого хотели; Rust в отладке шумит и просит сказать, что имеется в виду. Обратная сторона: одна и та же строка `u + 1` в Rust ведёт себя по-разному в debug и release — об этом надо помнить, тогда как в C её поведение одинаково всегда.

**Отличие от C по существу — пункт «з».** Здесь всё наоборот: C ничего не обещает, Rust обещает оба исхода. В C сдвиг на 35 — UB (строка 7 каталога), и мы это прочувствовали в Г13.Ч1.З1: одно и то же выражение дало `8` при вычислении на процессоре и `0` при свёртке компилятором, причём в первом случае без единого предупреждения. Хуже того, по §13.1.3 оптимизатор вправе строить на «такого не бывает» дальнейшие выводы. В Rust оба исхода определены правилами языка: либо остановка с диагнозом до всякой порчи данных, либо конкретное значение (`8`) — и рассуждать «сдвиг на 35 невозможен, значит эта ветка мертва» компилятор не может, потому что такой сдвиг возможен и его смысл задан. Показательно, что видимый результат в релизе совпал с C-шным (`8`): разница не в числе, а в том, что в C оно не гарантировано ничем, а в Rust — гарантировано.

**Ответ:**

| Пункт | Судьба в safe Rust | Пояснение |
|---|---|---|
| а) `u32::MAX + 1` | **паника** (debug) / **определённое значение** `0` (release) | заворот определён, но по умолчанию считается ошибкой; явный заворот — `wrapping_add` |
| б) `i32::MAX + 1` | **паника** (debug) / **определённое значение** `-2147483648` (release) | строка «знаковое переполнение» таблицы §13.2.3 |
| в) порядок вычисления аргументов | **не воспроизводится** | порядок задан: операнды вычисляются слева направо (R7) |
| г) размер целого типа | **определённое значение**: `i32` — 4, `i64` — 8 байт | ширина зафиксирована именем типа; платформенно-зависимы только `usize`/`isize` |
| д) `a[3]` при массиве из 3 | **ошибка компиляции** (индекс-константа); **паника**, если индекс из данных | `#[deny(unconditional_panic)]` |
| е) `x % 0` | **паника**: `attempt to calculate the remainder with a divisor of zero` | и в debug, и в release |
| ж) `i++ + i++` | **не воспроизводится** | `error: Rust has no postfix increment operator` |
| з) `1 << 35` для 32-битного типа | **ошибка компиляции** (константа); **паника** (debug) / **определённое значение** `8` (release) | `attempt to shift left with overflow` |

По существу: в «а» Rust **строже** C — то, что в C определено и молчаливо (заворот беззнакового), в Rust по умолчанию считается ошибкой и в отладке приводит к останову, а намеренная модульная арифметика требует явного метода. В «з» Rust, наоборот, **определяет то, что в C не определено вовсе**: вместо UB, на котором оптимизатор вправе строить любые выводы, — либо контролируемый останов с диагнозом, либо конкретное значение; наш эксперимент в C дал на одном и том же выражении `8` и `0` в зависимости от способа вычисления, и ни одно из этих чисел не было обещано.

### Г13.Ч2.З2

**Условие.** Разберите сообщение `error[E0382]` из §13.2.1 по строкам: что сообщают пометки `move occurs because ...`, `value moved here`, `value borrowed here after move` и `help: consider cloning ...`; какой строке каталога §13.1.2 соответствовала бы программа, если бы компилятор её пропустил; что изменится (и почему это законно), если совет из `help` принять.

**Решение.** Сообщение относится к трёхстрочной программе из §13.2.1: `s1` владеет строкой, `let s2 = s1;` перемещает владение, `println!` пытается напечатать обе. Разберём пометки по порядку; заголовок читается так же, как у ошибок компилятора C, — код ошибки, суть, координаты.

- **`error[E0382]: borrow of moved value: s1`** — заголовок. Ключевые слова два: `moved` (значение перемещено) и `borrow` (его пытаются **заимствовать**). Заимствование здесь не случайно: макрос `println!` берёт свои аргументы по ссылке, не забирая их себе, — потому в тексте не «использование», а «заимствование». Дальше идёт стрелка `-->` с файлом, строкой и столбцом — координаты той самой попытки.
- **`move occurs because s1 has type String, which does not implement the Copy trait`** — **объяснение причины**: почему присваивание вообще что-то переместило. `String` владеет буфером в куче (наш `char *`, полученный от `str_dup`), поэтому копировать его побайтово нельзя — получилось бы два владельца одного блока. Такие типы не имеют свойства `Copy`, и присваивание для них означает передачу владения, а не дублирование. Для типов вроде `i32`, целиком лежащих в самой переменной, `Copy` есть, и присваивание копирует — тогда никакой ошибки не будет.
- **`value moved here`** (указывает на строку `let s2 = s1;`) — **место преступления с точки зрения владения**: именно здесь `s1` перестал быть владельцем. Заметьте, что сама эта строка ошибкой не является: перемещать значения — обычное дело.
- **`value borrowed here after move`** (указывает внутрь `println!`) — **место нарушения**: обращение к имени, которое уже ничем не владеет. Пара пометок вместе образует рассказ: «владение ушло вот тут — а вот тут вы им снова пользуетесь». Это тот же приём, что у ASan, который в отчёте показывает и место освобождения, и место обращения (Г13.Ч1.З8, опыт 1); разница в том, что Rust показывает это **до запуска**.
- **`help: consider cloning the value if the performance cost is acceptable`** — **предложенное исправление** с честно названной ценой. На rustc 1.97 подсказка идёт вместе с готовой правкой — `let s2 = s1.clone();`, где вставляемые символы подчёркнуты плюсами. Оговорка «если цена по производительности приемлема» существенна: `clone` — не синтаксический трюк, а реальное копирование содержимого кучи.

**Какой строке каталога соответствовала бы пропущенная программа.** Прежде всего — **строке 4** (двойное освобождение). Если бы компилятор согласился считать владельцами обоих, то при выходе из блока каждый из них освободил бы свой буфер — а буфер один; получилось бы двойное освобождение того же адреса, UB по N3220 §7.24.3.3. Именно этот довод приводит официальная книга Rust в §13.2.1: «это ошибка двойного освобождения, одна из ошибок безопасности памяти».

Кроме того, программа задевала бы **строку 3** (использование после освобождения): если бы один из владельцев освободил буфер раньше, чтение через второе имя стало бы чтением освобождённой памяти. Иными словами, одна ошибка компиляции E0382 закрывает сразу два соседних класса каталога — те самые, которые в C ловятся только динамически, ASan-ом, и только если нужный путь выполнился.

**Что изменится, если принять совет.** Проверено — программа с `clone` собирается и работает:

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone();            // отдельная копия в куче — два владельца двух блоков
    println!("{s1}, world! {s2}");
}
```

```
hello, world! hello
```

Изменилось вот что: `clone` выделяет **новый** буфер в куче и копирует туда содержимое. Теперь блоков два и владельцев два — по одному на блок. Правило «владелец ровно один» не нарушено (оно про один блок, а не про одно содержимое), `s1` по-прежнему владеет своим буфером и потому остаётся пригодным к использованию, а в конце блока каждый владелец освободит **свой** буфер. Ни двойного освобождения, ни использования после освобождения не возникает — и потому это законно.

Точный аналог на C мы писали руками в главе 7: `char *s2 = str_dup(s1);` — новая память, посимвольное копирование, два независимых блока и два `free` в конце. Ошибочный вариант там записывался как `char *s2 = s1;` — то самое «второе имя того же блока», которое Rust отвергает. Плата в обоих языках одна и та же: `clone`/`str_dup` действительно копируют данные, и на больших строках это заметно. Поэтому подсказка компилятора и звучит с оговоркой: если копия не нужна, правильный ответ — не `clone`, а ссылка (`&s1`), то есть заимствование без передачи владения (глава 15).

**Ответ:** `move occurs because s1 has type String, which does not implement the Copy trait` объясняет, **почему** присваивание переместило значение: `String` владеет буфером в куче, побайтовое копирование дало бы двух владельцев одного блока, поэтому у таких типов нет свойства `Copy` и присваивание передаёт владение. `value moved here` указывает точку передачи (`let s2 = s1;`), `value borrowed here after move` — точку нарушения (обращение к `s1` внутри `println!`, который берёт аргументы по ссылке, отсюда «borrowed»); вместе они образуют рассказ «владение ушло здесь — использовано здесь». `help: consider cloning the value if the performance cost is acceptable` предлагает готовое исправление `s1.clone()` и честно называет его цену. Если бы компилятор программу пропустил, она соответствовала бы **строке 4** каталога (двойное освобождение: два владельца освободили бы один буфер при выходе из области видимости) и, при чтении через первое имя после освобождения, **строке 3** (use-after-free). Приняв совет, получаем два независимых буфера: `clone` копирует содержимое в новую память, у каждого блока остаётся ровно один владелец, каждый освобождается один раз — правило владения не нарушено, поэтому программа законна (проверено: печатает `hello, world! hello`). Это дословный аналог `str_dup` из главы 7 — с той же платой за настоящее копирование.

### Г13.Ч2.З3

**Условие.** По правилам §13.2.2 предскажите поведение Rust-выражения `x + 1` при `x: u8 = 255`: (а) в отладочной сборке; (б) в релизной сборке; (в) при записи `x.wrapping_add(1)`. Сравните с C: чем каждый из трёх исходов отличается от `unsigned char`-арифметики и от UB знакового переполнения (строки таблицы Г13.Ч1.З1 «а» и «б»).

**Решение.** `u8` — беззнаковый однобайтовый тип, его наибольшее значение 255; `255 + 1` в этот тип не помещается. По §13.2.2 переполнение целого в Rust — не UB, а определённое поведение, разное в двух сборках.

**Предсказание и проверка.** Чтобы компилятор не вычислил выражение заранее (иначе получим ошибку компиляции, как в Г13.Ч2.З1, пункты «д» и «з»), слагаемое берём из данных запуска:

```rust
fn main() {
    let x: u8 = 255;
    let step = std::env::args().count() as u8;   // 1 при запуске без аргументов
    println!("wrapping_add: {}", x.wrapping_add(step));
    println!("checked_add:  {:?}", x.checked_add(step));
    println!("x + step:     {}", x + step);
}
```

Отладочная сборка (`rustc --edition 2024`):

```
wrapping_add: 0
checked_add:  None

thread 'main' panicked at r7_u8.rs:6:34:
attempt to add with overflow
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
код завершения: 101
```

Релизная сборка (`rustc --edition 2024 -O`):

```
wrapping_add: 0
checked_add:  None
x + step:     0
код завершения: 0
```

- **(а) Отладочная сборка — паника.** `attempt to add with overflow`, с указанием файла, строки и столбца; программа останавливается **до** того, как результат куда-либо попадёт, код завершения 101. Это определённое поведение: не «может быть что угодно», а «гарантированно остановится здесь».
- **(б) Релизная сборка — определённое значение 0.** Заворот по модулю 256: `256 mod 256 == 0`. Никакой паники и никакого сообщения.
- **(в) `x.wrapping_add(1)` — определённое значение 0 в обеих сборках.** Метод означает «я хочу заворот», и он его даёт, не спрашивая про уровень оптимизации. Рядом полезно держать `checked_add`, который вместо заворота возвращает `None` (в выводе видно) — то есть переводит переполнение в значение, которое нельзя случайно не заметить.

**Сравнение с `unsigned char`-арифметикой C.** Здесь у C припасён сюрприз, который стоит проверить руками:

```c
/* uchar.c — что даёт x + 1 при unsigned char x = 255 */
    unsigned char x = 255;
    unsigned char back = x + 1;

    printf("x + 1        = %d\n", x + 1);      /* значение выражения */
    printf("sizeof(x+1)  = %zu\n", sizeof(x + 1));
    printf("back         = %u\n", back);       /* после записи обратно в uchar */
```

```
x + 1        = 256
sizeof(x+1)  = 4
back         = 0
```

**`x + 1` в C равно 256, а не 0.** Причина — целочисленные повышения (integer promotions, N3220 §6.3.1.1): операнд типа `unsigned char` перед арифметикой преобразуется в `int`, потому что `int` способен представить все его значения. Значит, складываются два `int`, результат `256` имеет тип `int` (что подтверждает `sizeof` — 4 байта), и никакого заворота не происходит. Ноль появляется только при **записи обратно** в `unsigned char`: вот это преобразование и заворачивает по модулю 256 (определено, N3220 §3.28).

Отсюда — три отличия по каждому исходу:

| | C, `unsigned char x = 255` | Rust, `x: u8 = 255` |
|---|---|---|
| Тип и значение `x + 1` | `int`, **256** — операнд повышается до `int` | `u8`; переполнение, «результата в типе нет» |
| Отладочная сборка | 256, тихо, всегда | **паника** `attempt to add with overflow` |
| Релизная сборка | 256, тихо, всегда | **0** (заворот) |
| Явный заворот | присвоить обратно в `unsigned char` → 0 | `wrapping_add` → 0 |
| Как узнать о переполнении | никак: его формально не было | `checked_add` → `None` |

То есть Rust не «повторяет C построже» — у него **другая модель**: арифметика над `u8` остаётся в `u8`, автоматических расширений нет, и потому ситуация «не помещается» вообще возникает (в C для однобайтовых типов она возникает лишь при обратном присваивании). Практическое следствие для читателя тома I: привычка «маленькие типы всё равно считаются в `int`» в Rust не работает — там, где в C сложение `unsigned char` безобидно, в Rust нужно решить, чего вы хотите: паники, заворота или `Option`.

**Сравнение с UB знакового переполнения (пункт «б» Г13.Ч1.З1).** А вот здесь разница категориальная, а не арифметическая. В C `INT_MAX + 1` — **UB**: результата нет вовсе, и, как мы видели в §13.1.3, компилятор вправе рассуждать «такого не бывает» и на этом основании выкидывать проверки и превращать циклы в вечные. Ни один из трёх исходов Rust на это не похож: паника — это остановка **в известном месте с диагнозом**, заворот в релизе — конкретное число, `wrapping_add` — оно же по явной просьбе. Ни в одном случае оптимизатор не получает права на «такого не бывает», поэтому `x + 1 > x` в Rust не свернётся в истину, а цикл `for i in ... { i *= 2 }` не станет вечным. Общий счёт по трём пунктам: C определяет «а» (беззнаковое) и не определяет «б» (знаковое); Rust определяет **оба**, но в отладке предпочитает шумно останавливаться, а не считать дальше.

**Ответ:** (а) в отладочной сборке — **паника** `attempt to add with overflow` с указанием места, код завершения 101; (б) в релизной — **определённое значение 0** (заворот по модулю 256); (в) `x.wrapping_add(1)` — **0 в обеих сборках**, без паники, потому что заворот запрошен явно (а `checked_add` вместо этого вернул бы `None`). Все три проверены запуском. Отличие от `unsigned char`-арифметики C: там `x + 1` равно **256**, а не 0, — операнд повышается до `int` (N3220 §6.3.1.1, подтверждено `sizeof(x+1) == 4`), и заворот случается только при обратном присваивании в `unsigned char`; в Rust расширения нет, арифметика `u8` остаётся в `u8`, поэтому переполнение возникает прямо в сложении и требует решения — паника, заворот или `Option`. Отличие от UB знакового переполнения: в C `INT_MAX + 1` не имеет результата вовсе и даёт оптимизатору право считать ситуацию невозможной (§13.1.3), тогда как все три исхода Rust определены правилами языка — контролируемый останов с диагнозом либо конкретное значение, и никаких прав на «такого не бывает» компилятор из них не извлекает.

### Г13.Ч2.З4

**Условие.** Сопоставьте дисциплину владения из §7.1.2 с тремя правилами владения Rust (§13.2.1): для функции `str_dup` (гл. 7) укажите, кто владелец результата, где происходит передача владения и где обязан стоять `free`; затем покажите, какое из трёх правил Rust соответствует каждому пункту и **что именно** превращается из соглашения в ошибку компиляции.

**Решение.** Напомним функцию из Г7.Ч1.З11: `char *str_dup(const char *s)` выделяет `strlen(s) + 1` байт, копирует туда строку и возвращает указатель.

**Разбор владения в C-версии.**

- **Кто владелец результата.** Внутри `str_dup` владельцем свежего блока недолго является сама функция — ровно до `return`. После возврата владельцем становится **вызывающий**: только у него остаётся указатель, только он знает, когда блок больше не нужен. Это соглашение нигде в коде не записано: тип возвращаемого значения `char *` ничем не отличается от указателя на строковый литерал или на буфер в стеке.
- **Где происходит передача владения.** В точке `return`: значение указателя копируется наружу, и обязанность освободить блок переходит вместе с ним. Момент невидим — ни компилятор, ни читатель кода не получают никакого сигнала, кроме комментария к функции.
- **Где обязан стоять `free`.** У вызывающего, ровно один раз, **на всех путях выхода** — включая ранние `return` по ошибке. Это и есть основная тяжесть дисциплины главы 7: путей может быть много, а `free` должен быть на каждом и только один раз.

**Сопоставление с тремя правилами Rust.**

| Пункт дисциплины C (§7.1.2) | Правило Rust (§13.2.1) | Что меняется |
|---|---|---|
| У блока есть код, ответственный за `free`, — его владелец | **Правило 1**: у каждого значения есть владелец-переменная | Владение перестаёт быть комментарием: оно записано в типе. `String` **владеет** буфером, `&str` — нет, и это видно в сигнатуре |
| Владелец один: два указателя на один блок — приглашение к двойному освобождению | **Правило 2**: владелец ровно один в каждый момент | Присваивание/передача в функцию **перемещает** владение; старое имя становится непригодным, и попытка им воспользоваться — ошибка E0382 |
| Освободить в конце времени жизни, на всех путях выхода | **Правило 3**: выход владельца из области видимости — автоматический `drop` | `free` перестаёт быть строкой кода, которую можно забыть: его вставляет компилятор, на каждом пути выхода, ровно один раз |

Rust-аналог самой `str_dup` — `String::from(s)` (или `s.to_string()`): функция возвращает **владеющее** значение, а не указатель. Передача владения происходит там же, где в C, — при возврате, — но теперь она видна в типе результата, а освобождение вызывающему писать не нужно вовсе.

**Что именно превращается из соглашения в ошибку компиляции.** Четыре конкретные вещи — и полезно заметить, что три из них соответствуют строкам каталога §13.1.2:

1. **«После передачи владения старым именем не пользоваться»** — в C это комментарий, в Rust `error[E0382]` (Г13.Ч2.З2). Закрывает **строку 3** каталога (use-after-free) и, при выходе из области видимости, **строку 4**.
2. **«Освобождать ровно один раз»** — в C это внимательность, в Rust следствие правила 2: владелец один, `drop` вызывается один раз. **Строка 4** (двойное освобождение) становится невыразимой.
3. **«Не возвращать указатель на то, что умрёт раньше»** — в C ловится лишь простейшими случаями (`-Wreturn-local-addr`), в Rust это `error[E0106]` про времена жизни (пример 2 §13.2.1). Закрывает висячие ссылки — **строки 2 и 3**.
4. **«Не забыть `free` на пути ошибки»** — перестаёт быть обязанностью программиста: `drop` вставляется на всех путях выхода автоматически. Заметьте разницу с тремя предыдущими пунктами: забытый `free` — это **утечка**, а не UB (§13.1.2, «типичные ошибки»), поэтому Rust здесь не «ловит ошибку», а **избавляет от работы**; гарантии отсутствия утечек он, как мы увидим в Г13.Ч2.З6, не даёт.

Что **не** превращается ни во что: решение о том, нужна ли копия. `str_dup` копирует данные, и в Rust копия тоже стоит денег (`clone` из Г13.Ч2.З2). Компилятор проверяет дисциплину владения, но не проектирует за вас структуру данных.

**Ответ:** в `str_dup` владелец результата — **вызывающий**; передача владения происходит в точке `return` (вместе со значением указателя уходит обязанность освободить блок); `free` обязан стоять у вызывающего, ровно один раз, на всех путях выхода. Сопоставление: «у блока есть ответственный за `free`» ↔ **правило 1** (у каждого значения есть владелец), «владелец один, два указателя на один блок опасны» ↔ **правило 2** (владелец ровно один; присваивание перемещает владение), «освободить в конце времени жизни на всех путях» ↔ **правило 3** (выход из области видимости — автоматический `drop`). Из соглашения в ошибку компиляции превращаются: использование имени после передачи владения (E0382 — закрывает строки 3 и 4 каталога), повторное освобождение (невыразимо: владелец один, `drop` один), возврат ссылки на умирающее значение (E0106 — строки 2 и 3). Забытый `free` на пути ошибки не превращается в ошибку компиляции, а исчезает как задача — `drop` расставляется компилятором; но это не гарантия отсутствия утечек, а лишь снятие ручной работы (см. Г13.Ч2.З6).

### Г13.Ч2.З5

**Условие.** Объясните разницу между паникой и UB на конкретной паре: `oob.c` (§13.1.2, вывод `a[4] = -677673440`) против Rust-паники `index out of bounds: the len is 4 but the index is 4` (§13.2.2). Перечислите: какие исходы допустимы у C-версии по стандарту; какой исход гарантирован у Rust-версии; почему для отладки и для безопасности эта разница принципиальна. В каком из двух случаев возможна «тихая» порча данных с продолжением работы?

**Решение.** Обе программы делают одно и то же: читают элемент с индексом 4 из массива, где элементов четыре (индексы 0…3), причём индекс вычисляется из аргументов запуска и потому неизвестен компилятору.

**Какие исходы допустимы у C-версии.** По определению UB (N3220 §3.5.3) — **любые**: стандарт «не налагает никаких требований». Примечание 1 к определению перечисляет спектр от «полного игнорирования ситуации с непредсказуемыми результатами» до «прекращения трансляции или выполнения с выдачей диагностики». Конкретно допустимы, в частности:

- напечатать мусор и завершиться успешно — именно это и происходит: `a[4] = -677673440` в §13.2.2, а наши три прогона дали `-25105104`, `-865634656`, `-192607184`, и ещё три (§13.1.2) — свои три числа;
- напечатать «правильное» на вид число — если по соседству со стеком лежит что-то похожее на данные;
- упасть с сигналом — если адрес попал на неотображённую страницу;
- вести себя по-разному при разных уровнях оптимизации — как `loop31.c` в Г13.Ч1.З2;
- исказить работу программы **после** места ошибки: по примечанию 3 к N3220 §3.5.3 наблюдаемое поведение гарантировано только **до** первой операции с UB.

И ещё одно, о чём легко забыть: компилятор вправе учесть, что `i` используется как индекс массива из четырёх элементов, и делать выводы о значении `argc` в остальной программе. UB не локализуется границами одной строки.

**Какой исход гарантирован у Rust-версии.** Ровно один: **паника на этом доступе**. Проверено:

```
thread 'main' panicked at r3_oob.rs:4:20:
index out of bounds: the len is 4 but the index is 4
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
код завершения: 101
```

Гарантировано при этом не только «остановится», но и:

- **чтения не происходит** — проверка выполняется до обращения, чужая память не читается;
- **сообщение содержит и место, и данные** — файл, строка, столбец, длина и индекс;
- **исход не зависит от сборки** — в отличие от переполнения (Г13.Ч2.З3), проверка индекса действует и в релизе;
- **код завершения фиксирован** (101) — то есть автоматика вокруг программы отличит панику от нормального завершения.

**Почему разница принципиальна для отладки.** В C-версии диагностика начинается с вопроса «а есть ли вообще ошибка?»: программа завершилась успешно, код возврата 0, напечатано какое-то число. Обнаружить дефект можно, только если кто-то заметил, что число неправдоподобно, — а при `a[4] = 3` не заметил бы никто. Дальше начинается худшее: числа разные от запуска к запуску, под отладчиком и под санитайзером поведение меняется, «на моей машине не воспроизводится». В Rust-версии отладка занимает одну строку вывода: известны файл, строка, столбец, длина массива и запрошенный индекс — то есть и место, и причина, и данные. Ровно об этом говорит §13.2.1, цитируя книгу Rust: ошибка с объяснением вместо воспроизведения редкого сбоя в отладчике.

**Почему разница принципиальна для безопасности.** Чтение за границей массива — не «неточность», а канонический механизм уязвимостей (§13.1.2, «связь с практикой»): за границей лежат чужие данные — остатки других переменных, адреса возврата, указатели. Прочитав их и отправив наружу (напечатав, записав в файл, послав по сети), программа раскрывает содержимое собственной памяти; при записи за границу — позволяет её испортить. В C-версии это происходит **молча и с продолжением работы**: значение уже прочитано и уже используется дальше. В Rust-версии программа останавливается **до** чтения — данные не покидают процесс, испорченное состояние не распространяется, и все последующие действия (запись файла, ответ по сети) не выполняются вовсе. Обмен понятен: паника — это отказ в обслуживании, но контролируемый и заметный; UB — это тихое продолжение работы с непредсказуемым состоянием.

**Где возможна «тихая» порча данных с продолжением работы.** Только в **C-версии**. У неё нет ни проверки, ни диагноза, ни изменения кода завершения: мусор попадает в вычисления и распространяется дальше как обычное значение. У Rust-версии «тихого» варианта нет по построению: проверка выполняется на каждом доступе, а паника — определённое поведение, которое нельзя не заметить.

**Ответ:** у C-версии допустимы **любые** исходы (N3220 §3.5.3: «никаких требований»), в том числе: напечатать мусор и завершиться с кодом 0 (что и наблюдается: `-677673440` в §13.2.2, `-25105104`/`-865634656`/`-192607184` в наших прогонах), напечатать правдоподобное число, упасть с сигналом, вести себя по-разному на разных уровнях оптимизации и исказить всё, что следует **после** места ошибки (примечание 3 к N3220 §3.5.3). У Rust-версии гарантирован ровно один исход — **паника на этом доступе**, до фактического чтения памяти, с сообщением `index out of bounds: the len is 4 but the index is 4`, местом (файл:строка:столбец) и фиксированным кодом завершения 101; причём в обеих сборках, отладочной и релизной. Для отладки разница принципиальна тем, что в C дефект сначала надо **заметить** (программа «успешно» отработала), а результаты невоспроизводимы, тогда как паника сразу называет место, причину и данные. Для безопасности — тем, что чтение за границей выдаёт наружу содержимое чужой памяти и является классическим механизмом уязвимостей, а Rust останавливает программу **до** чтения, не давая испорченному состоянию распространиться. «Тихая» порча данных с продолжением работы возможна **только в C-версии**; у Rust-версии такого варианта нет по построению.

### Г13.Ч2.З6

**Условие.** Почему утечка памяти в Rust «безопасна по памяти» (memory safe), хотя и нежелательна? Опираясь на классификацию §7.2.1 (утечка — потеря ресурса; UAF/double free — UB) и §13.2.3, объясните, почему Rust гарантирует отсутствие вторых, но не первых, и почему это различие — не каприз, а следствие определения UB из §13.1.1.

**Решение.** Разберём по шагам, что именно делает программа в каждом из трёх случаев.

**Что происходит при утечке.** Блок выделен и **не освобождён**; указатель на него потерян. Программа после этого:

- не читает и не пишет по этому адресу — читать нечем, указателя нет;
- не освобождает его повторно — она его вообще не освобождает;
- продолжает работать по всем правилам языка: каждая её операция определена.

Ущерб есть, и вполне реальный: память не возвращается, при повторении в цикле она кончается. Но это ущерб **ресурсный** — программа расходует больше, чем нужно. Ни одного обращения к памяти, на которое у программы нет прав, не происходит. Именно это и означает формула «утечки памяти безопасны по памяти»: свойство «безопасность по памяти» — про обращения, а не про экономию.

**Что происходит при UAF и double free.** Здесь наоборот: обращения есть, а прав на них нет. Use-after-free — чтение или запись объекта вне его времени жизни (N3220 §6.2.4¶2, строка 3 каталога); double free — передача аллокатору адреса, который он уже забрал (§7.24.3.3, строка 4). Оба — **UB**: результат не определён ничем, и, как показал §13.1.3, последствия не ограничены местом ошибки.

**Почему граница проходит именно здесь — следствие определения UB.** Определение из §13.1.1 не говорит ни слова о том, хорошо или плохо ведёт себя программа. Оно говорит только одно: есть ли у стандарта требования к её выполнению. Отсюда:

- у программы с утечкой требования **есть** и все они соблюдены: каждый вызов `malloc` определён, каждое чтение и запись — в пределах своих объектов, и то, что один блок остался невозвращённым, ни одного правила не нарушает. Программа определена — просто расточительна;
- у программы с UAF или double free есть операция, для которой требований **нет вообще**, — и с этого момента о поведении программы нельзя сказать ничего.

То есть граница проходит не по «желательно/нежелательно», а по «определено/не определено». Rust проводит её ровно там же (§13.2.3, R1 гл. 15): гарантии безопасности делают утечку трудной, но не невозможной, и предотвращение утечек **не входит** в обещания языка.

**Почему Rust может гарантировать отсутствие UAF и double free.** Потому что оба выражаются **статически проверяемым** свойством текста программы: «есть ли имя, через которое можно обратиться к значению после конца его времени жизни» и «может ли у одного значения оказаться больше одного владельца». Оба вопроса решаются правилами владения и заимствования, то есть до запуска — это и есть E0382/E0106 из §13.2.1 и Г13.Ч2.З2.

**Почему не может гарантировать отсутствие утечек.** Утечка — свойство не текста, а **выполнения**: «останется ли к моменту завершения выделенный, но недостижимый блок». Классический способ утечь в безопасном Rust — цикл из счётчиков ссылок `Rc` (§13.2.3, глава 22): каждый участник цикла честно владеет своей частью, счётчики никогда не доходят до нуля, `drop` не вызывается — и ни одно правило владения при этом не нарушено. Проверить такое статически означало бы решать вопрос о достижимости объектов в произвольной программе — задача, которая в общем случае не решается (мы обсуждали похожее ограничение в Г13.Ч1.З5 и Г13.Ч1.З6). Добавим и второе соображение, чисто прагматическое: раз утечка не UB, запрет на неё пришлось бы обеспечивать средствами, ограничивающими вполне законные программы, — платить строгостью за то, что не является нарушением безопасности.

Практический вывод для тома II: инструменты поиска утечек (LeakSanitizer, Memcheck из §7.2.2) остаются нужны и там. Меняется другое — их находки больше не смешиваются с ошибками памяти: UAF и double free к тому моменту уже невозможны, и всё, что нашёл инструмент, — это именно расточительность, а не мина.

**Ответ:** утечка «безопасна по памяти», потому что при ней программа **не совершает ни одного обращения к памяти, на которое у неё нет прав**: блок просто остаётся выделенным и недостижимым; каждая операция такой программы определена стандартом, и нарушено оказывается не правило языка, а разумность расхода ресурсов (§7.2.1: утечка — потеря ресурса). UAF и double free устроены противоположно: это обращение к объекту вне времени жизни (§6.2.4¶2) и повторная передача адреса аллокатору (§7.24.3.3), то есть **UB** — операции, для которых у стандарта нет никаких требований. Rust гарантирует отсутствие вторых, потому что они выражаются статически проверяемым свойством текста (кто владелец, переживает ли ссылка владельца) — это и проверяют правила владения, выдавая E0382/E0106 до запуска; и не гарантирует отсутствия первых, потому что утечка — свойство выполнения (останется ли недостижимый блок), в общем случае статически неразрешимое, а классический `Rc`-цикл не нарушает ни одного правила владения. Различие не каприз: определение UB из §13.1.1 проводит границу по признаку «есть ли у стандарта требования к выполнению», а не по признаку «хорошо ли это»; утечка все требования соблюдает, UAF и double free — нет, и Rust проводит границу своих гарантий ровно там же (R1 гл. 15: «утечки памяти безопасны по памяти»).

### Г13.Ч2.З7

**Условие.** *(прикладное)* Составьте «карту рисков» для вашего мини-блокнота из главы 12 (либо вектора из §9.1.1): найдите **пять** мест с потенциальным UB (подсказка: буфер `do_save`, пути ошибок с `free`, индексы/границы, арифметика размеров), укажите для каждого строку каталога §13.1.2, механизм Rust из таблицы §13.2.3, который закрыл бы его, и момент обнаружения (компиляция/паника). Отдельно перечислите риски проекта, которые Rust **не** закрыл бы.

**Решение.** Берём мини-блокнот из §12.2.4: окно с полем `EDIT`, кнопками Load/Save и строкой состояния; модуль `storage` с контрактом «буфер, возвращённый `storage_load`, освобождает вызывающий»; функции `do_save` и `do_load` в `notepad.c`.

Важная оговорка перед картой: проект §12.2.4 **написан правильно** — все пять мест ниже это не найденные дефекты, а точки, где ошибка была бы естественной и не была бы замечена компилятором. Именно такие места и заносят в карту рисков: аудит смотрит не на то, что сломано, а на то, что легко сломать.

**Карта рисков.**

**Риск 1 — арифметика буфера в `do_save`.** Код `int len = GetWindowTextLength(st->edit); char *buf = malloc((size_t)len + 1); GetWindowText(st->edit, buf, len + 1);` держится на том, что длина сообщается **без** завершающего нуля, а места нужно на единицу больше. Написать `malloc(len)` — типичная ошибка на единицу (§12.2.4 прямо называет её в «подводных камнях»): контрол допишет `'\0'` за концом блока.
- **Строка каталога:** 1 (выход за границы; в куче — heap-buffer-overflow).
- **Механизм Rust:** ручной арифметики размеров нет вовсе — `String`/`Vec` знают свою длину и растут сами, а завершающего нуля в них нет как понятия.
- **Момент обнаружения:** **компиляция** — ошибка попросту невыразима; там, где размер всё же считается руками, срабатывает проверка индекса (**паника**).

**Риск 2 — использование буфера после `free` на путях ошибок `do_load`/`do_save`.** В `do_load` порядок «отдать текст контролу → `free(text)`» правильный; поменяйте две строки местами (или добавьте после `free` строку состояния, использующую `text`) — и получите чтение освобождённой памяти. Соблазн реален: путей выхода несколько, и `free` хочется поставить сразу после получения буфера, «чтобы не забыть».
- **Строка каталога:** 3 (use-after-free).
- **Механизм Rust:** владение и `drop`; после перемещения значения старое имя непригодно.
- **Момент обнаружения:** **компиляция** (E0382 и родня — Г13.Ч2.З2).

**Риск 3 — двойное освобождение на границе модулей.** Контракт `storage.h` гласит: буфер освобождает вызывающий. Стоит кому-нибудь «на всякий случай» освободить его и внутри `storage_load` — и блок освобождается дважды. Контракт записан в комментарии к заголовку, то есть проверяется только чтением.
- **Строка каталога:** 4 (двойное освобождение).
- **Механизм Rust:** владелец ровно один, `drop` вызывается ровно один раз; функция, возвращающая `String`, **передаёт** владение, и оставить его себе она не может.
- **Момент обнаружения:** **компиляция** (нарушение выражается как использование перемещённого значения).

**Риск 4 — арифметика размеров и знаковость.** `GetWindowTextLength` возвращает `int`; в `(size_t)len + 1` смешиваются знаковый и беззнаковый типы, а само `len + 1` вычисляется в `int`. При очень большом тексте (граница `INT_MAX`) сложение переполнится — знаковое переполнение; при отрицательном результате функции преобразование к `size_t` даст огромное число, и `malloc` попытается выделить его.
- **Строка каталога:** 5 (знаковое переполнение); последствие — снова 1 (выход за границы выделенного блока).
- **Механизм Rust:** длина имеет тип `usize`, смешивать её с `i32` без явного преобразования компилятор не даст; переполнение определено — паника в отладке.
- **Момент обнаружения:** **компиляция** (несовпадение типов) либо **паника** (переполнение при вычислении размера).

**Риск 5 — указатель на состояние окна вне времени его жизни.** `get_state(hwnd)` достаёт `AppState *` из данных окна. До сообщения `WM_NCCREATE` там ещё ничего нет, после уничтожения окна — уже ничего нет, а оконная процедура вызывается и в эти моменты. Разыменовать `st` без проверки — значит обратиться по нулевому или устаревшему указателю; §12.2.2 требует проверять, и это требование ничем не подкреплено.
- **Строка каталога:** 2 (разыменование `NULL`/инвалидного указателя), при устаревшем указателе — 3.
- **Механизм Rust:** «может отсутствовать» выражается типом `Option<&T>`, и **непроверенный путь не компилируется**; переживание ссылкой владельца ловится временами жизни (E0106).
- **Момент обнаружения:** **компиляция**.

**Чего Rust не закрыл бы.**

- **Логические ошибки проекта.** Сохранить не тот текст, перепутать кнопки Load и Save, потерять последний символ, неверно определить кодировку файла — программа при этом безопасна по памяти и воспроизводима. Ловится только тестами и приёмкой (§13.2.3).
- **Утечки.** Не UB и не в гарантиях (Г13.Ч2.З6). В GUI-программе с долгим временем жизни это как раз болезненно.
- **Взаимоблокировки**, если в блокнот добавить фоновое сохранение с мьютексом (§13.2.3).
- **Ошибки использования самого Win32 API.** Неверные флаги окна, забытый `DestroyWindow`, несоответствие идентификаторов контролов, неправильный порядок обработки сообщений — всё это вне языка: система не обязана диагностировать, и никакой borrow checker про смысл `WM_COMMAND` не знает. Показательно, что два ребёнка с одинаковым ID компилируются молча (§12.2.1) — такая ошибка останется молчаливой в любом языке.
- **И главное для этого проекта: весь Win32 — это FFI.** Вызовы `CreateWindowEx`, `GetWindowText`, `SetWindowLongPtr` из Rust идут через `unsafe` (глава 24), а `unsafe` не разрешает UB, а лишь **переносит ответственность за его отсутствие на программиста** (§13.2.3, R7). То есть риски 1, 4 и 5 в Rust-версии блокнота не исчезли бы полностью, а сосредоточились бы в помеченных `unsafe`-обёртках вокруг вызовов API. Это и есть обещанный размен: вместо «весь код подозреваемый» — «грепни `unsafe`».
- **Ошибки ввода-вывода** (файл занят, нет прав, диск полон) — это не UB и не дефект: в C они возвращаются кодами `fopen`/`fwrite` (гл. 10), в Rust — типом `Result` (гл. 18). Язык заставляет их **обработать**, но не устраняет.

**Ответ:** пять мест — (1) арифметика буфера в `do_save` (`malloc(len)` вместо `len + 1`) — строка 1 каталога, в Rust невыразимо, так как длина является частью значения `String`/`Vec`, обнаружение на компиляции; (2) использование текста после `free` на путях `do_load`/`do_save` — строка 3, механизм «владение + `drop`», компиляция (E0382); (3) двойное освобождение на границе с модулем `storage`, где контракт «освобождает вызывающий» записан лишь комментарием, — строка 4, механизм «владелец ровно один, `drop` ровно один», компиляция; (4) арифметика размеров `int len` → `(size_t)len + 1` при очень большом тексте — строка 5 с последствием по строке 1, механизм «`usize` не смешивается с `i32`, переполнение определено», компиляция или паника; (5) `get_state(hwnd)` до `WM_NCCREATE` и после уничтожения окна — строки 2 и 3, механизм `Option<&T>` с обязательной веткой `None` плюс времена жизни, компиляция. Rust **не** закрыл бы: логические ошибки проекта, утечки, взаимоблокировки при добавлении фоновых потоков, ошибки использования самого Win32 API (флаги, идентификаторы, порядок сообщений), обычные ошибки ввода-вывода (они не UB, а `Result`) — и, что важнее всего для этого проекта, все вызовы Win32 из Rust идут через FFI, то есть через `unsafe`, где ответственность за отсутствие UB возвращается к программисту; риски 1, 4 и 5 не исчезли бы, а сосредоточились в помеченных `unsafe`-обёртках.

### Г13.Ч2.З8

**Условие.** *(прикладное)* Ошибки компилятора как техзадание: по полному тексту ошибок `r5_race` (§13.2.2) составьте письменный план исправления программы-счётчика: что предлагает `help: use the move keyword`; почему одного `move` недостаточно (какое правило владения нарушит `main`); какое из трёх легальных решений §13.2.3 повторяет вашу схему из Г13.Ч1.З9 — и сформулируйте общий принцип, которым Rust заменяет «дисциплину синхронизации» C (одно предложение, ключевое слово — владение).

**Решение. Читаем техзадание.** Компилятор выдал **две** ошибки (проверено на rustc 1.97 — обе воспроизводятся дословно), и это не два способа сказать одно и то же, а два разных нарушения.

**Ошибка 1 — E0373: `closure may outlive the current function, but it borrows counter, which is owned by the current function`.** Замыкание, переданное в `thread::spawn`, заимствует `counter`, который принадлежит `main`. Поток может пережить `main` — `spawn` не даёт никаких обещаний о моменте завершения, — а значит, ссылка внутри замыкания может пережить то, на что указывает. Это дословно второе правило заимствования из §13.2.1 и тот же механизм, что в примере с `dangle` (E0106): **ссылка не может пережить владельца**. Предлагаемое исправление — `help: to force the closure to take ownership of counter (and any other referenced variables), use the move keyword`: добавить `move` перед `||`, чтобы замыкание **забрало владение** переменной, а не заимствовало её.

**Ошибка 2 — E0503: `cannot use counter because it was mutably borrowed`.** Пока замыкание держит изменяющее заимствование `counter`, цикл в `main` тоже пишет в `counter`. Нарушено первое правило ссылок: в каждый момент — либо одна изменяющая ссылка, либо сколько угодно читающих. Заметьте, что эта ошибка сообщает уже не о временах жизни, а о **двух писателях** — то есть о самой сути гонки.

**План исправления.**

1. **Принять подсказку `move`.** `thread::spawn(move || { … })` передаёт владение `counter` замыканию. Ошибка E0373 закрывается: заимствования больше нет, есть перемещение, и переживать поток может что угодно — он владеет своей копией.
2. **Обнаружить, что этого недостаточно.** После `move` владельцем `counter` становится замыкание. Значит, `main` владельцем быть перестал — по **правилу 2 владения** («владелец ровно один в каждый момент времени», §13.2.1). А цикл в `main` продолжает писать `counter += 1`, то есть обращаться к значению, которым `main` больше не владеет и которое было перемещено. Компилятор снова откажет — теперь по той же логике, что и E0382 из Г13.Ч2.З2 («использование после перемещения»). Вывод, который стоит записать в план крупными буквами: **исправить эту программу «косметически» нельзя**. Компилятор последовательно отвергает все варианты, потому что отвергает саму конструкцию «два несинхронизированных писателя в одну память»; менять надо не запись, а замысел.
3. **Выбрать одно из трёх легальных решений (§13.2.3).**
   - *Каждому потоку своё, слияние после завершения.* Поток получает (или создаёт) собственный счётчик, `join` возвращает результат, `main` складывает.
   - *Канал*: значения передаются между владельцами, каждое в каждый момент принадлежит кому-то одному.
   - *`Arc<Mutex<i64>>`*: разделяемое владение со счётчиком ссылок плюс мьютекс, гарантирующий, что одновременно пишет один.
4. **Взять первое** — оно уже написано и проверено в C: это ровно `race_fix.c` из Г13.Ч1.З9 (`long partial[2]`, каждому потоку адрес своей ячейки, сложение после обоих `pthread_join`), а «поток отдаёт свою сумму по завершении» из варианта 2 того же задания — его дословный аналог в терминах владения: результат принадлежит потоку и **перемещается** к тому, кто его дождался.

**Почему одного `move` недостаточно — коротко.** Потому что `move` не убирает второго писателя, а лишь решает, кто из двух владелец. После него `main` нарушает правило «владелец ровно один»: он пишет в переменную, владение которой уже передал замыканию. Программа с двумя несинхронизированными писателями не должна существовать — и компилятор не даёт ей существовать ни в одном из вариантов.

**Какое из трёх решений повторяет схему Г13.Ч1.З9.** Первое: «отдать каждому потоку своё и слить результаты после завершения». Совпадение полное, включая момент слияния: в C оно после обоих `pthread_join`, в Rust — после `join()`, который тоже упорядочивает завершение потока и последующий код.

**Общий принцип одним предложением.** Rust заменяет дисциплину синхронизации правилом **владения**: изменяемые данные в каждый момент принадлежат ровно одному, поэтому разделять их можно либо не разделяя вовсе (у каждого потока своё, слияние после `join`), либо через тип, который делает единственность писателя частью владения (канал, `Arc<Mutex<T>>`), — и любой другой вариант просто не компилируется.

**Ответ:** `help: use the move keyword` предлагает добавить `move` перед замыканием, чтобы оно **забрало владение** `counter`, а не заимствовало его, — этим закрывается E0373 («замыкание может пережить функцию, чью переменную оно заимствует»). Одного `move` недостаточно: владельцем `counter` становится замыкание, и по правилу 2 владения («владелец ровно один в каждый момент времени») `main` теряет право писать в него — цикл `counter += 1` в `main` становится использованием перемещённого значения, и компилятор отказывает снова; отдельная ошибка E0503 говорит о том же с другой стороны — о двух писателях при одном разрешённом изменяющем заимствовании. Иными словами, программа с двумя несинхронизированными писателями не собирается ни в одном варианте, и правится не запись, а замысел. Из трёх легальных решений §13.2.3 схему Г13.Ч1.З9 повторяет **первое** — «каждому потоку свои данные, слияние результатов после завершения» (`long partial[2]` + сложение после обоих `pthread_join`; вариант с возвратом суммы через `join` — его же дословный аналог в терминах передачи владения). Общий принцип: **Rust заменяет дисциплину синхронизации правилом владения — изменяемые данные в каждый момент принадлежат ровно одному, поэтому они либо не разделяются вовсе (у каждого потока своё, слияние после `join`), либо разделяются через тип, делающий единственность писателя частью владения (канал, `Arc<Mutex<T>>`), а всё остальное не компилируется.**

**Источники части 13.2 (решения):** R1 (гл. 3, 4, 6, 15, 16); R7 (Rust Reference: порядок вычисления операндов; «Behavior considered undefined»); R9 (справочно: `wrapping_add`, `checked_add`); сторона C: C5 (N3220 §3.5.3, §3.28, §5.1.2.5, §6.2.4, §6.3.1.1, §7.24.3.3), C10; материал курса §§7.1–7.2, 9.1.1, 12.2.2, 12.2.4 и часть 13.1.

## Что стоит помнить о прогонах этой главы

1. **У `oob.c` (§13.1.2) «чистого» запуска нет.** `int i = argc + 3` при `argc >= 1` даёт `i >= 4`, а допустимые индексы 0…3, — оба осмысленных входа под UBSan дают отчёт. Демонстрация «вход решает всё» ставится на программе с правкой одной цифры (`int i = argc + 2`): без аргументов — `a[3] = 40` и молчание, с аргументом — отчёт об индексе 4 (Г13.Ч1.З6, §13.1.4).
2. **ASan и UBSan совместимы** на GCC 13.3: собираются и работают вместе, комбинированная сборка ловит ошибки обоих классов в одном прогоне. Несовместимы ASan и TSan: `cc1: error: '-fsanitize=thread' is incompatible with '-fsanitize=address'` (Г13.Ч1.З8).
3. **Номера строк в отчётах UBSan — свойство файла**, а не программы: с первой строкой-комментарием (как в листингах главы и сборника) отчёты дают `oob.c:9:32`, `nullref.c:7:5`, `divzero.c:8:23`, `addover.c:8:6`; без комментария каждый номер на единицу меньше, столбцы те же (Г13.Ч1.З3).
