## Часть 22.1. Box, Deref, Drop, Rc

### Г22.Ч1.З1

**Условие.** *(механика)* Дан листинг «коробка в работе» из §22.1.1 (`let b = Box::new(5);` и далее). Не запуская: (а) выпишите вывод программы; (б) нарисуйте картину памяти «стек/куча» после первой строки — где лежит `5`, где сам `b`; (в) что и в каком порядке произойдёт на закрывающей скобке `main`? Укажите тип выражения `*b` и объясните, почему `println!("{b}")` работает без звёздочки. Проверьте себя запуском.

**Решение.** Файл `p1/b1_box.rs` — листинг главы дословно:

```rust
// Г22.Ч1.З1: листинг «коробка в работе» из §22.1.1.
fn main() {
    let b = Box::new(5); // значение 5 уехало в кучу
    println!("b = {b}");

    let sum = *b + 1; // * добирается до содержимого
    println!("*b + 1 = {sum}");
} // здесь Box уничтожается — и память в куче освобождается
```

*(а) Предсказание.* `Box::new(5)` кладёт пятёрку в кучу; `{b}` печатает содержимое (§22.1.1 говорит, что за это отвечает реализация `Display` у самой `Box`, — ниже мы это проверим); `*b + 1` разыменовывает и прибавляет единицу. Две строки: `b = 5` и `*b + 1 = 6`.

```
$ rustc --edition 2024 b1_box.rs
$ ./b1_box.exe
b = 5
*b + 1 = 6
```

*(б) Картина памяти после первой строки.* Схема (не вывод программы):

```
        стек                       куча
┌────────────────────┐      ┌─────────────┐
│ b: 8 байт, адрес ──┼─────▶│  5 (i32)    │
└────────────────────┘      └─────────────┘
  сама переменная b            содержимое коробки
```

На стеке живёт **только указатель** — 8 байт на нашей платформе, как любой адрес (§6.1.1); четырёхбайтовая пятёрка лежит в куче, куда её перенёс `Box::new`. Это в точности картина §7.1.1 из тома I, где `int *p = malloc(sizeof(int)); *p = 5;` давал то же самое расположение — с той разницей, что `malloc` мог вернуть `NULL`, а `Box::new` либо возвращает готовую коробку, либо программа аварийно завершается по нехватке памяти (`Box` не бывает нулевым — на этом стоит niche-оптимизация из §22.1.1).

*(в) Что происходит на закрывающей скобке.* По правилам §22.1.2 сначала вызывается деструктор владельца, затем рекурсивно деструкторы содержимого; переменные уходят в порядке, обратном объявлению. Для `Box<i32>` это значит: `Drop` коробки освобождает блок в куче (`i32` собственного деструктора не имеет), `sum` (обычное число на стеке) исчезает вместе с кадром. Ничего не печатается — понаблюдать порядок можно, если положить в коробку тип с `Drop`. Файл `p1/b1_trace.rs`:

```rust
// Г22.Ч1.З1, опыт 3: что происходит на закрывающей скобке main.
struct Tracer(&'static str);

impl Drop for Tracer {
    fn drop(&mut self) {
        println!("drop: {}", self.0);
    }
}

fn main() {
    let _stack = Tracer("stack value");
    let _boxed = Box::new(Tracer("boxed value"));
    println!("end of main");
}
```

```
$ ./b1_trace.exe
end of main
drop: boxed value
drop: stack value
```

`_boxed` объявлен позже — умер раньше; уничтожение коробки уничтожило и `Tracer` внутри неё. Именно этот вызов в §22.1.1 назван «`free`, вписанным в жизнь переменной».

*Тип выражения `*b`.* Спросим компилятор приёмом §21.1.1 — файл `p1/b1_ask.rs`:

```rust
// Г22.Ч1.З1, опыт 2: спрашиваем компилятор, какого типа выражение *b.
fn main() {
    let b = Box::new(5);
    let () = *b; // ⛔ намеренная ошибка: покажи тип
}
```

```
error[E0308]: mismatched types

4 |     let () = *b; // ⛔ намеренная ошибка: покажи тип
```

`{integer}` — это ещё не решённый литеральный тип; согласовывать его не с чем, поэтому срабатывает умолчание языка (§14.2.2) и `b` оказывается `Box<i32>`, а `*b` — `i32`. Ровно поэтому `*b + 1` — обычное целочисленное сложение, а не что-то про указатели.

*Почему `println!("{b}")` работает без звёздочки.* Проверим утверждение §22.1.1 опытом: возьмём обёртку, у которой есть **только** `Deref`, — файл `p1/b1_display_bad.rs`:

```rust
// Г22.Ч1.З1, опыт 4: печатается ли «прозрачно» обёртка, у которой есть только Deref.
use std::ops::Deref;

struct MyBox<T>(T);

impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> &T {
        &self.0
    }
}

fn main() {
    let y = MyBox(5);
    println!("*y = {}", *y); // через звёздочку — работает
    println!("y = {y}"); // ⛔ а так?
}
```

```
  --> b1_display_bad.rs:17:19
   |

   |                   ^^^ `MyBox<{integer}>` cannot be formatted with the default formatter
   |

  --> b1_display_bad.rs:4:1
   |

   | ^^^^^^^^^^^^^^^
```

Значит, deref-коэрция в аргумент `println!` **не** вставляется: макрос ищет реализацию `Display` для самого типа. У `Box<T>` она есть — стандартная библиотека предоставляет `impl Display for Box<T> where T: Display`, которая просто передаёт вызов содержимому (R9, std::boxed). То есть печать без звёздочки — заслуга готовой реализации трейта, а не `Deref`; а вот **точка** (вызов методов) и **аргументы функций** — это уже `Deref` и коэрция (§22.1.2). Два механизма легко перепутать, потому что снаружи оба выглядят как «обёртки будто нет»: короткая проверка на своей обёртке — как здесь — разводит их за одну сборку.

**Ответ:** (а) программа печатает две строки — `b = 5` и `*b + 1 = 6`. (б) На стеке лежит переменная `b` — восьмибайтовый указатель; пятёрка живёт в куче, куда её перенёс `Box::new` (картина §7.1.1, но без `NULL` и без ручного `free`). (в) На закрывающей скобке `main` переменные уничтожаются в порядке, обратном объявлению; уничтожение `Box` освобождает блок в куче вместе с содержимым — наблюдаемо через `Drop`-трассировку (`drop: boxed value`, затем `drop: stack value`). Тип `*b` — `i32` (литерал `5` без суффикса даёт `{integer}`, которое по умолчанию становится `i32`, что и показал E0308). `println!("{b}")` работает не через `Deref`, а через стандартную реализацию `Display` для `Box<T>`, переадресующую печать содержимому: обёртка с одним лишь `Deref` не печатается — E0277.

### Г22.Ч1.З2

**Условие.** *(механика)* Возьмите список `Option<Box<Node>>` из §22.1.1 и допишите две функции в том же стиле: `len(list: &List) -> usize` — число узлов, и `contains(list: &List, target: i32) -> bool` — есть ли значение в списке. Реализуйте каждую дважды: рекурсией через `match` (по образцу `sum`) и циклом `while let` (по образцу обхода). Для списка `1 -> 2 -> 3` программа должна печатать `len = 3`, `contains(2) = true`, `contains(9) = false`.

**Решение.** Тип и конструктор берём из §22.1.1 без изменений — файл `p1/b2_list.rs`, начало:

```rust
// Г22.Ч1.З2: список Option<Box<Node>> — длина и поиск, по два способа каждый.
struct Node {
    value: i32,
    next: List,
}

type List = Option<Box<Node>>;

fn push_front(list: List, value: i32) -> List {
    Some(Box::new(Node { value, next: list }))
}
```

Длина — двумя способами. Рекурсия повторяет форму `sum`: у пустого списка длина 0, у непустого — единица плюс длина хвоста. Цикл повторяет форму обхода: шагаем по цепочке, пока `while let` выделяет `Some`:

```rust
// Рекурсия — по образцу sum из §22.1.1.
fn len_rec(list: &List) -> usize {
    match list {
        Some(node) => 1 + len_rec(&node.next),
        None => 0,
    }
}

// Цикл — по образцу обхода из §22.1.1.
fn len_loop(list: &List) -> usize {
    let mut count = 0;
    let mut cur = list;
    while let Some(node) = cur {
        count += 1;
        cur = &node.next;
    }
    count
}
```

Поиск устроен так же, но с ранним выходом: рекурсия — через `||` (короткое замыкание §2.2.2: если голова совпала, хвост не просматривается), цикл — через `return`:

```rust
fn contains_rec(list: &List, target: i32) -> bool {
    match list {
        Some(node) => node.value == target || contains_rec(&node.next, target),
        None => false,
    }
}

fn contains_loop(list: &List, target: i32) -> bool {
    let mut cur = list;
    while let Some(node) = cur {
        if node.value == target {
            return true;
        }
        cur = &node.next;
    }
    false
}
```

Проверочная программа собирает список `1 -> 2 -> 3` и печатает три ответа дважды — сначала рекурсивными версиями, потом цикловыми:

```rust
fn main() {
    let mut list: List = None;
    list = push_front(list, 3);
    list = push_front(list, 2);
    list = push_front(list, 1);

    println!("len = {}", len_rec(&list));
    println!("contains(2) = {}", contains_rec(&list, 2));
    println!("contains(9) = {}", contains_rec(&list, 9));

    // те же три ответа, но циклом
    println!("len = {}", len_loop(&list));
    println!("contains(2) = {}", contains_loop(&list, 2));
    println!("contains(9) = {}", contains_loop(&list, 9));
}
```

```
$ rustc --edition 2024 b2_list.rs
$ ./b2_list.exe
len = 3
contains(2) = true
contains(9) = false
len = 3
contains(2) = true
contains(9) = false
```

Три места, где легко ошибиться, — разберём их подробно.

**Почему `&List`, а не `List`.** Обе функции только *смотрят* на список, значит, принимают его заимствованием (§15.2.1). Возьми они список по значению — он бы в них переехал, и второй вызов не собрался бы. Именно это и происходит в частой неверной попытке — файл `p1/b2_byvalue_bad.rs`:

```rust
fn len(list: List) -> usize {
    match list {
        Some(node) => 1 + len(node.next),
        None => 0,
    }
}
```

```

  --> b2_byvalue_bad.rs:23:30
   |
17 |     let list: List = Some(Box::new(Node {
   |         ---- move occurs because `list` has type `Option<Box<Node>>`, which does not implement the `Copy` trait
...
22 |     println!("len = {}", len(list));
   |                              ---- value moved here
23 |     println!("len = {}", len(list)); // ⛔ список уже съеден первым вызовом
   |                              ^^^^ value used here after move
```

Компилятор сам называет починку: «this parameter takes ownership of the value» и совет заимствовать. Обратите внимание, что версия «по значению» не просто неудобна — она **уничтожает** список: съеденные узлы освобождаются по ходу подсчёта.

**Что за переменная `node` в `while let Some(node) = cur`.** `cur` имеет тип `&List`, то есть `&Option<Box<Node>>`. Сопоставление с образцом по ссылке даёт привязку по ссылке (правила §16.2.2): `node` — это `&Box<Node>`. Точка сквозь него достаёт поле (`node.value`), а `&node.next` — ссылка на хвост, то есть снова `&List`. Цикл ничего не перемещает и ничего не изменяет: с точки зрения главы 15 он держит одну разделяемую ссылку и переставляет её.

**Почему рекурсия здесь безопасна.** Каждый вызов `len_rec` заводит кадр стека, глубина равна длине списка. Для трёх узлов это ничто, но на списке в миллион элементов рекурсивная версия упрётся в размер стека (§4.3.2) — как и рекурсивное освобождение самого списка, о чём предупреждает R1. Цикловая версия к длине безразлична.

**Ответ:** четыре функции — по две на каждую задачу:

```rust
fn len_rec(list: &List) -> usize {
    match list {
        Some(node) => 1 + len_rec(&node.next),
        None => 0,
    }
}
```

```rust
fn contains_rec(list: &List, target: i32) -> bool {
    match list {
        Some(node) => node.value == target || contains_rec(&node.next, target),
        None => false,
    }
}
```

Цикловые версии держат `cur: &List` и переставляют его на `&node.next`, пока `while let` выделяет `Some`; `len_loop` считает шаги, `contains_loop` выходит через `return true` при первом совпадении. Для списка `1 -> 2 -> 3` обе пары дают одно и то же: `len = 3`, `contains(2) = true`, `contains(9) = false`. Список во всех четырёх функциях принимается по ссылке `&List` — по значению он был бы съеден первым же вызовом (E0382).

**Вариант 2 (итератор по списку).** Раз обход — это «выдавать значения по одному», его можно оформить итератором (§21.2.1), и тогда `len` и `contains` не пишутся вовсе: они превращаются в `count()` и `any()`. Файл `p1/b2_iter.rs`:

```rust
// Итератор по заимствованному списку: хранит место, где стоит обход.
struct Links<'a> {
    cur: &'a List,
}

fn links(list: &List) -> Links<'_> {
    Links { cur: list }
}

impl<'a> Iterator for Links<'a> {
    type Item = i32;

    fn next(&mut self) -> Option<i32> {
        match self.cur {
            Some(node) => {
                self.cur = &node.next; // шаг вперёд по цепочке
                Some(node.value)
            }
            None => None,
        }
    }
}

fn len(list: &List) -> usize {
    links(list).count()
}

fn contains(list: &List, target: i32) -> bool {
    links(list).any(|value| value == target)
}
```

```
$ rustc --edition 2024 b2_iter.rs
$ ./b2_iter.exe
len = 3
contains(2) = true
contains(9) = false
values = [1, 2, 3], sum = 6
```

Состояние итератора — та самая переменная `cur` из цикловой версии, только переехавшая в структуру; `next` делает ровно один шаг цикла. Параметр времени жизни `'a` обязателен: структура хранит ссылку внутрь списка и не должна пережить его (§19.3.2). Последняя строка вывода — бонус: раз это `Iterator`, к списку применим весь арсенал главы 21 (`collect`, `sum`, `filter`, ...), которого у ручных `len`/`contains` не было.

*Сравнение.* Ручные функции — по одной на задачу: коротко, прозрачно, никаких новых типов; но каждая новая операция («сумма», «максимум», «все элементы в вектор») требует новой функции с тем же обходом внутри. Итератор — один раз описанный обход, после которого операции берутся готовыми из библиотеки: `count`, `any`, `sum`, `collect` — и все они ленивые, то есть `contains` через `any` так же прерывается на первом совпадении, как ручной `return true`. Цена — 15 строк объявления, отдельный тип и параметр времени жизни; для одноразового учебного списка это перебор, для библиотечной структуры данных — обязательная программа (так устроены `Vec::iter`, `HashMap::iter` и все прочие коллекции главы 17).

### Г22.Ч1.З3

**Условие.** *(механика)* Воспроизведите путь §22.1.2: (а) объявите `MyBox<T>` без `Deref`, попробуйте `*y` — какой код ошибки и какая формулировка? (б) добавьте `impl Deref` и убедитесь, что заработали и `*y`, и `hello(&m)` для `m: MyBox<String>`. (в) Ответьте: зачем трейту слот `Target` и почему `deref` возвращает `&T`, а не `T` (что сломалось бы при возврате по значению — §15.1.2)?

**Решение.** *(а) Обёртка без `Deref`.* Файл `p1/b3_mybox_bad.rs` — кортежная структура (§16.1.1) с одним полем и конструктором, ничего больше:

```rust
// Г22.Ч1.З3(а): обёртка без Deref — не указатель.
struct MyBox<T>(T);

impl<T> MyBox<T> {
```

Код — **E0614**, формулировка — «type `MyBox<{integer}>` cannot be dereferenced», подчёркнуто выражение `*y` с пояснением «can't be dereferenced». Заметьте `{integer}` в имени типа: параметр `T` вывелся из литерала `5` и остался неопределившимся целым (§14.2.2) — на суть ошибки это не влияет, звёздочка неприменима к структуре независимо от начинки.

*(б) Добавляем `Deref`.* Файл `p1/b3_mybox.rs`:

```rust
    type Target = T; // «разыменование ведёт к T»

        &self.0 // ссылка на содержимое

    println!("privet, {name}!");
}

    let m = MyBox::new(String::from("Rust"));
```

Заработало и то и другое. `*y` компилятор развернул в `*(y.deref())`: наш метод вернул `&T`, внешняя звёздочка добралась до значения. `hello(&m)` — цепочка из двух коэрций (`&MyBox<String>` → `&String` → `&str`), причём вторая — библиотечная, из `impl Deref for String`. Третья строка вывода доказывает, что ручная запись `&(*m)[..]` даёт тот же результат: коэрция — сокращение, а не отдельная семантика.

*(в) Зачем `Target` и почему `&T`.* Два вопроса, ответы связаны.

**Слот `Target`** — ассоциированный тип (§21.2.1): он говорит, *к чему* ведёт разыменование, и делает это **однозначно**. Будь `Deref` обобщён по цели (`trait Deref<Target>`), один тип мог бы реализовать его несколько раз с разными целями — и выражение `*v` перестало бы иметь определённый смысл: компилятору пришлось бы гадать, какое из разыменований имелось в виду, а deref-коэрция вообще потеряла бы почву (какую из цепочек строить?). Ассоциированный тип — способ сказать «у каждого типа-указателя ровно одна цель», ровно как `Item` у `Iterator` («у каждого итератора ровно один тип элемента»).

**Возврат `&T`** — требование владения. Метод получает `&self`, то есть *заимствованную* обёртку; вернуть `T` — значит вынести содержимое наружу, а вынести его из-за разделяемой ссылки нельзя (§15.1.2). Проверим — файл `p1/b3_deref_value_bad.rs` отличается от рабочего только сигнатурой:

```rust
impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> T {
        self.0 // ⛔ вынести содержимое наружу через &self нельзя
    }
}
```

```
error[E0053]: method `deref` has an incompatible type for trait
  --> b3_deref_value_bad.rs:15:24
   |
12 | impl<T> Deref for MyBox<T> {
   |      - found this type parameter
...
15 |     fn deref(&self) -> T {
   |                        ^ expected `&T`, found type parameter `T`
   |
   = note: expected signature `fn(&MyBox<_>) -> &_`
              found signature `fn(&MyBox<_>) -> _`

   |
15 |     fn deref(&self) -> &T {
   |                        +
```

```
error[E0507]: cannot move out of `self` which is behind a shared reference
  --> b3_deref_value_bad.rs:16:9
   |
16 |         self.0 // ⛔ вынести содержимое наружу через &self нельзя
   |         ^^^^^^ move occurs because `self.0` has type `T`, which does not implement the `Copy` trait
```

Две ошибки — два уровня одного запрета. **E0053** — формальный: подпись метода не совпадает с объявленной в трейте (`expected signature fn(&MyBox<_>) -> &_`). **E0507** — содержательный: даже если бы трейт разрешал такую подпись, тело не собралось бы, потому что `self.0` пришлось бы *переместить* из-за разделяемой ссылки. Что сломалось бы по существу: `*v` вычислялось бы как `*(v.deref())`, то есть каждое разыменование выносило бы значение из обёртки, обёртка оставалась бы с дырой, а второе разыменование той же коробки стало бы использованием после переноса. Возврат ссылки оставляет владение на месте: наружу выдаётся только доступ.

**Ответ:** (а) без `Deref` — **E0614** «type `MyBox<{integer}>` cannot be dereferenced», подчёркнуто `*y`: для языка кортежная структура — обычная структура, звёздочка к ней неприменима. (б) С `impl<T> Deref for MyBox<T> { type Target = T; fn deref(&self) -> &T { &self.0 } }` работают оба обращения: `*y` печатает `5`, `hello(&m)` печатает `privet, Rust!` — компилятор построил цепочку `&MyBox<String>` → `&String` → `&str`, и ручная запись `&(*m)[..]` даёт тот же вывод. (в) Слот `Target` задаёт единственную цель разыменования (как `Item` у `Iterator`) — без него у типа могло бы быть несколько разыменований и `*v` стало бы неоднозначным, а deref-коэрция — непостроимой. `deref` возвращает `&T`, потому что получает `&self`: возврат по значению вынес бы содержимое из заимствованной обёртки — это E0507 «cannot move out of `self` which is behind a shared reference» (плюс E0053: подпись не совпадает с трейтом), а по смыслу означало бы, что каждое разыменование опустошает коробку.

### Г22.Ч1.З4

**Условие.** *(понимание)* Тип «конверт в конверте»: `struct Envelope { sender: String, inner: Envelope }`. (а) Объясните словами, почему компилятор не может вычислить его размер, и сверьте свой ответ с текстом E0072 (какие два указания даёт компилятор?). (б) Почините тип так, чтобы вложенность была *необязательной*. (в) Программа с `size_of::<Envelope>()` печатает для починенного типа 32 байта — разложите их по полям (подсказка: §17.1.3 про размер `String`, §16.2.3 про цену `Option` вокруг указателя). (г) Как та же проблема выглядела в C (§8.1.3)?

**Решение.** *(а) Почему размер не вычисляется.* Размер структуры — сумма размеров полей с учётом выравнивания (§8.2.2). Для `Envelope` это `size_of(String) + size_of(Envelope)`, то есть уравнение `x = 24 + x`, у которого нет конечного решения. Компилятору нужно знать размер, чтобы отвести место на стеке, посчитать смещения полей и шаг массива, — а здесь любой ответ противоречит сам себе. Файл `p1/b4_envelope_bad.rs`:

```rust
// Г22.Ч1.З4(а): «конверт в конверте» без косвенности.
struct Envelope {
    sender: String,
    inner: Envelope, // конверт содержит конверт, который содержит конверт...
}

fn main() {}
```

```
error[E0072]: recursive type `Envelope` has infinite size
 --> b4_envelope_bad.rs:2:1
  |
2 | struct Envelope {
  | ^^^^^^^^^^^^^^^
3 |     sender: String,
4 |     inner: Envelope, // конверт содержит конверт, который содержит конверт...
  |            -------- recursive without indirection
  |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
4 |     inner: Box<Envelope>, // конверт содержит конверт, который содержит конверт...
  |            ++++        +
```

**Два указания компилятора.** Первое — диагноз: под полем `inner` подписано `recursive without indirection`, то есть «рекурсия без косвенности» (и заголовок «has infinite size» объясняет, чем это плохо). Второе — рецепт: `help: insert some indirection (e.g., a Box, Rc, or &) to break the cycle`, причём готовая правка выписана посимвольно — `Box<Envelope>` с указанием, куда вставить `Box<` и `>`. Компилятор не выбирает за вас между `Box`, `Rc` и `&`: у них разные модели владения (глава 15 и §22.1.4), решать программисту.

*(б) Починка.* Подсказку берём буквально, но добавляем к ней `Option`: `Box<Envelope>` сделал бы размер конечным, однако вложенность стала бы **обязательной** — бесконечная матрёшка вместо бесконечного типа. Условие требует «необязательной», а необязательность в Rust — это `Option` (§16.2.3). Файл `p1/b4_envelope.rs`:

```rust
// Г22.Ч1.З4(б, в): починенный конверт — вложенность необязательна.
use std::mem::size_of;

struct Envelope {
    sender: String,
    inner: Option<Box<Envelope>>,
}

fn main() {
    let inner = Envelope {
        sender: String::from("Ann"),
        inner: None,
    };
    let outer = Envelope {
        sender: String::from("Bob"),
        inner: Some(Box::new(inner)),
    };

    if let Some(e) = &outer.inner {
        println!("{} -> {}", outer.sender, e.sender);
    }

    println!("String:                {} bytes", size_of::<String>());
    println!("Box<Envelope>:         {} bytes", size_of::<Box<Envelope>>());
    println!(
        "Option<Box<Envelope>>: {} bytes",
        size_of::<Option<Box<Envelope>>>()
    );
    println!("Envelope:              {} bytes", size_of::<Envelope>());
}
```

```
$ rustc --edition 2024 b4_envelope.rs
$ ./b4_envelope.exe
Bob -> Ann
String:                24 bytes
Box<Envelope>:         8 bytes
Option<Box<Envelope>>: 8 bytes
Envelope:              32 bytes
```

*(в) Разложение 32 байт.* Схема (не вывод программы):

```
Envelope = 32 байта
├── sender: String                 24 байта = указатель 8 + capacity 8 + len 8   (§17.1.3)
└── inner:  Option<Box<Envelope>>   8 байт  = указатель 8 + тег 0                (§16.2.3)
```

Оба числа подтверждены прогоном. `String` — тройка «указатель на буфер, ёмкость, длина», 24 байта (§17.1.3). `Box<Envelope>` — обычный указатель, 8 байт. А `Option<Box<Envelope>>` — **тоже 8**: обёртка `Option` вокруг коробки бесплатна, потому что коробка никогда не бывает нулевой и `None` кодируется нулевым адресом (niche-оптимизация, §16.2.3 и §22.1.1). Выравнивание ничего не добавляет: оба поля выровнены на 8, сумма 24 + 8 = 32 без дырок (§8.2.2). Тем самым «необязательная вложенность» досталась нам даром — ровно как `struct Envelope *inner` в C, только с проверкой на `None` в системе типов.

*(г) Как это выглядело в C.* Дословно так же — и упиралось в ту же стену. В §8.1.3 попытка положить структуру в саму себя давала `error: field 'next' has incomplete type`: на момент разбора поля тип ещё не достроен, значит, его размер неизвестен. Лекарство в C — указатель: `struct Node *next` (размер указателя известен всегда, даже на неполный тип), концом цепочки служил `NULL`. Rust произносит ту же мысль другими словами («infinite size», «recursive without indirection») и предлагает три вида косвенности вместо одного; роль `NULL` играет `None`, но, в отличие от C, забыть проверку невозможно — `Option` не разыменовывается без сопоставления с образцом.

**Ответ:** (а) Размер `Envelope` определяется уравнением «размер = 24 байта `String` + размер `Envelope`», решения у которого нет; компилятор даёт **E0072** «recursive type `Envelope` has infinite size» и два указания: диагноз `recursive without indirection` под полем и рецепт `help: insert some indirection (e.g., a Box, Rc, or &) to break the cycle` с готовой правкой `Box<Envelope>`. (б) Необязательная вложенность — `inner: Option<Box<Envelope>>` (голый `Box` дал бы бесконечную матрёшку). (в) 32 байта = 24 (`String`: указатель + ёмкость + длина) + 8 (`Option<Box<Envelope>>`: указатель, `None` — нулевой адрес, тег бесплатен по niche-оптимизации); выравнивание дырок не добавляет. (г) В C то же самое звучало как `field has incomplete type` (§8.1.3) и чинилось указателем `struct Envelope *inner` с `NULL` в роли `None`.

### Г22.Ч1.З5

**Условие.** *(понимание)* Не запуская, выпишите полный вывод программы «ранний уход» из §22.1.2 (листинг с `drop(a)` и блоком). Затем: (а) объясните каждую позицию строк `drop: ...` через правила порядка уничтожения (R7): почему `in_block` — раньше всех, а `a` — до конца `main`; (б) замените `drop(a)` на `a.drop()` — приведите код и текст ошибки и объясните, какой инвариант защищает запрет; (в) объясните, почему функция `drop` не нуждается ни в чём, кроме пустого тела.

**Решение.** Листинг главы — файл `p1/b5_early.rs`, дословно:

```rust
fn main() {
    let a = Tracer { name: "a" };
    {
        let _in_block = Tracer { name: "in_block" };
        println!("внутри блока");
    } // _in_block умирает здесь

    println!("между блоком и drop(a)");
    drop(a); // ранний уход: функция drop из прелюдии забирает владение
    println!("после drop(a) — main ещё работает");
}
```

*Предсказание.* Печатается «внутри блока»; на закрывающей скобке блока умирает `_in_block` — строка `drop: in_block`; затем «между блоком и drop(a)»; `drop(a)` уносит владение и вызывает деструктор — `drop: a`; последняя строка — «после drop(a) — main ещё работает». Итого пять строк:

```
$ rustc --edition 2024 b5_early.rs
$ ./b5_early.exe
внутри блока
drop: in_block
между блоком и drop(a)
drop: a
после drop(a) — main ещё работает
```

*(а) Почему строки стоят именно так.* Правило R7, приведённое в §22.1.2: значение уничтожается, когда заканчивается его область видимости; локальные переменные — в порядке, обратном объявлению.

- `_in_block` объявлен внутри блока `{ ... }`, и его область — этот блок. Скобка закрылась сразу после `println!("внутри блока")` — деструктор сработал там же, раньше всех остальных. Никакой «ранний» механизм для этого не понадобился: у переменной просто маленькая область.
- `a` объявлена в `main` и в обычной жизни умерла бы **последней** — после всех печатей, на закрывающей скобке `main`. Но `drop(a)` забирает владение (§15.1.2): значение переезжает в чужую функцию и умирает вместе с её телом — то есть в этой самой строке. Поэтому `drop: a` стоит **до** последней печати, а не после неё.
- Порядок «обратный объявлению» здесь не виден потому, что живых переменных к концу `main` не осталось вовсе: `_in_block` умер вместе с блоком, `a` — досрочно. Именно так и выглядит польза `drop`: он позволяет закончить жизнь значения раньше конца области, не заводя ради этого блок.

*(б) Ручной вызов деструктора.* Заменяем строку `drop(a);` на `a.drop();` — файл `p1/b5_explicit_bad.rs`:

```rust
    println!("между блоком и drop(a)");
    a.drop(); // ⛔ вызвать деструктор руками нельзя
    println!("после drop(a) — main ещё работает");
}
```

```
error[E0040]: explicit use of destructor method
  --> b5_explicit_bad.rs:20:7
   |
20 |     a.drop(); // ⛔ вызвать деструктор руками нельзя
   |       ^^^^ explicit destructor calls not allowed
   |
help: consider using `drop` function
   |
20 -     a.drop(); // ⛔ вызвать деструктор руками нельзя
20 +     drop(a); // ⛔ вызвать деструктор руками нельзя
   |
```

**E0040** «explicit use of destructor method» с готовой заменой в формате «убрать строку — добавить строку». Защищаемый инвариант: **деструктор значения выполняется ровно один раз**. `a.drop()` — это вызов метода по `&mut self`: значение остаётся живым и владеет всем, чем владело, а на закрывающей скобке `main` рантайм добросовестно вызовет `drop` **второй раз**. Для `Tracer` это была бы лишняя строка в выводе, для `Box` или `String` — освобождение уже освобождённой памяти, то есть double free, гвоздь программы §7.2.1. В C эта ошибка ловилась в лучшем случае санитайзером во время выполнения; здесь она не проходит компиляцию.

*(в) Почему `drop` обходится пустым телом.* Вот вся функция целиком (R9, `std::mem::drop`): `pub fn drop<T>(_x: T) {}`. Работу делает не тело, а **сигнатура**: параметр принимается **по значению**, значит, вызов переносит владение из `a` в `_x` (§15.1.2). Дальше начинает работать общее правило: `_x` — локальная переменная функции, её область заканчивается на закрывающей скобке тела, и рантайм уничтожает её со всей начинкой. Пустое тело — это просто «конец области сразу же». Отсюда два следствия, которые видно в нашем выводе: деструктор срабатывает в момент вызова (а не «когда-нибудь потом»), и после `drop(a)` переменная `a` недоступна — попытка ею воспользоваться дала бы E0382 (§15.1.2), то есть use-after-free из §7.2.1 непредставим синтаксически.

**Ответ:** вывод — пять строк:

```
внутри блока
drop: in_block
между блоком и drop(a)
drop: a
после drop(a) — main ещё работает
```

(а) `drop: in_block` стоит первым, потому что область `_in_block` — внутренний блок, и она закончилась раньше всего; `drop: a` стоит до последней печати, потому что `drop(a)` перенёс владение в чужую функцию и значение умерло вместе с её телом, не дожидаясь конца `main`. (б) `a.drop()` — **E0040** «explicit use of destructor method» с подсказкой `consider using drop function`; запрет охраняет инвариант «деструктор ровно один раз»: ручной вызов не отменяет автоматического, и вышло бы двойное освобождение (§7.2.1). (в) Функции `drop` не нужно тело, потому что всю работу делает сигнатура `fn drop<T>(_x: T)`: аргумент принимается по владению, переезжает внутрь, и уничтожение выполняет обычный конец области видимости параметра.

(а) Выпишите цепочку deref-коэрций с типом на каждом шаге. (б) Запишите эквивалент вручную (без коэрций) и объясните каждый символ своей записи. (в) Сформулируйте три правила коэрции и объясните, почему пути «из `&T` в `&mut U`» среди них нет (§15.2.2). Проверьте (а) и (б) компиляцией.

**Решение.** *(а) Цепочка коэрций.* `shout` ждёт `&str`, а `&b` — это `&Box<String>`. Компилятор строит цепочку, применяя правило 1 столько раз, сколько нужно (§22.1.2):

| Шаг | Тип на входе | Чей `Deref` | Тип на выходе |
|---|---|---|---|
| 0 | `&Box<String>` | — | это то, что написано в вызове |
| 1 | `&Box<String>` | `impl Deref for Box<T>` (`Target = T`) | `&String` |
| 2 | `&String` | `impl Deref for String` (`Target = str`) | `&str` |

Две коэрции — и `shout` получает ровно тот тип, который объявлен в её сигнатуре. Вся работа сделана при компиляции: в машинном коде остаётся передача одного и того же адреса (у `Box<String>` содержимое — сам `String`, у `String` — байтовый буфер), никаких вызовов `deref` в рантайме нет.

*(б) То же вручную.* Файл `p1/b6_shout.rs` — обе записи рядом, плюс цепочка, выписанная по шагам:

```rust
// Г22.Ч1.З6: коэрции сквозь Box<String>.
fn shout(s: &str) {
    println!("{}!", s.to_uppercase());
}

fn main() {
    let b = Box::new(String::from("ура"));

    shout(&b); // &Box<String> -> &String -> &str: две коэрции

    shout(&(*b)[..]); // то же самое вручную, без коэрций

    // цепочка по шагам: каждая аннотация в let — место коэрции
    let r0: &Box<String> = &b;
    let r1: &String = r0;
    let r2: &str = r1;
    shout(r2);
}
```

Разбор записи `&(*b)[..]` посимвольно, изнутри наружу:

- `*b` — разыменование коробки, то есть `*(b.deref())`; тип — `String`. Это **место**, а не копия: значение остаётся в куче, мы лишь получили доступ к нему.
- `(*b)[..]` — индексация полным диапазоном (§15.3.2): для `String` операция `Index<RangeFull>` даёт `str` — тоже «место», причём типа без размера (DST, §15.3.1).
- `&(*b)[..]` — ссылка на это место: `&str`. Скобки вокруг `*b` обязательны, потому что индексация связывает сильнее звёздочки.

Три строки `УРА!` подтверждают: ручная запись, автоматическая коэрция и пошаговая цепочка через `let`-аннотации дают один и тот же результат. Заодно видно второе место коэрции, помимо аргументов вызова: `let r1: &String = r0;` — присваивание с аннотацией типа (R7, type-coercions).

*(в) Три правила и отсутствующее четвёртое.* Правила из §22.1.2:

1. `&T` → `&U`, если `T: Deref<Target = U>`;
2. `&mut T` → `&mut U`, если `T: DerefMut<Target = U>`;
3. `&mut T` → `&U`, если `T: Deref<Target = U>` — изменяющую ссылку можно «понизить» до разделяемой.

Четвёртого правила — «`&T` → `&mut U`» — нет и быть не может: оно создало бы изменяющий доступ из разделяемого, а это прямое нарушение §15.2.2 («читатели XOR писатель»). Если бы такое превращение существовало, из одной `&T` можно было бы наделать сколько угодно `&mut U` на одни данные, и все гарантии главы 15 рассыпались бы. Компилятор отвечает на попытку обычным несовпадением типов — файл `p1/b6_mut_bad.rs`:

**Ответ:** (а) `shout(&b)` даёт цепочку из двух коэрций: `&Box<String>` --(`Deref for Box`)--> `&String` --(`Deref for String`)--> `&str`; обе строятся при компиляции и в рантайме ничего не стоят. Обратное направление законно и работает: `shout_mut(&mut b)` при `let mut b` печатает `HEY`.

### Г22.Ч1.З7

**Условие.** *(понимание)* Сравните два хранилища фигур: `Vec<Circle>` + `Vec<Rect>` (два однородных вектора) и единый `Vec<Box<dyn Shape>>`. (а) Что физически лежит в элементе каждого вектора и почему `Box<dyn Shape>` занимает 16 байт — из чего они состоят? (б) Как ищется код `area()` при вызове в каждом случае и на каком этапе (компиляция/рантайм) принимается решение? (в) Почему вызов через vtable нельзя встроить (inline) и что это значит для горячего цикла? (г) Назовите задачу, которую два однородных вектора не решают в принципе, и задачу, где они предпочтительнее. Сверьтесь с таблицей §22.1.3 и данными прогона размеров.

**Решение.** Оба хранилища собраны в одной программе, чтобы сравнивать было честно, — файл `p1/b7_sizes.rs`:

```rust
        + rects.iter().map(|r| r.area()).sum::<f64>();

    let shapes: Vec<Box<dyn Shape>> = vec![

        Box::new(Circle { r: 2.0 }),
```


*(а) Что физически лежит в элементе.* Схема (не вывод программы):

```
Vec<Circle>            элемент — САМА фигура, 8 байт (f64 r), данные в буфере вектора
┌──────┬──────┐
│ r=1.0│ r=2.0│  ← куча вектора, шаг 8 байт, никаких других аллокаций
└──────┴──────┘

Vec<Box<dyn Shape>>    элемент — ШИРОКИЙ УКАЗАТЕЛЬ, 16 байт
┌────────────────┬────────────────┐
│ данные │vtable │ данные │vtable │  ← буфер вектора
└───┬────┴───┬───┴───┬────┴───┬───┘
    ▼        ▼       ▼        ▼
 Circle   vtable  Rect     vtable
 в куче  (Circle, (своя    (Rect,
         Shape)   куча)    Shape)
```

`Box<dyn Shape>` — 16 байт, и прогон это подтверждает: `&Circle` и `Box<Circle>` (обычные, «тонкие» указатели) — по 8, `&dyn Shape` и `Box<dyn Shape>` — по 16. Половина — адрес данных, половина — адрес vtable, таблицы методов пары «тип + трейт», которую собрал компилятор (§22.1.3). Сам `Vec` в обоих случаях — 24 байта заголовка (указатель, ёмкость, длина, §17.1.1), разница — в том, что лежит в буфере и сколько аллокаций сделано: у хранилища A их одна на вектор, у B — одна на вектор плюс по одной на каждую фигуру.

*(б) Как ищется код `area()`.* В хранилище A тип элемента известен статически: `circles.iter().map(|c| c.area())` — это `Circle::area`, адрес подставлен при компиляции, а благодаря мономорфизации (§19.1.3) каждая копия цикла знает свой тип. В хранилище B элемент — `Box<dyn Shape>`; компилятор знает только номер записи, которая соответствует методу `area` в vtable трейта `Shape`. Код читает адрес из таблицы, на которую указывает вторая половина широкого указателя, и делает косвенный вызов. Решение «какой код исполнить» принимается **в рантайме** — поздняя привязка (R7).

*(в) Почему вызов через vtable не встраивается.* Это видно в машинном представлении. Файл `p1/b7_dispatch.rs` содержит две функции с одинаковым телом `s.area()`, различающиеся только видом параметра:

```rust
// Дженерик: мономорфизация даст свою копию под каждый тип (§19.1.3).
#[inline(never)]
pub fn via_generic<S: Shape>(s: &S) -> f64 {
    s.area()
}

// Трейт-объект: адрес метода придёт из vtable в рантайме.
#[inline(never)]
pub fn via_dyn(s: &dyn Shape) -> f64 {
    s.area()
}
```

Смотрим, во что они превратились, приёмом §19.1.3 (`--emit=llvm-ir`, оптимизация включена):

```

$ grep -A 5 "^define.*via_generic" b7_dispatch.ll

start:
  %_2.i = fmul double %s.0.val, 3.000000e+00
  %_0.i = fmul double %s.0.val, %_2.i
  ret double %_0.i

```

Имя функции содержит `via_generic` **и** `Circle`: это мономорфизированная копия под конкретный тип. Вызова `area` в ней нет вовсе — тело метода **встроено**: два умножения и возврат. Теперь версия с трейт-объектом:

```
$ grep -A 4 "^define.*via_dyn" b7_dispatch.ll

  %_0 = tail call noundef double %s.1.24.val(ptr noundef nonnull %s.0)
  ret double %_0
}
```

Функция одна на все типы (`Circle` в имени нет), параметров у неё **два** — это и есть широкий указатель, разобранный на половинки: `%s.0` — данные, `%s.1.24.val` — вынутый из vtable адрес метода. И вызов сделан **через значение** `%s.1.24.val`, а не по имени функции. Встроить тут нечего: чтобы подставить тело, компилятору нужно знать, *какое* тело, а он его не знает — выбор произойдёт при исполнении. Для горячего цикла это значит: нет инлайна — нет и всего, что за ним следует (свёртки констант, векторизации, устранения проверок); остаётся косвенный вызов, который вдобавок хуже предсказывается процессором. Для трёх фигур в отчёте разница неизмерима, для миллиона вызовов в кадре — измерима.

*(г) Что каждое хранилище решает и чего не решает.* Два однородных вектора не решают в принципе задачу **общего списка в исходном порядке**: «нарисовать сцену — фигуры в том порядке, в каком их добавил пользователь». Хранилища A перебирают типы по отдельности, и общий порядок восстановить нечем; добавление четвёртого типа означает четвёртый вектор и правку каждого места, где фигуры перебираются, а тип, объявленный *пользователем библиотеки*, в вашу коллекцию не попадёт никогда. Зато они предпочтительнее, когда типы обрабатываются пачками и производительность важна: «посчитать суммарную площадь всех кругов» — сплошной проход по 8-байтовым элементам без единой косвенности, с инлайном и векторизацией; это же расположение памяти естественно для расчётных задач.

Попытка обойтись без коробки — ещё одно подтверждение, что `dyn` живёт только за указателем; файл `p1/b7_novec_bad.rs`:

```
error[E0277]: the size for values of type `dyn Shape` cannot be known at compilation time
  --> b7_novec_bad.rs:17:17
   |
17 |     let shapes: Vec<dyn Shape> = Vec::new(); // ⛔ размер элемента неизвестен
   |                 ^^^^^^^^^^^^^^ doesn't have a size known at compile-time
   |
   = help: the trait `Sized` is not implemented for `dyn Shape`
```

`Vec` обязан знать шаг между элементами, а у `dyn Shape` размера нет (§15.3.1) — отсюда и коробка: она даёт элементу фиксированные 16 байт.

**Ответ:** (а) В `Vec<Circle>` элемент — сама фигура (8 байт, данные в буфере вектора, аллокация одна). В `Vec<Box<dyn Shape>>` элемент — широкий указатель 16 байт = 8 байт адреса данных + 8 байт адреса vtable; каждая фигура лежит в своей аллокации. Подтверждено прогоном: `&Circle` и `Box<Circle>` — 8 байт, `&dyn Shape` и `Box<dyn Shape>` — 16. (б) В однородном векторе адрес `area` подставлен при компиляции (мономорфизация, §19.1.3); в векторе коробок адрес читается из vtable при каждом вызове — решение принимается в рантайме. (в) Встроить косвенный вызов нельзя, потому что тело неизвестно на этапе компиляции: в LLVM-IR у `via_generic` тело метода уже подставлено (`fmul`, `fmul`, `ret` — вызова нет), а `via_dyn` принимает две половины широкого указателя и делает `tail call ... %s.1.24.val` — вызов через значение. Для горячего цикла это потеря инлайна и следующих за ним оптимизаций. (г) Два однородных вектора не решают задачу разнородной коллекции в общем порядке (и не принимают типы, добавленные пользователем библиотеки); они предпочтительнее для однотипных пачек, где важны плотность памяти и скорость: сплошной проход по 8-байтовым элементам без косвенности.

### Г22.Ч1.З8

**Условие.** *(прикладное)* Библиотека фигур. Все тесты зелёные; приведите строку `test result`.

**Решение.** Пакет-библиотека (§20.1.1):

Трейт и три фигуры — файл `p1/shapes/src/lib.rs`:

```rust
// Библиотека shapes: разнотипные фигуры за общим интерфейсом (Г22.Ч1.З8).

/// Общий интерфейс фигуры: как называется и какова площадь.
pub trait Shape {
    fn name(&self) -> &'static str;
    fn area(&self) -> f64;
}

pub struct Circle {
    pub r: f64,
}

pub struct Rect {
    pub w: f64,
    pub h: f64,
}

pub struct Triangle {
    pub base: f64,
    pub height: f64,
}

impl Shape for Circle {
    fn name(&self) -> &'static str {
        "circle"
    }
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.r * self.r
    }
}

impl Shape for Rect {
    fn name(&self) -> &'static str {
        "rect"
    }
    fn area(&self) -> f64 {
        self.w * self.h
    }
}

impl Shape for Triangle {
    fn name(&self) -> &'static str {
        "triangle"
    }
    fn area(&self) -> f64 {
        self.base * self.height / 2.0
    }
}
```

Обе функции работают со срезом коробок и потому одинаково относятся ко всем фигурам — и к тем, которых библиотека не знает:

```rust
/// Сумма площадей набора. Пустой срез даёт 0.0.
pub fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
    shapes.iter().map(|s| s.area()).sum()
}

/// Имя фигуры с наибольшей площадью; None для пустого среза.
pub fn largest_name(shapes: &[Box<dyn Shape>]) -> Option<&'static str> {
    shapes
        .iter()
        .max_by(|a, b| a.area().partial_cmp(&b.area()).unwrap())
        .map(|s| s.name())
}
```

**Почему сравнение с допуском.** `total_area` трёх фигур — это `π + 12 + 6`, а `π` в двоичной плавающей точке представим лишь приближённо (§2.1.3). Сумма трёх слагаемых, сложенных в другом порядке, может отличаться в последнем бите — и `assert_eq!` на `f64` был бы тестом не про площадь, а про порядок сложения. Поэтому `assert!((получилось - ожидалось).abs() < 1e-9)`. Единственное место, где `==` уместно, — пустой срез: `sum()` по пустому итератору возвращает ровно `0.0`, никакой арифметики не было.

**Почему `max_by`, а не `max`.** `max` требует `Ord`, а `f64` его не реализует — из-за `NaN` порядок на плавающих неполный (§2.1.3). `max_by` принимает компаратор, и мы строим его из `partial_cmp`, разворачивая `Option` через `unwrap`. Это единственное место с потенциальной паникой: если чья-то `area()` вернёт `NaN`, сравнение окажется неопределённым и `unwrap` уронит программу. Для библиотеки фигур такой вход — заведомо ошибочные данные (радиус `NaN`), и падение честнее молчаливой чепухи; будь это библиотека общего назначения, стоило бы возвращать `Result` или явно оговорить контракт.

**Почему `&[Box<dyn Shape>]`, а не `Vec<Box<dyn Shape>>`.** Срез — самая слабая форма запроса (§15.3.2): функция берёт то, что ей нужно (только читать), и подходит и вектору, и массиву, и куску вектора. Владение здесь не требуется вовсе.

**Как чужая фигура попадает в коллекцию.** `Square` объявлен в тестовом модуле — библиотека о нём не знает и не может знать. Достаточно `impl Shape for Square`: `Box::new(Square { .. })` превращается в `Box<dyn Shape>` приведением, к которому компилятор пристёгивает vtable пары «`Square` + `Shape`» (§22.1.3). Это и есть открытость трейт-объектов: расширять систему может пользователь библиотеки, не трогая её исходников.

Программа печатает `strong_count` до и после раздачи и результат работы подсистем. Затем письменно: (а) почему поля `&Config` потребовали бы параметра времени жизни и чем это ограничило бы использование (§19.3.2, §15.2.3); (б) что именно копирует `Rc::clone` и почему `String` внутри конфига не дублируется; (в) при каком условии счётчик вернётся к 1 и когда `Config` будет уничтожен.

**Решение.** Программа §22.1.4 плюс то, чего в главе не было: трассировка уничтожения самого конфига — иначе на вопрос (в) нечем ответить, кроме рассуждения. Файл `p1/b10_config.rs`:

```rust
// Г22.Ч1.З10: разделяемая конфигурация из §22.1.4 с трассировкой уничтожения.
use std::rc::Rc;

struct Config {
    lang: String,
    verbose: bool,
}

impl Drop for Config {
    fn drop(&mut self) {
        println!("drop: Config");
    }
}

struct Parser {
    config: Rc<Config>,
}

struct Reporter {
    config: Rc<Config>,
}
```

```rust
fn main() {
    let config = Rc::new(Config {
        lang: String::from("ru"),
        verbose: true,
    });
    println!("владельцев после создания: {}", Rc::strong_count(&config));

    {
        let parser = Parser {
            config: Rc::clone(&config),
        };
        let reporter = Reporter {
            config: Rc::clone(&config),
        };
        println!("владельцев после раздачи: {}", Rc::strong_count(&config));

        let words = parser.parse("раз два три");
        reporter.report(words);
    } // подсистемы умерли — их Rc вернули счётчик

    println!("владельцев после блока: {}", Rc::strong_count(&config));
    println!("конец main");
}
```

```
$ rustc --edition 2024 b10_config.rs
$ ./b10_config.exe
владельцев после создания: 1
владельцев после раздачи: 3
[разбор] вход: "раз два три"
слов: 3 (язык интерфейса: ru)
владельцев после блока: 1
конец main
drop: Config
```

Счётчик дышит: 1 → 3 → (конец блока) → 1 → 0. Последняя строка — доказательство: `Config` уничтожен **после** «конец main», то есть в момент смерти последнего владельца, и ровно один раз.

*(а) Почему `&Config` в полях потребовал бы времени жизни.* Структура, хранящая ссылку, обязана объявить, откуда эта ссылка (§19.3.2): `struct Parser<'a> { config: &'a Config }`. Параметр `'a` — это обещание компилятору: «`Parser` не переживёт то, на что смотрит». Обещание проверяется, и цена его — в том, что `Parser` перестаёт быть самостоятельным значением: его нельзя вернуть из функции, создавшей `Config` локально (§15.2.3), нельзя положить в структуру, живущую дольше, нельзя собрать «фабрику подсистем». Вариант 2 ниже показывает и рабочий случай, и стену, в которую он упирается.

*(б) Что копирует `Rc::clone`.* Только указатель на аллокацию — и увеличивает счётчик на единицу. Ни `Config`, ни `String` внутри него не дублируются: они лежат в куче в одном экземпляре, а `String` — это вообще отдельный буфер, на который смотрит поле структуры. Именно поэтому в главе оговорена конвенция писать `Rc::clone(&config)`, а не `config.clone()`: читающий должен видеть, что операция стоит одно приращение целого, а не глубокую копию (§15.1.3). Прогон подтверждает: три владельца — но `[разбор]` и `слов:` печатают один и тот же `lang`, взятый из одного места.

*(в) Когда счётчик вернётся к 1 и когда умрёт `Config`.* Счётчик уменьшается на единицу при смерти каждого `Rc` — а `Rc` подсистем живут в их полях, значит, гибнут вместе с подсистемами (`Drop` структуры уничтожает поля, §22.1.2). Как только оба — `parser` и `reporter` — вышли из области видимости (закрывающая скобка блока), счётчик вернулся к 1: остался единственный владелец, переменная `config`. `Config` будет уничтожен, когда счётчик дойдёт до **нуля**, то есть когда умрёт и она, — на закрывающей скобке `main`. В выводе это видно буквально: `drop: Config` стоит после `конец main`. Если бы подсистемы жили до конца `main` (без блока), порядок был бы другим, но результат тем же: последний уходящий гасит свет.

**Ответ:** программа печатает счётчик 1 → 3 → 1 и уничтожает `Config` последней строкой, после «конец main» (ниже — только строки про счётчик и финал, между ними в выводе стоят две строки работы подсистем):

```
владельцев после создания: 1
владельцев после раздачи: 3
владельцев после блока: 1
конец main
drop: Config
```

(а) Поле `&Config` заставило бы объявить `struct Parser<'a> { config: &'a Config }`: структура со ссылкой обязана назвать время жизни (§19.3.2) и не может пережить оригинал — такой `Parser` нельзя вернуть из функции, создавшей `Config` локально (§15.2.3), то есть нельзя построить фабрику подсистем. (б) `Rc::clone` копирует один указатель и увеличивает счётчик: сам `Config` и его `String` остаются в куче в единственном экземпляре — данные не дублируются, стоимость O(1) (потому конвенция и требует писать `Rc::clone(&x)` вместо `x.clone()`). (в) Счётчик вернётся к 1, когда умрут обе подсистемы (их `Rc` — поля структур, гибнут вместе с ними); `Config` будет уничтожен при нуле, то есть после смерти последней переменной-владельца — что и подтверждает `drop: Config` после «конец main».

**Вариант 2 (ссылки вместо `Rc`).** Пока все подсистемы живут в той же области, что и конфиг, разделение достигается обычным заимствованием — без аллокации, без счётчика, с проверкой на этапе компиляции. Файл `p1/b10_lifetime.rs`:

```rust
struct Parser<'a> {
    config: &'a Config,
}

struct Reporter<'a> {
    config: &'a Config,
}

impl Parser<'_> {
    fn parse(&self, src: &str) -> usize {
        if self.config.verbose {
            println!("[разбор] вход: {src:?}");
        }
        src.split_whitespace().count()
    }
}
```

```
$ rustc --edition 2024 b10_lifetime.rs
$ ./b10_lifetime.exe
[разбор] вход: "раз два три"
слов: 3 (язык интерфейса: ru)
конец main
```

Работает и печатает то же самое — минус строки про счётчик, которого больше нет. Запись `impl Parser<'_>` — анонимное время жизни (§19.3.2): методу всё равно, какое оно, лишь бы существовало. А теперь стена, о которой говорит пункт (а), — файл `p1/b10_factory_bad.rs`:

```rust
fn make_parser<'a>() -> Parser<'a> {
    let config = Config {
        lang: String::from("ru"),
        verbose: true,
    };
    Parser { config: &config } // ⛔ ссылка на локальную переменную
}
```

```
error[E0515]: cannot return value referencing local variable `config`
  --> b10_factory_bad.rs:16:5
   |
16 |     Parser { config: &config } // ⛔ ссылка на локальную переменную
   |     ^^^^^^^^^^^^^^^^^-------^^
   |     |                |
   |     |                `config` is borrowed here
   |     returns a value referencing data owned by the current function
```

**E0515** — «возвращаемое значение ссылается на локальную переменную». Обещание `'a` невыполнимо: `config` умрёт на выходе из функции, а `Parser` собирался жить дальше. С `Rc<Config>` та же фабрика собирается без единого замечания — подсистема уносит **владение** долей конфига, и оригинальной переменной жить дольше не нужно.

*Сравнение.* Ссылки дешевле по всем статьям: ноль аллокаций, ноль счётчиков, проверка на этапе компиляции, ошибку видно до запуска. Их естественная область — «конфиг создан в `main`, подсистемы живут тут же и умрут раньше»: времена жизни выстраиваются в дерево, и заимствование его описывает. `Rc` нужен там, где дерево не выстраивается или не известно заранее: фабрики, возвращающие связанные объекты; коллекции подсистем с разной судьбой; данные, у которых нет одного естественного «главного» владельца. Плата — аллокация под конфиг, счётчик и невозможность изменить содержимое (E0596, §22.1.4), пока не позовёшь `RefCell` из части 22.2. Правило выбора из §22.1.4 звучит буквально так: сначала пробуем `&`/`&mut`, `Rc` — когда времена жизни не сошлись.

## Часть 22.2. Внутренняя изменяемость

### Г22.Ч2.З1

**Условие.** *(механика)* Дан листинг «пропуска в действии» из §22.2.1 (ячейка `RefCell::new(5)`, два блока-скобки, чтение и запись). (а) Не запуская, выпишите вывод. (б) Укажите типы переменных `r` и `w` и объясните, почему для `*w += 10` переменная `w` объявлена `mut`, а сама `cell` — нет. (в) Уберите оба внутренних блока (пропуска станут жить до конца `main`) — предскажите, что произойдёт и на какой строке; проверьте запуском и приведите текст паники.

**Решение.** *(а) Предсказание.* Листинг главы — файл `p2/r1_cell.rs`:

```rust
fn main() {
    let cell = RefCell::new(5);

    {
        let r = cell.borrow(); // Ref<i32> — «пропуск читателя»
        println!("прочитали: {}", *r);
    } // пропуск сдан — счётчик читателей снова 0

    {
        let mut w = cell.borrow_mut(); // RefMut<i32> — «пропуск писателя»
        *w += 10;
    } // писатель закончил

    println!("после записи: {}", *cell.borrow());
}
```

Первый блок берёт пропуск читателя и печатает `прочитали: 5`; на закрывающей скобке пропуск сдан. Второй берёт пропуск писателя и добавляет 10 — печати нет. Последняя строка берёт третий пропуск (читателя) и печатает `после записи: 15`. Две строки:

```
$ rustc --edition 2024 r1_cell.rs
$ ./r1_cell.exe
прочитали: 5
после записи: 15
```

*(б) Типы и два `mut`.* `cell.borrow()` возвращает **`Ref<i32>`**, `cell.borrow_mut()` — **`RefMut<i32>`**. Оба — умные указатели (§22.1.2): у них есть `Deref` (потому `*r` и `*w` добираются до `i32`) и `Drop` (потому пропуск возвращается в журнал ячейки автоматически, на закрывающей скобке).

Теперь два разных «mut», которые в этом задании стоят рядом и потому путаются.

- `let mut w` — про **переменную `w`**. Выражение `*w += 10` изменяет то, на что смотрит `w`, а изменяющий доступ через умный указатель требует `DerefMut`, то есть заимствования `&mut w`; заимствовать переменную изменяющим образом можно, только если она объявлена `mut` (§15.2.1). Уберём `mut` — файл `p2/r1_nomut_bad.rs`:

```
error[E0596]: cannot borrow `w` as mutable, as it is not declared as mutable
 --> r1_nomut_bad.rs:9:10
  |
9 |         *w += 10;
  |          ^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
8 |         let mut w = cell.borrow_mut(); // ⛔ а вот пропуску mut нужен
  |             +++
```

- `let cell` — **без** `mut`, и это не оплошность, а суть внутренней изменяемости. Ячейке изменяющий доступ не нужен: `borrow_mut` объявлен как `fn borrow_mut(&self) -> RefMut<'_, T>` — он принимает **разделяемую** ссылку и выдаёт право на запись, опираясь на собственный журнал, а не на систему типов (R7, interior-mutability; фундамент — `UnsafeCell`). Снаружи ячейка выглядит неизменяемой, внутри — изменяется: ровно то, что §15.2.2 запрещал обычным типам.

*(в) Без блоков.* Уберём внутренние скобки — пропуска станут жить до конца `main`, и второй же вызов застанет ячейку занятой. Ждём паники на строке `let mut w = cell.borrow_mut();`: читатель ещё жив (переменная `r` не умерла), значит `borrow_mut` не сможет отметить писателя. Файл `p2/r1_noblocks.rs`:

```rust
fn main() {
    let cell = RefCell::new(5);

    let r = cell.borrow(); // пропуск читателя больше не сдаётся досрочно
    println!("прочитали: {}", *r);

    let mut w = cell.borrow_mut(); // ⛔ писатель при живом читателе
    *w += 10;

    println!("после записи: {}", *cell.borrow());
}
```

```
$ ./r1_noblocks.exe
прочитали: 5

thread 'main' (31024) panicked at r1_noblocks.rs:10:22:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Предсказание сбылось: первая печать успела пройти, а на строке 10 (это и есть `let mut w = cell.borrow_mut();`) программа упала с текстом **«RefCell already borrowed»** — «ячейка уже занята (читателем)». Столбец 22 указывает на сам вызов `borrow_mut()`. Код возврата — 101, обычный для паники (§18.1.3). Обратите внимание: NLL (§15.2.1) здесь не помогает — `r` больше не используется после первой печати, но `Ref` не «заканчивается на последнем использовании»: это значение с `Drop`, и живёт оно до конца области (§22.1.2). Отсюда дисциплина §22.2.1: пропуск берут как можно позже и отдают как можно раньше — блоком или явным `drop(r)`.

**Ответ:** (а) две строки — `прочитали: 5` и `после записи: 15`. (б) `r` — `Ref<i32>`, `w` — `RefMut<i32>`; оба пропуска суть умные указатели с `Deref` и `Drop`. `w` объявлена `mut`, потому что `*w += 10` изменяет данные *через* пропуск и требует изменяющего заимствования самой переменной `w` (без `mut` — E0596). А `cell` в `mut` не нуждается, потому что `borrow_mut` принимает `&self`: разрешение на запись выдаёт журнал ячейки, а не система типов, — это и есть внутренняя изменяемость. (в) Без блоков программа печатает `прочитали: 5` и падает на строке `let mut w = cell.borrow_mut();` с паникой `RefCell already borrowed` (код возврата 101): пропуск читателя `r` живёт до конца `main` — NLL не сокращает жизнь значения с `Drop`.

### Г22.Ч2.З2

**Условие.** *(механика)* Закройте вывод листинга «дерево» из §22.2.3 и восстановите по рассуждению все восемь строк: обе пары `strong`/`weak` для `leaf` и `branch` в каждой точке печати и оба ответа `show_parent` после связывания. Для каждой цифры назовите, *кто именно* держит ссылку. Проверьте себя запуском.

**Решение.** Восстанавливаем по одному правилу: `strong_count` — это число живых `Rc`, указывающих на аллокацию, `weak_count` — число живых `Weak`. Считать надо не «сколько имён у узла», а **кто именно** его держит. Файл `p2/r2_tree.rs` — листинг главы дословно; идём по точкам печати.

**Точка 1 — до связывания.** Создан только `leaf`; его поле `parent` — `Weak::new()`, то есть слабая ссылка «в никуда». `show_parent` вызывает `upgrade()`, получает `None` — и это не «родитель умер», а «родителя и не было»: пустая слабая ссылка не указывает ни на какую аллокацию. Счётчики `leaf`: strong 1 — **переменная `leaf`**; weak 0 — на сам `leaf` слабых ссылок никто не заводил.

**Точка 2 — внутри блока, после связывания.** `branch` создан со списком детей `vec![Rc::clone(&leaf)]`, а затем выполнено `*leaf.parent.borrow_mut() = Rc::downgrade(&branch);`. Считаем:

- детей у `branch` — 1 (вектор `children` содержит один `Rc`);
- `branch`: strong 1 — **только переменная `branch`**; поле `leaf.parent` слабое и в сильный счёт не идёт. weak 1 — **та самая ссылка из `leaf.parent`**;
- `leaf`: strong 2 — **переменная `leaf`** и **`Rc` внутри `branch.children`**; weak 0 — слабых ссылок на `leaf` нет ни у кого. Ссылка вверх слабая, а вниз — сильная: считаются только вторые;
- `show_parent("внутри блока", ...)`: `upgrade()` находит живую аллокацию и возвращает `Some`, печатается значение родителя — 5.

**Точка 3 — после блока.** На закрывающей скобке умерла переменная `branch` — единственный сильный владелец. Счётчик сильных дошёл до нуля, значение `branch` уничтожено, невзирая на живую слабую ссылку. Поэтому `show_parent("после блока", ...)` даёт «родителя нет»: `upgrade()` вернул `None`. Счётчики `leaf`: strong 1 — вектор `children` умершего `branch` уничтожен вместе с ним и отпустил свой `Rc`, осталась переменная; weak 0 — как и было.

Итого восемь строк:

```
$ rustc --edition 2024 r2_tree.rs
$ ./r2_tree.exe
до связывания: родителя нет
leaf: strong = 1, weak = 0
детей у branch: 1
branch: strong = 1, weak = 1
leaf: strong = 2, weak = 0
внутри блока: родитель жив, value = 5
после блока: родителя нет
leaf: strong = 1, weak = 0
```

Восстановленное совпало с прогоном. Полезно проговорить, чего в этих числах **нет**: `Weak` из `leaf.parent` жив всё это время, но он не появляется ни в одном `strong_count` — слабая ссылка не участвует в решении «жив ли объект». И наоборот: `weak_count` у `branch` равен 1 и после смерти `branch` — счётчики продолжают существовать, пока живёт хоть одна слабая ссылка (аллокация под счётчиками освобождается последней, R9); на судьбу *значения* это уже не влияет.

**Ответ:** восемь строк с расшифровкой, кто держит ссылку:

| Строка вывода | Кто держит |
|---|---|
| `до связывания: родителя нет` | `leaf.parent` = `Weak::new()`, `upgrade()` → `None` |
| `leaf: strong = 1, weak = 0` | strong: переменная `leaf` |
| `детей у branch: 1` | `branch.children` содержит один `Rc` на `leaf` |
| `branch: strong = 1, weak = 1` | strong: переменная `branch`; weak: ссылка из `leaf.parent` |
| `leaf: strong = 2, weak = 0` | strong: переменная `leaf` + `Rc` внутри `branch.children` |
| `внутри блока: родитель жив, value = 5` | `upgrade()` → `Some`: сильный владелец `branch` жив |
| `после блока: родителя нет` | `branch` умер (strong 0), `upgrade()` → `None` |
| `leaf: strong = 1, weak = 0` | вектор `children` умер вместе с `branch` и отпустил `Rc` |

Главное правило чтения: в `strong_count` попадают только сильные ссылки (переменные и `Rc` внутри чужих полей), слабые — никогда; поэтому ссылки в обе стороны есть, а цикла владения нет.

### Г22.Ч2.З3

**Условие.** *(механика)* Воспроизведите «общий журнал» из §22.2.2 и расширьте: третий датчик `hygro` (влажность), функция `clear_log(log: &SharedLog)`, очищающая журнал (метод `clear` — знакомый по `String::clear` из §18.2.3; у `Vec` он такой же — R9), и печать числа записей до и после очистки (`log.borrow().len()`). Убедитесь, что после очистки все три датчика продолжают писать в тот же журнал, и объясните, почему `clear_log` достаточно `&SharedLog` — без `mut`.

**Решение.** Файл `p2/r3_log.rs` — журнал из §22.2.2, третий датчик и очистка:

```rust
type SharedLog = Rc<RefCell<Vec<String>>>; // псевдоним — как typedef в §8.2.3

struct Sensor {
    name: &'static str,
    log: SharedLog,
}

impl Sensor {
    fn measure(&self, value: i32) {
        // Rc прозрачен (точка), RefCell выдаёт пропуск писателя
        self.log.borrow_mut().push(format!("{}: {}", self.name, value));
    }
}

// Очистка журнала: изменяющей ссылки не нужно — изменяемость внутри ячейки.
fn clear_log(log: &SharedLog) {
    log.borrow_mut().clear();
}
```

```rust

    baro.measure(748);
    hygro.measure(55);

    println!("владельцев журнала: {}", Rc::strong_count(&log));
    println!("записей до очистки: {}", log.borrow().len());
    for line in log.borrow().iter() {
        println!("{line}");
    }

    clear_log(&log);
    println!("записей после очистки: {}", log.borrow().len());

    thermo.measure(22);
    baro.measure(750);
    hygro.measure(54);
```

```
записей до очистки: 3
температура: 21
давление: 748
влажность: 55
записей после очистки: 0
записей после новых измерений: 3
температура: 22
давление: 750
влажность: 54
```

Четыре владельца — переменная `log` и по одному `Rc` в каждом из трёх датчиков (в главе владельцев было три: там датчиков два). После очистки журнал пуст, но **тот же самый**: все три датчика продолжили писать в него же, и порядок записей в точности соответствует порядку вызовов. Ячейка не пересоздавалась — `clear` опустошил вектор на месте.

**Почему `clear_log` хватает `&SharedLog`.** Разберём сигнатуру по слоям. `SharedLog` — это `Rc<RefCell<Vec<String>>>`, значит, параметр имеет тип `&Rc<RefCell<Vec<String>>>` — разделяемая ссылка на счётчик ссылок.

1. Изменять сам `Rc` (перенаправлять его на другую аллокацию) функция не собирается — значит, `&mut Rc<...>` ей не нужен. Более того, изменяющая ссылка на `Rc` ничего бы и не дала: сквозь `Rc` не выдают `&mut` на содержимое, у него нет `DerefMut` (E0596, §22.1.4).
2. Право на запись даёт не тип ссылки, а **ячейка**: `RefCell::borrow_mut` принимает `&self` и выдаёт `RefMut<Vec<String>>`, отметив писателя в своём журнале (§22.2.1). Именно поэтому изменяемость и называется «внутренней»: она не проступает наружу в сигнатурах.
3. `clear` — обычный метод `Vec` по `&mut self` (§18.2.3 показывал такой же у `String`; у вектора он тот же — R9). Изменяющую ссылку на вектор ему даёт пропуск `RefMut` через `DerefMut`, а не вызывающий код.

Отсюда общий вывод: `&mut` в сигнатуре означал бы «функция изменяет **переданное значение**» — то есть саму ручку `Rc`; нам же нужно изменить **данные за ячейкой**, и на это разрешение выдаётся в рантайме.

**Дисциплина пропуска — и как её нарушить.** В `main` каждый пропуск живёт ровно одно выражение: `log.borrow().len()` берёт и тут же отдаёт, `for line in log.borrow().iter()` держит пропуск читателя на время цикла и отдаёт на выходе. Стоит взять пропуск «на потом» — и следующая же запись упрётся в занятый журнал. Файл `p2/r3_hold_bad.rs` отличается от рабочего тремя строками:

```rust
    let lines = log.borrow(); // пропуск читателя живёт до конца main
    println!("записей: {}", lines.len());

    clear_log(&log); // ⛔ писатель при живом читателе

    println!("после очистки: {}", lines.len());
```

```
$ ./r3_hold_bad.exe
записей: 1

thread 'main' (16896) panicked at r3_hold_bad.rs:19:9:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Паника указывает на строку 19 — это `log.borrow_mut()` **внутри `clear_log`**, а не строка вызова в `main`. Так и выглядит коварство долгих пропусков: виновник (`let lines = log.borrow();`) остался в другой функции и в отчёте не упомянут вовсе. Лекарство — блок вокруг чтения или `drop(lines)` до вызова.

**Ответ:** третий датчик добавляется одной структурой (`hygro` с `Rc::clone(&log)` в поле), очистка — функцией

```rust
fn clear_log(log: &SharedLog) {
    log.borrow_mut().clear();
}
```

Программа печатает `владельцев журнала: 4` (переменная `log` плюс три датчика), `записей до очистки: 3`, сам журнал, `записей после очистки: 0`, а затем `записей после новых измерений: 3` — после очистки все три датчика продолжают писать в ту же ячейку: `clear` опустошил вектор на месте, ничего не пересоздавая. `clear_log` обходится `&SharedLog`, потому что изменять надо не переданную ручку `Rc`, а данные внутри ячейки; разрешение на запись выдаёт сам `RefCell` в ответ на `borrow_mut(&self)` — изменяемость «спрятана внутрь» и не проступает в сигнатуре (сквозь `Rc` изменяющую ссылку получить всё равно нельзя — у него нет `DerefMut`).

### Г22.Ч2.З4

**Условие.** *(понимание)* Напишите две минимальные программы: (а) паника «RefCell already borrowed»; (б) паника «RefCell already mutably borrowed». Для каждой укажите, какую ошибку компиляции — E0499 или E0502 (§15.2.2) — вы получили бы, замени мы `RefCell` на обычные `&`/`&mut` заимствования той же структуры (можете привести такой ⛔-вариант). Сформулируйте, что именно «переехало» из компиляции в рантайм и какой ценой.

**Решение.** *(а) Два писателя — «already borrowed».* Минимальная программа: ячейка, два пропуска писателя подряд. Файл `p2/r4_borrowed.rs`:

```rust
// Г22.Ч2.З4(а): паника «RefCell already borrowed» — два писателя.
use std::cell::RefCell;

fn main() {
    let cell = RefCell::new(String::from("data"));

    let first = cell.borrow_mut();
    let second = cell.borrow_mut(); // ⛔ второй писатель при живом первом

    println!("{} {}", *first, *second);
}
```

```
$ ./r4_borrowed.exe

thread 'main' (11260) panicked at r4_borrowed.rs:8:23:
RefCell already borrowed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

*(б) Писатель и читатель — «already mutably borrowed».* Меняем второй пропуск на читательский. Файл `p2/r4_mutably.rs`:

```rust
fn main() {
    let cell = RefCell::new(String::from("data"));

    let writer = cell.borrow_mut();
    let reader = cell.borrow(); // ⛔ читатель при живом писателе

    println!("{} {}", *writer, *reader);
}
```

```
$ ./r4_mutably.exe

thread 'main' (22572) panicked at r4_mutably.rs:8:23:
RefCell already mutably borrowed
```

Формулировки различаются одним словом, и это слово — про **того, кто уже держит журнал**: «already borrowed» — ячейка занята (в нашем случае писателем, но так же скажет и про читателей), «already **mutably** borrowed» — занята именно писателем, и потому нельзя даже читать. Обе паники указывают на строку и столбец **второго** пропуска: виновником вахтёр считает того, кто пришёл позже.

*Те же ошибки на обычных заимствованиях.* Заменим ячейку на обычную переменную, а пропуска — на `&mut`/`&`. Файл `p2/r4_e0499_bad.rs`:

```rust
// Г22.Ч2.З4(а): та же ошибка на обычных заимствованиях — ловит компилятор.
fn main() {
    let mut data = String::from("data");

    let first = &mut data;
    let second = &mut data; // ⛔ второй изменяющий заём

    println!("{} {}", first, second);
}
```

```
error[E0499]: cannot borrow `data` as mutable more than once at a time
 --> r4_e0499_bad.rs:6:18
  |
5 |     let first = &mut data;
  |                 --------- first mutable borrow occurs here
6 |     let second = &mut data; // ⛔ второй изменяющий заём
  |                  ^^^^^^^^^ second mutable borrow occurs here
7 |
8 |     println!("{} {}", first, second);
  |                       ----- first borrow later used here
```

Файл `p2/r4_e0502_bad.rs` — зеркальный случай:

```
error[E0502]: cannot borrow `data` as immutable because it is also borrowed as mutable
 --> r4_e0502_bad.rs:6:18
  |
5 |     let writer = &mut data;
  |                  --------- mutable borrow occurs here
6 |     let reader = &data; // ⛔ разделяемый заём при живом изменяющем
  |                  ^^^^^ immutable borrow occurs here
7 |
8 |     println!("{} {}", writer, reader);
  |                       ------ mutable borrow later used here
```

Соответствие получается дословным:

| Ситуация | С `RefCell` (рантайм) | С `&`/`&mut` (компиляция) |
|---|---|---|
| второй писатель | паника `RefCell already borrowed` | **E0499** `cannot borrow ... as mutable more than once at a time` |
| читатель при писателе | паника `RefCell already mutably borrowed` | **E0502** `cannot borrow ... as immutable because it is also borrowed as mutable` |

Обратите внимание на деталь, которая делает соответствие полным: обе версии ссылаются на **одну и ту же строку** — ту, где взят второй доступ; и обе объясняют, что первый доступ ещё жив («first borrow later used here» у компилятора, «уже занято» у ячейки).

*Что переехало и какой ценой.* Переехала **проверка**, а не правило. Правило §15.2.2 — «читатели XOR писатель» — осталось дословно: `RefCell` не разрешает ничего, чего не разрешал бы borrow checker. Изменилось время: компилятор доказывает свойство для всех путей исполнения ещё до запуска, а ячейка судит фактическое положение дел в момент вызова `borrow`/`borrow_mut`, считая живые пропуска.

Цена состоит из трёх частей.

1. **Ошибка после запуска, а не до.** Пути, по которым программа в тестах не пошла, останутся непроверенными; в C-версии этой истории (§7.1.2) непроверенным оставалось вообще всё, но здесь мы добровольно отказываемся от гарантии, которая у нас уже была.
2. **Паника вместо диагностики.** Компилятор показывает обе конфликтующие строки и объясняет связь; паника называет только вторую — искать первую (иногда в другой функции, как в З3) приходится глазами. Есть `try_borrow`/`try_borrow_mut` с `Result` (R9), но их появление в коде — сигнал, что архитектуру стоит пересмотреть.
3. **Расход на бегу.** Каждый `borrow`/`borrow_mut` — это проверка и обновление счётчика заимствований, а каждый `Ref`/`RefMut` — значение с деструктором, который счётчик возвращает. У обычных ссылок стоимость нулевая: они существуют только в голове компилятора.

Взамен получаем то, ради чего всё затевалось: возможность изменять данные там, где статический анализ слишком строг, — сквозь `&self` (мок-объекты, кеши, счётчики) и сквозь `Rc`, который `&mut` не выдаёт в принципе (§22.1.4).

**Ответ:** (а) паника `RefCell already borrowed` — два `borrow_mut()` подряд; (б) паника `RefCell already mutably borrowed` — `borrow()` при живом `borrow_mut()`. Обе указывают на строку **второго** пропуска. На обычных заимствованиях те же две ситуации ловит компилятор: первая — **E0499** «cannot borrow `data` as mutable more than once at a time», вторая — **E0502** «cannot borrow `data` as immutable because it is also borrowed as mutable». Из компиляции в рантайм переехало не само правило, а его проверка: `RefCell` соблюдает §15.2.2 дословно, но считает живые пропуска на бегу. Цена — ошибка обнаруживается после запуска и только на пройденном пути, диагностика беднее (названа лишь вторая точка конфликта, первая ищется вручную), плюс расход на счётчик и деструкторы пропусков; выигрыш — изменяемость там, где статический анализ доказуемо слишком строг.

### Г22.Ч2.З5

**Условие.** *(понимание)* Программа из §22.2.2 (пример 3) паникует: два `borrow_mut` через два клона `Rc`. (а) Объясните, почему «разные переменные» не означают «разные журналы». (б) Почините программу двумя способами: последовательные блоки (писатели по очереди) и один общий пропуск на всю работу. (в) Ответьте: изменилось бы что-нибудь, будь второй ручкой не `Rc::clone`, а *новый* `Rc::new(RefCell::new(...))` с теми же числами? Что это говорит о разнице «разделять значение» и «иметь равное значение» (§15.1.3)?

**Решение.** Исходная программа — файл `p2/r5_panic.rs`, листинг §22.2.2 дословно:

```rust
fn main() {
    let c1 = Rc::new(RefCell::new(vec![1, 2]));
    let c2 = Rc::clone(&c1);

    let first = c1.borrow_mut(); // писатель через первую ручку
    let second = c2.borrow_mut(); // и «другая» ручка — та же ячейка!

    println!("{:?} {:?}", *first, *second);
}
```

```
$ ./r5_panic.exe

thread 'main' (22828) panicked at r5_panic.rs:10:21:
RefCell already borrowed
```

*(а) Почему «разные переменные» ≠ «разные журналы».* Разберём, что именно создаёт `Rc::clone`. Он не копирует ни `RefCell`, ни вектор внутри — он копирует **указатель** на аллокацию и увеличивает счётчик владельцев (§22.1.4). В куче остаётся один блок, и в нём — одна ячейка с одним журналом заимствований. Схема (не вывод программы):

```
     c1 ──┐
          ├──▶ [Rc: strong = 2 | RefCell{ журнал: читателей 0, писатель нет } | Vec[1, 2] ]
     c2 ──┘
```

Переменные `c1` и `c2` — две **ручки** одного объекта, вроде двух ключей от одной двери. Журнал живёт при данных, а не при ручке, поэтому `c2.borrow_mut()` спрашивает разрешения у того же вахтёра, что и `c1.borrow_mut()` мгновением раньше, — и получает отказ. Мысленная модель «у меня своя копия» ошибочна ровно в той же мере, в какой она была бы ошибочна в C для двух указателей на один `malloc`-блок (§7.1.2): имён два, объект один.

*(б) Две починки.* Первая — писатели по очереди, каждый в своём блоке. Файл `p2/r5_blocks.rs`:

```rust
    {
        let mut first = c1.borrow_mut();
        first.push(3);
    } // пропуск сдан

    {
        let mut second = c2.borrow_mut();
        second.push(4);
    } // и этот сдан

    println!("{:?}", c1.borrow());
    println!("{:?}", c2.borrow());
```

```
$ ./r5_blocks.exe
[1, 2, 3, 4]
[1, 2, 3, 4]
```

Вторая — один пропуск на всю работу. Файл `p2/r5_one.rs`:

```rust
    {
        let mut cell = c1.borrow_mut(); // единственный писатель
        cell.push(3);
        cell.push(4);
    }

    println!("{:?}", c1.borrow());
    println!("{:?}", c2.borrow()); // вторая ручка видит обе записи
```

```
$ ./r5_one.exe
[1, 2, 3, 4]
[1, 2, 3, 4]
```

Результат одинаковый — `[1, 2, 3, 4]` через обе ручки, и это само по себе ответ на вопрос «одна ли ячейка»: запись через `c1` видна через `c2`. Разница между починками — в намерении. Блоки говорят «две независимые операции, каждая берёт доступ на минимальное время»: между ними ячейка свободна, и её может занять кто-то ещё (в однопоточной программе — вызванная функция). Единственный пропуск говорит «одна неделимая операция»: пока она идёт, никто не вмешается, но и вызывать чужой код внутри такого блока опасно — если он попробует взять пропуск, будет паника (та самая «через два кадра стека» из §22.2.2). Правило выбора: берите пропуск на минимальный участок, кроме случаев, когда несколько изменений обязаны быть атомарными.

*(в) Если бы вторая ручка была новой ячейкой.* Заменим `Rc::clone(&c1)` на самостоятельный `Rc::new(RefCell::new(vec![1, 2]))` — с теми же числами. Файл `p2/r5_separate.rs`:

```rust
fn main() {
    let c1 = Rc::new(RefCell::new(vec![1, 2]));
    let c2 = Rc::new(RefCell::new(vec![1, 2])); // не клон — новая ячейка

    let mut first = c1.borrow_mut();
    let mut second = c2.borrow_mut(); // паники нет: журналы разные

    first.push(3);
    second.push(4);

    println!("c1 = {:?}", *first);
    println!("c2 = {:?}", *second);
    println!("same cell: {}", Rc::ptr_eq(&c1, &c2));
}
```

```
$ ./r5_separate.exe
c1 = [1, 2, 3]
c2 = [1, 2, 4]
same cell: false
```

Изменилось всё: паники нет (два журнала — два независимых вахтёра), а данные разъехались — каждая ячейка получила свою запись. `Rc::ptr_eq` (R9) подтверждает диагноз формально: указатели на аллокации разные.

Это и есть разница между **разделять значение** и **иметь равное значение** (§15.1.3). Равенство — свойство содержимого в момент сравнения: две ячейки со списком `[1, 2]` равны, но связи между ними нет, и первая же запись их разводит. Разделение — свойство идентичности: один объект, к которому ведут несколько путей; запись по любому пути видна по всем остальным. `clone` у обычных типов (`Vec`, `String`) даёт равенство — глубокую копию; `Rc::clone` даёт разделение — ещё одну ручку. Одно слово `clone`, два принципиально разных смысла — потому конвенция §22.1.4 и требует писать `Rc::clone(&x)` явно.

**Ответ:** (а) `Rc::clone` копирует ручку, а не данные: ячейка в куче одна, журнал заимствований у неё один, поэтому `c2.borrow_mut()` при живом `c1.borrow_mut()` — это те же два `&mut` на одни данные, и вахтёр отвечает паникой `RefCell already borrowed`. (б) Починка 1 — писатели по очереди, каждый в своём блоке (`push(3)`, затем `push(4)`); починка 2 — один пропуск на обе записи. Обе печатают `[1, 2, 3, 4]` через обе ручки; блоки уместны для независимых операций, единый пропуск — когда изменения обязаны быть атомарными. (в) С двумя самостоятельными `Rc::new(RefCell::new(...))` паники нет — журналы разные, — но и разделения нет: `c1 = [1, 2, 3]`, `c2 = [1, 2, 4]`, `Rc::ptr_eq` → `false`. «Иметь равное значение» — свойство содержимого, которое исчезает при первой же записи; «разделять значение» — свойство идентичности: один объект, много путей к нему.

### Г22.Ч2.З6

**Условие.** *(понимание)* Заполните таблицу для четырёх инструментов — `&mut T`, `RefCell<T>`, `Rc<T>`, `Rc<RefCell<T>>` — по строкам: «сколько владельцев», «возможна ли запись», «когда проверяются правила заимствования», «что происходит при нарушении», «работает ли между потоками». Каждую клетку обоснуйте ссылкой на параграф курса (§15.2.2, §22.1.4, §22.2.1, §22.2.2; для потоков — анонс главы 23). Приведите по одному примеру задачи, для которой каждый инструмент — правильный выбор.

**Решение.** Таблица собирается из четырёх параграфов курса; каждую клетку сопровождаем ссылкой на то место, где утверждение доказано.

| | `&mut T` | `RefCell<T>` | `Rc<T>` | `Rc<RefCell<T>>` |
|---|---|---|---|---|
| **Сколько владельцев** | один — заимствование владения не даёт вовсе (§15.2.1) | один (§22.2.1) | много: `Rc::clone` — +1 к счётчику (§22.1.4) | много (§22.2.2) |
| **Возможна ли запись** | да, исключительная (§15.2.2) | да, по пропуску `borrow_mut` — в том числе сквозь `&self` (§22.2.1) | **нет**: у `Rc` нет `DerefMut` (§22.1.4) | да, по пропуску (§22.2.2) |
| **Когда проверяются правила** | компиляция (§15.2.2) | **рантайм**, счётчиком заимствований (§22.2.1) | компиляция (§22.1.4) | владение — компиляция, заимствование — рантайм (§22.2.2) |
| **Что при нарушении** | не компилируется: E0499/E0502 (§15.2.2) | **паника** `RefCell already borrowed` / `already mutably borrowed` (§22.2.1) | не компилируется: E0596 при попытке записи (§22.1.4) | паника, в том числе через две ручки (§22.2.2) |
| **Между потоками** | да, если само `T` это допускает — но передача ссылки в поток обсуждается в главе 23 | **нет**: `RefCell` однопоточен, замена — `Mutex` (§22.2.1, анонс главы 23) | **нет**: счётчик не атомарен, замена — `Arc` (§22.1.4, анонс главы 23) | **нет**: не годится ни один слой; замена — `Arc<Mutex<T>>` (§22.2.2, анонс главы 23) |

Последняя строка — единственная, которую в этой главе нельзя проверить запуском: `thread::spawn` появится только в главе 23, там же компилятор и покажет отказ вместе с заменой. Мы приводим её по анонсам §22.1.4 и §22.2.1—22.2.2 и помечаем как обещание, а не как проверенный опыт.

Четыре задачи — по одной на инструмент; все четыре собраны в файле `p2/r6_four.rs`.

**1. `&mut T` — «посчитать в одном месте».** Счётчик, который изменяет одна функция, вызванная из одного места:

```rust
// 1. &mut T: один владелец, запись, правила проверены при компиляции.
fn bump(counter: &mut u32) {
    *counter += 1;
}
```

Владелец один, заимствование живёт ровно на время вызова, всё проверено до запуска, накладных расходов ноль. Это выбор по умолчанию: любая другая строка таблицы — отступление, которое надо обосновать.

**2. `RefCell<T>` — «служебный учёт при логически неизменяющей операции».** Кеш, считающий обращения; сигнатура `get(&self)` честно говорит «чтение», а счётчик всё же растёт:

```rust
// 2. RefCell<T>: один владелец, но запись нужна сквозь &self.
struct Cache {
    hits: RefCell<u32>,
}

impl Cache {
    fn get(&self, key: &str) -> String {
        *self.hits.borrow_mut() += 1; // служебный учёт при «чтении»
        format!("value for {key}")
    }

    fn hits(&self) -> u32 {
        *self.hits.borrow()
    }
}
```

Взять здесь `&mut self` значило бы: любой держатель `&Cache` не может даже читать, а два одновременных `get` невозможны — контракт исказился бы ради детали реализации. Сюда же относится тестовый двойник из З8: трейт задаёт `log(&self)`, а копилка сообщений обязана расти.

**3. `Rc<T>` — «общая неизменяемая конфигурация».** Несколько подсистем владеют одним конфигом, и заранее не известно, какая закончит работу последней:

```rust
// 3. Rc<T>: много владельцев, только чтение.
struct Config {
    lang: String,
}

struct Subsystem {
    name: &'static str,
    config: Rc<Config>,
}
```

Запись не нужна ни одной подсистеме — и хорошо: `Rc` её и не даст (E0596). Зато каждая подсистема самостоятельна: её можно вернуть из фабрики, положить в коллекцию, уничтожить в любом порядке (см. З10 части 22.1).

**4. `Rc<RefCell<T>>` — «общий изменяемый итог».** Несколько объектов пишут в одно место:

```rust
// 4. Rc<RefCell<T>>: много владельцев, и каждый пишет.
type SharedTotal = Rc<RefCell<i32>>;

struct Adder {
    total: SharedTotal,
}

impl Adder {
    fn add(&self, value: i32) {
        *self.total.borrow_mut() += value;
    }
}
```

```
$ rustc --edition 2024 r6_four.rs
$ ./r6_four.exe
1. &mut T:          counter = 2
2. RefCell<T>:      hits = 2
3. Rc<T>:           parser uses lang ru
3. Rc<T>:           reporter uses lang ru
3. Rc<T>:           owners = 3
4. Rc<RefCell<T>>:  total = 42
```

Все четыре работают, и вывод подтверждает разное: счётчик дошёл до 2 через изменяющую ссылку; кеш насчитал два обращения сквозь `&self`; конфигом владеют трое (переменная и две подсистемы) и обе видят один и тот же `lang`; общий итог собрал вклады двух объектов — `2 + 40 = 42`.

**Ответ:** таблица приведена выше; ключ к ней — два независимых вопроса. Первый: **сколько владельцев** — один (`&mut T`, `RefCell<T>`) или много (`Rc<T>`, `Rc<RefCell<T>>`); за «много» платят счётчиком и аллокацией. Второй: **когда проверяются правила заимствования** — при компиляции (`&mut T`, `Rc<T>`: ошибка E0499/E0502/E0596 до запуска, стоимость ноль) или в рантайме (`RefCell<T>`, `Rc<RefCell<T>>`: паника `RefCell already borrowed` и расход на журнал). Между потоками не работает ни `Rc`, ни `RefCell` (замены — `Arc` и `Mutex`, глава 23). Задачи: `&mut T` — счётчик, изменяемый одной функцией; `RefCell<T>` — учёт обращений внутри метода с сигнатурой `&self` (и тестовые двойники); `Rc<T>` — разделяемая неизменяемая конфигурация; `Rc<RefCell<T>>` — общий журнал или итог, в который пишут несколько объектов. Порядок выбора — сверху вниз по этому списку: каждый следующий инструмент отдаёт часть гарантий, поэтому берётся, только когда предыдущий доказуемо не подходит.

### Г22.Ч2.З7

**Условие.** *(понимание)* Для программы «цикл» из §22.2.3 (пример 1, версия с замкнутым кругом): (а) составьте таблицу `strong_count` обоих узлов в пяти точках: после создания `a`, после создания `b`, после замыкания цикла, после смерти переменной `b`, после смерти переменной `a`; (б) объясните, почему деструкторы не вызваны и почему это утечка, но не UB (§13.1.2, §13.2.3); (в) предложите **два** исправления: перевод одной из ссылок на `Weak` и ручное размыкание цикла последней строкой `main` (`*a.next.borrow_mut() = None;`) — реализуйте второе и покажите, что оба `drop:` вернулись в вывод; объясните, почему порядок строк `drop:` именно такой.

**Решение.** *(а) Счётчики в пяти точках.* Программа главы печатает счётчики только в одной точке и ничего не может сказать о том, что происходит после смерти переменных, — а именно там и прячется утечка. Приём: завести **слабых наблюдателей**. `Weak` не влияет на `strong_count`, зато у него есть метод `strong_count()` (R9), и жить он может дольше самих переменных. Файл `p2/r7_counts.rs`:

```rust
fn main() {
    // слабые наблюдатели: видят счётчики, но никого не держат
    let wa: Weak<Node>;
    let wb: Weak<Node>;

    {
        let a = Rc::new(Node {
            name: "a",
            next: RefCell::new(None),
        });
        wa = Rc::downgrade(&a);
        println!("1. создан a:        a = {}", Rc::strong_count(&a));

        {
            let b = Rc::new(Node {
                name: "b",
                next: RefCell::new(Some(Rc::clone(&a))),
            });
            wb = Rc::downgrade(&b);
            println!(
                "2. создан b:        a = {}, b = {}",
                Rc::strong_count(&a),
                Rc::strong_count(&b)
            );

            *a.next.borrow_mut() = Some(Rc::clone(&b));
            println!(
                "3. цикл замкнут:    a = {}, b = {}",
                Rc::strong_count(&a),
                Rc::strong_count(&b)
            );
        } // умирает переменная b
```

```
$ rustc --edition 2024 r7_counts.rs
$ ./r7_counts.exe
1. создан a:        a = 1
2. создан b:        a = 2, b = 1
3. цикл замкнут:    a = 2, b = 2
4. умерла перем. b: a = 2, b = 1
5. умерла перем. a: a = 1, b = 1
конец main
```

Таблица с расшифровкой каждой цифры:

| Точка | `a` | кто держит `a` | `b` | кто держит `b` |
|---|---|---|---|---|
| 1. создан `a` | 1 | переменная `a` | — | узла ещё нет |
| 2. создан `b` | 2 | переменная `a` + поле `b.next` | 1 | переменная `b` |
| 3. цикл замкнут | 2 | переменная `a` + поле `b.next` | 2 | переменная `b` + поле `a.next` |
| 4. умерла переменная `b` | 2 | переменная `a` + поле `b.next` | 1 | **поле `a.next`** |
| 5. умерла переменная `a` | 1 | **поле `b.next`** | 1 | поле `a.next` |

И ни одной строки `drop:` в выводе — при том, что `Node` имеет `impl Drop`, который печатает своё имя.

*(б) Почему деструкторы не вызваны и почему это не UB.* `Rc` вызывает деструктор значения ровно тогда, когда его `strong_count` доходит до нуля. В точке 5 оба счётчика равны единице: `a` держится полем `b.next`, `b` — полем `a.next`. Уменьшить их больше некому: единственные, кто мог бы отпустить эти поля, — сами узлы, а они умрут только после уменьшения счётчиков. Замкнутый круг ожидания: каждый ждёт смерти другого.

Что получилось в итоге: два объекта в куче, до которых **невозможно добраться** (все внешние имена умерли) и которые **не будут освобождены** до конца процесса. Это классическая утечка — ровно то, что в §7.2.1 находил Valgrind в C-программах, забывших `free`.

Почему это не UB (§13.1.2, §13.2.3): неопределённое поведение — это когда программа делает то, у чего нет смысла по правилам языка: читает освобождённую память, разыменовывает висячий указатель, освобождает дважды. Здесь ничего подобного нет — наоборот, память **слишком жива**: все ссылки указывают на существующие, корректно инициализированные объекты; любое обращение к ним (если бы мы могли добраться) вернуло бы правильные данные. Утекший объект не нарушает ни одного инварианта — он просто никому не нужен и не освобождён. Поэтому гарантии Rust целы: «безопасность памяти» означает отсутствие UB, а не отсутствие утечек, и глава 15.6 R1 говорит об этом прямо. Практическое следствие из §22.2.3: компилятор о цикле не предупредит — это семантика вашей модели данных, а не свойство синтаксиса.

*(в) Два исправления.* Первое — **перевести обратную ссылку на `Weak`** (разобрано ниже как вариант 2): цикла владения не возникает вовсе, потому что «знать» перестаёт означать «владеть». Второе — **разомкнуть круг руками** перед выходом: если владение циклическое по природе задачи, кто-то должен обнулить одну из ссылок. Реализуем второе — файл `p2/r7_break.rs`:

```rust
    println!("a: strong = {}", Rc::strong_count(&a));
    println!("b: strong = {}", Rc::strong_count(&b));

    *a.next.borrow_mut() = None; // размыкаем круг
    println!("после размыкания: a = {}, b = {}", Rc::strong_count(&a), Rc::strong_count(&b));
    println!("конец main");
}
```

```
$ ./r7_break.exe
a: strong = 2
b: strong = 2
после размыкания: a = 2, b = 1
конец main
drop: b
drop: a
```

Обе строки `drop:` вернулись. Разбор по шагам:

1. `*a.next.borrow_mut() = None;` — присваивание уничтожает прежнее содержимое поля, то есть `Rc`, указывавший на `b`. Счётчик `b` падает с 2 до 1 (остаётся переменная `b`), счётчик `a` не меняется — его держат переменная `a` и поле `b.next`. Это видно в строке `после размыкания: a = 2, b = 1`.
2. Закрывающая скобка `main`. Переменные уничтожаются в порядке, обратном объявлению (§22.1.2), значит первой умирает `b`: её счётчик 1 → 0, значение уничтожается, печатается `drop: b`.
3. Уничтожение `b` уничтожает и его поля, в том числе `next: RefCell<Option<Rc<Node>>>` со ссылкой на `a`. Счётчик `a` падает с 2 до 1.
4. Умирает переменная `a`: 1 → 0, печатается `drop: a`.

Порядок `drop: b`, затем `drop: a` определяется, таким образом, двумя правилами сразу: обратным порядком объявления переменных (кто умрёт первым) и каскадом «уничтожение владельца отпускает то, чем он владел» (кто умрёт следом). Если бы мы разомкнули другую ссылку (`*b.next.borrow_mut() = None;`), порядок остался бы тем же — `b` всё равно умирает первой, — но каскада не случилось бы: `a` дожила бы до собственной строки объявления самостоятельно.

**Ответ:** (а) счётчики: после создания `a` — `a = 1`; после создания `b` — `a = 2, b = 1`; после замыкания цикла — `a = 2, b = 2`; после смерти переменной `b` — `a = 2, b = 1`; после смерти переменной `a` — `a = 1, b = 1` (держат друг друга полями `next`). Строк `drop:` в выводе нет. (б) Деструкторы не вызваны, потому что ни один счётчик не дошёл до нуля: каждый узел удерживается полем другого, и отпустить это поле мог бы только сам узел после своей смерти. Это утечка — объекты недостижимы и не освобождены, — но не UB: висячих ссылок нет, чтения освобождённой памяти нет, все инварианты целы; гарантии Rust покрывают UB, а не утечки (§13.2.3). (в) Исправление 1 — сделать обратную ссылку слабой (`Weak`), тогда цикла владения не возникает. Исправление 2 — разомкнуть круг явно: `*a.next.borrow_mut() = None;` перед выходом; после него счётчики становятся `a = 2, b = 1`, и в выводе появляются обе строки — сначала `drop: b`, затем `drop: a`. Порядок такой, потому что переменные умирают в обратном порядке объявления (`b` объявлена позже), а смерть `b` каскадом отпускает `a`, чей счётчик после этого доходит до нуля.

**Вариант 2 (слабая ссылка вместо ручного размыкания).** Ручное размыкание лечит симптом: о нём нужно помнить, его легко забыть при раннем `return` или панике, и оно не работает, если циклов много и они собираются динамически. Лекарство по существу — назначить **направление владения** (§22.2.3): вперёд владеем (`Rc`), назад только знаем (`Weak`). Файл `p2/r7_weak.rs`:

```rust
struct Node {
    name: &'static str,
    next: RefCell<Option<Rc<Node>>>, // вперёд — владеем
    back: RefCell<Weak<Node>>,       // назад — только знаем
}
```

```rust
    *a.back.borrow_mut() = Rc::downgrade(&b); // a знает b, но не владеет

    if let Some(node) = &*b.next.borrow() {
        println!("b владеет {}", node.name);
    }

    match a.back.borrow().upgrade() {
        Some(node) => println!("a знает про {}", node.name),
        None => println!("a никого не знает"),
    }
```

```
$ ./r7_weak.exe
b владеет a
a знает про b
a: strong = 2, weak = 0
b: strong = 1, weak = 1
конец main
drop: b
drop: a
```

Ссылки идут в обе стороны — `b` видит `a`, `a` видит `b`, — а счётчики показывают, что круга нет: у `b` всего один сильный владелец (переменная), потому что ссылка из `a.back` слабая и учтена отдельно (`weak = 1`). На выходе из `main` умирает `b` (1 → 0), затем каскадом `a`; обе строки `drop:` на месте, и ни одной строки уборки писать не пришлось.

*Сравнение.* Ручное размыкание не меняет типы: обе связи остаются сильными, и это честно, если по смыслу задачи оба объекта действительно владеют друг другом (скажем, узлы двусвязного списка, живущие и умирающие вместе). Зато корректность держится на дисциплине программиста: забыли строку — получили утечку, которую компилятор не заметит; при нескольких циклах строк уборки становится столько же, сколько связей, и это уже `free`-дисциплина тома I (§7.1.2) в новых декорациях. `Weak` переносит решение в **тип**: обратная ссылка синтаксически не может удержать объект в живых, забыть нечего, и вдобавок появляется честный ответ на вопрос «а жив ли тот, на кого я смотрю» — `upgrade()` возвращает `Option`. Цена — обращение через `upgrade` вместо прямого доступа и необходимость заранее решить, кто кем владеет. Правило §22.2.3: если направление владения определяется — `Weak`; если нет — это сигнал пересмотреть модель данных, а ручное размыкание оставить на случай, когда цикл создаётся заведомо временно и разрывается тут же.

### Г22.Ч2.З8

**Условие.** *(прикладное)* Тестовый двойник. В cargo-пакете: трейт `Logger` с методом `log(&self, message: &str)`; «боевая» реализация `ConsoleLogger` (печатает); функция `run_job(logger: &impl Logger, items: &[i32]) -> i32` — логирует «старт», суммирует, логирует «обработано элементов: N», возвращает сумму. В тестовом модуле — двойник `MockLogger` с полем `messages: RefCell<Vec<String>>`, копящий сообщения сквозь `&self`. Тесты: сумма верна; журнал содержит ровно два сообщения с точными текстами; пустой срез — сумма 0, но оба сообщения на месте. Все зелёные; приведите строку `test result`.

**Решение.** Пакет-библиотека; трейт, боевая реализация и сама работа — файл `p2/joblog/src/lib.rs`:

```rust
// Библиотека joblog: работа с журналом через трейт и тестовый двойник (Г22.Ч2.З8).

/// Куда работа докладывает о своём ходе.
pub trait Logger {
    fn log(&self, message: &str);
}

/// Боевая реализация: печатает в стандартный вывод.
pub struct ConsoleLogger;

impl Logger for ConsoleLogger {
    fn log(&self, message: &str) {
        println!("{message}");
    }
}

/// Суммирует элементы, докладывая о начале и конце работы.
pub fn run_job(logger: &impl Logger, items: &[i32]) -> i32 {
    logger.log("start");
    let sum: i32 = items.iter().sum();
    logger.log(&format!("processed items: {}", items.len()));
    sum
}
```

Ключевая деталь всего задания — сигнатура `fn log(&self, message: &str)`. Метод объявлен по **разделяемой** ссылке, потому что для боевой реализации это чистая правда: печать ничего не меняет в самом логгере. Но двойник обязан **копить** сообщения, то есть изменять себя, — и вот здесь `&self` из удобства превращается в препятствие, которое снимает внутренняя изменяемость:

Четыре решения, принятые по дороге.

**Почему `&self`, а не `&mut self` в трейте.** Соблазн велик: объявить `fn log(&mut self, ...)` — и двойник копит сообщения без всякого `RefCell`. Но тогда изменяющий доступ потребуется **всем** реализациям и **всем** держателям логгера: `run_job` пришлось бы принимать `&mut impl Logger`, а значит, никакой другой код не смог бы одновременно держать даже разделяемую ссылку на тот же логгер (§15.2.2). Деталь реализации одного двойника продиктовала бы контракт всей системы. С `&self` контракт честен («логгер только сообщают»), а `RefCell` локализует изменяемость там, где она действительно нужна, — в одном поле одного типа (R1: типовой сценарий mock-объектов).

**Почему `&impl Logger`, а не `&dyn Logger`.** Оба варианта работают, и это ровно тот выбор, который разбирался в З7 части 22.1. Здесь `run_job` в каждом вызове имеет дело с **одним** логгером известного типа, так что дженерик (`&impl Logger` — сокращённая запись, §19.2.2) даёт статическую диспетчеризацию бесплатно. `&dyn Logger` понадобился бы, если бы логгер выбирался в рантайме или хранился в коллекции разнородных.

**Почему пропуск в тесте берётся в переменную.** `let messages = logger.messages.borrow();` — здесь долгий пропуск читателя уместен: после `run_job` никто больше не пишет, а три `assert_eq!` подряд читают один и тот же снимок. Если бы понадобилось вызвать `run_job` ещё раз — пропуск пришлось бы сдать (блоком или `drop`), иначе паника, как в Г22.Ч2.З3.

**Почему тест на пустой срез проверяет не только сумму.** Условие требует «сумма 0, но оба сообщения на месте» — и это содержательное требование: реализация с ранним выходом (`if items.is_empty() { return 0; }`) прошла бы проверку суммы и провалила проверку журнала. Тест фиксирует контракт «работа всегда докладывает о себе», а не только арифметику; заодно проверяется, что счётчик в сообщении берётся из `items.len()`, а не из числа слагаемых.

**Ответ:** трейт `Logger` с единственным методом `fn log(&self, message: &str)`; `ConsoleLogger` печатает, `run_job(logger: &impl Logger, items: &[i32]) -> i32` докладывает «start», суммирует срез и докладывает `processed items: N`. Тестовый двойник копит сообщения сквозь `&self`, и это возможно только благодаря внутренней изменяемости:

```rust
    impl Logger for MockLogger {
        fn log(&self, message: &str) {
            self.messages.borrow_mut().push(String::from(message));
        }
    }
```

Три теста — сумма `1+2+3+4 = 10`; ровно два сообщения с точными текстами `start` и `processed items: 4`; пустой срез даёт сумму 0 и те же два сообщения (второе — `processed items: 0`):

### Г22.Ч2.З9

**Условие.** *(прикладное)* Дерево как библиотека. Оформите узел из §22.2.3 cargo-пакетом: `new_node(value) -> Rc<Node>`, `add_child(parent: &Rc<Node>, child: &Rc<Node>)` (двусторонняя связка: children — `Rc`, parent — `Weak`), `parent_value(node: &Node) -> Option<i32>`. Тесты: ребёнок видит родителя (и родитель — ребёнка); счётчики после связывания (`leaf`: strong 2/weak 0; `root`: strong 1/weak 1); после смерти родителя `parent_value` даёт `None`, а strong ребёнка возвращается к 1; после `drop` *нашей* ручки ребёнка узел жив внутри дерева (доступен через `children` корня), и strong корня остался 1 — цикла нет. Все зелёные; приведите строку `test result`.

**Решение.** Узел, три функции и одна вспомогательная — файл `p2/treelib/src/lib.rs`:

```rust
// Библиотека treelib: узел дерева, знающий родителя (Г22.Ч2.З9).
use std::cell::RefCell;
use std::rc::{Rc, Weak};

/// Направление владения: вниз — Rc (родитель владеет детьми),
/// вверх — Weak (ребёнок знает родителя, но не держит его в живых).
pub struct Node {
    pub value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

/// Одинокий узел: родителя нет, детей нет.
pub fn new_node(value: i32) -> Rc<Node> {
    Rc::new(Node {
        value,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(Vec::new()),
    })
}

/// Связывает узлы в обе стороны: вниз сильно, вверх слабо.
pub fn add_child(parent: &Rc<Node>, child: &Rc<Node>) {
    parent.children.borrow_mut().push(Rc::clone(child));
    *child.parent.borrow_mut() = Rc::downgrade(parent);
}

/// Значение родителя, если родитель ещё жив.
pub fn parent_value(node: &Node) -> Option<i32> {
    node.parent.borrow().upgrade().map(|p| p.value)
}

/// Значения детей узла — по порядку добавления.
pub fn child_values(node: &Node) -> Vec<i32> {
    node.children.borrow().iter().map(|c| c.value).collect()
}
```

Разбор типов полей — каждый слой отвечает за своё (§22.2.2):

- `children: RefCell<Vec<Rc<Node>>>` — вектор детей: `Rc`, потому что родитель ими **владеет**; `RefCell`, потому что детей добавляют уже после создания узла, а `add_child` получает родителя по разделяемой ссылке `&Rc<Node>`.
- `parent: RefCell<Weak<Node>>` — ссылка вверх: `Weak`, потому что ребёнок родителем **не владеет** (иначе цикл, см. ниже); `RefCell`, потому что в момент создания узла родителя ещё нет — там стоит `Weak::new()`, а связь появляется позже.
- Почему `add_child` принимает `&Rc<Node>`, а не `&Node`: обеим сторонам нужны именно счётчики — `Rc::clone(child)` для вектора детей и `Rc::downgrade(parent)` для слабой ссылки; из голого `&Node` ни того, ни другого не сделать.

### Г22.Ч2.З10

**Условие.** *(прикладное)* Отдел и сотрудники. Спроектируйте пару типов со взаимными ссылками без утечки: `Department { name, staff: RefCell<Vec<Rc<Employee>>> }` и `Employee { name, dept: RefCell<Weak<Department>> }`; функции `new_department(name) -> Rc<Department>`, `hire(dept: &Rc<Department>, name: &str) -> Rc<Employee>` (связывает в обе стороны), `department_of(employee: &Employee) -> Option<String>`. Тесты: наём двоих — список отдела и обе обратные ссылки верны; после расформирования отдела (`drop` последней сильной ссылки) `department_of` даёт `None`, strong уцелевшего сотрудника — 1; счётчики подтверждают отсутствие цикла (у отдела strong 1/weak по числу сотрудников). Все зелёные; приведите строку `test result`. В комментарии к типам укажите направление владения и объясните выбор.

**Решение.** Направление владения выбираем первым делом, до всякого кода: **отдел владеет сотрудниками**. Обоснование — вопрос «кто без кого не имеет смысла»: список штата — часть отдела и умирает вместе с ним, а сотрудник, чей отдел расформирован, остаётся сотрудником (условие прямо требует, чтобы он пережил отдел). Значит, вниз — `Rc`, вверх — `Weak`; эти два предложения и записаны в комментариях к типам. Файл `p2/orgchart/src/lib.rs`:

```rust
// Библиотека orgchart: отдел и сотрудники без утечки (Г22.Ч2.З10).
use std::cell::RefCell;
use std::rc::{Rc, Weak};

/// Отдел ВЛАДЕЕТ сотрудниками: список штата живёт ровно столько же, сколько отдел.
pub struct Department {
    pub name: String,
    staff: RefCell<Vec<Rc<Employee>>>,
}

/// Сотрудник ЗНАЕТ свой отдел, но не владеет им: сильная ссылка вверх
/// замкнула бы круг «отдел -> сотрудник -> отдел» и дала утечку (§22.2.3).
pub struct Employee {
    pub name: String,
    dept: RefCell<Weak<Department>>,
}
```

Дальше — наём, обратный вопрос и список штата (`new_department` просто создаёт отдел с пустым `RefCell::new(Vec::new())` и отдельного разбора не требует):

```rust
/// Нанимает сотрудника и связывает его с отделом в обе стороны.
pub fn hire(dept: &Rc<Department>, name: &str) -> Rc<Employee> {
    let employee = Rc::new(Employee {
        name: String::from(name),
        dept: RefCell::new(Rc::downgrade(dept)),
    });
    dept.staff.borrow_mut().push(Rc::clone(&employee));
    employee
}

/// Название отдела, если отдел ещё существует.
pub fn department_of(employee: &Employee) -> Option<String> {
    employee.dept.borrow().upgrade().map(|d| d.name.clone())
}

/// Имена сотрудников отдела — по порядку найма.
pub fn staff_names(dept: &Department) -> Vec<String> {
    dept.staff.borrow().iter().map(|e| e.name.clone()).collect()
}
```

`hire` возвращает `Rc<Employee>` — сильную ручку для вызывающего, — и одновременно кладёт ещё одну в штат отдела: сотрудник существует в двух ролях, «мой» и «в списке», и это отражено в счётчике. `department_of` возвращает `Option<String>`, а не `Option<&str>`: строка принадлежит отделу, который к моменту возврата может быть уже уничтожен, поэтому имя копируется (`clone`) — ссылку наружу отдавать не на что.

Три теста:


**Вариант 2 (связь ставится в конструкторе — без `RefCell` у сотрудника).** В основном решении `RefCell` вокруг `Weak` нужен ради одной возможности — **менять** отдел сотрудника после найма. Но `hire` знает отдел уже в момент создания `Employee`, и если переводы между отделами в задачу не входят, ячейка становится лишним слоем. Файл `p2/orgchart_ctor/src/lib.rs`:

```rust
/// Отличие от основного решения: поле dept — голый Weak, без ячейки.
pub struct Employee {
    pub name: String,
    dept: Weak<Department>,
}
```

```rust
pub fn hire(dept: &Rc<Department>, name: &str) -> Rc<Employee> {
    let employee = Rc::new(Employee {
        name: String::from(name),
        dept: Rc::downgrade(dept), // связь известна уже в конструкторе
    });
    dept.staff.borrow_mut().push(Rc::clone(&employee));
    employee
}

pub fn department_of(employee: &Employee) -> Option<String> {
    employee.dept.upgrade().map(|d| d.name.clone())
}
```

**E0594** — знакомый отказ §22.1.4 в новой роли: сотрудник живёт за `Rc` (он в штате отдела и у нас в руках), сквозь `Rc` изменяющей ссылки не выдают, и поле без ячейки изменить невозможно **в принципе**, кем бы вы ни были. *Сравнение.* Голый `Weak` строго лучше, пока связь неизменна: на слой меньше в типе, на вызов меньше в каждом обращении, невозможность случайной паники `RefCell already borrowed` и — главное — инвариант «сотрудник всегда в том отделе, куда его наняли» закреплён в типе, а не в дисциплине. `RefCell<Weak<..>>` покупает ровно одно: право переставить связь после создания. Кроме переводов, оно требуется и в других сценариях: узел, который сначала создаётся, а потом присоединяется к дереву (как `parent` в Г22.Ч2.З9 — там `Weak::new()` стоит заглушкой), или структура, собираемая по частям из внешних данных. Правило: если связь известна конструктору и не меняется — голый `Weak`; если связь появляется или меняется позже — `RefCell<Weak<..>>`, и тогда стоит спрятать `borrow_mut` внутрь метода (`transfer`), чтобы пропуск брался в одном месте (гигиена §22.2.2).
