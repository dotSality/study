## Часть 7.1. Куча и её API

### Г7.Ч1.З1

**Условие.** Выделите через `malloc` память под один `int`, проверьте результат на `NULL`, запишите в него `2026` и напечатайте. Освободите память и присвойте указателю `NULL`. Объясните в комментарии, зачем нужны проверка на `NULL` и `free`.

**Решение.** Это полный жизненный цикл блока из §7.1.2: выделить → проверить → использовать → освободить. `malloc(sizeof *p)` запрашивает ровно столько байтов, сколько занимает то, на что указывает `p` (идиома размера); проверка `NULL` обязательна до первого разыменования; `free` возвращает блок куче; финальное `p = NULL` — страховка от использования висячего адреса.

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(sizeof *p);       /* память под один int */
    if (p == NULL) {                  /* malloc мог вернуть NULL — разыменовать его нельзя */
        fprintf(stderr, "out of memory\n");
        return 1;
    }
    *p = 2026;
    printf("*p = %d\n", *p);
    free(p);                          /* каждому malloc — ровно один free, иначе утечка */
    p = NULL;                         /* страховка: ошибочное *p упрётся в NULL, а не в висячий адрес */
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra allocone.c -o allocone
./allocone
```

```
*p = 2026
```

**Ответ:** программа печатает `*p = 2026`. Проверка на `NULL` нужна потому, что при нехватке памяти `malloc` возвращает `NULL`, и разыменование без проверки — падение; `free` нужен потому, что память кучи сама не освобождается — без него блок остаётся занятым до конца программы (утечка).

### Г7.Ч1.З2

**Условие.** Выделите через `calloc` массив из 6 `int` и напечатайте все элементы, **ничего в них не записав**. Какой вывод гарантирован и почему? Освободите массив.

**Решение.** В отличие от `malloc`, `calloc` обнуляет выделенную память: все байты блока — `0`, поэтому каждый `int` в нём равен `0` (§7.1.3). Значит, читать элементы можно сразу после выделения, и вывод гарантирован — шесть нулей.

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *a = calloc(6, sizeof *a);    /* 6 int, все байты обнулены */
    if (a == NULL) return 1;
    for (int i = 0; i < 6; i++)
        printf("%d ", a[i]);          /* читаем, ничего не записав */
    printf("\n");
    free(a);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra zeros.c -o zeros
./zeros
```

```
0 0 0 0 0 0 
```

**Ответ:** гарантирован вывод `0 0 0 0 0 0` — `calloc` по стандарту обнуляет весь блок, поэтому чтение до записи здесь корректно и детерминировано.

**Типичная неверная попытка.** Заменить `calloc(6, sizeof *a)` на `malloc(6 * sizeof *a)` и печатать так же, ничего не записав. Такая версия собирается **без единого предупреждения**:

```
gcc -std=c17 -Wall -Wextra zeros_wrong.c -o zeros_wrong
```

— но её вывод не гарантирован ничем: `malloc` память не инициализирует, в ячейках произвольные байты, а чтение неинициализированной памяти — неопределённое поведение (§7.1.2). Программа может напечатать нули, мусор или что угодно ещё — поэтому её вывод здесь и не приводится. Молчание компилятора показательно: чтение неинициализированной кучи в цикле статикой не ловится (сравните с Г7.Ч1.З5, где чтение по константному индексу компилятор заметил).

### Г7.Ч1.З3

**Условие.** Задайте `int n = 7;`, выделите `malloc`-ом массив из `n` `int`, заполните его значениями `i * 3` (`0, 3, 6, …`), напечатайте и освободите. Используйте идиому размера `n * sizeof *a`.

**Решение.** Размер массива — переменная времени выполнения: `malloc(n * sizeof *a)` выделяет ровно `n` элементов. Заполнение и печать — обычные циклы по индексам; в конце — один `free` на один `malloc`.

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int n = 7;
    int *a = malloc(n * sizeof *a);   /* идиома размера: n * sizeof *a */
    if (a == NULL) return 1;
    for (int i = 0; i < n; i++)
        a[i] = i * 3;
    for (int i = 0; i < n; i++)
        printf("%d ", a[i]);
    printf("\n");
    free(a);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra fill3.c -o fill3
./fill3
```

```
0 3 6 9 12 15 18 
```

**Ответ:** `0 3 6 9 12 15 18` — семь элементов с шагом 3, выделенных по размеру, известному лишь во время выполнения.

**Вариант 2 (заполнение обходом указателя).** Динамический массив — та же непрерывная последовательность элементов, что и обычный (§6.2), поэтому его можно заполнять движущимся указателем, а «индекс» получать как расстояние `q - a`:

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int n = 7;
    int *a = malloc(n * sizeof *a);
    if (a == NULL) return 1;
    for (int *q = a; q < a + n; q++)  /* обход указателем (§6.2.2) */
        *q = (int)(q - a) * 3;        /* «индекс» — это расстояние q - a */
    for (int i = 0; i < n; i++)
        printf("%d ", a[i]);
    printf("\n");
    free(a);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra fill3ptr.c -o fill3ptr
./fill3ptr
```

```
0 3 6 9 12 15 18 
```

*Сравнение.* Результат одинаков; индексная версия прямее выражает формулу «элемент i равен i·3», указательная — подчёркивает, что блок из кучи ничем не отличается от массива из главы 6: по нему так же ходят указателем от `a` до `a + n`. Для заполнения по формуле индексная версия читается проще; указательный обход выигрывает там, где элемент обрабатывают последовательно без нужды в номере (как в `str_dup`, Г7.Ч1.З11).

### Г7.Ч1.З4

**Условие.** Выделите `malloc`-ом массив из 3 `int` (значения `1, 2, 3`), затем через безопасную идиому `realloc` (с временным указателем) расширьте до 6, допишите `4, 5, 6`, напечатайте все шесть и освободите.

**Решение.** Безопасная идиома из §7.1.3: результат `realloc` принимаем во временный `tmp`, старый указатель `a` не трогаем до проверки. При неудаче (`tmp == NULL`) старый блок жив — его можно корректно освободить; при успехе переустанавливаем `a = tmp` и работаем только с новым указателем (блок мог переехать).

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *a = malloc(3 * sizeof *a);
    if (a == NULL) return 1;
    for (int i = 0; i < 3; i++) a[i] = i + 1;        /* 1 2 3 */

    int *tmp = realloc(a, 6 * sizeof *a);            /* безопасная идиома: через tmp */
    if (tmp == NULL) { free(a); return 1; }          /* при неудаче a ещё жив */
    a = tmp;                                         /* переустанавливаем только после проверки */
    for (int i = 3; i < 6; i++) a[i] = i + 1;        /* дописываем 4 5 6 */

    for (int i = 0; i < 6; i++) printf("%d ", a[i]);
    printf("\n");
    free(a);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra grow6.c -o grow6
./grow6
```

```
1 2 3 4 5 6 
```

**Ответ:** `1 2 3 4 5 6` — `realloc` сохранил первые три значения и добавил место ещё под три; освобождается в конце **один** блок (цепочка `malloc` → `realloc` → `free`).

**Вариант 2 (ручной перенос: `malloc` + копирование + `free`).** То, что `realloc` делает «под капотом» в худшем случае, можно выполнить руками: выделить новый блок на 6, скопировать три старых элемента, освободить старый блок:

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *a = malloc(3 * sizeof *a);
    if (a == NULL) return 1;
    for (int i = 0; i < 3; i++) a[i] = i + 1;        /* 1 2 3 */

    int *b = malloc(6 * sizeof *b);                  /* новый блок нужного размера */
    if (b == NULL) { free(a); return 1; }
    for (int i = 0; i < 3; i++) b[i] = a[i];         /* переносим старые данные */
    free(a);                                         /* старый блок больше не нужен */
    a = b;
    for (int i = 3; i < 6; i++) a[i] = i + 1;        /* дописываем 4 5 6 */

    for (int i = 0; i < 6; i++) printf("%d ", a[i]);
    printf("\n");
    free(a);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra grow6manual.c -o grow6manual
./grow6manual
```

```
1 2 3 4 5 6 
```

*Сравнение.* Ручной перенос всегда копирует данные и всегда занимает на время оба блока; `realloc` умеет расширить блок **на месте** (тогда копирования нет вообще) и лишь при невозможности переносит его сам. Поэтому в реальном коде предпочтителен `realloc` — он не медленнее и короче. Ручная версия ценна как разбор механики: она объясняет, почему после успешного `realloc` старый адрес недействителен (старый блок мог быть освобождён — здесь это `free(a)` в явном виде) и почему при неудаче старые данные целы (новый блок не получился — старый никто не трогал).

### Г7.Ч1.З5

**Условие.** *(понимание)* Найдите две ошибки и объясните последствия каждой (не запускайте):

```c
int *p = malloc(5 * sizeof *p);
printf("%d\n", p[0]);      /* (а) */
free(p);
free(p);                   /* (б) */
```

**Решение.** Разбираем построчно:

1. `malloc(5 * sizeof *p)` выделяет 5 `int`, но **не инициализирует** их — в ячейках произвольные байты. (Заодно отметим: результат не проверен на `NULL` — при нехватке памяти уже строка (а) разыменует `NULL`.)
2. **(а)** `printf("%d\n", p[0])` читает `p[0]` **до какой-либо записи** — чтение неинициализированной памяти (§7.1.2). Программа напечатает непредсказуемый мусор; полагаться на это значение нельзя (неопределённое поведение).
3. Первый `free(p)` корректен: блок возвращён куче.
4. **(б)** второй `free(p)` — **двойное освобождение** (§7.2.1): куче возвращают блок, который уже возвращён. Это портит внутренний учёт свободных блоков — неопределённое поведение, классическая почва для аварий и уязвимостей (CERT C MEM30-C).

Запускать не требуется, но собрать поучительно: GCC 15.2 замечает **обе** ошибки статически (здесь случай простейший — константный индекс и оба `free` в одной функции):

```
z5frag.c:7:5: warning: '*p' is used uninitialized [-Wuninitialized]
    7 |     printf("%d\n", p[0]);      /* (а) */
      |     ^~~~~~~~~~~~~~~~~~~~
z5frag.c:9:5: warning: pointer 'p' used after 'free' [-Wuse-after-free]
    9 |     free(p);                   /* (б) */
      |     ^~~~~~~
z5frag.c:8:5: note: call to 'free' here
    8 |     free(p);
      |     ^~~~~~~
```

**Ответ:** (а) — чтение неинициализированной памяти (`malloc` не обнуляет блок; напечатается непредсказуемый мусор, полагаться на него нельзя); (б) — двойное освобождение одного блока (портит учёт кучи, неопределённое поведение). Дополнительный недочёт — отсутствие проверки результата `malloc` на `NULL`.

### Г7.Ч1.З6

**Условие.** *(понимание)* Объясните разницу между `malloc(n * sizeof *p)` и `calloc(n, sizeof *p)`: чем отличается содержимое выделенной памяти сразу после вызова и какие ещё гарантии даёт `calloc`. Когда какой уместнее?

**Решение.** Разница — по трём пунктам (§7.1.3):

1. **Содержимое.** `malloc` возвращает блок с произвольными байтами — читать элементы до записи нельзя (Г7.Ч1.З5а). `calloc` обнуляет все байты блока — каждый `int` в нём равен `0`, читать можно сразу (Г7.Ч1.З2).
2. **Проверка переполнения размера.** `calloc(n, size)` сам проверяет произведение `n * size`: если оно не помещается в `size_t`, возвращает `NULL`. В `malloc(n * sizeof *p)` умножение выполняете вы, и при огромных множителях оно может молча переполниться — `malloc` выделит меньше нужного, а записи «в хвост» уйдут за границу блока.
3. **Цена.** Обнуление — это реальная работа по записи нулей; если блок всё равно немедленно и полностью заполняется данными, она выброшена впустую.

**Ответ:** после `malloc` в памяти произвольный мусор, после `calloc` — гарантированные нули; кроме того, `calloc` сам ловит переполнение произведения `count * size` (возвращая `NULL`), а у `malloc` эта проверка на совести программиста. `calloc` уместен для массивов-накопителей (счётчики, суммы) и всюду, где нужен «чистый» блок; `malloc` достаточен (и чуть дешевле), когда память сразу целиком заполняется своими значениями.

### Г7.Ч1.З7

**Условие.** *(понимание)* Почему запись `a = realloc(a, newsize);` опасна? Опишите конкретный сценарий, при котором она приводит к утечке и потере данных, и приведите правильную версию с временным указателем.

**Решение.** Опасность — в поведении `realloc` при **неудаче**: он возвращает `NULL`, но **старый блок остаётся выделенным и невредимым** (§7.1.3). Присваивание результата напрямую в `a` в этот момент затирает единственный указатель на живой блок.

Конкретный сценарий. Программа накопила в `a` массив из миллиона `int` и просит увеличить его: `a = realloc(a, 2000000 * sizeof *a);`. Памяти на новый размер не хватило — `realloc` вернул `NULL`, старый блок с миллионом значений цел. Но `a` уже перезаписан этим `NULL`: адреса старого блока больше нет **нигде**. Итог двойной: (1) **утечка** — 4 МБ заняты до конца программы, освободить их нечем (`free` звать не на что); (2) **потеря данных** — накопленный миллион значений недостижим, хотя физически ещё в памяти. Вдобавок первое же обращение `a[i]` — разыменование `NULL`.

Правильная версия — временный указатель; `a` не трогаем, пока успех не подтверждён:

```c
int *tmp = realloc(a, newsize);
if (tmp == NULL) {
    /* старый a жив: данные на месте, можно обработать ошибку и free(a) */
} else {
    a = tmp;                      /* только теперь переустанавливаем */
}
```

Ровно эта идиома прогнана в работе в Г7.Ч1.З4 (`grow6.c`) и в растущем массиве §7.1.3.

**Ответ:** при неудаче `realloc` возвращает `NULL`, не освобождая старый блок; `a = realloc(a, ...)` в этом случае затирает единственный указатель на живой блок — данные потеряны, память утекла, а очередное `a[i]` упадёт по `NULL`. Правильно: `int *tmp = realloc(a, newsize); if (tmp == NULL) { /* a жив — обработать */ } else a = tmp;`.

### Г7.Ч1.З8

**Условие.** *(понимание)* В функции `int *make_squares(int n)` из §7.1.2 нельзя вызывать `free(a)` перед `return a;`. Почему? Кто в этой схеме владелец памяти и кто обязан её освободить? Что вернёт функция, если освободить блок до возврата?

**Решение.** Смысл `make_squares` — отдать вызывающему **живой** блок с данными; вместе с указателем передаётся и **владение** (§7.1.2). `free(a)` перед `return` разрушает ровно то, что мы обещали отдать: блок возвращается куче, и наружу уходит адрес уже не нашего блока.

- **Почему нельзя.** После `free(a)` блок может быть в любой момент выдан другому `malloc`; обращение вызывающего к `sq[i]` — use-after-free, неопределённое поведение (§7.2.1).
- **Кто владелец.** Функция выделила блок, но по `return a;` передала владение вызывающему — в примере §7.1.2 это `main`. Правило «кто выделил — тот (или назначенный им) освобождает» здесь означает: освобождает **назначенный** владелец, `main`, вызовом `free(sq)` после использования.
- **Что вернётся при `free` до возврата.** Само **значение** указателя `free` не меняет — функция вернёт тот же адрес, но теперь **висячий**: он указывает на память, которая программе больше не принадлежит. Формально даже само значение освобождённого указателя недействительно — использовать его нельзя.

Ошибку видит уже компилятор — версия с `free(a); return a;` собирается с предупреждением (GCC 15.2, сборка без запуска):

```
makesqbad.c:11:12: warning: pointer 'a' used after 'free' [-Wuse-after-free]
   11 |     return a;
      |            ^
makesqbad.c:10:5: note: call to 'free' here
   10 |     free(a);
      |     ^~~~~~~
```

**Ответ:** `free(a)` перед `return a;` убивает блок, который функция обязана отдать живым, — вызывающий получит висячий указатель, и любое обращение к нему будет use-after-free. Владелец памяти после возврата — вызывающий (`main`): он и обязан вызвать `free`. Функция при этом вернула бы прежний адрес — но адрес уже освобождённого блока, пользоваться которым нельзя.

### Г7.Ч1.З9

**Условие.** *(понимание)* Не запуская, объясните, почему идиома `malloc(n * sizeof *p)` надёжнее, чем `malloc(n * sizeof(int))`. Что сломается во втором варианте, если тип `p` позже поменяют с `int *` на `long *`, а в первом — нет?

**Решение.** `sizeof *p` — размер **того, на что указывает `p`**, какого бы типа `p` ни был: выражение привязано к самой переменной, а не к записанному руками имени типа. `sizeof(int)` — константа, никак с `p` не связанная.

Пусть тип `p` поменяли на `long *`, а размер в `malloc` править забыли (типичная правка «в одном месте из двух»):

- **Первый вариант** `p = malloc(n * sizeof *p);` перестроится сам: `*p` теперь имеет тип `long`, `sizeof *p` — размер `long`. Выделится ровно `n` элементов нового типа. Чинить нечего.
- **Второй вариант** `p = malloc(n * sizeof(int));` продолжит выделять по размеру `int`. Если на платформе `long` больше `int`, блока хватит лишь на часть элементов: записи `p[i]` в «хвост» массива уйдут **за границу блока** — переполнение кучи (§7.2.1), которое компилятор не заметит (типы в самом вызове `malloc` корректны — он принимает просто число байтов).

Платформенный нюанс, который делает эту ошибку особенно коварной: проявится ли она — зависит от машины. На эталоне курса (Windows, LLP64) `long` совпадает по размеру с `int`, и ошибка **замаскирована**; на Linux (LP64) `long` вдвое больше — и тот же код выделяет вдвое меньше нужного. Проверено прогоном одной и той же программы на обоих контурах:

```
sizeof(int)=4 sizeof(long)=4
```

— эталон (MinGW), и

```
sizeof(int)=4 sizeof(long)=8
```

— Linux (WSL). Код с `sizeof(int)` «работал бы» на первой машине и переполнял кучу на второй.

**Ответ:** `sizeof *p` автоматически следует за типом `p`, поэтому при смене типа выделение остаётся верным. С `sizeof(int)` после смены `p` на `long *` функция продолжит выделять по 4 байта на элемент; там, где `long` занимает 8 байт (Linux LP64), блока хватит лишь на половину элементов, и записи в остальные — переполнение буфера кучи; на эталоне (LLP64, `long` = 4 байта) ошибка до поры незаметна — что и делает её опасной.

### Г7.Ч1.З10

**Условие.** *(прикладное)* Напишите функцию `int *dup_array(const int *src, int n)`, которая выделяет в куче новый массив из `n` `int`, копирует в него `src` и возвращает (при нехватке памяти — `NULL`). В `main` продублируйте `{5, 10, 15, 20}`, напечатайте копию, освободите. Обратите внимание на `const` у источника (§6.3.1).

**Решение.** Схема «выделила — заполнила — вернула вместе с владением» из §7.1.2. Источник объявлен `const int *`: функция обещает только читать его (§6.3.1) — попытка записи в `src[i]` не скомпилировалась бы. Освобождает копию новый владелец — `main`.

```c
#include <stdio.h>
#include <stdlib.h>

int *dup_array(const int *src, int n)     /* источник только читаем (§6.3.1) */
{
    int *dst = malloc(n * sizeof *dst);
    if (dst == NULL) return NULL;
    for (int i = 0; i < n; i++)
        dst[i] = src[i];
    return dst;                           /* вместе с указателем уходит владение */
}

int main(void)
{
    int src[] = {5, 10, 15, 20};
    int n = (int)(sizeof src / sizeof src[0]);
    int *copy = dup_array(src, n);
    if (copy == NULL) { fprintf(stderr, "alloc failed\n"); return 1; }
    for (int i = 0; i < n; i++)
        printf("%d ", copy[i]);
    printf("\n");
    free(copy);                           /* владелец копии — main */
    return 0;
}
```

```
./duparr
```


**Ответ:** программа печатает `5 10 15 20` — копию исходного массива из отдельного блока кучи; исходный `src` не изменён (и защищён `const`), копию освобождает `main`.

**Вариант 2 (выходной параметр и код результата).** Та же функция в стиле примера 3 из §7.1.2: `return` отдан под код успеха/ошибки, а копия уходит через `int **out`:

```c
#include <stdio.h>
#include <stdlib.h>

/* 0 — успех, -1 — нехватка памяти; копия отдаётся через *out */
int dup_array(int **out, const int *src, int n)
{
    int *dst = malloc(n * sizeof *dst);
    if (dst == NULL) return -1;
    for (int i = 0; i < n; i++)
        dst[i] = src[i];
    *out = dst;                           /* адрес копии — в указатель вызывающего */
    return 0;
}

int main(void)
{
    int src[] = {5, 10, 15, 20};
    int n = (int)(sizeof src / sizeof src[0]);
    int *copy = NULL;
    if (dup_array(&copy, src, n) != 0) { fprintf(stderr, "alloc failed\n"); return 1; }
    for (int i = 0; i < n; i++)
        printf("%d ", copy[i]);
    printf("\n");
    free(copy);
    return 0;
}
```


*Сравнение.* Версия с `return dst` короче и естественна, пока «не получилось» кодируется единственным способом — `NULL`. Версия с выходным параметром разводит **данные** и **статус**: `return` может различать причины отказа (нехватка памяти, неверные аргументы — как в `fill_range`, Г7.Ч1.З12), а указатель вызывающего заполняется только при успехе. Для одной причины ошибки достаточно первой; как только статусов становится больше одного, переходят ко второй — это типовой каркас ресурсных API.

### Г7.Ч1.З11

**Условие.** *(прикладное)* Напишите функцию `char *str_dup(const char *s)`, которая выделяет память под копию строки (длина + 1 под `'\0'`), копирует туда `s` посимвольно (обходом указателя, §6.2.3) и возвращает. Проверьте на `"memory"`; напечатайте копию и освободите. (Аналог библиотечной `strdup`.)

**Решение.** Два прохода по строке: первый считает длину (идём указателем до `'\0'`), второй копирует символы идиомой `*w++ = *s++` (§6.2.2). Выделяем `len + 1` байт — терминатор в длину не входит, но место в блоке ему нужно; после цикла копирования ставим его вручную (цикл остановился **на** `'\0'`, не скопировав его).

```c
#include <stdio.h>
#include <stdlib.h>

char *str_dup(const char *s)
{
    int len = 0;
    for (const char *q = s; *q != '\0'; q++)   /* длина — обходом до '\0' (§6.2.3) */
        len++;
    char *d = malloc(len + 1);                 /* +1 — место под завершающий '\0' */
    if (d == NULL) return NULL;
    char *w = d;
    while (*s != '\0')                         /* посимвольное копирование */
        *w++ = *s++;                           /* идиома *p++ (§6.2.2) */
    *w = '\0';                                 /* терминатор ставим вручную */
    return d;                                  /* владение копией — у вызывающего */
}

int main(void)
{
    char *copy = str_dup("memory");
    if (copy == NULL) { fprintf(stderr, "alloc failed\n"); return 1; }
    printf("copy = %s\n", copy);
    free(copy);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra mystrdup.c -o mystrdup
./mystrdup
```


Продвигать параметр `s` внутри функции безопасно: это локальная копия переданного адреса (§4.1.3), исходный указатель вызывающего не меняется.

**Ответ:** программа печатает `copy = memory` — в куче создана независимая копия строки размером `strlen("memory") + 1 = 7` байт; освобождает её вызывающий.

**Вариант 2 (через `strlen` и `strcpy` из `<string.h>`).** Оба прохода уже реализованы в стандартной библиотеке (§5.2.3): `strlen` меряет, `strcpy` копирует вместе с терминатором:

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

char *str_dup(const char *s)
{
    size_t n = strlen(s);              /* длина без '\0' (§5.2.3) */
    char *d = malloc(n + 1);           /* +1 под терминатор */
    if (d == NULL) return NULL;
    strcpy(d, s);                      /* копирует вместе с '\0'; место есть */
    return d;
}

int main(void)
{
    char *copy = str_dup("memory");
    if (copy == NULL) { fprintf(stderr, "alloc failed\n"); return 1; }
    printf("copy = %s\n", copy);
    free(copy);
    return 0;
}
```

```

```


*Сравнение.* Библиотечная версия короче, не содержит ручных циклов (меньше мест для ошибки на единицу) и обычно быстрее — `strlen`/`strcpy` оптимизированы. Ручная версия ценна тем, что показывает механику: откуда берётся `+1`, почему терминатор надо не забыть и как копирование сводится к `*w++ = *s++`. Требование «приёмник достаточно велик» для `strcpy` здесь выполнено конструктивно: буфер только что выделен размером `strlen(s) + 1`. В рабочем коде предпочтительна библиотечная версия; условие же этого задания прямо просит посимвольную — она и является основной.

### Г7.Ч1.З12

**Условие.** *(прикладное)* Напишите функцию `int fill_range(int **out, int lo, int hi)`, которая выделяет массив из `hi - lo + 1` элементов, заполняет его числами от `lo` до `hi` включительно и отдаёт через выходной параметр `*out` (возврат: `0` — успех, `-1` — нехватка памяти или `hi < lo`). В `main` получите диапазон `[3, 8]`, напечатайте и освободите. Используйте `int **` (§6.3.2, §7.1.2).

**Решение.** Каркас примера 3 из §7.1.2: статус — через `return`, массив — через `int **out`. Сначала проверяем аргументы (`hi < lo` — сразу `-1`, ничего не выделяя), затем выделяем `hi - lo + 1` элементов («включительно» даёт `+1`), заполняем `a[i] = lo + i` и лишь при полном успехе пишем адрес в `*out`.

```c
#include <stdio.h>
#include <stdlib.h>

/* 0 — успех; -1 — нехватка памяти или hi < lo */
int fill_range(int **out, int lo, int hi)
{
    if (hi < lo) return -1;
    int n = hi - lo + 1;                  /* включительно, поэтому +1 */
    int *a = malloc(n * sizeof *a);
    if (a == NULL) return -1;
    for (int i = 0; i < n; i++)
        a[i] = lo + i;
    *out = a;                             /* адрес блока — в указатель вызывающего */
    return 0;
}

int main(void)
{
    int *r = NULL;
    if (fill_range(&r, 3, 8) != 0) { fprintf(stderr, "fill_range failed\n"); return 1; }
    for (int i = 0; i < 8 - 3 + 1; i++)
        printf("%d ", r[i]);
    printf("\n");
    free(r);

    printf("fill_range(&r, 8, 3) -> %d\n", fill_range(&r, 8, 3));  /* hi < lo */
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra fillrange.c -o fillrange
./fillrange
```

```
3 4 5 6 7 8 
fill_range(&r, 8, 3) -> -1
```

**Ответ:** для диапазона `[3, 8]` печатается `3 4 5 6 7 8` (шесть элементов, `8 - 3 + 1`); обратный порядок границ корректно отвергается кодом `-1` без выделения памяти. Владелец блока — `main`, он и вызывает `free(r)`.

**Типичная неверная попытка.** Потерять `+1`: `int n = hi - lo;` — классическая ошибка на единицу при «включительных» границах. Версия с такой формулой (и печатью того же числа элементов) собирается чисто и спокойно работает:

```
3 4 5 6 7 
```

— но диапазон «от 3 до 8 включительно» превратился в пять чисел: верхняя граница `8` потеряна (вывод выше — реальный прогон неверной версии). Коварство в том, что ошибка **тихая** — ни предупреждения, ни падения, просто на один элемент меньше. Проверяйте формулу длины на минимальном случае: при `lo == hi` диапазон состоит из одного числа, значит `n` обязан быть `1` — а `hi - lo` даёт `0`.

### Г7.Ч2.З2

**Условие.** *(понимание)* Для каждого фрагмента назовите класс ошибки (утечка / use-after-free / double free / переполнение буфера) и одно предложение — чем это опасно:

```c
/* A */ int *p = malloc(sizeof *p); free(p); *p = 1;
/* B */ int *q = malloc(4 * sizeof *q); for (int i=0;i<=4;i++) q[i]=i; free(q);
/* C */ int *r = malloc(sizeof *r); free(r); free(r);
/* D */ int *s = malloc(sizeof *s); *s = 5;   /* и больше ничего */
```

**Решение.** Сверяем каждый фрагмент с каталогом §7.2.1:

- **A** — запись `*p = 1` **после** `free(p)`: блок уже возвращён куче и мог быть выдан другому.
- **B** — цикл `i <= 4` при блоке из 4 элементов (`q[0..3]`): итерация `i == 4` пишет в `q[4]`, за границей блока.
- **C** — два `free(r)` подряд на один блок.
- **D** — блок выделен, записан и **никогда не освобождён**; по выходе из области видимости указатель теряется.

**Ответ:**

- **A — use-after-free:** запись идёт в память, которая уже не принадлежит программе, — можно молча испортить чужие данные (неопределённое поведение).
- **B — переполнение буфера кучи:** запись `q[4]` затирает память за блоком — соседние данные или служебные структуры кучи, со сбоем «позже и в другом месте».
- **C — double free:** повторное освобождение портит внутренний учёт свободных блоков кучи — почва для аварий и уязвимостей.
- **D — утечка:** 4 байта останутся занятыми до конца программы; тот же паттерн в цикле или долгоживущем сервере исчерпает память.

### Г7.Ч2.З3

**Условие.** *(понимание)* Дан отчёт AddressSanitizer:

```

0x... is located 0 bytes after 16-byte region ...
```

Объясните по отчёту: какой класс ошибки, что означает «0 bytes after 16-byte region», сколько `int`-элементов помещалось в блоке и в какой элемент массива произошла запись.

**Решение.** Читаем отчёт по строкам, как учит §7.2.2:

1. `heap-buffer-overflow` — класс ошибки: выход за границы блока **кучи**.
2. `WRITE of size 4` — нарушение было **записью** четырёх байтов, то есть одного `int`; произошло в `main`, строка `prog.c:8`.
3. `0 bytes after 16-byte region` — адрес доступа лежит на расстоянии **0 байт после** конца 16-байтового блока: запись пришлась в первый же байт **сразу за** блоком.

### Г7.Ч2.З4

**Условие.** *(понимание)* `gcc -Wall` предупреждает об use-after-free в программе §7.2.1 (пример 2), но не поймал бы его, будь `free(p)` в одной функции, а `printf("%d", *p)` — в другой (через переданный указатель). Объясните, почему статический анализ теряет след, и почему рантайм-инструмент (ASan/Valgrind) — нет.

**Решение.** Статическое предупреждение `-Wuse-after-free` строится на анализе потока значений **внутри одной функции**: компилятор видит в её теле вызов `free(p)` и последующее использование того же `p` — и сопоставляет их. Как только эти два события разнесены по разным функциям, в анализируемой функции нет одновременно и `free`, и использования: глядя на `main`, компилятор видит лишь вызов «какой-то функции», принявшей указатель, — освобождает она его или нет, из сигнатуры не следует. Проверять это точно означало бы анализировать все возможные пути через все функции программы (включая другие единицы трансляции и библиотеки) — общего решения у такой задачи нет, и статика честно молчит.

Проверено на разнесённой версии: `free` спрятан в функцию `dispose`, обращение осталось в `main` —

```c
#include <stdio.h>
#include <stdlib.h>

void dispose(int *p)             /* освобождает блок; вызывающий об этом «не знает» */
{
    free(p);
}

int main(void)
{
    int *p = malloc(sizeof *p);
    if (p == NULL) return 1;
    *p = 42;
    dispose(p);                  /* free спрятан в другой функции */
    printf("%d\n", *p);          /* use-after-free, но main этого «не видит» */
    return 0;
}
```

`gcc -std=c17 -Wall -Wextra uaf2.c` на эталоне собирает эту программу **без единого предупреждения**. (Граница проходит именно по «кто видит `free`»: если оба события в одной функции — пусть даже использование лишь передаёт указатель дальше, `show(p)` после `free(p)`, — GCC 15.2 предупреждение выдаёт.)

Рантайм-инструменту межпроцедурный анализ не нужен: он смотрит не на код, а на **сам блок памяти**. ASan в момент `free` помечает регион как освобождённый («отравляет» его) и проверяет каждый фактический доступ: чтение по этому адресу — ошибка, из какой бы функции оно ни пришло. Прогон разнесённой версии под ASan (Linux-контур):

```
$ gcc -std=c17 -g -fsanitize=address uaf2.c -o uaf2 && ./uaf2
```

```
==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010 ...
READ of size 4 at 0x502000000010 thread T0
    #0 ... in main uaf2.c:15              ← обращение *p (строка 15, в main)
    …
freed by thread T0 here:
    #0 ... in free …
    #1 ... in dispose uaf2.c:6            ← free — в ДРУГОЙ функции
    #2 ... in main uaf2.c:14
    …
previously allocated by thread T0 here:
    #0 ... in malloc …
    #1 ... in main uaf2.c:11
    …
SUMMARY: AddressSanitizer: heap-use-after-free uaf2.c:15 in main
```

Отчёт даже показывает разнесённость прямо: доступ — `main uaf2.c:15`, освобождение — `dispose uaf2.c:6` (вызван из `main uaf2.c:14`). Статике этот след недоступен, рантайму — очевиден.

**Ответ:** статический анализ сопоставляет `free` и использование в пределах видимого ему потока значений одной функции; когда `free` уходит в другую функцию, вызов для анализатора непрозрачен (проверить все межпроцедурные пути в общем виде невозможно), и след теряется — разнесённая версия собирается вообще без предупреждений. ASan/Valgrind отслеживают состояние **самого блока** во время выполнения: блок помечен освобождённым в момент `free`, и любой последующий фактический доступ к нему ловится в момент обращения — независимо от того, из каких функций пришли `free` и доступ.

### Г7.Ч2.З5

**Условие.** *(понимание)* В отчёте Valgrind различают `definitely lost` и `still reachable`. Объясните разницу на примерах: (а) `malloc` без `free` в функции, из которой указатель не вернули; (б) `malloc` в `main` без `free` перед `return`, но указатель ещё в переменной. Какая из них — «настоящая» утечка и почему?

**Решение.** Классификация Memcheck отвечает на вопрос: **остался ли к концу программы хоть один указатель на неосвобождённый блок**. `definitely lost` — не остался: блок недостижим, освободить его уже принципиально невозможно — это настоящая утечка. `still reachable` — указатель есть: блок просто не освободили к выходу, но программа «знала», где он.

Случай **(а)** — указатель был локальной переменной функции и исчез вместе с её кадром:

```c
#include <stdlib.h>

void worker(void)
{
    int *tmp = malloc(8 * sizeof *tmp);   /* блок из 32 байт */
    if (tmp == NULL) return;
    tmp[0] = 1;
}                                          /* tmp исчез вместе с кадром — указатель потерян */

int main(void)
{
    worker();
    return 0;
}
```

```
$ gcc -std=c17 -g lostdemo.c -o lostdemo && valgrind --leak-check=full ./lostdemo
```

```
==...== 32 bytes in 1 blocks are definitely lost in loss record 1 of 1
==...==    at 0x...: malloc (...)
==...==    by 0x...: worker (lostdemo.c:5)
==...==    by 0x...: main (lostdemo.c:12)
==...==
==...== LEAK SUMMARY:
==...==    definitely lost: 32 bytes in 1 blocks
```

Случай **(б)** тоньше, чем кажется, — и здесь буквальный эксперимент поучителен. Программа с указателем в локальной переменной `main` (`int *keep = malloc(...); return 0;`) даёт у Memcheck… тоже `definitely lost: 32 bytes in 1 blocks` (реальный прогон `reachdemo.c`). Причина — **момент подсчёта**: Valgrind классифицирует блоки **после возврата из `main`**, когда кадр `main` уже уничтожен, — локальная переменная с адресом к этому моменту исчезла точно так же, как `tmp` из (а). «Указатель ещё в переменной» надо понимать как «указатель доживает до самого конца программы» — например, в статической переменной (§7.1.1: статическое время жизни — весь запуск):

```c
#include <stdlib.h>

static int *keep;                         /* статический указатель живёт весь запуск */

int main(void)
{
    keep = malloc(8 * sizeof *keep);      /* free нет, но указатель цел до самого конца */
    if (keep == NULL) return 1;
    keep[0] = 1;
    return 0;
}
```

```
$ gcc -std=c17 -g reachstatic.c -o reachstatic && valgrind --leak-check=full ./reachstatic
```

```
==...== HEAP SUMMARY:
==...==     in use at exit: 32 bytes in 1 blocks
==...==   total heap usage: 1 allocs, 0 frees, 32 bytes allocated
==...==
==...== LEAK SUMMARY:
==...==    definitely lost: 0 bytes in 0 blocks
==...==    ...
==...==    still reachable: 32 bytes in 1 blocks
==...==
==...== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)
```

Блок не освобождён (`0 frees`), но Memcheck нашёл на него живой указатель — категория `still reachable`, и в `ERROR SUMMARY` это даже **не ошибка** (память такого блока корректно вернёт ОС при завершении; освобождать её всё равно хорошая практика — §7.2.2).

**Ответ:** `definitely lost` — на блок не осталось ни одного указателя, освободить его уже невозможно — это и есть «настоящая» утечка (случай (а); ею же на практике оборачивается и буквальный случай (б) — к моменту подсчёта, после возврата из `main`, локальный указатель уже уничтожен). `still reachable` — блок не освобождён, но живой указатель на него в момент завершения есть (например, в статической переменной): программа была в шаге от корректного `free`, и Valgrind не считает это ошибкой. Настоящая утечка опаснее, потому что она **некорректируема** — код с потерянным указателем уже никогда не сможет вернуть память, и в долгоживущей программе такие блоки накапливаются.

### Г7.Ч2.З6

**Условие.** *(понимание)* Почему `p = NULL;` сразу после `free(p)` — полезная привычка? Как это превращает потенциальный use-after-free в предсказуемое поведение и почему делает случайный повторный `free(p)` безвредным? (Вспомните, что делает `free(NULL)`.)

**Решение.** После `free(p)` в `p` остаётся прежний адрес — теперь висячий: обращение по нему — тихое неопределённое поведение, которое может «работать», портить чужие данные или падать от запуска к запуску (§7.2.1). Присваивание `p = NULL` заменяет опасное значение на безопасное и **проверяемое**:

- **UAF → предсказуемость.** Ошибочное `*p` по `NULL`-указателю — не «лотерея» на висячем адресе, а гарантированно некорректный доступ, который на практике немедленно роняет программу в месте ошибки (а не «позже и в другом месте»); главное — `NULL` можно честно проверить: `if (p != NULL)` отсекает обращение вовсе.
- **Double free → no-op.** `free(NULL)` по стандарту **ничего не делает** (§7.1.2). Значит, случайный повторный `free(p)` при `p == NULL` — безвредный вызов, а не порча учёта кучи.

Демонстрация обеих линий защиты (корректная программа, эталонный прогон):

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(sizeof *p);
    if (p == NULL) return 1;
    *p = 7;
    free(p);
    p = NULL;                    /* страховка сразу после free */
    if (p != NULL)               /* ошибочное обращение отсекается честной проверкой */
        printf("%d\n", *p);
    free(p);                     /* «случайный» повторный free: p == NULL — безвредно */
    printf("done\n");
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra nullafterfree.c -o nullafterfree
./nullafterfree
```

```
done
```

Печать `*p` не выполнилась (проверка не пустила), повторный `free` прошёл как `free(NULL)` — программа корректно дошла до `done`.

**Ответ:** `p = NULL` после `free(p)` убивает висячий адрес: потенциальный use-after-free превращается из недетерминированного UB в предсказуемую ситуацию — `NULL` либо отсекается явной проверкой, либо немедленно и шумно роняет программу в точке ошибки; а случайный повторный `free(p)` становится `free(NULL)`, который по стандарту не делает ничего, — двойное освобождение исключено.

### Г7.Ч2.З7

**Условие.** *(прикладное)* Напишите программу с намеренным переполнением буфера кучи: выделите массив из 3 `int`, в цикле запишите в индексы `0..3` (на один больше). Соберите её с `-fsanitize=address`, запустите, приведите ключевые строки отчёта (класс ошибки, `WRITE`, `... after ... region`). Затем исправьте границу и убедитесь, что отчёт чист.

**Решение.** Программа с промахом на единицу — блок `a[0..2]`, цикл до `i == 3` включительно:

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *a = malloc(3 * sizeof *a);   /* 3 элемента: a[0..2] */
    if (a == NULL) return 1;
    for (int i = 0; i <= 3; i++)      /* ОШИБКА: i == 3 — запись за границей */
        a[i] = i;
    printf("%d\n", a[0]);
    free(a);
    return 0;
}
```

На эталоне `gcc -std=c17 -Wall -Wextra` собирает её **без единого предупреждения** — как и обещает §7.2.1, размер блока кучи статике неизвестен. Сборка и запуск с ASan (Linux-контур):

```

```

Ключевые строки отчёта:

Всё по нашей арифметике: класс — `heap-buffer-overflow`; `WRITE of size 4` — запись одного `int`; `0 bytes after 12-byte region` — адрес сразу за блоком в 12 байт (3 × `int`), то есть `a[3]` при допустимых `a[0..2]`. **Ответ:** запись в `a[3]` при блоке из трёх `int` даёт отчёт `heap-buffer-overflow`, `WRITE of size 4`, `0 bytes located after 12-byte region` — запись одного `int` в первый байт за 12-байтовым блоком; компилятор при этом молчал. После исправления границы (`i < 3`) прогон под ASan чист: вывод `0`, код возврата 0, ни одной диагностики.

### Г7.Ч2.З8

**Условие.** *(прикладное)* Дана функция, «протекающая» через владельца:

```c
#include <stdlib.h>

int *make(int n) { return malloc(n * sizeof(int)); }
int main(void) {
    for (int i = 0; i < 3; i++) {
        int *a = make(4);
        a[0] = i;                 /* используем */
    }                             /* a теряется каждую итерацию */
    return 0;
}
```

Найдите утечку (сколько блоков теряется?), объясните, кто здесь владелец, и исправьте программу так, чтобы Valgrind сообщил `no leaks are possible`. Проверьте под Valgrind.

**Решение.** `make(4)` выделяет блок на 4 `int` (16 байт) и по `return` передаёт **владение** вызывающему (§7.1.2): освобождать обязан тот, кто получил указатель, — `main`. Но `main` не вызывает `free` ни разу, а локальный `a` живёт лишь до конца итерации: на каждом витке адрес предыдущего блока теряется безвозвратно. Теряются **все три блока** — 3 × 16 = 48 байт. Valgrind это подтверждает:

```
$ gcc -std=c17 -g loopleak.c -o loopleak && valgrind --leak-check=full ./loopleak
```

```
==...== HEAP SUMMARY:
==...==     in use at exit: 48 bytes in 3 blocks
==...==   total heap usage: 3 allocs, 0 frees, 48 bytes allocated
==...==
==...== 48 bytes in 3 blocks are definitely lost in loss record 1 of 1
==...==    at 0x...: malloc (...)
==...==    by 0x...: make (loopleak.c:3)
==...==    by 0x...: main (loopleak.c:6)
==...==
==...== LEAK SUMMARY:
==...==    definitely lost: 48 bytes in 3 blocks
```

Исправление: владелец (`main`) обязан вернуть блок до того, как потеряет указатель, — `free(a)` в конце тела цикла:

```c
#include <stdlib.h>

int *make(int n) { return malloc(n * sizeof(int)); }
int main(void) {
    for (int i = 0; i < 3; i++) {
        int *a = make(4);
        a[0] = i;                 /* используем */
        free(a);                  /* владелец блока — main: вернуть до конца итерации */
    }
    return 0;
}
```

```
$ gcc -std=c17 -g loopleakfix.c -o loopleakfix && valgrind --leak-check=full ./loopleakfix
```

```
==...== HEAP SUMMARY:
==...==     in use at exit: 0 bytes in 0 blocks
==...==   total heap usage: 3 allocs, 3 frees, 48 bytes allocated
==...==
==...== All heap blocks were freed -- no leaks are possible
==...==
==...== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)
```

`3 allocs, 3 frees` — каждому выделению нашлось освобождение. (Попутный недочёт исходника: результат `make` не проверяется на `NULL` перед `a[0] = i` — в полноценном коде проверка обязательна, §7.1.2.)

**Ответ:** теряются все 3 блока по 16 байт — 48 байт (`48 bytes in 3 blocks are definitely lost`, стек: `make` ← `main`). Владелец — `main`: `make` передаёт владение вместе с возвращённым указателем. Исправление — `free(a)` в конце каждой итерации; после него Valgrind сообщает `All heap blocks were freed -- no leaks are possible` (`3 allocs, 3 frees`).

**Типичная неверная попытка.** Вынести «один `free` за цикл» — освободить после цикла последний `a`:

```c
int *a = NULL;
for (int i = 0; i < 3; i++) {
    a = make(4);              /* каждая итерация затирает предыдущий адрес */
    a[0] = i;
}
free(a);                      /* «исправление»: освобождён только последний блок */
```

```
==...==   total heap usage: 3 allocs, 1 frees, 48 bytes allocated
==...==
==...== 32 bytes in 2 blocks are definitely lost in loss record 1 of 1
```

Реальный прогон под Valgrind: утечка стала меньше (2 блока вместо 3), но не исчезла — `free` в конце получает лишь адрес **последней** итерации, а два предыдущих затёрты присваиванием `a = make(4)`. Правило «каждому `malloc` — свой `free`» считается по числу вызовов: три выделения не закрыть одним освобождением.

**Вариант 2 (один буфер вне цикла).** Если каждая итерация использует блок лишь как временный буфер одного и того же размера, утечку можно устранить архитектурно — выделить буфер один раз до цикла и освободить один раз после:

```c
#include <stdlib.h>

int *make(int n) { return malloc(n * sizeof(int)); }
int main(void) {
    int *a = make(4);             /* один блок на все итерации */
    if (a == NULL) return 1;
    for (int i = 0; i < 3; i++) {
        a[0] = i;                 /* переиспользуем тот же буфер */
    }
    free(a);                      /* один malloc — один free */
    return 0;
}
```

```
$ gcc -std=c17 -g loopleakreuse.c -o loopleakreuse && valgrind --leak-check=full ./loopleakreuse
```

```
==...==   total heap usage: 1 allocs, 1 frees, 16 bytes allocated
==...==
==...== All heap blocks were freed -- no leaks are possible
```

*Сравнение.* Первый способ (free в теле цикла) сохраняет семантику исходника — «свежий блок на каждую итерацию» — и обязателен, когда блоки разного размера или их время жизни привязано к итерации; платится за это тремя парами malloc/free. Второй способ дешевле (одно выделение вместо трёх — `1 allocs, 1 frees`) и проще для контроля владения, но меняет семантику: буфер один, данные предыдущей итерации в нём не изолированы — годится лишь тогда, когда каждая итерация полностью перезаписывает нужную ей часть буфера. Для настоящего «своего блока на итерацию» корректен только первый способ.
