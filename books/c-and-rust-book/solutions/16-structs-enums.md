## Часть 16.1. Структуры и методы

### Г16.Ч1.З1

**Условие.** Объявите структуру `Book` с полями `title: String`, `pages: u32`, `available: bool`. Создайте экземпляр, напечатайте все поля, затем уменьшите `pages` на 10 и напечатайте снова. Предскажите, что скажет компилятор, если убрать `mut`, — и проверьте (код ошибки и `help`-подсказку сверьте с §16.1.1).

**Решение.** Объявление — имя типа и список полей `имя: тип` через запятую; `typedef`-церемония из §8.2.3 не нужна, `Book` сразу является типом. Экземпляр создаётся указанием **всех** полей по именам, порядок произволен. Право менять поля выдаётся не полю, а переменной целиком — значит, `let mut b`. Файл `s1.rs`:

```rust
struct Book {
    title: String,
    pages: u32,
    available: bool,
}

fn main() {
    let mut b = Book {
        title: String::from("Rust in Action"),
        pages: 456,
        available: true,
    };
    println!("{}, {} pages, available: {}", b.title, b.pages, b.available);
    b.pages -= 10;
    println!("{}, {} pages, available: {}", b.title, b.pages, b.available);
}
```

```
Rust in Action, 456 pages, available: true
Rust in Action, 446 pages, available: true
```

Три замечания по коду. Первое: `title` — владеющая `String`, а не `&str`, поэтому в литерале стоит `String::from(...)`; почему именно так — разберём в З5. Второе: печатаются **поля**, а не структура целиком: у `Book` нет `Display`, а у `String`, `u32` и `bool` он есть (§16.1.2). Третье: `b.pages -= 10` — составное присваивание, то есть всё-таки присваивание; именно на нём и споткнётся версия без `mut`.

*Предсказание.* Уберём `mut` — ожидаем E0594 «cannot assign to `b.pages`, as `b` is not declared as mutable» и `help`, предлагающий вписать `mut` в **объявление переменной**. Файл `s1_nomut.rs` (⛔ не компилируется):

```
error[E0594]: cannot assign to `b.pages`, as `b` is not declared as mutable
  --> s1_nomut.rs:14:5
   |
14 |     b.pages -= 10;
   |     ^^^^^^^^^^^^^ cannot assign
   |
help: consider changing this to be mutable
   |
 8 |     let mut b = Book {
   |         +++

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0594`.
```

Предсказание подтвердилось; тот же текст (для файла `field_mut.rs`, оттого другие номера строк) приведён в §16.1.1. В отчёте важны две детали. Подчёркнуто **всё присваивание целиком**, а не имя поля: компилятор смотрит на операцию и на владельца операции — переменную. И `help` показывает пальцем на строку 8, где переменная объявлена: разрешение писать выдаётся при объявлении и сразу на весь экземпляр — «изменяемого поля» в Rust не существует.

**Ответ:** структура и программа — листинг `s1.rs` выше; вывод — `Rust in Action, 456 pages, available: true`, затем `Rust in Action, 446 pages, available: true`. Без `mut` программа **не компилируется**: `error[E0594]: cannot assign to `b.pages`, as `b` is not declared as mutable` с подсказкой `help: consider changing this to be mutable`, предлагающей вставить `mut` в строку `let b = Book {`. Причина: изменяемость в Rust — свойство переменной, а не отдельного поля; `b.pages -= 10` — присваивание, а права на запись у `b` нет.

### Г16.Ч1.З2

**Условие.** Напишите функцию `build_book(title: String, pages: u32) -> Book`, использующую сокращение полей (field init shorthand), с `available: true` по умолчанию. Объясните: почему сокращение здесь применимо только к двум полям из трёх и почему параметр `title` правильно брать по владению, а не по ссылке (§15.2.1 и пример 1 §16.1.1 вам в помощь).

**Решение.** Файл `s2.rs`:

```rust
struct Book {
    title: String,
    pages: u32,
    available: bool,
}

fn build_book(title: String, pages: u32) -> Book {
    Book {
        title,           // сокращение: параметр называется как поле
        pages,           // то же самое
        available: true, // параметра нет — значение по умолчанию пишем явно
    }
}

fn main() {
    let b = build_book(String::from("The Rust Programming Language"), 560);
    println!("{}, {} pages, available: {}", b.title, b.pages, b.available);
}
```

```
The Rust Programming Language, 560 pages, available: true
```

*Почему сокращение работает только для двух полей.* Field init shorthand — чисто синтаксическое правило: `имя` разрешено писать вместо `имя: имя`, когда в области видимости есть переменная **ровно с именем поля** (§16.1.1). Параметры `title` и `pages` названы как поля — сокращение применимо. Для `available` никакой переменной нет вообще: значение берётся из литерала `true`, и записать «сокращённо» нечего — сокращать можно только повтор имени, а не отсутствие имени. Правило легко проверить от противного: назовите параметр `t` — и придётся писать `title: t`.

*Почему `title` берут по владению.* Работает правило сигнатур §15.2.1: функция получает значение **по владению**, если оставляет его себе. `build_book` именно это и делает — кладёт строку в поле `title: String`, где та будет жить, пока жива структура (§16.1.1: структура владеет всеми своими данными). Ссылка тут не подойдёт по двум причинам сразу. Во-первых, типы разные: в поле объявлена `String`, а `&String`/`&str` — не `String`, и положить одно вместо другого нельзя. Во-вторых, если бы мы **объявили поле ссылкой**, чтобы «сэкономить», структура стала бы заимствующей — а это E0106 и времена жизни главы 19 (задание З5). Остаётся выбор: либо вызывающий отдаёт готовую `String` (наш вариант), либо строитель принимает `&str` и делает копию сам — см. вариант 2.

**Ответ:** функция — `fn build_book(title: String, pages: u32) -> Book { Book { title, pages, available: true } }`; вызов `build_book(String::from("The Rust Programming Language"), 560)` даёт `The Rust Programming Language, 560 pages, available: true`. Сокращение применимо к `title` и `pages` потому, что это чисто синтаксическая замена `имя: имя` на `имя`, а такие переменные (параметры) существуют; у `available` соответствующей переменной нет — значение пишется литералом `true`, сокращать нечего. Параметр `title` берётся по владению, потому что функция оставляет строку себе — кладёт её в поле владеющего типа `String` (правило сигнатур §15.2.1); ссылку в поле положить нельзя ни по типу (`&str` ≠ `String`), ни по смыслу — заимствующее поле требует времён жизни (E0106, глава 19).

**Вариант 2 (строитель принимает `&str` и копирует сам).** Кто платит за копию — вопрос дизайна, а не правил языка. Файл `s2v2.rs`:

```rust
fn build_book(title: &str, pages: u32) -> Book {
    Book {
        title: String::from(title), // копию делает строитель, а не вызывающий
        pages,
        available: true,
    }
}

fn main() {
    let b = build_book("The Rust Programming Language", 560);
    println!("{}, {} pages, available: {}", b.title, b.pages, b.available);
}
```

```
The Rust Programming Language, 560 pages, available: true
```

*Сравнение.* Вывод тот же, разница — в контракте. Версия с `String` **не копирует ничего**: вызывающий отдаёт готовую строку, и она просто переезжает в поле; зато у вызывающего её больше нет, а литерал приходится оборачивать вручную (`String::from("…")` на месте вызова). Версия с `&str` принимает что угодно строковое — литерал, `&owned`, срез `&owned[4..]` (§15.3.2), — и вызов читается короче, но копия в кучу делается **всегда**, даже когда вызывающему строка была не нужна и он охотно отдал бы её насовсем. Заодно теряется сокращение полей: `title: String::from(title)` — уже не `имя: имя`. Практическое правило: если функция обязана получить владение (кладёт в структуру), честнее просить `String` и позволить вызывающему решить, отдавать или клонировать; `&str`-параметр удобнее в «одноразовых» строителях, которые зовут в основном с литералами.

### Г16.Ч1.З3

**Условие.** Объявите кортежную структуру `Rgb(i32, i32, i32)` и единичную структуру `Sentinel`. Создайте `Rgb(30, 144, 255)`, напечатайте средний канал через индекс `.1`, затем деструктурируйте значение в три переменные и напечатайте их. Чем `Rgb` отличается от простого кортежа `(i32, i32, i32)` — и когда это отличие полезно?

**Решение.** Файл `s3.rs`:

```rust
struct Rgb(i32, i32, i32);
struct Sentinel;

fn main() {
    let c = Rgb(30, 144, 255);
    println!("green channel = {}", c.1);

    let Rgb(r, g, b) = c; // деструктуризация — с именем типа
    println!("r = {r}, g = {g}, b = {b}");

    let _s = Sentinel; // полей нет: у типа только имя
}
```

```
green channel = 144
r = 30, g = 144, b = 255
```

Здесь три конструкции. `Rgb(30, 144, 255)` — вызов имени типа как функции-конструктора; доступ к полям — по индексам `.0`, `.1`, `.2`, как у кортежей §14.2.2. `let Rgb(r, g, b) = c;` — деструктуризация с именем типа; заметьте, она **потребляет** `c`: `Rgb` не помечен `Copy`, а собственная структура по умолчанию перемещается, даже если все её поля — `i32` (§16.1.3). Нам это не мешает — `c` дальше не нужен, — но если бы понадобился, пришлось бы либо навесить `derive(Clone, Copy)`, либо разбирать по индексам. И `let _s = Sentinel;` — единичная структура: у значения нет ни полей, ни данных; подчёркивание в имени просит компилятор не предупреждать о неиспользуемой переменной.

*Чем `Rgb` отличается от кортежа.* Составом — ничем, **именем** — всем. Кортеж `(i32, i32, i32)` структурен: любые две тройки чисел взаимозаменяемы. `Rgb` номинален: это отдельный тип, и подставить вместо него голый кортеж нельзя. Файл `s3_plain.rs` (⛔ не компилируется):

```rust
struct Rgb(i32, i32, i32);

fn brightness(c: &Rgb) -> i32 {
    (c.0 + c.1 + c.2) / 3
}

fn main() {
    let plain = (30, 144, 255); // обычный кортеж того же состава
    println!("{}", brightness(&plain));
}
```

```
error[E0308]: mismatched types
 --> s3_plain.rs:9:31
  |
9 |     println!("{}", brightness(&plain));
  |                    ---------- ^^^^^^ expected `&Rgb`, found `&({integer}, {integer}, {integer})`
  |                    |
  |                    arguments to this function are incorrect
  |
  = note: expected reference `&Rgb`
             found reference `&({integer}, {integer}, {integer})`
note: function defined here
 --> s3_plain.rs:3:4
  |
3 | fn brightness(c: &Rgb) -> i32 {
  |    ^^^^^^^^^^ -------
```

(Запись `{integer}` в отчёте — «целое, конкретный тип которого компилятор ещё не выбрал»: у литералов кортежа нет аннотации, и до момента ошибки тип оставался неопределённым.)

Сведём различия:

| | кортеж `(i32, i32, i32)` | `Rgb(i32, i32, i32)` |
|---|---|---|
| Имя типа | нет, тип задан составом | есть, тип задан именем |
| Совместимость с таким же составом | полная | никакой (E0308) |
| Доступ к полям | `.0` `.1` `.2` | `.0` `.1` `.2` — одинаково |
| Деструктуризация | `let (r, g, b) = t;` | `let Rgb(r, g, b) = c;` |
| Методы | объявить нельзя | `impl Rgb { … }` |

Когда отличие полезно: (1) когда одинаковые по составу данные означают разное — цвет и точка, метры и секунды (З7, З9); (2) когда типу нужны методы — кортежу их не выдать; (3) когда имя типа само по себе документация: `fn fill(c: Rgb)` читается без комментария, `fn fill(c: (i32, i32, i32))` — нет.

**Ответ:** программа — листинг `s3.rs`; вывод — `green channel = 144`, затем `r = 30, g = 144, b = 255`. `Rgb` отличается от кортежа `(i32, i32, i32)` **номинальностью**: это отдельный тип, а не «любая тройка чисел», поэтому голый кортеж туда, где ждут `&Rgb`, не проходит (`error[E0308]: mismatched types`, `expected &Rgb, found &({integer}, {integer}, {integer})`); кроме того, у именованного типа могут быть методы в `impl`, а у кортежа — нет. Отличие полезно, когда одинаковые по составу данные означают разное (цвет против точки, метры против секунд — приём newtype), когда типу нужны собственные методы и когда имя типа заменяет комментарий в сигнатуре. `Sentinel` — единичная структура: полей нет, значение одно, нужна ради имени (систематически — с трейтами, глава 19).

### Г16.Ч1.З4

**Условие.** Для каждого фрагмента предскажите: скомпилируется или нет; если нет — какая ошибка и какое поле в ней названо. Затем проверьте все три (`s1` — экземпляр `Student` из §16.1.1):
а) `let s2 = Student { name: String::from("Bob"), ..s1 }; println!("{}", s1.name);`
б) `let s2 = Student { year: 4, ..s1 }; println!("{}", s1.name);`
в) `let s2 = Student { year: 4, ..s1 }; println!("{}", s1.year);`

**Решение.** Все три фрагмента — один и тот же `..`-синтаксис обновления, и решает всё одно правило §16.1.1: `..s1` работает **как присваивание**, причём **пополевно** — из источника берутся только те поля, которые не названы явно; Copy-поля при этом копируются, не-Copy — перемещаются. Значит, вопрос к каждому фрагменту простой: *уехало ли из `s1` именно то поле, которое мы потом печатаем?*

*а)* Явно названо `name`, поэтому по `..s1` едут только `year: u32` и `active: bool` — оба `Copy` (§15.1.3). Поле `s1.name` не тронуто. Предсказание: компилируется, печатает `Alice`. Файл `s4a.rs`:

```rust
struct Student {
    name: String,
    year: u32,
    active: bool,
}

fn main() {
    let s1 = Student {
        name: String::from("Alice"),
        year: 3,
        active: true,
    };
    let s2 = Student {
        name: String::from("Bob"),
        ..s1
    };
    println!("{}", s1.name);
}
```

```
Alice
```

Попутно компилятор выдаёт два предупреждения — `unused variable: s2` и `fields year and active are never read`: мы построили `s2` и ни разу к нему не обратились. Для протокола опыта это полезно — предупреждения подтверждают, что структура действительно **создана** (иначе о ней не было бы речи), просто не использована.

*б)* Явно назван `year`; значит, по `..s1` едут `name` и `active`, и `name` — `String`, то есть **перемещается**. Печать `s1.name` после переезда — E0382, причём виновником компилятор назовёт не всю `s1`, а поле `s1.name`. Файл `s4b.rs` (⛔ не компилируется):

```rust
    let s2 = Student { year: 4, ..s1 };
    println!("{}", s1.name);
```

```
error[E0382]: borrow of moved value: `s1.name`
  --> s4b.rs:14:20
   |
13 |     let s2 = Student { year: 4, ..s1 };
   |              ------------------------- value moved here
14 |     println!("{}", s1.name);
   |                    ^^^^^^^ value borrowed here after move
   |
   = note: move occurs because `s1.name` has type `String`, which does not implement the `Copy` trait
```

Тот же отчёт, что в примере 2 §16.1.1, с одной косметической разницей: там литерал структуры записан в три строки, и подчёркивание в отчёте многострочное; здесь он в одну — и `value moved here` подчёркивает всю строку.

*в)* Тот же переезд, что и в (б), но печатаем `s1.year` — Copy-поле, которое **скопировалось**, а не уехало. Предсказание: компилируется, печатает `3`. Файл `s4c.rs`:

```
3
```

Предупреждения те же (`unused variable: s2`, `fields name and active are never read`).

Итог в таблице — это и есть содержание «пополевного» отслеживания владения:

| Фрагмент | Названо явно | Едет по `..s1` | Что печатаем | Результат |
|---|---|---|---|---|
| а | `name` | `year`, `active` (Copy — копия) | `s1.name` — не тронуто | `Alice` |
| б | `year` | `name` (**move**), `active` | `s1.name` — уехало | ⛔ E0382, назван `s1.name` |
| в | `year` | `name` (move), `active` | `s1.year` — скопировано | `3` |

**Ответ:** а) компилируется, печатает `Alice`: имя задано явно, по `..s1` уезжают только Copy-поля `year` и `active`, `s1.name` остаётся действительным (плюс предупреждения о неиспользуемой `s2`); б) ⛔ не компилируется — `error[E0382]: borrow of moved value: `s1.name``, в ошибке названо **поле** `s1.name`: оно имеет тип `String`, не реализующий `Copy`, и по `..s1` переехало в `s2`; в) компилируется, печатает `3`: несмотря на переезд `name`, поле `year` — `Copy`, оно скопировалось и осталось доступным. Общее правило: `..s1` — это присваивание, применённое **пополевно** только к тем полям, что не названы явно.

### Г16.Ч1.З5

**Условие.** Структура `struct Label { text: &str }` не компилируется (E0106, §16.1.1). Объясните по `help`-подсказкам компилятора, какие есть два пути починки, почему до главы 19 нам доступен только один (владеющее поле) и как это согласуется с правилом «в полях — владеющие типы». Почините и проверьте.

**Решение.** Сначала воспроизведём отказ — файл `s5_bad.rs` (⛔ не компилируется):

```rust
struct Label {
    text: &str,
}

fn main() {
    let l = Label { text: "hello" };
    println!("{}", l.text);
}
```

```
error[E0106]: missing lifetime specifier
 --> s5_bad.rs:2:11
  |
2 |     text: &str,
  |           ^ expected named lifetime parameter
  |
help: consider introducing a named lifetime parameter
  |
1 ~ struct Label<'a> {
2 ~     text: &'a str,
  |
```

Компилятор жалуется не на «нельзя ссылку в поле», а на **нехватку одного указания**: `expected named lifetime parameter`. Смысл (§16.1.1, и E0106 вы уже видели в §15.2.3): поле-ссылка означает, что структура не владеет текстом, а **заимствует** его у кого-то. Значит, у структуры появляется обязанность, которой нет у владеющей: она не должна пережить того, у кого заняла. Компилятор готов это проверять, но ему нужно имя для связи «структура живёт не дольше, чем данные» — то самое `'a`.

*Два пути починки.* Прямо из отчёта видно оба.

1. **Согласиться на заимствование** и ввести параметр времени жизни — ровно та правка, которую печатает `help`: `struct Label<'a> { text: &'a str }`. Путь рабочий (проверено отдельным прогоном: с этой правкой программа собирается и печатает `hello`), но язык этих аннотаций — глава 19, и мы им ещё не владеем: до неё мы не сможем ни прочитать сигнатуру функции, возвращающей такую структуру, ни объяснить, почему компилятор в каком-то месте откажет.
2. **Отказаться от заимствования** и сделать поле владеющим: `text: String`. Тогда обязанности «не пережить чужие данные» просто не возникает — структура держит свой буфер, и никакие аннотации не нужны.

Второй путь и есть правило §16.1.1 «в полях — владеющие типы»: оно не про экономию, а про **самодостаточность**. Структура с `String` внутри жива сама по себе; её можно вернуть из функции, положить в массив, отдать в другой поток (глава 23) — никто не спросит, откуда взялись байты. Структура с `&str` — это «окно» в чужую память, и всё её время жизни привязано к владельцу. Правило говорит: пока вы не умеете выражать привязку, не создавайте её. Заодно оно согласуется с правилом сигнатур §15.2.1: «оставляешь себе — бери во владение», а поле — это и есть «оставить себе».

*Починка.* Файл `s5.rs`:

```rust
struct Label {
    text: String, // владеющее поле: структура самодостаточна
}

fn main() {
    let l = Label {
        text: String::from("hello"),
    };
    println!("{}", l.text);
}
```

```
hello
```

Обратите внимание на цену: одно `String::from` — копирование пяти байт литерала в кучу при создании. За это структура получает независимость от источника.

**Ответ:** E0106 сообщает, что ссылке в поле не хватает **параметра времени жизни**, потому что поле-ссылка делает структуру заимствующей, и компилятору нужно доказательство, что данные переживут структуру. Пути починки два: (1) ввести аннотацию — `struct Label<'a> { text: &'a str }`, ровно как предлагает `help` (работает, но язык времён жизни — глава 19); (2) сделать поле владеющим — `text: String` (тогда доказывать нечего). До главы 19 доступен только второй, и он же — правило «в полях — владеющие типы»: владеющее поле делает структуру самодостаточной (её можно вернуть, сохранить, передать), тогда как ссылка в поле — это окно в чужую память, требующее выражать связь времён жизни. Починенная программа — листинг `s5.rs`, печатает `hello`.

### Г16.Ч1.З6

**Условие.** Разберите ошибку E0382 из примера 2 §16.1.2 (`consume.rs`): что сообщает note «takes ownership of the receiver `self`»? Почините программу двумя способами, не меняя её вывода: (а) поменяйте приёмник `into_dims` на `&self` (и объясните, почему теперь имя `into_...` стало неудачным); (б) не трогая сигнатур, переставьте вызовы. Какой способ правильнее по смыслу и почему?

**Решение.** Воспроизведём исходную программу целиком — файл `s6_bad.rs` (⛔ не компилируется):

```rust
struct Rect {
    width: u32,
    height: u32,
}

impl Rect {
    fn area(&self) -> u32 {
        self.width * self.height
    }

    fn into_dims(self) -> (u32, u32) {
        (self.width, self.height)
    }
}

fn main() {
    let r = Rect {
        width: 3,
        height: 4,
    };
    let (w, h) = r.into_dims();
    println!("{w} x {h}");
    println!("{}", r.area());
}
```

```
error[E0382]: borrow of moved value: `r`
  --> s6_bad.rs:23:20
   |
17 |     let r = Rect {
   |         - move occurs because `r` has type `Rect`, which does not implement the `Copy` trait
...
21 |     let (w, h) = r.into_dims();
   |                    ----------- `r` moved due to this method call
22 |     println!("{w} x {h}");
23 |     println!("{}", r.area());
   |                    ^ value borrowed here after move
   |
note: `Rect::into_dims` takes ownership of the receiver `self`, which moves `r`
  --> s6_bad.rs:11:18
   |
11 |     fn into_dims(self) -> (u32, u32) {
   |                  ^^^^
```

*Что сообщает note.* Дословно: «`Rect::into_dims` забирает во владение приёмник `self`, и это перемещает `r`». Компилятор объясняет **причину** переезда — не «где-то присвоили», а «вызов метода с приёмником-значением». Приёмник `self` (без `&`) — обычный параметр по значению (§16.1.2), а передача не-`Copy` значения в параметр по значению — перемещение (§15.1.2). Дальше note работает как ссылка на источник проблемы: он указывает на **строку сигнатуры** и подчёркивает именно слово `self`. То есть чинить надо либо контракт метода, либо порядок вызовов — и оба пути в условии.

*(а) Приёмник `&self`.* Файл `s6a.rs`:

```rust
    fn into_dims(&self) -> (u32, u32) {
        (self.width, self.height) // u32 — Copy, читателю этого хватает
    }
```

```
3 x 4
12
```

Работает, и потому что возвращаемые данные — `u32`: они `Copy`, их можно прочитать через разделяемую ссылку и скопировать в кортеж. Будь в структуре поле `String`, читатель вернуть его по значению уже не смог бы — проверено на файле `s6_e0507.rs`: `error[E0507]: cannot move out of `self.title` which is behind a shared reference`, с подсказкой дописать `.clone()`. Но у нас числа, и вопрос не встаёт.

Почему имя `into_dims` теперь неудачно: приставка `into_` в имени — обещание, а обещания в Rust даёт сигнатура. У исходного метода `self` без `&` означал «объект будет потреблён, дальше его не будет», и имя честно предупреждало об этом на месте вызова. У новой версии ничего не потребляется — метод просто читает два поля; имя обещает разрушение, которого нет, и вводит читателя в заблуждение ровно там, где Rust обычно даёт правду без комментариев. Правильное имя для читателя — `dims`.

*(б) Перестановка вызовов.* Сигнатуры не трогаем; чиним порядок: читаем, пока объект цел, а потребляем — последним. Файл `s6b.rs`:

```rust
    let a = r.area(); // читаем, пока прямоугольник цел
    let (w, h) = r.into_dims(); // а теперь потребляем — он больше не нужен
    println!("{w} x {h}");
    println!("{a}");
```

```
3 x 4
12
```

Вывод тот же (порядок печати сохранён — печать отделена от вычисления), а владение больше не нарушено: заимствование в `r.area()` закончилось на той же строке, и к моменту `into_dims` объект свободен.

*Какой способ правильнее по смыслу.* Ответ зависит от того, был ли контракт «потребляю» осознанным.

| | (а) `&self` + переименование | (б) перестановка вызовов |
|---|---|---|
| Что меняем | контракт типа (и имя метода) | порядок операций в `main` |
| Что говорит тип после правки | «прочитать размеры можно сколько угодно раз» | «разобрать объект можно один раз, и он кончится» |
| Когда это правда | `Rect` — две копируемые величины, разрушать нечего | если объект по смыслу *преобразуется* и дальше не нужен |
| Цена | нет | вызывающий обязан следить за порядком |

Для **нашего** `Rect` — двух чисел без ресурсов — правильнее (а) с переименованием в `dims`: потреблять объект незачем, а метод-читатель ничего не запрещает вызывающему. Способ (б) — минимальная правка, не трогающая тип, и он правилен там, где потребление задумано: так устроены `into_`-методы стандартной библиотеки, отдающие наружу внутренний буфер (тогда «объект кончился» — не досадное ограничение, а суть операции). Общее правило прежнее (§16.1.2): `self` пишут осознанно, по умолчанию — `&self`.

**Ответ:** note «takes ownership of the receiver `self`» сообщает причину перемещения: метод объявлен с приёмником-значением, то есть забирает объект во владение, как всякий параметр по значению, — и указывает на строку сигнатуры, подчёркивая слово `self`; после такого вызова `r` больше не существует, поэтому `r.area()` — E0382. Починка (а): `fn into_dims(&self) -> (u32, u32)` — читатель, возвращающий копии двух `u32`; имя `into_...` становится неудачным, потому что приставка обещает потребление объекта, которого больше не происходит, — метод следует назвать `dims`. Починка (б): не меняя сигнатур, вычислить площадь **до** потребляющего вызова (`let a = r.area(); let (w, h) = r.into_dims();`), а печатать в прежнем порядке. Обе версии печатают `3 x 4` и `12`. По смыслу для `Rect` из двух `u32` правильнее (а) с переименованием: разрушать здесь нечего, и контракт «читаю» точнее описывает операцию; (б) верна тогда, когда потребление задумано осознанно (метод *преобразует* объект, и дальше он не нужен).

### Г16.Ч1.З7

**Условие.** `Color(i32, i32, i32)` и `Point3(i32, i32, i32)` устроены одинаково, но `sum_color(&point)` — E0308 (§16.1.1). Сравните с томом I: §8.1.1 отклонял смешение структур с разными тегами, но `int brightness = x;` для «яркости» и «координаты» компилировался всегда. Сформулируйте, что даёт приём «новый тип» (newtype) по сравнению с голыми числами, и приведите два собственных примера пар величин, которые стоит так развести.

Программа собралась и невозмутимо сообщила, что 90 секунд — это 0.09 километра. Вся разница между двумя прогонами — в том, где обнаружилась ошибка: в первом случае её нашёл компилятор и назвал по именам (`expected Meters, found Seconds`), во втором её должен был найти читатель отчёта.

*Чем это отличается от тома I.* В C номинальность существовала, но только для составных типов: §8.1.1 отклонял присваивание структур с разными тегами (`invalid initializer`) — тип структуры задавался её именем, а не составом. А вот **скалярные** величины именовать было нечем: «яркость», «координата», «идентификатор», «индекс» — всё это `int`, и `int brightness = x;` компилировался всегда, каким бы «иксом» ни оказался икс. `typedef int brightness_t;` не спасал: `typedef` в C создаёт синоним, а не новый тип, — совместимость остаётся полной. Поэтому в томе I защита от путаницы величин держалась на именах переменных и внимании.

*Что даёт newtype.* Обёртка `struct Meters(f64)` переносит различие величин **из имён переменных в систему типов**, и дальше работает вся машинерия компилятора:

- **ошибка становится невозможной, а не маловероятной**: перепутанные аргументы — E0308 на этапе сборки, а не странное число в выводе;
- **сигнатура становится документацией**: `fn to_kilometers(m: Meters)` объясняет себя без комментария — сравните с `fn to_kilometers(m: f64)`;
- **имя получает поведение**: на своём типе можно объявить `impl` — методы, конверсии (З9), позже трейты (глава 19); у `f64` этого не отнять и не добавить;
- **правки видны компилятору**: решив однажды хранить расстояние в `Meters`, вы получите список всех мест, где это нарушено, — бесплатно.

Цена — в исходном тексте (обёртка и `.0` при доступе), но не в памяти: замер на эталонной машине (файл `s7_size.rs`, `size_of` — §14.2.2) даёт `f64: 8` и `Meters: 8` — обёртка одного поля занимает столько же, сколько поле. (Раскладку язык не гарантирует — §16.2.1, — но именно эта пара чисел на нашем эталоне воспроизводится.)

*Две собственные пары.* Первая: **`UserId(u64)` и `OrderId(u64)`** — идентификаторы разных сущностей, которые в базе выглядят одинаково; перепутать их в вызове `fn cancel(order: OrderId, by: UserId)` — классическая ошибка, а с newtype она не собирается. Вторая: **`Index(usize)` и `Count(usize)`** — «номер элемента» и «сколько элементов»; в томе I мы держали их в голове весь путь от главы 5 до главы 9, и именно на их смешении рождаются ошибки на единицу (`for (i = 0; i <= n; i++)`) и выход за границу — препарат 1 §13.1.2.

**Ответ:** приём newtype даёт то, чего в C не было для скаляров: **имя, которое компилятор проверяет**. Одинаковые по составу величины становятся несовместимыми типами, поэтому перепутанный аргумент — ошибка сборки (`error[E0308]: mismatched types`, `expected Meters, found Seconds`), а не тихо неверное число (`0.09 km` в версии на голых `f64`); сигнатура функции документирует себя; типу можно выдать методы; а изменение решения о величине компилятор превращает в список мест правки. В C номинальность действовала только для структур с разными тегами (§8.1.1), тогда как `int` и `typedef`-синонимы смешивались свободно. Две пары, которые стоит развести: `UserId(u64)` / `OrderId(u64)` — идентификаторы разных сущностей с одинаковым представлением; `Index(usize)` / `Count(usize)` — «номер элемента» и «количество элементов», путаница которых даёт классические ошибки на единицу. Стоимость приёма — только в исходном тексте: `size_of::<Meters>()` на эталонной машине равен `size_of::<f64>()` (8 байт).

### Г16.Ч1.З8

**Условие.** *(прикладное)* Реализуйте `Rect` с ассоциированной функцией `new(width, height)` и методами `perimeter(&self) -> u32`, `is_square(&self) -> bool`, `stretch(&mut self, factor: u32)` (умножает обе стороны). Повесьте `derive(Debug)`. Контроль: `Rect::new(3, 4)` — периметр 14, не квадрат; после `stretch(2)` — `6 x 8`, периметр 28; `Rect::new(5, 5)` — квадрат. Для каждого метода объясните выбор приёмника.

**Решение.** Файл `s8.rs`:

```rust
#[derive(Debug)]
struct Rect {
    width: u32,
    height: u32,
}

impl Rect {
    fn new(width: u32, height: u32) -> Self {
        Self { width, height }
    }

    fn perimeter(&self) -> u32 {
        2 * (self.width + self.height)
    }

    fn is_square(&self) -> bool {
        self.width == self.height
    }

    fn stretch(&mut self, factor: u32) {
        self.width *= factor;
        self.height *= factor;
    }
}

fn main() {
    let mut r = Rect::new(3, 4);
    println!(
        "{r:?}: perimeter {}, square: {}",
        r.perimeter(),
        r.is_square()
    );

    r.stretch(2);
    println!(
        "{r:?}: perimeter {}, square: {}",
        r.perimeter(),
        r.is_square()
    );

    let sq = Rect::new(5, 5);
    println!(
        "{sq:?}: perimeter {}, square: {}",
        sq.perimeter(),
        sq.is_square()
    );
}
```

```
Rect { width: 3, height: 4 }: perimeter 14, square: false
Rect { width: 6, height: 8 }: perimeter 28, square: false
Rect { width: 5, height: 5 }: perimeter 20, square: true
```

Контроль сходится: 3×4 — периметр 14, не квадрат; после `stretch(2)` — `6 x 8` и периметр 28; 5×5 — квадрат.

*Выбор приёмника — по правилу сигнатур §15.2, применённому к «нулевому параметру» (§16.1.2).*

| Член `impl` | Приёмник | Почему |
|---|---|---|
| `new` | нет (ассоциированная функция) | объекта ещё не существует — его как раз создают; зовётся через тип: `Rect::new(3, 4)` |
| `perimeter` | `&self` | только читает поля; ничего не меняет и не потребляет — значит, разделяемая ссылка |
| `is_square` | `&self` | то же самое: сравнение двух полей |
| `stretch` | `&mut self` | пишет в поля — нужна исключительная ссылка; и у вызывающего обязана быть `mut`-переменная |

Две детали. В `new` возвращаемый тип записан как `Self` — псевдоним типа, которому принадлежит `impl` (§16.1.2); писать `Rect` тоже законно, но `Self` не придётся править при переименовании типа. И `Self { width, height }` — то же сокращение полей, что в З2: параметры названы как поля.

*Типичная неверная попытка: забыть `mut` у переменной.* Право писать складывается из двух: метод просит `&mut self`, а вызывающий должен иметь изменяемую переменную (§15.2.2). Проверено на файле `s10_nomut.rs` из следующего задания (структура другая, механика та же): вызов `c.tick()` для `let c = …` даёт `error[E0596]: cannot borrow `c` as mutable, as it is not declared as mutable` с подсказкой дописать `mut` в объявление. Диагноз тот же, что в З1, только там мешало прямое присваивание полю, а здесь — метод-писатель.

**Ответ:** реализация — листинг `s8.rs`; вывод: `Rect { width: 3, height: 4 }: perimeter 14, square: false`, затем `Rect { width: 6, height: 8 }: perimeter 28, square: false`, затем `Rect { width: 5, height: 5 }: perimeter 20, square: true` — контроль сходится. Приёмники: у `new` его нет (это ассоциированная функция-конструктор — объекта ещё не существует, вызов `Rect::new(3, 4)` через тип и `::`); `perimeter` и `is_square` — `&self`, потому что только читают поля; `stretch` — `&mut self`, потому что пишет в поля, и поэтому у вызывающего переменная обязана быть `mut` (иначе E0596).

**Вариант 2 (потребляющий строитель вместо изменения на месте).** Ту же задачу можно решить, не меняя объект: метод забирает прямоугольник и возвращает новый. Файл `s8v2.rs`:

```rust
    fn stretched(self, factor: u32) -> Self {
        Self {
            width: self.width * factor,
            height: self.height * factor,
        }
    }
```

```rust
fn main() {
    let r = Rect::new(3, 4); // mut не нужен: ничего не меняем
    println!(
        "{r:?}: perimeter {}, square: {}",
        r.perimeter(),
        r.is_square()
    );

    let r = r.stretched(2); // старый прямоугольник потреблён, имя переиспользовано
```

```
Rect { width: 3, height: 4 }: perimeter 14, square: false
Rect { width: 6, height: 8 }: perimeter 28, square: false
Rect { width: 5, height: 5 }: perimeter 20, square: true
```

*Сравнение.* Вывод совпадает дословно, а высказывания разные. `stretch(&mut self)` говорит: «объект один, он изменился» — состояние живёт в переменной, вызывающий обязан объявить её `mut`, старое значение исчезает. `stretched(self) -> Self` говорит: «из старого получен новый» — переменной `mut` не нужно, а исходный прямоугольник **потреблён** (приёмник по значению, §16.1.2), так что случайно воспользоваться устаревшим значением нельзя: E0382 не даст. Плата — новый экземпляр на каждый вызов (для двух `u32` это ничто, для структуры с `String` внутри — реальное перемещение полей) и невозможность менять объект «на месте», когда он лежит в чужой структуре или в коллекции (глава 17). Правило выбора: изменяющий метод — когда объект долгоживущий и его состояние и есть смысл (счётчик, буфер, конфигурация); потребляющий — когда операция читается как преобразование и удобно писать цепочки `Rect::new(3, 4).stretched(2)`. Отдельная выгода второго стиля: приставка `-ed` в имени (`stretched` против `stretch`) сама по себе сообщает, что возвращается новое значение, — та же логика именования, что в З6.

### Г16.Ч1.З9

**Условие.** *(прикладное)* Температуры без путаницы: кортежные структуры `Celsius(f64)` и `Fahrenheit(f64)`, функции `to_fahrenheit(Celsius) -> Fahrenheit` (формула `c * 9/5 + 32`) и `to_celsius(Fahrenheit) -> Celsius`. Повесьте `derive(Debug, Clone, Copy)` — объясните, почему здесь уместны все три. Контроль: `Celsius(100.0)` → `Fahrenheit(212.0)` → обратно `Celsius(100.0)`; `Fahrenheit(98.6)` → `Celsius(37.0)`. Что теперь будет, если перепутать аргументы функций, — и что было бы с голыми `f64`?

**Решение.** Файл `s9.rs`:

```rust
#[derive(Debug, Clone, Copy)]
struct Celsius(f64);

#[derive(Debug, Clone, Copy)]
struct Fahrenheit(f64);

fn to_fahrenheit(c: Celsius) -> Fahrenheit {
    Fahrenheit(c.0 * 9.0 / 5.0 + 32.0)
}

fn to_celsius(f: Fahrenheit) -> Celsius {
    Celsius((f.0 - 32.0) * 5.0 / 9.0)
}

fn main() {
    let boiling = Celsius(100.0);
    let f = to_fahrenheit(boiling);
    let back = to_celsius(f);
    println!("{boiling:?} -> {f:?} -> {back:?}");
    println!("original is still usable: {boiling:?}"); // Copy: источник жив

    let body = Fahrenheit(98.6);
    println!("{body:?} -> {:?}", to_celsius(body));
}
```

```
Celsius(100.0) -> Fahrenheit(212.0) -> Celsius(100.0)
original is still usable: Celsius(100.0)
Fahrenheit(98.6) -> Celsius(37.0)
```

Контроль сходится по обеим строкам: 100 °C → 212 °F → 100 °C, и 98.6 °F → 37.0 °C. Числа с плавающей точкой обычно оставляют «хвосты» (98.6 не представимо в двоичной `f64` точно), но в этой цепочке округления сложились ровно: отдельным прогоном проверены четыре порядка вычисления — `(f - 32.0) * 5.0 / 9.0`, `(f - 32.0) / 9.0 * 5.0`, `(f - 32.0) * (5.0 / 9.0)` и `5.0 / 9.0 * (f - 32.0)` — все четыре печатают `37.0`.

*Почему уместны все три `derive`.*

- **`Debug`** — иначе температуру нечем напечатать: `Display` у своего типа нет (§16.1.2), а контроль в условии сформулирован в терминах `Celsius(100.0)`/`Fahrenheit(212.0)` — это и есть формат отладочной печати кортежной структуры.
- **`Copy`** — тип «плоский»: одно поле `f64`, никаких ресурсов и буферов (§16.1.3). Температура по смыслу — значение, как число: передали в функцию и продолжаем пользоваться исходной переменной (строка `original is still usable` это подтверждает). Без `Copy` вызов `to_fahrenheit(boiling)` **переместил** бы `boiling`, и следующая строка не собралась бы — E0382 на пустом месте.
- **`Clone`** — обязателен технически: `Copy` выводится только в паре с `Clone` (§16.1.3), и это не формальность: `Copy` — «копируй неявно и побитово», `Clone` — «умей копировать по запросу»; второе — более общее умение, первое без него не имеет смысла.

*Если перепутать аргументы.* Файл `s9_swap.rs` (⛔ не компилируется) — подаём фаренгейты туда, где ждут цельсии:

```

13 |     println!("{:?}", to_fahrenheit(body)); // подали фаренгейты вместо цельсиев

   |                      arguments to this function are incorrect

note: function defined here

Ошибка названа своими словами: `expected Celsius, found Fahrenheit`. А теперь то же самое на голых `f64` — файл `s9_bare.rs`:

Программа собралась и выдала «температуру тела 209 градусов». Ни компилятор, ни тип не возражают: для `f64` 98.6 — просто число. Это ровно ситуация §8.1.1 из тома I, где `int brightness = x;` компилировался всегда (см. З7); разница между двумя прогонами — в том, кто ловит описку: машина на этапе сборки или человек, разглядывающий вывод.

**Ответ:** программа — листинг `s9.rs`; вывод `Celsius(100.0) -> Fahrenheit(212.0) -> Celsius(100.0)` и `Fahrenheit(98.6) -> Celsius(37.0)`, контроль сходится. `Debug` нужен, чтобы температуру было чем печатать (`Display` своему типу не выдаётся автоматически); `Copy` уместен, потому что тип плоский — одно поле `f64` без ресурсов, — и температура по смыслу ведёт себя как число: после передачи в функцию исходная переменная остаётся доступной; `Clone` обязателен технически, поскольку `Copy` выводится только в паре с ним. Если перепутать аргументы, программа **не соберётся**: `error[E0308]: mismatched types`, `expected Celsius, found Fahrenheit`. С голыми `f64` та же описка компилируется молча и печатает `209.48` — правдоподобное, но бессмысленное число.

**Вариант 2 (конверсии как методы типов).** Те же формулы можно повесить на сами типы — тогда преобразование читается слева направо, от значения. Файл `s9v2.rs`:

```rust
impl Celsius {
    fn to_fahrenheit(self) -> Fahrenheit {
        Fahrenheit(self.0 * 9.0 / 5.0 + 32.0)
    }
}

impl Fahrenheit {
    fn to_celsius(self) -> Celsius {
        Celsius((self.0 - 32.0) * 5.0 / 9.0)
    }
}

fn main() {
    let boiling = Celsius(100.0);
    let f = boiling.to_fahrenheit();
    let back = f.to_celsius();
    println!("{boiling:?} -> {f:?} -> {back:?}");

    let body = Fahrenheit(98.6);
    println!("{body:?} -> {:?}", body.to_celsius());
}
```

```
Celsius(100.0) -> Fahrenheit(212.0) -> Celsius(100.0)
Fahrenheit(98.6) -> Celsius(37.0)
```

*Сравнение.* Числа те же, разница — в том, где живёт операция. Свободные функции — прямой перенос стиля тома I (`rect_area(&r)`, §16.1.2): имя функции полностью описывает преобразование, но какому типу оно принадлежит, компилятору безразлично. Методы кладут операцию **в пространство имён типа**: `boiling.to_fahrenheit()` невозможно вызвать на `Fahrenheit` — такого метода у него просто нет, и ошибка будет не «перепутанный аргумент» (E0308), а «нет такого метода» (E0599). Побочный выигрыш — цепочки: `Celsius(100.0).to_fahrenheit().to_celsius()` читается по порядку выполнения, тогда как `to_celsius(to_fahrenheit(Celsius(100.0)))` — изнутри наружу. Приёмник взят по значению (`self`, а не `&self`) сознательно: тип `Copy`, копия одного `f64` не дороже ссылки, а вызывающий ничего не теряет. Свободные функции удобнее, когда преобразование не «принадлежит» ни одному из типов (например, симметрично использует оба) или когда тип объявлен не вами: `impl` для чужого типа в своём коде — тема трейтов, глава 19.

### Г16.Ч1.З10

**Условие.** *(прикладное)* Счётчик как тип: `struct Counter { value: i32 }` с ассоциированной функцией `new() -> Self` и методами `tick(&mut self)` (+1) и `report(&self) -> i32`. Прокрутите `tick` пять раз в цикле `for`, напечатайте `count = 5`. Объясните выбор приёмника каждого из трёх членов `impl` по правилу сигнатур §15.2 — и сравните с решением Г15.Ч2.З8 (`tick(n: &mut i32)`): что изменилось, а что осталось тем же?

**Решение.** Файл `s10.rs`:

```rust
struct Counter {
    value: i32,
}

impl Counter {
    fn new() -> Self {
        Self { value: 0 }
    }

    fn tick(&mut self) {
        self.value += 1;
    }

    fn report(&self) -> i32 {
        self.value
    }
}

fn main() {
    let mut c = Counter::new();
    for _ in 0..5 {
        c.tick();
    }
    println!("count = {}", c.report());
}
```

```
count = 5
```

*Выбор приёмника — по правилу §15.2.1 «читает / меняет / потребляет».*

- **`new() -> Self`** — приёмника нет вовсе, и не может быть: объект ещё не существует, функция его создаёт. Это ассоциированная функция, зовётся через тип — `Counter::new()`. Родня `String::from` (§16.1.2).
- **`tick(&mut self)`** — метод пишет в поле, значит просит **исключительную** ссылку. Отсюда `let mut c` в `main`: право на запись складывается из двух — метод должен его попросить, а вызывающий иметь (§15.2.2).
- **`report(&self) -> i32`** — только читает; разделяемой ссылки достаточно. Возврат `i32` — копия значения поля (`i32` — `Copy`), поэтому читателю ничего не мешает вернуть его наружу.

*Типичная неверная попытка — забыть `mut`.* Файл `s10_nomut.rs` (⛔ не компилируется), `let c = Counter::new();`:

```
error[E0596]: cannot borrow `c` as mutable, as it is not declared as mutable
  --> s10_nomut.rs:22:9
   |
22 |         c.tick();
   |         ^ cannot borrow as mutable
   |
help: consider changing this to be mutable
   |
20 |     let mut c = Counter::new(); // забыли mut
   |         +++
```

Обратите внимание, насколько точен диагноз: ошибка не в методе и не в поле, а в **заимствовании** переменной — «нельзя занять `c` изменяемо». Компилятор снова показывает на объявление и предлагает вписать `mut` туда.

*Сравнение с Г15.Ч2.З8.* Там счётчик был голым `i32`, а «метод» — свободной функцией `fn tick(n: &mut i32)`, вызываемой `tick(&mut counter)`.

| | Г15.Ч2.З8: `tick(n: &mut i32)` | Г16.Ч1.З10: `Counter::tick(&mut self)` |
|---|---|---|
| Где состояние | в переменной `counter: i32` | в поле `value` структуры `Counter` |
| Кто отвечает за начальное значение | вызывающий: `let mut counter = 0;` | тип: `Counter::new()` |
| Запись | `*n += 1` — явное разыменование | `self.value += 1` — разыменование подставляет компилятор |
| Вызов | `tick(&mut counter)` — `&mut` пишем руками | `c.tick()` — `&mut` подставляет компилятор (§16.1.2) |
| Кто может звать `tick` | кто угодно с `&mut i32` — любым числом | только `Counter` |
| Право на запись | у вызывающего `let mut` | у вызывающего `let mut` — **то же самое** |

*Что изменилось.* Состояние получило имя и адрес: `i32` стал типом `Counter`, свободная функция — членом `impl`, а `&mut i32` — приёмником `&mut self`. Инициализация переехала из `main` в `new`, то есть перестала быть заботой вызывающего (в C эту роль играли функции-инициализаторы по соглашению, §8.1.2 — здесь это конструкция языка). Исчез явный амперсанд в месте вызова: `c.tick()` вместо `tick(&mut counter)` — компилятор сам подставляет `&mut` к приёмнику, оператора `->` в Rust нет. И сузился круг: `tick` больше не применим к «любому `i32`», а только к счётчику, — то самое пространство имён типа вместо префиксной дисциплины `vec_`/`stack_` из глав 9 и 11.

*Что осталось тем же.* Правило сигнатур: пишущая операция требует исключительной ссылки, читающая — разделяемой. Право на запись по-прежнему выдаёт вызывающий, объявляя переменную `mut`, и по-прежнему невозможно «забыть присвоить результат» — изменение и есть эффект вызова (это был главный довод §15.2 против версии `counter = tick(counter)`). Ссылка живёт только на время вызова, поэтому никаких конфликтов заимствования в цикле не возникает — ни там, ни здесь.

**Ответ:** реализация — листинг `s10.rs`, вывод `count = 5`. Приёмники: `new()` — без приёмника (ассоциированная функция: объекта ещё нет, она его и создаёт; вызов `Counter::new()`); `tick(&mut self)` — исключительная ссылка, потому что метод пишет в поле, а значит переменная у вызывающего обязана быть `mut` (иначе `error[E0596]: cannot borrow `c` as mutable`); `report(&self)` — разделяемая ссылка, потому что метод только читает и возвращает копию `i32`. По сравнению с Г15.Ч2.З8 изменилось то, что состояние стало типом: инициализация ушла в `new`, функция стала методом, `&mut i32` — приёмником `&mut self`, амперсанд в вызове подставляет компилятор (`c.tick()` вместо `tick(&mut counter)`), а сам `tick` теперь применим только к `Counter`, а не к любому `i32`. Осталось тем же правило сигнатур §15.2 (пишет — `&mut`, читает — `&`), необходимость `mut` у вызывающего, невозможность «забыть присвоить результат» и то, что заимствование живёт лишь на время вызова.

## Часть 16.2. Перечисления, Option и сопоставление с образцом

### Г16.Ч2.З1

**Условие.** Объявите `enum Season { Winter, Spring, Summer, Autumn }` с `derive(Debug, Clone, Copy)` и методом `next(self) -> Season` (циклический порядок времён года). Напечатайте пять сезонов подряд, начиная с `Winter` (ожидается `Winter Spring Summer Autumn Winter`, по одному в строке). Затем удалите из `match` любой рукав — предскажите точный текст ошибки и сверьте.

**Решение.** Перечисление из четырёх единичных вариантов, метод — одно выражение `match`, как светофор из примера 1 §16.2.2. Файл `m1.rs`:

```rust
#[derive(Debug, Clone, Copy)]
enum Season {
    Winter,
    Spring,
    Summer,
    Autumn,
}

impl Season {
    fn next(self) -> Season {
        match self {
            Season::Winter => Season::Spring,
            Season::Spring => Season::Summer,
            Season::Summer => Season::Autumn,
            Season::Autumn => Season::Winter,
        }
    }
}

fn main() {
    let mut s = Season::Winter;
    for _ in 0..5 {
        println!("{s:?}");
        s = s.next();
    }
}
```

```
Winter
Spring
Summer
Autumn
Winter
```

Цикл прокручивается пять раз, и пятое значение снова `Winter` — порядок замкнулся. Приёмник `self` по значению здесь законен и дёшев: `Season` помечен `Copy` (данных у вариантов нет), поэтому `s.next()` работает с копией, а исходная переменная остаётся действительной. `derive(Debug)` даёт печать имени варианта через `{:?}`.

Полезно знать, чего `Copy` здесь **не** делает. Без него эта программа тоже собирается — проверено, файл `m1_nocopy.rs` печатает те же пять строк. Причина: `s.next()` переместила бы `s`, но следующая же строка — присваивание `s = …` — заново её инициализирует, а обращений к `s` между переездом и присваиванием нет; перемещение из локальной переменной с последующим присваиванием законно (§15.1.2). `Copy` даёт другое: свободу написать `let t = s.next();`, не потеряв `s`, — и превращает вызов в копирование метки варианта вместо перемещения.

*Предсказание для удалённого рукава.* Уберём `Season::Summer => Season::Autumn`. Ожидаем E0004 с **именем** непокрытого варианта, ссылкой на объявление `enum` и `help`, предлагающим дописать рукав с `todo!()`. Файл `m1_bad.rs` (⛔ не компилируется):

Предсказание подтвердилось дословно. Стоит обратить внимание на одну тонкость: `Season::Summer` встречается в удалённом рукаве **дважды** — слева (как разбираемый образец) и в правой части соседнего рукава `Season::Spring => Season::Summer`. ### Г16.Ч2.З2

**Условие.** Объявите `enum Event` с вариантами всех трёх форм: `Tick`, `Key(char)`, `Move { dx: i32, dy: i32 }` — и функцию `describe(e: Event) -> String`, использующую `format!` для вариантов с данными. Продемонстрируйте все три варианта. Укажите для каждого варианта, чем он был бы в C (§8.2.2): тегом без данных, полем union какого типа?

**Решение.** Файл `m2.rs`:

```rust
enum Event {
    Tick,
    Key(char),
    Move { dx: i32, dy: i32 },
}

fn describe(e: Event) -> String {
    match e {
        Event::Tick => String::from("tick"),
        Event::Key(c) => format!("key '{c}'"),
        Event::Move { dx, dy } => format!("move by ({dx}, {dy})"),
    }
}

fn main() {
    println!("{}", describe(Event::Tick));
    println!("{}", describe(Event::Key('q')));
    println!("{}", describe(Event::Move { dx: 3, dy: -2 }));
}
```

```
tick
key 'q'
move by (3, -2)
```

Три формы вариантов — и три формы образцов, по одной на каждую: `Event::Tick` — просто имя (разбирать нечего); `Event::Key(c)` — привязка содержимого кортежного варианта к свежей переменной `c`; `Event::Move { dx, dy }` — привязка по именам полей структурного варианта. Первый рукав возвращает `String::from("tick")`, а не `format!` — строка постоянная, форматировать нечего; но тип у всех трёх рукавов обязан быть один (`String`), иначе `match`-выражение не соберётся (это проверим в З3).

*Чем каждый вариант был бы в C (§8.2.2).* Ручное размеченное объединение выглядело бы так: `struct event { enum kind tag; union { … } u; };`.

| Вариант Rust | Форма | В C: тег | В C: поле union |
|---|---|---|---|
| `Tick` | единичный | `EV_TICK` | нет — данных у события нет, поле `u` не используется |
| `Key(char)` | кортежный, одно поле | `EV_KEY` | одно символьное поле, `char key;` — но с оговоркой: Rust-`char` (4 байта, юникодный скаляр, §14.2.1) соответствует не C-`char`, а 32-битному типу; C-`char` — это `u8` |
| `Move { dx, dy }` | структурный | `EV_MOVE` | вложенная структура `struct { int dx, dy; } move;` |

И главное различие, ради которого глава и написана: в C тег и объединение — **два соседних поля**, связанные только дисциплиной. Ничто не мешает записать тег `EV_KEY`, а прочитать `u.move.dx` — компилируется и даёт мусор (§8.2.2). В Rust данные достаются **только разбором**: попытка взять их точкой — E0609 (пример 2 §16.2.1), а разбор обязан назвать вариант, то есть сначала доказать, какой он.

**Ответ:** программа — листинг `m2.rs`; вывод — `tick`, `key 'q'`, `move by (3, -2)`. Соответствия с §8.2.2: `Tick` — тег без данных (`EV_TICK`, поле union не используется); `Key(char)` — тег `EV_KEY` плюс поле union символьного типа, причём точным соответствием Rust-`char` служит не C-`char` (это байт, ему отвечает `u8`), а 32-битный тип, поскольку Rust-`char` — четырёхбайтовый юникодный скаляр (§14.2.1); `Move { dx, dy }` — тег `EV_MOVE` плюс поле union со вложенной структурой `struct { int dx, dy; }`. Разница не в раскладке, а в гарантии: в C тег и union связаны дисциплиной программиста, и чтение «не того поля» компилируется; в Rust данные варианта доступны только через разбор, назвавший вариант.

### Г16.Ч2.З3

**Условие.** Напишите `match` по числу `n: i32`: для 0 — `"zero"`, для 1 — `"one"`, для остальных — строка вида `"many: N"` (используйте привязку-уловитель `other` и `format!`). Затем замените уловитель на `_ => ()` — и объясните, почему программа перестала компилироваться (подсказка: match — выражение; каких типов стали рукава?). Проверьте оба варианта.

**Решение.** Файл `m3.rs`:

```rust
fn classify(n: i32) -> String {
    match n {
        0 => String::from("zero"),
        1 => String::from("one"),
        other => format!("many: {other}"),
    }
}

fn main() {
    println!("{}", classify(0));
    println!("{}", classify(1));
    println!("{}", classify(42));
}
```

```
zero
one
many: 42
```

По `i32` перебрать все значения рукавами невозможно — их миллиарды, — поэтому исчерпывающесть обеспечивает уловитель. Взят именованный (`other`), а не `_`, потому что значение нужно внутри рукава: `format!("many: {other}")`. Тело `classify` — одно `match`-выражение без `return`: значение выбранного рукава и есть значение функции (§14.2.3).

*Замена уловителя на `_ => ()`.* Файл `m3_bad.rs` (⛔ не компилируется):

```rust
fn classify(n: i32) -> String {
    match n {
        0 => String::from("zero"),
        1 => String::from("one"),
        _ => (),
    }
}
```

```
error[E0308]: `match` arms have incompatible types
 --> m3_bad.rs:5:14
  |
2 | /     match n {
3 | |         0 => String::from("zero"),
  | |              -------------------- this is found to be of type `String`
4 | |         1 => String::from("one"),
  | |              ------------------- this is found to be of type `String`
5 | |         _ => (),
  | |              ^^ expected `String`, found `()`
6 | |     }
  | |_____- `match` arms have incompatible types
```

Причина названа в заголовке: **рукава разных типов**. `match` — не оператор, а выражение (§16.2.2), и у выражения ровно один тип; значит, все рукава обязаны давать одно и то же. Первые два дают `String`, третий — `()`, единичный тип (§14.2.2): «ничего». Компилятор аккуратно показывает, как он рассуждал: два рукава «found to be of type `String`» задали ожидание, третий его нарушил — `expected String, found ()`.

Обратите внимание, что идиома `_ => ()` сама по себе законна — в примере 4 §16.2.2 она работала: там `match` стоял **оператором**, его значение никому не было нужно, и все рукава давали `()`. Ошибка не в `()`, а в смешении: в одном `match` нельзя одновременно «вычислять строку» и «ничего не делать». Если по смыслу для остальных чисел значения действительно нет — значит, и функция должна возвращать не `String`, а что-то, умеющее выразить отсутствие: `Option<String>` с рукавом `_ => None` (§16.2.3).

**Ответ:** рабочая версия — листинг `m3.rs`, печатает `zero`, `one`, `many: 42`. С уловителем `_ => ()` программа **не компилируется**: `error[E0308]: `match` arms have incompatible types` — `expected `String`, found `()``. Причина: `match` — выражение, у него один тип, поэтому все рукава обязаны давать одинаковый тип; первые два рукава дают `String`, а `()` — единичный тип «ничего», и совместить их нельзя. Сама по себе идиома `_ => ()` законна там, где значение `match` никому не нужно и все рукава дают `()`; здесь же значение — возвращаемое значение функции.

### Г16.Ч2.З4

**Условие.** Почему `let d: Direction = 2;` — E0308, хотя в C `enum color c = 42;` компилировался без предупреждений (§8.2.1)? Объясните, что означает «закрытый тип» для надёжности разбора: чем список значений, известный компилятору полностью, лучше «int с именованными константами»? Где в C эта открытость стреляла (вспомните донумерацию и `-Wswitch`)?

**Решение.** Сперва воспроизведём сторону C — файл `m4.c`, эталонный компилятор тома I, `-std=c17 -Wall -Wextra`:

```c
#include <stdio.h>

enum color { RED, GREEN, BLUE };
enum code { OK = 3, WARN, ERR = 1, INFO };

static const char *name(enum color c)
{
    switch (c) {                 /* ветки BLUE нет — предупреждение -Wswitch */
    case RED:
        return "red";
    case GREEN:
        return "green";
    }
    return "???";
}

int main(void)
{
    enum color c = 42;           /* значения 42 в списке вариантов нет */
    printf("c = %d, name = %s\n", (int)c, name(c));
    printf("OK=%d WARN=%d ERR=%d INFO=%d\n", OK, WARN, ERR, INFO);
    return 0;
}
```

Сборка и запуск:

```
m4.c: In function 'name':
m4.c:8:5: warning: enumeration value 'BLUE' not handled in switch [-Wswitch]
    8 |     switch (c) {                 /* ветки BLUE нет — предупреждение -Wswitch */
      |     ^~~~~~
```

```
c = 42, name = ???
OK=3 WARN=4 ERR=1 INFO=2
```

Три факта в одном прогоне. `enum color c = 42;` — **ни одного диагностического сообщения** даже с `-Wall -Wextra`: значения 42 в списке нет, но компилятор не возражает. Донумерация `{OK = 3, WARN, ERR = 1, INFO}` даёт 3, 4, 1, 2 — «следующий = предыдущий + 1» независимо от того, занято ли уже это число (у `INFO` и `WARN` значения разные, но обе «дырки» в списке доступны любому `int`). И `-Wswitch` отработал: непокрытый `BLUE` — предупреждение, **сборка продолжилась**, программа отработала и напечатала `???`.

*Почему в Rust это E0308.* Потому что `enum` в Rust — **закрытый номинальный тип** (§16.2.1), а не «`int` с именованными константами». Множество его значений задано объявлением исчерпывающе: у `Direction` их ровно четыре, и целое `2` в этом множестве не лежит — не потому, что «двойка не разрешена», а потому, что целые числа вообще не входят в тип `Direction`. Дискриминант (внутренний номер варианта) у значений есть, но он — деталь представления, а не сам тип; в C всё было наоборот: тип **был** целым, а имена — сахаром над числами.

*Что даёт закрытость для надёжности разбора.* Когда список значений известен компилятору полностью, он может **проверять полноту** — то самое E0004 (§16.2.2, З1, З5, З8). Цепочка простая:

1. значений вне списка не бывает → значит, перечислить все случаи возможно в принципе;
2. компилятор знает список → значит, он может сверить с ним ваши рукава;
3. непокрытый вариант — не повод для подозрения, а доказанная дыра → значит, это ошибка, а не предупреждение.

В C ни один шаг не проходит: значения вне списка возможны (`c = 42`), поэтому «перечислить все» нельзя даже теоретически — отсюда и `default`, и `-Wswitch` в статусе предупреждения. Практический эффект виден при **росте** программы: добавили вариант в enum — Rust выдаёт список всех мест, где разбор перестал быть полным, и не собирает программу, пока вы их не пройдёте; C в лучшем случае напишет несколько предупреждений в общий поток вывода сборки.

*Где открытость стреляла в томе I.* Три места, все в §8.2:

- **Значение вне списка.** `enum color c = 42;` — молча; дальше такое значение доезжает до `switch`, проваливается в `default` (или мимо всех `case`, как у нас, — функция вернула `???`) и живёт в программе «нормальным» цветом.
- **Донумерация.** `{A = 3, B, C = 1, D}` → 3, 4, 1, 2: значения назначаются «предыдущее + 1» и легко **сталкиваются** — два перечислителя с одним числом становятся неразличимы, а `switch` с двумя такими `case` не соберётся вовсе («duplicate case value»). В Rust нумерация внутренняя, а явные дискриминанты разрешены только перечислению без данных (E0732, §16.2.1).
- **`switch` с `default`.** Как только в разборе появляется `default`, `-Wswitch` **замолкает** (§8.2: «`default` формально покрывает всё»), и добавленный вариант тихо уезжает в «остальное». Оттуда и правило тома I — разбирая enum, перечислять все `case` и не писать `default`; в Rust то же правило звучит как «не глушите E0004 уловителем `_`» (§16.2.2), но теперь его нарушение видно, а соблюдение проверяется.

**Ответ:** `let d: Direction = 2;` — E0308 потому, что в Rust перечисление есть **закрытый номинальный тип**: множество его значений исчерпывающе задано объявлением, целые числа в него не входят, а дискриминант — внутренняя деталь представления, а не сам тип. В C `enum` — это `int` с именованными константами, поэтому `enum color c = 42;` собирается без единого предупреждения даже с `-Wall -Wextra` (проверено: программа печатает `c = 42, name = ???`). Закрытость даёт надёжность разбора: раз список значений известен целиком, компилятор может доказать неполноту `match` — и делает непокрытый вариант ошибкой E0004, а не предупреждением; при добавлении варианта в enum это превращается в готовый список мест правки. В C открытость стреляла трижды: значение вне списка проходило молча; донумерация назначала числа «предыдущее + 1» и приводила к столкновениям (`{OK = 3, WARN, ERR = 1, INFO}` → 3, 4, 1, 2); а `-Wswitch` — единственная частичная страховка — вообще не срабатывал при наличии `default` и в любом случае не останавливал сборку.

### Г16.Ч2.З5

**Условие.** Разберите сообщение E0004 для пропущенной ветки `None` (§16.2.2, `nonexh_opt.rs`): что компилятор знает о вашем `match`, что предлагает `help`. Объясните, почему правка `_ => todo!()` формально проходит, но хуже явной ветки `None => ...`, и сравните всю ситуацию с `-Wswitch` из §8.2.1: предупреждение против отказа — в чём практическая разница для большой программы?

**Решение.** Воспроизведём отказ — файл `m5.rs` (⛔ не компилируется):

```rust
fn describe(x: Option<i32>) -> String {
    match x {
        Some(v) => format!("value {v}"),

fn main() {
    println!("{}", describe(Some(7)));
    println!("{}", describe(None));
}
```

```
error[E0004]: non-exhaustive patterns: `None` not covered
 --> m5.rs:2:11
  |
2 |     match x {
  |           ^ pattern `None` not covered
  |
note: `Option<i32>` defined here
 --> …/core/src/option.rs:597:0
 ::: …/core/src/option.rs:601:4

  = note: not covered
  = note: the matched value is of type `Option<i32>`
help: ensure that all possible cases are being handled by adding a match arm with a wildcard pattern or an explicit pattern as shown

*Что компилятор знает о вашем `match`.* Из отчёта видно всё его рассуждение по шагам:

1. **тип разбираемого значения** — `the matched value is of type `Option<i32>``;
2. **полный список вариантов этого типа** — причём `Option` объявлен не вами, а в стандартной библиотеке: `note: `Option<i32>` defined here` со ссылкой на `option.rs`. Компилятору безразлично, чей это тип: закрытость — свойство перечисления, а не авторства;
3. **какие варианты покрыты вашими рукавами** и, следовательно, **какой не покрыт** — `pattern `None` not covered`, с точным именем;

*Что предлагает `help`.* Не абстрактный совет, а готовую правку: «добавьте рукав — с уловителем или явным образцом, как показано» — и печатает две строки будущего кода, где новый рукав `None => todo!()` встаёт следом за существующим. Макрос `todo!()` — заглушка «допишу позже»: он позволяет коду собраться, а при попадании в эту ветку паникует.

*Почему `_ => todo!()` формально проходит, но хуже.* Проверим на опыте — файл `m5_todo.rs`, где вместо явной ветки стоит уловитель с заглушкой:

```rust
fn describe(x: Option<i32>) -> String {
    match x {
        Some(v) => format!("value {v}"),
        _ => todo!(),
    }
}
```

Собирается (исчерпывающесть восстановлена — уловитель покрывает всё) и запускается:

```
value 7

thread 'main' (18576) panicked at m5_todo.rs:4:14:
not yet implemented
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Программа не сообщила о проблеме на сборке — она сообщила о ней **в работе**, аварийной остановкой (код возврата 101; номер потока в скобках служебный, §14.2.2). Сравните с честной веткой — файл `m5_ok.rs`:

```rust
        None => String::from("no value"),
```

```
value 7
no value
```

Разница между двумя правками — в том, что именно вы сказали компилятору:

| | `_ => todo!()` | `None => String::from("no value")` |
|---|---|---|
| Что сказано о случае `None` | «разберусь потом» | «вот что делать» |
| Когда узнаем о недоделке | при запуске, если ветка встретится | никогда — её нет |
| Что будет с новым вариантом типа | молча уедет в `_` | E0004 в этом месте |
| Что видно на ревью | заглушка (это плюс `todo!` перед голым `_`) | законченная логика |

Отдельно стоит различать `_ => todo!()` и просто `_ => …`. Заглушка хотя бы честна: она громко падает и оставляет метку. Уловитель с «разумным умолчанием» (`_ => String::from("")`) хуже обоих вариантов — он выглядит законченным кодом и **навсегда** гасит E0004 в этом месте: новый вариант перечисления молча уедет в «остальное» (§16.2.2, «каждый `_` по enum — это будущий вариант, молча провалившийся в остальное»).

*Предупреждение против отказа — практическая разница.* На маленькой программе разницы почти нет: предупреждение видно, вы его читаете и чините. Всё меняется с масштабом.

- **Предупреждения теряются.** Сборка большого проекта печатает сотни строк; чужие предупреждения (из зависимостей, генерированного кода) заглушают ваши. Отказ невозможно не заметить — сборки просто нет.
- **Предупреждение не блокирует поставку.** Программа с забытой веткой соберётся, пройдёт тесты (если тест на этот вариант не написан — а его обычно и нет, вариант-то новый) и уедет к пользователю. Отказ останавливает конвейер до правки.
- **`-Wswitch` вдобавок хрупок.** Он молчит при наличии `default` (§8.2) — а `default` в большом коде пишут почти всегда, «на всякий случай». E0004 обойти можно тем же способом (уловитель `_`), но это **видимое** решение в исходном тексте, а не побочный эффект оборонительного стиля.
- **Главное — направление работы.** Добавили вариант в enum: в Rust компилятор выдаёт полный список мест, где разбор перестал быть полным, и вы идёте по нему как по чеклисту; в C вы ищете эти места сами — грепом по имени типа, надеясь, что нигде не написан `default`.

**Ответ:** из сообщения E0004 видно, что компилятор знает: тип разбираемого значения (`the matched value is of type `Option<i32>``), полный список его вариантов — даже для типа из стандартной библиотеки (`note: `Option<i32>` defined here` со ссылкой на `option.rs`), какой именно вариант не покрыт (`pattern `None` not covered`) и в каком месте программы (строка `match x`). `help` предлагает готовую правку — добавить рукав с уловителем или явным образцом — и печатает строки будущего кода с `None => todo!()`. Правка `_ => todo!()` формально проходит: исчерпывающесть восстановлена, программа собирается — но проблема лишь перенесена со сборки на выполнение: прогон печатает `value 7`, а затем паникует `not yet implemented`. Кроме того, уловитель `_` глушит E0004 в этом месте навсегда: следующий добавленный вариант молча уедет в «остальное», тогда как явная ветка `None => …` и решает случай окончательно, и оставляет проверку полноты работать. Практическая разница с `-Wswitch` для большой программы: предупреждение теряется в потоке сборки, не блокирует поставку и вдобавок не выдаётся вовсе при наличии `default`, поэтому забытая ветка спокойно доезжает до пользователя; отказ компиляции остановит сборку и превратит добавление варианта в готовый список мест правки.

### Г16.Ч2.З6

**Условие.** Фрагмент `let x: i32 = 5; let y: Option<i32> = Some(5); let sum = x + y;` не компилируется (E0277). Объясните по сообщению, чего именно не существует, и почините тремя способами с разной семантикой: (а) `match`; (б) `unwrap_or(0)`; (в) сложение только внутри ветки `Some` (`if let`). Для каждого способа сформулируйте, что происходит при `y == None`.

**Решение.** Файл `m6_bad.rs` (⛔ не компилируется); хвост подсказок — список типов, реализующих `Add`, — сокращён:

```
error[E0277]: cannot add `Option<i32>` to `i32`
 --> m6_bad.rs:4:17
  |
4 |     let sum = x + y;
  |                 ^ no implementation for `i32 + Option<i32>`
  |
  = help: the trait `Add<Option<i32>>` is not implemented for `i32`
```

*Чего именно не существует.* Не «переменной», не «значения» — **операции**. Компилятор говорит: «нет реализации для `i32 + Option<i32>`», то есть у типа `i32` не заявлено умение складываться с `Option<i32>` (трейт `Add<Option<i32>>`). Сложение в Rust не встроено в синтаксис «для всего, что похоже на числа»: `+` работает ровно для тех пар типов, для которых умение объявлено, — и пары «число и может-быть-число» среди них нет. Это и есть механизм из §16.2.3: `Option<T>` и `T` — разные типы, и до тех пор, пока вы не разобрали оба случая, числа у вас в руках нет. Обратите внимание, что в отчёте нет ни слова про `None`: компилятор не знает и знать не хочет, что лежит в `y` прямо сейчас, — он рассуждает о **типах**, а значит, ошибка не зависит от данных.

Три починки — три разных ответа на вопрос «а что делать, если значения нет».

*(а) `match` — отсутствие протекает насквозь.* Файл `m6a.rs`:

```rust
fn add(x: i32, y: Option<i32>) -> Option<i32> {
    match y {
        Some(n) => Some(x + n),
        None => None, // нечего складывать — результата тоже нет
    }
}

fn main() {
    println!("{:?}", add(5, Some(5)));
    println!("{:?}", add(5, None));
}
```

```
Some(10)
None
```

Это `plus_one` из §16.2.3, только с двумя слагаемыми: складываем, если есть что; если нет — честно сообщаем наверх, что результата нет. Отсутствие не превращается в число, а **распространяется**: следующий слой снова обязан его разобрать.

*(б) `unwrap_or(0)` — умолчание.* Файл `m6b.rs`:

```rust
fn add(x: i32, y: Option<i32>) -> i32 {
    x + y.unwrap_or(0) // нет значения — считаем его нулём
}

fn main() {
    println!("{}", add(5, Some(5)));
    println!("{}", add(5, None));
}
```

```
10
5
```

Одно выражение, результат всегда `i32`. При `None` слагаемое считается нулём — и в этой задаче умолчание безобидно: ноль — нейтральный элемент сложения, `5 + 0 == 5` не искажает смысл. Важно, что решение **озвучено** в коде: слово `unwrap_or(0)` видно на ревью, в отличие от C-шной привычки молча подставить 0 в неинициализированную переменную.

*(в) `if let` — считаем только когда есть что считать.* Файл `m6c.rs`:

```rust
fn report(x: i32, y: Option<i32>) {
    if let Some(n) = y {
        println!("sum = {}", x + n);
    } else {
        println!("nothing to add"); // сложения просто не происходит
    }
}

fn main() {
    report(5, Some(5));
    report(5, None);
}
```

```
sum = 10
nothing to add
```

Здесь сложение вообще не выполняется при `None` — ветка `else` описывает другое поведение, а не другое число. Заметьте, что функция ничего не возвращает: это осознанно. Попытка вернуть из `if let`-выражения число в одной ветке и «ничего» в другой упёрлась бы ровно в ошибку из З3 — у ветвей одного выражения должен быть один тип.

Сведём:

| Способ | Тип результата | При `y == None` | Когда уместен |
|---|---|---|---|
| (а) `match` | `Option<i32>` | результата нет: возвращается `None` | внутри логики: пусть каждый слой честно видит «может не быть» |
| (б) `unwrap_or(0)` | `i32` | слагаемое считается нулём, сумма равна `x` | когда у отсутствия есть осмысленное умолчание (для сложения ноль нейтрален) |
| (в) `if let` | нет (действие) | сложения не происходит, выполняется ветка `else` | на границе программы: печать, отчёт, ветвление поведения |

**Ответ:** E0277 сообщает, что не существует **операции**: `no implementation for `i32 + Option<i32>``, то есть у `i32` не реализован трейт `Add<Option<i32>>` — «может-быть-число» не является числом и складываться с ним не умеет; заметьте, что вывод не зависит от того, что лежит в `y`, — компилятор рассуждает о типах. Починки: (а) `match y { Some(n) => Some(x + n), None => None }` — при `None` результата нет, возвращается `None`, и отсутствие протекает к вызывающему (печатает `Some(10)` и `None`); (б) `x + y.unwrap_or(0)` — при `None` слагаемое считается нулём и сумма равна `x` (печатает `10` и `5`); (в) `if let Some(n) = y { … } else { … }` — при `None` сложение не выполняется вовсе, работает ветка `else` (печатает `sum = 10` и `nothing to add`). Первый способ уместен внутри логики, второй — когда у отсутствия есть осмысленное умолчание, третий — на границе программы, где надо не вычислить число, а по-разному поступить.

### Г16.Ч2.З7

**Условие.** Не запуская, предскажите вывод `opt_size.rs` (§16.2.3) — размеры `i32`, `Option<i32>`, `&i32`, `Option<&i32>`. Объясните: откуда лишние 4 байта у `Option<i32>`; почему `Option<&i32>` не стоит ничего и почему это гарантия, а не удача (какое битовое значение «свободно» у ссылки — §15.2.1?). Проверьте запуском.

**Решение.** *Предсказание.* Рассуждаем по каждой строке.

- `i32` — 4 байта по определению: ширина записана в имени типа (§14.2.1).
- `Option<i32>` — **8**. Значение должно уметь отвечать на вопрос «`Some` или `None`?», а все 2³² битовых комбинаций `i32` уже заняты числами — свободной комбинации, которой можно было бы обозначить `None`, нет. Значит, нужен отдельный дискриминант (§16.2.1). Одного байта хватило бы, но `i32` требует выравнивания по 4 байта, поэтому размер округляется вверх: 4 (данные) + 1 (метка) → 8 с выравниванием.
- `&i32` — **8**: это адрес, а на x86-64 адрес — 8 байт.
- `Option<&i32>` — **8**, столько же, сколько голая ссылка. У ссылки есть «невозможное» битовое значение: ссылки в Rust никогда не бывают нулевыми (§15.2.1), то есть комбинация «все нули» типу `&i32` не принадлежит. Компилятор занимает её под `None` — и лишний байт не нужен.

Проверка — файл `m7.rs`:

```rust
fn main() {
    println!("i32:          {}", std::mem::size_of::<i32>());
    println!("Option<i32>:  {}", std::mem::size_of::<Option<i32>>());
    println!("&i32:         {}", std::mem::size_of::<&i32>());
    println!("Option<&i32>: {}", std::mem::size_of::<Option<&i32>>());
}
```

```
i32:          4
Option<i32>:  8
&i32:         8
Option<&i32>: 8
```

Предсказание сошлось по всем четырём строкам (числа совпадают и с §16.2.3).

*Откуда лишние 4 байта у `Option<i32>`.* Из необходимости различать варианты плюс выравнивание. Дискриминанту достаточно одного бита по смыслу и одного байта по устройству, но структура с полем `i32` обязана быть выровнена на 4 байта, поэтому 5 «содержательных» байт округляются до 8. Отсюда и оговорка: это числа **нашей** платформы; точную раскладку язык не обещает и вправе её оптимизировать (§16.2.1).

*Почему `Option<&i32>` бесплатен и почему это гарантия.* Механика — та самая niche-оптимизация (§16.2.3): компилятор ищет у вкладываемого типа битовую комбинацию, которая ему **запрещена**, и кодирует ею `None`. У ссылки такая комбинация есть, и она ровно одна и та же для всех ссылок — нулевой адрес: ссылка всегда указывает на действительное значение, нулевых ссылок в языке не существует (§15.2.1). Именно поэтому речь идёт не об удаче конкретного компилятора, а о **гарантии**: правило «ссылка не бывает нулевой» — часть языка, а не свойство сборки, и обещание «`Option<&T>` того же размера, что `&T`» документировано для `Option` (R9, §16.2.3). Практический вывод перевёрнут по сравнению с C: раньше «указатель, который может быть нулём» был дешёвой, но опасной конструкцией, а «честная проверка» — вопросом дисциплины; теперь `Option<&T>` стоит столько же, сколько указатель, но разыменовать «ноль» не даст компилятор — NULL остался в машинном коде и исчез из системы типов.

**Ответ:** предсказание и результат совпадают: `i32: 4`, `Option<i32>: 8`, `&i32: 8`, `Option<&i32>: 8`. Лишние 4 байта у `Option<i32>` — это дискриминант плюс выравнивание: у `i32` заняты все битовые комбинации, свободной для обозначения `None` нет, поэтому метка варианта хранится отдельно (одного байта достаточно, но выравнивание по 4 байта округляет 4 + 1 до 8). `Option<&i32>` не стоит ничего, потому что у ссылки есть запрещённое битовое значение — нулевой адрес: ссылки в Rust никогда не бывают нулевыми (§15.2.1), и компилятор кодирует этой комбинацией `None` (niche-оптимизация). Это гарантия, а не удача, потому что запрет нулевых ссылок — правило языка, а совпадение размеров `Option<&T>` и `&T` документировано (R9); на удачу компилятора здесь ничего не оставлено. Числа — эталонной машины (x86-64); точную раскладку язык не обещает (§16.2.1).

### Г16.Ч2.З8

**Условие.** *(прикладное)* Мини-калькулятор: `enum Op { Add(i32, i32), Sub(i32, i32), Neg(i32) }` и функция `eval(op: Op) -> i32` одним `match`-выражением (без `return`). Контроль: `Add(2, 3)` → 5, `Sub(10, 4)` → 6, `Neg(7)` → −7. Добавьте вариант `Mul(i32, i32)` в enum, **не** трогая `eval`, — предскажите реакцию компилятора, проверьте, затем дочините.

**Решение.** Файл `m8.rs`:

```rust
enum Op {
    Add(i32, i32),
    Sub(i32, i32),
    Neg(i32),
}

fn eval(op: Op) -> i32 {
    match op {
        Op::Add(a, b) => a + b,
        Op::Sub(a, b) => a - b,
        Op::Neg(a) => -a,
    }
}

fn main() {
    println!("{}", eval(Op::Add(2, 3)));
    println!("{}", eval(Op::Sub(10, 4)));
    println!("{}", eval(Op::Neg(7)));
}
```

```
5
6
-7
```

Контроль сошёлся. Тело `eval` — одно выражение: `match` стоит последним (и единственным) выражением функции, поэтому `return` не нужен, а тип каждого рукава — `i32`. Кортежные варианты с двумя полями разбираются образцом `Op::Add(a, b)`: два имени, обе привязки — свежие переменные.

*Предсказание для добавленного `Mul`.* Перечисление выросло, разбор — нет; значит, `match` перестал быть исчерпывающим, и компилятор откажется собирать программу с E0004, назвав непокрытым `Op::Mul(_, _)` — с подчёркиваниями вместо данных, потому что не покрыт вариант целиком, при любых значениях полей. note: `Op` defined here
  --> m8_mul.rs:1:6

 1 | enum Op {
   |      ^^

   |     --- not covered

Предсказание подтвердилось, включая форму `Op::Mul(_, _)`. Это и есть «страховка на вырост» из §16.2.2 в действии: изменение **типа** мгновенно превратилось в список мест, где нужно принять решение, — и обратите внимание, что список компилятор выдал бы даже в чужом коде, который вы никогда не открывали.

*Починка.* Дописываем рукав — файл `m8_fix.rs`:

        Op::Mul(a, b) => a * b,

После добавления `Mul(i32, i32)` в перечисление, но не в разбор, программа **перестаёт собираться**: `error[E0004]: non-exhaustive patterns: `Op::Mul(_, _)` not covered` — с указанием на строку `match op`, сноской на объявление `enum` (подчёркнут вариант `Mul`, `not covered`) и готовой правкой `Op::Mul(_, _) => todo!()` в `help`. ### Г16.Ч2.З9

**Условие.** *(прикладное)* Перепишите `find` из витрины §13.2.2 доступными нам средствами: `find_index(xs: &[i32], needle: i32) -> Option<usize>` индексным циклом (без `iter().enumerate()`). Прогоните на `[3, 7, 42, 9]`: поиск 42 (есть) и 100 (нет) — разбор `match`-ем; затем покажите вариант с `unwrap_or(0)` и объясните, чем он опасен именно для *индекса* (0 — валидная позиция!) и когда умолчание всё же уместно.

**Решение.** Файл `m9.rs`:

```rust
fn find_index(xs: &[i32], needle: i32) -> Option<usize> {
    for i in 0..xs.len() {
        if xs[i] == needle {
            return Some(i);
        }
    }
    None
}

fn main() {
    let xs = [3, 7, 42, 9];

    match find_index(&xs, 42) {
        Some(i) => println!("42 is at index {i}"),
        None => println!("42 is not in the array"),
    }
    match find_index(&xs, 100) {
        Some(i) => println!("100 is at index {i}"),
        None => println!("100 is not in the array"),
    }

    // умолчание для индекса: два разных исхода дают одно и то же число
    println!("index of 100 or 0: {}", find_index(&xs, 100).unwrap_or(0));
    println!("index of 3 or 0:   {}", find_index(&xs, 3).unwrap_or(0));
}
```

```
42 is at index 2
100 is not in the array
index of 100 or 0: 0
index of 3 or 0:   0
```

Сигнатура — вся суть задания. Параметр `xs: &[i32]` — срез (§15.3.1): функция работает и с массивом, и с его частью, и ничего не копирует. Возврат `Option<usize>` говорит правду: «может не быть». Тело — индексный цикл `for i in 0..xs.len()`, ранний `return Some(i)` при совпадении и `None` последним выражением, если цикл дошёл до конца.

Сравните с тем I. Там `find` возвращал `int` и сообщал о неудаче значением −1 (главы 5, 9): «нет ответа» и «ответ» были значениями одного типа, и различить их можно было только по договорённости в комментарии. Здесь различие вынесено в тип: `usize` из `Option<usize>` не достать, не разобрав оба случая, — а разбор `match`-ем не даст забыть `None` (E0004, З5). Заодно исчезла и старая мелочь: `usize` беззнаковый, «отрицательный индекс» в нём не выражается — sentinel −1 не был бы доступен, даже если бы мы захотели.

*Чем опасен `unwrap_or(0)` именно для индекса.* Две последние строки вывода — готовая иллюстрация: `index of 100 or 0: 0` и `index of 3 or 0: 0`. Числа совпали, а смыслы противоположны — «в массиве нет сотни» и «тройка стоит на нулевой позиции». Умолчание уничтожает различие, ради которого мы и заводили `Option`: для индекса `0` — не «пусто», а **валидная позиция**, причём самая частая. Дальше это разъезжается в две беды: программа читает `xs[0]` вместо «ничего не найдено» (то есть возвращает чужие данные, не выходя за границы и не паникуя — тихая логическая ошибка, которую не поймает ни один санитайзер) и «находит» отсутствующее — ровно поведение C-шного `find`, вернувшего −1 в код, который забыл проверить (§13.1.2).

*Когда умолчание всё же уместно.* Когда у отсутствия есть **осмысленный нейтральный представитель в той же области значений** и подмена не создаёт ложного факта:

- слагаемое — `unwrap_or(0)`: ноль нейтрален для сложения (З6);
- множитель — `unwrap_or(1)`;
- количество/длина — `unwrap_or(0)`: «ничего не нашли» и «нашли ноль штук» — это одно и то же;
- настройка с документированным значением по умолчанию — `unwrap_or(8080)` для порта;
- строка для печати — `unwrap_or(String::from("-"))`: пользователю нужен прочерк, а не разбор случая.

Для позиции, идентификатора, дескриптора и любого «указателя на конкретный объект» умолчания не существует — там `match`, `if let` или `let else` (§16.2.4).

**Ответ:** функция — `fn find_index(xs: &[i32], needle: i32) -> Option<usize>` с индексным циклом `for i in 0..xs.len()`, ранним `return Some(i)` при совпадении и `None` последним выражением (листинг `m9.rs`). Прогон на `[3, 7, 42, 9]` печатает `42 is at index 2` и `100 is not in the array`; вариант с умолчанием даёт `index of 100 or 0: 0` и `index of 3 or 0: 0`. Опасность `unwrap_or(0)` для индекса именно в этом совпадении: 0 — валидная позиция (самая первая), поэтому умолчание делает «не найдено» неотличимым от «найдено в начале»; программа затем читает `xs[0]` вместо обработки отсутствия — тихая логическая ошибка без паники и без выхода за границы, то есть возвращение к C-шному sentinel −1 из глав 5 и 9. Умолчание уместно, когда у отсутствия есть нейтральный представитель, не создающий ложного факта: `unwrap_or(0)` для слагаемого или количества, `unwrap_or(1)` для множителя, документированное значение по умолчанию для настройки, прочерк для печати. Для позиций и идентификаторов — только разбор.

**Вариант 2 (накопитель вместо раннего возврата).** Тот же поиск с единственным выходом из функции. Файл `m9v2.rs`:

```rust
fn find_index(xs: &[i32], needle: i32) -> Option<usize> {
    let mut found: Option<usize> = None; // «пока не нашли»
    for i in 0..xs.len() {
        if xs[i] == needle {
            found = Some(i);
            break; // первое совпадение — и хватит
        }
    }
    found // единственный выход из функции
}
```

```
42 is at index 2
100 is not in the array
```

*Сравнение.* Поведение неотличимо (первое совпадение, `None` при неудаче), различие — в форме управления. Версия с `return` короче и не требует переменной: «нашли — ушли». Версия с накопителем держит **состояние поиска в значении**, а не в потоке управления: у функции один выход, и в этом её выгода, когда после цикла надо что-то доделать — записать в журнал, обновить счётчик попыток, вернуть общий результат; с ранним `return` такой код пришлось бы повторять в каждой точке выхода. Обратите внимание и на объявление: `let mut found: Option<usize> = None;` — аннотация типа обязательна, голому `None` неоткуда узнать, отсутствие чего он изображает (§16.2.3). Ещё одна деталь: без `break` цикл продолжил бы работу и переписывал бы `found` на каждом совпадении — функция стала бы искать **последнее** вхождение; ранний `return` такую ошибку сделать не даёт вовсе.

### Г16.Ч2.З10

**Условие.** *(прикладное)* Робот на плоскости: `enum Command { North(i32), East(i32), South(i32), West(i32), Home }` (с `derive(Clone, Copy)`) и функция `apply(pos: (i32, i32), cmd: Command) -> (i32, i32)`. Прогоните программу из пяти команд по массиву, печатая позицию после каждого шага (старт `(0, 0)`; например, `North(3), East(2), South(1), West(5), North(4)` даёт `(0,3) (2,3) (2,2) (-3,2) (-3,6)`), затем `Home` — возврат в `(0, 0)`. Объясните: почему `apply` берёт команду по значению и это дёшево; какие рукава match разбирают данные, а какой — нет.

**Решение.** Файл `m10.rs`:

```rust
#[derive(Clone, Copy)]
enum Command {
    North(i32),
    East(i32),
    South(i32),
    West(i32),
    Home,
}

fn apply(pos: (i32, i32), cmd: Command) -> (i32, i32) {
    match cmd {
        Command::North(d) => (pos.0, pos.1 + d),
        Command::East(d) => (pos.0 + d, pos.1),
        Command::South(d) => (pos.0, pos.1 - d),
        Command::West(d) => (pos.0 - d, pos.1),
        Command::Home => (0, 0), // данных у варианта нет — и разбирать нечего
    }
}

fn main() {
    let program = [
        Command::North(3),
        Command::East(2),
        Command::South(1),
        Command::West(5),
        Command::North(4),
    ];

    let mut pos = (0, 0);
    for i in 0..program.len() {
        pos = apply(pos, program[i]);
        println!("({}, {})", pos.0, pos.1);
    }

    pos = apply(pos, Command::Home);
    println!("home: ({}, {})", pos.0, pos.1);
}
```

```
(0, 3)
(2, 3)
(2, 2)
(-3, 2)
(-3, 6)
home: (0, 0)
```

Траектория совпала с ожидаемой из условия, `Home` вернул робота в начало. Соглашение об осях здесь такое: первая координата — восток-запад, вторая — север-юг; `North` увеличивает вторую, `South` уменьшает, `West` уводит первую в минус (после `West(5)` из позиции `(2, 2)` получается `(-3, 2)` — координаты знаковые, `i32`).

*Почему `apply` берёт команду по значению и почему это дёшево.* По значению — потому что функции нужна сама команда, а не доступ к чьей-то: она разбирает её и тут же забывает. По правилу сигнатур §15.2.1 это выбор «функция получает данные, ничего не возвращая владельцу», и он законен ровно потому, что тип помечен `Copy`: у всех вариантов данные — `i32` (или их нет вовсе), ресурсов и буферов нет (§16.1.3, правило композиции). Отсюда практическое следствие: `program[i]` в цикле **копируется** в параметр, а массив остаётся нетронутым. Уберите `derive(Clone, Copy)` — и программа перестанет собираться, а не «станет медленнее»: проверено на файле `m10_nocopy.rs`, `error[E0508]: cannot move out of type `[Command; 5]`, a non-copy array` («move occurs because `program[_]` has type `Command`, which does not implement the `Copy` trait»). Вынести элемент из массива нельзя: массив остался бы с дыркой, а такого состояния язык не допускает. Дёшево же копирование потому, что копия — метка варианта плюс одно `i32`, то есть заведомо не больше, чем указатель при передаче по ссылке. Для типа с `String` внутри пришлось бы писать `&Command` и разбирать по ссылке (глава 17).

*Какие рукава разбирают данные, а какой — нет.* Четыре первых рукава — образцы кортежных вариантов: `Command::North(d)` вводит свежую переменную `d` и кладёт в неё содержимое варианта; то же у `East`, `South`, `West` (имя `d` в каждом рукаве своё — рукава независимы, «провалиться» из одного в другой нельзя, в отличие от `switch` без `break`, §16.2.2). Пятый рукав, `Command::Home`, — образец единичного варианта: данных у него нет, привязывать нечего, и скобок в образце не пишут вовсе. Компилятор следит и за этим — проверено на файле `m10_pat.rs`, где перепутаны обе формы: `Command::North` без скобок даёт `error[E0532]: expected unit struct, unit variant or constant, found tuple variant `Command::North`` с подсказкой `use the tuple variant pattern syntax instead: `Command::North(_)``, а `Command::Home(x)` — `error[E0532]: expected tuple struct or tuple variant, found unit variant `Command::Home`` с подсказкой `use this syntax instead: `Command::Home``. Форма образца обязана совпадать с формой варианта.

**Ответ:** программа — листинг `m10.rs`; вывод — `(0, 3)`, `(2, 3)`, `(2, 2)`, `(-3, 2)`, `(-3, 6)`, затем `home: (0, 0)`. `apply` берёт команду по значению, потому что разбирает её и владельцу ничего не возвращает (правило сигнатур §15.2.1), а `Copy` делает это безопасным: данные всех вариантов — `i32`, ресурсов нет, поэтому `program[i]` копируется в параметр, а массив остаётся целым (без `Copy` первый же виток цикла унёс бы элемент, и программа не собралась бы). Дёшево — потому что копия равна дискриминанту плюс одному `i32`, то есть не больше указателя. Данные разбирают четыре рукава — `North(d)`, `East(d)`, `South(d)`, `West(d)`: каждый привязывает содержимое кортежного варианта к свежей переменной `d`; рукав `Command::Home` ничего не разбирает — это единичный вариант без данных, и образец у него состоит из одного имени, без скобок.

**Вариант 2 (изменение позиции на месте через `&mut`).** Вместо «получить новую позицию» можно «поправить существующую». Файл `m10v2.rs`:

```rust
fn apply(pos: &mut (i32, i32), cmd: Command) {
    match cmd {
        Command::North(d) => pos.1 += d,
        Command::East(d) => pos.0 += d,
        Command::South(d) => pos.1 -= d,
        Command::West(d) => pos.0 -= d,
        Command::Home => {
            pos.0 = 0;
            pos.1 = 0;
        }
    }
}
```

Массив команд в `main` тот же, что и в основном решении; меняются только вызовы (продолжение файла `m10v2.rs`):

```rust
    let mut pos = (0, 0);
    for i in 0..program.len() {
        apply(&mut pos, program[i]);
        println!("({}, {})", pos.0, pos.1);
    }

    apply(&mut pos, Command::Home);
    println!("home: ({}, {})", pos.0, pos.1);
}
```

```
(0, 3)
(2, 3)
(2, 2)
(-3, 2)
(-3, 6)
home: (0, 0)
```

*Сравнение.* Траектория совпадает дословно, различаются высказывание и гарантии. Версия с возвратом — **чистая функция**: позиция никуда не записывается, `apply` невозможно вызвать «не туда», а результат нельзя потерять незаметно... почти: `apply(pos, cmd);` без присваивания скомпилируется и молча ничего не изменит — та же ловушка, что у `counter = tick(counter)` в Г15.Ч2.З8. Версия с `&mut` эту ловушку закрывает (изменение и есть эффект вызова) и не создаёт промежуточных значений, но взамен требует `mut`-переменной у вызывающего, а исключительная ссылка на время вызова запрещает читать `pos` из других мест (§15.2.2) — на кортеже из двух чисел это незаметно, на большой структуре или на элементе коллекции (глава 17) станет ощутимым ограничением. Меняется и форма `match`: рукава больше не дают значение, а выполняют действие — все они имеют тип `()`, и потому вариант `Home` пришлось записать блоком из двух присваиваний. Практическое правило: для маленьких `Copy`-состояний удобнее и честнее возврат нового значения (легко тестировать: вход → выход, никаких скрытых эффектов); для больших или долгоживущих состояний — изменение на месте.

## Что дальше

Глава 16 дала слова: собственные структуры с методами, перечисления с данными, `Option<T>` вместо NULL и `match`, который не даст забыть ветку. Все они подчинялись правилам главы 15 без единого исключения — приёмник `&self` оказался тем же читателем, `&mut self` тем же писателем, а `..`-обновление и разбор `match`-ем перемещали не-Copy поля ровно так же, как обычное присваивание.

Чего не хватает — **вместилищ**. Наши примеры жили на массивах фиксированной длины (`[Command; 5]`) и одиночных значениях; растущего массива, словаря и строки, которую можно менять, у нас всё ещё нет. Глава 17 — прямое зеркало главы 9: `Vec<T>` вместо самодельного массива с ручной ёмкостью и `realloc`, `String` изнутри (почему индексация не как в C), `HashMap` вместо самописной хеш-таблицы. Ваши структуры и перечисления поедут внутрь этих коллекций — и там же выяснится, что разбор по ссылке (`match &cmd`), отложенный в §16.2.2, нужен буквально с первого же цикла по вектору.
