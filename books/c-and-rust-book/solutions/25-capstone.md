# Решения. Глава 25. Итоговые проекты

> Сборник решений самоучителя «C, затем Rust». Условия заданий продублированы из `chapters/25-capstone.md`. Глава проектная: половина заданий — «сделайте и объясните», и ценность здесь именно в том, чтобы сначала собрать и прогнать своё, а потом сверяться. Числа замеров у вас будут свои — сходиться должны выводы, а не миллисекунды.

> **Стенд — не набор файлов, а набор проектов** (приём главы 20): каждое состояние пакета живёт в отдельном каталоге, иначе листинг перестаёт быть куском реального файла. `p1` — часть 25.1: четыре стадии мини-grep (`v1_draft` → `v2_lib` → `v3_tests` → `minigrep`), проверочный `text.txt` и по каталогу на задание (`z3`, `z3b`, `z3_bad`, `z4`, `z5`, `z6`, `z7`, `z8`, `z8b`, `z9`, `z9b`, `z10`, `z10b`). `p2` — часть 25.2: копия готовой библиотеки Ч1 (`p2/minigrep` — path-зависимость требует соседства пакетов), три стадии пула (`pool_v2`, `pool_whilelet`, `pool_v3`), финальный `pargrep`, генератор `gen.rs` с данными `data/big1..big8.txt` (по 33 476 090 байт), файлы `small1.txt`/`small2.txt` и каталоги заданий (`z2`, `z2_1`, `z2_2`, `z2_8`, `z2b`, `z3`, `z5`, `z6`, `z6b`, `z6_bad`, `z7`, `z8`, `z9`, `z9b`, `z10`). Имя пакета во всех копиях сохранено (`minigrep`, `pargrep`) — поэтому выводы копий сравнимы с выводами главы построчно.

> **Сокращения и машинозависимое.** Строку `For more information about this error, try 'rustc --explain EXXXX'` опускаем везде, где код ошибки уже назван; абсолютные пути стенда и пути внутрь стандартной библиотеки сокращены до `...`; строки `Compiling`/`Finished`/`Running` от cargo опускаем, кроме случаев, где они и есть предмет разговора. На вашей машине будут другими: все времена (`за 601.3907ms`, `finished in 0.00s`), номера потоков в скобках в строках паники, адреса в выводе `{:p}`, хеши тестовых бинарников и — главное — **порядок строк любого многопоточного вывода**: недетерминизм §23.1.1 здесь норма, а не сбой. Порядок строк `test ... ok` тоже меняется от прогона к прогону: тесты идут параллельно (§20.2.1).

## Часть 25.1. CLI-утилита: мини-grep

### Г25.Ч1.З1

**Условие.** Пройдите чекпоинты 1–4 руками: создайте пакет, повторите каждую стадию, прогоните все показанные запуски (обе паники черновика — тоже) и `cargo test`. Сверьте свои коды возврата через `echo $?` (PowerShell: `$LASTEXITCODE`).

**Решение.** Задание требует не понимания, а дисциплины: пройти четыре стадии подряд и убедиться, что каждая ведёт себя ровно так, как обещает глава. Первое проектное решение — своё: **каждой стадии свой каталог** (`p1/v1_draft`, `p1/v2_lib`, `p1/v3_tests`, `p1/minigrep`). Иначе последняя правка стирает предыдущую стадию, и «повторить прогон чекпоинта 1» становится невозможно. Имя пакета во всех четырёх — `minigrep`, поэтому сообщения cargo и пути в панике совпадают с главой.

Каждый каталог собран одинаково: `Cargo.toml` из пяти строк, `src/` и копия `text.txt` рядом с `Cargo.toml` (программа получает путь `text.txt`, а cargo запускает бинарник из корня пакета):

```toml
[package]
name = "minigrep"
version = "0.1.0"
edition = "2024"

[dependencies]
```

**Чекпоинт 1.** `v1_draft/src/main.rs` — весь черновик из §25.1.1, вся программа в `main`. Два успешных прогона:

```
$ cargo run -- Rust text.txt
Ищем `Rust` в файле text.txt
Затем пришёл Rust — и владение

$ cargo run -- куча text.txt
Ищем `куча` в файле text.txt
указатели, куча и ручная дисциплина.
```

И обе обещанные паники — они здесь главное, ради них и просят «прогнать тоже»:

```
$ cargo run
thread 'main' (19680) panicked at src\main.rs:7:22:
index out of bounds: the len is 1 but the index is 1
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
$ echo $?
101

$ cargo run -- Rust nofile.txt
Ищем `Rust` в файле nofile.txt
thread 'main' (32600) panicked at src\main.rs:13:10:
не удалось прочитать файл: Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
$ echo $?
101
```

Координаты совпали с главой до символа: `7:22` — это `args[1]` (столбец 22 — открывающая скобка индексации), `13:10` — `.expect` на второй строке разбитого на две строки выражения. Совпадение не случайно: паника берёт координаты из места вызова (§18.1.1), а раскладка строк у нас дословная. Номер потока в скобках — свой у каждого запуска.

Обратите внимание на вторую панику: строка «Ищем …» **успела напечататься** — в stdout. Это и есть болезнь, которую вылечит чекпоинт 2 и о которой отдельно спросит Г25.Ч1.З5.

**Чекпоинт 2.** `v2_lib` — два crate в пакете: `src/lib.rs` (`Config`, `run`) и `src/main.rs` (16 строк церемонии). Прогоны:

```
$ cargo run -- Rust text.txt
Затем пришёл Rust — и владение
$ echo $?
0

$ cargo run
Ошибка разбора аргументов: нужно два аргумента: <запрос> <файл>
$ echo $?
1

$ cargo run -- Rust nofile.txt
Ошибка выполнения: The system cannot find the file specified. (os error 2)
$ echo $?
1
```

И контрольный опыт с перенаправлением:

```
$ cargo run -- Rust nofile.txt > результат.txt
Ошибка выполнения: The system cannot find the file specified. (os error 2)
$ wc -c < результат.txt
0
```

Сообщение осталось на экране, файл — ровно 0 байт. Ни одной паники: код 101 сменился на осознанную единицу.

**Чекпоинт 3.** `v3_tests` — три теста и режим `IGNORE_CASE`. `cargo test` (строки cargo и два пустых набора — бинарника и документации — опущены, как и в главе):

```
$ cargo test
running 3 tests
test tests::search_is_case_sensitive ... ok
test tests::case_insensitive_finds_both ... ok
test tests::finds_one_line ... ok

test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

Порядок строк у нас другой, чем в главе, — и это не расхождение: тесты выполняются параллельно (§20.2.1), печатаются в порядке завершения. Дальше — рубильник регистра:

```
$ cargo run -- rust text.txt
Не доверяй — проверяй: rustc не спит.

$ IGNORE_CASE=1 cargo run -- rust text.txt
Затем пришёл Rust — и владение
Не доверяй — проверяй: rustc не спит.
```

**Чекпоинт 4.** `minigrep` — итераторный `build` и конвейерный `search`. Тесты те же три и те же зелёные; прогоны совпадают с чекпоинтом 3, плюс новая формулировка отказа при **одном** аргументе (раньше проверялась длина среза, теперь — `Option` от `next()`):

```
$ cargo run -- Rust
Ошибка разбора аргументов: нужно два аргумента: <запрос> <файл>
$ echo $?
1
```

Побочная находка захода. Тестовые бинарники чекпоинтов 3 и 4 назвались **одинаково** — `minigrep-2382e24421bae8bf.exe` (библиотека) и `minigrep-f607c2c68774b920.exe` (бинарник), хотя `lib.rs` у них разный: в одном циклы, в другом конвейеры. Это прямое подтверждение находки главы 20 (§20.2.1 и решение Г20.Ч2.З4): хеш в имени тестового бинарника считается от имени и версии пакета, а не от содержимого исходников.

Счёт строк финальной версии — тот, что глава называет в чекпоинте 5:

```
$ wc -l minigrep/src/main.rs minigrep/src/lib.rs

  99 minigrep/src/lib.rs

```

**Ответ.** Все четыре стадии воспроизводятся дословно. Сводка прогонов и кодов возврата:

### Г25.Ч1.З2

**Условие.** Найдите на своей машине текстовый файл (или соберите свой) и продемонстрируйте на нём все три режима финальной версии: обычный поиск, `IGNORE_CASE=1`, перенаправление вывода в файл при ошибке (файл должен остаться пустым).

**Решение.** Проверочный `text.txt` из главы — пять строк; на нём не видно ни цены `read_to_string`, ни того, что утилита вообще пригодна для работы. Возьмём файл посерьёзнее: `p2/data/big1.txt`, изготовленный генератором §25.2.4, — 400 000 строк, 33 476 090 байт, в каждой тысячной спрятано слово «Rust». Файл в 33 МБ — это уже разговор о памяти: `fs::read_to_string` втягивает его в `String` целиком (§18.2.2), то есть пик потребления памяти нашей утилиты равен размеру файла. Для проектного решения «читаем всё сразу» это честная плата; построчное чтение (`BufRead::lines`) сняло бы её, но лишило бы `search` возможности отдавать ломтики одного долгоживущего текста — а именно на этом стоит вся часть.

Режим первый — обычный поиск (релизная сборка, иначе поиск по 33 МБ в дебаге заметен на глаз):

```
$ cargo run --release -- "спрятан Rust" ../../p2/data/big1.txt > hits.txt
$ wc -l < hits.txt
400
$ head -3 hits.txt
строка 999: здесь спрятан Rust
строка 1999: здесь спрятан Rust
строка 2999: здесь спрятан Rust
```

400 совпадений — ровно столько, сколько заложил генератор (`i % 1000 == 999` на 400 000 строках). Детерминированный счёт на большом файле — удобный контроль: он ещё пригодится в части 25.2 как эталон правильности параллельной версии.

Режим второй — регистр. Запрос `rust` строчными в файле не встречается ни разу, а `Rust` — 400 раз:

```
$ cargo run --release -- "rust" ../../p2/data/big1.txt | wc -l
0
$ IGNORE_CASE=1 cargo run --release -- "rust" ../../p2/data/big1.txt | wc -l
400
```

Ноль против четырёхсот — нагляднее любого рассуждения: без флага утилита строго уважает регистр, с флагом обе формы сливаются. (Внутри режим дороже: `to_lowercase` строит новую `String` для **каждой** строки файла — 400 000 выделений; на глаз это не заметно, но в §25.2.4 именно эту функцию мы нарочно выберем как «самую дорогую», чтобы нагрузить пул.)

Режим третий — перенаправление при ошибке, финальной версией:

```
$ cargo run -- Rust nofile.txt > результат.txt
Ошибка выполнения: The system cannot find the file specified. (os error 2)
$ echo $?
1
$ wc -c < результат.txt
0
```

Сообщение — на экране, файл создан и пуст. Тот, кто напишет `minigrep Rust *.txt > out.txt`, получит либо результаты, либо пустой файл, но никогда не смесь результатов с диагностикой.

**Ответ.** На файле `p2/data/big1.txt` (33 МБ, 400 000 строк) все три режима работают, как заявлено: обычный поиск даёт 400 строк, регистрозависимый запрос `rust` — 0 строк, он же с `IGNORE_CASE=1` — снова 400; перенаправление вывода при ошибке чтения оставляет `результат.txt` нулевого размера, сообщение уходит в stderr, код возврата 1. Побочный вывод, важный для проектирования: `read_to_string` держит в памяти весь файл, поэтому «мини-grep» по гигабайтному файлу потребует гигабайт — цена архитектуры, выбранной ради ломтиков в `search`.

### Г25.Ч1.З3

**Условие.** Добавьте в тестовый модуль четвёртый тест: запрос, которого в тексте нет, — `search` обязан вернуть пустой вектор. Подсказка: `assert_eq!` с `Vec::<&str>::new()` — годная возможность вспомнить турбо-рыбу из §19.1.2.

**Решение.** Тест пишется в тот же модуль `mod tests` библиотеки (`p1/z3/src/lib.rs` — копия финальной версии плюс четвёртый тест):

```rust
    #[test]
    fn finds_nothing() {
        let query = "Python";
        let contents = "\
Rust не прощает,
но rustc объясняет.";

        assert_eq!(Vec::<&str>::new(), search(query, contents));
    }
```

```
$ cargo test --lib
running 4 tests
test tests::case_insensitive_finds_both ... ok
test tests::search_is_case_sensitive ... ok
test tests::finds_one_line ... ok
test tests::finds_nothing ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

Почему подсказка условия настаивает на турбо-рыбе? Попробуйте написать «естественно» — `assert_eq!(vec![], search(query, contents));` (файл `p1/z3_bad/src/lib.rs`):

```
$ cargo test
error[E0282]: type annotations needed
   --> src\lib.rs:107:9
    |
107 |         assert_eq!(vec![], search(query, contents));
    |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ cannot infer type

error: could not compile `minigrep` (lib test) due to 1 previous error
```

Знакомая по §19.1.1 ошибка E0282 — и урок в том, **почему** она возникает, хотя справа стоит `Vec<&str>` и «тип же очевиден». `assert_eq!` разворачивается в сравнение `left == right`, а сравнение векторов обслуживает реализация `impl<A: PartialEq<B>> PartialEq<Vec<B>> for Vec<A>`: типы элементов слева и справа **не обязаны совпадать**, достаточно, чтобы левый умел сравниваться с правым. Значит, из `Vec<&str>` справа тип элемента слева не выводится — компилятор честно говорит, что не знает, чем заполнять пустой `vec![]`. Турбо-рыба `Vec::<&str>::new()` (§19.1.2) отвечает на этот вопрос явно.

**Ответ.** Четвёртый тест — `finds_nothing`: запрос `"Python"`, тот же двухстрочный текст, `assert_eq!(Vec::<&str>::new(), search(query, contents));`. Тест зелёный с первого раза, всего в наборе становится 4. Турбо-рыба обязательна: без неё пустой `vec![]` не типизируется (E0282), потому что `PartialEq` для векторов допускает разные типы элементов слева и справа и не переносит тип с одной стороны на другую.

**Вариант 2 (предикат вместо сравнения).** Проверять пустоту можно не сравнением с эталонным пустым вектором, а вопросом к результату — `p1/z3b/src/lib.rs`:

```rust
    #[test]
    fn finds_nothing() {
        let query = "Python";
        let contents = "\
Rust не прощает,
но rustc объясняет.";

        assert!(search(query, contents).is_empty());
    }
```

```
$ cargo test --lib
running 4 tests
test tests::case_insensitive_finds_both ... ok
test tests::finds_one_line ... ok
test tests::finds_nothing ... ok
test tests::search_is_case_sensitive ... ok

test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

*Сравнение.* Вариант короче и не требует турбо-рыбы: `is_empty()` спрашивает у готового вектора его длину, никакого второго значения создавать не нужно — вопрос о выводе типов просто не возникает. Плата — качество отчёта при провале: `assert_eq!` печатает `left` и `right` целиком, то есть при поломке вы сразу видите, **что** нашлось лишнего; `assert!` умеет сказать лишь «условие ложно» (§20.2.1). Для теста-сторожа, который годами будет зелёным, разница невелика; для теста, который вы отлаживаете прямо сейчас, лучше `assert_eq!`. Основное решение выбрано ещё и потому, что его требует подсказка условия — и потому, что мимоходом объясняет E0282.

### Г25.Ч1.З4

**Условие.** Объясните, почему `search` возвращает `Vec<&'a str>`, а не `Vec<String>`, и чем это лучше. Затем — почему время жизни `'a` привязано только к `contents`: что сломалось бы у вызывающего кода, будь оно привязано и к `query`? Проверьте своё объяснение экспериментом: заведите в `main` короткоживущий `String`-запрос внутри блока `{}` и попробуйте использовать результат поиска снаружи блока при обеих сигнатурах.

**Решение.** Разберём три вопроса по очереди.

**Почему `Vec<&'a str>`, а не `Vec<String>`.** Ломтик (§15.3.1) — это пара «указатель + длина», 16 байт на эталонной машине, и он **не владеет** текстом: `search` не копирует ни байта, а лишь размечает уже прочитанный `contents`. Версия с `Vec<String>` обязана скопировать каждую найденную строку в отдельное выделение кучи. Замерим цену на тексте из 400 000 строк, где совпадает каждая десятая (`p1/z4/z4_bench.rs`, релизная сборка):

```rust
fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents
        .lines()
        .filter(|line| line.contains(query))
        .collect()
}

fn search_owned(query: &str, contents: &str) -> Vec<String> {
    contents
        .lines()
        .filter(|line| line.contains(query))
        .map(|line| line.to_string())
        .collect()
}
```

```
$ rustc -O --edition 2024 z4_bench.rs
$ ./z4_bench.exe
текст: 18640000 байт
Vec<&str>:  40000 строк за 8.477ms
Vec<String>: 40000 строк за 10.2093ms
скопировано в кучу: 1320000 байт
```

Владеющая версия сделала 40 000 выделений и скопировала 1,32 МБ — за это заплачено ~20 % времени поиска. Разрыв невелик потому, что в обеих версиях доминирует проход по 18 МБ текста; на выборке пошире (например, «найти все строки») он растёт. Но главное даже не время: `Vec<&str>` не даёт **вырасти пиковому потреблению памяти** — при поиске, находящем половину файла, владеющая версия удваивает занятое.

**Почему `'a` только у `contents`.** Время жизни в сигнатуре — это обещание вызывающему: «элементы результата не переживут того аргумента, к которому привязано `'a`». Ломтики режутся из `contents`, из `query` в результат не попадает ничего — значит, честное обещание касается только `contents`. Привязка к обоим («на всякий случай») компилятор устроит, но обещание станет строже, чем правда: результат объявят зависящим и от запроса. Проверяем экспериментом. `p1/z4/z4_ok.rs` — сигнатура главы, короткоживущий запрос внутри блока:

```rust

но rustc объясняет.");

    let found;
    {

        found = search(&query, &contents);
    } // query умер здесь

    println!("{found:?}"); // а результат жив
}

**Обратная ловушка** (её тоже называет чекпоинт 3). Функция, которая сама владеет текстом, вернуть ломтики не может — `p1/z4/z4_e0515.rs`:

        .collect()

Время жизни `'a` привязано только к `contents`, потому что оттуда и только оттуда режутся ломтики. Привязка к обоим аргументам компилируется, но лжёт вызывающему: в опыте с запросом, живущим внутри блока, версия из главы печатает результат снаружи блока, а версия с общим `'a` не собирается — E0597 «`query` does not live long enough», причём с прямым `note`, что результат объявлен хранящим ссылки на запрос. Зеркальная ошибка — функция, владеющая текстом и возвращающая ломтики: E0515.

### Г25.Ч1.З5

**Условие.** В чекпоинте 2 ошибки ушли в stderr. Объясните, что оказалось бы в `результат.txt` после `cargo run -- Rust nofile.txt > результат.txt`, останься в программе `println!` вместо `eprintln!`, — и почему для утилиты, встраиваемой в конвейеры, это дисквалификация. Какая глава тома I ввела это разделение и для чего?

**Решение.** Ответ на «что оказалось бы в файле» лучше не угадывать, а получить. `p1/z5` — точная копия финального пакета, в котором обе диагностические строки `main` переведены с `eprintln!` на `println!`:

```rust
fn main() {
    let config = Config::build(env::args()).unwrap_or_else(|err| {
        println!("Ошибка разбора аргументов: {err}");
        process::exit(1);
    });

    if let Err(e) = minigrep::run(config) {
        println!("Ошибка выполнения: {e}");
        process::exit(1);
    }
}
```

```
$ cargo run -- Rust nofile.txt > результат.txt
$ echo $?
1
$ wc -c < результат.txt
91
$ cat результат.txt
Ошибка выполнения: The system cannot find the file specified. (os error 2)
```

Экран при этом пуст: пользователь **не увидел ничего**, а в файле результатов лежит 91 байт текста, который результатом не является. Сравните с правильной версией из Г25.Ч1.З2 — тот же запуск оставляет файл нулевого размера, а сообщение показывает человеку.

Почему для утилиты, встраиваемой в конвейеры, это дисквалификация — три следствия, каждое ломает свой сценарий:

1. **Данные загрязнены.** Следующее звено конвейера (`sort`, `wc -l`, `grep`) получит строку про ошибку как обычную строку. `minigrep Rust nofile.txt | wc -l` ответит «1», хотя не найдено ничего: ошибка притворилась результатом.
2. **Диагностика невидима.** Тот, кто перенаправил stdout, ошибку не увидит вовсе — она уехала в файл. Код возврата 1 остался единственным намёком, и то если его проверять.
3. **Нечего проверить глазами.** Классический приём отладки «запустить с перенаправлением и посмотреть на экран» перестаёт работать: экран пуст в обоих исходах.

Правильное разделение известно из тома I. Три стандартных потока (`stdin`, `stdout`, `stderr`) и правило «результаты в stdout, диагностика в stderr» вводит **глава 10, §10.1.1**; там же объясняется, зачем: `stderr` не буферизуется наравне с `stdout` и не участвует в перенаправлении `>`, поэтому сообщение доходит до человека немедленно и не смешивается с данными. В томе II тот же приём переехал в пару `println!` / `eprintln!` (§18.1.2) — синтаксис другой, дисциплина та же.

**Ответ.** В `результат.txt` оказалась бы сама диагностика — 91 байт строки `Ошибка выполнения: The system cannot find the file specified. (os error 2)` (прогон подтверждает: файл 91 байт, экран пуст, код возврата 1). Для утилиты конвейера это дисквалификация: ошибка подмешивается в данные и считается следующим звеном за результат (`| wc -l` даст 1 вместо 0), а сам человек диагностику не видит, потому что она уехала в файл. Разделение потоков ввёл том I, **глава 10 (§10.1.1)** — ради того, чтобы результаты можно было перенаправлять и обрабатывать машинно, а сообщения об ошибках при этом доходили до человека; в томе II это пара `println!` (stdout) и `eprintln!` (stderr).

### Г25.Ч1.З6

**Условие.** Сравните две версии `Config::build` — из чекпоинта 2 (`&[String]` + `clone`) и из чекпоинта 4 (итератор + `match`). Проследите путь строки `query` от операционной системы до поля структуры в обеих: где происходят выделения памяти и копирования? Почему итераторная версия не смогла бы принять `&[String]` без изменений?

**Решение.** Проследим путь строки `query` по шагам — одинаковое начало и разные концовки.

**Общее начало (обе версии).** Операционная система передаёт процессу аргументы; `env::args()` (§25.1.1) отдаёт их итератором, и каждый очередной `next()` **выделяет новую `String`** — проверенную на валидность UTF-8 копию аргумента. Это выделение №1, его не избежать ни в одной версии. `collect()` в `Vec<String>` выделяет ещё и буфер самого вектора, но символы строк при этом никуда не копируются: `String`-значения (по 24 байта — указатель, длина, ёмкость) просто переезжают в вектор (§17.1.1).

**Чекпоинт 2 (`&[String]` + `clone`).** `build` получил вектор взаймы. Владеть он не может, поэтому `args[1].clone()` — выделение №2 и **побайтовое копирование** содержимого. Итог: две живые копии запроса — одна в `args`, другая в `Config`; первая умрёт в конце `main`, вторая уедет в `run`.

**Чекпоинт 4 (итератор владеющих `String`).** `args.next()` **отдаёт владение** очередной строкой (§21.2.1). `Config` забирает её себе целиком — вместе с уже выделенным буфером. Второго выделения нет, копирования байтов нет; переезжает 24-байтовое значение `String`, буфер в куче остаётся на месте.

Слова «буфер остаётся на месте» проверяются прямым замером (`p1/z6/z6_ptr.rs`): печатаем адрес буфера у `args[1]`, затем прогоняем обе версии `build` — сначала заимствующую, потом потребляющую тот же самый вектор:

```rust
fn main() {
    let args: Vec<String> = env::args().collect();
    println!(
        "args[1]:       ptr={:p} len={} cap={}",
        args[1].as_ptr(),
        args[1].len(),
        args[1].capacity()
    );

    let c2 = build_v2(&args).unwrap();
    println!(
        "v2 (clone):    ptr={:p} len={} cap={}",
        c2.query.as_ptr(),
        c2.query.len(),
        c2.query.capacity()
    );

    let c4 = build_v4(args.into_iter()).unwrap();
    println!(
        "v4 (итератор): ptr={:p} len={} cap={}",
        c4.query.as_ptr(),
        c4.query.len(),
        c4.query.capacity()
    );
```

```
$ rustc --edition 2024 z6_ptr.rs
$ ./z6_ptr.exe Rust text.txt
args[1]:       ptr=0x2ade0391890 len=4 cap=4
v2 (clone):    ptr=0x2ade038ab90 len=4 cap=4
v4 (итератор): ptr=0x2ade0391890 len=4 cap=4
файлы: text.txt и text.txt
```

Адрес у итераторной версии **тот же самый**, что у исходного аргумента, у версии с `clone` — другой. (Адреса машинозависимы, важно только их совпадение и различие.) Ещё нагляднее — на длинном запросе, где видно и ёмкость:

```
$ ./z6_ptr.exe длинный-запрос-на-кириллице text.txt
args[1]:       ptr=0x24bb5dd1280 len=51 cap=54
v2 (clone):    ptr=0x24bb5dd1140 len=51 cap=51
v4 (итератор): ptr=0x24bb5dd1280 len=51 cap=54
```

Тот же адрес — тот же буфер: строка не копировалась, а переехала. И маленькая улика в придачу: у исходной строки ёмкость 54 при длине 51 (запас, оставшийся от преобразования аргумента внутри `env::args()`), а у копии — ровно 51. `clone` выделяет буфер **по длине**, а не повторяет чужую раскладку, — ещё одно доказательство, что перед нами новое выделение; итераторная версия сохранила и ёмкость, потому что не выделяла ничего.

**Почему итераторная версия не приняла бы `&[String]`.** Параметр `impl Iterator<Item = String>` требует итератора, который отдаёт **владеющие** `String`. У среза `&[String]` такого итератора нет и быть не может: `iter()` даёт `Item = &String`, а вынести значение из-под заимствования нельзя — это ровно та E0507, которую мы обходили `Option::take` и `Vec::drain` (§25.2.3 покажет оба приёма). Срез не владеет элементами, отдать их во владение он не вправе. Отсюда и цепочка решений главы: чтобы `build` мог забирать строки себе, ему нужен владеющий источник — `env::args()` напрямую (в `main`) или `Vec::into_iter()` (в нашем замере и в тестах Г25.Ч1.З10). Именно поэтому `clone` в чекпоинте 2 был не небрежностью, а неизбежностью выбранной сигнатуры: пока вход заимствован, копия — единственный законный способ получить владение.

**Ответ.** Путь одинаков до входа в `build`: ОС → `env::args()` выделяет по одной `String` на аргумент (выделение №1, обязательное) → `collect()` выделяет буфер вектора и **перемещает** в него готовые строки. Дальше версии расходятся. Чекпоинт 2: `args[1].clone()` — второе выделение и побайтовая копия содержимого; в памяти две копии запроса (в `args` и в `Config`). Чекпоинт 4: `args.next()` отдаёт владение — второго выделения и копирования нет, переезжает только 24-байтовое значение `String`, буфер в куче тот же (замер: адрес `as_ptr()` у поля `Config` совпадает с адресом исходного `args[1]`, тогда как у `clone`-версии отличается). Принять `&[String]` итераторная версия не может: срез не владеет элементами, его итератор отдаёт `&String`, а вынести значение из-под заимствования — E0507. Владеющий источник (`env::args()` или `Vec::into_iter()`) — обязательное условие того, чтобы `clone` исчез.

### Г25.Ч1.З7

**Условие.** Разберите эксперимент с длинной строкой из чекпоинта 5 по шагам: что именно возвращает каждый вызов `fgets` для строки в 1525 байт при буфере 1024? Затем подберите содержимое файла, на котором C-версия, наоборот, **удвоит совпадение**: одна физическая строка даст два срабатывания `strstr` и два вызова `fputs`. - вызов 3 вернул вторую физическую строку целиком (48 байт со словом `Rust`);
- вызов 4 (в протоколе его нет) вернул бы `NULL` — конец файла.

fgets #2: strlen=521, first6="bbbbbb", last6="?????", newline=yes, Rust=yes
```

Оба куска проходят проверку `strstr`, значит, `fputs` вызывается **дважды на одну физическую строку**: с точки зрения grep-семантики файл дал два совпадения там, где строка одна, — счётчик совпадений удвоился.

А вот в **строках вывода** прибавки нет, и это стоит проговорить точно:

```
$ ./minigrep_c.exe Rust twice.txt | wc -l
1
$ ./minigrep_c.exe Rust twice.txt | wc -c
1545
```

Один перевод строки — потому что перевод строки в физической строке ровно один и достаётся он последнему куску; два `fputs` подряд просто склеивают строку обратно. (1545 байт против 1544 в файле — это UCRT в текстовом режиме превращает `\n` в `\r\n` на выводе, §10.2.1.) Так что артефакт «одна физическая строка выведется как две» на числе строк не проявляется: получить переводов строки больше, чем строк в файле, `fgets`-цикл не может в принципе.

Зато есть зеркальный артефакт — и он **уменьшает** число строк, портя вывод по-настоящему. Файл `glue.txt`: длинная строка, у которой совпадение есть только в первом куске, и следом обычная строка с совпадением:

```
$ ./probe.exe glue.txt
fgets #1: strlen=1023, first6="Rust ?", last6="cccccc", newline=no, Rust=yes
fgets #2: strlen=499, first6="cccccc", last6="ccccc", newline=yes, Rust=no
fgets #3: strlen=38, first6="??????", last6=" Rust", newline=yes, Rust=yes
$ ./minigrep_c.exe Rust glue.txt | wc -l
1
$ cd ../minigrep && cargo run -q -- Rust ../z7/glue.txt | wc -l
2
```

Два совпадения из разных физических строк слиплись в одну строку вывода: первый кусок напечатан без перевода строки (он остался во втором куске, который не совпал и не печатался), и к нему вплотную приклеилась третья строка файла. Rust-версия печатает две строки — она работает со строкой целиком, а не с тем, что влезло в буфер.

**Ответ.** Для строки в 1525 байт (плюс перевод строки) при буфере 1024 `fgets` вызывается дважды: первый вызов возвращает указатель на буфер с 1023 байтами без перевода строки (`aaa…aaaaRu`), второй — с оставшимися 503 байтами, начинающимися с `st` и заканчивающимися переводом строки; следующий вызов читает уже вторую физическую строку, а по концу файла возвращает `NULL`. Слово `Rust` рассечено границей и в целом виде не встречается ни в одном куске, поэтому `strstr` молчит дважды. Больше **совпадений**, чем строк в файле, C-версия печатает тогда, когда одна физическая строка длиннее буфера и запрос встречается по обе стороны границы (`twice.txt`): `fputs` срабатывает дважды на одной строке. Однако на числе **строк вывода** это не сказывается — перевод строки в физической строке один, и два куска склеиваются обратно (`wc -l` → 1 при двух `fputs`); получить строк вывода больше, чем строк в файле, `fgets`-цикл не может в принципе — это и есть невозможный артефакт из условия. Настоящий артефакт обратного знака — склейка: если совпал первый кусок, а последний (тот, что несёт перевод строки) — нет, напечатанное сливается со следующей найденной строкой, и строк становится **меньше** (`glue.txt`: два совпадения — одна строка вывода). Общее правило: цикл `fgets` с фиксированным буфером работает не со «строками», а с «тем, что поместилось», поэтому на записи длиннее буфера возможны четыре артефакта — потеря совпадения, рассечённого границей; удвоение совпадения, встретившегося по обе стороны границы; склейка соседних записей из-за потерянного перевода строки; обрезка вывода. Ни один из них не является ошибкой памяти: программа не падает, санитайзер молчит, тесты (если они проверяют короткие строки) зелены — она просто отвечает неверно.

### Г25.Ч1.З8

**Условие.** Добавьте в библиотеку режим нумерации строк: `minigrep` с установленной переменной `SHOW_LINES` печатает `номер: строка` (нумерация с 1). Подсказка: `enumerate` (§21.2.2). Не забудьте тест — и обратите внимание, какую сигнатуру придётся дать функции, чтобы номер пережил возврат из неё.

**Решение.** Сначала — вопрос о сигнатуре, который условие просит заметить. Номер строки нужно вычислить **там, где ещё известен порядок строк исходного текста**, то есть внутри поиска: после того как `search` вернул `Vec<&str>`, отобранные ломтики уже ничем не отличаются от любых других — восстановить по ним номера невозможно (искать `position` в исходном тексте — не восстановление, а второй поиск, к тому же неверный при повторяющихся строках). Значит, номер обязан уехать из функции вместе со строкой: `Vec<(usize, &'a str)>`. Заметьте, что времени жизни в кортеже требует только вторая половина: `usize` — самостоятельное значение, оно ничего не заимствует и переживает возврат само по себе.

`p1/z8/src/lib.rs`, обе функции поиска (`enumerate` из §21.2.2, `+ 1` — потому что нумерация с 1):

```rust
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<(usize, &'a str)> {
    contents
        .lines()
        .enumerate()
        .map(|(i, line)| (i + 1, line))
        .filter(|(_, line)| line.contains(query))
        .collect()
}

pub fn search_case_insensitive<'a>(query: &str, contents: &'a str) -> Vec<(usize, &'a str)> {
    let query = query.to_lowercase();
    contents
        .lines()
        .enumerate()
        .map(|(i, line)| (i + 1, line))
        .filter(|(_, line)| line.to_lowercase().contains(&query))
        .collect()
}
```

Важен порядок звеньев: `enumerate` стоит **до** `filter`. Поменяйте местами — и нумероваться будут только найденные строки (1, 2, 3…), то есть номер перестанет быть номером строки в файле. Рубильник — по образцу `IGNORE_CASE`: поле `pub show_lines: bool` в `Config`, строка `let show_lines = env::var("SHOW_LINES").is_ok();` в `build` и выбор формата в `run`:

```rust
    for (number, line) in results {
        if config.show_lines {
            println!("{number}: {line}");
        } else {
            println!("{line}");
        }
    }
```

Тесты — три; средний специально закрывает ту самую ловушку с порядком звеньев (в тексте есть пустая строка, и она обязана считаться):

```rust

        let query = "rust";
        let contents = "\
Rust не прощает,
пустая строка ниже

но rustc объясняет.";

        assert_eq!(vec![(4, "но rustc объясняет.")], search(query, contents));
    }
```

Номера 3 и 5 — правильные: в `text.txt` пять строк, найденные — третья и пятая.

**Ответ.** Нумерация вводится в самой функции поиска: `search<'a>(query: &str, contents: &'a str) -> Vec<(usize, &'a str)>`, конвейер `lines().enumerate().map(|(i, line)| (i + 1, line)).filter(…).collect()`, причём `enumerate` обязан стоять **до** `filter`, иначе нумеруются найденные строки, а не строки файла. Такая сигнатура и требуется, чтобы номер пережил возврат: `usize` — независимое значение, `'a` по-прежнему нужно только ломтику. `Config` получает поле `show_lines`, заполняемое из `env::var("SHOW_LINES").is_ok()`, `run` печатает `{number}: {line}` или просто `{line}`. Тест `numbers_count_all_lines_not_only_hits` (текст с пустой строкой, ожидается номер 4) закрывает ошибку с перестановкой звеньев; на `text.txt` режим печатает `3: …` и, вместе с `IGNORE_CASE=1`, `3: …` и `5: …`.

**Вариант 2 (ленивый поиск: `impl Iterator` вместо `Vec`).** Собирать вектор необязательно — можно вернуть сам конвейер (`p1/z8b/src/lib.rs`):

```rust
pub fn search<'a>(query: &'a str, contents: &'a str) -> impl Iterator<Item = (usize, &'a str)> {
    contents
        .lines()
        .enumerate()
        .map(|(i, line)| (i + 1, line))
        .filter(move |(_, line)| line.contains(query))
}
```

Печать при этом выносится в общую функцию — иначе две ветви `if config.ignore_case` вернут **разные** типы и не сойдутся в одном `let`:

```rust
fn print_hits<'a>(hits: impl Iterator<Item = (usize, &'a str)>, show_lines: bool) {
    for (number, line) in hits {
        if show_lines {
            println!("{number}: {line}");
        } else {
            println!("{line}");
        }
    }
}
```

$ SHOW_LINES=1 cargo run -- Rust text.txt
3: Затем пришёл Rust — и владение

*Сравнение.* Ленивая версия не выделяет вектор вовсе: строки идут в печать по одной, память под результат не растёт с числом совпадений — на файле, где совпадает всё, это разница между «ничего» и «вектор в полфайла». Платится тремя неудобствами. Первое: тесты обязаны дописывать `.collect()`, а вызывающий не может ни спросить `len()`, ни пройти результат дважды. Второе: две функции поиска возвращают разные анонимные типы, поэтому общий `let results = if … {…} else {…}` больше не собирается — печать приходится выносить в обобщённую функцию. Третье, и самое интересное: **ленивый результат заимствует запрос**. В издании 2024 `impl Trait` захватывает все времена жизни из области видимости, а замыкание фильтра и правда держит ссылку на `query` — поэтому урок §25.1.3 «`'a` только к `contents`» для ленивой версии не работает. Опыт Г25.Ч1.З4 с короткоживущим запросом на ленивой версии не собирается:

```
error[E0597]: `query` does not live long enough
...
note: this call may capture more lifetimes than intended, because Rust 2024 has adjusted the `impl Trait` lifetime capture rules
help: use the precise capturing `use<...>` syntax to make the captures explicit
   |
 2 | fn search<'a>(query: &str, contents: &'a str) -> impl Iterator<Item = &'a str> + use<'a> {
   |                                                                                +++++++++
```

Подсказка компилятора здесь **не чинит** — она открывает второй барьер (знакомый приём: так же вела себя починка E0106 через `'static` в §15.3.2):

```
error[E0700]: hidden type for `impl Iterator<Item = &'a str>` captures lifetime that does not appear in bounds
...
  |                      hidden type `Filter<std::str::Lines<'a>, {closure@z4_lazy_use.rs:3:29: 3:40}>` captures the anonymous lifetime defined here
help: add `'_` to the `use<...>` bound to explicitly capture it
```

Заимствование настоящее, подписью его не отменить: чтобы результат перестал зависеть от запроса, копию запроса надо отправить внутрь итератора (`let query = query.to_string();` перед `filter(move …)`) — тогда `use<'a>` проходит и программа печатает `["но rustc объясняет."]`. То есть ленивость экономит память под результат, но возвращает копию запроса, от которой избавился чекпоинт 4. Для утилиты, где результат печатается сразу, — разумный размен; для библиотеки, чей второй клиент (глава 26) захочет держать результат, считать его и показывать по кусочкам, — `Vec` честнее.

### Г25.Ч1.З9

**Условие.** Научите утилиту искать в нескольких файлах: `minigrep <запрос> <файл>...`. Каждая найденная строка печатается с префиксом имени файла (`text.txt: строка`), ошибка чтения одного файла не прерывает обработку остальных (сообщение в stderr — и дальше). Решите сами (и обоснуйте): менять ли сигнатуру `search` или собрать всё в `run`.

**Решение.** Первое — обоснование развилки. **Сигнатуру `search` не трогаем.** Три довода. (1) `search` отвечает за поиск в тексте, имя файла к тексту отношения не имеет — это оформление вывода; смешав их, мы получим функцию, которую нельзя протестировать без файловой системы (сейчас все её тесты — чистые строки в памяти). (2) У `search` уже есть второй клиент — `pargrep` из §25.2.4, и третий на подходе (глава 26); менять сигнатуру ради формата печати значит ломать их обоих. (3) Правило §20.1.1: библиотека держит логику, а `run` — сценарий работы утилиты; «пройти по списку файлов» — сценарий. Меняется, стало быть, `Config` (одно имя файла → список) и `run`.

`p1/z9/src/lib.rs` — `build` забирает остаток итератора целиком:

`args.collect()` после двух `next()` — это «всё, что осталось»: снова та же выгода владеющего итератора, что и в чекпоинте 4, — ни одного `clone`. Цикл `run` устроен так, что ошибка одного файла не трогает остальные:

        let results = if config.ignore_case {

Ключевая деталь — `?` здесь неуместен: он вернул бы ошибку наружу и оборвал обработку на первом же нечитаемом файле (§18.1.3). Ошибка становится **сообщением в stderr плюс `continue`**; `run` по-прежнему возвращает `Result`, но теперь только на случай отказов, которые действительно фатальны для всего запуска.

**Ответ.** Сигнатуру `search` менять не следует: поиск в тексте и оформление вывода — разные обязанности, у `search` уже есть сторонние клиенты (`pargrep`, а затем GUI главы 26), и его тесты не должны зависеть от файловой системы. Меняются `Config` (поле `file_paths: Vec<String>`, заполняемое `args.collect()` — снова без единого `clone`) и `run`: цикл по путям, `match` вместо `?` на `read_to_string`, ветка ошибки печатает `{path}: не удалось прочитать: {e}` в stderr и делает `continue`, найденные строки печатаются как `{path}: {line}`. Прогон на трёх файлах, один из которых не существует, даёт две найденные строки с префиксами, одно сообщение в stderr и код возврата 0; при `2>/dev/null` в stdout остаются только результаты.

### Г25.Ч1.З10

**Условие.** Настоящий `grep` различает исходы кодом возврата: 0 — совпадения найдены, 1 — не найдены, 2 — ошибка. Реализуйте эту схему: `run` должен вернуть признак «нашли или нет» (какой тип для этого честнее — `bool` в `Ok` или отдельный `enum`?), `main` — превратить его в код. Покройте тестами `Config::build` — оба отказа и успех; убедитесь, что сообщения об ошибках проверяемы без запуска бинарника.

**Решение.** Вопрос условия — `bool` или `enum` — это вопрос о том, кто будет читать код. `Ok(true)` в точке возврата не говорит ничего: «истина» может значить и «нашли», и «всё прошло гладко», и «файл был непустой». Заведём тип, который называет себя сам (`p1/z10/src/lib.rs`):

```rust
/// Чем кончился поиск: этот ответ `main` превращает в код возврата.
#[derive(Debug, PartialEq)]
pub enum Outcome {
    Found,
    NotFound,
}
```

`run` печатает найденное и отчитывается исходом. Обратите внимание на `for line in &results` — по ссылке: сам вектор нужен после цикла, чтобы спросить `is_empty()` (§15.2.1):

```rust

Первая: `unwrap_err()` требует `Debug` у **успешного** типа (ему надо напечатать `Ok(...)`, если ошибки не случилось), поэтому `Config` получает `#[derive(Debug)]`. Вторая: `assert_eq!` сравнивает `&'static str` с `&str` — сообщение об ошибке проверяется дословно, и любая переформулировка текста уронит тест. ### Г25.Ч2.З2

**Условие.** Добавьте в демонстрационный `main` чекпоинта 3 счётчик выполненных задач по образцу теста `pool_runs_all_tasks` и печатайте его после `drop(pool)`. Убедитесь, что он равен числу задач при любом размере пула — и объясните, какое свойство `Drop` это гарантирует.

**Решение.** Счётчик устроен дословно как в тесте `pool_runs_all_tasks`: `Arc<Mutex<i32>>`, клон на задачу, инкремент под замком (§23.2.2). `p2/z2/src/main.rs`:

```rust
fn main() {
    let start = Instant::now();
    let done = Arc::new(Mutex::new(0));
    let pool = ThreadPool::new(4);

    for id in 1..=8 {
        let done = Arc::clone(&done);
        pool.execute(move || {
            println!("задача {id}: начало");
            thread::sleep(Duration::from_millis(300));
            *done.lock().unwrap() += 1;
            println!("задача {id}: конец");
        });
    }

    drop(pool); // провожаем пул: Drop дождётся всех задач
    println!("выполнено задач: {}", done.lock().unwrap());
    println!("все задачи завершены за {:?}", start.elapsed());
}
```

Печать **после** `drop(pool)` — это и есть содержательная часть задания. Проверяем на трёх размерах пула (каталоги `z2_1`, `z2_2`, `z2_8` — те же файлы, отличается только число в `ThreadPool::new`):

Какое свойство `Drop` это гарантирует? Не одно, а связка из трёх, и все три — в четырёх строках `impl Drop for ThreadPool`:

1. **`drop` вызывается детерминированно** в точке `drop(pool)`, а не «когда-нибудь» (§22.1.2). Это делает строку `drop(pool)` барьером синхронизации: всё, что было запланировано до неё, завершится до того, как выполнится следующая строка.
2. **`drop(self.sender.take())` закрывает вход.** Пока жив хоть один отправитель, `recv` у воркера блокируется; как только последний умер и очередь опустела, `recv` возвращает `Err`, и воркер выходит из цикла (§23.1.3). Важно, что `Err` приходит **после** выдачи всех накопленных задач, а не вместо неё, — иначе счётчик был бы меньше восьми.
3. **`join` в цикле по `drain(..)` дожидается каждого воркера** (§23.1.1). Возврат из `join` означает, что поток завершился, — а завершиться он мог только выйдя из цикла, то есть выполнив все доставшиеся ему задачи.

Вместе это даёт нужное: после `drop(pool)` очередь пуста, все задачи выполнены, все потоки закончились — значит, счётчик финален, и прочитать его можно без всякой дополнительной синхронизации (замок нужен только потому, что данные лежат под `Mutex`). Уберите любой из трёх пунктов — и гарантии не станет: пул чекпоинта 2 (без `Drop`) полагался на слепой `sleep`, и там мы своими глазами видели строку, обрубленную на полуслове.

**Ответ.** Счётчик — `Arc<Mutex<i32>>` с клоном на задачу, инкремент внутри задачи, печать **после** `drop(pool)`. При пулах 1, 2, 4 и 8 он равен 8 всегда; меняется только общее время (2.40 с, 1.20 с, 610 мс, 301 мс). Гарантирует это связка свойств `Drop`: он вызывается детерминированно в точке `drop(pool)` (значит, служит барьером), сначала хоронит отправителя — и `recv` отдаёт `Err` только после того, как очередь опустела, — а затем `join`-ит каждого воркера, то есть возвращается лишь тогда, когда все потоки вышли из цикла. Иными словами, `drop(pool)` возвращает управление тогда и только тогда, когда каждая отданная задача выполнена.

**Вариант 2 (счётчик через канал).** Вместо разделяемого состояния — обратный канал: каждая задача шлёт свой номер, `main` собирает после проводов пула (`p2/z2b/src/main.rs`):

**Условие.** Замерьте каждую задачу отдельно: пусть задача в `pargrep` берёт свой `Instant::now()` и отправляет длительность в кортеже результата, а `main` печатает её рядом со счётчиком. Сравните сумму времён задач с общим временем прогона при 1 и 8 потоках — что показывает разница?

        pool.execute(move || {

            let result = match fs::read_to_string(&file) {
                Ok(contents) => {
                    Ok(minigrep::search_case_insensitive(&query, &contents).len())
                }
                Err(e) => Err(e),
            };
            tx.send((file, result, task_start.elapsed())).unwrap();

`main` печатает время рядом со счётчиком и подводит два итога — сумму времён задач и общее время:

### Г25.Ч2.З4

**Условие.** Разберите ⛔-вариант с `while let` из чекпоинта 2 по шагам: где начинается и где заканчивается жизнь `MutexGuard` в нём и в рабочем варианте с `let message = ...`? Почему прогон ⛔-варианта показал ровно одну задачу за раз — и почему при этом не пострадала корректность (все выполненные задачи выполнились правильно)?

**Решение.** Разберём обе формы по правилу времён жизни временных значений (R7, Destructors).

**Рабочая форма.**

```rust
                let message = receiver.lock().unwrap().recv();
```

Здесь три временных значения: результат `lock()` (`LockResult`), извлечённый из него `MutexGuard` и заимствование `Receiver` внутри `recv()`. Все они — временные значения **оператора `let`**, и все умирают в его конце, то есть на точке с запятой. `MutexGuard` в своём `Drop` отпирает замок (§23.2.1) — значит, замок жив ровно на время `lock()` + `recv()`, а в переменной `message` остаётся `Result<Job, RecvError>`, никак с замком не связанный. Дальше `job()` выполняется **без замка**: пока один воркер работает, остальные свободно берут следующие задачи.

**⛔-форма.**

```rust
            while let Ok(job) = receiver.lock().unwrap().recv() {
                job();
            }
```

Выражение-скрутиниз стоит в условии `while let`, а для `while let` (как и для `if let`) временные значения условия живут **до конца тела итерации**. `MutexGuard` попадает в их число — и держит замок всё время, пока крутится `job()`. Замок отпирается только на границе итерации, и тут же захватывается снова тем же потоком: остальные трое стоят у запертой двери.

Прогон подтверждает (`p2/pool_whilelet`, тот же демонстрационный `main` чекпоинта 2):

```
$ cargo run
задача 1: начало
задача 1: конец
задача 2: начало
задача 2: конец
задача 3: начало
задача 3: конец
задача 4: начало
главный поток выходит через 1.0005524s
```

Ровно одна задача за раз, «начало» никогда не встречается дважды подряд; за секунду слепого ожидания успели три задачи с хвостиком вместо восьми — и повторный прогон дал ту же картину до строки. Сравните с рабочей формой, где первые четыре «начало» идут подряд.

**Почему не пострадала корректность.** Замок в этой конструкции держится дольше нужного, но держится **правильно**: инвариант «одну задачу берёт ровно один воркер» никогда не нарушается, `recv` по-прежнему отдаёт каждую задачу единственному получателю, а `job()` выполняется целиком и один раз. Ошибка касается только **степени параллельности** — то есть производительности, — и в этом её коварство: программа компилируется, ничего не портит, отчёты санитайзеров чисты (да и нечего им ловить), тесты вроде `pool_runs_all_tasks` останутся зелёными, потому что все сто задач всё равно выполнятся — просто по очереди. Ловится такое только замером: строчки «начало/конец» чередуются вместо того, чтобы идти волнами. Потерянные задачи 5–8 — это не следствие замка, а следствие чекпоинта 2: там ещё нет `Drop`, и слепая секунда просто истекла раньше, чем очередь дошла до них. С `Drop` из чекпоинта 3 ⛔-форма выполнила бы все восемь задач — за 2,4 с вместо 0,6.

**Ответ.** В рабочей форме `let message = receiver.lock().unwrap().recv();` `MutexGuard` — временное значение оператора `let`: он рождается на `lock()` и умирает на точке с запятой, поэтому `job()` выполняется уже без замка. В форме `while let Ok(job) = receiver.lock().unwrap().recv()` временные значения условия живут до конца тела итерации, так что `MutexGuard` держит замок всё время работы `job()` и отпускает его лишь на границе итерации. Отсюда и прогон: строго одна задача за раз (1,0005 с слепого ожидания хватило на три задачи с хвостиком вместо восьми). Корректность при этом не страдает, потому что удержание замка нарушает не инвариант («задачу берёт ровно один воркер» соблюдается), а только параллельность: каждая выполненная задача выполнена правильно и один раз. Именно поэтому ошибка не ловится ни компилятором, ни тестами, ни санитайзером — только замером.

### Г25.Ч2.З5

**Условие.** Объясните, почему приёмник пришлось завернуть в `Arc<Mutex<...>>`: что именно не так с `receiver.clone()` (какой трейт не реализован и почему это не случайность — вспомните буквы m, p, s, c) и чем кончилось бы совместное чтение из одного приёмника без замка, будь оно возможно?

**Решение.** Три вопроса — три опыта.

**Что не так с `receiver.clone()`.** У приёмника попросту нет такого метода (`p2/z5/z5_clone.rs`):

```rust
    let tx2 = tx.clone(); // передатчик клонируется: multi-producer
    let rx2 = rx.clone(); // ⛔ приёмник — нет: single-consumer
```

```
$ rustc --edition 2024 z5_clone.rs
error[E0599]: no method named `clone` found for struct `std::sync::mpsc::Receiver<T>` in the current scope
 --> z5_clone.rs:8:18
  |
8 |     let rx2 = rx.clone(); // ⛔ приёмник — нет: single-consumer
  |                  ^^^^^ method not found in `std::sync::mpsc::Receiver<i32>`
```

Не реализован трейт `Clone` — и заметьте, что соседняя строка с `tx.clone()` компилятора не смутила. Это не упущение библиотеки, а расшифровка имени модуля: **mpsc** — multi-**p**roducer, **s**ingle-**c**onsumer. Передатчиков может быть сколько угодно (`Sender: Clone`), приёмник — ровно один. Так устроена сама очередь: её алгоритм рассчитан на то, что из хвоста читает единственный поток, и именно на этом допущении держится её скорость. Разрешить `Receiver::clone` значило бы поменять алгоритм — то есть сделать другую очередь (такие есть в экосистеме под именем mpmc).

**Что было бы, «будь оно возможно».** Проверим соседнюю дверь: раздать один приёмник воркерам без замка, через `Arc` (`p2/z5/z5_arc.rs`) — компилятор не пускает и туда:

```
$ rustc --edition 2024 z5_arc.rs
error[E0277]: `std::sync::mpsc::Receiver<i32>` cannot be shared between threads safely
  --> z5_arc.rs:13:36
   |
13 |           handles.push(thread::spawn(move || {
   |  ______________________-------------_^
...
   | |_________^ `std::sync::mpsc::Receiver<i32>` cannot be shared between threads safely
   |
   = help: the trait `Sync` is not implemented for `std::sync::mpsc::Receiver<i32>`
   = note: required for `Arc<std::sync::mpsc::Receiver<i32>>` to implement `Send`
```

Вот и ответ, и он важнее первого: `Receiver<T>` **не `Sync`** (§23.2.3) — то есть делиться им по ссылке между потоками запрещено на уровне типов, а раз `Arc<T>: Send` требует `T: Sync`, то и ручка `Arc<Receiver>` в чужой поток не уедет. Гипотетическое «совместное чтение без замка» кончилось бы гонкой данных: два потока одновременно правили бы внутренние указатели очереди — та самая UB, которую в C ловят TSan-ом по факту (§13.1.4), а в Rust не пускают на компиляции. `Mutex` здесь не украшение: он превращает `!Sync`-тип в разделяемый, потому что `Mutex<T>: Sync` при `T: Send` — доступ к содержимому возможен только по одному за раз, а значит, допущение «читатель один» соблюдается в каждый момент времени.

Что и подтверждает третий опыт — те же два воркера, но под замком (`p2/z5/z5_mutex.rs`):

```
$ rustc --edition 2024 z5_mutex.rs
$ ./z5_mutex.exe
воркер 0: 0
воркер 0: 2
воркер 0: 3
воркер 1: 1
готово
```

Работает — и попутно показывает свойство пула, которое стоит помнить: раздача задач **не равномерна**. Воркер 0 успел взять три сообщения из четырёх просто потому, что первым добежал до замка; никакой очерёдности `Mutex` не обещает (§23.2.1).

**Ответ.** `receiver.clone()` не проходит, потому что для `Receiver<T>` не реализован `Clone` (E0599: `no method named clone found for struct Receiver<T>`), тогда как у `Sender<T>` он есть. Это не случайность, а буквы m-p-s-c: multi-producer, single-consumer — очередь по построению рассчитана на единственного получателя, и на этом допущении держится её устройство. Совместное чтение без замка невозможно даже обходным путём: `Receiver<T>` не реализует `Sync`, поэтому `Arc<Receiver<T>>` не `Send` и в чужой поток не передаётся (E0277 с прямым `note: required for Arc<Receiver<i32>> to implement Send`). Будь такое возможно, два потока правили бы внутренности очереди одновременно — гонка данных и UB. `Arc<Mutex<Receiver<T>>>` решает обе задачи разом: `Arc` даёт совместное владение, `Mutex` — единственность читателя в каждый момент (и делает всю конструкцию `Sync`), так что допущение канала соблюдается, а воркеры берут задачи по очереди — но не поровну: в опыте один воркер забрал три сообщения из четырёх.

### Г25.Ч2.З6

**Условие.** В чекпоинте 4 мы отправляем счётчик, а не найденные строки. Объясните по цепочке типов, почему `tx.send(minigrep::search_case_insensitive(&query, &contents))` не пройдёт компиляцию. Затем почините: пусть задача отправляет `Vec<String>`, а `main` печатает первые три совпадения на файл. Какова цена решения и где она платится?

**Решение.** Сначала — цепочка типов, по которой видно отказ ещё до компилятора.

1. `search_case_insensitive(&query, &contents)` возвращает `Vec<&'a str>`, где `'a` — время жизни `contents` (§25.1.3).
2. `contents` — локальная переменная **замыкания**: она рождается в `read_to_string` и умирает на закрывающей скобке задачи.
3. `tx` имеет тип `Sender<T>`, и `T` фиксируется один раз на весь канал. Взяв `T = Vec<&'a str>`, мы обязали `'a` пережить сам канал — а он живёт в `main`, дольше любой задачи.
4. Вдобавок замыкание обязано быть `'static` (§25.2.1): оно уезжает в чужой поток и не вправе держать ссылок на чужой стек. Ссылка на `contents` этому не противоречит только потому, что `contents` — своя; но отправить её наружу — значит вынести ссылку за пределы жизни владельца.

Компилятор говорит то же самое, но точнее (`p2/z6_bad`):

```

...
17 |         let contents = fs::read_to_string(&file).unwrap();
   |             -------- binding `contents` declared here
18 |         tx.send(minigrep::search_case_insensitive(&query, &contents))
   |         --------------------------------------------------^^^^^^^^^--
   |         |                                                 |
   |         |                                                 borrowed value does not live long enough
   |         argument requires that `contents` is borrowed for `'1`
19 |             .unwrap();
20 |     });
   |     - `contents` dropped here while still borrowed

Первая же строка отчёта — про то, что «время жизни `'1` фигурирует в типе `tx`»: канал протащил требование к времени жизни через свой параметр типа, как и предсказывала цепочка.

**Починка.** Отправлять надо владеющие значения — `Vec<String>`; копия делается в задаче, перед отправкой (`p2/z6/src/main.rs`):

```rust

            let result = match fs::read_to_string(&file) {
                Ok(contents) => {
                    // Ломтики указывают в contents — перед отправкой копируем.

                        .into_iter()
                        .map(|line| line.to_string())
                        .collect();
                    Ok(hits)
                }
                Err(e) => Err(e),
            };
            tx.send((file, result)).unwrap();
        });
```

`main` печатает первые три совпадения на файл — `take(3)` по ссылкам, сам вектор нужен дальше для `len()`:

```rust
            Ok(hits) => {
                println!("{file}: {} совпадений", hits.len());

                    println!("    {line}");

```

**Цена решения — и где она платится.** Каждая найденная строка копируется в отдельное выделение кучи, и происходит это **в задаче**, то есть в рабочем потоке; затем вектор строк едет через канал (перемещением, не копией) и живёт в `main` до печати. На маленьких файлах не видно ничего, поэтому измерим на восьми файлах по 33 МБ, где совпадений 400 на файл:

На запросе, совпадающем с половиной файла, разница между «восемь `usize`» и «полфайла в куче» становится решающей.

**Ответ.** `tx.send(minigrep::search_case_insensitive(&query, &contents))` не компилируется, потому что `search_case_insensitive` возвращает `Vec<&'a str>` с `'a` от `contents`, а `contents` — локальная переменная замыкания; тип канала `Sender<Vec<&'a str>>` фиксирует это время жизни и требует, чтобы оно пережило сам канал, живущий в `main`. Компилятор так и пишет: `lifetime '1 appears in the type of tx`, `argument requires that contents is borrowed for '1`, `contents dropped here while still borrowed` (E0597). Починка — отправлять владеющие данные: в задаче `into_iter().map(|line| line.to_string()).collect::<Vec<String>>()`, в `main` печать `hits.iter().take(3)`. Цена — 3200 выделений и копирований на нагрузочном прогоне (523 мс против ~405 мс, то есть около четверти времени) плюс память под все найденные строки сразу; платится она в рабочем потоке, в момент, когда все восемь потоков и без того конкурируют за память.

### Г25.Ч2.З7

**Условие.** Уберите строку `drop(tx);` из `pargrep` и объясните — не запуская — что произойдёт и на какой строке программа застрянет. Потом проверьте запуском (Ctrl+C вас спасёт). Почему та же ошибка в один поток (§23.1.3) и здесь выглядит одинаково, хотя между каналом и приёмником теперь стоит пул?

**Решение.** Сначала — предсказание, не запуская.

Цикл `for (file, result) in rx` заканчивается тогда и только тогда, когда канал **закрыт**, то есть когда умер последний живой отправитель (§23.1.3). Считаем отправителей: один оригинал `tx`, созданный в `main`, и по клону на задачу. Клоны умирают вместе с замыканиями — каждый в момент, когда его задача доработала. А оригинал жив: он лежит в переменной `main` и умрёт только в конце `main`, куда управление не придёт, пока не кончится цикл приёма. Круг замкнулся: цикл ждёт смерти отправителя, отправитель ждёт конца цикла.

Значит, программа должна напечатать **все** результаты (задачи-то отработали и отчитались) и застрять на следующей попытке взять сообщение — то есть на строке `for (file, result) in rx {`, внутри неявного `next()`, который блокируется в `recv`. Строка «всего: … совпадений» не напечатается никогда.

Проверяем (`p2/z7`, `drop(tx)` закомментирован; вместо Ctrl+C — `timeout 10`, чтобы прогон попал в протокол):

```
$ timeout 10 ./target/debug/pargrep.exe 2 rust ../small1.txt ../small2.txt
../small2.txt: 3 совпадений
../small1.txt: 5 совпадений
$ echo $?
124
```

Оба файла обработаны, оба результата напечатаны, итога нет, процесс снят по таймауту (код 124). Предсказание подтвердилось до строки.

**Почему пул ничего не меняет.** Условие окончания приёма — свойство **канала**, а не того, кто в него пишет: приёмник считает живых отправителей, а не потоки, задачи или воркеров. Пул стоит между `main` и задачами, но он не владеет ни `tx`, ни его клонами — клоны захвачены замыканиями и живут ровно столько, сколько живёт замыкание. Поэтому арифметика та же, что в однопоточном примере §23.1.3: пока хоть один `Sender` жив, `recv` обязан ждать — вдруг ещё пришлют. Единственная разница — декорации: в §23.1.3 забытый отправитель лежал прямо в `main` рядом с циклом, здесь он лежит в `main` рядом с пулом. Отсюда и правило, одинаковое в обоих случаях: **у канала должен быть момент, когда все передатчики мертвы**, и организовать его — обязанность того, кто канал создал.

Полезно заметить и то, чего в отчёте нет: строк «ждём воркера …» не появилось. `drop(pool)` стоит в конце `main`, куда управление не дошло, — то есть в этой программе висит не только приём, но и всё завершение целиком.

**Ответ.** Без `drop(tx)` программа напечатает все результаты и застрянет навсегда на строке `for (file, result) in rx {` — внутри неявного `next()`, блокирующегося в `recv`; строка с итогом не напечатается. Причина: цикл приёма кончается только при закрытии канала, а канал закрыт лишь тогда, когда умер последний отправитель; клоны умирают вместе с задачами, но оригинал `tx` жив до конца `main`, до которого управление не дойдёт, пока идёт цикл. Прогон подтверждает: оба файла обработаны и напечатаны, итога нет, `timeout 10` снимает процесс с кодом 124. Пул на это не влияет, потому что условие окончания приёма — свойство канала (счётчик живых `Sender`), а не потоков: пул не владеет ни оригиналом, ни клонами, он лишь исполняет замыкания, внутри которых клоны живут и умирают.

### Г25.Ч2.З8

**Условие.** Спроектируйте `ThreadPool::build(size) -> Result<ThreadPool, PoolCreationError>` — версию без паники (R1 предлагает это упражнением в гл. 21.2). `PoolCreationError` — свой тип ошибки (§18.2.1); `main` `pargrep` переведите на `build`. В каком слое программы уместнее решать, паника это или ошибка, — в библиотеке или у вызывающего? Обоснуйте выбором сигнатур.

**Решение.** Тип ошибки — по образцу §18.2.1: своя структура, `Display` для человека, `Error` для совместимости с `Box<dyn Error>` (`p2/z8/src/lib.rs`):

```rust
/// Почему пул не удалось создать.
#[derive(Debug, PartialEq)]
pub struct PoolCreationError {
    requested: usize,
}

impl fmt::Display for PoolCreationError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(
            f,
            "в пуле должен быть хотя бы один поток, запрошено {}",
            self.requested
        )
    }
}

impl Error for PoolCreationError {}
```

Поле `requested` — не украшение: сообщение об ошибке, называющее полученное значение, экономит вызывающему один заход в отладчик. Сама `build` отличается от `new` двумя строками — и заголовком док-комментария: `# Panics` сменился на `# Errors` (конвенция §20.2.3):

```rust
    /// Создаёт пул с `size` рабочими потоками.
    ///
    /// # Errors
    ///
    /// Возвращает `PoolCreationError`, если `size` равен нулю.
    pub fn build(size: usize) -> Result<ThreadPool, PoolCreationError> {
        if size == 0 {
            return Err(PoolCreationError { requested: size });
        }
```

В `main` пакета `pargrep` исчезает ручная проверка `if threads == 0` — знание о том, что ноль недопустим, теперь живёт в одном месте, в библиотеке:

```rust
    let start = Instant::now();
    // Проверку «ноль потоков» держит библиотека — и отдаёт значением.
    let pool = match ThreadPool::build(threads) {
        Ok(pool) => pool,
        Err(e) => {
            eprintln!("не удалось создать пул: {e}");
            process::exit(1);
        }
    };
```

../small2.txt: 3 совпадений

**Типичная неверная попытка** (мы в неё и попали при первом прогоне). Написать тест естественным образом — `let err = ThreadPool::build(0).unwrap_err();` — не выходит:

```
error[E0277]: `ThreadPool` doesn't implement `Debug`
   --> src\lib.rs:108:40
    |
108 |         let err = ThreadPool::build(0).unwrap_err();
    |                                        ^^^^^^^^^^ unsatisfied trait bound
    |
help: the trait `Debug` is not implemented for `ThreadPool`
   --> src\lib.rs:26:1
    |
 26 | pub struct ThreadPool {
    | ^^^^^^^^^^^^^^^^^^^^^
    = note: add `#[derive(Debug)]` to `ThreadPool` or manually `impl Debug for ThreadPool`
note: required by a bound in `Result::<T, E>::unwrap_err`
```

Причина логичная: `unwrap_err` обязан напечатать содержимое `Ok`, если ошибки не случилось, — значит, требует `Debug` **от успешного** типа. Заводить `Debug` пулу ради одного теста незачем; достаточно спросить ошибку через `Option`:

```rust
        // .err().unwrap(), а не .unwrap_err(): второй потребовал бы Debug у ThreadPool.
        let err = ThreadPool::build(0).err().unwrap();
```

**В каком слое решать — паника или ошибка.** Ответ виден из сигнатур, и он двухступенчатый.

Сигнатура `fn new(size: usize) -> ThreadPool` — это обещание «получится всегда»; раз возвращаемый тип не оставляет места отказу, единственный способ сообщить о недопустимом входе — паника, а паника означает «это ошибка программиста, чините код» (§18.1.1). Сигнатура `fn build(size: usize) -> Result<ThreadPool, PoolCreationError>` говорит обратное: «отказ — законный исход, обработайте его». Библиотека **не может знать**, откуда пришло число: если это литерал в коде (`ThreadPool::new(4)`), ноль — опечатка автора и паника уместна; если это `args[1].parse()`, как у нас, ноль — обычный пользовательский ввод, и паниковать из-за него так же неправильно, как паниковать из-за несуществующего файла.

Отсюда вывод: решать должен **вызывающий**, а библиотека обязана дать ему такую возможность — то есть предложить обе двери. Ровно так устроена и стандартная библиотека (`Vec::with_capacity` паникует, `Vec::try_with_capacity` возвращает `Result`). Наш `pargrep` берёт число у пользователя и потому выбирает `build`; демонстрационный `main` чекпоинта 3, где размер пула — литерал, спокойно остаётся с `new`.

**Ответ.** `PoolCreationError` — структура с полем `requested`, реализующая `Display` («в пуле должен быть хотя бы один поток, запрошено 0») и `Error`; `ThreadPool::build(size) -> Result<ThreadPool, PoolCreationError>` возвращает `Err` при нуле, док-комментарий получает раздел `# Errors` вместо `# Panics`. В `main` пакета `pargrep` ручная проверка `if threads == 0` удаляется — знание переезжает в библиотеку, а `main` разбирает `Result`; прогон с нулём печатает сообщение и выходит с кодом 1, обычный прогон не изменился. Решать «паника или ошибка» уместнее у **вызывающего**, и доказывают это сигнатуры: `-> ThreadPool` обещает, что отказа не бывает, и оставляет для недопустимого входа только панику («это ошибка программиста»), а `-> Result<…>` объявляет отказ законным исходом. Библиотека не знает, литерал перед ней или пользовательский ввод, поэтому её дело — предложить обе двери (как `Vec::with_capacity` и `Vec::try_with_capacity`), а выбор двери — дело клиента: `pargrep` берёт число из аргументов и выбирает `build`, демонстрация чекпоинта 3 с литералом `4` остаётся с `new`. Попутная находка: `unwrap_err()` в тесте не собирается — E0277 «`ThreadPool` doesn't implement `Debug`», потому что `unwrap_err` печатает содержимое `Ok`; лечится не `derive(Debug)` у пула, а `.err().unwrap()`.

### Г25.Ч2.З9

**Условие.** Результаты приходят в порядке завершения задач. Сделайте вывод устойчивым: собирайте пары `(файл, результат)` в вектор и после конца приёма отсортируйте по имени файла (подойдёт метод `Vec::sort` — R9). Почему сортировать лучше в `main`, а не заставлять задачи «ждать своей очереди» на отправку?

**Решение.** Приём остаётся прежним — меняется только то, что с ним делать: не печатать на лету, а собрать и упорядочить (`p2/z9/src/main.rs`):

```rust
    // Приём — в порядке завершения; печать — в порядке имён.
    let mut results: Vec<(String, Result<usize, io::Error>)> = rx.iter().collect();
    results.sort_by(|a, b| a.0.cmp(&b.0));
```

`rx.iter().collect()` — тот же цикл приёма, только сразу в вектор; он по-прежнему заканчивается сам, когда умрёт последний клон отправителя. Сортировка — `sort_by` по первому полю кортежа: `Vec::sort` без аргументов здесь не подойдёт, потому что `io::Error` не реализует `Ord`, а значит, кортеж целиком не сравним; сравниваем только имя. Три прогона на четырёх файлах, поданных в перемешанном порядке:

```
$ ./target/release/pargrep.exe 4 rust ../data/big8.txt ../data/big1.txt ../data/big5.txt ../data/big3.txt
../data/big1.txt: 400 совпадений
../data/big3.txt: 400 совпадений
../data/big5.txt: 400 совпадений
../data/big8.txt: 400 совпадений
всего: 1600 совпадений за 279.5464ms
```

Второй и третий прогоны дали ту же четвёрку строк в том же порядке (менялось только время). Для сравнения — исходный `pargrep` на тех же данных, три прогона подряд:

```
=== прогон 1
../data/big3.txt: 400 совпадений
../data/big5.txt: 400 совпадений
../data/big8.txt: 400 совпадений
../data/big1.txt: 400 совпадений
=== прогон 2
../data/big1.txt: 400 совпадений
../data/big5.txt: 400 совпадений
../data/big3.txt: 400 совпадений
../data/big8.txt: 400 совпадений
=== прогон 3
../data/big3.txt: 400 совпадений
../data/big5.txt: 400 совпадений
../data/big1.txt: 400 совпадений
../data/big8.txt: 400 совпадений
```

Три прогона — три разных порядка: наглядная иллюстрация того, что «порядок завершения» — это не порядок, а погода.

**Почему сортировать в `main`, а не заставлять задачи ждать своей очереди.** Четыре довода, от практического к принципиальному.

1. **Ожидание очереди убивает параллельность.** Чтобы задачи отправляли результаты по порядку, каждая закончившая обязана дождаться всех предыдущих. Задача №8, отработавшая первой, будет держать своего воркера (или блокироваться на условной переменной), пока не отчитается №1, — в пределе пул выродится в последовательное исполнение, ровно как в ⛔-варианте с `while let` (Г25.Ч2.З4). Мы заплатили бы всей выгодой части 25.2 за косметику вывода.
2. **Это лишняя синхронизация — то есть лишний источник ошибок.** Понадобился бы разделяемый «номер, чья очередь», замок и оповещение; каждая такая конструкция — кандидат на взаимную блокировку (§23.2.4). Сортировка восьми кортежей не может заблокироваться никак.
3. **Цена несопоставима.** Упорядочивание — это доли микросекунды на восьми элементах против сотен миллисекунд полезной работы. Оптимизировать надо то, что дорого.
4. **Ответственность на месте.** Задача знает только про свой файл; порядок — свойство **всего набора**, и знает его только тот, кто набор собрал. Отдав упорядочивание в `main`, мы оставили задачам ровно одну обязанность — считать, а `main` — ровно одну — оформлять. Это та же граница «библиотека считает, `main` оформляет», что и в части 25.1.

**Ответ.** В `main` цикл приёма заменяется на `let mut results: Vec<(String, Result<usize, io::Error>)> = rx.iter().collect();` с последующей `results.sort_by(|a, b| a.0.cmp(&b.0))` — сравниваем только имя файла, потому что `io::Error` не сравним и `Vec::sort` для кортежа целиком не подойдёт. Три прогона подряд дают один и тот же порядок строк, тогда как исходный `pargrep` на тех же данных выдал три разных. Сортировать надо в `main`, потому что «отправлять по очереди» означало бы заставить закончившие задачи ждать предыдущих — то есть выродить пул в последовательное исполнение и добавить синхронизацию, способную заблокироваться; при этом порядок — свойство всего набора результатов, известное только собравшему их `main`, а стоит сортировка восьми элементов неизмеримо меньше, чем сотни миллисекунд работы задач.

### Г25.Ч2.З10

**Условие.** Доведите `pargrep` до grep-совместимости: коды возврата 0/1/2 (совпадения есть / нет / была ошибка чтения) и уважение к `IGNORE_CASE` — без переменной ищите с учётом регистра, как `minigrep` из Ч1. Не забудьте: решение о коде возврата можно принять только **после** конца цикла приёма — объясните, почему.

**Решение.** Обе доработки затрагивают только `main` пакета — библиотека `ThreadPool` не меняется вовсе.

**Регистр.** Флаг читается один раз, до старта пула, и захватывается замыканиями по значению (`bool` — `Copy`, каждой задаче достаётся своя копия, §23.1.2):

```rust
    let ignore_case = env::var("IGNORE_CASE").is_ok();
```

```rust
                Ok(contents) => {
                    let count = if ignore_case {
                        minigrep::search_case_insensitive(&query, &contents).len()
                    } else {
                        minigrep::search(&query, &contents).len()
                    };
                    Ok(count)
                }
```

**Коды возврата.** Все три исхода grep: 0 — что-то нашли, 1 — не нашли ничего, 2 — была ошибка чтения. Копим два факта во время приёма и выносим приговор после цикла:

```rust
    let mut total = 0;
    let mut had_error = false;
    for (file, result) in rx {
        match result {
            Ok(count) => {
                println!("{file}: {count} совпадений");
                total += count;
            }
            Err(e) => {
                eprintln!("{file}: не удалось прочитать: {e}");
                had_error = true;
            }
        }
    }

    println!("всего: {total} совпадений за {:?}", start.elapsed());

    // Приговор выносится только здесь: до конца приёма итог неизвестен.
    let code = if had_error {
        2
    } else if total > 0 {
        0
    } else {
        1
    };
    process::exit(code);
```

Ошибки разбора аргументов тоже получают код 2 — они той же природы, что и ошибка чтения: не «ничего не нашли», а «не смогли выполнить работу».

**Почему решение о коде можно принять только после конца цикла приёма.** Потому что до этого момента картины ещё нет — и не может быть по устройству программы. Результаты приходят **в порядке завершения задач**, который недетерминирован (§23.1.1, наглядно — в Г25.Ч2.З9): файл с ошибкой может оказаться первым, а может последним. Приняв решение раньше, мы получили бы код возврата, зависящий от расписания ОС: один и тот же запуск на тех же данных выдавал бы то 0, то 2. Кроме того, оба факта по своей природе — свойства **всего набора**: «нашли хоть где-нибудь» и «была ли хоть одна ошибка» — кванторы существования по всем файлам, а проверить квантор можно только просмотрев всё. Конец цикла `for … in rx` и есть точка, где набор становится полным: цикл кончается, когда умер последний отправитель, то есть когда отчиталась последняя задача.

Одна честная деталь напоследок: `process::exit` не выполняет деструкторы (§25.1.2), поэтому `Drop` пула не отработает — в выводе нет ни одной строки «ждём воркера». Здесь это безопасно ровно потому, что конец цикла приёма **доказывает**: все задачи отчитались, воркеры простаивают на `recv`, терять нечего. Если бы после цикла оставалась незавершённая работа, `drop(pool)` следовало бы поставить явно перед `process::exit`.

**Ответ.** В `main` добавляется `let ignore_case = env::var("IGNORE_CASE").is_ok();` (флаг — `Copy`, каждой задаче достаётся своя копия), и задача выбирает между `search_case_insensitive` и `search`. Во время приёма копятся `total` и `had_error`, после цикла считается код: `2`, если была ошибка чтения (или разбора аргументов), иначе `0` при `total > 0` и `1` при нуле; выход — `process::exit(code)`. Прогоны: совпадения есть — 0, совпадений нет — 1, файл не прочитан — 2 (даже когда в других файлах совпадения нашлись: ошибка перекрывает находки, как у настоящего `grep`); `IGNORE_CASE=1` даёт 8 совпадений против 3 без него. Раньше конца цикла приёма решение принять нельзя: результаты приходят в недетерминированном порядке завершения, поэтому код возврата зависел бы от расписания ОС, а оба нужных факта — «нашли хоть где-то» и «была ли хоть одна ошибка» — относятся ко всему набору файлов и известны только после того, как отчиталась последняя задача.

Отдельного разговора стоит вопрос из Г25.Ч1.З7 — «какой артефакт невозможен». Удваивается не число строк вывода, а число **совпадений**: файл `twice.txt` из одной физической строки в 1544 байта, где `Rust` стоит по обе стороны границы 1023, даёт два срабатывания `strstr` и два вызова `fputs` — но в выводе по-прежнему один перевод строки (`wc -l` → 1, `wc -c` → 1545), потому что куски печатаются подряд и склеиваются обратно в исходную строку. Больше переводов строки, чем строк в файле, `fgets`-цикл выдать не может в принципе: перевод строки в физической строке ровно один и достаётся он последнему куску, а каждый кусок печатается не более одного раза. Реальный артефакт этого класса — обратного знака: если совпал первый кусок, а последний (тот, что несёт перевод строки) не совпал, напечатанное слипается со следующей найденной строкой, и строк становится **меньше** (файл `glue.txt`: два совпадения из разных физических строк — одна строка вывода против двух у Rust-версии).
