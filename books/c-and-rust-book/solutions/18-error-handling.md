## Часть 18.1. panic! и Result: два рода отказов

### Г18.Ч1.З1

**Условие.** Напишите `fn check_positive(x: i32)`, которая паникует с сообщением `отрицательное значение: {x}` для отрицательных аргументов и печатает `{x} — годится` для остальных. Вызовите её для `7`, `-3`, `100`. До запуска предскажите: что напечатается, что нет, из каких частей состоит сообщение паники и какой код выхода покажет `echo $?` (Git Bash) или `$LASTEXITCODE` (PowerShell). Запустите ещё раз с `RUST_BACKTRACE=1` и найдите в трассировке свой кадр.

**Решение.** *Предсказание.* Первый вызов печатает `7 — годится`. Второй паникует — и на этом всё: третий вызов **не выполнится никогда**, потому что паника по умолчанию завершает процесс (§18.1.1). Сообщение паники должно состоять из четырёх частей: строка `thread 'main' (номер) panicked at файл:строка:колонка:`, наш текст с подставленным значением, и подсказка про `RUST_BACKTRACE`. Код выхода — 101 (наблюдение эталона, а не гарантия языка).

Файл `p1.rs`:

```rust
fn check_positive(x: i32) {
    if x < 0 {
        panic!("отрицательное значение: {x}");
    }
    println!("{x} — годится");
}

fn main() {
    check_positive(7);
    check_positive(-3);
    check_positive(100);
}
```

```
7 — годится

thread 'main' (8124) panicked at p1.rs:3:9:
отрицательное значение: -3
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
[exit code: 101]
```

Строка `[exit code: 101]` — это не вывод программы, а печать `$?` сразу после запуска (в скрипте стенда `echo "[exit code: $?]"`); в Git Bash то же самое даёт `./p1.exe; echo $?`.

Разбор по частям — ровно то, что предсказывали:

| Часть сообщения | Что означает |
|---|---|
| `thread 'main' (8124)` | имя потока и его служебный номер; **номер свой при каждом запуске** (§14.2.2) |
| `panicked at p1.rs:3:9` | файл, строка и колонка **макроса `panic!`** — не места вызова функции |
| `отрицательное значение: -3` | наш текст; `{x}` подставлен форматированием, как в `println!` |
| `note: run with RUST_BACKTRACE=1 …` | подсказка рантайма, а не наш код |

Обратите внимание на `3:9` — это позиция самого `panic!`, а не строки `check_positive(-3)` в `main`. Место паники всегда указывает, **где рвануло**, а не кто виноват; за «кто вызвал» отвечает трассировка.

Второй запуск, с переменной окружения (`RUST_BACKTRACE=1 ./p1.exe`; пути внутрь тулчейна сокращены):

```
7 — годится

thread 'main' (13188) panicked at p1.rs:3:9:
отрицательное значение: -3
stack backtrace:
   0: __rustc::rust_begin_unwind
             at …/panicking.rs:689:5
   1: core::panicking::panic_fmt
             at …/panicking.rs:80:14
   2: p1::check_positive
   3: p1::main
   4: <fn() as core::ops::function::FnOnce<()>>::call_once
note: Some details are omitted, run with `RUST_BACKTRACE=full` for a verbose backtrace.
[exit code: 101]
```

Свой кадр — **номер 2, `p1::check_positive`**: первый сверху кадр, чьё имя начинается с имени нашего крейта (`p1::`). Кадры 0 и 1 — внутренности механизма паники, кадры 3 и 4 — те, кто нас вызвал (`main` и служебная обёртка запуска). В §18.1.1 таких служебных кадров было три (`0`, `1`, `2: core::panicking::panic_bounds_check`), потому что там паниковал индексатор вектора; у явного `panic!` проверки индекса нет — и кадр `panic_bounds_check` не появляется. Правило чтения от этого не меняется: **сверху вниз до первого своего кадра**.

**Ответ:** программа — листинг `p1.rs`. Печатается только `7 — годится`; вызов `check_positive(-3)` паникует, а `check_positive(100)` **не выполняется**. Сообщение состоит из четырёх частей: `thread 'main' (8124)` (имя потока и его номер, меняется от запуска), `panicked at p1.rs:3:9` (файл, строка и колонка **макроса `panic!`**), сам форматированный текст `отрицательное значение: -3` и подсказка про `RUST_BACKTRACE=1`. Код выхода — **101** (`echo $?`; на эталонной машине — стандартом языка номер не обещан). С `RUST_BACKTRACE=1` свой кадр — **`2: p1::check_positive`**: кадры 0–1 принадлежат механизму паники, 3–4 — вызывающим.

### Г18.Ч1.З2

**Условие.** Каталог паник: воспроизведите три знакомые паники минимальными программами — индекс `v[5]` в векторе из трёх элементов, срез `&s[0..1]` по строке `"привет"`, `unwrap()` на `None`. Выпишите три сообщения и сверьте с таблицей §18.1.1 и первоисточниками (§17.1.1, §17.1.4, §16.2.3). Что общего у всех трёх сообщений (структура, место, подсказка)?

**Решение.** Три программы, потому что каждая паника завершает процесс: в одной программе до второй строки дело бы не дошло. Файл `p2a.rs`:

```rust
fn main() {
    let v = vec![10, 20, 30];
    println!("{}", v[5]);
}
```

```
thread 'main' (27316) panicked at p2a.rs:3:21:
index out of bounds: the len is 3 but the index is 5
```

Файл `p2b.rs`:

```rust
fn main() {
    let s = String::from("привет");
    println!("{}", &s[0..1]);
}
```

```
thread 'main' (29248) panicked at p2b.rs:3:22:
end byte index 1 is not a char boundary; it is inside 'п' (bytes 0..2 of string)
```

Файл `p2c.rs`:

```rust
fn main() {
    let x: Option<i32> = None;
    println!("{}", x.unwrap());
}
```

```
thread 'main' (7408) panicked at p2c.rs:3:22:
called `Option::unwrap()` on a `None` value
```

(В каждом случае за приведёнными строками идёт одна и та же `note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace`, а процесс завершается кодом 101.)

*Сверка с первоисточниками.* Все три текста совпадают с таблицей §18.1.1 с точностью до чисел нашего опыта: `the len is 3 but the index is 5` против `… index is 99` в §17.1.1 — та же формула с нашими числами; сообщение про границу символа — из §17.1.4, где `&s[0..1]` по строке `"привет"` разрезал двухбайтовую `'п'` (UTF-8: кириллическая буква занимает два байта, а байтовый индекс 1 приходится на её середину); `called `Option::unwrap()` on a `None` value` — дословно из §16.2.3.

*Что общего.* Три разные библиотечные операции — а форма отказа одна:

- **структура** — три строки: `thread 'имя' (номер) panicked at место:` → одна строка причины → `note:` с подсказкой;
- **место** — `файл:строка:колонка` **нашего** кода: `p2a.rs:3:21` указывает на `v[5]`, `p2b.rs:3:22` — на `&s[0..1]`, `p2c.rs:3:22` — на `.unwrap()`. Ни одна паника не показала внутренностей стандартной библиотеки, хотя рвануло именно там: за это отвечает специальный механизм отслеживания вызывающего (`#[track_caller]`, R9), и он же делает `unwrap` пригодным для диагностики;
- **подсказка** — одинаковая и всегда: трассировка по `RUST_BACKTRACE=1`;
- **причина** — одна строка с конкретикой: длина и индекс, байтовый индекс и разрезанный символ, имя метода и вариант. Никаких «segmentation fault» и никакого «повезло»: сравните с §13.1.1, где то же самое обращение за границу в C давало UB — тишину, мусор или падение без адреса.

**Ответ:** три сообщения (без общей для всех строки `note:`):

| Программа | Сообщение |
|---|---|
| `p2a.rs` (`v[5]`, длина 3) | `index out of bounds: the len is 3 but the index is 5` |
| `p2b.rs` (`&s[0..1]` по `"привет"`) | `end byte index 1 is not a char boundary; it is inside 'п' (bytes 0..2 of string)` |
| `p2c.rs` (`unwrap` на `None`) | `` called `Option::unwrap()` on a `None` value `` |

Общее у всех трёх: одинаковая **структура** (заголовок `thread 'main' (номер) panicked at файл:строка:колонка:` → строка причины → `note:` про `RUST_BACKTRACE=1`), **место** — координаты нашей строки, а не внутренностей стандартной библиотеки (`#[track_caller]`), одинаковая **подсказка** и **код выхода 101**. Причина всегда конкретна и однострочна — паника определена и диагностируема, в отличие от UB в C (§13.1.1).

### Г18.Ч1.З3

**Условие.** Откройте match-ем несуществующий файл и напечатайте ошибку двумя способами: `{e}` и `{e:?}`. Затем создайте файл и покажите ветку успеха. Объясните: какая форма печати для пользователя, какая для программиста, и откуда берётся текст `The system cannot find the file specified.` (почему у читателя с Linux он будет другим).

**Решение.** Одна программа делает всё три шага подряд: пробует открыть, печатает обе формы ошибки, создаёт файл, открывает снова. Файл `p3.rs`:

```rust
use std::fs::File;

fn main() {
    // 1) файла нет: одна и та же ошибка, напечатанная двумя способами
    match File::open("notes.txt") {
        Ok(f) => println!("opened: {f:?}"),
        Err(e) => {
            println!("Display  {{e}}   -> {e}");
            println!("Debug    {{e:?}} -> {e:?}");
        }
    }

    // 2) создаём файл и повторяем попытку — теперь сработает ветка успеха
    match File::create("notes.txt") {
        Ok(_) => println!("created notes.txt"),
        Err(e) => panic!("не удалось создать notes.txt: {e}"),
    }
    match File::open("notes.txt") {
        Ok(f) => println!("opened: {f:?}"),
        Err(e) => println!("still failing -> {e}"),
    }
}
```

Двойные фигурные скобки `{{e}}` в строке формата — способ напечатать саму скобку (экранирование в форматных строках, R9); без удвоения `{e}` было бы подстановкой.

Запуск в каталоге, где `notes.txt` нет (путь в отладочной печати сокращён):

```
Display  {e}   -> The system cannot find the file specified. (os error 2)
Debug    {e:?} -> Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
created notes.txt
opened: File { handle: 0xe4, path: "\\\\?\\C:\\…\\notes.txt" }
```

Повторный запуск — файл уже есть, срабатывает ветка успеха с самого начала:

```
opened: File { handle: 0xc4, path: "\\\\?\\C:\\…\\notes.txt" }
created notes.txt
opened: File { handle: 0xc4, path: "\\\\?\\C:\\…\\notes.txt" }
```

Мимоходом видна разница `open` и `create` из §18.1.2: `File::create` во втором запуске не пожаловался на существующий файл, а **обнулил** его (у нас он и так был пуст).

*Две формы печати.* `{e}` — это **Display**: одна фраза от операционной системы, годная для человека. `{e:?}` — **Debug** (§16.1.3): структура значения целиком, `Os { code: 2, kind: NotFound, message: … }`, — то, что нужно программисту: числовой код, категория `ErrorKind` (по ней ветвятся, §18.1.2) и текст. Правило границы: пользователю — `{e}`, в отладку, в лог, в панику — `{e:?}`.

*Откуда текст.* Строку `The system cannot find the file specified.` не сочиняли ни `std`, ни компилятор: это сообщение **операционной системы** по коду ошибки. `os error 2` — тот самый код, который в C приезжал в глобальной `errno` под именем `ENOENT` (§10.1.1), а текст к нему в C доставал `perror`/`strerror`. Отсюда и ответ про Linux: на нём тот же код 2 назван по-другому, и `{e}` напечатает `No such file or directory (os error 2)`. Более того, текст зависит и от языка системы. Практический вывод (он же — «подводный камень» §18.1.2): **ветвить логику по тексту нельзя**, для этого есть `e.kind()`; текст — только для показа человеку.

**Ответ:** программа — листинг `p3.rs`. Формы печати: `{e}` — **Display**, `The system cannot find the file specified. (os error 2)` — для пользователя; `{e:?}` — **Debug**, `Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }` — для программиста (виден код и категория `ErrorKind`). После `File::create` ветка успеха печатает `File { handle: 0xe4, path: "\\\\?\\C:\\…\\notes.txt" }` (дескриптор и путь свои при каждом запуске). Текст ошибки выдаёт **операционная система** по коду `os error 2` (аналог `errno == ENOENT` из §10.1.1); на Linux тот же код даст `No such file or directory`, а на локализованной системе — перевод. Поэтому ветвиться нужно по `e.kind()`, а не по подстроке сообщения.

### Г18.Ч1.З4

**Условие.** *(понимание)* Приём «спроси компилятор»: узнайте с помощью заведомо неверной аннотации `let x: u32 = ...` полные типы результатов `File::create("t.txt")`, `vec![1, 2].pop()` и `File::open("t.txt")` с последующим `.metadata()` (подсказка: для последнего сначала получите `File` честно). Для каждого объясните по тексту E0308, что за `T` и `E` (или `T` у `Option`) внутри.

**Решение.** Приём из §18.1.2: компилятор всё равно печатает найденный тип в тексте E0308, значит, достаточно потребовать заведомо не тот тип. Три ⛔-программы — три ответа справочной службы.

⛔ Файл `p4a.rs`:

```rust
use std::fs::File;

fn main() {
    let x: u32 = File::create("t.txt");
    println!("{x}");
}
```

```
error[E0308]: mismatched types
 --> p4a.rs:4:18
  |
4 |     let x: u32 = File::create("t.txt");
  |            ---   ^^^^^^^^^^^^^^^^^^^^^ expected `u32`, found `Result<File, Error>`
  |            |
  |            expected due to this
  |
  = note: expected type `u32`
             found enum `Result<File, std::io::Error>`
```

Читаем последнюю строку — она полнее верхней, там типы записаны с путями: `Result<File, std::io::Error>`. Значит, `T` = `File` (дескриптор созданного файла, владелец ресурса), `E` = `std::io::Error` (отказ ОС: нет прав, каталог не существует, диск заполнен). То же самое, что у `File::open` из §18.1.2, — и это логично: обе функции возвращают одно и то же русло успеха.

⛔ Файл `p4b.rs`:

```rust
fn main() {
    let x: u32 = vec![1, 2].pop();
    println!("{x}");
}
```

```
error[E0308]: mismatched types
 --> p4b.rs:2:18
  |
2 |     let x: u32 = vec![1, 2].pop();
  |            ---   ^^^^^^^^^^^^^^^^ expected `u32`, found `Option<{integer}>`
  |            |
  |            expected due to this
  |
  = note: expected type `u32`
             found enum `Option<{integer}>`
help: consider using `Option::expect` to unwrap the `Option<{integer}>` value, panicking if the value is an `Option::None`
  |
2 |     let x: u32 = vec![1, 2].pop().expect("REASON");
  |                                  +++++++++++++++++
```

Здесь `Option`, а не `Result`: у `pop` нет причины отказа — вектор либо пуст, либо нет (§17.1.1, правило выбора между `Option` и `Result` — §18.1.2). А `T` записан необычно: **`{integer}`** — это не тип, а «ещё не зафиксированное целое»: литералы `1, 2` не получили конкретного типа, потому что аннотация, которая должна была его задать, оказалась несовместимой. Напиши мы `let v: Vec<i64> = vec![1, 2];`, в сообщении стояло бы `Option<i64>`. Приятный бонус — `help`: компилятор предлагает `expect("REASON")` и даже показывает, куда его вписать.

⛔ Файл `p4c.rs` (подсказка условия: `File` сначала надо получить честно — `metadata()` есть у файла, а не у `Result`):

```rust
use std::fs::File;

fn main() {
    let f = File::open("t.txt").unwrap();
    let x: u32 = f.metadata();
    println!("{x}");
}
```

```
error[E0308]: mismatched types
 --> p4c.rs:5:18
  |
5 |     let x: u32 = f.metadata();
  |            ---   ^^^^^^^^^^^^ expected `u32`, found `Result<Metadata, Error>`
  |            |
  |            expected due to this
  |
  = note: expected type `u32`
             found enum `Result<Metadata, std::io::Error>`
```

`T` = `Metadata` — сведения о файле (размер, права, времена; `.len()` из §18.1.3 — как раз метод `Metadata`), `E` = снова `std::io::Error`: даже у открытого файла запрос метаданных — обращение к ОС, которое может не удаться. Заметьте, что `unwrap()` в четвёртой строке ни на что не повлиял: программа не собралась, значит, и не запускалась — `t.txt` не понадобился.

**Ответ:** три ⛔-программы (`p4a.rs`, `p4b.rs`, `p4c.rs`) и три ответа компилятора:

| Выражение | Найденный тип | Что внутри |
|---|---|---|
| `File::create("t.txt")` | `Result<File, std::io::Error>` | `T` = `File` (дескриптор-владелец), `E` = ошибка ОС |
| `vec![1, 2].pop()` | `Option<{integer}>` | `T` = целое, тип которого ещё не зафиксирован (`{integer}` — не имя типа, а «литерал без решения»); причины отказа нет — потому `Option`, а не `Result` |
| `f.metadata()` | `Result<Metadata, std::io::Error>` | `T` = `Metadata` (у неё `.len()` — размер), `E` = ошибка ОС |

Полные типы читаются из строки `= note: found enum …` — она печатает пути (`std::io::Error`), в отличие от короткой подписи под стрелками. Для `Option` компилятор добавил `help` с готовой правкой `.expect("REASON")`.

**Условие.** *(понимание)* Напишите программу, которая вызывает `File::open` и игнорирует результат. Сравните с томом I: что говорил GCC с `-Wall -Wextra` на проигнорированный `fopen` (§10.1)? Когда `let _ =` честен — приведите один убедительный пример.

Разбор по частям:

- **`unused `Result` that must be used`** — сработал атрибут **`#[must_use]`**, которым помечен сам тип `Result` в стандартной библиотеке (R9). Атрибут — это пометка «значение этого типа выбрасывать молча нельзя»; компилятор проверяет её на каждом выражении-операторе, чьё значение никуда не пошло. Помечать так можно и типы, и функции — механизм общий, `Result` просто самый известный его пользователь.
- **`this `Result` may be an `Err` variant, which should be handled`** — объяснение, почему нельзя: выброшено значение **суммы двух русел**, и компилятор не знает, какое из них там оказалось. Может быть `Ok` — и тогда потеряли открытый файл; может быть `Err` — и тогда потеряли отказ вместе с причиной. Формулировка «may be» здесь буквальна: это статическая проверка, а не догадка о поведении.
- **`#[warn(unused_must_use)]` (part of `#[warn(unused)]`) on by default`** — имя линта и его группа: предупреждение включено по умолчанию, а не запрошено флагом. Тем же именем его можно и усилить до ошибки (`#![deny(unused_must_use)]`), и заглушить.
- **`help: use `let _ = ...`**` — предложенная правка с точной вставкой (`+++++++` показывает добавляемые символы). Это **глушитель**, а не решение: `let _ =` говорит «я осознанно выбрасываю оба русла».

*Сравнение с томом I.* Тот же сюжет на C — файл `p5c.c`:

```c
#include <stdio.h>

int main(void) {
    fopen("nope.txt", "r"); /* результат выброшен: том I, §10.1 */
    printf("still running\n");
    return 0;
}
```

Сборка эталонным компилятором тома I — `gcc -std=c17 -Wall -Wextra p5c.c -o p5c.exe` (MinGW GCC 15.2.0) — прошла **без единого слова диагностики**: пустой вывод, код возврата 0. Запуск:

```

```

И это ещё мягкий случай: выброшен только результат `fopen`, а сам файл остался открытым до конца процесса (утечка дескриптора). Разница с Rust не в «строгости характера», а в том, что в C нечего пометить: `FILE *` — обычный указатель, и «его нельзя игнорировать» негде записать. В Rust отказ — часть типа, и на типе висит атрибут.

*Когда `let _ =` честен.* Когда **обе** ветви результата вас устраивают и вы это можете объяснить. Убедительный пример — уборка перед работой: удалить файл прошлого прогона, если он есть. Файл `p5b.rs`:

```rust

    // «нет файла» здесь не ошибка, а желаемое состояние — обе ветки нас устраивают

```

Компилируется без единого предупреждения; два запуска подряд (второй — когда `out.txt` от первого уже лежит на месте) дают один и тот же результат:

```

```

```
out.txt created from scratch
```

Ключ к «честности» здесь — цель сформулирована как состояние («файла быть не должно»), а не как действие («удалить»): `Ok` означает «удалили», `Err(NotFound)` — «его и не было», и оба исхода ведут к нужному состоянию. Заметьте, что настоящую ошибку — `File::create` — программа при этом разбирает match-ем: глушитель поставлен на один конкретный вызов, а не на стиль работы.

**Ответ:** программа — листинг `p5.rs`, полный текст предупреждения приведён выше (программа собирается и печатает `still running`, код выхода 0). Части: заголовок `unused `Result` that must be used` — сработал атрибут **`#[must_use]`** на типе `Result` (R9), запрещающий молча выбрасывать значение; `note: this `Result` may be an `Err` variant, which should be handled` — выброшено значение из двух русел, и компилятор статически не знает, какое там, поэтому «may be»; `note: #[warn(unused_must_use)] (part of #[warn(unused)]) on by default` — имя линта и то, что он включён по умолчанию; `help: use let _ = ...` — предложенная правка-**глушитель**. В томе I тот же приём на C (`p5c.c`) с MinGW GCC 15.2 и `-std=c17 -Wall -Wextra` не дал **ни одного** слова диагностики. `let _ =` честен, когда обе ветви результата ведут к нужному состоянию: `let _ = fs::remove_file("out.txt");` перед созданием файла (`p5b.rs`) — «его нет» и «удалили» одинаково хороши; при этом настоящий отказ (`File::create`) разбирается match-ем.

### Г18.Ч1.З6

**Условие.** *(понимание)* Три вызова: `File::open("cfg")` в начале утилиты, чтение обязательного файла в тесте (глава 20 — но представьте), `v.pop()` на векторе, в который вы только что сделали `push`. Для каждого решите: `match`, `?`, `unwrap` или `expect` — и почему. Перепишите «голые» `unwrap` на `expect` с сообщениями, формулирующими нарушенное ожидание (правило R1: «почему `Err`/`None` здесь невозможен»).

**Решение.** Разбираем по правилу §18.1.3 «внутри логики — `?`, на границе — `match`» и по своду §18.2.3 «чей это провал».

- **(а) `File::open("cfg")` в начале утилиты.** Начало утилиты — это и есть **граница** программы: выше нас никого нет, пробрасывать некуда, а отсутствие конфигурации — провал внешнего мира, не баг. Значит, **`match`**: сообщение человеку в stderr и осмысленный выход. `?` тут был бы уместен, только если бы это была не `main`, а вызываемая из неё функция; `unwrap` превратил бы обычную ситуацию «нет файла» в панику с трассировкой — ровно тот «рефлекторный `unwrap`», от которого предостерегает §18.1.2.
- **(б) Чтение обязательного файла в тесте.** В тесте паника — штатный механизм: упавший тест **и есть** паника (§18.1.1). Отказ здесь означает не «жизнь такая», а «комплект теста сломан», то есть провал программиста. Значит, **`expect`** с формулировкой ожидания: сообщение сразу скажет, что искать.
- **(в) `v.pop()` после собственного `push`.** Отказ невозможен, и доказательство — соседняя строка кода: мы сами только что положили элемент. Это случай «я знаю больше компилятора» из свода §18.2.3 → **`expect("почему невозможен")`**. Голый `unwrap` работал бы так же, но молчал бы о том, на чём держится уверенность.

Все три решения в одной программе — файл `p6.rs`:

```rust
use std::fs::File;

// (в) вектор, в который мы сами только что сделали push:
// инвариант доказан соседней строкой — expect с формулировкой ожидания
fn last_pushed() -> i32 {
    let mut v = Vec::new();
    v.push(42);
    v.pop().expect("push сделан строкой выше — вектор не может быть пуст")
}

// (б) обязательный файл теста (глава 20 — представляем):
// отказ здесь означает сломанный комплект теста, а не жизнь программы
fn fixture_len() -> u64 {
    let f = File::open("fixture.txt")
        .expect("fixture.txt входит в комплект теста и лежит рядом с ним");
    f.metadata()
        .expect("файл только что открыт — метаданные обязаны читаться")
        .len()
}

fn main() {
    // (а) начало утилиты — это граница программы: match и сообщение человеку
    match File::open("cfg") {
        Ok(_) => println!("cfg opened"),
        Err(e) => {
            eprintln!("cannot open cfg: {e}");
            return;
        }
    }
    println!("last pushed: {}", last_pushed());
    println!("fixture: {} bytes", fixture_len());
}
```

Три прогона. Без `cfg` — граница отработала и ушла молча:

```

[exit code: 0]
```

С `cfg` и `fixture.txt` (в файле 13 байт):

```
cfg opened
last pushed: 42
fixture: 13 bytes
[exit code: 0]
```

И третий прогон — `cfg` на месте, а `fixture.txt` удалён: так выглядит «сломанный комплект теста»:

```
cfg opened
last pushed: 42

thread 'main' (28528) panicked at p6.rs:15:10:
fixture.txt входит в комплект теста и лежит рядом с ним: Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
[exit code: 101]
```

Вот ради чего пишется текст в `expect`: сообщение не «что-то не нашлось», а «нарушено вот такое ожидание» — и рядом полная отладочная печать самой ошибки, `Os { code: 2, kind: NotFound, … }`, которую `unwrap` тоже показал бы, но без объяснения, почему автор считал отказ невозможным. Обратите внимание и на второй `expect` в `fixture_len`: метаданные запрашиваются у **только что открытого** файла — снова инвариант, доказанный соседней строкой.

Одна честная оговорка к первому прогону: `[exit code: 0]`. Наша граница сообщила об отказе, но процесс завершился **успешным** кодом — для утилиты это ошибка проектирования (скрипт, вызвавший её, решит, что всё хорошо). Лечится это возвратом `Result` из `main` — ровно следующее задание, Г18.Ч1.З9.

**Ответ:** (а) `File::open("cfg")` в начале утилиты — **`match`**: это граница программы, отказ ожидаемый, пробрасывать некуда, нужно сообщение человеку; (б) обязательный файл в тесте — **`expect`**: в тесте паника штатна, а отсутствие фикстуры — провал комплекта, то есть программиста; (в) `v.pop()` после своего же `push` — **`expect`**: `None` невозможен, и доказательство в соседней строке. Голые `unwrap` переписаны так: `v.pop().expect("push сделан строкой выше — вектор не может быть пуст")`, `File::open("fixture.txt").expect("fixture.txt входит в комплект теста и лежит рядом с ним")`, `f.metadata().expect("файл только что открыт — метаданные обязаны читаться")`. Программа — листинг `p6.rs`; прогон без фикстуры даёт панику `p6.rs:15:10` с этим текстом и приложенной `Os { code: 2, kind: NotFound, … }`, код выхода 101.

### Г18.Ч1.З7

**Условие.** *(понимание)* Десахаризация: перепишите `log_size()` из §18.1.3 без единого `?` — только `match` и ранние `return` (не подглядывая в `log_size_manual`, потом сверьтесь). Убедитесь прогоном, что поведение совпадает на обоих исходах. Посчитайте строки. В каком месте вашей версии «спрятан» `return`, которого не видно в версии с `?`?

**Решение.** Формула из R7 (§18.1.3): `выражение?` — это «`Ok(v)` → `v`, `Err(e)` → `return Err(From::from(e))`». Типы ошибок здесь совпадают (`io::Error` и там, и там), поэтому конвертация тождественна и в ручной версии её можно писать как `return Err(e)`. Раскрываем обе `?` по этой формуле. Файл `p7.rs`:

```rust
use std::fs::File;
use std::io;

// версия из §18.1.3 — с оператором ?
fn log_size() -> Result<u64, io::Error> {
    let f = File::open("app.log")?;
    let meta = f.metadata()?;
    Ok(meta.len())
}

// та же функция без единого ? — только match и ранние return
fn log_size_by_hand() -> Result<u64, io::Error> {
    let f = match File::open("app.log") {
        Ok(f) => f,
        Err(e) => return Err(e),
    };
    let meta = match f.metadata() {
        Ok(m) => m,
        Err(e) => return Err(e),
    };
    Ok(meta.len())
}

fn main() {
    println!("with ?: {:?}", log_size());
    println!("by hand: {:?}", log_size_by_hand());
}
```

Оба исхода — без `app.log` и с файлом в 12 байт (`printf 'hello world\n' > app.log`):

```
with ?: Err(Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." })
by hand: Err(Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." })
```

```
with ?: Ok(12)
by hand: Ok(12)
```

Версии неразличимы по обоим руслам — и это не совпадение, а определение оператора. Сверка с `log_size_manual` из §18.1.3: код получился тот же с точностью до имени функции и имени связанной переменной — потому что свободы в раскрытии `?` нет, формула одна.

*Счёт строк.* Тело с `?` — **3 строки**, тело руками — **9** (вся функция: 5 против 11). Три к одному, и вся разница — чистый ритуал: два `match`, четыре рукава, два `return`.

*Где спрятан `return`.* В рукаве `Err(e) => return Err(e)`. Именно эта строка — вся смысловая нагрузка `?`: **оператор `?` содержит внутри себя досрочный выход из функции**. В версии с `?` в тексте нет ни слова `return`, ни `match`, но управление уходит из `log_size` ровно там же — на первой же неудаче. Отсюда практическое следствие, о котором легко забыть: строка с `?` — это **точка выхода**, а не просто вычисление; всё, что должно случиться после неё, при отказе не случится (это и обыгрывает Г18.Ч1.З10).

**Ответ:** ручная версия — функция `log_size_by_hand` в листинге `p7.rs`: два `match` с рукавами `Ok(v) => v` и `Err(e) => return Err(e)`. Поведение совпадает с версией на `?` по обоим руслам: `Err(Os { code: 2, kind: NotFound, … })` без файла и `Ok(12)` с файлом в 12 байт. Счёт: **3 строки тела против 9** (5 против 11 строк вместе с сигнатурой и скобкой). Спрятанный `return` живёт в рукаве **`Err(e) => return Err(e)`**: `?` — это досрочный выход из функции, записанный одним символом, и строка с `?` является точкой выхода, хотя слова `return` в ней не видно.

**Вариант 2 (вложенные `match` без единого `return`).** Ту же функцию можно раскрыть не «лесенкой с ранними выходами», а одним выражением: `match` возвращает значение, значит, второй `match` можно поставить прямо в рукав `Ok` первого. Файл `p7v2.rs`:

```rust
// без ? и без единого return: вложенные match, значение последнего выражения
fn log_size_nested() -> Result<u64, io::Error> {
    match File::open("app.log") {
        Err(e) => Err(e),
        Ok(f) => match f.metadata() {
            Err(e) => Err(e),
            Ok(meta) => Ok(meta.len()),
        },
    }
}
```

```
with ?: Ok(12)
nested: Ok(12)
```

```
with ?: Err(Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." })
nested: Err(Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." })
```

*Сравнение.* Результат тот же, а устройство другое: здесь нет ни одного `return` — функция целиком есть одно выражение, и её значение вычисляется «изнутри наружу» (§16.2.2 о `match` как выражении). Плюс: видно, что `Err` не «выпадает», а **возвращается как значение**; такой стиль естественнее для тех, кто пришёл из языков с выражениями, и он же — единственный доступный, когда результат нужно не вернуть, а куда-то передать. Минус — плата за вложенность: каждый следующий отказной шаг сдвигает счастливый путь на уровень вправо, и уже на трёх шагах текст расползается лесенкой (тело — 7 строк против 3 у версии с `?`; на трёх вызовах разрыв был бы 11 против 4). Именно этот рост и мотивировал появление `?`: он линеаризует то, что вложенные `match` загибают вправо. Когда предпочесть: вложенные `match` — если шагов один-два и хочется подчеркнуть, что функция есть выражение (или если между руслами надо сделать что-то ещё, кроме проброса); `?` — как только шагов становится больше двух.

### Г18.Ч1.З8

**Условие.** *(прикладное)* Анкета кандидата: `struct Candidate { years: Option<u32>, rating: Option<u32> }` и функция `fn bonus(c: &Candidate) -> Option<u32>`, считающая `years * 10 + rating` через оператор `?`. Проверьте три случая: обе графы заполнены (`Some(3)`, `Some(4)` → `Some(34)`), нет рейтинга (→ `None`), пустая анкета (→ `None`). Объясните, где именно выполнение покидает функцию во втором и третьем случаях.

**Решение.** `?` работает не только с `Result`, но и с `Option` (§18.1.3): `Some(v)` → `v`, `None` → досрочный `return None`. Функция возвращает `Option`, значит, оба русла сходятся. Файл `p8.rs`:

```rust
struct Candidate {
    years: Option<u32>,
    rating: Option<u32>,
}

fn bonus(c: &Candidate) -> Option<u32> {
    let y = c.years?; // нет стажа — выходим отсюда с None
    let r = c.rating?; // нет рейтинга — выходим отсюда с None
    Some(y * 10 + r)
}

fn main() {
    let full = Candidate { years: Some(3), rating: Some(4) };
    let no_rating = Candidate { years: Some(3), rating: None };
    let empty = Candidate { years: None, rating: None };

    println!("full:      {:?}", bonus(&full));
    println!("no rating: {:?}", bonus(&no_rating));
    println!("empty:     {:?}", bonus(&empty));
}
```

```
full:      Some(34)
no rating: None
empty:     None
```

Контроль сошёлся: `3 * 10 + 4 = 34`. Две технические детали, на которых легко споткнуться. Первая: `c` — это `&Candidate`, но `c.years?` работает без всяких `*` и `clone`, потому что `Option<u32>` — `Copy` (внутри `u32`, §15.1.2): из-за ссылки значение **копируется**, а не перемещается, и анкета остаётся целой (для `Option<String>` так уже не вышло бы — потребовалась бы ссылка или клонирование). Вторая: последняя строка — `Some(y * 10 + r)`, упаковать результат обязаны мы сами; `?` только распаковывает (§18.1.3).

*Где выполнение покидает функцию.* Ровно на той `?`, которая первой встретила `None`:

| Анкета | Строка выхода | Что успело выполниться |
|---|---|---|
| `no_rating` (`Some(3)`, `None`) | `let r = c.rating?;` — вторая `?` | `y` получил 3; умножение и сложение — нет |
| `empty` (`None`, `None`) | `let y = c.years?;` — **первая** `?` | ничего; поле `rating` даже не читалось |

Разница между вторым и третьим случаем — не в результате (оба дают `None`), а в том, сколько работы сделано до выхода. Для чистой арифметики это неважно, но стоит подставить сюда обращение к диску или к сети — и «где именно вышли» станет ценой запроса. Это, кстати, ответ на вопрос «зачем короткое замыкание вообще»: `bonus` не считает `3 * 10`, чтобы потом выбросить результат, — она уходит раньше.

**Ответ:** программа — листинг `p8.rs`, результаты: `Some(34)`, `None`, `None`. Во втором случае (`no_rating`) выполнение покидает `bonus` на **второй** `?` — в строке `let r = c.rating?;`: стаж уже прочитан в `y`, но умножение не выполняется. В третьем (`empty`) — на **первой** `?`, в строке `let y = c.years?;`: поле `rating` не читается вовсе. `?` на `Option` — это `return None` из текущей функции, поэтому «где вышли» определяется первым же незаполненным полем.

**Вариант 2 (лесенка вложенных `match`).** Как та же функция выглядела бы без `?` — и, кстати, как она выглядела бы в томе I, где вместо `Option` был бы флажок «поле заполнено». Файл `p8v2.rs`:

```rust
// тот же расчёт лесенкой из вложенных match — так это писалось бы без ?
fn bonus(c: &Candidate) -> Option<u32> {
    match c.years {
        None => None,
        Some(y) => match c.rating {
            None => None,
            Some(r) => Some(y * 10 + r),
        },
    }
}
```

```
full:      Some(34)
no rating: None
empty:     None
```

*Сравнение.* Результаты совпадают до символа, и точки выхода те же самые: рукав `None` внешнего `match` — это первая `?`, рукав `None` внутреннего — вторая. Различие в читаемости и в масштабировании: у версии с `?` счастливый путь — три строки подряд, у версии с `match` он спрятан в самой глубокой вложенности, а два отказных рукава написаны раньше него. С двумя полями это дело вкуса; с пятью — у варианта 2 будет пять уровней отступа и пять одинаковых строк `None => None`, а у версии с `?` — пять строк с закорючкой и один `Some(...)` в конце. Зато вариант 2 честно показывает, что `Option` — обычный `enum` из главы 16 и никакой магии в `?` нет: это тот же разбор образцов, только записанный компилятором за вас. Когда предпочесть: `match` — если в отказном русле надо не просто вернуть `None`, а сделать что-то ещё (умолчание, сообщение, другой источник данных); `?` — во всех остальных случаях.

### Г18.Ч1.З9

**Условие.** *(прикладное)* `main -> Result`: программа открывает `a.txt` и `b.txt` через `?` и печатает размер каждого (`metadata()?.len()`). Прогоните три сценария: оба файла есть; нет второго; нет первого. Для каждого предскажите вывод (что успеет напечататься?), строку `Error: ...` и код выхода. Чем это поведение отличается от `unwrap` по сути и по форме вывода?

**Решение.** *Предсказание.* Печать идёт по ходу дела, поэтому в сценарии «нет второго» первая строка успеет выйти, а вторая — нет; в сценарии «нет первого» не выйдет ничего. `Err`, долетевший до верха, рантайм печатает сам — строкой `Error: ...` с отладочной формой ошибки, и код выхода будет ненулевым (§18.1.3 обещает 1).

Файл `p9.rs` (в `a.txt` — 4 байта, в `b.txt` — 6):

```rust
use std::fs::File;
use std::io;

fn main() -> Result<(), io::Error> {
    let a = File::open("a.txt")?;
    println!("a.txt: {} bytes", a.metadata()?.len());
    let b = File::open("b.txt")?;
    println!("b.txt: {} bytes", b.metadata()?.len());
    Ok(())
}
```

Сценарий 1 — оба файла на месте:

```
a.txt: 4 bytes
b.txt: 6 bytes
[exit code: 0]
```

Сценарий 2 — нет `b.txt`:

```
a.txt: 4 bytes
Error: Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
[exit code: 1]
```

Сценарий 3 — нет ни одного:

```
Error: Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
[exit code: 1]
```

Предсказание сошлось полностью. Три замечания по механике. Первое: `metadata()?.len()` — `?` применён к промежуточному значению прямо в цепочке, до вызова `.len()`; это обычное выражение, а не особый синтаксис. Второе: строку `Error: ...` печатает **не наш код** — её выводит рантайм, получив `Err` из `main` (механизм `Termination`, R9), и печатает через `{:?}`, отсюда `Os { … }` вместо человеческой фразы. Третье: `Ok(())` в конце обязателен — без него E0308 «expected `Result`, found `()`» (§18.1.3).

*Чем отличается от `unwrap`.* По сути — тем, кто принимает решение и что происходит со стеком:

| | `unwrap`/`expect` | `main -> Result` + `?` |
|---|---|---|
| решение | функция сама объявляет отказ невозможным | отказ признаётся возможным и уходит наверх значением |
| механизм | **паника**: размотка стека, `drop` живым значениям, аварийное завершение | обычный `return` до самого верха, затем штатный выход из процесса |
| код выхода | 101 (на эталоне) | 1 |
| форма вывода | `thread 'main' (…) panicked at файл:строка:колонка:` + текст + `note: run with RUST_BACKTRACE=1` | одна строка `Error: <Debug-печать ошибки>` |
| место в коде | указано точно (файл, строка, колонка) | **не указано** — только сама ошибка |
| ловится ли | это баг: сигнал программисту | это ожидаемый отказ: сигнал скрипту/пользователю |

Практическое следствие пары «место указано / не указано»: у `?`-версии вывод чище (пользователю не нужны координаты `unwrap` внутри вашей программы), но и диагностики меньше — если файлов два, из строки `Error: ...` не видно, какой именно не открылся (эту дыру закрывает Г18.Ч2.З7 — заворачивать путь в свой тип ошибки).

**Ответ:** программа — листинг `p9.rs`. Сценарий 1 (оба файла): `a.txt: 4 bytes`, `b.txt: 6 bytes`, код выхода **0**. Сценарий 2 (нет `b.txt`): успевает напечататься `a.txt: 4 bytes`, затем `Error: Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }`, код **1**. Сценарий 3 (нет `a.txt`): полезного вывода нет вовсе, только та же строка `Error: …` и код **1**. Отличие от `unwrap` по сути: `?` не паникует — ошибка едет наверх обычным возвратом, решение принимает граница, а не глубина; по форме: одна строка `Error: <Debug>` вместо трёхстрочного сообщения паники с `файл:строка:колонка` и подсказкой про `RUST_BACKTRACE`, и код выхода 1 вместо 101. Взамен теряется указание места: какой именно из двух файлов не открылся, из вывода не видно.

### Г18.Ч1.З10

**Условие.** *(прикладное)* «Первая ошибка останавливает конвейер»: `fn sizes(names: &[String]) -> Result<Vec<u64>, io::Error>` обходит список имён циклом, печатает `открываю {name}` перед каждым открытием и собирает размеры в вектор; любая ошибка — немедленный выход через `?`. В `main` — `match` с печатью результата. Контроль: для списка `["a.txt", "b.txt", "c.txt"]`, где `c.txt` отсутствует, трассировка покажет все три строки `открываю ...`, затем `остановились: ...`; после создания `c.txt` — `размеры: [...]` (числа — ваши). Объясните: почему при отсутствии `b.txt` строка `открываю c.txt` не печатается, хотя цикл «хотел» продолжить?

**Решение.** Файл `p10.rs` (размеры файлов: `a.txt` — 4 байта, `b.txt` — 6, `c.txt` — 3):

```rust
use std::fs::File;
use std::io;

fn sizes(names: &[String]) -> Result<Vec<u64>, io::Error> {
    let mut out = Vec::new();
    for name in names {
        println!("открываю {name}");
        let f = File::open(name)?; // первая же неудача покидает функцию
        out.push(f.metadata()?.len());
    }
    Ok(out)
}

fn main() {
    let names = vec![
        String::from("a.txt"),
        String::from("b.txt"),
        String::from("c.txt"),
    ];
    match sizes(&names) {
        Ok(v) => println!("размеры: {v:?}"),
        Err(e) => println!("остановились: {e}"),
    }
}
```

Прогон 1 — нет `c.txt` (контрольный сценарий условия):

```
открываю a.txt
открываю b.txt
открываю c.txt
остановились: The system cannot find the file specified. (os error 2)
```

Прогон 2 — все три файла на месте:

```
открываю a.txt
открываю b.txt
открываю c.txt
размеры: [4, 6, 3]
```

Прогон 3 — на месте `a.txt` и `c.txt`, нет `b.txt`:

```
открываю a.txt
открываю b.txt
остановились: The system cannot find the file specified. (os error 2)
```

Контроль сошёлся: три строки `открываю` и `остановились: …` в первом прогоне, `размеры: [4, 6, 3]` во втором.

*Почему `открываю c.txt` не печатается.* Потому что `?` — не проверка, а **выход из функции** (Г18.Ч1.З7). Разберём третий прогон по шагам: первая итерация печатает `открываю a.txt`, открывает файл, кладёт 4 в вектор; вторая печатает `открываю b.txt` и упирается в `File::open("b.txt")` → `Err`; оператор `?` немедленно выполняет `return Err(...)` — **из `sizes`, а не из итерации цикла**. Цикл не «хотел продолжить»: его вместе со всей функцией просто больше нет. Третьей итерации не будет, значит, и печати `открываю c.txt` не будет тоже.

Заодно виден ответ на вопрос, который часто задают про ранние выходы: что стало с накопленным вектором? На момент выхода в `out` лежал размер `a.txt`, и этот вектор был **уничтожен** при выходе из функции — `drop` при любом возврате, как и при обычном (§15.1.1, §18.1.3). Никакого «полурезультата» вызывающий не увидит: сигнатура `Result<Vec<u64>, io::Error>` обещает либо полный список, либо ошибку — третьего в типе нет.

Полезно сопоставить это с C-предком (§10.1): там цикл с `fopen` внутри пришлось бы завершать вручную — `break` с флажком или `goto cleanup`, а накопленный массив освобождать самому, не забыв ни одной ветки выхода. `?` делает и то, и другое, и делает всегда.

**Ответ:** программа — листинг `p10.rs`. Контроль: при отсутствующем `c.txt` печатаются все три строки `открываю …`, затем `остановились: The system cannot find the file specified. (os error 2)`; когда все три файла на месте — `размеры: [4, 6, 3]`. При отсутствии `b.txt` строка `открываю c.txt` не печатается, потому что `?` в строке `let f = File::open(name)?;` выполняет `return Err(...)` **из всей функции `sizes`**, а не «переход к следующей итерации»: цикл прекращается вместе с функцией. Накопленный к этому моменту вектор уничтожается `drop`-ом при выходе (§15.1.1) — вызывающему достаётся либо полный список, либо ошибка, что и обещает тип `Result<Vec<u64>, io::Error>`.

**Вариант 2 (не останавливаться: пропускать сбойные имена).** «Первая ошибка останавливает конвейер» — это решение, а не закон природы. Противоположная стратегия: обойти весь список, а сбойные имена пропустить. Файл `p10v2.rs`:

```rust
use std::fs::File;

// конвейер, который не останавливается: сбойное имя пропускаем и идём дальше
fn sizes_present(names: &[String]) -> Vec<u64> {
    let mut out = Vec::new();
    for name in names {
        println!("открываю {name}");
        match File::open(name) {
            Ok(f) => match f.metadata() {
                Ok(m) => out.push(m.len()),
                Err(e) => println!("пропускаем {name}: {e}"),
            },
            Err(e) => println!("пропускаем {name}: {e}"),
        }
    }
    out
}
```

Тот же сценарий — нет `c.txt`:

```
открываю a.txt
открываю b.txt
открываю c.txt
пропускаем c.txt: The system cannot find the file specified. (os error 2)
размеры: [4, 6]
прочитано 2 из 3
```

*Сравнение.* Разница не в стиле, а в контракте. Версия с `?` возвращает `Result` и говорит: «всё или ничего, причина отказа — ваша»; вариант 2 возвращает `Vec<u64>` и говорит: «сколько получилось, столько получилось». Отсюда три следствия. Первое: у варианта 2 **нет типа отказа** — вызывающий по результату не отличит «файла не было» от «файл пуст», и `2 из 3` приходится печатать отдельно (потому в программе и стоит эта строка). Второе: решение, что делать с отказом, переехало **внутрь** функции — она сама печатает `пропускаем …`, то есть нарушает правило §18.1.3 «глубина пробрасывает, граница решает»; в настоящей программе это чинят возвратом `Vec<Result<u64, io::Error>>` или пары «результаты + список ошибок», чтобы решение осталось у вызывающего. Третье: цена вложенности — вместо двух `?` появились четыре рукава и два одинаковых сообщения. Когда предпочесть: `?`-версию — когда результат осмыслен только целиком (посчитать общий объём, собрать конфигурацию из частей); вариант 2 — когда обработка независимых элементов не должна падать из-за одного (обход каталога, импорт списка записей, отчёт по серверам), и тогда сразу проектируйте, **как** вызывающий узнает о пропусках.

## Часть 18.2. Проектирование ошибок

### Г18.Ч2.З1

**Условие.** Перенесите `parse_u32.rs` из §18.2.1 к себе и прогоните `report` для входов `"2048"`, `""`, `"12x7"`, `"99999999999"`, `"4294967295"`, `"007"` — для каждого предскажите результат (вариант или число) до запуска. Затем поменяйте местами рукава `Err(ParseError::BadChar(c))` и `Err(ParseError::TooBig)` в `report` и объясните, почему поведение не изменилось (§16.2.2: когда порядок рукавов важен, а когда нет).

**Решение.** *Предсказание.* `"2048"` — все символы цифры, страж переполнения не сработает → `Ok(2048)`. `""` — первая же проверка `is_empty` → `Empty`. `"12x7"` — на третьем символе `to_digit(10)` даст `None` → `BadChar('x')`, причём разбор прекратится сразу, до `'7'`. `"99999999999"` — одиннадцать девяток, это больше `u32::MAX` (4 294 967 295) → `TooBig`. `"4294967295"` — ровно `u32::MAX`, граница должна пройти → число. `"007"` — ведущие нули не мешают накоплению (`0*10+0`, потом `0*10+7`) → 7.

Файл `d1.rs`:

```rust
#[derive(Debug)]
enum ParseError {
    Empty,
    BadChar(char),
    TooBig,
}

fn parse_u32(s: &str) -> Result<u32, ParseError> {
    if s.is_empty() {
        return Err(ParseError::Empty);
    }
    let mut acc: u32 = 0;
    for c in s.chars() {
        let d = match c.to_digit(10) {
            Some(d) => d,
            None => return Err(ParseError::BadChar(c)),
        };
        if acc > (u32::MAX - d) / 10 {
            return Err(ParseError::TooBig);
        }
        acc = acc * 10 + d;
    }
    Ok(acc)
}

fn report(input: &str) {
    match parse_u32(input) {
        Ok(n) => println!("{input:?} -> число {n}"),
        Err(ParseError::Empty) => println!("{input:?} -> ошибка: пустая строка"),
        Err(ParseError::BadChar(c)) => println!("{input:?} -> ошибка: недопустимый символ {c:?}"),
        Err(ParseError::TooBig) => println!("{input:?} -> ошибка: не помещается в u32"),
    }
}

fn main() {
    report("2048");
    report("");
    report("12x7");
    report("99999999999");
    report("4294967295");
    report("007");
}
```

```
"2048" -> число 2048
"" -> ошибка: пустая строка
"12x7" -> ошибка: недопустимый символ 'x'
"99999999999" -> ошибка: не помещается в u32
"4294967295" -> число 4294967295
"007" -> число 7
```

Все шесть предсказаний сошлись. Отдельно стоит остановиться на `"4294967295"`: это граничный случай, ради которого страж и написан в форме `acc > (u32::MAX - d) / 10`. На последнем шаге `acc = 429496729`, `d = 5`; проверка считает `(4294967295 - 5) / 10 = 429496729` и сравнивает **строго больше** — равенство проходит, значение помещается ровно. Сдвинь мы условие на `>=` — и последнее допустимое число ложно объявлялось бы переполнением.

*Перестановка рукавов.* Файл `d1b.rs` — тот же код, в `report` рукава `TooBig` и `BadChar` поменяны местами:

```rust
// тот же report, но рукава TooBig и BadChar поменяны местами

        Ok(n) => println!("{input:?} -> число {n}"),
        Err(ParseError::Empty) => println!("{input:?} -> ошибка: пустая строка"),
        Err(ParseError::TooBig) => println!("{input:?} -> ошибка: не помещается в u32"),
        Err(ParseError::BadChar(c)) => println!("{input:?} -> ошибка: недопустимый символ {c:?}"),
    }
}
```

```
"2048" -> число 2048
"" -> ошибка: пустая строка
"12x7" -> ошибка: недопустимый символ 'x'
"99999999999" -> ошибка: не помещается в u32
"4294967295" -> число 4294967295
"007" -> число 7
```

Вывод совпал до символа. Причина — правило §16.2.2: `match` берёт **первый подошедший** рукав, значит, порядок важен ровно тогда, когда два образца могут подойти к одному значению, то есть **перекрываются**. Здесь все четыре образца попарно несовместимы: значение — либо `Ok`, либо `Err` ровно с одним из трёх вариантов, и никакой `Err(ParseError::TooBig)` никогда не совпадёт с `Err(ParseError::BadChar(c))`. Перестановка непересекающихся рукавов — это перестановка строк в таблице: смысл таблицы от этого не меняется.

Когда порядок всё-таки важен — стоит помнить три случая: (1) рукав `_` или рукав-переменная (`Err(pe)`) подходит ко **всему**, поэтому обязан стоять последним — поставленный раньше, он затенит остальные, и компилятор скажет `unreachable pattern`; (2) образцы с ограничением (`Some(n) if n > 100`) перекрываются с безусловными; (3) диапазоны и вложенные образцы разной общности — `Err(AppError::Parse(ParseError::BadChar(c)))` перекрывается с `Err(AppError::Parse(pe))`, и порядок между ними решает всё (ровно этим пользуется `main` в §18.2.3).

**Ответ:** программа — листинг `d1.rs`; результаты для шести входов: `2048` → число 2048, `""` → пустая строка, `"12x7"` → недопустимый символ `'x'`, `"99999999999"` → не помещается в `u32`, `"4294967295"` → число 4294967295 (граница проходит: страж написан со строгим `>`), `"007"` → число 7. После перестановки рукавов `TooBig` и `BadChar` (`d1b.rs`) вывод **не изменился**, потому что `match` выбирает первый подошедший рукав, а эти два образца **не перекрываются**: одно и то же значение не может быть одновременно `TooBig` и `BadChar`. Порядок важен только для перекрывающихся образцов — рукава `_` и рукава-переменной (обязаны быть последними), рукавов с ограничениями и вложенных образцов разной степени общности.

### Г18.Ч2.З2

**Условие.** Безопасное деление: `enum DivError { Zero }` и `fn safe_div(a: i32, b: i32) -> Result<i32, DivError>`. В `main` — функция-репортёр с match. Контроль: `10 / 3 = 3`, `-7 / 2 = -3` (усечение к нулю — §14.2.2), `5 / 0: деление на ноль`. Чем ваш `Err(DivError::Zero)` лучше паники `attempt to divide by zero` (§13.2.2) — назовите два конкретных отличия для вызывающего.

**Решение.** Файл `d2.rs`:

```rust
#[derive(Debug)]
enum DivError {
    Zero,
}

fn safe_div(a: i32, b: i32) -> Result<i32, DivError> {
    if b == 0 {
        return Err(DivError::Zero);
    }
    Ok(a / b)
}

fn report(a: i32, b: i32) {
    match safe_div(a, b) {
        Ok(q) => println!("{a} / {b} = {q}"),
        Err(DivError::Zero) => println!("{a} / {b}: деление на ноль"),
    }
}

fn main() {
    report(10, 3);
    report(-7, 2);
    report(5, 0);
}
```

```
10 / 3 = 3
-7 / 2 = -3
5 / 0: деление на ноль
```

Контроль сошёлся, включая `-7 / 2 = -3`: целочисленное деление усекает **к нулю**, а не «вниз» (§14.2.2), поэтому не −4. Проверка `b == 0` стоит до деления — это единственный способ: спросить у процессора «а получится?» уже нельзя, деление на ноль в машинном коде не имеет результата.

*Два отличия от паники — для вызывающего.* Оба про власть и про информацию:

1. **Вызывающий остаётся жив и решает сам.** Паника `attempt to divide by zero` (§13.2.2) завершает процесс: у вызывающего нет ни ветки «попросить другой делитель», ни ветки «пропустить строку отчёта и считать дальше». `Err(DivError::Zero)` — обычное значение: его можно разобрать match-ем, подставить умолчание через `unwrap_or`, пробросить наверх оператором `?`. Решение «это фатально» остаётся за тем, у кого есть контекст, — ровно правило §18.1.3.
2. **Отказ виден в типе, и компилятор заставит его учесть.** Сигнатура `-> Result<i32, DivError>` — это документация, которую проверяет компилятор: получить `i32` без разбора русел нельзя. У паникующего деления сигнатура «i32 на i32 даёт i32» — она **умалчивает** о том, что бывает третий исход, и узнаёте вы о нём в рантайме, у пользователя. Плюс к тому причина названа вариантом (`DivError::Zero`), а не строкой в консоли: её можно сравнить, сосчитать, передать наверх.

*Типичная неверная попытка: «страж на ноль закрывает вопрос».* Не закрывает. Файл `d2ovf.rs` — та же `safe_div`, один вызов:

```rust
fn main() {
    // делитель не ноль — страж пропускает; а деление всё равно не выполнимо
    println!("{:?}", safe_div(i32::MIN, -1));
}
```

```
thread 'main' (26724) panicked at d2ovf.rs:10:8:
attempt to divide with overflow
[exit code: 101]
```

Делитель не ноль, страж пропустил, а результат `2147483648` в `i32` не помещается: диапазон типа несимметричен (§14.2.1), и `-i32::MIN` — единственное частное, которого нет. Обратите внимание на текст: `divide with overflow`, а не `by zero` — это второй, независимый способ уронить деление. Тип ошибки, объявляющий единственной причиной `Zero`, тем самым **врёт** вызывающему.

**Ответ:** программа — листинг `d2.rs`; контроль сошёлся: `10 / 3 = 3`, `-7 / 2 = -3` (усечение к нулю), `5 / 0: деление на ноль`. Два отличия `Err(DivError::Zero)` от паники для вызывающего: (1) **он остаётся жив и решает сам** — значение можно разобрать match-ем, заменить умолчанием, пробросить `?`, тогда как паника завершает процесс и лишает выбора; (2) **отказ виден в типе** — сигнатура `-> Result<i32, DivError>` не даёт получить `i32`, не разобрав оба русла, а причина названа вариантом, который можно сравнить и передать, тогда как у паникующего `a / b` сигнатура умалчивает о третьем исходе. Обнаружена и ловушка: страж `b == 0` не закрывает всех отказов деления — `safe_div(i32::MIN, -1)` паникует с `attempt to divide with overflow` (`d2ovf.rs`).

**Вариант 2 (через `checked_div`: обе непредставимости разом).** Раз отказов у деления два, пусть и тип ошибки знает про оба. Стандартная библиотека даёт готовую проверку: `checked_div` возвращает `Option<i32>` — `None` и при нулевом делителе, и при непредставимом частном (R9). Файл `d2v2.rs`:

```rust
#[derive(Debug)]
enum DivError {
    Zero,
    Overflow { a: i32, b: i32 },
}

// checked_div возвращает None на обоих непредставимых случаях сразу (R9)
fn safe_div(a: i32, b: i32) -> Result<i32, DivError> {
    if b == 0 {
        return Err(DivError::Zero);
    }
    match a.checked_div(b) {
        Some(q) => Ok(q),
        None => Err(DivError::Overflow { a, b }),
    }
}

fn report(a: i32, b: i32) {
    match safe_div(a, b) {
        Ok(q) => println!("{a} / {b} = {q}"),
        Err(DivError::Zero) => println!("{a} / {b}: деление на ноль"),
        Err(DivError::Overflow { a, b }) => println!("{a} / {b}: частное не влезает в i32"),
    }
}
```

```
10 / 3 = 3
-7 / 2 = -3
5 / 0: деление на ноль
-2147483648 / -1: частное не влезает в i32
```

*Сравнение.* На трёх контрольных входах обе версии дают одно и то же — вариант 2 не «другой ответ», а более честный тип. Различий три. Первое: причин отказа стало две, и вызывающий может поступить с ними **по-разному** (на `Zero` спросить другой делитель, на `Overflow` предложить `i64`) — это критерий 3 из §18.2.1 в действии, а заодно и критерий «объединяйте варианты, по которым нельзя поступить по-разному»: здесь как раз можно. Второе: `Overflow { a, b }` несёт данные структурными полями (§16.2.1) — сообщение печатается без того, чтобы репортёр помнил аргументы. Третье: проверка на ноль осталась **перед** `checked_div` намеренно; убери мы её, `None` пришёл бы и на делении на ноль, и различить причины стало бы нечем — `Option` причин не хранит (§18.1.2), поэтому «сначала свой страж, потом чужая проверка». Цена варианта — лишний уровень разбора и один дополнительный вариант в каждом `match` у всех вызывающих. Когда предпочесть: базовую версию — если делимое заведомо не `i32::MIN` (например, все числа неотрицательные); вариант 2 — везде, где `a` приходит извне.

### Г18.Ч2.З4

**Условие.** *(понимание)* Десахаризация с конвертацией: перепишите `sum_of_file` из §18.2.3 без `?` — два `match` с `return Err(From::from(e))`. Прогоном подтвердите совпадение всех трёх исходов (сумма, нет файла, плохой символ). Ответьте: в строке с `parse_numbers` — какой именно `impl From` вызывается и откуда компилятор это знает? А почему внутри `parse_numbers` оператор `?` обходится без `From`?

**Решение.** Обе версии живут в одной программе и вызываются подряд — так совпадение исходов видно в одном выводе. Файл `d4.rs`, ключевая часть:

```rust
// оригинал из §18.2.3 — с двумя ?
fn sum_of_file(path: &str) -> Result<u32, AppError> {
    let text = fs::read_to_string(path)?;
    let nums = parse_numbers(&text)?;
    let mut total: u32 = 0;

// то же самое без ? — два match с явным return Err(From::from(e))
fn sum_of_file_by_hand(path: &str) -> Result<u32, AppError> {
    let text = match fs::read_to_string(path) {
        Ok(t) => t,
        Err(e) => return Err(From::from(e)),
    };
    let nums = match parse_numbers(&text) {
        Ok(v) => v,
        Err(e) => return Err(From::from(e)),
    };
    let mut total: u32 = 0;
    for n in &nums {
        total += *n;
    }
    Ok(total)
}
```

Три прогона — `scores.txt` с числами `10 25 7`, отсутствующий файл, файл `10 abc 5`:

```
с ?    : сумма: 42
руками : сумма: 42
```

```
с ?    : не удалось прочитать scores.txt: The system cannot find the file specified. (os error 2)
руками : не удалось прочитать scores.txt: The system cannot find the file specified. (os error 2)
```

```
с ?    : в файле не число: символ 'a'
руками : в файле не число: символ 'a'
```

Все три исхода совпали. Заметьте: в ручной версии **обе** ветви написаны одинаково — `return Err(From::from(e))`, хотя типы ошибок разные (`io::Error` и `ParseError`). Это и есть точная десахаризация: формула R7 одна на все случаи, различия прячутся в том, какой `impl From` подберёт компилятор.

*Какой `impl From` вызывается в строке с `parse_numbers`.* Вызывается **`impl From<ParseError> for AppError`** — тот, что заворачивает разборную ошибку в вариант `AppError::Parse`. Компилятор выводит это из двух известных ему фактов, без единой подсказки от нас:

- **что на руках**: `parse_numbers(&text)` имеет тип `Result<Vec<u32>, ParseError>`, значит, в рукаве `Err(e)` переменная `e` — это `ParseError`;
- **что требуется**: сигнатура функции обещает `Result<u32, AppError>`, а `return Err(...)` обязан вернуть именно её, значит, аргумент `Err` должен быть `AppError`.

Из пары «из `ParseError` в `AppError`» и получается единственный подходящий `impl`. Отсюда важное следствие: `From::from` — запись **без имени типа**, её смысл определяется контекстом. Перенеси мы ту же строку в функцию с другим типом ошибки — вызвался бы другой `impl` (или E0277, если подходящего нет), а текст строки не изменился бы ни на символ.

*Почему внутри `parse_numbers` оператор `?` обходится без `From`.* Потому что конвертировать там нечего: `parse_numbers` объявлена как `Result<Vec<u32>, ParseError>` и внутри вызывает `parse_u32(&token)?`, у которой тип ошибки **тот же** `ParseError`. Формула R7 не отменяется — `Err(From::from(e))` выполняется и здесь, но преобразование идёт из типа в себя же, а для этого случая в стандартной библиотеке есть готовая реализация `impl<T> From<T> for T` (R9): она просто возвращает значение как есть. Писать свой `impl From<ParseError> for ParseError` не нужно (и нельзя — он уже существует). Так что верное объяснение звучит не «`From` не участвует», а «участвует тождественный `From`, который ничего не делает».

**Ответ:** ручная версия — функция `sum_of_file_by_hand` в листинге `d4.rs`: два `match`, в отказных рукавах `return Err(From::from(e))`. Все три исхода совпали с оригиналом: `сумма: 42`, `не удалось прочитать scores.txt: The system cannot find the file specified. (os error 2)`, `в файле не число: символ 'a'`. В строке с `parse_numbers` вызывается **`impl From<ParseError> for AppError`**; компилятор выбирает его сам, зная тип выражения (`Result<Vec<u32>, ParseError>` → `e: ParseError`) и требуемый тип возврата из сигнатуры (`Result<u32, AppError>`) — то есть `From::from` разрешается по паре «откуда, куда», а не по написанному имени. Внутри `parse_numbers` `?` обходится без нашего `From`, потому что тип ошибки совпадает с типом ошибки функции: срабатывает **тождественная реализация `impl<T> From<T> for T`** из стандартной библиотеки (R9), возвращающая значение неизменным.

**Решение.** Переписать легко — тип ошибки заменяется на `String`, три `return Err(...)` начинают строить текст. Файл `d5.rs`:

```rust
// та же parse_u32, но причина отказа — строка вместо типа
fn parse_u32(s: &str) -> Result<u32, String> {
    if s.is_empty() {
        return Err(String::from("пустая строка"));
    }
    let mut acc: u32 = 0;
    for c in s.chars() {
        let d = match c.to_digit(10) {
            Some(d) => d,
            None => return Err(format!("недопустимый символ {c:?}")),
        };
        if acc > (u32::MAX - d) / 10 {
            return Err(String::from("не помещается в u32"));
        }
        acc = acc * 10 + d;
    }
    Ok(acc)
}
```

Трудности начинаются у вызывающего. Различить причины больше нечем — только сравнением текста, а символ приходится добывать из сообщения:

```rust
fn report(input: &str) {
    match parse_u32(input) {
        Ok(n) => println!("{input:?} -> число {n}"),
        Err(msg) => {
            // различить причины можно только сравнением текста
            if msg == "пустая строка" {
                println!("{input:?} -> пусто, пропускаем");
            } else if msg == "не помещается в u32" {
                println!("{input:?} -> велико, предложить u64");
            } else {
                // символа в типе нет: приходится выковыривать его из сообщения
                let mut cs = Vec::new();
                for c in msg.chars() {
                    cs.push(c);
                }
                let bad = cs[cs.len() - 2]; // предпоследний символ: ... 'x'
                println!("{input:?} -> {msg}; символ добыт разбором текста: {bad:?}");
            }
        }
    }
}
```

```
"2048" -> число 2048
"" -> пусто, пропускаем
"12x7" -> недопустимый символ 'x'; символ добыт разбором текста: 'x'
"99999999999" -> велико, предложить u64
"4294967295" -> число 4294967295
"007" -> число 7
```

Работает — и ровно этим опасно: на глаз результат неотличим от версии с `enum`. Разница вскрывается на четырёх вопросах критериев R2 (§18.2.1):

| Критерий R2 | `enum ParseError` | `Result<u32, String>` |
|---|---|---|
| 1. один тип на функцию | есть; варианты перечислены в объявлении, их видно в документации | формально есть, но множество возможных сообщений нигде не записано — вызывающий узнаёт их из чтения кода функции |
| 2. конкретные варианты вместо строк | `match` по вариантам; компилятор проверяет полноту (E0004), опечатка в имени варианта — ошибка сборки | цепочка `if msg == "…"`; полноту проверить нечем, «забытая» причина молча уходит в `else` |
| 3. данные внутри варианта | `BadChar(c)` — символ уже в руках, тип `char` | символа нет: его добывают **разбором текста** (`cs[cs.len() - 2]`) — код, который сломается от любой правки формулировки |
| 4. сочетаемость | `impl From<ParseError> for AppError` — заворачивается в чужой тип, причина сохраняется (§18.2.2) | заворачивать нечего: `String` в `AppError::Parse(String)` — это уже пересказ, `e.kind()`-подобных вопросов задать некому |

Ответы на конкретные вопросы условия: **отличить «пустую строку» от «плохого символа»** можно только сравнением текста (`msg == "пустая строка"`); **достать символ** — только вытащив его из сообщения по позиции, зная формат, который никто не гарантирует; **опечатка в тексте** превращается из косметики в логику — и это стоит показать отдельно.

*Что случится при опечатке.* Файл `d5b.rs` — то же самое, с единственной правкой: сообщение переформулировано с `"пустая строка"` на `"строка пустая"` (перестановка слов, какую делают, чтобы «звучало лучше»). Проверка в `report` осталась прежней:

```rust
fn parse_u32(s: &str) -> Result<u32, String> {
    if s.is_empty() {
        return Err(String::from("строка пустая")); // было: "пустая строка"
    }
```

```
"" -> строка пустая; символ добыт разбором текста: 'а'
```

Программа собралась без единого предупреждения — и **сломалась молча**: ветка «пусто, пропускаем» больше не срабатывает, пустая строка провалилась в `else`, предназначенный для плохих символов, и «добыла» из сообщения букву `'а'` (предпоследний символ фразы «строка пустая»). Ни компилятор, ни рантайм ничего не заметили: с точки зрения типов всё корректно, `String` есть `String`. В версии с `enum` такая правка невозможна в принципе: текст сообщения живёт в `report`, а не в типе, и переименование варианта — ошибка сборки во всех местах разбора.

**Ответ:** версия на строках — листинги `d5.rs` (и `d5b.rs` для опыта с опечаткой); вывод на шести входах совпадает с версией из Г18.Ч2.З1. По критериям R2 строковая версия проваливает все четыре: набор причин нигде не объявлен (1); различать их приходится сравнением текста, полноту разбора компилятор не проверяет (2); данных в ошибке нет — символ добывается разбором сообщения `cs[cs.len() - 2]` (3); в чужой тип ошибки такая ошибка заворачивается только пересказом (4). Конкретно: «пустую строку» от «плохого символа» отличают через `msg == "пустая строка"`; символ достают из текста по позиции; а переформулировка сообщения на `"строка пустая"` (`d5b.rs`) **молча** ломает логику — пустой вход уходит в ветку плохого символа и печатает `"" -> строка пустая; символ добыт разбором текста: 'а'`, причём ни компилятор, ни рантайм не возражают. Вывод одним предложением: **строка — это сообщение для человека, а не тип ошибки для программы; делая её типом, вы превращаете текст в логику, а компилятор — из союзника в постороннего.**

### Г18.Ч2.З6

**Условие.** *(понимание)* Классифицируйте по своду §18.2.3 (panic или Result — и почему): (а) индекс вышел за границы вектора из-за ошибки в вашей формуле; (б) конфигурационный файл не найден при старте; (в) пользователь ввёл `"abc"` вместо числа; (г) функция библиотеки получила аргумент, нарушающий её документированный контракт; (д) проверка в тесте; (е) черновой скрипт для одноразового расчёта. Для (б) приведите две разные *правильные* реакции границы — в зависимости от того, обязателен ли файл.

**Решение.** Прикладываем лакмус §18.2.3 — **чей это провал?** — к каждому пункту.

| | Ситуация | Инструмент | Почему |
|---|---|---|---|
| (а) | индекс за границей из-за ошибки в формуле | **паника** | Провал программиста: формула неверна, инвариант «индекс < длины» нарушен вашим же кодом. Продолжать нельзя — дальше пойдут вычисления по неверным данным. Делать ничего не надо: язык паникует сам (§17.1.1), и это ровно то, что нужно. Если же индекс приходит **извне** (номер строки от пользователя), это уже пункт (в): проверять `get` и возвращать `Result`. |
| (б) | конфиг не найден при старте | **`Result`** | Провал внешнего мира: файла нет — обычное состояние файловой системы, не баг. Решает граница; две правильные реакции разобраны ниже. |
| (в) | пользователь ввёл `"abc"` | **`Result`** | «Опечатка — не авария»: программа обязана пережить любой ввод и внятно ответить. Паника здесь — грубость к пользователю и потеря контекста для вызывающего (§18.2.1, `parse_u32`). |
| (г) | нарушен документированный контракт функции | **`panic!`** | Провал программиста — но того, кто вызвал. Контракт («индекс меньше длины», «делитель не ноль») — часть определения функции; его нарушение означает баг у вызывающего, и молча «как-нибудь продолжить» опаснее, чем остановиться. Так устроены `Vec::insert` и взятие срезов строк в самой стандартной библиотеке. |
| (д) | проверка в тесте | **паника** | Упавший тест **и есть** паника (§18.1.1); `assert!`-механика главы 20 на ней и построена. Возвращать `Result` из проверки бессмысленно: адресат сообщения — программист, и он его увидит. |
| (е) | черновой скрипт на один расчёт | **`unwrap`/`expect`** | Прототип: краткость важнее устойчивости, обрабатывать нечего и некому. `expect` при этом честнее `unwrap` — он ещё и маркер «здесь недоделано», когда черновик внезапно переезжает в продакшен. |

*Две правильные реакции границы для (б).* Различает их один вопрос: **может ли программа работать без этого файла?**

- **Файл необязателен** (тема оформления, кэш, пользовательские предпочтения) — отсутствие штатно, берём умолчание и работаем дальше. Ошибку здесь не пробрасывают и даже не показывают: сообщать не о чем.
- **Файл обязателен** (адрес базы, ключ доступа) — работать без него нельзя, но и паниковать с трассировкой не за что: это не баг. Правильная реакция границы — **внятное сообщение в stderr и ненулевой код выхода** (`main -> Result` из Г18.Ч1.З9 или явный `match` с последующим выходом).

Обе — файл `d6.rs`:

```rust
use std::fs;
use std::io;

// (б-1) файл необязателен: его отсутствие — штатная ситуация, берём умолчание
fn load_optional(path: &str) -> String {
    match fs::read_to_string(path) {
        Ok(text) => text,
        Err(_) => String::from("theme=light\n"),
    }
}

// (б-2) файл обязателен: решение остаётся за границей — она и сообщит
fn load_required(path: &str) -> Result<String, io::Error> {
    fs::read_to_string(path)
}

fn main() {
    println!("optional: {:?}", load_optional("theme.cfg"));
    match load_required("db.cfg") {
        Ok(text) => println!("required: {text:?}"),
        Err(e) => eprintln!("db.cfg нужен для работы: {e}"),
    }
}
```

Прогон без обоих файлов и прогон, когда оба на месте:

```
optional: "theme=light\n"
db.cfg нужен для работы: The system cannot find the file specified. (os error 2)
```

```
optional: "theme=dark\n"
required: "host=localhost\n"
```

Обратите внимание на асимметрию, которая и есть суть задания. `load_optional` **поглощает** ошибку — и это законно ровно потому, что у неё есть план Б; рукав `Err(_)` без данных здесь честен, причина отказа не нужна (сравните с «проглатыванием» из §18.2.3, где план Б отсутствует). `load_required` не решает ничего: она даже не пишет `match`, а просто возвращает `Result` — решение принимает `main`. Сообщение при этом уходит в **stderr** (`eprintln!`), а не в stdout: диагностика не должна попадать в полезный вывод (§18.1.2).

**Ответ:** (а) **паника** — провал программиста, инвариант нарушен своим же кодом; язык паникует сам, ничего писать не нужно; (б) **`Result`** — провал внешнего мира, решает граница; (в) **`Result`** — плохой ввод не авария, программа обязана его пережить; (г) **`panic!`** — нарушен документированный контракт, то есть баг вызывающего, продолжать опаснее, чем остановиться; (д) **паника** — упавший тест и есть паника; (е) **`unwrap`/`expect`** — черновик, краткость важнее, `expect` заодно маркирует недоделку. Две правильные реакции границы для (б): если файл **необязателен** — молча взять умолчание (`load_optional` в `d6.rs`: `Err(_) => String::from("theme=light\n")`, план Б есть, причина не нужна); если **обязателен** — вернуть `Result` наверх и на границе напечатать сообщение в stderr с ненулевым кодом выхода (`load_required` + `match` в `main`, вывод `db.cfg нужен для работы: The system cannot find the file specified. (os error 2)`). Паника в обоих случаях избыточна: отсутствие файла — не баг программы.

### Г18.Ч2.З7

**Условие.** *(понимание)* Ошибка без адреса: почему сообщение `The system cannot find the file specified.` не называет имя файла и чем это неудобно? Кто в программе §18.2.3 знает путь и как сообщение получилось полным? Сравните с `perror("scores.txt")` из §10.1.1: где в каждой из систем «знание пути» встречается со «знанием причины»? Предложите (словами, без кода) вариант `AppError`, который несёт путь с собой.

**Решение.** Сначала — факт, а не рассуждение. Файл `d7.rs` открывает два разных несуществующих файла:

```rust
use std::fs::File;

fn show(path: &str) {
    match File::open(path) {
        Ok(_) => println!("{path}: opened"),
        Err(e) => {
            println!("{path}: Display -> {e}");
            println!("{path}: Debug   -> {e:?}");
        }
    }
}

fn main() {
    // два разных пути — одна и та же ошибка: имени файла в ней нет
    show("alpha.cfg");
    show("beta.cfg");
}
```

```
alpha.cfg: Display -> The system cannot find the file specified. (os error 2)
alpha.cfg: Debug   -> Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
beta.cfg: Display -> The system cannot find the file specified. (os error 2)
beta.cfg: Debug   -> Os { code: 2, kind: NotFound, message: "The system cannot find the file specified." }
```

Две ошибки от двух разных путей неразличимы — ни в Display, ни в Debug. Имя файла в них отсутствует не по недосмотру: `io::Error` — это **ответ операционной системы**, а система отвечает на вопрос «почему не вышло», а не «с чем не вышло». Путь был **аргументом** вызова; ни ядро, ни обёртка `File::open` его в ошибке не сохраняют — иначе каждая ошибка ввода-вывода таскала бы за собой строку, которую вызывающий и так знает.

*Чем это неудобно.* Тем, что ошибка путешествует, а контекст — нет. Пока `Err` не покинул строку вызова, всё очевидно. Но `?` уносит его наверх (§18.1.3), и уже через два этажа сообщение `не удалось прочитать: The system cannot find the file specified.` не отвечает на первый вопрос пользователя — **какой** файл? Особенно наглядно это в Г18.Ч1.З9: программа открывала `a.txt` и `b.txt`, а строка `Error: Os { code: 2, kind: NotFound, … }` одинакова для обоих отказов.

*Кто знает путь в §18.2.3.* Знает **`main`** — потому что он же и задал его литералом: `sum_of_file("scores.txt")`. Поэтому сообщение получилось полным не «само», а вручную: рукав `Err(AppError::Io(e)) => eprintln!("не удалось прочитать scores.txt: {e}")` **приписывает** имя файла к причине. Знание пути и знание причины встречаются в одной строке `eprintln!` — на границе, где оба доступны. Приём работает ровно до тех пор, пока путь один и известен на месте; для `sizes(names)` из Г18.Ч1.З10 такой фокус уже не проходит — имя приходит из списка, и `main` не знает, на каком элементе оборвалось.

*Сравнение с C (§10.1.1).* Устройство `perror("scores.txt")` — то же самое, только руками и через глобаль: причина живёт в `errno` (общий канал на всю программу), путь программист передаёт **аргументом** `perror`, и функция печатает `scores.txt: No such file or directory` — приписав к строке-префиксу расшифровку `errno`. То есть встреча знаний происходит в момент **печати**, в точке вызова `perror`. Разница между системами не в месте встречи (в обоих случаях это граница), а в том, что едет между этажами: в C наверх едет `-1`, а причина остаётся в `errno`, которую следующий же вызов перезапишет; в Rust наверх едет само значение ошибки с причиной внутри, и потерять её нельзя — но приписать к ней путь всё равно должен тот, кто его знает.

*Вариант `AppError`, несущий путь (словами).* Вариант-обёртку `Io` следует превратить из «одного поля» в вариант со структурными полями (§16.2.1): **`Io { path: String, source: io::Error }`** — путь строкой и исходная ошибка целиком, чтобы у вызывающего остался и `kind()`, и текст ОС. Тогда сообщение собирается автоматически из данных ошибки — `не удалось прочитать {path}: {source}`, — и остаётся верным, даже если путь пришёл из списка, а не из литерала.

Важное следствие, которое стоит проговорить: с таким вариантом **`?` перестаёт заворачивать ошибку сам**. `impl From<io::Error> for AppError` написать больше нельзя — `from` получает только ошибку, а пути ей взять негде (и придумывать его она не вправе: §18.2.2, «`from` без логики»). Значит, на месте вызова придётся заворачивать вручную — `match` с построением `AppError::Io { path: path.to_string(), source: e }` (в настоящем коде для этого есть `map_err`, глава 21). Это честная цена: пути автоматической конвертации и дополнительного контекста расходятся, и выбирать между «`?` в одну закорючку» и «в сообщении есть имя файла» приходится осознанно.

**Ответ:** сообщение не называет файл, потому что `io::Error` — это ответ **операционной системы** на вопрос «почему», а путь был аргументом вызова и нигде в ошибке не сохраняется; проверено `d7.rs`: два разных несуществующих файла дают побайтно одинаковые Display и Debug. Неудобно это тем, что ошибка уезжает наверх через `?`, а контекст остаётся внизу: на границе уже не видно, какой из файлов не открылся (ровно случай Г18.Ч1.З9). В §18.2.3 путь знает **`main`** — он задал его литералом `sum_of_file("scores.txt")` — и приписывает имя к причине руками, в рукаве `eprintln!("не удалось прочитать scores.txt: {e}")`; там же, на границе, знание пути встречается со знанием причины. В C место встречи то же самое, но механика иная: причина лежит в глобальной `errno`, путь передаётся аргументом `perror("scores.txt")`, и склейка происходит в момент печати; при этом `errno` перезаписывается следующим вызовом, а значение-ошибка Rust — нет. Вариант, несущий путь: **`Io { path: String, source: io::Error }`** — структурные поля вместо одного, исходная ошибка сохраняется целиком (`kind()` остаётся доступен). Цена: автоматическая конвертация через `impl From<io::Error>` становится невозможной (пути `from` взять негде), и заворачивать придётся на месте вызова.

### Г18.Ч2.З8

**Условие.** *(прикладное)* Оценка по шкале: `enum ScoreError { Bad(ParseError), TooLarge(u32) }`, `impl From<ParseError> for ScoreError` и `fn parse_score(s: &str) -> Result<u32, ScoreError>`: разобрать строку через `parse_u32(s)?` и отвергнуть значения больше 100. Репортёр — match с вложенными образцами (для `Bad(BadChar(c))` — отдельное сообщение). Контроль: `"85"` → оценка 85; `"100"` → оценка 100; `"150"` → `150 вне шкалы 0..=100`; `"8x"` → `не число: символ 'x'`; `""` → сообщение про `Empty`. Здесь `?` конвертирует ваш тип в ваш же — что это говорит о механизме `From`?

**Решение.** Схема ровно та же, что в §18.2.2, только оба типа теперь наши. Файл `d8.rs`, существенная часть:

```rust
#[derive(Debug)]
enum ScoreError {
    Bad(ParseError),
    TooLarge(u32),
}

// «из моей в мою»: From ничего не знает про чужеродность типов
impl From<ParseError> for ScoreError {
    fn from(e: ParseError) -> ScoreError {
        ScoreError::Bad(e)
    }
}
```

```rust
fn parse_score(s: &str) -> Result<u32, ScoreError> {
    let n = parse_u32(s)?; // ParseError -> ScoreError силами From
    if n > 100 {
        return Err(ScoreError::TooLarge(n));
    }
    Ok(n)
}

fn report(input: &str) {
    match parse_score(input) {
        Ok(n) => println!("{input:?} -> оценка {n}"),
        Err(ScoreError::TooLarge(n)) => println!("{input:?} -> {n} вне шкалы 0..=100"),
        Err(ScoreError::Bad(ParseError::BadChar(c))) => {
            println!("{input:?} -> не число: символ {c:?}")
        }
        Err(ScoreError::Bad(ParseError::Empty)) => println!("{input:?} -> оценка не заполнена"),
        Err(ScoreError::Bad(ParseError::TooBig)) => {
            println!("{input:?} -> не число: не помещается в u32")
        }
    }
}
```

```
"100" -> оценка 100
"150" -> 150 вне шкалы 0..=100
"8x" -> не число: символ 'x'
```

Контроль сошёлся; шестой вход добавлен сверх условия — чтобы было видно, что `TooBig` из `ParseError` тоже доезжает до репортёра, завёрнутый в `Bad`. Устройство разбора — вложенные образцы из §16.2.2 в три этажа: `Err` → `ScoreError::Bad` → `ParseError::BadChar(c)`, и на самом дне связывается `c`. Порядок рукавов здесь **важен** (в отличие от Г18.Ч2.З1): образец `Bad(ParseError::BadChar(c))` уже, чем `Bad(pe)`, — поставь мы общий рукав раньше, персонального сообщения про символ не увидели бы никогда (и компилятор пометил бы недостижимый рукав). Заметьте также, что `TooLarge(u32)` несёт **само число**: репортёр печатает `150 вне шкалы`, не заглядывая во вход, — критерий 3 из §18.2.1.

*Что это говорит о механизме `From`.* Ровно то, что в его определении нет слов «чужой» и «свой». `From` — это преобразование **между двумя типами**, и обе стороны могут быть какими угодно: стандартными, вашими, из разных крейтов. `?` не спрашивает, откуда приехал `ParseError`; он смотрит на пару «тип ошибки выражения → тип ошибки функции» и ищет для неё реализацию (§18.2.2). Отсюда два практических вывода. Первый: **уровни ошибок можно вкладывать** — `ParseError` → `ScoreError` → дальше в `AppError`, и на каждом этаже `?` доклеивает нужный слой контекста; это стандартный рисунок слоистой программы. Второй: тождественный случай — не исключение, а частный случай той же схемы, в котором работает готовая реализация `impl<T> From<T> for T` (Г18.Ч2.З4). Единственное настоящее ограничение — не в «своём/чужом», а в правилах согласованности: реализовать `From` можно, если ваш крейт владеет хотя бы одной из сторон (потому обёртку и пишут для **своего** типа ошибки); подробности — глава 19, где трейты объясняются целиком.

**Ответ:** программа — листинг `d8.rs`; контроль сошёлся: `"85"` → `оценка 85`, `"100"` → `оценка 100`, `"150"` → `150 вне шкалы 0..=100`, `"8x"` → `не число: символ 'x'`, `""` → `оценка не заполнена` (вариант `Empty`), плюс проверочный `"99999999999"` → `не число: не помещается в u32`. Разбор — вложенные образцы в три этажа (`Err` → `ScoreError::Bad` → `ParseError::BadChar(c)`), и порядок рукавов здесь важен: частный `Bad(BadChar(c))` обязан стоять раньше общих. То, что `?` конвертирует `ParseError` в `ScoreError` — то есть ваш тип в ваш же, — показывает: **`From` не различает «свои» и «чужие» типы**, это преобразование между парой типов, и `?` выбирает реализацию по паре «тип ошибки выражения → тип ошибки функции». Отсюда возможность **вкладывать уровни ошибок** (`ParseError` → `ScoreError` → `AppError`), доклеивая контекст на каждом этаже, и понимание, что тождественный случай — тот же механизм с готовой реализацией `impl<T> From<T> for T`.

### Г18.Ч2.З9

**Условие.** *(прикладное)* Статистика вместо суммы: на базе `sum_scores.rs` напишите `fn stats_of_file(path: &str) -> Result<(u32, u32, u32), AppError>`, возвращающую `(min, max, count)`. Пустой список чисел — новый вариант ошибки `AppError::NoData` (сумме пустота не мешала, статистике — да; добавьте вариант и ветку в `main`, для `BadChar` сохраните персональное сообщение). Контроль: `10 25 7` → `min=7 max=25 count=3`; пустой файл → `файл пуст: статистики нет`; нет файла → сообщение с причиной ОС.

**Решение.** От `sum_scores.rs` берём всё, кроме последнего этажа: `parse_u32`, `parse_numbers`, оба `impl From` и рисунок `main`. Меняется тип успеха (кортеж из трёх чисел вместо одного) и добавляется третий вариант ошибки — **`NoData`**, у которого, в отличие от `Io` и `Parse`, нет данных: заворачивать нечего, «чисел не было» — исчерпывающее описание. Файл `d9.rs`, существенная часть:

```rust
#[derive(Debug)]
enum AppError {
    Io(io::Error),
    Parse(ParseError),
    NoData, // статистике пустой список мешает, а сумме не мешал
}
```

```rust
fn stats_of_file(path: &str) -> Result<(u32, u32, u32), AppError> {
    let text = fs::read_to_string(path)?;
    let nums = parse_numbers(&text)?;
    if nums.is_empty() {
        return Err(AppError::NoData);
    }
    // затравка — первый элемент: он заведомо есть, и никаких «магических» границ
    let mut min = nums[0];
    let mut max = nums[0];
    let mut count: u32 = 0;
    for n in &nums {
        if *n < min {
            min = *n;
        }
        if *n > max {
            max = *n;
        }
        count += 1;
    }
    Ok((min, max, count))
}

fn main() {
    match stats_of_file("scores.txt") {
        Ok((min, max, count)) => println!("min={min} max={max} count={count}"),
        Err(AppError::Io(e)) => eprintln!("не удалось прочитать scores.txt: {e}"),
        Err(AppError::NoData) => eprintln!("файл пуст: статистики нет"),
        Err(AppError::Parse(ParseError::BadChar(c))) => {
            eprintln!("в файле не число: символ {c:?}")
        }
        Err(AppError::Parse(pe)) => eprintln!("файл повреждён: {pe:?}"),
    }
}
```

Первое — **проверка пустоты стоит до расчёта**, и это не придирчивость: без неё пришлось бы придумывать `min` и `max` для пустого списка. Второе — распаковка кортежа прямо в образце: `Ok((min, max, count))` связывает три имени за один шаг (§16.2.2). Возвращать три числа кортежем удобно ровно до тех пор, пока их смысл очевиден из порядка; в настоящем коде на четвёртом-пятом поле пора заводить `struct`.

Третье — рукав `NoData` стоит **раньше** общего `Parse(pe)`, но это не обязательное требование, а вкус: образцы не перекрываются (Г18.Ч2.З1). А вот `Parse(ParseError::BadChar(c))` перед `Parse(pe)` — обязательно.

Контроль: `10 25 7` → `min=7 max=25 count=3`; пустой файл → `файл пуст: статистики нет`; отсутствующий файл → `не удалось прочитать scores.txt: The system cannot find the file specified. (os error 2)`; проверочный `10 abc 5` → `в файле не число: символ 'a'` (персональное сообщение сохранено). Вариант `NoData` намеренно без данных — описывать нечего; проверка пустоты обязана стоять **до** расчёта, иначе «затравка бесконечностями» вернула бы на пустом входе бессмысленные `min=4294967295 max=0` вместо честного отказа.

**Вариант 2 (один проход, без промежуточного вектора).** `parse_numbers` строит `Vec<u32>` целиком — а статистике вектор не нужен: числа можно учитывать по мере разбора и тут же забывать. Файл `d9v2.rs`:

```rust
// один проход: слово разобрали — сразу учли, вектора чисел нет вовсе
fn stats_of_text(text: &str) -> Result<(u32, u32, u32), AppError> {
    let mut token = String::new();
    let mut min: u32 = 0;
    let mut max: u32 = 0;
    let mut count: u32 = 0;
    for c in text.chars() {
        if c.is_whitespace() {
            if !token.is_empty() {
                let n = parse_u32(&token)?; // ParseError -> AppError силами From
                if count == 0 || n < min {
                    min = n;
                }
                if count == 0 || n > max {
                    max = n;
                }
                count += 1;
                token.clear();
            }
        } else {
            token.push(c);
        }
    }
    if !token.is_empty() {
        let n = parse_u32(&token)?;
        if count == 0 || n < min {
            min = n;
        }
        if count == 0 || n > max {
            max = n;
        }
        count += 1;
    }
    if count == 0 {
        return Err(AppError::NoData);
    }
    Ok((min, max, count))
}
```

### Г18.Ч2.З10

**Условие.** *(прикладное)* Банкомат: `struct Account { balance: u32 }` и метод `fn withdraw(&mut self, amount: u32) -> Result<u32, WithdrawError>` (возвращает новый остаток), где `enum WithdrawError { Zero, Insufficient { balance: u32, need: u32 } }` — второй вариант со структурными полями (§16.2.1). Репортёр печатает по-человечески. Контроль для счёта 100 и попыток снять 30, 0, 200, 70: `снято 30, остаток 70` / `снятие нуля не имеет смысла` / `нужно 200, а на счёте 70 — отказ` / `снято 70, остаток 0`. Объясните: почему `withdraw` при отказе не должен трогать `balance` — и как ранние `return Err` это гарантируют.

**Решение.** Файл `d10.rs`:

```rust
#[derive(Debug)]
enum WithdrawError {
    Zero,
    Insufficient { balance: u32, need: u32 },
}

struct Account {
    balance: u32,
}

impl Account {
    fn withdraw(&mut self, amount: u32) -> Result<u32, WithdrawError> {
        if amount == 0 {
            return Err(WithdrawError::Zero); // счёт не тронут
        }
        if amount > self.balance {
            return Err(WithdrawError::Insufficient {
                balance: self.balance,
                need: amount,
            }); // счёт не тронут
        }
        self.balance -= amount; // единственная строка, меняющая состояние
        Ok(self.balance)
    }
}

fn report(acc: &mut Account, amount: u32) {
    match acc.withdraw(amount) {
        Ok(rest) => println!("снято {amount}, остаток {rest}"),
        Err(WithdrawError::Zero) => println!("снятие нуля не имеет смысла"),
        Err(WithdrawError::Insufficient { balance, need }) => {
            println!("нужно {need}, а на счёте {balance} — отказ")
        }
    }
}

fn main() {
    let mut acc = Account { balance: 100 };
    report(&mut acc, 30);
    report(&mut acc, 0);
    report(&mut acc, 200);
    report(&mut acc, 70);
}
```

```
снято 30, остаток 70
снятие нуля не имеет смысла
нужно 200, а на счёте 70 — отказ
снято 70, остаток 0
```

Контроль сошёлся полностью, и последняя строка — главное доказательство: после двух отказов подряд на счёте оставалось ровно 70, поэтому снятие 70 прошло и обнулило счёт. Устройство: `&mut self` — метод-изменение из §16.1.2; `Insufficient { balance, need }` — вариант со **структурными полями** (§16.2.1), и в образце эти же имена связываются автоматически (`Err(WithdrawError::Insufficient { balance, need })`), так что репортёру не нужно помнить ни запрошенную сумму, ни состояние счёта — оба числа приехали в ошибке. Отсюда и человеческое сообщение `нужно 200, а на счёте 70 — отказ`, собранное **только** из данных ошибки.

Один момент, который легко проглядеть: `self.balance -= amount` для `u32` безопасно ровно потому, что выше стоит проверка `amount > self.balance`. Без неё вычитание ушло бы в отрицательное — то есть, для беззнакового типа, в панику `attempt to subtract with overflow` в debug-профиле и в тихое «огромное число» в release (§14.2.2). Страж здесь не только правило бизнес-логики, но и защита от переполнения.

*Почему `withdraw` при отказе не должен трогать `balance`.* Потому что `Err` — это обещание: «операция не состоялась, состояние такое же, как до вызова». На нём держатся три вещи. Первая: **повтор безопасен** — вызывающий, получив `Insufficient`, вправе спросить другую сумму, и списание не должно накопиться из неудачных попыток. Вторая: **сообщение остаётся правдой** — в ошибке уехало `balance: 70`, и если бы метод успел что-то списать, число в сообщении уже не соответствовало бы счёту. Третья: **вызывающему не нужно чинить состояние** — иначе после каждого `Err` пришлось бы возвращать деньги обратно, то есть знать внутреннее устройство `Account` (и не забыть об этом ни в одной ветке — в точности та дисциплина `goto cleanup` из тома I, от которой мы уходим). Свойство «либо целиком, либо ничего» стоит рядом с тем, что делает `?` в Г18.Ч1.З10: там при отказе не оставалось полурезультата, здесь — полусписания.

*Как это гарантируют ранние `return Err`.* Механически: **единственная строка, меняющая состояние (`self.balance -= amount`), стоит ниже всех проверок**, и попасть на неё можно, только миновав их все. Каждый `return Err(...)` покидает метод до неё — значит, ни одна отказная ветка физически не достигает изменения. Проверить это можно глазами по одному правилу: «изменения — после всех `return Err`». Стиль с ранними выходами тем и хорош, что делает такую проверку локальной; если бы отказы разбирались вложенными `if/else` вокруг изменения, пришлось бы прослеживать все ветви. Оговорка на будущее: правило работает, пока изменение **одно**. Меняй метод два поля подряд, а отказ случайся между ними — половина работы осталась бы сделанной; для таких случаев состояние либо готовят целиком и присваивают одним махом, либо (в настоящих системах) заводят транзакцию.

**Ответ:** программа — листинг `d10.rs`; контроль сошёлся: `снято 30, остаток 70` / `снятие нуля не имеет смысла` / `нужно 200, а на счёте 70 — отказ` / `снято 70, остаток 0` (последняя строка подтверждает, что отказы счёт не тронули). Оба числа в сообщении о недостатке средств приехали из самой ошибки — вариант `Insufficient { balance, need }` со структурными полями, имена которых связываются прямо в образце. `withdraw` не должен трогать `balance` при отказе, потому что `Err` означает «операция не состоялась»: на этом держатся безопасность повтора, правдивость чисел в сообщении и отсутствие у вызывающего обязанности чинить состояние. Гарантируют это ранние `return Err`: **единственная изменяющая строка `self.balance -= amount` стоит ниже всех проверок**, и каждая отказная ветка покидает метод раньше неё — свойство проверяется одним взглядом («изменения после всех `return Err`»), пока изменение одно.

**Вариант 2 (операция сообщает только об исходе).** Возврат нового остатка — не единственный разумный контракт: метод может отвечать `Result<(), WithdrawError>`, а остаток вызывающий прочитает у счёта сам. Файл `d10v2.rs`:

```rust
impl Account {
    // операция сообщает только об исходе; остаток читается у счёта
    fn withdraw(&mut self, amount: u32) -> Result<(), WithdrawError> {
        if amount == 0 {
            return Err(WithdrawError::Zero);
        }
        if amount > self.balance {
            return Err(WithdrawError::Insufficient {
                balance: self.balance,
                need: amount,
            });
        }
        self.balance -= amount;
        Ok(())
    }
}

fn report(acc: &mut Account, amount: u32) {
    match acc.withdraw(amount) {
        Ok(()) => println!("снято {amount}, остаток {}", acc.balance),
        Err(WithdrawError::Zero) => println!("снятие нуля не имеет смысла"),
        Err(WithdrawError::Insufficient { balance, need }) => {
            println!("нужно {need}, а на счёте {balance} — отказ")
        }
    }
}
```

*Сравнение.* Вывод совпадает до символа — разница в контракте, а не в поведении. Плюсы варианта 2: единственный источник истины об остатке — поле счёта, и «устаревшего» числа на руках у вызывающего не бывает; рукав `Ok(())` явно говорит, что полезного значения нет — сигнатура не обещает лишнего. Минусы: остаток читается **после** вызова, значит, вызывающий обязан иметь доступ к счёту в тот же момент (в нашем `report` он есть, а вот при пробросе результата наверх — уже нет), и при `?`-стиле цепочка `let rest = acc.withdraw(30)?;` перестаёт давать число. Базовая версия с `Result<u32, _>` возвращает «остаток на момент операции» — самодостаточный ответ, который можно записать в журнал или отправить по сети, не таща с собой сам счёт. Когда предпочесть: `Result<(), E>` — когда объект под рукой и число легко перечитать (типично для методов, меняющих состояние: `insert`, `set`, `commit`); `Result<T, E>` — когда результат операции нужен как самостоятельное значение, особенно если он уезжает от объекта (журнал, ответ пользователю, следующий шаг конвейера).
