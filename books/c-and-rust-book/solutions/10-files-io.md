## Часть 10.1. Текстовые файлы

### Г10.Ч1.З1

**Условие.** Запишите в файл `diary.txt` три строки: `day 1: sunny`, `day 2: rain`, `day 3: fog` — одним `fopen("w")` и тремя `fprintf` (номер дня подставьте через `%d`). Закройте файл, откройте на чтение и напечатайте содержимое с нумерацией: `1: day 1: sunny` и т. д. Оба открытия — с проверкой на `NULL` и `perror`.

**Решение.** Задание — полный цикл §10.1.1: `fopen` → проверка `NULL` → работа → `fclose`, дважды: сначала на запись, потом на чтение. Три детали, о которых легко забыть.

1. **Режим `"w"`** создаёт файл заново (существующий обнуляется) — именно то, что нужно «дневнику», который программа пишет с нуля.
2. **`fclose` записывающего потока проверяется**: до него данные лежат в буфере, и только `fclose` сообщит, что запись не удалась (§10.1.1). Открывать файл на чтение раньше, чем он закрыт, — верный способ прочитать половину.
3. **`fgets` оставляет `'\n'` в буфере** (§10.1.2), поэтому в `printf` своего `\n` не нужно: строка уже заканчивается переводом строки.

```c
#include <stdio.h>

int main(void)
{
    FILE *out = fopen("diary.txt", "w");          /* "w": создать заново */
    if (out == NULL) { perror("diary.txt"); return 1; }
    fprintf(out, "day %d: sunny\n", 1);
    fprintf(out, "day %d: rain\n", 2);
    fprintf(out, "day %d: fog\n", 3);
    if (fclose(out) == EOF) { perror("diary.txt"); return 1; }

    FILE *in = fopen("diary.txt", "r");           /* "r": только чтение */
    if (in == NULL) { perror("diary.txt"); return 1; }
    char line[128];
    int n = 0;
    while (fgets(line, sizeof line, in) != NULL)
        printf("%d: %s", ++n, line);              /* '\n' уже внутри line */
    fclose(in);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra diary.c -o diary
./diary
```

```
1: day 1: sunny
2: day 2: rain
3: day 3: fog
```

Номер строки считает сам цикл (`++n` в аргументе `printf`), а не «знание», что строк три: программа напечатает столько номеров, сколько строк реально прочитала. Цикл управляется результатом `fgets` — по правилу §10.1.3, а не `feof`.

**Ответ:** программа печатает
```
1: day 1: sunny
2: day 2: rain
3: day 3: fog
```
Схема — две триады «`fopen` → проверка `NULL` (+`perror`) → работа → `fclose`»: первая с режимом `"w"` и тремя `fprintf` (номер дня подставлен через `%d`), вторая с `"r"` и циклом `while (fgets(...) != NULL)`. Результат `fclose` записывающего потока проверяется — это последний рубеж, на котором ещё можно узнать, что данные не долетели до диска; в `printf("%d: %s", ...)` собственный `\n` не нужен, потому что `fgets` вернула строку вместе с переводом строки из файла.

### Г10.Ч1.З2

**Условие.** Напишите функцию `int append_line(const char *path, const char *text)`: открыть `path` в режиме `"a"`, дописать `text` и перевод строки, закрыть; вернуть 0 при успехе и −1 при любой ошибке. В `main` вызовите её трижды со строками `first`, `second`, `third`, затем напечатайте файл: должны быть три строки в порядке вызовов. Объясните (и проверьте), что изменилось бы при режиме `"w"` внутри функции.

**Решение.** Функция владеет потоком целиком: открыла — обязана закрыть на любом пути выхода (§10.1.1). Ошибкой считается всё три: отказ `fopen`, отказ записи (`fprintf` возвращает отрицательное число), отказ `fclose`. Режим `"a"` гарантирует, что каждая запись уходит в текущий конец файла, — журналу большего и не нужно.

Одна тонкость про воспроизводимость: `"a"` не обнуляет файл, поэтому при повторном запуске в той же папке строки накапливались бы. Поэтому `main` начинает с явного «создать пустой файл» — это единственное место, где уместен `"w"`.

```c
#include <stdio.h>

int append_line(const char *path, const char *text)
{
    FILE *f = fopen(path, "a");                 /* "a": всегда в конец */
    if (f == NULL) { perror(path); return -1; }
    if (fprintf(f, "%s\n", text) < 0) {         /* запись тоже может не удаться */
        fclose(f);
        return -1;
    }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

static void dump(const char *path)
{
    FILE *f = fopen(path, "r");
    if (f == NULL) { perror(path); return; }
    char line[128];
    while (fgets(line, sizeof line, f) != NULL)
        printf("  %s", line);
    fclose(f);
}

int main(void)
{
    FILE *fresh = fopen("log.txt", "w");        /* начинаем с пустого файла */
    if (fresh == NULL) { perror("log.txt"); return 1; }
    if (fclose(fresh) == EOF) { perror("log.txt"); return 1; }

    if (append_line("log.txt", "first") != 0)  return 1;
    if (append_line("log.txt", "second") != 0) return 1;
    if (append_line("log.txt", "third") != 0)  return 1;

    puts("log.txt:");
    dump("log.txt");
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra append.c -o append
./append
```

```
log.txt:
  first
  second
  third
```

Теперь проверка обещанного: та же программа, но внутри функции — `"w"`.

```c
int append_line_w(const char *path, const char *text)   /* !!! "w" вместо "a" */
{
    FILE *f = fopen(path, "w");
    if (f == NULL) { perror(path); return -1; }
    if (fprintf(f, "%s\n", text) < 0) { fclose(f); return -1; }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra append_w.c -o append_w
./append_w
```

```
log_w.txt:
  third
```

Три вызова — одна строка в файле: каждый `fopen(..., "w")` обнулял файл, и до конца дожила только последняя запись. Ни компилятор, ни `-Wall -Wextra` об этом не предупредят — для них `"a"` и `"w"` просто разные строки.

**Ответ:** функция открывает файл в `"a"`, пишет `fprintf(f, "%s\n", text)`, закрывает и возвращает −1 при отказе любого из трёх шагов (открытие, запись, закрытие), иначе 0. Три вызова дают файл из трёх строк в порядке вызовов: `first`, `second`, `third`. С режимом `"w"` внутри функции результат — **одна** строка `third`: `"w"` обнуляет существующий файл при каждом открытии, поэтому каждый вызов стирает написанное предыдущим. Отсюда правило §10.1.1: для дозаписи (журналы, «итог в конец») — только `"a"`, а `"w"` уместен ровно там, где файл сознательно создаётся заново, — в нашей программе это единственная строка в `main`, обнуляющая `log.txt` перед серией дозаписей.

### Г10.Ч1.З3

**Условие.** В файле `nums.txt` записаны целые числа, разделённые пробелами и переводами строк (создайте его программно с содержимым `3 1 4 1 5 9 2 6`). Прочитайте их циклом `while (fscanf(...) == 1)` и напечатайте `count=8 sum=31 max=9` (количество, сумму, максимум — вычислите, а не захардкодьте).

**Решение.** `fscanf(f, "%d", &x)` возвращает число заполненных позиций — здесь ровно 1 при успехе (§10.1.2), поэтому цикл `while (fscanf(f, "%d", &x) == 1)` останавливается и на конце файла, и на нечисловом мусоре. Спецификатор `%d` сам пропускает пробельные символы, поэтому пробелы и переводы строк в разделении чисел роли не играют — файл специально записан двумя строками, чтобы это было видно.

Единственная ловушка — инициализация максимума. `int max = 0` молча даст неверный ответ на файле из одних отрицательных чисел, поэтому первый элемент назначается максимумом явно (`count == 0`).

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("nums.txt", "w");
    if (f == NULL) { perror("nums.txt"); return 1; }
    fputs("3 1 4 1\n5 9 2 6\n", f);              /* пробелы и переводы строк */
    if (fclose(f) == EOF) { perror("nums.txt"); return 1; }

    f = fopen("nums.txt", "r");
    if (f == NULL) { perror("nums.txt"); return 1; }
    int x, count = 0, sum = 0, max = 0;
    while (fscanf(f, "%d", &x) == 1) {           /* 1 = число прочитано */
        if (count == 0 || x > max)               /* первый элемент — сам себе максимум */
            max = x;
        sum += x;
        count++;
    }
    fclose(f);

    if (count == 0) {
        puts("no numbers");
        return 1;
    }
    printf("count=%d sum=%d max=%d\n", count, sum, max);
    return 0;
}
```

```
gcc -std=c17 -Wall -Wextra nums.c -o nums
./nums
```

```
count=8 sum=31 max=9
```

Сверка вручную: 3+1+4+1+5+9+2+6 = 31, чисел восемь, наибольшее — 9. Обратите внимание, что ни одно из трёх чисел в программе не записано константой: они вычисляются из того, что реально прочитано, — поэтому программа не соврёт и на другом файле.

**Ответ:** `count=8 sum=31 max=9`. Цикл `while (fscanf(f, "%d", &x) == 1)` работает по возвращаемому значению — «одна позиция заполнена» (§10.1.2); `%d` сам пропускает пробелы и переводы строк, поэтому разбиение файла на строки не влияет на разбор. Максимум инициализируется первым прочитанным элементом (`count == 0 || x > max`), а не нулём: иначе на файле из отрицательных чисел ответом стал бы 0 — число, которого в файле нет. Пустой файл обрабатывается отдельной веткой (`count == 0`): среднего, максимума и «итога» у пустых данных не бывает.

### Г10.Ч1.З4

**Условие.** *(понимание)* Назовите не меньше трёх разных причин, по которым `fopen` может вернуть `NULL` (подсказка: подумайте про режимы `"r"` и `"w"` отдельно). Что печатает `perror` и из чего складывается его сообщение? Почему сообщение об ошибке правильно отправлять в `stderr`, а не в `stdout` — приведите сценарий, где вывод в `stdout` навредит.

**Решение.** Причины удобно разложить по режимам — они отказывают по-разному.

**Режим `"r"` (нужен существующий файл):**
1. **файла нет** — самая частая причина (опечатка в имени, файл ещё не создан);
2. **нет прав на чтение** — файл существует, но принадлежит другому пользователю;
3. **путь ведёт не туда**: промежуточного каталога не существует, либо имя оказалось **каталогом**, а не файлом.

**Режим `"w"` (файл создаётся или обнуляется):**
4. **каталога назначения не существует** — создавать файл негде;
5. **нет прав на запись**: файл помечен «только для чтения» или каталог закрыт для записи;
6. **файл занят**: на Windows другой процесс может держать файл так, что открыть его на запись нельзя.

Есть и причины, общие для любого режима: исчерпан лимит открытых файлов процесса (§10.1.1 — именно поэтому потоки закрывают сразу, C10 FIO42-C), слишком длинное или недопустимое имя, кончилось место или квота. Проверим четыре случая прогоном:

```c
#include <stdio.h>

static void try_open(const char *path, const char *mode)
{
    FILE *f = fopen(path, mode);
    if (f == NULL) {
        perror(path);            /* префикс + ": " + системный текст, всё в stderr */
        return;
    }
    printf("opened: %s (%s)\n", path, mode);
    fclose(f);
}

int main(void)
{
    try_open("no-such-file.txt", "r");     /* 1) файла нет, а "r" требует существующего */
    try_open("no-such-dir/out.txt", "w");  /* 2) каталога нет — создавать негде */
    try_open("readonly.txt", "w");         /* 3) файл только для чтения */
    try_open("sub", "r");                  /* 4) это каталог, а не файл */
    return 0;
}
```

Перед запуском в рабочей папке созданы `readonly.txt` (с атрибутом «только чтение») и каталог `sub`.

```
gcc -std=c17 -Wall -Wextra openfail.c -o openfail
./openfail
```

В `stdout` — пусто, весь вывод ушёл в `stderr`:

```
no-such-file.txt: No such file or directory
no-such-dir/out.txt: No such file or directory
readonly.txt: Permission denied
sub: Permission denied
```

Четыре вызова — четыре отказа, и ни одного падения: программа каждый раз получила `NULL` и обработала его.

**Что печатает `perror`.** Сообщение складывается из трёх частей: **ваш префикс** (аргумент `perror`), **`": "`** и **системное описание последней ошибки** — текст, соответствующий текущему значению `errno` (`<errno.h>`, C5 §7.5), плюс перевод строки. Пишется всё это в `stderr` (C5 §7.23.10.4). Формулировки системных текстов зависят от платформы: `No such file or directory`, `Permission denied` — то, что напечатала наша; на другой системе и в другой локали слова будут другими. Отсюда практический смысл префикса: системная часть говорит, *что* случилось, ваша — *с чем именно*, поэтому в префикс ставят имя файла (как в примерах главы), а не слово «ошибка».

**Почему `stderr`.** Потому что `stdout` — это канал полезных данных, и он часто **перенаправлен**. Сценарий: наш фильтр комментариев из Г10.Ч1.З9 запускают как `./nocomments config.txt > clean.txt`. Если сообщение об ошибке уйдёт в `stdout`, оно (а) попадёт **внутрь** `clean.txt`, испортив данные — следующий инструмент увидит в конфигурации строку `config.txt: No such file or directory`; (б) **не появится на экране** — пользователь будет уверен, что всё прошло успешно. Через `stderr` сообщение и на экран попадёт, и в файл-результат не просочится. Тот же довод в конвейере: `./tool data.txt | sort` — диагностика, попавшая в `stdout`, станет для `sort` строкой данных.

**Ответ:** причин отказа минимум шесть, и они распадаются по режимам: для `"r"` — файла не существует, нет прав на чтение, путь указывает на каталог или несуществующий каталог; для `"w"` — не существует каталог назначения, нет прав на запись (файл «только для чтения», закрытый каталог), файл занят другим процессом; общие для любого режима — исчерпан лимит открытых файлов, недопустимое имя, нет места. Прогон дал дословно `no-such-file.txt: No such file or directory`, `no-such-dir/out.txt: No such file or directory`, `readonly.txt: Permission denied`, `sub: Permission denied`. `perror(префикс)` печатает в `stderr` строку «префикс`: `системное описание последней ошибки» — описание берётся из `errno` и зависит от платформы, поэтому осмысленный префикс (имя файла) обязателен. Диагностика идёт в `stderr`, потому что `stdout` — канал результата: при `./prog > out.txt` сообщение из `stdout` испортило бы файл результата и осталось бы невидимым для пользователя, а в конвейере `./prog | sort` — стало бы входными данными следующей программы.

### Г10.Ч1.З5

**Условие.** *(понимание)* Дан фрагмент: `while (!feof(f)) { fgets(line, sizeof line, f); printf("%s", line); }`. Файл содержит две строки: `one` и `two`. Выпишите по итерациям, что вернёт `fgets`, что лежит в `line` и что уйдёт на печать; какая гарантия стандарта о поведении `fgets` при конце файла делает результат воспроизводимым? Исправьте цикл.

**Решение.** Разбор по итерациям (файл — `one\ntwo\n`, буфер `line[64]`):

| Итерация | `feof` на входе | что вернёт `fgets` | что в `line` | что напечатает `printf` |
|---|---|---|---|---|
| 1 | 0 | адрес `line` | `"one\n"` | `one` + перевод строки |
| 2 | 0 | адрес `line` | `"two\n"` | `two` + перевод строки |
| 3 | **0** | **`NULL`** | **`"two\n"` — не изменилось** | `two` **ещё раз** |
| — | 1 | цикл не начинается | — | — |

Ключ — третья итерация. После чтения второй строки индикатор конца файла ещё **не** установлен: `fgets` прочитала `"two\n"` целиком и в конец не упиралась (§10.1.3). Поэтому `!feof(f)` истинно, цикл входит в третью итерацию, `fgets` пытается читать, получает конец файла и возвращает `NULL` — а печатается при этом старое содержимое буфера.

Воспроизводимость обеспечивает гарантия C5 §7.23.7.2: **если встречен конец файла и в массив не прочитано ни одного символа, содержимое массива остаётся неизменным**, а функция возвращает нулевой указатель. Именно поэтому в `line` гарантированно лежит прошлая строка (а не мусор и не пустая строка) — дублирование последней строки предсказуемо и одинаково воспроизводится везде.

Программа печатает и трассировку, и оба цикла — ошибочный и правильный:

```c
#include <stdio.h>

static void show(const char *s)          /* печатает строку, показывая '\n' как \n */
{
    for (const char *p = s; *p != '\0'; p++) {
        if (*p == '\n')
            printf("\\n");
        else
            printf("%c", *p);
    }
}

int main(void)
{
    FILE *f = fopen("two.txt", "w");
    if (f == NULL) { perror("two.txt"); return 1; }
    fputs("one\ntwo\n", f);
    if (fclose(f) == EOF) { perror("two.txt"); return 1; }

    /* --- трассировка ошибочного цикла --- */
    f = fopen("two.txt", "r");
    if (f == NULL) { perror("two.txt"); return 1; }
    char line[64] = "";
    int n = 0;
    puts("-- trace of while (!feof) --");
    while (!feof(f)) {
        char *r = fgets(line, sizeof line, f);
        printf("iter %d: fgets -> %s, line = [", ++n, r == NULL ? "NULL" : "buf");
        show(line);
        printf("], feof after = %d\n", feof(f) != 0);
    }
    fclose(f);

    /* --- как это выглядит в исходном виде (результат fgets не проверяется) --- */
    f = fopen("two.txt", "r");
    if (f == NULL) { perror("two.txt"); return 1; }
    n = 0;
    puts("-- while (!feof) as written --");
    while (!feof(f)) {
        fgets(line, sizeof line, f);
        printf("line %d: %s", ++n, line);
    }
    fclose(f);

    /* --- исправленный цикл --- */
    f = fopen("two.txt", "r");
    if (f == NULL) { perror("two.txt"); return 1; }
    n = 0;
    puts("-- while (fgets != NULL) --");
    while (fgets(line, sizeof line, f) != NULL)
        printf("line %d: %s", ++n, line);
    fclose(f);
    return 0;
}
```

```

Трассировка подтверждает разбор дословно: после второй строки `feof` ещё 0 — вот откуда берётся третья итерация; в ней `fgets` вернула `NULL` и буфер не тронула. Заметьте, что компилятор с `-Wall -Wextra` не сказал об этом ни слова: игнорирование результата `fgets` — не синтаксическая, а логическая ошибка.

Исправление — управлять циклом по результату функции чтения:

```c
while (fgets(line, sizeof line, f) != NULL)
    printf("%s", line);
```

**Ответ:** по итерациям — 1: `fgets` вернула `line`, в буфере `"one\n"`, печатается `one`; 2: вернула `line`, в буфере `"two\n"`, печатается `two`; 3: `feof` всё ещё 0 (за край файла не заглядывали), поэтому цикл входит снова, `fgets` возвращает `NULL` и **не меняет буфер** — печатается `two` во второй раз; только теперь `feof` даёт 1 и цикл завершается. Итог: две строки в файле, три строки на печати. Воспроизводимость обеспечена гарантией C5 §7.23.7.2 — при конце файла и нуле прочитанных символов содержимое массива остаётся неизменным, поэтому дублируется именно последняя строка. Правильный цикл — `while (fgets(line, sizeof line, f) != NULL) printf("%s", line);`: он проверяет результат самой операции чтения, а `feof`/`ferror` вызывают **после** цикла, чтобы узнать причину остановки (§10.1.3).

### Г10.Ч1.З6

**Условие.** *(понимание)* Программа читает файл циклом `while (fgets(line, sizeof line, f) != NULL) printf("[%s]\n", line);`. Почему закрывающая скобка печатается на следующей строке? Покажите идиому среза `'\n'` и объясните каждую её проверку. Чем `fgets(line, sizeof line, f)` безопаснее `fscanf(f, "%s", line)` — и при каком содержимом файла разница станет фатальной?

**Решение.** Скобка «уезжает», потому что `fgets` отдаёт строку **вместе с переводом строки**: она читает до `'\n'` **включительно** и дописывает `'\0'` (C5 §7.23.7.2). В буфере лежит `"alpha\n"`, формат `"[%s]\n"` подставляет это целиком — и `]` печатается уже после чужого перевода строки.

```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    FILE *f = fopen("lines.txt", "w");
    if (f == NULL) { perror("lines.txt"); return 1; }
    fputs("alpha\nbeta\n", f);
    if (fclose(f) == EOF) { perror("lines.txt"); return 1; }

    f = fopen("lines.txt", "r");
    if (f == NULL) { perror("lines.txt"); return 1; }
    char line[64];
    while (fgets(line, sizeof line, f) != NULL) {
        printf("as is:    [%s]\n", line);        /* '\n' из файла ещё внутри */
        size_t n = strlen(line);
        if (n > 0 && line[n - 1] == '\n')        /* срез: только если он там есть */
            line[n - 1] = '\0';
        printf("stripped: [%s]\n", line);
    }
    fclose(f);
    return 0;
}
```

**Идиома среза и её проверки:**

```c
size_t n = strlen(line);
if (n > 0 && line[n - 1] == '\n')
    line[n - 1] = '\0';
```

- `n > 0` — защита индексации: при `n == 0` выражение `line[n - 1]` превратилось бы в `line[(size_t)-1]` — огромный индекс и выход за границы массива (`size_t` беззнаковый, §2.3). Нулевая длина возможна: если первым байтом строки в файле окажется `'\0'` (бинарный мусор в «текстовом» файле никто не запрещал), `strlen` вернёт 0.
- `line[n - 1] == '\n'` — проверка, что срезать вообще есть что. Перевода строки в буфере не окажется в двух штатных случаях: строка в файле длиннее буфера (`fgets` прочитала первые `n − 1` символов, остаток дочитается следующим вызовом) и последняя строка файла не завершена переводом строки. Резать «последний символ» без проверки — значит в этих случаях испортить данные, отрезав полезный символ.
- присваивание `'\0'` не «удаляет» символ, а обрывает строку на нём: длина по `strlen` уменьшается на 1, физически буфер тот же.

**Почему `fgets` безопаснее `fscanf(f, "%s", line)`.** `fgets` получает **размер буфера** и читает не более `n − 1` символов — переполнить массив она не может по контракту. У `fscanf` с `%s` без ширины никакого знания о размере буфера нет: сколько непробельных символов лежит в файле, столько она и запишет. Разница становится фатальной, как только в файле встретится «слово» длиннее буфера: например, строка из 40 символов при `char small[8]`. Это переполнение буфера — неопределённое поведение (гл. 5), а поскольку буфер обычно на стеке, затираются соседние объекты и служебные данные кадра.

Демонстрация — намеренно сломанная программа:

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("long.txt", "w");
    if (f == NULL) { perror("long.txt"); return 1; }
    for (int i = 0; i < 40; i++)          /* строка из 40 символов 'x' */
        fputc('x', f);
    fputc('\n', f);
    if (fclose(f) == EOF) { perror("long.txt"); return 1; }

    f = fopen("long.txt", "r");
    if (f == NULL) { perror("long.txt"); return 1; }
    char small[8];
    if (fscanf(f, "%s", small) == 1)      /* !!! без ширины: 40 символов в буфер на 8 */
        printf("read: %s\n", small);
    fclose(f);
    return 0;
}
```

Идиома среза — `size_t n = strlen(line); if (n > 0 && line[n - 1] == '\n') line[n - 1] = '\0';`: проверка `n > 0` не даёт вычислить индекс `n - 1` при нулевой длине (беззнаковое вычитание дало бы огромный индекс и выход за границы), а сравнение с `'\n'` не даёт отрезать полезный символ, когда перевода строки в буфере нет — при слишком длинной строке или незавершённой последней строке файла. `fgets` безопаснее `fscanf(f, "%s", line)` тем, что знает размер буфера и читает не более `n − 1` символов, тогда как `%s` без ширины пишет столько, сколько есть в файле. Разница фатальна, как только слово в файле длиннее буфера: прогон с 40 символами `'x'` и `char small[8]` дал отчёт ASan `stack-buffer-overflow`, `WRITE of size 41` — переполнение стекового буфера, которого компилятор с `-Wall -Wextra` не заметил.

### Г10.Ч1.З7

**Условие.** *(понимание)* Почему приёмник результата `fgetc` обязан быть `int`, а не `char`? Файл содержит два байта: 255 и `'A'`. Проследите выполнение `while ((c = fgetc(f)) != EOF)` для `char c` на платформе со знаковым `char` (наша) и с беззнаковым: сколько итераций сделает цикл в каждом случае и почему? Каким правилом CERT это описано?

**Решение.** `fgetc` возвращает прочитанный байт **как `unsigned char`, преобразованный к `int`** — то есть значение из диапазона 0…255, — либо `EOF`, отрицательную константу (на нашей платформе −1) (C5 §7.23.7.1, §7.23.1). Итого 257 различных исходов, а в `char` помещается только 256 значений: любой приёмник-`char` обязан «склеить» какое-то значение байта с `EOF`. Именно поэтому тип результата — `int`.

Прослеживаем оба варианта на файле из байтов 255 и `'A'` (65).

**Знаковый `char` (наша платформа).** Первый `fgetc` возвращает 255. Присваивание в знаковый `char` усекает значение: 255 не помещается, получается −1 (гл. 2). Сравнение `(-1) != EOF` ложно — цикл завершается **на первом же байте данных**, сделав **0 итераций**. Данные потеряны все, ошибки нет ни одной.

**Беззнаковый `char`.** Первый `fgetc` вернул 255 → в `char` помещается как есть → 255 ≠ −1, итерация выполняется; второй — 65, тоже итерация. Третий вызов возвращает `EOF` (−1) → присваивание в беззнаковый `char` даёт 255 → `255 != -1` истинно → цикл **не заканчивается никогда**: `fgetc` за концом файла продолжает возвращать `EOF`, а он продолжает превращаться в 255. Итераций — **бесконечно много**.

Чтобы это можно было наблюдать, в демонстрацию добавлена страховка — выход после десятой итерации:

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("bytes.dat", "w");
    if (f == NULL) { perror("bytes.dat"); return 1; }
    fputc(0xFF, f);                       /* байт 255 — законное значение данных */
    fputc('A', f);
    if (fclose(f) == EOF) { perror("bytes.dat"); return 1; }

    printf("(char)255 as int: %d\n", (char)255);   /* знаковость char этой сборки */

    f = fopen("bytes.dat", "r");
    if (f == NULL) { perror("bytes.dat"); return 1; }
    char bad;                             /* !!! char вместо int */
    int n_bad = 0;
    while ((bad = fgetc(f)) != EOF) {
        n_bad++;
        if (n_bad == 10) {                /* страховка: без неё цикл может не кончиться */
            printf("char loop: 10 iterations, stopped by hand\n");
            break;
        }
    }
    fclose(f);

    f = fopen("bytes.dat", "r");
    if (f == NULL) { perror("bytes.dat"); return 1; }
    int c, n_ok = 0;
    while ((c = fgetc(f)) != EOF) {
        printf("int loop: got %d\n", c);
        n_ok++;
    }
    fclose(f);

    printf("char loop read: %d bytes\n", n_bad);
    printf("int  loop read: %d bytes\n", n_ok);
    return 0;
}
```

Обратите внимание на асимметрию диагностики: на беззнаковой сборке GCC **предупредил** (`comparison is always true due to limited range of data type` — сравнение всегда истинно, потому что `EOF` вне диапазона типа), а на нашей, знаковой, где программа теряет **все** данные, не сказал ничего. Полагаться на предупреждения тут нельзя — только на правило.

**Ответ:** приёмник обязан быть `int`, потому что `fgetc` возвращает 257 различимых результатов — 256 значений байта (0…255, байт трактуется как `unsigned char`) плюс отрицательный `EOF`; в `char` они не помещаются, и одно из значений данных неизбежно сливается с признаком конца файла. На файле из байтов 255 и `'A'`: со **знаковым** `char` (наша платформа) первый же байт 255 усекается до −1, совпадает с `EOF`, и цикл делает **0 итераций** — программа молча теряет всё содержимое; с **беззнаковым** `char` цикл, наоборот, **не завершается никогда**: возвращаемый в конце `EOF` (−1) превращается в 255, что не равно `EOF` (в прогоне цикл остановила искусственная страховка на десятой итерации, напечатав `char loop read: 10 bytes`). Корректный цикл `int c; while ((c = fgetc(f)) != EOF)` в обеих сборках читает ровно 2 байта — 255 и 65. Правило CERT — **FIO34-C** («различайте символы, прочитанные из потока, и `EOF`»).

### Г10.Ч1.З8

**Условие.** *(прикладное)* Мини-`wc`: прочитайте файл посимвольно и напечатайте число символов, слов и строк в формате `chars=... words=... lines=...`. Слово — максимальная последовательность символов без пробела, табуляции и перевода строки (используйте флаг «внутри слова»). Для файла из двух строк — `to be or not` и `that is the question`, каждая завершена переводом строки, — ожидается `chars=34 words=8 lines=2` (переводы строк входят в число символов).

**Решение.** Классическая задача K&R решается одним посимвольным проходом: три счётчика и одно состояние. Считать «слова» напрямую нельзя — можно считать только **переходы** из состояния «вне слова» в состояние «внутри слова»: именно переход означает, что началось новое слово. Флаг `in_word` и хранит это состояние.

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("text.txt", "w");
    if (f == NULL) { perror("text.txt"); return 1; }
    fputs("to be or not\nthat is the question\n", f);
    if (fclose(f) == EOF) { perror("text.txt"); return 1; }

    f = fopen("text.txt", "r");
    if (f == NULL) { perror("text.txt"); return 1; }
    int c, chars = 0, words = 0, lines = 0;
    int in_word = 0;                                  /* флаг «мы внутри слова» */
    while ((c = fgetc(f)) != EOF) {
        chars++;
        if (c == '\n')
            lines++;
        if (c == ' ' || c == '\t' || c == '\n')
            in_word = 0;                              /* разделитель: слово кончилось */
        else if (!in_word) {
            in_word = 1;                              /* переход «вне слова» -> «в слове» */
            words++;                                  /* считаем именно переходы */
        }
    }
    fclose(f);
    printf("chars=%d words=%d lines=%d\n", chars, words, lines);
    return 0;
}
```

```

```

Сверка: `"to be or not\n"` — 13 символов, `"that is the question\n"` — 21, вместе 34 (переводы строк входят); слов 4 + 4 = 8; строк 2 — по числу `'\n'`.

Три замечания о деталях, из-за которых такие программы обычно врут:

- **Приёмник — `int`**, иначе байт 255 остановит счёт (Г10.Ч1.З7); для текстового файла это кажется неважным, но `wc` вполне могут натравить на что угодно.
- **Строки считаются по `'\n'`**, а не «по числу вызовов чего-нибудь»: файл, последняя строка которого не завершена переводом строки, честно даст на единицу меньше — то же самое делает системный `wc`.
- **Число символов зависит от режима**: в текстовом режиме на Windows пара `\r\n` из файла сворачивается в один символ, поэтому получается 34, а не 36. Если бы файл открывался в `"rb"` (§10.2.1), тот же файл дал бы `chars=36`. На Linux, где трансляции нет, оба режима дают 34; прогон на Linux-контуре подтвердил тот же вывод `chars=34 words=8 lines=2`.

**Ответ:** `chars=34 words=8 lines=2`. Один посимвольный цикл `while ((c = fgetc(f)) != EOF)` с приёмником `int` считает символы (все, включая `'\n'`), строки (по числу `'\n'`) и слова — причём слова считаются **не** по буквам, а по **переходам** «разделитель → не-разделитель», которые фиксирует флаг `in_word`: он сбрасывается на пробеле, табуляции и переводе строки и взводится (с инкрементом `words`) на первом символе очередного слова. Такой счёт устойчив к нескольким пробелам подряд, к пробелам в начале и конце строки и к файлу без завершающего перевода строки.

**Вариант 2 (без флага — по предыдущему символу).** То же состояние можно хранить не отдельным флагом, а «памятью о прошлом символе»: начало слова — это граница, где предыдущий символ был разделителем, а текущий — нет. Переменная `prev` инициализируется пробелом: перед началом файла мы как будто стоим на разделителе, поэтому первое же слово будет посчитано.

```c
#include <stdio.h>

static int is_sep(int c)                 /* разделитель слов */
{
    return c == ' ' || c == '\t' || c == '\n';
}

int main(void)
{
    FILE *f = fopen("text.txt", "w");
    if (f == NULL) { perror("text.txt"); return 1; }
    fputs("to be or not\nthat is the question\n", f);
    if (fclose(f) == EOF) { perror("text.txt"); return 1; }

    f = fopen("text.txt", "r");
    if (f == NULL) { perror("text.txt"); return 1; }
    int c, chars = 0, words = 0, lines = 0;
    int prev = ' ';                       /* «перед файлом» — как будто разделитель */
    while ((c = fgetc(f)) != EOF) {
        chars++;
        if (c == '\n')
            lines++;
        if (!is_sep(c) && is_sep(prev))   /* граница «разделитель -> буква» = начало слова */
            words++;
        prev = c;
    }
    fclose(f);
    printf("chars=%d words=%d lines=%d\n", chars, words, lines);
    return 0;
}
```

Вариант с флагом ближе к формулировке задания и чуть быстрее читается («вошли в слово — посчитали»); вариант с `prev` короче в теле цикла и легче расширяется, когда правила усложняются: если понадобится считать предложения (граница «точка → пробел») или различать `\r\n`, вся нужная информация уже под рукой, тогда как флаговому варианту потребуется завести дополнительное состояние. Общее у них — вынесенная проверка `is_sep`: набор разделителей задан в одном месте, и добавить, скажем, `'\r'` можно правкой одной строки.

### Г10.Ч1.З9

**Условие.** *(прикладное)* Фильтр комментариев: напечатайте только те строки файла, которые **не** начинаются с символа `#`. Создайте программно файл `config.txt` из четырёх строк: `# config file`, `width=80`, `# to be ignored`, `height=25` — программа должна напечатать ровно `width=80` и `height=25`. Читайте построчно `fgets`-ом; подумайте, почему проверка `line[0] == '#'` безопасна даже для пустой строки.

**Решение.** Построчное чтение — ровно тот случай, для которого `fgets` и создана: она читает строку целиком (в пределах буфера), сохраняет перевод строки, и решение «печатать или пропустить» принимается по первому символу.

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("config.txt", "w");
    if (f == NULL) { perror("config.txt"); return 1; }
    fputs("# config file\nwidth=80\n# to be ignored\nheight=25\n", f);
    if (fclose(f) == EOF) { perror("config.txt"); return 1; }

    f = fopen("config.txt", "r");
    if (f == NULL) { perror("config.txt"); return 1; }
    char line[256];
    while (fgets(line, sizeof line, f) != NULL) {
        if (line[0] == '#')          /* комментарий — пропускаем целиком */
            continue;
        printf("%s", line);          /* '\n' уже в строке */
    }
    fclose(f);
    return 0;
}
```

**Почему `line[0]` безопасен.** `fgets` при успехе **всегда** оставляет в буфере правильную строку: не более `n − 1` символов и обязательный `'\0'` в конце (C5 §7.23.7.2). Значит, обращение к `line[0]` законно в любом случае:

- строка из файла непустая — в `line[0]` её первый символ;
- строка в файле пустая, то есть состоит из одного перевода строки, — в `line[0]` лежит `'\n'` (это уже не «пустая строка» с точки зрения буфера), сравнение с `'#'` просто ложно;
- дочитать не удалось ничего — `fgets` вернула `NULL`, и в тело цикла мы не входим вовсе;
- даже вырожденный случай, когда `line[0] == '\0'` (в файле нулевой байт), безопасен: элемент существует, чтение законно, сравнение ложно.

Опасной такая проверка была бы для «последнего» символа (`line[strlen(line) - 1]`, Г10.Ч1.З6) — там индекс вычисляется и может уйти в минус. Индекс 0 существует всегда, потому что массив `line` объявлен с ненулевым размером, — вопрос лишь в том, что в нём лежит.

**Ответ:** программа печатает ровно две строки — `width=80` и `height=25`. Цикл `while (fgets(line, sizeof line, f) != NULL)` читает по строке, и строки, у которых `line[0] == '#'`, пропускаются через `continue`; свой `'\n'` в `printf` не нужен — он пришёл из файла вместе со строкой. Проверка `line[0]` безопасна потому, что `fgets` при успешном чтении гарантированно формирует завершённую строку в буфере, а сам элемент с индексом 0 в массиве существует всегда: для строки из одного перевода строки в нём окажется `'\n'`, при неудачном чтении тело цикла не выполняется вовсе. Опасны в этой задаче не начала строк, а концы — вычисляемый индекс `strlen(line) - 1` (Г10.Ч1.З6).

**Вариант 2 (посимвольный фильтр с состоянием строки).** Ту же фильтрацию можно сделать без буфера строки вообще — одним потоком символов. Тогда состояние приходится хранить явно: «сейчас начало строки» и «текущую строку пропускаем».

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("config.txt", "w");
    if (f == NULL) { perror("config.txt"); return 1; }
    fputs("# config file\nwidth=80\n# to be ignored\nheight=25\n", f);
    if (fclose(f) == EOF) { perror("config.txt"); return 1; }

    f = fopen("config.txt", "r");
    if (f == NULL) { perror("config.txt"); return 1; }
    int c;
    int at_line_start = 1;               /* состояние: следующий символ — первый в строке */
    int skipping = 0;                    /* состояние: текущая строка — комментарий */
    while ((c = fgetc(f)) != EOF) {
        if (at_line_start) {
            skipping = (c == '#');       /* решение принимается по первому символу строки */
            at_line_start = 0;
        }
        if (!skipping)
            fputc(c, stdout);            /* печать посимвольно — в stdout */
        if (c == '\n')
            at_line_start = 1;
    }
    fclose(f);
    return 0;
}
```

Посимвольный вариант от длины строк не зависит вовсе: памяти он занимает столько же на файл любого размера и корректно пропустит комментарий длиной хоть в мегабайт — ценой того, что состояние («начало строки», «пропускаем») приходится вести руками, а разбор содержимого строки (`strcmp`, поиск `=`) в таком виде уже не сделать. Практическое правило: если строку надо **разбирать**, читайте `fgets`-ом и увеличивайте буфер; если её надо только **пропустить или скопировать**, посимвольный поток надёжнее.

### Г10.Ч1.З10

**Условие.** *(прикладное)* «Итог в конец»: файл `best.txt` содержит строки вида `имя очки` (создайте с `alice 90`, `bob 75`, `carol 82`). Прочитайте его (`fscanf`, `"%31s %d"`), найдите участника с максимумом очков, затем **допишите** в конец файла строку `best: имя очки` (режим `"a"`) и напечатайте итоговое содержимое файла — 4 строки, последняя `best: alice 90`. Копию имени лидера храните через `strcpy` (гл. 5).

**Решение.** Программа состоит из трёх фаз, и каждая — отдельное открытие файла со своим режимом: `"r"` (прочитать и найти максимум), `"a"` (дописать итог), `"r"` (показать результат). Копия имени обязательна: `name` — один буфер, который перезаписывается на каждой итерации, поэтому «запомнить лидера», сохранив только его очки, недостаточно — нужен `strcpy` в отдельный буфер `best_name`.

Ширина `%31s` защищает буфер `name[32]` (гл. 5, §10.1.2), а условие `== 2` требует, чтобы заполнились обе позиции — имя и число.

```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    FILE *f = fopen("best.txt", "w");
    if (f == NULL) { perror("best.txt"); return 1; }
    fputs("alice 90\nbob 75\ncarol 82\n", f);
    if (fclose(f) == EOF) { perror("best.txt"); return 1; }

    /* 1) читаем и ищем максимум */
    f = fopen("best.txt", "r");
    if (f == NULL) { perror("best.txt"); return 1; }
    char name[32], best_name[32] = "";
    int score, best_score = 0, count = 0;
    while (fscanf(f, "%31s %d", name, &score) == 2) {
        if (count == 0 || score > best_score) {
            best_score = score;
            strcpy(best_name, name);          /* копия имени: name перезапишется */
        }
        count++;
    }
    fclose(f);
    if (count == 0) { puts("no records"); return 1; }

    /* 2) дописываем итог в конец */
    f = fopen("best.txt", "a");               /* "a": запись всегда в конец */
    if (f == NULL) { perror("best.txt"); return 1; }
    fprintf(f, "best: %s %d\n", best_name, best_score);
    if (fclose(f) == EOF) { perror("best.txt"); return 1; }

    /* 3) печатаем итоговый файл */
    f = fopen("best.txt", "r");
    if (f == NULL) { perror("best.txt"); return 1; }
    char line[64];
    while (fgets(line, sizeof line, f) != NULL)
        printf("%s", line);
    fclose(f);
    return 0;
}
```

```

```

Почему нельзя обойтись одним открытием: поток, открытый в `"r"`, писать не даёт (режим — это контракт, §10.1.1), а открывать сразу в `"a"` для чтения бессмысленно — режим `"a"` предназначен для записи. Универсальный выход — открыть каждую фазу в своём режиме; режимы обновления (`"r+"`, §10.2.2) здесь избыточны и требуют дисциплины позиционирования.

Заметьте также, что «дописать в конец» и «дописать после последней прочитанной строки» — не одно и то же: `"a"` гарантирует запись именно в текущий конец файла, даже если между открытием и записью файл вырос (§10.1.1). Для журналов и итогов это именно то поведение, которое нужно.

**Ответ:** файл после работы программы содержит четыре строки:
```
alice 90
bob 75
carol 82
best: alice 90
```
Чтение — циклом `while (fscanf(f, "%31s %d", name, &score) == 2)`: ширина `%31s` защищает буфер `name[32]`, условие `== 2` требует заполнения обеих позиций. Лидер хранится в отдельном буфере `best_name`, куда имя копируется `strcpy`-ем: `name` перезаписывается следующей итерацией, и указатель на него «запомнить» нельзя. Максимум инициализируется первым прочитанным элементом (`count == 0 || score > best_score`), пустой файл обрабатывается отдельно. Дозапись — вторым открытием в режиме `"a"` (он всегда пишет в текущий конец файла), печать итога — третьим открытием в `"r"`; писать в поток, открытый на чтение, нельзя, поэтому три фазы — три открытия.

**Источники части 10.1 в решениях:** C5 (§7.23.5.3 `fopen` и режимы, §7.23.6.2 `fscanf`, §7.23.7.1 `fgetc`, §7.23.7.2 `fgets`, §7.23.10.2 `feof`, §7.23.10.4 `perror`); C2 (гл. 22); C1 (гл. 7); C10 (FIO34-C, FIO42-C).

## Часть 10.2. Бинарные файлы и позиционирование

### Г10.Ч2.З1

**Условие.** Запишите массив `int a[8] = {1,2,3,4,5,6,7,8}` в файл `eight.bin` одним `fwrite` (режим `"wb"`). Посчитайте размер файла побайтовым чтением в `"rb"` (как `file_size` из §10.2.1) — объясните полученное число через `sizeof(int)` (на нашей платформе ожидается 32). Затем прочитайте файл одним `fread` в новый массив и напечатайте его, используя возвращённое `fread` число элементов.

**Решение.** Три шага задания — три контракта из §10.2.1: `fwrite` пишет `n` элементов по `size` байтов и возвращает число записанных; бинарный поток обязан вернуть байты в точности; `fread` возвращает число **полностью** прочитанных элементов, и печатать надо именно его, а не ожидаемое.

```c
#include <stdio.h>

static long file_size(const char *path)      /* размер = число байтов при чтении в "rb" */
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) return -1;
    long size = 0;
    while (fgetc(f) != EOF)
        size++;
    fclose(f);
    return size;
}

int main(void)
{
    int a[8] = {1, 2, 3, 4, 5, 6, 7, 8};

    FILE *f = fopen("eight.bin", "wb");
    if (f == NULL) { perror("eight.bin"); return 1; }
    size_t written = fwrite(a, sizeof a[0], 8, f);      /* 8 элементов по sizeof(int) */
    if (fclose(f) == EOF) { perror("eight.bin"); return 1; }
    printf("written: %zu elements\n", written);

    printf("sizeof(int) = %zu -> expected %zu bytes\n",
           sizeof a[0], 8 * sizeof a[0]);
    printf("file size:  %ld bytes\n", file_size("eight.bin"));

    int b[8] = {0};
    f = fopen("eight.bin", "rb");
    if (f == NULL) { perror("eight.bin"); return 1; }
    size_t got = fread(b, sizeof b[0], 8, f);
    fclose(f);
    printf("read: %zu elements:", got);
    for (size_t i = 0; i < got; i++)                    /* печатаем ровно got, не 8 */
        printf(" %d", b[i]);
    printf("\n");
    return 0;
}
```

./eight
```

```

sizeof(int) = 4 -> expected 32 bytes
file size:  32 bytes
read: 8 elements: 1 2 3 4 5 6 7 8
```

Арифметика простая: 8 элементов × `sizeof(int)` = 8 × 4 = **32 байта**. Четвёрка здесь — свойство платформы (LLP64, гл. 2), а не языка: на реализации с 8-байтовым `int` тот же код дал бы 64 байта, и старый файл на ней не прочитался бы (§10.2.3). Именно поэтому размер вычисляется как `8 * sizeof a[0]`, а не пишется числом.

Побайтовый счёт (`file_size`) — переносимый способ измерить файл. Тот же результат даёт `fseek(f, 0, SEEK_END)` + `ftell` (проверено: `size by SEEK_END+ftell: 32 bytes`), но стандарт не обязан поддерживать `SEEK_END` для бинарных потоков (C5 §7.23.9.2), и CERT рекомендует не измерять так размер (C10, FIO19-C, §10.2.2). Быстрее — да; переносимо — нет.

**Ответ:** программа печатает
```
written: 8 elements
sizeof(int) = 4 -> expected 32 bytes
file size:  32 bytes
read: 8 elements: 1 2 3 4 5 6 7 8
```
Размер 32 байта — это 8 элементов × `sizeof(int)` = 8 × 4 на нашей платформе (LLP64, гл. 2): `fwrite(a, sizeof a[0], 8, f)` копирует представление массива байт в байт, а бинарный режим `"wb"` не даёт библиотеке ничего дописать или перевести (§10.2.1). Обратное чтение выполняется одним `fread`, и цикл печати идёт **до `got`** — числа реально прочитанных элементов, а не до восьми: только это число говорит правду о том, сколько данных получено (короткий файл или ошибка ввода дадут меньше). Измерять размер побайтовым чтением переносимо, через `SEEK_END` + `ftell` — быстрее, но стандартом не гарантировано (C10, FIO19-C).

### Г10.Ч2.З2

**Условие.** Для файла `pos.bin` из пяти `int` `{10, 20, 30, 40, 50}` (создайте его `fwrite`-ом) напечатайте значения `ftell`: сразу после открытия в `"rb"`, после чтения одного `int`, после `fseek(f, 0, SEEK_END)`. Ожидается `0`, `4`, `20`. Затем `rewind` и прочитайте первый элемент — убедитесь, что это снова `10`. Объясните каждое из трёх чисел.

**Решение.** Для бинарного потока `ftell` — это число байтов от начала файла (C5 §7.23.9.4), поэтому все три числа выводятся из арифметики представления.

```c
#include <stdio.h>

int main(void)
{
    int a[5] = {10, 20, 30, 40, 50};

    FILE *f = fopen("pos.bin", "wb");
    if (f == NULL) { perror("pos.bin"); return 1; }
    if (fwrite(a, sizeof a[0], 5, f) != 5) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("pos.bin"); return 1; }

    f = fopen("pos.bin", "rb");
    if (f == NULL) { perror("pos.bin"); return 1; }
    printf("after fopen:          ftell = %ld\n", ftell(f));

    int x;
    if (fread(&x, sizeof x, 1, f) != 1) { fclose(f); return 1; }
    printf("after reading one int: ftell = %ld (read %d)\n", ftell(f), x);

    if (fseek(f, 0, SEEK_END) != 0) { fclose(f); return 1; }
    printf("after SEEK_END:        ftell = %ld\n", ftell(f));

    rewind(f);                                  /* назад в начало */
    if (fread(&x, sizeof x, 1, f) != 1) { fclose(f); return 1; }
    printf("after rewind:          read %d, ftell = %ld\n", x, ftell(f));
    fclose(f);
    return 0;
}
```

```

```
after fopen:          ftell = 0
after reading one int: ftell = 4 (read 10)
after SEEK_END:        ftell = 20
after rewind:          read 10, ftell = 4
```

Объяснение чисел:

- **0** — открытие в `"rb"` (как и `"r"`, `"wb"`) ставит позицию в начало файла (C5 §7.23.3): следующее чтение возьмёт самый первый байт. (Исключение — режимы `"a"`: там запись всегда идёт в конец.)
- **4** — `fread(&x, sizeof x, 1, f)` прочитала один `int`, то есть `sizeof(int) = 4` байта, и позиция сдвинулась ровно на это число: курсор всегда стоит **за** прочитанным. Прочитанное значение — 10, первый элемент массива.
- **20** — `fseek(f, 0, SEEK_END)` устанавливает позицию «конец файла плюс ноль»: 5 элементов × 4 байта = 20. На нашей платформе это совпадает с размером файла (§10.2.2), но полагаться на такой способ измерения переносимый код не должен (C10, FIO19-C).
- `rewind(f)` — то же, что `fseek(f, 0, SEEK_SET)`, плюс сброс индикатора ошибки (C5 §7.23.9.5): следующий `fread` снова возвращает 10, а позиция опять становится 4.

**Ответ:** печатается `ftell = 0` после открытия, `ftell = 4` после чтения одного `int` (прочитано значение 10), `ftell = 20` после `fseek(f, 0, SEEK_END)`; после `rewind` снова читается `10`, и позиция опять равна 4. Смысл чисел: 0 — открытие в `"rb"` ставит позицию в начало файла; 4 — каждое чтение продвигает позицию ровно на число прочитанных байтов, а `sizeof(int)` на нашей платформе равен 4, и курсор всегда стоит за прочитанным; 20 — конец файла, то есть 5 × 4 байта, что здесь совпадает с размером файла (для бинарного потока `ftell` — байтовое смещение от начала, C5 §7.23.9.4; но использовать `SEEK_END` для измерения размера переносимо нельзя — C10 FIO19-C). `rewind` эквивалентен `fseek(f, 0, SEEK_SET)` со сбросом индикатора ошибки, поэтому чтение начинается заново с первого элемента.

### Г10.Ч2.З3

**Условие.** Файл содержит четыре записи `typedef struct { int id; int score; } Record` (создайте с данными на свой вкус). Не читая файл целиком, достаньте **одним** `fread` только запись с индексом 2 (третью) и напечатайте её поля. Какое смещение вы передали `fseek` и почему? Что изменится, если в структуру добавить поле `char grade`?

**Решение.** Записи фиксированного размера превращают файл в «массив на диске»: элемент с индексом `i` лежит по смещению `i * sizeof(Record)` (§10.2.2). Смещение считает `sizeof`, а не человек: любая правка структуры автоматически меняет и его.

```c
#include <stdio.h>

typedef struct {
    int id;
    int score;
} Record;

int main(void)
{
    Record all[4] = { {101, 90}, {102, 75}, {103, 82}, {104, 60} };

    FILE *f = fopen("recs.bin", "wb");
    if (f == NULL) { perror("recs.bin"); return 1; }
    if (fwrite(all, sizeof all[0], 4, f) != 4) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("recs.bin"); return 1; }

    printf("sizeof(Record) = %zu -> offset of record 2 = %ld\n",
           sizeof(Record), 2 * (long)sizeof(Record));

    f = fopen("recs.bin", "rb");
    if (f == NULL) { perror("recs.bin"); return 1; }
    Record r;
    if (fseek(f, 2 * (long)sizeof r, SEEK_SET) != 0) { fclose(f); return 1; }
    if (fread(&r, sizeof r, 1, f) != 1) { fclose(f); return 1; }   /* ровно одна запись */
    fclose(f);
    printf("record 2: id=%d score=%d\n", r.id, r.score);
    return 0;
}
```

```

```

Смещение — **16 байтов**: `2 * sizeof(Record)` = 2 × 8. Первые две записи не читаются вовсе — в этом и смысл произвольного доступа: одна операция позиционирования и одно чтение вместо прохода по файлу. Приведение `(long)` обязательно, потому что `sizeof` даёт `size_t`, а `fseek` принимает `long` (§10.2.2).

**Что изменит поле `char grade`.** Проверяем той же программой с изменённой структурой:

```c
typedef struct {
    int id;
    int score;
    char grade;        /* новое поле: +1 байт данных, но sizeof вырастет на 4 */
} Record;
```

./onerec_grade
```

record 2: id=103 score=82 grade=B
```

Размер структуры вырос с 8 до **12** байтов, хотя данных добавился один байт: выравнивание требует, чтобы `sizeof` был кратен выравниванию самого строгого члена (`int`, 4 байта), поэтому за `grade` дописываются 3 байта-заполнителя (§8.2.3). Соответственно, смещение записи 2 стало 24, а файл из четырёх записей — 48 байтов вместо 32. Код при этом не изменился ни на символ — всё пересчитал `sizeof`.

Важное следствие: **старые файлы после такой правки не читаются**. Программа с новой структурой, открыв файл, записанный старой, прочтёт по смещению 24 то, что лежало в середине четвёртой записи, — и не получит ни одной ошибки `fread`. Раскладка структуры — часть формата файла (§10.2.3).

**Ответ:** `fseek` получает смещение `2 * (long)sizeof(Record)` = **16 байтов**, потому что записи имеют фиксированный размер и лежат подряд: запись с индексом `i` начинается на `i * sizeof(Record)` — файл ведёт себя как массив, а `fseek` играет роль индексации (§10.2.2). Прогон печатает `record 2: id=103 score=82`, прочитав ровно одну запись одним `fread` и не тронув остальные. С добавленным полем `char grade` `sizeof(Record)` становится 12 (1 байт данных + 3 байта-заполнителя до кратности выравниванию `int`, §8.2.3), смещение той же записи — 24, файл из четырёх записей — 48 байтов; сам код не меняется, поскольку смещение считает `sizeof`. Но файлы, записанные прежней версией структуры, новой программой уже не читаются: `fread` не сообщит об ошибке, а вернёт мусор — раскладка структуры входит в формат файла.

### Г10.Ч2.З4

**Условие.** *(понимание)* Структура `struct { char tag; int value; }` занимает 8 байтов при 5 байтах полей (§10.2.3, пример 1). Что лежит в трёх «лишних» байтах файла и можно ли на это полагаться? Сравните размеры файлов для `struct { char a; int b; char c; }` и `struct { int b; char a; char c; }` (ожидается 12 и 8 — почему? §8.2.3). Что это означает для «формата файла», записанного через `fwrite` структуры?

**Решение.** В «лишних» байтах лежат **байты-заполнители** (паддинг, §8.2.3) — то, что компилятор вставил между полями ради выравнивания. Их значения стандарт не определяет: это могут быть нули, а может быть всё, что осталось в памяти от предыдущего содержимого. `fwrite` копирует объект как массив `unsigned char` (C5 §7.23.8.2) и записывает их наравне с полями.

Чтобы увидеть это буквально, заполним весь объект узнаваемым значением `0xEE` (через объединение — приём §8.2.2), затем присвоим поля и запишем структуру в файл:

```c
#include <stdio.h>

typedef struct { char tag; int value; } Item;    /* 1 + 4 байта полей */
typedef struct { char a; int b; char c; } Wide;
typedef struct { int b; char a; char c; } Tight;

union item_raw {          /* доступ к байтам объекта — приём §8.2.2 */
    Item it;
    unsigned char b[sizeof(Item)];
};

static long dump_file(const char *path)     /* печатает байты файла, возвращает их число */
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }
    long size = 0;
    int c;
    while ((c = fgetc(f)) != EOF) {
        printf(" %02x", c);
        size++;
    }
    fclose(f);
    return size;
}

static int save(const char *path, const void *p, size_t size)
{
    FILE *f = fopen(path, "wb");
    if (f == NULL) { perror(path); return -1; }
    if (fwrite(p, size, 1, f) != 1) { fclose(f); return -1; }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

int main(void)
{
    printf("sizeof(Item)=%zu sizeof(Wide)=%zu sizeof(Tight)=%zu\n",
           sizeof(Item), sizeof(Wide), sizeof(Tight));

    union item_raw r;
    for (size_t i = 0; i < sizeof r.b; i++)   /* весь объект — узнаваемым мусором */
        r.b[i] = 0xEE;
    r.it.tag = 'A';
    r.it.value = 1000;
    if (save("item.bin", &r.it, sizeof r.it) != 0) return 1;
    printf("item.bin  bytes:");
    long n = dump_file("item.bin");
    printf("  (%ld bytes)\n", n);

    Wide w = { 'x', 1, 'y' };
    if (save("wide.bin", &w, sizeof w) != 0) return 1;
    printf("wide.bin  bytes:");
    n = dump_file("wide.bin");
    printf("  (%ld bytes)\n", n);

    Tight t = { 1, 'x', 'y' };
    if (save("tight.bin", &t, sizeof t) != 0) return 1;
    printf("tight.bin bytes:");
    n = dump_file("tight.bin");
    printf("  (%ld bytes)\n", n);
    return 0;
}
```

./padding
```

item.bin  bytes: 41 ee ee ee e8 03 00 00  (8 bytes)
wide.bin  bytes: 78 00 00 00 01 00 00 00 79 00 00 00  (12 bytes)
tight.bin bytes: 01 00 00 00 78 79 00 00  (8 bytes)
```

Первая строка дампа — прямой ответ на первый вопрос: `41` — это `'A'`, `e8 03 00 00` — 1000 (little-endian, §8.2.2), а между ними — **наши** `ee ee ee`. Компилятор не обнулял их и не трогал: что оказалось в памяти, то и уехало в файл. Полагаться на содержимое этих байтов нельзя ни при какой погоде: в другой сборке, при другом порядке присваиваний, при другом расположении объекта на стеке там будет другое. Отсюда практические следствия: побайтовое сравнение двух файлов, «одинаковых» по данным, может дать «различаются»; вычислять контрольную сумму по такой структуре бессмысленно; искать поля по «глазомерным» смещениям — тоже.

**Почему 12 и 8.** Правила выравнивания (§8.2.3): каждое поле должно начинаться со смещения, кратного его выравниванию (`int` — 4, `char` — 1), а размер всей структуры — быть кратным наибольшему выравниванию среди полей (здесь 4).

```
Wide { char a; int b; char c; }          Tight { int b; char a; char c; }

смещение 0: a  (1 байт)                  смещение 0: b  (4 байта)
смещение 1: паддинг 3 байта              смещение 4: a  (1 байт)
смещение 4: b  (4 байта)                 смещение 5: c  (1 байт)
смещение 8: c  (1 байт)                  смещение 6: паддинг 2 байта
смещение 9: паддинг 3 байта              -----------------------------
-----------------------------            итого 8 байтов
итого 12 байтов
```

Дампы это подтверждают: в `wide.bin` видно `78` (`'x'`), три байта заполнителя, `01 00 00 00` (`b = 1`), `79` (`'y'`) и снова три байта; в `tight.bin` — `01 00 00 00` (`b`), затем `78 79` (`'x'`, `'y'`) вплотную и два байта заполнителя. Поля те же, порядок объявления разный — размер отличается в полтора раза.

**Что это значит для «формата файла».** Что формата, в сущности, нет: `fwrite` структуры фиксирует не смысл данных, а **раскладку объекта в конкретной сборке**. Порядок объявления полей, размеры типов (гл. 2), правила выравнивания компилятора и порядок байтов (§8.2.2) — всё это входит в файл наравне с данными, но нигде не записано. Такой файл читается только «своей» сборкой; переставили поля местами (что для программы — безобидный рефакторинг) — и старые файлы молча превращаются в мусор.

**Ответ:** в трёх «лишних» байтах лежат байты-заполнители, вставленные компилятором ради выравнивания поля `value`; их значения стандартом не определены, и `fwrite` записывает их в файл вместе с полями (C5 §7.23.8.2 — объект копируется как массив `unsigned char`). В прогоне заполнители, предварительно забитые значением `0xEE`, так и уехали на диск: `41 ee ee ee e8 03 00 00`. Полагаться на них нельзя — ни сравнивать такие файлы побайтово, ни считать по ним контрольные суммы. Размеры 12 и 8 объясняются выравниванием (§8.2.3): в `struct { char a; int b; char c; }` после `a` вставляются 3 байта, чтобы `b` начинался с кратного 4 смещения, и ещё 3 в конце — чтобы общий размер был кратен 4; в `struct { int b; char a; char c; }` оба `char` укладываются вплотную после `int`, и до кратности 4 не хватает лишь 2 байтов. Для «формата файла» это означает, что `fwrite` структуры формата не задаёт: он консервирует раскладку конкретной сборки — порядок полей, размеры типов, паддинг и порядок байтов, — поэтому такой файл читается только той же программой, собранной тем же компилятором на той же платформе, а любая перестановка полей ломает совместимость со старыми файлами без единого сообщения об ошибке.

### Г10.Ч2.З5

**Условие.** *(понимание)* Почему `fwrite(&p, sizeof p, 1, f)` для `struct { char *name; int score; }` не сохраняет имя (что именно попадает в файл вместо него — и почему пример 3 §10.2.3 не нашёл в файле букв `alice`)? Что произойдёт при чтении такого файла другим запуском программы и разыменовании `name`? Предложите формат сохранения этой структуры «по-честному» (подсказка: длина + байты) и распишите последовательность `fwrite`/`fread`.

**Решение.** `fwrite` копирует **байты объекта** — ровно `sizeof p` штук, ни байтом больше. В объекте `Player` лежат: 8 байтов указателя `name` (LLP64), 4 байта `score` и 4 байта заполнителя — всего 16. Указатель — это **адрес**, число; сама строка `"alice"` живёт по этому адресу, **вне** структуры, и в кадр «фотографии» не попадает (§10.2.3). Поэтому поиск байтов `alice` в файле из примера 3 главы и дал `no`: в файле лежит адрес строки, а не строка.

Что произойдёт при чтении другим запуском: `fread` честно вернёт 16 байтов, поле `score` окажется осмысленным, а в `name` попадёт **адрес из прошлого запуска программы**. Он не значит ничего: в новом процессе по этому адресу либо ничего не отображено (обращение уронит программу), либо лежат посторонние данные (напечатается мусор). Разыменование такого указателя — неопределённое поведение, ровно как использование указателя после `free` (§7.2.1). Компилятор об этом не предупреждает — программа собирается без единого замечания:

```c
#include <stdio.h>

typedef struct {
    char *name;
    int score;
} Player;

int main(void)
{
    Player back;
    FILE *f = fopen("player.bin", "rb");        /* файл записан ДРУГИМ запуском */
    if (f == NULL) { perror("player.bin"); return 1; }
    if (fread(&back, sizeof back, 1, f) != 1) { fclose(f); return 1; }
    fclose(f);

    printf("score = %d\n", back.score);         /* это ещё осмысленно */
    printf("name  = %s\n", back.name);          /* !!! разыменование чужого адреса — UB */
    return 0;
}
```

gcc -std=c17 -Wall -Wextra playerbad.c -o playerbad
```

Сборка проходит молча; запускать эту программу мы не будем — у неопределённого поведения нет «показательного» результата, наблюдать в нём нечего.

**Честный формат.** Указатель сохранять бессмысленно — сохранять надо то, на что он указывает. Значит, строка пишется как **длина + байты**:

```
| int len | len байтов имени (без '\0') | int score |
```

Последовательность записи: `fwrite(&len, sizeof len, 1, f)` → `fwrite(p->name, 1, len, f)` → `fwrite(&p->score, sizeof p->score, 1, f)`.
Последовательность чтения — зеркальная: `fread(&len, ...)` → проверить `len` на разумность → `malloc(len + 1)` → `fread(name, 1, len, f)` → дописать `'\0'` → `fread(&score, ...)`.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    char *name;
    int score;
} Player;

/* формат: int len | len байтов имени (без '\0') | int score */
int player_save(const Player *p, const char *path)
{
    FILE *f = fopen(path, "wb");
    if (f == NULL) { perror(path); return -1; }
    int len = (int)strlen(p->name);
    if (fwrite(&len, sizeof len, 1, f) != 1) { fclose(f); return -1; }
    if (len > 0 && fwrite(p->name, 1, (size_t)len, f) != (size_t)len) { fclose(f); return -1; }
    if (fwrite(&p->score, sizeof p->score, 1, f) != 1) { fclose(f); return -1; }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

int player_load(Player *p, const char *path)
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }
    int len;
    if (fread(&len, sizeof len, 1, f) != 1) { fclose(f); return -1; }
    if (len < 0) { fclose(f); return -1; }                 /* доверять файлу нельзя */
    char *name = malloc((size_t)len + 1);                  /* +1 под '\0' */
    if (name == NULL) { fclose(f); return -1; }
    if (len > 0 && fread(name, 1, (size_t)len, f) != (size_t)len) {
        free(name);                                        /* ошибочный путь освобождает */
        fclose(f);
        return -1;
    }
    name[len] = '\0';
    int score;
    if (fread(&score, sizeof score, 1, f) != 1) { free(name); fclose(f); return -1; }
    fclose(f);
    p->name = name;                                        /* владение переходит вызывающему */
    p->score = score;
    return 0;
}

int main(void)
{
    Player p = { "alice", 90 };
    if (player_save(&p, "player2.bin") != 0) return 1;

    FILE *f = fopen("player2.bin", "rb");
    if (f == NULL) { perror("player2.bin"); return 1; }
    int c;
    printf("player2.bin bytes:");
    while ((c = fgetc(f)) != EOF)
        printf(" %02x", c);
    printf("\n");
    fclose(f);

    Player back;
    if (player_load(&back, "player2.bin") != 0) return 1;
    printf("loaded: name=%s score=%d\n", back.name, back.score);
    free(back.name);                                       /* строка в куче — освобождаем */
    back.name = NULL;
    return 0;
}

Тринадцать байтов вместо шестнадцати — и теперь в них есть смысл: `05 00 00 00` — длина 5, `61 6c 69 63 65` — буквы `alice`, `5a 00 00 00` — 90. Имя действительно в файле, паддинга нет, адресов нет. Прогон под ASan чист: единственный `malloc` в `player_load` парен `free` в `main`, а все ошибочные пути функции освобождают блок перед возвратом.

Три обязательные предосторожности этого формата: длина проверяется на разумность до `malloc` (файл может быть повреждён или враждебен), `'\0'` дописывается читателем (в файле его нет — он не часть данных), а владение выделенной строкой явно переходит вызывающему (§7.1.3): кто получил `Player` из `player_load`, тот и делает `free`.

**Ответ:** в файл попадают ровно `sizeof p` байтов самого объекта — 8 байтов **адреса** `name`, 4 байта `score` и 4 байта заполнителя; строка живёт по адресу, вне структуры, и в файл не копируется — потому поиск букв `alice` в примере 3 §10.2.3 и вернул `no`. При чтении таким файлом другим запуском `score` восстановится, а `name` будет содержать чужой, давно неактуальный адрес: разыменование — неопределённое поведение (падение или мусор), как у указателя после `free` (§7.2.1), причём компилятор с `-Wall -Wextra` не скажет ни слова. Честный формат — «длина + байты»: `int len`, затем `len` байтов имени без завершающего нуля, затем `int score`. Запись: `fwrite(&len, sizeof len, 1, f)`, `fwrite(p->name, 1, len, f)`, `fwrite(&p->score, sizeof p->score, 1, f)`. Чтение зеркально: `fread(&len, ...)` → проверка `len >= 0` → `malloc(len + 1)` → `fread(name, 1, len, f)` → `name[len] = '\0'` → `fread(&score, ...)`, с освобождением блока на каждом ошибочном пути. Прогон даёт файл из 13 байтов `05 00 00 00 61 6c 69 63 65 5a 00 00 00`, где имя видно буквально, и корректную загрузку `name=alice score=90`.

### Г10.Ч2.З6

**Условие.** *(понимание)* На Windows файл, записанный `fputs("one\ntwo\n", f)` в режиме `"w"`, занимает 10 байтов, а в `"wb"` — 8 (§10.2.1, пример 2). Откуда берутся лишние байты и какие именно? Почему при чтении этого файла в текстовом режиме программа всё равно видит 8 символов? Что случится с массивом `int`, среди байтов которого есть `0x0A`, если записать его без `"b"`, — и почему на Linux этот дефект не проявится?

**Решение.** Лишние байты — **`0x0D` (возврат каретки)**, которые библиотека вставляет перед каждым `0x0A` при записи в текстовом режиме: на Windows конец строки представляется парой `\r\n` (C15, §10.2.1). Строк две — значит, добавляются два байта, 8 → 10.

Читая тот же файл в текстовом режиме, программа видит 8 символов, потому что трансляция **симметрична**: при чтении пара `0x0D 0x0A` сворачивается обратно в один `'\n'`. Текстовый поток — «переводчик» в обе стороны, и для текста это незаметно (глава 10.1 потому и работала без сюрпризов). Правда открывается, только если посмотреть на файл в `"rb"`.

#include <stdio.h>

static long file_size(const char *path)
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }
    long size = 0;
    while (fgetc(f) != EOF)
        size++;
    fclose(f);
    return size;
}

static void dump(const char *path)

    while ((c = fgetc(f)) != EOF)
        printf(" %02x", c);
    printf("\n");
    fclose(f);
}

    dump("t.txt");
    printf("b.bin (\"wb\"): %ld bytes:", file_size("b.bin"));

    int back[3] = {0};

На Linux конец строки — один байт `\n`, транслировать нечего, и текстовый режим байт в байт совпадает с бинарным: программа «работает», хотя написана неправильно. Это и есть худший сорт ошибки — она невидима там, где её пишут, и всплывает у пользователя другой платформы.

**Ответ:** лишние байты — по одному `0x0D` перед каждым `0x0A`: на Windows текстовый режим представляет конец строки парой `\r\n` (C15, §10.2.1), поэтому два перевода строки дают +2 байта, 8 → 10 (дамп: `6f 6e 65 0d 0a 74 77 6f 0d 0a`). При чтении в текстовом режиме программа видит 8 символов, потому что трансляция симметрична — пара `0d 0a` сворачивается обратно в один `'\n'`; увидеть настоящие байты можно, только открыв файл в `"rb"`. Массив `int`, среди байтов которого есть `0x0A` (например, `{10, 20, 30}`: десятка представлена байтом `0a`), записанный без `"b"`, портится: библиотека вставляет `0x0D` перед байтом данных, файл вырастает с 12 до 13 байтов, а обратное чтение даёт `2573 5120 7680` вместо `10 20 30` — без единой ошибки от `fwrite`/`fread`. На Linux дефект не проявляется, потому что там конец строки — один байт `\n` и текстовый режим ничего не транслирует: тот же исходник даёт 12 байтов и `10 20 30`. Отсюда правило §10.2.1: `fwrite`/`fread` — только с `"b"`-режимами, а проверка на одной платформе такую ошибку не ловит.

### Г10.Ч2.З7

**Условие.** *(понимание)* Вы просите `fread(buf, sizeof(Record), 5, f)`, а она возвращает 3. Перечислите возможные причины и порядок их диагностики (`feof`/`ferror`). Можно ли пользоваться четвёртым элементом `buf`? А третьим? Обоснуйте по контракту `fread` (C5 §7.23.8.1).

**Решение.** Контракт `fread` (C5 §7.23.8.1): функция возвращает число **полностью** прочитанных элементов; оно меньше запрошенного при конце файла или ошибке чтения, а если элемент прочитан частично, его значение **не определено**.

**Причины, по которым вернулось 3:**
1. **файл кончился** — в нём было ровно 3 записи (или 3 записи и «хвост» короче записи);
2. **ошибка ввода** — сбой носителя, оборванный поток;
3. частный случай первой причины — **последняя запись прочиталась частично**: байты в файле были, но на целый элемент их не хватило.

**Порядок диагностики** — после `fread`, а не до:
```c
if (got < 5) {
    if (ferror(f))      /* сначала ошибка: она важнее */
        /* сбой ввода: сообщить, файл считать негодным */;
    else if (feof(f))
        /* конец файла: коротких данных ожидали? */;
}
```
`ferror` спрашивают первым: конец файла — штатная ситуация, ошибка — нет; при сбое индикатор конца может и не стоять, а вот полагаться на «раз не ошибка, значит конец» гораздо надёжнее, чем наоборот.

Проверим оба случая — файл ровно из 3 записей и файл «3 записи + половина четвёртой». Буфер заранее забит `0xEE`, чтобы было видно, какие байты изменил `fread`:

```c
#include <stdio.h>

typedef struct {
    int id;
    int score;
} Record;

union buf5 {                       /* тот же буфер, вид по записям и вид по байтам */
    Record r[5];
    unsigned char b[5 * sizeof(Record)];
};

static void try_read(const char *path)
{
    union buf5 buf;
    for (size_t i = 0; i < sizeof buf.b; i++)     /* заполняем узнаваемым мусором */
        buf.b[i] = 0xEE;

    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return; }
    size_t got = fread(buf.r, sizeof buf.r[0], 5, f);
    printf("%s: fread asked 5, got %zu; feof=%d ferror=%d\n",
           path, got, feof(f) != 0, ferror(f) != 0);
    fclose(f);

    for (size_t i = 0; i < got; i++)
        printf("  [%zu] id=%d score=%d\n", i, buf.r[i].id, buf.r[i].score);

    printf("  bytes of element 3:");                /* элемент, который НЕ прочитан целиком */
    for (size_t i = 3 * sizeof(Record); i < 4 * sizeof(Record); i++)
        printf(" %02x", buf.b[i]);
    printf("\n");
}

int main(void)
{
    Record all[3] = { {1, 10}, {2, 20}, {3, 30} };

    FILE *f = fopen("short.bin", "wb");             /* ровно 3 записи */
    if (f == NULL) { perror("short.bin"); return 1; }
    if (fwrite(all, sizeof all[0], 3, f) != 3) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("short.bin"); return 1; }

    f = fopen("partial.bin", "wb");                 /* 3 записи + половина четвёртой */
    if (f == NULL) { perror("partial.bin"); return 1; }
    if (fwrite(all, sizeof all[0], 3, f) != 3) { fclose(f); return 1; }
    int half = 4;
    if (fwrite(&half, sizeof half, 1, f) != 1) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("partial.bin"); return 1; }

    printf("sizeof(Record) = %zu\n", sizeof(Record));
    try_read("short.bin");
    try_read("partial.bin");
    return 0;
}
```

Оба файла дали `got = 3`, `feof = 1`, `ferror = 0` — по возвращаемому значению они неразличимы, и это нормально: `fread` сообщает, сколько **целых** элементов получено, а не сколько байтов осталось. Байты четвёртого элемента в обоих прогонах остались нашими `ee` — на этой реализации библиотека не переносит неполный «хвост» в буфер; но полагаться на такое поведение нельзя: стандарт объявляет значение частично прочитанного элемента неопределённым, то есть в другой реализации там окажутся байты из файла.

**Ответ:** причин ровно три: файл кончился раньше (в нём меньше пяти записей), произошла ошибка ввода, либо последний элемент прочитан частично — байты были, но на целую запись их не хватило. Диагностика — **после** цикла и в порядке «сначала `ferror`, потом `feof`»: ошибка ввода важнее и требует считать данные негодными, конец файла — штатная ситуация. Четвёртым элементом (`buf[3]`) пользоваться **нельзя**: `fread` вернула 3, значит про элементы с индексами 3 и 4 она не обещает ничего — их либо не трогали вовсе, либо (при частичном чтении) заполнили частично, и стандарт объявляет значение такого элемента неопределённым (C5 §7.23.8.1). Третьим (`buf[2]`) пользоваться **можно**: он входит в число полностью прочитанных, и его содержимое гарантировано контрактом. Прогон это подтверждает: и на файле из 3 записей, и на файле «3 записи + 4 лишних байта» получено `got = 3`, `feof = 1`, `ferror = 0`, элементы 0…2 корректны, а байты элемента 3 остались тем мусором (`ee`), которым буфер был заполнен до чтения.

### Г10.Ч2.З8

**Условие.** *(прикладное)* «База рекордов»: запишите в `game.bin` четыре записи `Record` `{1,10}, {2,20}, {3,30}, {4,40}`. Реализуйте `int update_score(const char *path, int index, int delta)`: открыть `"r+b"`, `fseek` к записи `index`, прочитать, увеличить `score` на `delta`, вернуть позицию `fseek`-ом и записать обратно; аккуратные коды ошибок. Вызовите `update_score("game.bin", 1, 5)` и напечатайте все записи: ожидается `id=2 score=25`, остальные без изменений. Не забудьте правило «между чтением и записью — позиционирование».

**Решение.** Обновление на месте — конвейер из пяти шагов: `fseek` к записи → `fread` → правка в памяти → `fseek` назад → `fwrite`. Второй `fseek` выполняет сразу две работы: возвращает позицию к началу записи (её сдвинул `fread`) и удовлетворяет требованию стандарта — на потоке, открытом в режиме обновления, между чтением и записью обязан стоять вызов позиционирования (C5 §7.23.5.3).

Отказ возможен на каждом шаге, и функция обязана на каждом закрыть поток и вернуть −1. Отдельно проверяется результат `fread`: если записи с таким индексом в файле нет, `fseek` за конец файла всё равно **успешен** — обнаружит проблему только чтение (§10.2.2).

```c
#include <stdio.h>

typedef struct {
    int id;
    int score;
} Record;

int update_score(const char *path, int index, int delta)
{
    if (index < 0) return -1;
    FILE *f = fopen(path, "r+b");                  /* чтение И запись, без обнуления */
    if (f == NULL) { perror(path); return -1; }

    long off = (long)index * (long)sizeof(Record);
    if (fseek(f, off, SEEK_SET) != 0) { fclose(f); return -1; }

    Record r;
    if (fread(&r, sizeof r, 1, f) != 1) { fclose(f); return -1; }   /* записи нет — отказ */
    r.score += delta;

    if (fseek(f, off, SEEK_SET) != 0) { fclose(f); return -1; }     /* и назад, и «смена передачи» */
    if (fwrite(&r, sizeof r, 1, f) != 1) { fclose(f); return -1; }

    if (fclose(f) == EOF) { perror(path); return -1; }              /* последняя проверка записи */
    return 0;
}

static int dump_all(const char *path)
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }
    Record r;
    while (fread(&r, sizeof r, 1, f) == 1)
        printf("id=%d score=%d\n", r.id, r.score);
    fclose(f);
    return 0;
}

int main(void)
{
    Record all[4] = { {1, 10}, {2, 20}, {3, 30}, {4, 40} };

    FILE *f = fopen("game.bin", "wb");
    if (f == NULL) { perror("game.bin"); return 1; }
    if (fwrite(all, sizeof all[0], 4, f) != 4) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("game.bin"); return 1; }

    if (update_score("game.bin", 1, 5) != 0) { puts("update failed"); return 1; }
    if (update_score("game.bin", 9, 5) == 0) { puts("index 9 must fail"); return 1; }
    puts("index 9: refused, as expected");

    return dump_all("game.bin") == 0 ? 0 : 1;
}

Ошибка на любом шаге (открытие, позиционирование, чтение, запись, закрытие) даёт −1 с закрытием потока; несуществующий индекс отсекается именно проверкой результата `fread`, потому что `fseek` за конец файла успешен сам по себе. На диск уходит ровно одна запись (8 байтов), остальные не переписываются.

**Вариант 2 (прочитать всё, поправить, переписать целиком).** Если файл заведомо небольшой, можно не заниматься позиционированием: прочитать все записи в массив, изменить нужную и записать файл заново в режиме `"wb"`.

```c
#include <stdio.h>

#define MAX_RECS 64

typedef struct {
    int id;
    int score;
} Record;

/* вариант 2: прочитать весь файл в память, поправить, переписать целиком */
int update_score(const char *path, int index, int delta)
{
    if (index < 0) return -1;

    Record all[MAX_RECS];
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }
    size_t n = fread(all, sizeof all[0], MAX_RECS, f);
    int bad = ferror(f) != 0;
    fclose(f);
    if (bad || (size_t)index >= n) return -1;

    all[index].score += delta;

    f = fopen(path, "wb");                     /* "wb" обнуляет файл — пишем всё заново */
    if (f == NULL) { perror(path); return -1; }
    if (fwrite(all, sizeof all[0], n, f) != n) { fclose(f); return -1; }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

### Г10.Ч2.З9

**Условие.** *(прикладное)* Сохранение вектора (§9.1.1): реализуйте `int vec_save(const Vec *v, const char *path)` (формат: `int len`, затем `len` элементов `int`) и `int vec_load(Vec *v, const char *path)` (прочитать `len`, выделить память, прочитать данные; `cap = len`). Сохраните вектор из `{10,20,30,40,50}`, загрузите в новый и напечатайте `len`, `cap` и элементы. Все ошибочные пути освобождают выделенное; AddressSanitizer обязан быть чист. Почему формат «длина + данные» лучше, чем `fwrite(&v, sizeof v, 1, f)`?

**Решение.** Формат задан условием и повторяет приём из Г10.Ч2.З5: сначала количество, затем сами данные.

```
| int len | len элементов int |
```

`vec_save` пишет два раза: длину и (если она положительна) блок данных одним `fwrite`. `vec_load` симметричен, и вся его сложность — в аккуратности: длина проверяется до выделения памяти, `malloc` проверяется, а **любой** ошибочный путь после успешного `malloc` обязан освободить блок, иначе утечка. Пустой вектор (`len == 0`) — отдельная ветка без выделения: `malloc(0)` — случай, которого лучше не иметь вовсе.

```c
/* Vec, vec_init, vec_push, vec_free — как в §9.1.1 */

/* формат файла: int len | len элементов int */
int vec_save(const Vec *v, const char *path)
{
    FILE *f = fopen(path, "wb");
    if (f == NULL) { perror(path); return -1; }
    if (fwrite(&v->len, sizeof v->len, 1, f) != 1) { fclose(f); return -1; }
    if (v->len > 0 &&
        fwrite(v->data, sizeof v->data[0], (size_t)v->len, f) != (size_t)v->len) {
        fclose(f);
        return -1;
    }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

int vec_load(Vec *v, const char *path)
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return -1; }

    int len;
    if (fread(&len, sizeof len, 1, f) != 1) { fclose(f); return -1; }
    if (len < 0) { fclose(f); return -1; }            /* содержимому файла не доверяем */

    if (len == 0) {                                   /* пустой вектор: без выделения */
        fclose(f);
        v->data = NULL;
        v->len = v->cap = 0;
        return 0;
    }

    int *data = malloc((size_t)len * sizeof *data);
    if (data == NULL) { fclose(f); return -1; }
    if (fread(data, sizeof *data, (size_t)len, f) != (size_t)len) {
        free(data);                                   /* ошибочный путь освобождает блок */
        fclose(f);
        return -1;
    }
    fclose(f);

    v->data = data;
    v->len = len;
    v->cap = len;                                     /* ровно столько, сколько данных */
    return 0;
}

int main(void)
{
    Vec v;
    if (vec_init(&v) != 0) return 1;
    int src[5] = {10, 20, 30, 40, 50};
    for (int i = 0; i < 5; i++)
        if (vec_push(&v, src[i]) != 0) { vec_free(&v); return 1; }
    printf("saving:  len=%d cap=%d\n", v.len, v.cap);
    if (vec_save(&v, "vec.bin") != 0) { vec_free(&v); return 1; }
    vec_free(&v);

    printf("vec.bin: %ld bytes\n", file_size("vec.bin"));

    Vec w;
    if (vec_load(&w, "vec.bin") != 0) return 1;
    printf("loaded:  len=%d cap=%d:", w.len, w.cap);
    for (int i = 0; i < w.len; i++)
        printf(" %d", w.data[i]);
    printf("\n");
    vec_free(&w);
    return 0;
}
```

Каждый ошибочный путь после `malloc` освобождает блок и закрывает поток; отчёт AddressSanitizer чист — ни ошибок доступа, ни утечек. Формат «длина + данные» лучше `fwrite(&v, sizeof v, 1, f)` потому, что `Vec` — описатель: в нём лежит **указатель** на блок кучи, и запись структуры сохранила бы 16 байтов, где 8 — бесполезный адрес (в прогоне он различался от запуска к запуску), а сами элементы не попали бы в файл вовсе; кроме того, «длина + данные» не тащит в файл ни паддинг, ни ёмкость, то есть описывает именно содержимое вектора.

**Вариант 2 (текстовый формат).** Тот же вектор можно хранить текстом: первая строка — длина, дальше по числу в строке. Читается человеком и любым инструментом, переживает смену платформы.

```c
/* Vec, vec_init, vec_push, vec_free — как в §9.1.1 */

/* вариант 2: текстовый формат — первая строка len, дальше по числу в строке */
int vec_save(const Vec *v, const char *path)
{
    FILE *f = fopen(path, "w");
    if (f == NULL) { perror(path); return -1; }
    if (fprintf(f, "%d\n", v->len) < 0) { fclose(f); return -1; }
    for (int i = 0; i < v->len; i++)
        if (fprintf(f, "%d\n", v->data[i]) < 0) { fclose(f); return -1; }
    if (fclose(f) == EOF) { perror(path); return -1; }
    return 0;
}

int vec_load(Vec *v, const char *path)
{
    FILE *f = fopen(path, "r");
    if (f == NULL) { perror(path); return -1; }

    int len;
    if (fscanf(f, "%d", &len) != 1 || len < 0) { fclose(f); return -1; }

    if (len == 0) {
        fclose(f);
        v->data = NULL;
        v->len = v->cap = 0;
        return 0;
    }

    int *data = malloc((size_t)len * sizeof *data);
    if (data == NULL) { fclose(f); return -1; }
    for (int i = 0; i < len; i++)
        if (fscanf(f, "%d", &data[i]) != 1) {      /* оборвался файл — откат */
            free(data);
            fclose(f);
            return -1;
        }
    fclose(f);

    v->data = data;
    v->len = len;
    v->cap = len;
    return 0;
}

### Г10.Ч2.З10

**Условие.** *(прикладное)* Инструмент `hexdump`: функция `void hexdump(const char *path)` печатает все байты файла в шестнадцатеричном виде (`%02x`), по 8 в строке, читая файл в `"rb"`. Прогоните её на двух файлах: `num.bin` с `unsigned x = 0x01020304` (ожидается `04 03 02 01` — объясните порядок, §8.2.2) и `hi.txt`, записанном `fputs("Hi\n", f)` в текстовом режиме (на Windows ожидается `48 69 0d 0a` — объясните, откуда `0d`). Почему сам `hexdump` обязан открывать файл именно в `"rb"`?

**Решение.** Функция — посимвольный цикл §10.1.2 с форматированием: приёмник `int` (иначе байт 255 оборвал бы дамп — Г10.Ч1.З7), счётчик байтов для переноса строки каждые 8 и «хвост» неполной строки в конце.

```c
#include <stdio.h>

void hexdump(const char *path)
{
    FILE *f = fopen(path, "rb");            /* только "rb": нужны байты как есть */
    if (f == NULL) { perror(path); return; }
    int c;
    int n = 0;
    while ((c = fgetc(f)) != EOF) {         /* приёмник — int (§10.1.2) */
        if (n % 8 != 0)
            printf(" ");
        printf("%02x", c);
        n++;
        if (n % 8 == 0)
            printf("\n");
    }
    if (n % 8 != 0)                         /* хвост неполной строки */
        printf("\n");
    fclose(f);
}

int main(void)
{
    unsigned x = 0x01020304;
    FILE *f = fopen("num.bin", "wb");
    if (f == NULL) { perror("num.bin"); return 1; }
    if (fwrite(&x, sizeof x, 1, f) != 1) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("num.bin"); return 1; }

    f = fopen("hi.txt", "w");               /* текстовый режим — специально */
    if (f == NULL) { perror("hi.txt"); return 1; }
    fputs("Hi\n", f);
    if (fclose(f) == EOF) { perror("hi.txt"); return 1; }

    int a[8] = {1, 2, 3, 4, 5, 6, 7, 8};    /* 32 байта — четыре полные строки дампа */
    f = fopen("eight.bin", "wb");
    if (f == NULL) { perror("eight.bin"); return 1; }
    if (fwrite(a, sizeof a[0], 8, f) != 8) { fclose(f); return 1; }
    if (fclose(f) == EOF) { perror("eight.bin"); return 1; }

    puts("num.bin:");
    hexdump("num.bin");
    puts("hi.txt:");
    hexdump("hi.txt");
    puts("eight.bin:");
    hexdump("eight.bin");
    return 0;
}

**Порядок `04 03 02 01`.** Наша платформа — little-endian (§8.2.2): в памяти многобайтовое число лежит младшим байтом вперёд. У `0x01020304` младший байт — `0x04`, старший — `0x01`, и `fwrite` копирует байты в том порядке, в каком они лежат в памяти, ничего не переставляя. Поэтому файл начинается с `04`. Машина с обратным порядком байтов записала бы `01 02 03 04`, а прочитав наш файл, получила бы число `0x04030201` — без единой ошибки ввода-вывода (§10.2.3).

**Откуда `0d` в `hi.txt`.** Файл записан в **текстовом** режиме (`"w"`), а на Windows перевод строки в текстовом потоке представляется парой `\r\n`: библиотека превратила один символ `'\n'` (`0x0a`) в два байта `0d 0a` (§10.2.1, C15). Строка `"Hi\n"` из трёх символов заняла в файле четыре байта: `48` (`'H'`), `69` (`'i'`), `0d`, `0a`. На Linux-контуре тот же код дал ожидаемо `48 69 0a` — трансляции там нет; остальные два дампа на обеих платформах совпали дословно.

**Почему `hexdump` обязан открывать файл в `"rb"`.** Потому что его задача — показать **настоящие байты файла**, а текстовый режим их искажает: на Windows он свернул бы пару `0d 0a` обратно в один `0a`, и дамп `hi.txt` показал бы `48 69 0a` — три байта вместо четырёх реально лежащих в файле. Инструмент, который врёт про содержимое, бесполезен именно там, где он нужнее всего, — при разборе непонятного формата. Второй довод: у бинарных файлов вообще нет «строк», и любая трансляция для них — порча данных (§10.2.1). Ровно поэтому `file_size` из §10.2.1 тоже открывает файл в `"rb"`.

**Ответ:** прогон даёт
```
num.bin:
04 03 02 01
hi.txt:
48 69 0d 0a
```
(и, для файла из восьми `int`, четыре полные строки по 8 байтов — перенос строки каждые 8 байтов с корректным «хвостом»). Порядок `04 03 02 01` объясняется little-endian-представлением нашей платформы (§8.2.2): число `0x01020304` лежит в памяти младшим байтом вперёд, а `fwrite` копирует байты как есть — на big-endian-машине тот же код записал бы `01 02 03 04`. Байт `0d` в `hi.txt` появился из-за текстового режима записи: на Windows `'\n'` представляется парой `\r\n`, поэтому три символа `"Hi\n"` заняли четыре байта (§10.2.1); на Linux тот же файл содержит `48 69 0a`. Сам `hexdump` обязан открывать файл в `"rb"`, потому что показывать он должен реальные байты: в текстовом режиме библиотека свернула бы `0d 0a` обратно в `0a`, и дамп соврал бы о содержимом файла — а для бинарных данных трансляция и вовсе разрушительна.

**Вариант 2 (чтение блоками).** Вместо посимвольного цикла можно читать сразу по строке дампа — 8 байтов одним `fread`. Тогда `got` (число прочитанных байтов) само задаёт длину последней, неполной строки, и отдельная обработка «хвоста» не нужна.

```c
#include <stdio.h>

/* вариант 2: чтение блоками по 8 байтов — строка дампа за один fread */
void hexdump(const char *path)
{
    FILE *f = fopen(path, "rb");
    if (f == NULL) { perror(path); return; }
    unsigned char buf[8];
    size_t got;
    while ((got = fread(buf, 1, sizeof buf, f)) > 0) {   /* got — сколько реально прочитано */
        for (size_t i = 0; i < got; i++) {
            if (i > 0)
                printf(" ");
            printf("%02x", buf[i]);
        }
        printf("\n");
    }
    if (ferror(f))
        perror(path);
    fclose(f);
}
```

```
gcc -std=c17 -Wall -Wextra hexdump2.c -o hexdump2
./hexdump2
```

```
num.bin:
04 03 02 01
hi.txt:
48 69 0d 0a
eight.bin:
01 00 00 00 02 00 00 00
03 00 00 00 04 00 00 00
05 00 00 00 06 00 00 00
07 00 00 00 08 00 00 00
```

*Сравнение.* Вывод дословно совпадает, различается устройство. Посимвольный вариант проще всего и не требует буфера, но каждый байт проходит через вызов `fgetc`, а «конец строки каждые 8 байтов» приходится считать вручную — включая отдельную проверку хвоста после цикла. Блочный вариант читает файл порциями (одно обращение к потоку вместо восьми), а неполная последняя строка получается сама собой: `fread` вернул 3 — печатаем 3 байта. Плата — буфер и внимательность: `fread` возвращает 0 и при конце файла, и при ошибке, поэтому после цикла обязателен `ferror` (§10.1.3), иначе оборванное чтение будет неотличимо от нормального завершения. Для реального инструмента, который прогоняют по большим файлам, предпочтителен блочный вариант — с буфером в 4–64 КБ и печатью по 8 (или 16) байтов из него.
